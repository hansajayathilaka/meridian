# 10.1 — Ratchet HKDF-export for per-stream keys

**Phase:** 10 — File Transfer Stream · **Feature:** T09 · **Depends on:** — · **Status:** done

**User surface:** none — crate-local crypto primitive with no wiring yet (session.rs wiring is task
10.4; TUI surface for the feature lands in 10.11). No TUI surface applies to this task.

## Goal
Give `DoubleRatchet` a safe way to derive a per-stream symmetric key tied to one specific,
already-synchronized ratchet message, so stream types (starting with `mrd.file/1`) can encrypt bulk
data with fast symmetric AEAD instead of ratcheting per chunk — the mechanism `docs/api/stream-types-v1.md`
and the crypto-protocols skill already specify (`stream_key = HKDF(ratchet_export, info =
"mrd/stream/" ‖ type ‖ sid)`) but that does not exist in code yet.

## Scope
- **In:** a paired `encrypt_and_export` / `decrypt_and_export` API on `apps/crypto/src/ratchet.rs`'s
  `DoubleRatchet` (or an optional out-parameter on the existing `encrypt`/`decrypt` — implementer's
  call, pin whichever in the Outcome), tied to the one message naturally exchanged at stream OPEN
  (the `CtrlFrame::Accept` frame the substrate already sends/receives). Internally: derive `mk` exactly
  as `encrypt`/`decrypt` do today, use it for the real ciphertext, then additionally compute and return
  `HKDF(mk, info)` — **never `mk` itself** — to the caller. `info` is caller-supplied bytes (the file
  type/`session.rs` builds `"mrd/stream/" ‖ type ‖ sid` per the wire contract; this crate does not know
  about stream types or sids, it only takes an opaque `info: &[u8]`).
- **Out:** wiring this into `session.rs`'s Accept handling (task 10.4) or into any stream type (task
  10.6) — this task only adds the crate-local primitive and its own unit tests. No change to `encrypt`/
  `decrypt`'s existing behavior for callers that don't ask for an export (chat keeps working unchanged).
  No change to the AAD/wire format of the ratchet message itself (ADR 0016 untouched).

## Deliverables
1. `encrypt_and_export`/`decrypt_and_export` (or equivalent) on `DoubleRatchet` in
   `apps/crypto/src/ratchet.rs`.
2. Unit tests pinning the five invariants below.

## Risks / notes
Do **not** expose `rk`, `cks`, or `ckr` directly, or a general "export current chain state" method —
either would let a holder derive every future message key in that chain, destroying forward secrecy for
the whole session rather than just one stream (architect consult, this phase's planning). The export
must be scoped to exactly the one `mk` already consumed for the paired encrypt/decrypt call.

Invariants the test suite must pin (architect-recommended, this phase's planning):
1. **One-wayness** — the exported key must not permit recovering `mk`, `cks`/`ckr`, or `rk` (assert no
   code path returns the pre-HKDF value; HKDF's one-wayness is the security argument, but pin that the
   API surface never leaks the input).
2. **No skip-ahead leak** — exporting must not let a caller derive *other* message keys in the same
   chain; the export is scoped to exactly the one already-consumed `mk`.
3. **Determinism** — same synchronized ratchet state + same `info` on both peers → identical exported
   key (round-trip test: initiator encrypts+exports, responder decrypts+exports, assert equality).
4. **Zeroization** — the internal `mk` is zeroized immediately after HKDF-derivation, matching
   `zeroize_secrets`'s existing discipline; the returned exported key is caller-owned like any other
   secret (downstream callers are responsible for zeroizing their own copy — note this in the doc
   comment).
5. **FS/PCS non-regression** — the crate's existing ratchet FS/PCS harness must still pass unmodified;
   exporting must not weaken "compromising a later state doesn't recover earlier keys."

this crate; this task should accept `info: &[u8]` opaque and let task 10.12's spec-doc pin the concrete

## Tests
`cargo nextest run -p meridian-crypto` (new export-specific tests plus the existing FS/PCS harness
re-run to confirm no regression).

## Reviews
**security-reviewer** (mandatory — `apps/crypto/CLAUDE.md`: "the most security-critical crate in the
tree... route any change here through the security-reviewer agent"; this adds a new capability surface
on `DoubleRatchet`).

## Outcome
Added paired `encrypt_and_export`/`decrypt_and_export` methods on `DoubleRatchet`
(`apps/crypto/src/ratchet.rs`) rather than an out-parameter on the existing `encrypt`/`decrypt` — keeps
the chat path's signatures/behavior byte-identical (zero regression risk) and makes the export intent
explicit at call sites. Both derive `mk` exactly as `encrypt`/`decrypt` (sharing a new crate-private
`decrypt_core`/`try_skipped` path so the skip-ahead/DH-ratchet logic isn't duplicated), use it for the
real AEAD operation, then compute `HKDF(mk, info)` via a crate-private `export_and_zeroize` helper with a
fixed, domain-separated `EXPORT_SALT` — never returning `mk` itself, `cks`, `ckr`, or `rk`, and no general
"export current chain state" method exists. `info: &[u8]` is fully opaque to this crate; the concrete
`"mrd/stream/" ‖ type ‖ sid` encoding stays owned by callers per the task's own `TODO: confirm`, to be
pinned by task 10.12.

Five new tests pin the required invariants (one-wayness, no skip-ahead leak — including the tricky
out-of-order/skipped-key decrypt path, determinism/symmetry between encrypt and decrypt sides,
zeroization, and FS/PCS non-regression via the crate's existing unmodified harness).

security-reviewer (mandatory) returned **PASS**, independently re-deriving each invariant against the
actual code rather than trusting the implementer's claims (confirmed the one-wayness/skip-ahead/
determinism/capability-surface/non-regression properties hold, and confirmed the five new tests are
non-vacuous). It flagged one non-blocking should-fix, closed in a same-task follow-up commit before this
task was marked done: the transient `mk` local in `encrypt`/`encrypt_and_export`/`decrypt_core`/
`try_skipped` was zeroized via a single explicit call late in each function, which an early `?`-return
on AEAD/header-seal failure (the routine adversary-triggered path) could skip. Fixed by wrapping `mk` in
`zeroize::Zeroizing<[u8;32]>` at each `kdf_ck` call site instead, so it clears via `Drop` regardless of
return path; also added a `Drop` impl for the internal `Skipped` struct (its `mk` field had the same gap
on removal/eviction) rather than wrapping its field type directly, since that would have broken
`Skipped`'s existing `Serialize`/`Deserialize` derive needed for persisted session state. All 4 new
task-10.1 tests plus the crate's full existing suite (23 tests total) stayed green throughout, independently
re-run after the hardening fix; `cargo clippy -p meridian-crypto --all-targets -- -D warnings` clean.
