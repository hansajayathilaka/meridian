# 4.49 — Persist the accepted sender's intro into `history.jsonl` (fix for 4.48's fifth defect)

**Phase:** 4 — Verification & Trust + Terminal TUI Client · **Feature:** T17 — Terminal TUI Client (gap closure, fix for 4.48's fifth defect) · **Depends on:** 4.42, 4.44 · **Status:** pending

## Goal
Make an accepted message request's intro message survive into the responder's own transcript: today
`worker::run_accept_request` writes `sessions.bin`/`trust.bin`/`contacts.json` on accept but never
`history.jsonl`, so the very first message of every accepted conversation is silently, permanently
absent — live and after restart. This closes the fifth defect the phase's exit gate found (task 4.48),
the remaining blocker on T17's own acceptance criterion "restart restores contacts, **history**, and
ratchet state … local dedup by message id."

## Pre-code consult assessment — recorded here, not deferred
**No mandatory pre-code architect/security-reviewer consult is required.** Compared against why 4.40 and
4.42 needed one: 4.40 extended decrypted key material's in-memory residency for the whole session
lifetime — a real security-posture question with no existing precedent. 4.42 faced a structurally forced
choice between severable shapes, decided by an architect consult because `TrustStore::observe`'s
`hint == ""` output made one candidate workaround provably impossible — a genuine design decision with
real alternatives. This task has neither.

4.48's own Status section posed the question as a live choice between two shapes: (1) write inside
`run_accept_request` itself, or (2) a follow-up `Effect::PersistHistory` dispatched by `App` after
`AcceptRequest` completes, mirroring how `App::apply_accepted_request` reconciles other side effects.
Reading the actual code resolves this, not just favors one option:

- **Every existing `App`-side reconciliation method for a completed effect is purely in-memory.**
  `apply_accepted_request`, `apply_added_contact`, `apply_loaded_history`, and `apply_rejected_request`
  (`apps/tui/src/app.rs:2212-2422`) only ever replay state the worker *already made durable* — none of
  them triggers a **new** write-effect as a side effect of reconciling a completion. Shape 2 would
  introduce a "completion triggers a fresh write" mechanism with no precedent anywhere in this crate,
  and it would open a real durability gap: the accept becomes durable in `trust.bin`/`contacts.json` at
  the end of `run_accept_request`'s single async call, then the intro write would only happen later, as
  a *second*, separately-dispatched effect — a crash in between leaves the peer accepted and reachable
  but with no way to ever recover the discarded `MessageRequest.intro` (it is removed from
  `pending_requests` the moment `accept_request` runs and lives nowhere else).
- **Shape 1 needs zero new mechanism.** `run_accept_request` already writes three sealed documents
  (`sessions.bin`, `trust.bin`, `contacts.json`) inside one function, under the one `(store, handle)`
  pair it already holds (`worker.rs:1245-1288`) — exactly the same "one function performs every write
  this decision requires" pattern `run_add_contact` also uses. Adding a fourth call to
  `crate::store::history::append` — the same writer `worker::run_persist_history` already calls
  identically (`hex::encode(request.peer_pubkey)` + `(store, handle)`, `worker.rs:1773-1782`) — extends
  that pattern by one line's worth of new call, not a new architecture.
- **The "where does `mid` come from" question 4.48 flagged as the crux is already answered by the
  existing type**, not an open design choice: `MessageRequest.intro: ChatContent` is either
  `ChatContent::Text { id, body }` or `ChatContent::Receipt { ack }` (`apps/envelope/src/chat.rs:18-30`
  — only two variants exist today). The ordinary inbound-Text handler
  (`worker::process_inbound_delivery`, `worker.rs:2273-2306`) already mints its `HistoryEntry.mid` from
  exactly this same `id` field (`mid: hex::encode(id)`) — the intro carries the identical wire-level id
  the sender minted, with no new id-generation or effect-field-widening needed.

This is much closer to 4.46's situation ("the fix shape is an almost line-for-line mirror of an existing,
already-reviewed precedent … There is no ADR-adjacent identity or residency question here") than to
4.40's or 4.42's. Ordinary post-diff `reviewer`/`test-engineer` sign-off (below) is sufficient. **If
implementation reveals a genuine design choice this planning pass did not anticipate, stop and flag it
explicitly rather than deciding silently** — but this planning pass, reading `run_accept_request`,
`MessageRequest`, `ChatContent`, and `history::append` directly, found none.

## Scope
- **In:**
  1. `worker::run_accept_request` (`apps/tui/src/worker.rs:1245-1288`): capture the actual
     `Option<MessageRequest>` `chat.accept_request(&request.sender_ik)` returns (today collapsed to
     `.is_some()` at line 1254 and discarded) instead of only its presence. On the genuine, fresh-accept
     branch (`Some(request_taken)` — **not** the `pin_still_owed`-only retry branch, which has no
     `MessageRequest` to source content from: `chat.accept_request` already returns `None` there, since
     the entry was removed from `pending_requests` by the first, partially-successful attempt), and
     **after** the existing `trust.bin`/`contacts.json` writes succeed: if `request_taken.intro` is
     `ChatContent::Text { id, body }`, build a `HistoryEntry` with the exact same shape the ordinary
     inbound-Text handler already builds (`v: crate::store::history::CURRENT_VERSION, mid:
     hex::encode(id), dir: Direction::In, ts: now, stream: "mrd.chat/1", body: body.clone(), state:
     MessageState::Received` — reusing the `now` already computed earlier in the function for
     `trust.observe`, since `MessageRequest` carries no original-arrival timestamp to source a more
     precise one from) and call `crate::store::history::append(&hex::encode(request.sender_ik), &entry,
     store, handle)` — the same writer, the same call shape, `worker::run_persist_history` already uses.
     If `request_taken.intro` is `ChatContent::Receipt { .. }` (the only other variant `ChatContent` has
     today — reachable only from a degenerate/adversarial first envelope, since a receipt as a *first*
     message makes no protocol sense, but the gate in `open_inbound_gated` fires before content-type is
     inspected, so it is type-reachable), **skip the history write** — do not invent a receipt-shaped
     history entry, do not error. This mirrors the existing display-layer precedent
     (`screens/requests.rs::intro_summary`, `"(not a text message — a delivery receipt)"`) rather than
     inventing new handling for a case the crate already has an answer for.
  2. Update `run_accept_request`'s own doc comment to describe this fourth write, in the same style it
     already documents the trust/contacts writes, and to name the narrowed partial-failure window this
     introduces (see Risks below) — extending, not replacing, its existing partial-failure discussion.
  3. Resolve `AcceptRequestRequest`'s own doc comment (`apps/tui/src/app.rs:684-703`), which explicitly
     deferred "the intro → transcript question" to a future task, citing exactly this shape
     (`Effect::PersistHistory` → `crate::store::history`) as the eventual mechanism. Replace the
     "deferred on purpose" paragraph with one recording this task's resolution, mirroring how 4.42 itself
     replaced an earlier version of that same paragraph.
  4. Remove (or convert to a plain assertion that production already did it — implementer's call,
     documented) the hand-rolled `persist_entry(...)` workaround in
     `apps/tui/tests/live_session_e2e.rs` (`AcceptRequest` call at ~617-651, helper at ~714-744) — now
     redundant, since production performs the equivalent write.
- **Out:** the `^N`/`^V` doc-only keybinding nit 4.48 also found (unrelated root cause; stays in
  [phase-4/README.md](./README.md#tasks-todo)'s "Findings with no task yet," not folded in here — mirrors
  the 4.46/4.47 split); the already-tracked `run_accept_request` partial-failure repair-action follow-up
  for a missing `contacts.json` row (this task names a narrower, history-only analog — see Risks — but
  does not fix either; fold the history-only analog into that same tracked follow-up rather than opening
  a third, freestanding partial-failure task); Shape B (`OpenChat`-style transition, already severed by
  4.42, unrelated); any change to `ts` semantics beyond using accept-time as the best available
  approximation (no design doc tracks original-request-arrival-time, and none is invented here); any new
  wire type, protocol, or crypto change; widening `ChatContent`/`MessageRequest`'s own schema; the
  interleaving-gap defect class 4.42/4.46 each fixed generically (`apply_accepted_request`'s stack walk)
  — this task's disk write is independent of which screen is on top, and 4.44's already-built
  `apply_loaded_history` dedup-by-`mid` handles in-memory reconciliation regardless of interleaving, so
  nothing further is needed here.

## Risks / notes
- **A narrower, but real, partial-failure window survives, named honestly rather than fixed.** The
  history write is placed *after* `save_trust`/`contacts::save` succeed, gated on `accepted` only. If
  `history::append` itself then fails, the function returns `Err`, and a client retry finds
  `accepted == false && pin_still_owed == false` (the pin is already complete) — the same early
  `Ok(None)` return the existing guard already takes for a fully-completed retry, per its own doc
  comment's derivation. The retry never re-attempts the history write: the peer stays durably trusted and
  fully reachable in the UI, but the intro is then permanently missing, even though nothing else about
  the accept is broken. **Do not widen the guard to cover this** — same "do not resurrect a case that
  should not self-heal automatically" discipline the function's own existing doc comment already states
  for the analogous `contacts.json`-row-missing case. Name this explicitly as a narrower analog of that
  already-tracked repair-action follow-up (`docs/tasks/phase-4/README.md`'s "Findings with no task yet")
  rather than opening a third, freestanding partial-failure task; the review round should confirm whether
  to fold it into that follow-up's own description.
- **`ChatContent::Receipt` as a first-contact intro is a degenerate, not a normal, case** — handle it
  type-safely (skip, don't error, don't invent), mirroring `intro_summary`'s existing precedent, rather
  than treating it as unreachable and `unwrap`-ing or panicking.
- **`chat_state_lock` scope is unchanged.** The history write is a separate sealed document from
  `sessions.bin`/`trust.bin`/`contacts.json`, not covered by that mutex — mirrors how
  `handle_persist_history`'s existing `Effect::PersistHistory` handler does not take that lock either. Do
  not introduce a new lock and do not widen `chat_state_lock`'s existing scope to cover it.
- **`ts` is accept-time, not original-request-arrival-time** — `MessageRequest` carries no arrival
  timestamp anywhere, so there is nothing more precise to source from. This is a deliberate, stated
  approximation (not a `TODO: confirm` — no design doc claims otherwise, and every other worker-side
  write in this crate already timestamps at write-time, not at an idealized original-event time).
- **Do not touch `TrustStore::can_send`'s fail-open semantics, `verification-ux.md`'s wording, or any
  trust-state transition** — this is a history-write gap, not a trust decision; unrelated to this fix
  entirely, restated only as a guardrail.
- **Definition of Done gate 9:** no new TUI surface — this repairs existing T17 core write path
  (Requests → accept → history), the same "intrinsically satisfied" reasoning 4.42/4.44/4.46 already
  used. No `SurfaceRegistry` registration is added.
