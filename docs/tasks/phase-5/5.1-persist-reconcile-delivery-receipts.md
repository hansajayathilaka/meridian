# 5.1 — Persist and always-reconcile Sent→Delivered receipts

**Phase:** 5 — Review of Phase 4 · **Feature:** review fix (F1) · **Depends on:** — · **Status:** done

## Goal
Make the Sent/Delivered message-status indicator (landed out-of-band in PRs #71/#72, outside the
tracked-task pipeline) actually correct: a delivery receipt must update the sender's transcript
regardless of which screen is currently on top of the stack, and the transition must survive a restart.

## Scope
- **In:** `App::handle_inbound`'s `InboundEvent::Receipt` arm (`apps/tui/src/app.rs`, currently only
  applies the transition when the exact `Screen::Chat` for that peer is `self.screens.last_mut()`);
  `chat::apply_receipt` (`apps/tui/src/screens/chat.rs`); persisting the `Delivered` state so a reload
  from `history.jsonl` doesn't silently revert it to `Sent`.
- **Out:** Any change to the ack/receipt wire protocol itself (out of scope — this is a client-side
  reconciliation bug, not a protocol gap). Retrying receipts that never arrive (acks are one-shot by
  design; not this task's concern).

## Deliverables
1. `App::handle_inbound`'s Receipt arm reconciles into the live screen stack the same way
   `apply_accepted_request`/`apply_added_contact` do for other inbound events — walk the stack and
   update the matching `ChatState` wherever it lives, not only when it's on top.
2. The `Delivered` transition is persisted (a small update-in-place write, not a full history rewrite),
   so `Effect::LoadHistory` reflects it after a restart.
3. A new App-level test (new file or extension of `apps/tui/tests/inbound_delivery.rs`) that opens
   `Screen::Chat` for a peer, sends a message, navigates away, dispatches a real
   `AppEvent::Inbound(InboundEvent::Receipt{..})`, navigates back, and asserts the double-tick renders —
   plus a restart-persistence variant.

## Risks / notes
Do not conflate this with F10 (5.10) — that's about `PersistHistory`'s own write-durability window on
shutdown; this task is about the receipt *reconciliation logic* being reachable at all regardless of
screen state, plus persisting the resulting status. `apply_receipt`'s existing unit test
(`screens_chat.rs:438`) drives `ChatState` directly and must keep passing unchanged; it is not sufficient
coverage on its own (it can't catch a routing bug), which is exactly what F1 found.

## Status
**Done.** `App::handle_inbound`'s `InboundEvent::Receipt` arm now walks the full `self.screens` stack —
the same shape `apply_accepted_request`/`apply_added_contact`/`apply_loaded_history` already use — instead
of only updating when the matching `Screen::Chat` is topmost, closing F1's routing gap. A new
`Effect::PersistReceipt` (mirroring the existing `PersistHistory` request/effect/handler triple) is
dispatched **unconditionally**, regardless of whether a matching screen was found, and persists the
transition via `history::mark_delivered`/`mark_delivered_at` — a targeted read→flip-one-field→reseal-write
against `history.jsonl`, reusing the same sealing primitives every other history write already uses (no
new at-rest exposure). `chat::apply_receipt` itself and its existing unit test (`screens_chat.rs:438`) are
byte-for-byte unchanged.

New coverage in `apps/tui/tests/inbound_delivery.rs` drives the real `App::update`/`AppEvent::Inbound`
entry point and the real `worker::dispatch` path (not internals directly): a receipt reconciling into a
non-topmost `Screen::Chat`, a restart-persistence round trip via `worker::dispatch` + `load_or_default`,
a receipt for a peer with **no** `Screen::Chat` open at all (added after review — confirms the effect still
persists even with zero matching screens), and an unknown-`mid` receipt asserted byte-for-byte unchanged on
disk (added after review — confirms `mark_delivered_at`'s documented no-op contract holds at the disk
layer, not just in memory).

No doc-sync needed: `tui-client.md`'s existing message-state schema (`sent | delivered | ...`) already
documented the intended contract this task fixes an implementation gap against; nothing about the
documented behavior itself changed.

### Review round
`reviewer` (combined architect + code-reviewer) — **PASS**, no blocking issues. Architect confirmed the
stack-walk genuinely extends the existing reconciliation pattern (no divergence) and that
`Effect::PersistReceipt` fits ADR 0021's sealed-write model with no new architectural seam. Code-reviewer
confirmed correctness of the stack-walk (only one `Screen::Chat` can ever be live at a time, so first-match
is safe), the sequential (non-racing) effect-dispatch loop, and that the new tests exercise the real
routing path rather than calling internals directly.

`test-engineer` — **PASS with two should-fix gaps, both closed**: independently confirmed the new tests
exercise the real bug shape (not a shortcut), then flagged the same two coverage gaps code-reviewer
separately raised (no-open-chat-screen case; unknown-`mid` persistence at the disk layer). Both closed with
two additional tests before sign-off; full suite reconfirmed green (64 tests across `inbound_delivery`,
`accept_to_chat`, `screens_chat`), `cargo fmt`/`cargo clippy -D warnings` clean.
