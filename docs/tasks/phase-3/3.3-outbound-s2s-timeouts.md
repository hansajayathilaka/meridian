# 3.3 — Bound every outbound s2s I/O exchange

**Phase:** 3 — Review of Phase 2 · **Feature:** review fix (F3, **blocking**) · **Depends on:** 3.2 · **Status:** done

## Goal
A black-holed partner must not hang the originating client's WebSocket session or leak a pinned task
plus TLS link.

## Scope
- **In:** a connect timeout on `link::dial`'s `TcpStream::connect` (L355); a timeout on the TLS
  handshake + `exchange_hello`; a per-exchange timeout on `fetch_foreign_bundle`'s (L118) and
  `reachable_foreign`'s (L429) reply receives; surfaced as `fed_unreachable`; cancellation of the
  awaited work when the client ws session drops.
- **Out:** `ROUTE_REPLY_GRACE`'s value (3.20); the inbound accept path (3.2); link reuse (3.7).

**Why this is split from 3.2/F2:** different code paths (dial-side vs accept-side), different threat
(partner-induced local resource leak vs unauthenticated remote DoS), different tests, independently
revertable. They share only the `with_deadline` helper 3.2 introduces.

## Deliverables
1. `apps/rendezvous/src/federation/link.rs` — `dial` reads a `FederationTimeouts`;
   `tokio::time::timeout` around connect, TLS, and `exchange_hello`; new `LinkError::Timeout { phase }`.
2. `apps/rendezvous/src/federation/outbound.rs` — every reply receive awaited under a per-exchange
   timeout; mapped to `FED_UNREACHABLE`.
3. `apps/rendezvous/src/config.rs` — `federation.connect_timeout_ms`,
   `federation.request_timeout_ms` (**`TODO: confirm` defaults** — proposed 5_000 / 10_000).
4. `apps/rendezvous/tests/federation_timeouts.rs` — a listener that accepts TCP and never handshakes
   → fetch returns `fed_unreachable` within bound; a peer that completes `FedHello` then never
   replies → same; the link gauge / task count returns to baseline after the client disconnects
   (**no leak**).

## Risks / notes
- Must not introduce a **timing oracle** distinguishing "policy denial" (3.1) from "timeout" — a
  denial is immediate and a timeout is not, which is already observable; keep the client-visible
  codes as 2.9 defined them and note the residual rather than papering over it.
- Cancellation-on-disconnect is the part most likely to be asserted vacuously; prove the task count
  actually drops.

## Outcome
`dial()` now takes a `FederationTimeouts { connect, request }` and wraps `TcpStream::connect` under
`connect`, and the TLS handshake + `exchange_hello` each under their own independent `request`
deadline, via a `dial_phase` helper built on 3.2's `with_deadline`. Every outbound reply-receive in
`fetch_foreign_bundle`/`reachable_foreign`, and (after a review follow-up, see below)
`route_foreign`'s own outbound send, are bounded the same way via `with_request_deadline`, folding
into the existing `LinkError::Dial`/`FED_UNREACHABLE` path 2.9 already defined — no new
client-visible error shape. New `federation.{connect_timeout_ms,request_timeout_ms}` config knobs
(**`TODO: confirm`** — 5_000/10_000, the task file's proposed values, not grounded in an existing
doc), fail-closed validated.

**Two-round review, both closed:**
1. Combined `reviewer` agent — found one **blocking** correctness gap: `route_foreign`'s own
   outbound `send_frame` (the call carrying an actual authenticated user's routed envelope) was the
   one call site in `outbound.rs` the original diff missed wrapping — exactly the failure mode this
   task exists to close. Fixed in a follow-up commit: wrapped under the same `with_request_deadline`
   pattern as the other two call sites. A live-socket regression test for this specific call site
   turned out to be vacuous in this environment (a single `route_foreign` frame is well under a
   fresh socket's local send-buffer size, so `write_all` doesn't block regardless of peer behavior
   or the fix's presence — confirmed by running the same live-socket scenario against both pre- and
   post-fix code and observing identical pass/fail either way); replaced with a source-level
   structural test pinning the exact call site's wrapping, plus a deterministic unit test proving
   `with_request_deadline` itself bounds a never-resolving future. A second, narrowly-scoped
   re-review verified this fix independently (confirmed the structural test's boundary search
   correctly isolates `route_foreign`'s body, confirmed the "live-socket test would be vacuous"
   claim empirically, and raised one non-blocking documentation-precision nit — since fixed — about
   distinguishing "no socket-config hook exists to make this testable" from "no payload could ever
   block").
2. **test-engineer mutation-check** — independently verified all three original tests are
   load-bearing (not vacuous) by neutering the timeout wrapping and confirming (a)/(b) then fail,
   and specifically interrogated whether test (c)'s no-leak assertion (`Metrics::
   connections_active()`) measures the right resource — traced `ws.rs`'s single-task-per-connection
   `serve` loop to confirm the gauge is causally gated on exactly the blocked task the Goal
   describes (not some unrelated signal), then confirmed by mutation that the test correctly stays
   red when the leak is real.

**Ratified design decisions** (surfaced by review as needing explicit sign-off rather than a silent
pass, per the Definition of Done's "no invented/no silently-descoped design" bar):
- **"Cancellation of the awaited work when the client ws session drops" (Scope) was delivered as
  bounded-eventual cleanup, not reactive cancellation.** `ws::serve`'s single-task-per-connection
  loop is strictly sequential and cannot observe the client socket while blocked inside a handler
  (confirmed: test (c) shows the blocked resource is *not* freed at t+150ms after a client abort,
  only once the deadline elapses). True reactive cancellation would require restructuring that loop
  around `select!` against the client stream — a materially larger, riskier change than "add
  timeouts," and out of scope for this task. **Accepted as sufficient**: the Goal ("must not hang...
  or leak... forever") is genuinely satisfied by a bound of `connect_timeout_ms +
  request_timeout_ms` (or ×2 for a send+recv pair) even without reactive cancellation. Reactive
  cancellation is **not** spun out as a new task — no user-visible or security harm has been
  identified from the bounded-vs-reactive gap (worst case is a foreign partner's own connection
  budget being held slightly longer, not a client-facing hang) — but this note is the record that
  the interpretation was reviewed and deliberately accepted, not silently substituted.
- **The two timeout phases (`connect` vs `request`) are independent, not a single shared budget**,
  despite the Deliverables text's "a timeout on the TLS handshake + `exchange_hello`" reading
  ambiguously as one combined budget. Chosen because tracking remaining budget across two sequential
  async operations is meaningfully more complex than two independent deadlines, at the cost of a
  larger worst-case latency (documented in `FederationTimeouts`' doc comment: with defaults, a
  single `dial` can take up to `connect + 2×request` ≈ 25s, and a full `fetch`/`route` up to
  `connect + 4×request` ≈ 45s before a client sees `fed_unreachable`).
- **Timing-oracle residual, updated from "no new residual" to an explicit note**: this task's two
  independent deadlines (`connect_timeout_ms` vs `request_timeout_ms`) do add a finer-grained
  wall-clock bucketing than existed before — pre-3.3, dial failures had no bound at all (noisy
  OS-default TCP timeouts); post-3.3, a client can distinguish "unreachable at the TCP layer" (fast,
  ~`connect_timeout_ms`) from "reachable but application-layer silent" (slower, further bounded by
  `request_timeout_ms`) with more determinism than before. This is a refinement of the pre-existing,
  already-accepted "policy denial is fast, timeout is slow" residual from task 3.1 — still no
  plaintext/contact-graph/identity leakage, low severity, not blocking — but is recorded explicitly
  here per the task's own Risk note ("note the residual rather than papering over it"), rather than
  left as only an implicit doc-comment aside.
