# 4.51 — Root-cause and fix the file-backed responder's blocking-scrypt hazard (delivery non-determinism + the known interactive-latency finding)

**Phase:** 4 — Verification & Trust + Terminal TUI Client · **Feature:** T17 — Terminal TUI Client (gap closure, fix for 4.50's sixth defect) · **Depends on:** 4.50 · **Status:** done

## Goal
Close the sixth exit-gate defect: first-contact message delivery to a file-backed responder from an
OS-keystore initiator is non-deterministically silent or very slow (70 s–260 s, reproduced ~15/15 trials
by 4.50's independent run). Do this by actually finishing the investigation 4.50's reviewer left open
(root cause corroborated as *plausible*, not *closed*) before choosing a fix shape, then implement
whatever that investigation points to — and, if it generalizes cleanly, close the same-class,
already-known `run_mark_verified`/`run_set_petname` latency finding (4.43's own recorded, deliberately
deferred follow-up) in the same pass rather than as a second patch.

## Pre-code consult assessment — recorded here, gated on this task's own investigation, not skipped
**This is a two-phase task with a conditional consult gate, decided in-task before Phase 2's code
lands — mirroring 4.35's and 4.9's own precedent for an in-task (not plan-time) consult**, because this
planning pass genuinely cannot know which fix shape the investigation will produce, and the instruction
that created this task is explicit: let the investigation decide, do not presume the fix shape at plan
time.

**Phase 1 (investigation — Deliverables 1–4) needs no consult.** It reads, measures, and instruments;
it changes no code and touches no key material's residency.

**Phase 2 (the fix) is gated by a binding decision rule, to be applied and recorded in this task's own
Status section before any Phase-2 code lands:**
- **If the investigation concludes the fix is `spawn_blocking`-only** — wrapping the existing
  synchronous `decrypt_seed()`-calling operations (`process_inbound_delivery`'s `use_key`/`derive_key`
  calls, and — see Scope point 2 below — `SignalingClient::handshake`'s `sign()` call as invoked from
  `run_inbound_loop`) in `tokio::task::spawn_blocking`, with **no new caching, no new residency, the
  same seed decrypted the same number of times at the same call sites, freed at the same points as
  today** — **no consult is required.** This is a pure execution-context change, not a security-posture
  change: it does not touch anything either 4.40's or 4.43's consults reasoned about. Mirrors 4.43's own
  reasoning for why its narrow shape needed no new sign-off ("reduces, does not extend, residency" — a
  `spawn_blocking` wrap reduces *nothing* about residency, but it also doesn't extend anything, which is
  the same "no new exposure class" test 4.43 applied).
- **If the investigation concludes the fix requires caching an already-unwrapped seed** (a
  `MemorySecretStore`-shaped object) for `InboundHandoff::store`'s lifetime (making per-delivery signing
  in `run_inbound_loop` scrypt-free) and/or widening `OnboardingSession::live_store` the same way for the
  interactive contacts/trust/chat handlers — **a mandatory security-reviewer delta sign-off is required
  before implementation.** This is not a new judgment call: 4.43's own "The boundary" section already
  named *both* of these exact widenings by description ("putting the `MemorySecretStore` into
  `live_store`" / "handing it to `run_inbound_loop`") and reserved them for "their own task… gated on a
  security-reviewer delta sign-off" — this task is that task, for both. Given the inbound-loop widening
  specifically would extend raw-seed residency to the **full process lifetime** (unlike 4.43's own
  bulk-signing cache, which is dropped after ~50 ms), a materially larger residency window than either
  4.40's or 4.43's consults ever evaluated, **architect input is also required alongside
  security-reviewer** — treat this as a full consult mirroring 4.40's dual-lens shape, not a lighter
  "delta" review alone. **Do not implement first and consult after** (4.40's own binding rule, restated).
- **If the investigation points to a third shape neither bullet above anticipates** (e.g., a runtime
  scheduling change with no residency question at all) — the implementer must record, explicitly and in
  writing in this task's Status section, why that shape does or does not trip either bullet above, before
  proceeding. Silence is not permitted.

## Risks / notes
- **`tokio::task::block_in_place` is not a legal alternative to `spawn_blocking` here.** It panics when
  called from a `current_thread` runtime — and `apps/cli/src/main.rs::runtime()` builds exactly that
  flavor (`tokio::runtime::Builder::new_current_thread()`, confirmed). Do not reach for it.
- **`spawn_blocking`'s closure must be `'static + Send`.** Every call site this task's investigation
  names (`process_inbound_delivery`, `SignalingClient::handshake`) currently receives `&dyn SecretStore`
  by borrow, not by owned/`Arc` value — wrapping requires either an owned/`Arc`-cloneable store or
  restructuring the call boundary. This is a real mechanical question the fix phase must resolve, not
  hand-wave; if it forces a wider-than-expected signature change, name that explicitly rather than
  quietly narrowing which call sites get fixed.
- **Do not conflate this task's fix with 4.40's `live_store` or 4.43's `bulk_signing_store`.** If a cache
  is chosen (consult-gated, see above), it must be a *new*, explicitly-scoped and explicitly-bounded
  structure — not a silent widening of either existing cache's documented contract, both of which their
  own doc comments describe precisely and both of which other code currently depends on staying as
  documented.
- **Never log, `Debug`-print, or persist any newly introduced store/cache/seed material.** Follow the
  existing redaction precedents (`OnboardingSession`'s hand-rolled `Debug`, `InboundHandoff`'s "no `Debug`
  impl at all, by construction" pattern). A new type needs its own redaction coverage if it's
  `Debug`-reachable.
- **Describe the mechanism accurately.** `run_inbound_loop`'s `while let Ok(deliver) = client.next_deliver().await`
  is a blocking `await`, not a busy-poll loop — the 4.50 reviewer already corrected a "polling"
  mischaracterization once; don't reintroduce it.
- **`chat_state_lock()` discipline must not be affected** by any `spawn_blocking`/caching change inside
  `process_inbound_delivery` — if that function's structure changes, confirm explicitly that the lock is
  still held across the whole load-open-save sequence, exactly as its own doc comment requires.
- **If in-sandbox packet-capture/strace tracing isn't available**, say so and record what could and
  couldn't be checked (Scope point 4) — do not guess at a below-the-app-layer mechanism and present it as
  confirmed.
- **Definition of Done gate 9:** no new TUI surface expected — this is a reliability/perf fix, state
  explicitly, mirroring 4.40's/4.43's own "no user surface" notes — unless the investigation surfaces a
  case where a visible "connecting/unlocking" status affordance is a genuinely necessary part of the fix
  (not required by default); if one is added, it must register through the TUI extension registry, never
  by editing the TUI core.

| call site | when it fires | measured cost | frequency |

descriptor.save()`, `apps/tui/src/worker.rs` line ~431). Without it, `worker::resolve_server` finds
neither `config.toml`'s `[account] server` nor `descriptor.server`, `inbound_handoff`'s `Effect::Unlock`
arm's `resolve_server(&descriptor).ok()?` fails, and the whole match arm returns `None` — **the
persistent inbound loop silently never starts at all**, a *different*, more severe failure mode than a
slow connect (this is the exact `TODO: confirm` `inbound_handoff`'s own doc comment already flags: "no
design doc this task read specifies whether that should instead be a visible, named failure"). This is a
**test-harness artifact of headless CLI setup bypassing the interactive onboarding flow's own
`server`-persisting write, not a defect in the code path 4.50's own live onboarding-driven trials
exercised** — 4.50's own methodology always drove real interactive onboarding for both peers, so this
exact mechanism cannot be what 4.50 hit. Fixed in the driver by setting the documented
`MERIDIAN_TUI__ACCOUNT__SERVER` config-env-var override for the file-backed account (functionally
equivalent to what onboarding's own write achieves, without needing to drive the full onboarding UI for
every trial) — every trial after that fix reached `Connected` in ~4 s. Named honestly here because
distinguishing a driver bug from a real defect, before reporting anything, is this project's own
standing discipline (4.41's own "two bugs in the driver itself" precedent).

### Deliverable 4 — reconciled wall-clock accounting for the 70 s–260 s range

**What is confirmed, mechanistically and live:** six synchronous, non-`spawn_blocking`'d `decrypt_seed()`

1) — ~7.7 s of aggregate blocking, during which every other task on the process (rendering, other
effects, this very loop's next envelope) is frozen. This is a real, mechanistically well-grounded
reliability hazard independent of whether it explains the full reported range.

**Correction, recorded honestly (reviewer-caught):** this task's own first landing wrapped only **four**
of these six calls (`process_inbound_delivery`'s three plus `handshake`'s `sign()`), leaving `run_unlock`'s
own `export_seed()` and `inbound_handoff`'s `unwrap_keyfile_for_bulk_signing` `export_seed()` — the

prose overclaiming "is what this task's fix closes" for all six when only four were actually wrapped, and
this Status section (see the now-corrected Deliverable 5 below) records the fix for the remaining two

**What could not be reproduced or fully explained here:** across 12 reconnect-storm trials (Deliverable 3)
plus a further 15 trials total run in this investigation (properly configured, once the driver bug above

further ~4 s, with zero reconnects and zero stalls beyond the one driver-bug trial already excluded and
explained above.** The confirmed ~7.7 s mechanism does not, on its own, reach 70 s–260 s, and this task
could not reproduce a genuine multi-minute stall in this sandbox once the driver artifact was corrected.
**Named honestly, mirroring 4.50's own reviewer's "root cause not fully closed" discipline**: either (a)

(plausible — the ~1.3 s/unwrap figure is CPU-speed-dependent, and a slower or more contended machine would

happen to trigger (an OS/sandbox-level TCP stall under a genuinely stalled reader, which 4.43's own
Deliverable-2-equivalent caveat already flagged as a candidate and which this task cannot rule in or out

this sandbox (confirmed: `strace` was used for an unrelated diagnostic above), but a below-the-app-layer
trace of a genuinely non-reproducing intermittent condition was judged not to be a productive use of this
task's remaining scope once the confirmed mechanism was identified, real, and fixable regardless of
whether it explains 100% of the originally-reported range. Recorded as an open question for a future task
if the seventh exit-gate attempt (4.52) reproduces the full range again after this fix lands.

### Deliverable 5 — the fix-shape decision and the fix itself

**Binding decision applied:** the investigation's own findings (Deliverables 1–4) point to a pure
execution-context change — wrap the existing synchronous `decrypt_seed()`-calling operations
(`process_inbound_delivery`'s `use_key`/`derive_key` calls, and `SignalingClient::handshake`'s `sign()`
call as invoked from `run_inbound_loop`) in `tokio::task::spawn_blocking`, **no new caching, no new
residency, the same seed decrypted the same number of times at the same call sites, freed at the same
points as today**. Per this task's own "Pre-code consult assessment," this trips the **first** bullet
(`spawn_blocking`-only) — **no consult required.** Recorded here, before implementation, per that
section's own binding sequencing rule.

**The fix, as landed:**
- `apps/tui/src/worker.rs::InboundHandoff::store` and `run_inbound_loop`'s own `store` parameter widened
  from `Box<dyn SecretStore>` to `Arc<dyn SecretStore>` — the mechanical widening
  `spawn_blocking`'s `'static + Send` closure bound forces (`&dyn SecretStore` cannot satisfy it; a
  cloned `Arc` can, and `SecretStore: Send + Sync` already). Named explicitly here per this task's own
  risk note, not quietly narrowed away. `InboundHandoff::bulk_signing_store` (the `MemorySecretStore`
  path) is untouched — it never called `decrypt_seed()` at all, so it needed no `spawn_blocking` wrap.
- `process_inbound_delivery`'s whole `load_chat` → `chat.open_inbound` → (auto-ack `seal_outbound` +
  routing-hint lookup) → `save_chat` sequence now runs inside one `tokio::task::spawn_blocking` call.
  **Ordering note, named explicitly per this task's own Risks section:** `save_chat` now runs *before*
  the auto-ack's best-effort `client.route_with_hint` (previously after, inside the `Text` match arm) —
  a strictly safer order (durable state persisted before an already-best-effort network send whose
  failure was already silently swallowed both before and after this change), not a weaker one.
  `chat_state_lock`'s guard (`_chat_guard`) still spans the *entire* sequence — both the blocking closure
  and the network route after it — exactly as that lock's own discipline requires; confirmed explicitly,
  not assumed.
- `apps/signaling/src/client.rs` gained an **additive** `SignalingClient::connect_owned`/
  `handshake_owned` pair — identical wire behavior to `connect`/`handshake`, differing only in taking an
  owned `Arc<dyn SecretStore>`/`KeyHandle` instead of a borrow and running the handshake's one `sign()`
  call inside `spawn_blocking`. **Every other caller of `SignalingClient::connect`
  (`cmd_register`, `cmd_fetch_bundle`, `cmd_chat`, `session_connect`, `republish_bundle`, every existing
  test) is untouched — the original borrow-based `connect`/`handshake` still exists, byte-for-byte, and
  is what they all still call.** `run_inbound_loop` is the only caller switched to `connect_owned`.
  This is the "wider-than-expected signature change" this task's own Risks section anticipated —
  resolved by adding a second, additive entry point rather than widening the existing one's signature for
  every caller in the workspace (16 call sites across `apps/cli`/`apps/tui`/`apps/rendezvous` tests would
  otherwise have needed touching); named explicitly here per that section's own instruction rather than
  silently narrowed.
- **No new caching, no new residency, verified, not just asserted:** every `Arc<dyn SecretStore>` wraps
  the *same* store object `inbound_handoff` already constructed (a raw `FileSecretStore` for the
  file-backed branch, a free `OsSecretStore` for the OS-keystore branch) — `Arc::new` around an existing
  value, never a second construction, never a cache. `decrypt_seed()` still runs on every single
  `use_key`/`derive_key` call, the same as before this task; only the thread it runs on changed.

**Reviewer-caught gap, closed in the same task before landing (not a second task).** The bullets above
were this task's *first* landing, and covered only four of the six calls Deliverable 2's own table names
— `run_unlock`'s own passphrase-verification `export_seed()` and `unwrap_keyfile_for_bulk_signing`'s
`export_seed()` (reached via `inbound_handoff`'s `Effect::Unlock` arm) were still fully synchronous,
still running directly on the `current_thread` runtime at unlock time (~2.6 s real hazard, live and
unfixed). A `reviewer` pass read the current source directly (`apps/tui/src/worker.rs`'s `run_unlock` and
`unwrap_keyfile_for_bulk_signing`) and caught both the residual hazard and the resulting Deliverable-4
overclaim. Closed as follows, in the same `spawn_blocking`-only shape:
- `unwrap_keyfile_for_bulk_signing` (`apps/tui/src/worker.rs`) — its one `fs.export_seed()` call now
  runs inside `tokio::task::spawn_blocking`, with `keyfile`/`passphrase`/`label` cloned into the closure
  (owned, `'static`-compatible; the function's own `&Path`/`&str` parameters can't satisfy
  `spawn_blocking`'s bound directly). This function is shared by two callers — `inbound_handoff`'s
  `Effect::Unlock` arm (this task's own target) and `open_store_for_bulk_signing` (onboarding's
  `handle_register` path, already `async fn`) — so it, and `open_store_for_bulk_signing` one level up,
  both became `async fn` too; `handle_register`'s one call site gained an `.await`, mechanically, no
  logic change.
- `inbound_handoff` (`apps/tui/src/worker.rs`) itself became `async fn`, purely to `.await` the call
  above. **This does not touch its own "never a new round trip" contract (task 4.35)** — that contract is
  about not starting a *new network* round trip, and a local `spawn_blocking` dispatch is not one; the
  function's own doc comment, and `republish_bundle`'s neighboring doc comment (which explains why
  *that* function stays separate — it *does* do a real network round trip), were both updated to say so
  explicitly rather than leave the older "synchronous" wording stale. `apps/tui/src/lib.rs::run_worker`'s
  one call site gained an `.await`.
- `run_unlock` (`apps/tui/src/worker.rs`) itself became `async fn`. Its own `fs.export_seed()`
  passphrase-verification call now runs inside `spawn_blocking`, against a throwaway `FileSecretStore`
  built inside the closure from cloned, owned `keyfile`/`passphrase` (same reason as above). The `fs`
  used afterward for `load_live_session` and the returned store is a **second**, separate
  `FileSecretStore::new(...)` construction — cheap, no I/O, not a second unwrap — so the total
  `decrypt_seed()` call count is unchanged (still exactly one from this function). `handle_unlock`'s one
  call site gained an `.await`.
- Six test call sites in `apps/tui/tests/republish_bundle.rs` (all of which call `inbound_handoff`
  directly, since it's a `pub fn`/now `pub async fn`) needed a mechanical `.await` (five already ran
  inside an existing `block_on(async { ... })` closure; one needed wrapping in `block_on(...)` since it
  was a bare synchronous call). One in-module test
  (`run_unlock_fails_closed_for_an_os_keystore_account_never_touching_the_keyfile`) changed from `#[test]`
  to `#[tokio::test]` for the same reason. No test assertion was weakened — every one of these is a pure
  mechanical `.await`/attribute change, confirmed by re-running the full suite (see "Tests run" below).

**The binding consult-gate decision applies unchanged to these two additional call sites, confirmed and
recorded explicitly (not silently assumed to carry over):** both are a pure `spawn_blocking` execution-
context change — the exact same `export_seed()` call, same call site, same frequency (once per session for
each), no new caching, no new residency, freed at the same point as before. This still trips the
"Pre-code consult assessment" section's **first** bullet (`spawn_blocking`-only) — **no consult required**,
for the same reasons Deliverable 5's original decision gave.
