# 11.1 — Namespace `open_stream`'s `sid`/channel-label derivation to fix concurrent-open collisions

**Phase:** 11 — Review of Phase 10 · **Feature:** review fix (F1, blocking) · **Depends on:** — · **Status:** done

**User surface:** none — session-substrate internal fix (`meridian-core`); no client-visible behavior
change beyond making concurrent bidirectional transfers work instead of silently corrupting, so no new
TUI surface applies (Definition of Done gate 9).

## Goal
Eliminate the deterministic `sid` collision in `P2pSession::open_stream` when both peers concurrently
open the same bidirectional stream type, so `mrd.file/1` (and any future `Bidir` stream type) can never
have two independently-opened streams bound to the same wire channel label.

## Scope
- **In:** `apps/core/src/session.rs` — `next_sid`/`open_stream`'s local counter, `stream_channel_label`'s
  derivation, and the `handle_ctrl` `Open`/`Accept` arms, which must agree with whatever new derivation
  is chosen. A short architect consult folded into this task (not a separate pre-task — the derivation is
  a small, bounded decision, not a new protocol surface) to ratify the exact namespacing scheme before
  implementation.
- **Out:** no change to the `StreamType` trait, the stream registry, or any other stream type's behavior.
  No new ADR expected (implementation-level fix to an existing substrate primitive, mirroring how task
  10.4's substrate-completion work landed without one) — if the architect judges the fix changes
  wire-visible protocol shape beyond channel-label derivation, escalate to `/adr` rather than proceeding
  silently.

## Deliverables
1. Architect-ratified namespacing scheme recorded in this task's Risks/notes (e.g. reusing the existing
   identity-key lexicographic tie-break already used for dial/answer roles and `ice_restart` glare — even
   `sid` for the smaller-key identity, odd for the larger; or an explicit originator marker folded into
   `stream_channel_label`).
2. Fix in `apps/core/src/session.rs`: `next_sid`/`open_stream`, `stream_channel_label`, and the
   `handle_ctrl` `Open`/`Accept` arms updated to agree on the same derivation on both sides.
3. Regression test proving two concurrent bidirectional `open_stream` calls (same stream type, both
   directions) never collide on `LoopbackTransport` (`apps/core/tests/p2p_session.rs`), plus an analogous
   test under `--features webrtc` confirming two `RTCDataChannel`s never bind to the same negotiated SCTP
   stream.

## Risks / notes
This is a pinned wire-shape derivation other stream types will rely on — get the architect's sign-off on
the exact scheme before writing the fix, not after. Confirm the chosen scheme doesn't affect anything
`test-vectors/` pins (no existing vector currently covers the ctrl-frame `sid` field). `TODO: confirm` the
exact namespacing scheme with the architect — do not guess it independently of that sign-off.

**Architect-ratified scheme (implementation-level, no new ADR — wire shape unchanged):** partition the
`u64` sid space by the existing identity-key lexicographic tie-break already used twice in this file
(dial/answer role; ICE-restart glare, ADR 0025). At session construction (`dial_established`/
`answer_established`, where `next_sid` is currently seeded to `CHAT_SID`), seed instead: `our_ik <
peer_ik` (smaller key) → `next_sid = 0`; otherwise → `next_sid = 1`. In `open_stream`, change the
increment from `+= 1` to `+= 2`. Result: the smaller-key side only ever allocates even sids (`2, 4, 6,
…`), the larger-key side only ever allocates odd sids (`3, 5, 7, …`) — two disjoint domains starting
cleanly above the fixed `CTRL_SID = 0`/`CHAT_SID = 1`, no special-casing needed. Both sides still derive
the *same* value for a given logical stream exactly as today (initiator via its own counter, responder by
reading `sid` verbatim off the `Open` frame) — `stream_channel_label` and the `handle_ctrl` `Accept`/
`Reject` arms need zero changes, they're already sid-value-agnostic. No griefing/DoS exposure: `our_ik`/
`peer_ik` are fixed, mutually-authenticated pre-session values, so a peer cannot forge or flip its own
parity class. Confirmed clean against `test-vectors/` (no vector pins the ctrl-frame `sid` field).

## Tests
`cargo nextest run -p meridian-core`; `cargo nextest run -p meridian-core --features webrtc`; the new
regression test(s).

## Reviews
**architect** (mandatory — wire-shape sign-off on the `sid`/label derivation), **security-reviewer**
(session/transport substrate — confirms the fix can't be starved/griefed by a peer racing opens),
**code-reviewer**.

## Outcome
Implemented the architect-ratified scheme exactly: a new `initial_next_sid(our_ik, peer_ik)` helper seeds
`next_sid` to `0` (smaller identity key) or `1` (larger key) at session construction
(`dial_established`/`answer_established`), and `open_stream` increments by `2` instead of `1` — the
smaller-key side allocates even sids, the larger-key side odd, two disjoint domains that can never
collide, starting cleanly above the fixed `CTRL_SID = 0`/`CHAT_SID = 1`. `stream_channel_label` and
`handle_ctrl`'s `Open`/`Accept`/`Reject` arms needed zero changes — confirmed sid-value-agnostic as
predicted. New regression tests (loopback in `apps/core/tests/p2p_session.rs`, `--features webrtc` in
`apps/core/tests/p2p_session_webrtc.rs`) both independently confirmed to fail pre-fix and pass post-fix,
asserting disjoint parity and zero cross-talk end-to-end; the webrtc test specifically proves no
negotiated-SCTP-stream-id collision, not just no observable data corruption.

Combined architect/security-reviewer/code-reviewer pass: **PASS, zero blocking findings**. Full suite
green (`meridian-core` 169/169 default + 174/174 `--features webrtc`, `meridian-streams` 68/68), clippy
clean both configs, no `test-vectors/` impact. One **non-blocking, pre-existing** residual surfaced by
review (not a regression from this diff — the touched code path is unchanged): `handle_ctrl`'s `Open` arm
never validates an incoming `sid` against this side's own `pending_opens`/`stream_channels` entries, so a
malicious *authenticated counterparty* (not a MITM) could still craft an `Open` frame whose `sid`
deliberately collides with a locally-pending sid, clobbering the `HashMap` entry — orthogonal to F1 (which
was about two *honest* peers' independent counters colliding), carried forward to the tracker for a future
task rather than silently dropped.
