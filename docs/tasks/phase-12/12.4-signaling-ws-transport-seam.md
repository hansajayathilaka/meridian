# 12.4 — `meridian-signaling` WebSocket transport seam

**Phase:** 12 — Browser & Desktop Clients · **Feature:** T11 (substrate completion, not the feature
itself) · **Depends on:** 12.1 · **Status:** done

**User surface:** none — internal substrate seam, no user-visible behavior change on the native path.
No TUI surface applies.

## Goal
Close the second half of the wasm32-buildability gap the architect consult found (see
[phase-12/README.md](./README.md#architect-consult-substratestoresigning-decisions-settled-before-task-breakdown)
point 3): `meridian-signaling`'s `SignalingClient` hardcodes `WebSocketStream<MaybeTlsStream<TcpStream>>`
(via `tokio-tungstenite`), which has no `wasm32-unknown-unknown` story at all. Introduce a small internal
trait so a browser build can swap in the browser's native `WebSocket` (via `web-sys`/
`wasm-bindgen-futures`) while native builds keep `tokio-tungstenite` byte-for-byte unchanged. This is
**not** one of the two frozen `core-api-contracts.md` traits (`Transport`/`SecretStore`) — it is an
internal implementation seam local to `meridian-signaling`, so it raises no stability-policy question.
Passing `cargo check -p meridian-signaling -p meridian-core --target wasm32-unknown-unknown` here is
what finally proves the full `meridian-core` wasm32 build green, closing the arc 12.1 started.

**This finding and its fix shape were settled by an architect consult during `/plan-phase`** — this task
file implements that decision, it does not re-open it.

## Scope
- **In:** a new internal `WsConnection`-style trait inside `meridian-signaling`; `SignalingClient`
  refactored to use it instead of the hardcoded stream type, with an unchanged public API; a native impl
  wrapping the existing `tokio-tungstenite` stream unchanged (byte-identical handshake/wire behavior —
  no conformance-vector changes); a `wasm32` impl wrapping the browser's native `WebSocket` via
  `web-sys`/`wasm-bindgen-futures`; `Cargo.toml`'s `[target.'cfg(target_arch = "wasm32")'.dependencies]`
  split (drops `tokio-tungstenite`/`rustls` there, adds `wasm-bindgen`/`web-sys` for that target only).
- **Out:** any browser-UI-specific reconnect/backoff policy beyond what `SignalingClient` already does
  natively; the browser `Transport` shim (12.11, a separate trait entirely); any change to the WSS wire
  handshake itself.

## Deliverables
1. `apps/signaling/src/ws_transport.rs` — the `WsConnection` trait + native/wasm impls.
2. `apps/signaling/Cargo.toml` — target-conditional dependency split.
3. `SignalingClient` refactored onto the trait, public API unchanged.
4. `cargo check -p meridian-signaling -p meridian-core --target wasm32-unknown-unknown` passing (new
   `just`/CI step, extends 12.1's).

## Reviews
**reviewer** (combined pass: architect lens — confirms the seam doesn't touch the frozen
`Transport`/`SecretStore` contracts and needs no ADR, per the consult's point 3; security-reviewer lens

## Outcome
Introduced `apps/signaling/src/ws_transport.rs`'s `WsConnection` trait (`pub(crate)`, never exported —
distinct from the frozen `Transport`/`SecretStore` contracts) with a `NativeWsConnection` (unchanged
`tokio-tungstenite` wrapper, byte-identical handshake/wire behavior) and a `WasmWsConnection` (browser
`web_sys::WebSocket`, events bridged into a `futures_channel::mpsc` queue). `SignalingClient` refactored
onto the trait; public API unchanged. `cargo check -p meridian-signaling -p meridian-core --target
wasm32-unknown-unknown` passes — the full six-crate arc task 12.1 started plus `meridian-signaling`/
`meridian-core` is now green (8 crates total, Justfile/CI `check-wasm32` extended accordingly). Along the
way, discovered `meridian-core`'s own `tokio = { workspace = true, features = ["sync"] }` had the
identical additive-union defect task 12.1 found in `apps/transport` (silently linking the full workspace
tokio feature set, `mio` included, onto every target) — split the same way, in scope per this task's own
Goal even though not itemized in Deliverables. Also fixed a previously-unverified bug in 12.1's own
`time_compat::Instant` wasm32 arm: `wasmtimer::tokio` has no `Instant` export at all, and the correct
type (`wasmtimer::std::Instant`) panics on subtraction instead of clamping — a newtype restoring
`saturating_duration_since` was needed.

The `WasmWsConnection`/`Closure`/`web_sys::WebSocket` types are `!Send` by wasm-bindgen's own design,
which propagated into `meridian_core::session::SignalRelay: Send` (required by `#[async_trait]`'s
default bound); rather than cfg-splitting `SignalRelay` itself across ~15 call sites, a narrow
`unsafe impl Send for WasmWsConnection {}` was added, confined to that one `pub(crate)` type.

The combined review (architect + security-reviewer) returned **PASS** on both lenses after independently
verifying the `unsafe impl Send` rather than accepting it on the implementer's word: confirmed no
`+atomics`/multi-threaded wasm config exists anywhere in the workspace (the premise it depends on), and
empirically proved it's genuinely load-bearing — not speculative — by temporarily removing the line and
confirming `meridian-core` fails to compile for wasm32 with 12 `E0277` errors rooted at
`SignalRelay: Send`, then restoring it and reconfirming a clean build. The review also caught one real,
verified correctness bug the implementation had missed: three call sites in `apps/core/src/session.rs`
(`P2pSession::ping`, `dial_with_config`, `answer_with_config`) called the raw `std::time::Instant::now()`
instead of going through the crate's own new `time_compat` seam — `cargo check` passing proved only that
these compiled for wasm32, not that they were runtime-safe, and the reviewer empirically reproduced a
real wasm32 trap (`RuntimeError: unreachable`) for that call. Fixed in a same-task follow-up commit: added
`elapsed()` to the wasm32 `time_compat::Instant` newtype and migrated all three sites; re-verified clean
(wasm32 check, full native `meridian-core`/`meridian-signaling` suites, clippy, fmt) with a grep confirming
no raw `std::time::Instant::now()` call remains outside `time_compat` itself. Also added, per the review's
one non-blocking hardening recommendation, a `#[cfg(not(target_feature = "atomics"))]` tripwire above the
`unsafe impl` so a future multi-threaded wasm build fails to compile there instead of silently inheriting
an unsound impl.

Deferred scope, stated honestly rather than silently claimed as covered: no headless-browser/Node
WebSocket runtime test harness (`wasm-bindgen-test` + a local WS echo server) exists yet — this task's
wasm32 coverage is `cargo check`/`cargo clippy` passing (compiles, type-checks, correct `web-sys` API
usage) plus the full native-path regression suite, not a runtime-verified browser WebSocket round trip.
Left for the browser-integration tasks (12.11/12.13) per this task's own stated default. The pre-existing
`wasmtimer = "0.2"` pin (task 12.1's own `TODO: confirm`) remains open — build-verified for the first
time here, with one real bug fixed in its usage, but the crate choice itself wasn't re-litigated.
