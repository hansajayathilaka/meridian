**Known, confirmed browser↔native interop defect, found by task 12.11's own review — read before
running the chat/file cells.** `apps/wasm/src/transport.rs`'s `stream_id_for_label` uses modulus `1_000`
while `apps/transport/src/webrtc_backend.rs`'s native equivalent uses modulus `65_534` — for the same
channel label (e.g. `"mrd.ctrl/1"`), the two pure functions compute different negotiated SCTP stream ids
almost always (~1/65 coincidence chance). A pre-negotiated data channel needs both sides to agree on the
numeric id, so a real browser↔native session is expected to fail to line up `mrd.ctrl/1` (and any other
label) until this is reconciled — likely by widening the browser-side modulus back to match, once
whatever caused Chrome to reject the wider range (task 12.11's own finding: `RTCPeerConnection::
createDataChannel` throws `OperationError` for at least one 65,534-range id) is root-caused. This is a
tracked carry-forward (see [tracker](../README.md#live-carry-forwards-not-owned-by-any-open-task)), not
something to silently work around inside this task's own harness — expect the browser↔CLI/browser↔desktop
cells to need this fixed first, or file a dedicated fix-task if this task's own run surfaces it live.
