# 5.1 — Persist and always-reconcile Sent→Delivered receipts

**Phase:** 5 — Review of Phase 4 · **Feature:** review fix (F1) · **Depends on:** — · **Status:** pending

## Goal
Make the Sent/Delivered message-status indicator (landed out-of-band in PRs #71/#72, outside the
tracked-task pipeline) actually correct: a delivery receipt must update the sender's transcript
regardless of which screen is currently on top of the stack, and the transition must survive a restart.

## Scope
- **In:** `App::handle_inbound`'s `InboundEvent::Receipt` arm (`apps/tui/src/app.rs`, currently only
  applies the transition when the exact `Screen::Chat` for that peer is `self.screens.last_mut()`);
  `chat::apply_receipt` (`apps/tui/src/screens/chat.rs`); persisting the `Delivered` state so a reload
  from `history.jsonl` doesn't silently revert it to `Sent`.
- **Out:** Any change to the ack/receipt wire protocol itself (out of scope — this is a client-side
  reconciliation bug, not a protocol gap). Retrying receipts that never arrive (acks are one-shot by
  design; not this task's concern).

## Deliverables
1. `App::handle_inbound`'s Receipt arm reconciles into the live screen stack the same way
   `apply_accepted_request`/`apply_added_contact` do for other inbound events — walk the stack and
   update the matching `ChatState` wherever it lives, not only when it's on top.
2. The `Delivered` transition is persisted (a small update-in-place write, not a full history rewrite),
   so `Effect::LoadHistory` reflects it after a restart.
3. A new App-level test (new file or extension of `apps/tui/tests/inbound_delivery.rs`) that opens
   `Screen::Chat` for a peer, sends a message, navigates away, dispatches a real
   `AppEvent::Inbound(InboundEvent::Receipt{..})`, navigates back, and asserts the double-tick renders —
   plus a restart-persistence variant.

## Risks / notes
Do not conflate this with F10 (5.10) — that's about `PersistHistory`'s own write-durability window on
shutdown; this task is about the receipt *reconciliation logic* being reachable at all regardless of
screen state, plus persisting the resulting status. `apply_receipt`'s existing unit test
(`screens_chat.rs:438`) drives `ChatState` directly and must keep passing unchanged; it is not sufficient
coverage on its own (it can't catch a routing bug), which is exactly what F1 found.

## Tests
`cargo nextest run -p meridian-tui --test inbound_delivery --test accept_to_chat --test screens_chat`

## Reviews
**architect** + **code-reviewer** (combined `reviewer` call — the reconciliation pattern this follows
is the same one `apply_accepted_request`/`apply_added_contact` established, so architect should confirm
this task extends rather than diverges from it) + **test-engineer** (the new App-level test is the
actual deliverable here, not incidental).
