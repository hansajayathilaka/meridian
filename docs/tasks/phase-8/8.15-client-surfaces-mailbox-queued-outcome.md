# 8.15 — Client surfaces the mailbox-queued outcome (fix-task, found during 8.14's live demo)

**Phase:** 8 — Offline Ciphertext Mailbox · **Feature:** T07 · **Depends on:** 8.5, 8.6 · **Status:** done

## Goal
Fix a real, confirmed defect found while preparing task 8.14's live acceptance demo: the
client-visible layer (`meridian-signaling`'s `SignalingClient`, `meridian-cli`, `meridian-tui`) never
surfaces `RouteOk.queued` (added by task 8.3, populated by tasks 8.5/8.6) — every offline-recipient
send still shows the stale **pre-T07** "not delivered, mailbox is T07 / peer is offline, press r to
retry" copy, even though the message is now genuinely, durably queued and will actually arrive on
reconnect. Per task 8.14's own Risks/notes ("if the live demo finds a defect... don't force a PASS...
record the defect, open the next-numbered fix-task"), this is that fix-task.

## Scope
- **In:**
  1. `apps/signaling/src/client.rs`: `SignalingClient::route_with_hint` only ever returns
     `ok.delivered` — `ok.queued` is decoded off the wire (implicitly, as part of `RouteOk`) and then
     silently discarded. Add a way for a caller to see both fields without breaking the existing
     `Result<bool>`-returning callers that deliberately don't care about the distinction
     (`apps/core/src/signal_relay.rs`'s P2P-session relay — see its own doc comment: no
     mailbox/async-queuing story for SDP offer/answer exchange, `route()==Ok(false)` is correctly a
     hard error there regardless of `queued`, not this task's concern).
  2. `apps/cli/src/chat.rs::send_text`/`route_tolerant`: replace the stale
     `"[you] {text}  (peer offline — not delivered; mailbox is T07)"` line with copy that
     distinguishes "queued into the recipient's mailbox, will arrive on reconnect" from "genuinely
     not delivered" (`ttl_days == 0`/no mailbox) — matching the feature spec's own demo script line
     (`07-offline-mailbox.md`: `[mailbox] bob offline — queued at org-b (expires in 14d)`).
  3. `apps/tui/src/app.rs::SentMessage` / `apps/tui/src/worker.rs` / `apps/tui/src/screens/chat.rs`:
     `SentMessage`'s doc comment currently states `delivered == false` is "never 'queued for later
     delivery'" — no longer true. `offline_failure_copy`'s "not delivered — offline — press r to
     retry" is actively misleading for a queued send (retrying resends a message that's already
     durably queued, risking a duplicate once the peer reconnects — the eid-dedup mechanism, task
     6.4, protects the recipient from a literal duplicate deliver, but "press r to retry" is still
     the wrong instruction to give the user for a message that doesn't need retrying at all). Add the
     queued outcome as its own tracked state and its own, accurate copy; keep the existing offline/no-
     mailbox copy and retry action for the genuine case.
  4. `docs/architecture/tui-client.md` §7's "What the user sees when things go wrong" table: update
     the "Peer offline (pre-T07)" row to add the now-real queued outcome as a second row, rather than
     leaving the table implying only one possible offline outcome still exists.
  5. Update the doc comments that explicitly describe this as "pre-T07"/"out of scope for this whole
     phase" now that this phase (T07) is done: `apps/signaling/src/client.rs` (`route`/`route_with_hint`
     doc), `apps/tui/src/app.rs` (`SentMessage`), `apps/tui/src/screens/chat.rs` (module doc +
     `offline_failure_copy`'s own doc), `apps/tui/tests/run_worker_chat.rs`'s doc reference.
- **Out:** `apps/core/src/signal_relay.rs` — its `route()==Ok(false)` ⇒ hard-error behavior is
  correct and unrelated (P2P signaling has no mailbox story at all); leave its doc comment's
  reference to "that's T07, and even then only chat envelopes get it" as-is, since that's still
  accurate. `docs/api/wire-protocol.md`/`rendezvous-protocol-v1.md`'s own "pre-T07 `not_connected`"
  references (describing the still-current `ttl_days==0` case) are accurate contrastive terminology,
  not stale — not touched. Historical task files (`docs/tasks/phase-4/*.md`) and
  `docs/architecture/features/02-rendezvous-mvp.md` (T02's own historical MVP-scope note) are
  point-in-time records, not touched.

## Deliverables
1. `SignalingClient` exposes both `delivered` and `queued` to a caller that wants them, without
   breaking `route_with_hint`'s existing `Result<bool>` callers.
2. CLI: accurate, demo-script-matching copy for a queued send.
3. TUI: `SentMessage` carries the queued outcome; `offline_failure_copy` gains an accurate queued
   variant; the extension-contract doc table is updated (gate 9 — this phase's own client surface,
   now corrected rather than newly added).
4. Regression tests: CLI prints the queued copy for a `{delivered:false, queued:true}` reply and the
   existing offline copy for a genuine `{delivered:false, queued:false}`-shaped drop (`Err{not_connected}`
   at `ttl_days==0`); TUI's `SentMessage`/copy do the same.

## Risks / notes
Keep this narrowly scoped to the actual defect (client-visible copy + the one missing bit of API
surface) — not a redesign of the offline-send UX. `apps/core/src/signal_relay.rs` must not change
behavior at all (confirm with a regression test that a P2P relay send to an offline peer is still a
hard error regardless of mailbox availability).

## Status
**Done.** Implemented exactly the Scope's five items:
1. `apps/signaling/src/client.rs`: new `RouteOutcome { delivered, queued }` + `route_with_hint_detailed`;
   `route_with_hint` is now a thin wrapper (`route_with_hint_detailed(...).map(|o| o.delivered)`), so
   every other existing caller (`apps/tui/src/worker.rs`'s auto-ack call site,
   `apps/core/src/signal_relay.rs`'s `RendezvousRelay::send`) is behavior-unchanged and needed no edits.
2. `apps/cli/src/chat.rs`: `route_tolerant` returns `RouteOutcome`; `send_text`'s print logic extracted
   into a pure `sent_line` function (three-way `delivered`/`queued`/neither mapping, JSON mode carries
   both fields additively) with new unit tests in the existing `#[cfg(test)] mod tests` block.
3. `apps/tui/src/app.rs`/`worker.rs`/`screens/chat.rs`: `SentMessage` gained `queued: bool`;
   `complete_send` now treats `delivered || queued` as `MessageState::Sent` (never `Failed` — a
   queued send is not a failure and must never be `r`-retryable, confirmed structurally since
   `retry_last_failed` filters strictly on `MessageState::Failed`), with a new one-time
   `state.notice` (`queued_notice_copy`) for the queued case rather than a new persisted
   `MessageState` variant — deliberately avoiding a schema migration
   (`apps/tui/src/store/history.rs`'s `MessageState` is version-migrated on disk) for what is a
   fix-task, not a redesign. `queued_notice_copy` reuses the same attacker-resistant
   `ChatState::failure_copy_label` `offline_failure_copy` already used (security-review Finding 2,
   task 4.20), with a new dedicated hostile-hint test mirroring the existing one.
4. `docs/architecture/tui-client.md` §7's table updated with the new queued row.
5. Doc comments explicitly calling this "pre-T07"/"out of scope for this whole phase" corrected
   across `apps/signaling/src/client.rs`, `apps/tui/src/app.rs`, `apps/tui/src/screens/chat.rs`
   (module doc + `offline_failure_copy`/`failure_copy_label`), and `apps/tui/tests/run_worker_chat.rs`
   — the last of these turned out to need more than a doc fix: its own test scenario (default
   `Config`, `ttl_days=14`) already exercises the queued path today (not the "pre-T07 dropped" case
   its old doc comment claimed), so a `sent.queued` assertion was added and the test renamed
   (`..._and_queued_true`) to match what it actually proves.

### Review round
**code-reviewer** — PASS, zero blocking findings, two should-fix (both addressed in this same
commit) plus one nit (addressed):
- **Should-fix 1**: `sent_line`'s doc comment claimed the queued line "matches the demo script"
  without noting that a federated route (task 8.6, architect consult point 2) always replies to its
  own sender with the optimistic `RouteOk{delivered:true}` regardless of whether the foreign server
  delivered live or queued — so `outcome.queued` can only ever be `true` here for a **same-server**
  peer, never a cross-org one. Fixed: `sent_line`'s doc comment now states this explicitly, plus
  acknowledges the copy intentionally drops the demo script's illustrative `(expires in 14d)` (no TTL
  is available in `RouteOk` for this client to report).
- **Should-fix 2**: the task's own Risks/notes asked for "a regression test that a P2P relay send to
  an offline peer is still a hard error regardless of mailbox availability." `apps/core/src/signal_relay.rs`
  has zero diff from this task (confirmed via `git diff` — nothing in it changed), and its
  `RendezvousRelay::send` still calls the unchanged-signature `route_with_hint`, whose new body
  (`route_with_hint_detailed(...).map(|o| o.delivered)`) is a pure, provably behavior-preserving
  refactor of the old body — the pre-existing `route_not_delivered_is_a_hard_error` unit test
  (`map_route_result(Ok(false))` ⇒ `SessionError::Relay`) already covers the exact bool this call site
  ever sees, unchanged by this task. Per the reviewer's own offered alternative ("or explicitly
  documenting... that this was verified by inspection rather than a new test"), recorded here instead
  of adding a new full server-spawning integration test for zero-diff code: `signal_relay.rs` needed
  no test addition because it needed no code change, and the composition proof above is exact, not
  approximate.
- **Nit**: `apps/tui/tests/run_worker_chat.rs`'s renamed test (see item 5 above) already resolves
  this — its name now names both halves of what it asserts.
