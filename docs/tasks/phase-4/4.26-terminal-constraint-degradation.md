# 4.26 — Terminal-constraint degradation

**Phase:** 4 — Verification & Trust + Terminal TUI Client · **Feature:** T17 — Terminal TUI Client · **Depends on:** 4.20 · **Status:** done

## Goal
Make the running app degrade correctly under real terminal constraints — these are acceptance criteria,
not polish.

## Scope
- **In:** `NO_COLOR=1` honored; `ui.unicode = false` ASCII-only glyph fallback as a first-class path, not
  a degraded afterthought; status conveyed by glyph + label, never color alone; below-80-columns contacts
  pane collapses into a toggled overlay rather than truncating the conversation; alternate screen always
  used, so conversation text never survives in scrollback after exit.
- **Out:** the entry-point refusal for `TERM=dumb`/non-TTY/too-small-at-launch (4.12 handles that; this
  task handles degradation *within* an already-running session, e.g. after a resize).

**Carry-forward from 4.22's review:** the Verify screen's security banner now always claims the full
height its canonical wording needs (never clipped in favor of the number/QR pane — a 4.22 review fix),
but at a mid-session resize shorter than that content requires, the banner itself still clips against
the physical terminal height, since nothing currently re-checks size after launch. This task's own
scope (`AppEvent::Resize` handling) is the natural place to add either a minimum-height guard or
scrollable/paginated banner content for that extreme case — not spotted as a new requirement here, just
flagged so it isn't lost.

## Deliverables
1. Degradation handling wired through the render layer (glyph+label status indicators, ASCII fallback
   set, narrow-width layout).
2. Snapshot tests at narrow width and under `NO_COLOR=1`; a test confirming the app never writes to the
   primary screen buffer (alternate-screen-always).

## Tests
`cargo nextest run -p meridian-tui --test degradation`

## Status
Done. `apps/tui/src/theme.rs` centralizes degradation: `RenderCtx` resolves `NO_COLOR` (env) + `TuiConfig
.ui.{unicode,theme}` once per frame in `App::render`, exposing `color_or_none`/`GlyphKind::glyph` (unicode/
ASCII pairs) and `contacts_pane_layout` (the below-80-columns overlay-vs-side-by-side mechanism). Retrofit
into `contacts.rs`/`contact_detail.rs`/`chat.rs`/`verify.rs` — confirmed by review to be this crate's
entire set of trust/delivery-glyph renderers, not a partial pass; every other screen either has no
color-or-glyph status to retrofit or already conveys it through label text alone. The narrow-width
contacts-pane mechanism is built and tested against `contacts.rs`'s own rendering directly; no combined
Main screen exists yet to fully integrate it into, documented as deferred to whatever future task builds
that layout. Alternate-screen-always is proven via two static checks (a source sweep for raw stdout/
crossterm-execute tokens outside `terminal.rs`, and a byte-offset ordering check that `TerminalGuard::
install` precedes backend construction in `lib.rs::run`) rather than a dynamic test, with the rejected
dynamic approach's race condition (against `TerminalGuard`'s process-global panic hook) documented.

Also closes this task's carried-forward item from 4.22's own review: the Verify screen's security banner
now survives a mid-session resize shorter than its content requires (previously only the launch-time case
was fixed) via a new scroll mechanism, intercepted only from `View`/`Error` modes so the exhaustive "no
dismiss without verify" property from 4.22/4.23 stays untouched.

**Review (combined `reviewer`, as named — "rendering/layout concern... doesn't need a second
security-reviewer pass"):** two rounds of real findings on the Verify-screen carry-forward fix
specifically, both fixed and re-confirmed clean — the reviewer explicitly treated this sub-fix with
4.22-level rigor despite the lighter-weight named reviewer, given its proximity to the phase's central
security-critical screen:
- **Round 1 (blocking):** the new scroll mechanism's height calculation (`wrapped_row_count`) undercounted
  any single space-free "word" longer than the render width as exactly one row, when ratatui's real
  wrapping breaks it across `ceil(word_len/width)` rows. Since the banner's text interpolates
  `Contact::hint` — wire-observed and attacker-influenced — a peer supplying a long space-free hint at
  exactly the moment they present a changed key could defeat the fix entirely: reproduced not just at an
  extreme resize (scroll got stuck before the tail was reachable) but at an *ordinary* 40×30 terminal,
  where the undercount was severe enough the overflow/scroll branch never even engaged and the canonical
  warning's tail was silently absent with no scroll hint offered at all. Fixed with correct `ceil`
  row-counting and remainder-tracking, plus regression tests reproducing both failure modes.
- **Round 2 (blocking):** the fixed row-count math was correct, but the underlying width measurement
  wasn't — `char` count instead of terminal display-cell width, so double-width characters (CJK, fullwidth
  forms, many emoji) still undercounted by up to 2x, reproduced identically via a wide-character hint at
  an ordinary terminal. Fixed by measuring width via grapheme-cluster iteration + `unicode-width`'s
  cell-width (matching ratatui's own renderer exactly, confirmed by reading its source), with a matching
  regression test. The reviewer independently reproduced both rounds' original failures by reverting each
  fix in turn and confirming the new tests fail without it, then confirmed both are genuinely closed.

`cargo test -p meridian-tui --test degradation` (19 tests, new in this task), `cargo test -p meridian-tui
--test screens_verify` (unaffected, all 27 still pass including the exhaustive keyspace sweeps), `cargo
test -p meridian-tui` (full suite), `cargo test -p meridian-cli --bins`, `cargo fmt --check`, `cargo
clippy --workspace --all-targets -- -D warnings`, and `bash tools/lint-tui-no-cli.sh` all clean.
