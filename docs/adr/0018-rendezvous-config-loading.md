# ADR 0018: Config loading — `figment` for rendezvous (and the CLI's local stores)
**Options:** (A) hand-rolled TOML parse + one `if let Ok(v) = env(...)` block per field (the original shape of this change); (B) the `config` crate; (C) **`figment` (chosen)**.
**Trade-offs:** A is fully explicit and auditable per field but is ~150 lines of repetitive boilerplate for `apps/rendezvous/src/config.rs`'s ~24 leaf fields alone, and doesn't scale to also covering the CLI's `account.json`/`policy.json`. B needs a global `try_parsing(true)` flag (affects every env var, not just the ones that should coerce) plus a per-field `with_list_parse_key` for each array, and its `Environment` source's fallback semantics are less clearly specified. C (`figment`) auto-coerces bool/int/float per-value with no global flag, reports errors with the offending key path and source attached, and is already the tool of choice for the same job elsewhere in the Rust ecosystem (e.g. Rocket's own config). **Decision: C**, with four binding conditions. (1) The rendezvous server's env prefix is `MERIDIAN_RENDEZVOUS_`, not bare `MERIDIAN_` — scoped per-service so it can't collide with other Meridian components' env vars sharing a process environment (e.g. the CLI's `MERIDIAN_HOME`, `MERIDIAN_PASSPHRASE`, `MERIDIAN_POLICY__*`). (2) List values from env use figment's native TOML/JSON bracket syntax (`MERIDIAN_RENDEZVOUS_TURN__URLS=["turn:a","turn:b"]`), not comma-separated — a clean choice since this landed before the hand-rolled comma-separated format (PR #37) ever merged. (3) `apps/cli/src/account.rs`'s `account.json` gets figment's `Json` provider for the file-read only, with **no** `Env` merge layer: its fields (`pubkey`, `keyfile` path, `service`, `label`) are identity-bearing, and an env var silently redirecting them is an identity-substitution/confused-deputy risk, not a legitimate config knob — nothing in the docs anticipates overriding *who you are* via environment. `apps/cli/src/policy.rs`'s `policy.json`, by contrast, gets both the `Json` provider and `Env::prefixed("MERIDIAN_POLICY__")`, since org-pushed connection-policy defaults are already anticipated architecture (`data-model.md`: "org-pushed defaults... + user overrides"; `deployment.md` already named `meridian config set policy` as the org-default mechanism). (4) Fail-closed semantics are preserved and, on one axis, *tightened*: a set-but-unparseable env var, an explicitly-supplied `--config` path that doesn't exist, and now **any malformed `rendezvous.toml`** — whether loaded via `--config` or picked up implicitly from the working directory — are all fatal boot errors. Previously only the explicit-`--config` case was fatal; a malformed *implicit* file silently fell back to defaults. Only a **missing** file on the implicit path stays non-fatal, unchanged. **Consequence:** every other crate in the workspace (`core`, `identity`, `store`, `crypto`, `transport`, `signaling`, `proto`, `web`) has no config-file-reading code at all and is out of scope — there was nothing else to migrate. `figment` is a new external dependency in `apps/rendezvous` and `apps/cli`; it does not touch any `meridian-*` workspace crate, so it cannot trip `tools/lint-server-no-core.sh`'s "rendezvous depends only on `meridian-proto`" check.

**Update (task 4.13, Phase 4):** `meridian-core` now also depends on `figment`, `Json`-provider-only and no `Env` layer — condition (3) above (`account.json` gets no env override) relocated from `apps/cli/src/account.rs` into `apps/core/src/account.rs` verbatim, per [ADR 0020](./0020-tui-packaging.md)'s requirement that both `meridian-cli` and the future `meridian-tui` consume the same account/`$MERIDIAN_HOME` helpers from `meridian-core` rather than forking them. This is the first `meridian-*` workspace crate the "Consequence" paragraph above's blanket claim no longer covers; it does not touch `apps/rendezvous`, so the `lint-server-no-core.sh` invariant that paragraph exists to protect is unaffected — `meridian-core` is never on the rendezvous dependency path.
