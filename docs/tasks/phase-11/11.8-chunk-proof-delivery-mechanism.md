# 11.8 — Wire `FileReceiver`'s per-chunk verification into the real send path, or narrow the claim

**Phase:** 11 — Review of Phase 10 · **Feature:** review fix (F8) · **Depends on:** — (independent of 11.7 — see note) · **Status:** done

**User surface:** likely none if wiring a real caller (internal verification-path change to the existing
`meridian send`/receive flow, no new user-facing affordance); if the architect instead narrows the
claimed deliverable, the change is docs-only. Either way no new TUI surface is expected — confirm against
Definition of Done gate 9 once the mechanism is chosen.

## Goal
Give `FileReceiver`'s incremental per-chunk merkle verification a real caller in the shipped
`meridian send` path, or explicitly narrow the feature's claimed deliverable until it does — closing the
gap between what's tested in isolation and what the real CLI actually verifies.

## Scope
- **In:** an architect consult folded into this task (the decision is bounded to one wire-shape question
  rather than a whole new subsystem; if the consult surfaces a larger design question, split it out like
  Phase 10's 10.4-before-10.6 pattern before continuing) deciding the proof-delivery mechanism: extend the
  `ChunkFrame` wire shape with a proof field, or exchange a bulk proof set (or the flat leaf-hash list) once
  via `mrd.ctrl/1`, per `receiver.rs`'s own documented candidates. Then: wire the chosen mechanism through
  `apps/cli/src/send.rs`'s `run_responder`/`finalize_transfer` so `FileReceiver::receive_frame`'s real
  per-chunk verification actually runs in the shipped path, and update
  `docs/api/stream-types-v1.md`'s "Known gap" section to reflect the resolution.
- **Out:** if the architect instead decides to narrow the feature's claimed deliverable rather than wire a
  real caller, this task's scope becomes: update the feature spec / `stream-types-v1.md` to no longer
  claim "incremental subtree verification" as a shipped guarantee of the real CLI path, and leave
  `FileReceiver` as a tested-in-isolation engine for a future caller — explicitly recorded as a deliberate,
  documented choice, not silently dropped.

## Deliverables
1. Architect decision record (this task's own Risks/notes, or a short `/adr` if the architect judges the
   wire-shape change big enough — e.g. if it changes the pinned `ChunkFrame` shape 11.7 may have just
   vectored).
2. If wiring a real caller: the chosen mechanism implemented (wire-shape change in `apps/streams`/
   `meridian-proto` as needed, `apps/cli/src/send.rs` updated to supply/consume proofs,
   `FileReceiver::receive_frame` genuinely called from `run_responder`).
3. `docs/api/stream-types-v1.md`'s "Known gap" section and `apps/streams/src/receiver.rs`'s module doc
   both updated to match whichever resolution was chosen.
4. New/updated test(s) proving the real CLI path now runs (or, if narrowed, no longer falsely implies)
   incremental per-chunk verification.

## Risks / notes
This is the review's most architecturally significant should-fix. If the chosen mechanism changes
`ChunkFrame`'s wire shape, flag explicitly to whoever owns 11.7 (or, if 11.7 already landed, file the
resulting conformance-vector amendment as this task's own residual rather than silently leaving 11.7's
vector stale). `TODO: confirm` the proof-delivery mechanism with the architect before implementing either
half of this task.

### Architect decision record (this task's own required first step)
**Verdict: a consistent path forward exists; no ADR needed.** The architect rejected both candidate
directions **as literally written** and picked a third variant:

- **Option 1 rejected** (extend `ChunkFrame`'s wire shape with a proof field): amends an
  already-shipped, conformance-vector-pinned shape (11.7 landed before 11.8 started, deliberately
  sequenced that way per this task's own note) and is wire-inefficient — a `MerkleProof` for the
  feature spec's own 16384-chunk reference file is ~460 bytes/chunk, so summed across every chunk
  that's ≈7.5 MB of redundant proof data (shared internal-node hashes repeated across proofs) for one
  transfer.
- **Option 2 rejected as literally written** (bulk proof set / flat leaf-hash list via `mrd.ctrl/1` or
  the manifest): folding into `FileManifest` amends its own pinned, conformance-vectored 4-field shape;
  a new `mrd.ctrl/1` `CtrlFrame` variant repeats the exact "forces `CtrlFrame`/`session.rs::handle_ctrl`
  to grow a file-transfer-specific arm" mistake task 10.9's own review already rejected once for the
  resume bitmap (`docs/api/wire-protocol.md` §5's "Correction (task 10.12)").
- **Chosen: a flat leaf-hash list, sent once per transfer, as a new *in-stream* `mrd.file/1` frame
  kind** (`FRAME_TAG_LEAF_HASHES`), reusing the same tag-discriminator multiplexing mechanism task
  10.9 already shipped for the resume bitmap (`apps/streams/src/resume.rs`). This is additive — it
  touches neither `ChunkFrame`'s nor `FileManifest`'s pinned CBOR, and no `CtrlFrame`/core-crate
  change — so it stays within the additive-stream-type contract (root `CLAUDE.md` rule 3) and needs
  no ADR; it is precedent-matched to task 10.9's own architect-ratified-at-review in-stream design.
  ~14x cheaper on the wire than option 1 for the reference demo file (524288 bytes once vs. ~7.5 MB of
  redundant per-chunk proof data).
- **A real, concrete constraint the consult surfaced:** the SCTP association's negotiated
  max-message-size is 262144 bytes (task 10.18). A flat leaf-hash list is `leaf_count × 32` bytes — for
  the spec's own 16384-chunk demo file that's 524288 bytes, 2x over the ceiling in one frame. The
  eventual mechanism **must paginate** (multiple `FRAME_TAG_LEAF_HASHES` frames, reassembled before
  verifying the concatenated list's rebuilt root) — the same class of bug task 10.18 already had to fix
  once for `ChunkFrame`. Flagged here so a future implementer doesn't rediscover it the hard way.
- **11.7's conformance vectors are NOT triggered for amendment** by this decision (confirmed: neither
  `ChunkFrame`'s nor `FileManifest`'s pinned `encoded_hex` values are touched). A future implementation
  task will need its **own new** vectors for the new frame kind, mirroring how `ResumeRequest` got
  vectored — not an amendment of 11.7's existing ones.
- **`FileReceiver::receive_frame`'s signature will need to change** (confirmed, not just "may") when
  this is wired: its current per-call `proof: &MerkleProof` parameter doesn't fit a once-verified
  leaf-hash list. The future implementation should instead install a verified leaf-hash list once
  (e.g. a new `FileReceiver::install_leaf_hashes` step) before any `receive_frame` call is accepted.
  `apps/streams/src/merkle.rs` will also need a new `MerkleTree::from_leaf_hashes` constructor (it
  currently only exposes `from_chunks`/`from_bytes`, both of which hash raw chunk bytes into leaves).
- **DoD gate 9 (TUI surface): confirmed none.** Purely an internal wire/verification-path mechanism,
  mirroring the existing resume-bitmap precedent.
- **This task closes with the decision above, the doc narrowing (Option 3, landed in parallel — see
  Outcome), and this unowned carry-forward recorded**, per the task's own out-of-scope clause — the
  real wiring (pagination, the new `MerkleTree` constructor, the `FileReceiver` API change, and
  rewriting `run_responder`/`finalize_transfer` from whole-buffer-then-check-once to incremental
  per-chunk verification) is a genuine multi-part build effort, not a small fix, so it is split out
  into its own future build-phase task rather than crammed into this review-phase fix-task — mirroring
  the task's own invited 10.4-before-10.6 precedent. See the master tracker's carry-forward list.

## Outcome
Landed the Scope's "Out" path (narrow the claim), per the architect decision above: the mechanism is
chosen but its real wiring is deliberately deferred to a future build-phase task, not implemented here.

Docs updated at all three sites the decision touches: `docs/architecture/features/09-file-transfer.md`
(both the Scope "In:" line and the Acceptance criteria sentence — the first review round found the
Acceptance-criteria fix alone left the Scope line's own unqualified "incremental subtree verification"
claim standing, fixed in a follow-up commit), `docs/api/stream-types-v1.md`'s "Known gap" section
(rewritten to record the chosen mechanism and mark it not yet implemented), and
`apps/streams/src/receiver.rs`'s module doc (records `FileReceiver` as tested-in-isolation with no live
caller, points at the chosen mechanism, flags the future signature change). The master tracker's
pre-existing carry-forward bullet for this gap (originally from task 10.12) is updated to match, rather
than left stale — the first review round caught this gap too.

One new regression test, `apps/cli/src/send.rs::a_merkle_corrupted_chunk_fails_the_whole_transfer_not_just_itself`:
proves the real CLI path's whole-file-only merkle detection today — a chunk sealed correctly under its
own index (so AEAD authenticates) but carrying another chunk's plaintext fails the *entire* transfer,
discarding two other genuinely-correct chunks along with it, not just the corrupted one. No production
code changed; docs + one test only.

Combined architect/code-reviewer/security-reviewer pass, first round: architecture and security both
**PASS**; correctness **should-fix** (non-blocking) — the Scope-line overclaim and the master-tracker
carry-forward staleness above, plus this task file's own dangling "see Outcome" forward-reference before
this section existed. All three fixed in a same-task follow-up commit; a focused correctness
re-verification pass confirmed all three landed correctly with no regressions (architecture/security
were not re-implicated — the follow-up stayed docs + this Outcome section only). Tree green throughout
(`cargo test -p meridian-cli`/`-p meridian-streams`, `cargo fmt --all -- --check`,
`cargo clippy -p meridian-cli -p meridian-streams --all-targets -- -D warnings` in both default and
`--features webrtc` configs, `tools/check-docs.sh`).
