# 10.4 — Generalize the session substrate to drive a second stream type

**Phase:** 10 — File Transfer Stream · **Feature:** T09 (substrate completion, not the feature itself)
· **Depends on:** 10.1, 10.2 · **Status:** pending

## Goal
Complete the generic multi-stream machinery `apps/core/src/session.rs` was always meant to have but
never finished: today, `open_stream`/`handle_ctrl`'s `Open`/`Accept` arms negotiate a stream over
`mrd.ctrl/1` but never actually open a second WebRTC data channel, and `pump`'s demux only recognizes
the two hardcoded `CTRL_LABEL`/`CHAT_LABEL` channels — anything else is force-decoded as a ctrl frame.
This task makes the substrate able to drive **any** registered stream type generically, which every
future stream type (T10/T15/T16) needs identically, not just `mrd.file/1`.

**This finding and its fix shape were settled by an architect consult during `/plan-phase`** (see
[phase-10/README.md](./README.md)'s dependency-check/decisions section for the full record) — this task
file implements that decision, it does not re-open it.

## Scope
- **In:**
  1. Symmetric, explicit `transport.add_data_channel(...)` on **both** sides for a non-chat/ctrl
     stream — the responder calls it when deciding `OpenDecision::Accept` (alongside sending
     `CtrlFrame::Accept`), the initiator calls it on receiving `CtrlFrame::Accept`. Both derive the same
     channel label/negotiated id from the stream id (mirroring `CTRL_LABEL`/`CHAT_LABEL`'s existing
     `stream_id_for_label`-style symmetric pattern in `apps/transport/src/webrtc_backend.rs` — confirmed
     necessary because negotiated data channels do not fire an `ondatachannel`-equivalent event on a
     side that never called `add_data_channel` itself, and the loopback test transport also needs both
     sides to have called it to populate `P2pSession::labels`).
  2. Generalize `labels: HashMap<ChannelId, &'static str>` to hold dynamically-registered stream-type
     names (not `&'static str`-only), and add a `ChannelId ⇄ StreamId` bookkeeping map.
  3. Generalize `pump`'s demux: resolve a `ChannelId` to its stream type via the new label map, decrypt
     the frame generically (using task 10.1's export primitive, keyed by the stream's `type`/`sid`), and
     call the registered `StreamType::on_frame` with the decrypted bytes. Chat and ctrl keep their
     existing special-cased paths unchanged (no behavior change for `mrd.chat/1`).
  4. A new generic outbound path, `P2pSession::send_stream_frame(sid, bytes) -> Result<...>`, that
     encrypts (via 10.1's export) and sends on the stream's data channel — the only way a `StreamType`
     impl can ever push bytes out, since `on_frame` is synchronous with no return channel.
  5. A `buffered_amount`-backed backpressure query exposed alongside `send_stream_frame` (consumes
     task 10.2), so a sender engine (task 10.7) can throttle without this task inventing throttling
     policy itself.
- **Out:** **zero file-transfer-specific logic.** No mention of `mrd.file/1`, chunks, manifests, or
  merkle trees anywhere in this diff — this task must be reviewable as pure substrate completion that
  any future stream type benefits from identically. The `mrd.file/1` `StreamType` implementation itself
  is task 10.6 and must show zero diffs to this crate.

## Deliverables
1. Symmetric data-channel open on Open/Accept in `apps/core/src/session.rs`.
2. Generalized `labels` map + `ChannelId ⇄ StreamId` bookkeeping.
3. Generic decrypt-and-dispatch in `pump` for any non-chat/ctrl channel.
4. `P2pSession::send_stream_frame` + backpressure query.
5. Tests using the existing test-only `Exotic`-style stream type (already present in
   `apps/core/src/streams.rs`'s own test module) driven end-to-end over the loopback transport: open,
   accept, send a frame each way, confirm `on_frame` fires with correctly decrypted bytes, confirm
   backpressure query reflects a synthetic buffered-amount.

## Risks / notes
This is a `meridian-core::session` (core crate) change — legitimate per the architect consult (T04's own
scope note in `open_stream`'s doc comment already anticipated "T09 is the first second stream type to
drive it"), but the review gate below must explicitly confirm no file-type-specific logic leaked in;
treat any diff outside the generic label/dispatch/backpressure machinery as a review-blocking finding.

`docs/architecture/system-design.md` line ~202 says "the initiator opens" the data channel — this task's
actual (symmetric) implementation is more precise than that prose; task 10.12 records the `/doc-sync`
correction, this task does not need to edit system-design.md itself.
