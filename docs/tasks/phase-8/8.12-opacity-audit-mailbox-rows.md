# 8.12 — Opacity/at-rest audit extension for mailbox rows

**Phase:** 8 — Offline Ciphertext Mailbox · **Feature:** T07 · **Depends on:** 8.2 · **Status:** done

## Goal
Satisfy the feature spec's acceptance criterion "opacity audit covers at-rest DB pages (no
plaintext, headers encrypted)" — extend the existing opacity-audit harness rather than building a
new one.

## Scope
- **In:** extend `harnesses/opacity-audit` to scan the SQLite mailbox table's raw pages (once 8.2
  lands) for plaintext leakage — same technique the harness already applies to other tables
  (`prekeys`, `device_records`, etc.), reused, not reinvented. Confirm the header-encryption claim
  (Double Ratchet's encrypted-headers variant, system-design §4.3) holds for a mailbox-queued
  envelope exactly as it does for a live-routed one — this is a corollary of the transport-
  independence invariant 8.10 already exercises, checked here from the at-rest angle instead.
- **Out:** no changes to the ratchet/header-encryption code itself — this task is audit coverage
  only; if it finds a real leak, that becomes its own follow-up finding, not silently patched here
  without review.

## Deliverables
1. `harnesses/opacity-audit` extended to include the `mailbox` table in its page scan.
2. A test proving the harness actually detects a planted-plaintext regression (write a raw
   known-plaintext string into a mailbox row directly via the store's test-only path, confirm the
   harness's scan flags it) — the harness must be shown to actually work, not merely run clean by
   default.

## Risks / notes
An opacity audit that only ever passes proves nothing; the planted-plaintext non-vacuity check in
Deliverable 2 is the load-bearing part of this task, matching this project's established discipline
for every "prove the security property, don't just assert it" task (7.4, 8.9).

## Tests
`harnesses/opacity-audit/run.sh` (or whatever the harness's existing invocation is — follow its own
README).

## Reviews
- **security-reviewer** — the harness extension itself, and confirms the planted-plaintext test is
  a genuine non-vacuity proof.

## Status
**Done, with a corrected Scope.** This task's literal Scope description ("extend the existing
per-table raw-page scanner... the same technique the harness already applies to other tables
(`prekeys`, `device_records`, etc.)") does not match this codebase: those tables don't exist (the
real schema is `accounts`, `bundles`, `mailbox`), and no raw-DB-page scanner existed for any table
before this task — `run_audit`/`run_federated_audit` in `apps/cli/src/opacity.rs` only ever scanned
**wire transcripts**, never on-disk bytes. Verified independently by the reviewer via a full-repo
grep, not just accepted from the implementer's report.

Built instead: a genuinely new at-rest audit, `run_mailbox_at_rest_audit`
(`apps/cli/src/opacity.rs`), applying `run_audit`'s existing technique (seal a real envelope
carrying an unmistakable marker, scan captured bytes for it) to a real, file-backed `SqliteStore`
(task 8.2) read back as raw `.db` file bytes — exactly what an admin with filesystem access (threat
A7) would see. It also proves the header-encryption claim for a **mailbox-queued** envelope: two
identical-content envelopes are sealed and enqueued, and their stored blobs (read back via
`Store::mailbox_list_for_recipient`, not the in-memory bytes sent in) must differ. `#[cfg(test)]`
-only; `meridian-rendezvous`'s `sqlite` feature is enabled only on `apps/cli`'s **dev**-dependency,
never linked into the release `meridian` binary. Non-vacuity (Deliverable 2, this task's
load-bearing part) is `mailbox_at_rest_audit_catches_a_planted_plaintext_regression`: plants a raw,
literally-unencrypted marker directly via the production `Store::mailbox_enqueue` (bypassing client
sealing), closes the connection, reads raw bytes, and asserts the scan catches it. Wired into
`harnesses/opacity-audit/run.sh` as a new "no-plaintext-at-rest audit, mailbox rows" step; doc-synced
in `docs/testing/strategy.md`.

### Review round
**security-reviewer** — **PASS**, zero blocking findings. Independently confirmed (by reading the
diff directly, not the implementer's report): the Scope correction is accurate and the right call;
the store is dropped before the raw file read; the stored-blob comparison is load-bearing on what's
actually persisted, not the original in-memory blobs; the non-vacuity assertion cannot pass
vacuously (by hand-tracing `contains`'s logic); no ratchet/crypto files were touched, confirmed by
reading `apps/rendezvous/src/store.rs`/`store/sqlite.rs` in full; `#[cfg(test)]` gating and the
dev-only `sqlite` feature keep this out of the release binary; the harness wiring runs both new
tests with `set -euo pipefail` intact. The reviewer additionally checked a non-obvious way this
class of test could be silently vacuous — SQLite WAL mode diverting recent writes to an unscanned
`-wal` side file — by reading the vendored `sqlx-sqlite` source and confirming `SqliteStore::connect`
never enables it; today's `DELETE`-mode default is what makes the audit sound.

Two non-blocking should-fixes, **both fixed in this same commit**:
1. A doc-comment near the non-vacuity test called `mailbox_enqueue` a "test-only path" — inaccurate,
   since it's the general-purpose production method called directly with an unencrypted blob,
   skipping only the client-side sealing step. Reworded for precision.
2. The audit's correctness has an implicit, unenforced dependency on `SqliteStore::connect` never
   switching to WAL journal mode (which would move fresh writes to an unscanned side file, letting a
   real at-rest leak pass vacuously). Recorded as an explicit tripwire doc comment on
   `SqliteStore::connect` (`apps/rendezvous/src/store/sqlite.rs`) naming this task and the exact
   failure mode, so a future WAL-mode change is forced to reckon with it.

The reviewer's session had no Bash tool available and could not itself run the verification
commands; I ran them directly (see Definition of Done below) after applying its should-fixes.
