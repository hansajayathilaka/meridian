# 6.4 — `eid` replay-dedup key

**Phase:** 6 — Envelope v2 · **Feature:** ADR 0016 (C7, second half) · **Depends on:** 6.3 · **Status:** done

## Goal
Add the envelope-level dedup key `wire-protocol.md` specifies but today's implementation lacks, per
ADR 0016 C7 and the Phase-2/Phase-3 carry-forward obligation (task 2.13 only bounded a replay's harm to
one failed decrypt; full dedup via `eid` is this task's job — see
[docs/tasks/README.md](../README.md)'s "Live carry-forwards" and
[2.8](../phase-2/2.8-federated-route-reachability.md)).

## Scope
- **In:** `apps/envelope/src/envelope.rs` — add `eid: [u8; 16]` to `MessageEnvelope` v2.
  `apps/core/src/chat.rs` — a bounded, sealed-at-rest "recently seen `eid`" structure consulted in
  `open_bytes`.
- **Out:** server-side dedup (explicitly out of scope per task 2.8's "no s2s dedup" and `route`'s
  opaque-blob contract — the server never decodes envelopes); wiring `eid` into `apps/tui`/`apps/cli`'s
  own local-store `history/`/`outbox/` dedup (ADR 0021 already notes this as a separate future
  migration, not this task's job).

## Deliverables
1. `eid` field on `MessageEnvelope` v2, generated once in `seal_bytes` and reused verbatim on
   prekey-preamble re-attach for the same logical message (so a genuine unconfirmed-initiator
   retransmit dedups against itself, mirroring `ChatContent::Text.id`'s existing pattern and
   `data-model.md`'s "outbox... idempotent by eid").
2. A bounded seen-`eid` set in `ChatState`, consulted early in `open_bytes`, dropping a genuinely
   redelivered envelope without reprocessing it as new.
3. Explicit written decision (record in this task's Outcome section) on whether `eid` sits inside or
   outside the C3 canonical AAD. Recommendation: **outer plaintext, not part of the AAD** — the ADR's
   canonical AAD formula (`"mrd.env/2" ‖ AD ‖ prekey_preamble ‖ enc_header`) does not include it, and
   `eid` carries no confidentiality/authenticity requirement of its own (it is a dedup convenience, not
   a security boundary — see Risks).

## Risks / notes
- **This is a real design gap, not resolved by any existing doc — do not silently invent a security
  property `eid` doesn't have.** ADR 0016's R2 ("loss of the cheap pre-filter") stays the accepted
  residual: `eid` dedup is a redelivery/duplicate-processing convenience, explicitly *not* required to
  be a pre-crypto DoS filter. Framing it as a security boundary in code comments or docs would
  overclaim.
- `TODO: confirm` with **architect**: `eid`'s exact generation scheme (sender-random vs.
  content-derived — proposed: sender-random 128 bits), and the seen-set's bound/eviction policy
  (proposed: mirror `MAX_PENDING_REQUESTS`'s precedent — a fixed-size LRU, not literally unbounded).
  No design doc specifies these; an earlier draft of `wire-protocol.md §3` that had an `eid` field was
  itself disclaimed as wrong on a different axis (missing `sender_pub`), so it cannot be trusted as a
  template.
- Must not regress a genuine unconfirmed-initiator retransmit (same `eid`, same content, sent because
  the initiator hasn't seen a reply yet) into being treated as an attack or silently dropped in a way
  that breaks delivery — write a test for this exact case, not just the malicious-replay case.
- A flood of distinct `eid`s must not grow `ChatState` unboundedly — same test shape as
  `message_request_flood.rs`'s existing precedent (task 3.10).

## Outcome

**Implemented.** `eid: [u8; 16]` added to `MessageEnvelope` v2
(`apps/envelope/src/envelope.rs`), generated fresh in `ChatState::seal_bytes`
(`apps/core/src/chat.rs`) and checked in a new bounded, sealed-at-rest `ChatState::seen_eids`
set consulted at the very top of `ChatState::open_bytes` — immediately after the existing
`v`/`sender_pub` checks, strictly before any session lookup, provisional X3DH establishment, or
ratchet decrypt attempt. A match returns the new `ChatError::DuplicateEnvelope`; `seen_eids` is
populated only on a *successful* decrypt (all three of `open_bytes`'s `Ok` return points), never
speculatively. New test file `apps/core/tests/eid_dedup.rs` (3 cells, all independently confirmed
non-vacuous by temporarily disabling the relevant code and re-running — see below).

### Decision 1 — `eid`'s AAD placement: outer plaintext, NOT part of the AAD

Implemented exactly per the task's recommended default. `eid` is a plain struct field on
`MessageEnvelope`, positioned alongside `v`/`sender_pub`/`prekey` (never inside `ct`), and is never
threaded into `apps/crypto/src/ratchet.rs`'s AAD construction or into
`apps/envelope/src/envelope.rs::preamble_aad_bytes`. Reasoning (matches the task file's own,
confirmed by implementation): ADR 0016 C3's canonical AAD formula
(`"mrd.env/2" ‖ AD ‖ prekey_preamble ‖ enc_header`) does not include it, and `eid` carries no
confidentiality/authenticity requirement of its own. Concretely, `eid` is unauthenticated
outer-plaintext an attacker with byte access can freely read, omit, or vary — `ChatError::DuplicateEnvelope`'s
doc comment states this explicitly, and `apps/core/tests/desync_recovery.rs`'s replay cells now
rely on exactly this property (flipping a byte of `eid` on an otherwise byte-identical replay to
keep exercising the deeper `responder_session_ek` freshness gate independently of this new layer —
see `with_different_eid`'s doc comment there). No security assertion anywhere in the codebase treats
`eid` as authenticated or as a substitute for the ratchet AEAD / freshness gate.

### Decision 2 — generation scheme: sender-random 128 bits, freshly minted every `seal_bytes` call

Implemented per the task's recommended default: `getrandom::fill` into a `[u8; 16]`, the same CSPRNG
source and width `ChatContent::Text::id` already uses (`apps/cli/src/chat.rs::send_text`,
`apps/core/src/session.rs::send_chat`). RNG failure maps through the existing
`meridian_crypto::CryptoError::Rng` variant (already used identically by
`apps/crypto/src/primitives.rs`/`at_rest.rs`) via `ChatError::Crypto`'s `#[from]`, rather than adding
a new error variant for the same failure mode.

**Retransmit-reuse semantics — the specific design decision this task asked to be made and
recorded, not invented silently.** `seal_bytes` mints a **fresh** `eid` on *every* call; it has no
notion of "the same logical message" beyond the `plaintext` bytes handed to any one call, and does
not cache, hash, or compare across calls. The "reused verbatim on prekey-preamble re-attach for the
same logical message" property the task deliverable describes is achieved structurally, not by extra
bookkeeping inside `seal_bytes`: a genuine retransmit dedups against itself exactly when the
retransmission resends the *exact previously-produced envelope bytes* (the `Vec<u8>` `seal_bytes`
already returned) — never by calling `seal_bytes` a second time for already-sent content. Resent
verbatim, those bytes trivially carry the original `eid` (and prekey preamble, if any) unchanged,
which is what lets `open_bytes`'s dedup check recognize the redelivery.

This was a deliberate choice among two options, both considered:
- **(chosen) No sender-side content-comparison cache.** Simple, adds no new sealed-at-rest state on
  the sender side, and is safe by construction: since each `seal_bytes` call always mints a fresh
  `eid`, there is no risk of a cache bug accidentally deduping two *genuinely different* messages
  sent back-to-back while a session is unconfirmed (which a plaintext-equality cache could get
  wrong under hash/comparison edge cases, and which would silently drop a real message — a strictly
  worse failure mode than this task's chosen one, which never drops genuinely new content). The
  cost: a future retry/outbox mechanism that calls `seal_bytes` again for logically-the-same content
  (rather than replaying stored bytes) will mint a fresh, different `eid` — and, since
  `Session::encrypt` always advances the sending chain, a genuinely different `ct` — so the two
  envelopes will *not* dedup against each other. This is explicitly out of scope here:
  `docs/architecture/data-model.md`'s `outbox/` ("idempotent by `eid`") is a client local-store
  concern this task's own "Out" scope excludes (ADR 0021, a separate future migration), and no
  caller in this codebase today re-invokes `seal_bytes` for already-sent content — there is nothing
  to regress. `apps/core/src/chat.rs::seal_bytes`'s doc comment records this explicitly so a future
  retry/outbox task designs its own reuse strategy deliberately rather than assuming this method
  already provides one.
- **(rejected) A per-peer "last unconfirmed plaintext + eid" cache inside `ChatState`.** Would
  achieve dedup even across independent `seal_bytes` calls for identical content, but requires
  storing plaintext (or a hash of it) at rest specifically for this comparison — new sealed-at-rest
  state with no current caller to justify it, and a real risk of mis-deduping two coincidentally
  identical-content-but-distinct messages if not scoped with extreme care. Not built, per this task's
  "do not invent" instruction: no caller in this codebase needs it today.

### Decision 3 — bound/eviction policy: `MAX_SEEN_EIDS = 256`, oldest-first eviction

Mirrors `MAX_PENDING_REQUESTS`'s exact shape (`ChatState::seen_eids`/`seen_eid_order`, a
`BTreeSet`/`Vec` pair with insertion-order tracking; `record_seen_eid`/`evict_oldest_seen_eid` mirror
`insert_pending_request`/`evict_oldest_pending` line for line) and, per the task's own suggestion,
the **same numeric value**, 256.

Reasoning for the value, and for why this set is *not* subject to the identical attack shape
`MAX_PENDING_REQUESTS` bounds: unlike `pending_requests`/`responder_session_ek`, an `eid` is recorded
in `seen_eids` only on a **successful** decrypt (see `ChatState::seen_eids`'s doc comment), so an
attacker cannot grow this set for free with garbage ciphertext — every entry costs a genuine AEAD
success. It is still not literally unbounded: a flood of distinct, fresh identities each completing
one genuine (if pointless) OTK-free X3DH handshake against a victim — exactly `MAX_PENDING_REQUESTS`'s
own attack shape, since a first-contact envelope that lands in the gated request queue still commits
per ADR 0016 C2 and therefore still records an `eid` — is a real, if costlier, way to grow it (proven
non-vacuously by `apps/core/tests/eid_dedup.rs::seen_eid_set_is_bounded_under_a_flood_of_distinct_eids`).
256 is therefore set to the same value as `MAX_PENDING_REQUESTS` rather than a larger one, deliberately:
`eid` dedup is a **recent-redelivery** convenience (a relay retry landing twice, or a genuine
unconfirmed-initiator resend before a reply arrives), not a permanent replay ledger. An `eid` evicted
by this cap simply falls back to whatever protection existed before this task for that envelope
shape — the ratchet's own single-use-message-key discipline for an ordinary steady-state message
(confirmed empirically during development: redelivering an already-consumed steady-state message,
with the `eid` check disabled, fails with a generic `CryptoError::Crypto`, not a silent accept), or
the `responder_session_ek` freshness gate for a prekey-carrying one — never a silent acceptance.

### Retransmit-vs-replay semantics: what actually happens on a redelivered/retransmitted `eid`

**Silently no-op, never surfaced as an error the caller should act on, and never re-delivered.** On a
duplicate, `open_bytes` returns `Err(ChatError::DuplicateEnvelope)` — reusing `Result`'s error channel
for a non-fatal, distinguishable outcome exactly the way `ChatError::MessageRequest` already does
(task 2.10 precedent) — rather than re-decoding and re-returning the original content a second time.
Concretely:
- The content is **not** redelivered/re-processed: it was already delivered on the envelope's first,
  genuine arrival, so re-delivering it again would show the user (or a P2P `mrd.ctrl/1` consumer) the
  same message/frame twice.
- It is explicitly **not** classified as an attack: `ChatError::DuplicateEnvelope` is a distinct
  variant from `Desync`/`Crypto`/`UnknownPrekey`/`SenderMismatch`, all of which remain reserved for
  genuinely hostile or malformed input. `apps/core/tests/eid_dedup.rs::unconfirmed_initiator_retransmit_is_not_treated_as_an_attack`
  asserts this precisely — panicking if the retransmit case ever surfaces as one of those variants.
- No session, trust, request-queue, or OTK-pool state is touched (`seen_eids` itself is unchanged
  too, since the `eid` was already present — `record_seen_eid` is a documented no-op on an
  already-seen key).
- This is out-of-scope territory for actually *acting* on the duplicate signal at the caller level
  (e.g. showing a distinct "already sent" UI toast): `apps/cli`/`apps/tui` are explicitly untouched by
  this task, and their existing generic `Err(e) => eprintln!("! rejected an envelope ...")` fallback
  handles the new variant gracefully (harmlessly logs it) without any wiring change — a caller that
  wants richer UX for this specific outcome can match on `ChatError::DuplicateEnvelope` explicitly in
  a later task.

### Test non-vacuity — verified, not assumed

Each of the three new `apps/core/tests/eid_dedup.rs` cells was independently confirmed to fail against
code with the relevant mechanism disabled, then re-confirmed green against the real implementation:
- `redelivered_envelope_is_dropped_before_any_decrypt_attempt` — with the early `eid` check disabled,
  this cell fails because the duplicate instead surfaces as `ChatError::Crypto(_)` (the ratchet's own
  already-consumed-message-key rejection), not `ChatError::DuplicateEnvelope` — proving the pinned
  variant is genuine evidence the decrypt path was skipped, not an assumption.
- `unconfirmed_initiator_retransmit_is_not_treated_as_an_attack` — same technique, same result: the
  disabled-check run produces `ChatError::Crypto(_)`, which this cell's own match arms explicitly
  panic on as an "attack-shaped" misclassification.
- `seen_eid_set_is_bounded_under_a_flood_of_distinct_eids` — with the `MAX_SEEN_EIDS` eviction branch
  disabled, this cell fails with `left: 264, right: 256` (the flood's `MAX_SEEN_EIDS + 8` total),
  proving the assertion is sensitive to real unbounded growth, not vacuously true.

### Regression fixups required by this task's own behavioral change (documented, not silent)

Implementing the early `eid` check changes the classification of four **pre-existing** pinned replay
cells in `apps/core/tests/desync_recovery.rs` (they exercised `responder_session_ek`'s freshness gate
via a byte-identical replay of an already-succeeded opening envelope, which the new, earlier-running
`eid` check now intercepts first) and one in `apps/cli/tests/relay_attacks.rs` (`replay` — a real,
byte-identical relay redelivery). Both files are outside this task's literal "In" scope list, but the
change is a direct, necessary consequence of implementing deliverable 2 correctly, and leaving them
broken/vacuous would violate the "0 silent successes"/non-vacuity discipline this codebase holds
elsewhere:
- `desync_recovery.rs`: added a `with_different_eid` helper (flips one `eid` byte before replaying) so
  the four affected cells keep exercising `responder_session_ek`/the `UnknownPrekey`-after-pruning
  fallback specifically, independent of the new dedup layer — `eid` being unauthenticated,
  attacker-forgeable outer plaintext makes this a *more*, not less, realistic attacker construction.
  All four still assert `ChatError::Desync`, unchanged.
- `relay_attacks.rs::replayed_delivery_is_not_accepted_twice`: re-pointed at
  `ChatError::DuplicateEnvelope` (previously `ChatError::Crypto`/`ChatError::Desync`), with updated doc
  comments explaining the earlier rejection point; the session-survival assertions (task 2.13) are
  kept and still pass, now more trivially (the duplicate no longer reaches `Session::decrypt` at all).
