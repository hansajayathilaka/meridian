### 1. The live acceptance demo

Full transcript: [10.17-demo-transcript.md](./10.17-demo-transcript.md).

**Scope decision (real WebRTC only):** `meridian send` has no loopback-transport mode — confirmed
directly in `apps/cli/src/send.rs` (`#[cfg(feature = "webrtc")]`-gated with no alternative path) and
already stated in task 10.10's own Outcome. So this demo ran entirely over the real
`WebRtcTransport` backend, per this task's own option (ii): run as far as the real demo goes, and
document precisely what happens rather than substituting loopback or fabricating a pass.

**Part 1 — real `meridian send`, real rendezvous, real WebRTC: PASS.** A real, fresh two-identity,
two-process run (real `meridian id new`, a real in-process `meridian-rendezvous::serve`, real
`WebRtcTransport` host-candidate direct path) sent a genuine 208953-byte `/dev/urandom` file (4
chunks: 3 full 64 KiB + 1 short) end to end; the accept/reject prompt was answered live; both ends'
`sha256sum` are byte-identical. This is a real confirmation of task 10.18's SCTP `max_message_size`
fix **in the actual shipped CLI path** (not just its own unit-level regression test or the standalone
soak-test harness) — before 10.18, this exact scenario would have failed on the first full chunk.

**Part 2 — network cut + `ice_restart()` + resume: does NOT pass, live-reconfirmed.** `send.rs` has
zero automatic drop-detection/resume wiring of its own, so the spec's literal "same process narrates
cut→reconnect→resume" demo isn't reachable through the shipped CLI at all — only through task 10.15's
own dedicated test-only driver (`apps/cli/examples/kill_resume_netns_drive.rs`), which drives the
same real `meridian-core`/`meridian-streams` primitives `send.rs` itself uses. Running that harness
for real (`tools/netns-kill-resume.sh run`, real netns/veth, root available in this sandbox) with
task 10.18's fix landed: 15/24 real chunks (983040 bytes) send correctly before a genuine 15-second
veth cut; after the cut is restored, `ice_restart()` returns `Ok` on both sides and the receiver
correctly computes and sends a resume bitmap (9/24 missing — exactly right), but the sender never
receives that bitmap and the receiver never receives the resent chunks. This is exactly the
`WebRtcTransport::ice_restart` no-op gap `docs/tasks/README.md`'s "Live carry-forwards" section and
task 10.15's own Outcome already named — now independently reconfirmed live, for the real
`mrd.file/1` scenario (10.15's own live reproduction used only the smaller chat-only `probe`, since
the SCTP defect blocked `run` at the time). **This is a genuine, unfixed defect surfacing during this
task's own exit-gate run, exactly as the task's Risks section anticipated as a possible outcome — it
is recorded as a phase-exit-blocking finding, not silently downgraded to a partial pass.** Per this
task's explicit scope, it was not fixed here (closing it needs a real session-layer ctrl-channel
ICE-renegotiation design — architect-review territory, unrelated to anything file-transfer-specific)
— logged as a candidate gap-closure task in `docs/tasks/README.md`'s "Live carry-forwards" and
▶ NOW/NEXT sections instead, per the Phase 4 precedent this task's own file names.

**One new, independent bug found and worked around (not fixed) while preparing Part 2:**
`tools/netns-kill-resume.sh`'s own pre-flight self-check (`need_veth_linkstate`) names its probe
interfaces `kr-probe-a-$$`/`kr-probe-b-$$`; in this sandbox `$$` is a 5-digit PID, producing a
16-byte interface name that exceeds Linux's 15-usable-byte `IFNAMSIZ` limit, so the probe's own
`ip link add ... peer name ...` call fails and the script reports a false "not usable in this
environment — skipping" even though the real capability it needs (confirmed manually, and via the
script's own `run()`, which uses short fixed names) works fine. Worked around for this run only by
using a throwaway copy of the script with just the two broken pre-flight call sites no-op'd (its
actual `run()` logic, using the same real, unmodified short interface names, was not touched) — the
real script in the repo was not edited. Logged as a new carry-forward
(`docs/tasks/README.md`), not fixed here.
