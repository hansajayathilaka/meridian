# 8.16 — `meridian register` persists its published bundle's prekey secrets (fix-task, found during 8.14's live demo)

**Phase:** 8 — Offline Ciphertext Mailbox · **Feature:** T07 · **Depends on:** none (pre-existing, T01/T02-era) · **Status:** done

## Goal
Fix a real, confirmed, severe defect found while driving task 8.14's live same-server demo: the
standalone `meridian register` subcommand ("Register the current account with a rendezvous server
and publish a prekey bundle") publishes a bundle's **public** keys to the server, but discards the
matching **private** one-time-prekey and signed-prekey secrets entirely — never persisting them
anywhere, on disk or in memory. Any peer who X3DH-initiates against that published bundle produces
an envelope this account can **never** decrypt, not even in a later `meridian chat` run against the
very same account on the very same machine, because nothing durable ever recorded which secret
scalars the server's published public bundle corresponded to. This is not new to T07 — it is a
latent T01/T02-era gap in `cmd_register` — but it directly blocked an honest run of the mailbox
demo script (`meridian register` is the natural way to give an offline recipient a bundle to be
found offline against), so it must be fixed before 8.14 can close.

## Scope
- **In:** `apps/cli/src/main.rs::cmd_register` — currently calls `SignalingClient::publish_bundle`,
  reads only `generated.bundle.otk_count()` off the result, and discards `generated`'s secret
  scalars. Fix by routing through the same connect+publish+persist pattern
  `apps/cli/src/chat.rs::run` already uses correctly for its own bundle republish (see that
  function's "Publish a fresh bundle so the peer can reach us, and record the matching prekey
  secrets" comment): load (or default) the account's `ChatState`, call `publish_bundle`, install the
  returned secrets via `state.vault.set_bundle(...)`, and durably save the state
  (`sessions.bin`-equivalent) before returning — extracted as a new, small, reusable function in
  `chat.rs` (not duplicated inline in `main.rs`, and not a copy-paste of `chat.rs::run`'s own
  version) so there is exactly one place this connect+publish+persist sequence is implemented.
- **Out:** no wire-shape change (this is a purely local persistence gap, not a protocol issue);
  `chat.rs::run`'s own inline publish-on-connect logic is already correct and untouched;
  `rotate_spk_if_due`'s own separate publish+persist call is already correct and untouched.

## Deliverables
1. `cmd_register` durably persists the secrets matching what it publishes.
2. Regression test: `meridian register` followed by a **separate** `meridian chat` process
   invocation (a genuinely different OS process, not the same long-running session) against the
   same account must be able to decrypt an X3DH-opening message sent against the bundle `register`
   published.

## Risks / notes
This is exactly the kind of defect this project's own precedent treats as in-scope to fix on
discovery (task 6.3's desync fix, found the same way) — a genuine, severe, silent data-loss bug
(every message sent against a `register`-only-published bundle was permanently undecryptable),
not scope creep. Keep the fix itself minimal: the correct persist sequence already exists in
`chat.rs::run`; this task's job is to make `cmd_register` use the identical one, not invent a new
one.

## Tests
`cargo test -p meridian-cli --bin meridian` (existing suite stays green) plus the new regression
test above, in whichever file already covers multi-process CLI account-lifecycle behavior (or a new
one if none fits — follow this crate's existing `apps/cli/tests/` conventions).

## Status
**Done.** `cmd_register` (`apps/cli/src/main.rs`) now delegates to a new `chat::register_bundle`
(`apps/cli/src/chat.rs`), a byte-for-byte extraction of `run`'s own already-correct
connect→publish→`state.vault.set_bundle`→`save_state` sequence — `register_bundle` loads (or
defaults) the account's `ChatState` via the existing private `load_state`, publishes, installs the
returned secret scalars, and durably saves before returning. New regression test
`apps/cli/tests/register_persists_secrets.rs` drives three genuinely separate OS processes (a
`register`, then an X3DH-initiating peer, then a THIRD process for the account that ran
`register`) and asserts the third process decrypts the peer's message — the property that was
broken before this fix.

### Review round
