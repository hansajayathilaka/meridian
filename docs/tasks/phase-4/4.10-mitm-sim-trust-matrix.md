# 4.10 — `meridian-mitm-sim` trust-state matrix

**Phase:** 4 — Verification & Trust + Terminal TUI Client · **Feature:** T08 — Verification & Contact Trust · **Depends on:** 4.3, 4.4, 4.5, 4.9 · **Status:** done

## Goal
Prove, with the adversarial harness, that a fully malicious rendezvous cannot complete an undetected
MITM against a verified or pinned contact — the headline acceptance criterion of Feature 08 — including
that 4.9's guarded re-handshake is un-triggerable into a substituted key.

## Scope
- **In:** `harnesses/mitm-sim/` **already exists** (`run.sh` + `README.md`) and is explicit that T08
  extends it — do not delete existing cells. Add: substitute-key attacks against `tofu`, `pinned`, and
  `verified` states; a pass/fail matrix; a cell scripting an attacker substituting a key **during 4.9's
  bundle-refetch window** and asserting the recovery path blocks/warns per 4.4 rather than silently
  accepting it.
- **Out:** any change to the harness's existing pre-T08 cells except what's needed to add the new
  matrix.

## Deliverables
1. Extended `harnesses/mitm-sim/run.sh` + new test cell(s) for the trust-state matrix.
2. Pass/fail matrix output: 0 silent successes against `verified`; 0 successes against `pinned` without
   the exact `verification-ux.md` warning shown.

## Risks / notes
- This task is what actually proves 4.9's recovery path is safe — sequencing it after 4.9 (not just
  after 4.3/4.4/4.5) is required, not incidental: testing "un-triggerable into a substituted key" is
  meaningless before the re-handshake path exists.
- Do not weaken any existing harness assertion to make a new cell pass.

## Status
Done. `meridian_signaling::verify_bundle` pins every live fetch to the exact requested key
regardless of the caller's pre-existing trust state, so a network-level substitution never reaches
`TrustStore` at all — T02's existing `full_rendezvous_demo` already proved that for a fresh contact.
This task closed the two places that guarantee was not yet load-bearing:

1. **Network+CLI layer, pre-existing contact.** New `apps/cli/tests/mitm_preexisting_contact.rs`:
   a real `meridian-rendezvous` (`test-tamper-hook`) substitutes bob's bundle via the same
   `substitute_bundle` hook T02 uses, but this time against an alice who already has a pinned
   contact record for bob (`meridian contact add`). Proves the tampered fetch fails closed
   identically (`FATAL: bundle signature does not match requested identity`, non-zero exit) *and*
   that the failed attempt leaves the pre-existing trust record byte-identical (`contact list
   --json` snapshot, `TrustStore` is a `BTreeMap` so the comparison is order-stable) — no phantom
   `PinnedKeyChanged`/`Blocked` state, no new contact row for the attacker's key. Confirmed
   structural, not just empirical: `cmd_fetch_bundle` never touches `TrustStore` at all today.
2. **Decision-gate layer, task 4.9's recovery window.** The one path where a genuinely different
   signing key can legitimately reach `TrustStore` (`crate::desync::attempt_recovery`, since every
   live fetch is exact-key-pinned per (1)). Extended the existing
   `apps/core/tests/desync_recovery.rs::attempt_recovery_routes_a_surfaced_key_change_through_the_gate_never_bypassing_it`
   with canonical-wording assertions (mirroring `key_change_gate.rs`'s wording checks, same
   underlying `trust.rs` format strings, not a paraphrase) for both its `Pinned` (→ `Warn`) and
   `Verified` (→ `Blocked`) starting-state cases, plus a check that `acknowledge_key_change` is
   refused outright against the `Blocked` case even from the state `attempt_recovery` itself just
   produced (not a fresh `TrustStore`).

No separate live "tofu" cell: `cmd_fetch_bundle`'s fetch-layer defense is exact-key pinning, which
doesn't branch on trust state at all, so a from-scratch live cell would exercise byte-identical code
to the pinned cell above; and desync recovery is only reachable once a session already exists, so a
tofu-starting-state variant there would be vacuous. Documented transparently as a scope boundary in
`harnesses/mitm-sim/README.md`, not silently assumed. `harnesses/mitm-sim/run.sh` gained a labeled
T08 section wiring both cells plus the existing gated-then-cleared recovery test, ending in an
explicit printed pass/fail matrix (tofu / pinned / verified × attack); `README.md`'s cell table and
scope-boundary notes were extended to match, without touching or weakening any pre-existing cell.

**Reviews:** security-reviewer and test-engineer both signed off with zero findings, each
independently re-deriving the load-bearing claims from source rather than trusting the test files'
own doc comments — confirmed `cmd_fetch_bundle` structurally never reaches `TrustStore`; confirmed
`observe_key_change`'s only non-test production call site in the whole codebase is
`apps/core/src/desync.rs`; confirmed `chat.rs`'s ordinary send path never re-fetches a bundle outside
the initial-session and 4.9-recovery call sites; confirmed a third fetch call site
(`session_connect.rs`) shares the same `SignalingClient::fetch_bundle`/`verify_bundle` choke point
and touches no persisted trust state either, so it isn't a hole in the scope-boundary reasoning; and
confirmed none of the new wording assertions could be satisfied by a softened/degraded message.

Full harness (`bash harnesses/mitm-sim/run.sh`) passes end to end, exit 0, including every
pre-existing T02/T04/1.28/1.32/2.12 cell. `cargo fmt --check` and `cargo clippy --workspace
--all-targets -- -D warnings` clean.
