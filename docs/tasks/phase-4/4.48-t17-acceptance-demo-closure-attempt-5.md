### The defect: the accepted sender's intro message is silently, permanently dropped from the responder's own history

**Found by the second (genuinely independent) live run, missed by the first.** Symptom: right after a
responder accepts a message request and opens Chat, the transcript shows `(no messages yet)` — the
sender's intro message, visible moments earlier in the Requests detail pane, is gone. Confirmed
permanent across two separate restarts, both account types, with direct decrypted on-disk proof via
`--export-json`: the responder's own `history.jsonl` for that peer contains only their own reply, never
the sender's original intro.

**Root cause, independently confirmed from source by a third pass** (not trusting either live run's
report): `worker::run_accept_request` (`apps/tui/src/worker.rs:1245-1288`) writes exactly three
documents — `sessions.bin` (`chat.accept_request`), `trust.bin` (`trust.observe`), `contacts.json` — and
never writes `history.jsonl`. `ChatState::accept_request` returns `Option<MessageRequest>`, and
`MessageRequest.intro: ChatContent` genuinely carries the decrypted first payload — it is in hand at
exactly the point it's needed, collapsed to `.is_some()` and discarded at `worker.rs:1254`. Persisting it
would be a local, straightforward addition (build a `HistoryEntry` from the returned `MessageRequest`
and call `history::append`), not a data-availability problem. Severity is narrow, also confirmed from
source: `App::handle_inbound`'s `InboundEvent::Message` arm unconditionally dispatches
`Effect::PersistHistory` for every ordinary message before and after the accept, in both directions — the
gap is confined to exactly the one intro message bundled into the original request, not a general
history-persistence defect.

**Corroborating evidence the crate's own test suite already knew about this.** `apps/tui/tests/
live_session_e2e.rs:617-651` manually extracts the intro and calls a hand-rolled `persist_entry(...)`
helper immediately after dispatching `AcceptRequest`, precisely because production code doesn't do this
— the crate's own regression suite has been compensating for the gap in the test itself, not catching
it.

**Already flagged and deliberately deferred once — then dropped, not tracked.** `AcceptRequestRequest`'s
own doc comment (`apps/tui/src/app.rs:684-703`) and
[4.42's own Status section](./4.42-post-accept-chat-affordance.md#status) both explicitly named this
gap and deferred it, reasoning "reader-before-second-writer is the honest sequencing" and citing 4.44 as
owning "the reader half." **[4.44](./4.44-chat-history-load-on-open.md) built only the reader**
(`Effect::LoadHistory`/`apply_loaded_history`) — its own Scope's "Out" list explicitly excludes "4.42's
and 4.43's concerns," i.e. the writer side was scoped out on purpose. No later task ever picked up the
writer half, and — independently confirmed — the gap is **not** listed in
[phase-4/README.md](./README.md#tasks-todo)'s "Findings with no task yet" section, so it evaporated from
the tracker between being named and now, rather than being silently absorbed by a later task.
