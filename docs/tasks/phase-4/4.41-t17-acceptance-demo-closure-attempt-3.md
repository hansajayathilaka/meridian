### Approach: live PTY driver (methodology, condensed — full rationale already on record from 4.38)
Same overall approach as 4.38's own Evidence 1 (a throwaway Python script, stdlib `pty`, spawning the
real `target/debug/meridian tui` binary under a real pseudo-terminal against a real
`target/debug/meridian-rendezvous --config apps/rendezvous/demo.toml`), extended in two ways this attempt
actually needed:
- **`pyte`** (available in this sandbox, not previously used) for real terminal-emulator screen-buffer
  parsing instead of raw-output regex matching — more reliable across ANSI cursor movement/redraws.
- **Two concurrent PTY sessions, in two Python threads**, each driving a separate `meridian tui` process
  against separate temp `$MERIDIAN_HOME`s, synchronized on a `threading.Barrier` once both reach a live
  `Screen::Main` — needed because, unlike 4.38's single-account run (which stopped at the first
  contacts/trust error), this task's own mandate is to drive a **real two-peer exchange live through the
  UI**, which needs both peers' processes running and connected concurrently, exactly as
  `live_session_e2e.rs`'s own module doc explains for the same reason (offline delivery isn't built yet —
  T07 — so a message routed while the recipient isn't already connected is simply dropped).

Nothing checked in; the driver scripts and full raw transcripts live only in this session's scratchpad.

**Two bugs in the driver itself, found and fixed before trusting any result** (named here because both
briefly produced misleading failures that were driver bugs, not product defects — the same discipline
4.38's own Evidence 1 held itself to about distinguishing script bugs from real ones):
1. A screen-matching regex assumed "mrd1 id: or QR image path:" renders on one line; it actually renders
   as two separate lines ("mrd1 id:" / "or QR image path:"), and the em-dash in the Chat screen's title
   is one character, not two, breaking a naive `..` wildcard match. Fixed by matching narrower, single-line
   anchors ("mrd1 id:", "Enter send").
2. **The more important one:** initial role-assignment logic (which peer is the X3DH *initiator*, per
   `worker::run_send_message`'s own `account_pub.as_slice() <= peer_pubkey.as_slice()` rule) compared the
   two peers' `mrd1:` id strings as **ASCII text**. This is wrong: `meridian-identity`'s base32 alphabet is
   `"abcdefghijklmnopqrstuvwxyz234567"` — letters `a`–`z` encode values 0–25, but digits `2`–`7` encode
   values 26–31, which is the *opposite* of their ASCII order (digit code points are numerically lower
   than letters). A naive string comparison of the id text therefore does not agree with the byte-order
   comparison of the raw pubkeys the app itself performs, and picked the wrong "initiator" about half the
   time. First run: script assigned peer A as initiator; app correctly refused
   (`message not sent: sealing message: no session and no prekey preamble to establish one` — exactly
   `run_send_message`'s own documented non-initiator-with-no-session behavior, working as designed).
   Fixed by decoding the base32 key part properly (unsigned 5-bit accumulation) and comparing the raw
   32-byte pubkeys, matching the app's own rule; every run after that fix picked the correct role and sent
   successfully. Flagged in detail because it is exactly the kind of harness bug this task's own governing
   note ("never weaken a security assertion... fix root causes") requires distinguishing from a real one
   before reporting anything — this was the driver, not the app.

### Evidence 1 — OS-keystore now works live in this sandbox (contrary to 4.38's own finding — reverified, not assumed)
4.38's Evidence 3 found `keyring::Entry::new(..)` failing with "no secret service provider or dbus session
found," tried `apt-get install gnome-keyring dbus-x11` plus several `dbus-launch`/
`gnome-keyring-daemon --login`/`--unlock` combinations, and concluded the sandbox could not bind a working
control socket. Re-verified directly here, not assumed still true: the same failure **does** reproduce
with no keyring installed. But installing `gnome-keyring` + `dbus-x11` (`apt-get update` first — the
initial attempt without it hit a stale mirror 404 on an unrelated `libgtk-4-common` transitive dependency)
and using **`gnome-keyring-daemon --components=secrets --unlock`** (not `--start --unlock` together — the

`dbus-launch`-started session bus, with `$HOME` pointed at a private, empty scratch directory, produces a
working control socket. A minimal Rust probe (`keyring::Entry::new(...).set_password(...)`) then succeeds,
and so does the real binary: `MERIDIAN_HOME=<tmp> meridian id new --store os` under that environment
prints a real `mrd1:...` id with no error. This sandbox's own keystore limitation is real but **narrower
than 4.38 found** — a different daemon invocation than 4.38 tried works. Documented explicitly (not
silently) since the task instructed verifying this directly rather than assuming 4.38's finding still

### New finding — Defect C (working number 4.42): no live-UI path to reply to (or verify) an accepted message-request sender
Reproduced live, identically, for both account types (Evidence 2 and 3 above). Root cause traced fully in
the source, not guessed:
- `apps/tui/src/worker.rs::run_accept_request` (the real handler behind `Effect::AcceptRequest`) writes
  exactly two sealed files — `sessions.bin` (`chat.accept_request`) and `trust.bin`
  (`trust.observe(sender_ik, "", now_unix())`) — and **never** touches `contacts.json`.
- `apps/tui/src/screens/main.rs::build_contact_entries` (the join that builds every row
  `Screen::Main`'s Contacts pane renders) is driven by `contacts.contacts` (the `contacts.json` document),
  not `trust.contacts()` — deliberately, so a locally-deleted contact stays removed even though its
  `TrustStore` record survives (see that function's own doc comment). The same doc comment already named
  the resulting gap as a `TODO: confirm`, unresolved, during task 4.36: *"A `TrustStore` contact with no
  matching `contacts.json` row at all — reachable today only via `Effect::AcceptRequest`'s own
  `TrustStore::observe` call... is invisible to this join entirely."* This task is the first to actually
  reach that exact state live (every earlier attempt hit Defect A or B first) and confirm what it means
  end to end: **the accepted sender never appears in the Contacts list, at all, ever** (confirmed a restart
  would not help either — `contacts.json` on disk genuinely has no row to reload; not just an in-memory
  staleness issue).
- `apps/tui/src/screens/requests.rs::handle_worker`'s `Effect::AcceptRequest` success arm only removes the
  entry and returns to `RequestsMode::List` — it returns no action that could open a `Screen::Chat` (unlike
  `crate::screens::main::MainAction::OpenChat`, which `contacts::handle_key`'s `Enter` on a *known* contact
  row produces). There is no other affordance anywhere: `apps/tui/src/app.rs::register_builtin_commands`
  registers exactly two palette commands (`nav.diagnostics`, `nav.settings`) — no chat-related command
  exists to reach a non-contact peer either. And even if a user tried to work around it by adding the
  sender as an ordinary contact afterward, `requests.rs`'s own request-detail view never shows the sender's
  full `mrd1:...@hint` id or hint — only a truncated pubkey fingerprint (`short_pubkey`) — so there is no
  value in the UI a user could paste into `n`'s "add a contact" form even if they thought to try.
- A second inbound message from the same (still non-contact) sender, arriving later while no matching
  `Screen::Chat` is open (which it structurally can never be), is silently written to `history.jsonl` via
  `Effect::PersistHistory` and never surfaced in the UI at all (`apps/tui/src/app.rs::handle_inbound`'s
  `InboundEvent::Message` arm) — traced, not exercised live a second time here (would just re-confirm the
  same root cause at extra time cost for no new information).

**Practical effect on the T17 acceptance demo:** the demo script's own "accept → both sides chat; ^V
shows the same 60-digit safety number on both → mark verified" step cannot be completed through the live,
interactive TUI as it exists today, for either account type. The initiator's side of a first-contact
exchange works completely (add, chat, verify are all reachable, since the initiator's own `AddContact`
call did put a `contacts.json` row in place). The responder's side stops at "sees and can correctly decode
the request" — genuinely proving Defect A is fixed — but can go no further live. This is a different,
new, third defect, not a re-manifestation of Defect A or B: both of those are confirmed independently
fixed by the same evidence above (a broken republish or a fail-closed file-backed store would have
prevented reaching this point at all).

**Not fixed here, per this task's own explicit, non-negotiable scope.** Needs a new task, working number
**4.42** — likely shape: either synthesize a minimal `contacts.json` row on accept (a real product/UX
decision the task's own pre-existing `TODO: confirm` already flags as needing a design call, not an
implementer's unilateral choice) or give `Screen::Requests`' accept action a real `OpenChat`-style
transition, mirroring `MainAction::OpenChat`. Either shape is a genuine design decision, not a mechanical
fix, and belongs behind the same kind of pre-code architect/security-reviewer consult 4.40 held for its
own comparably-shaped decision — not decided unilaterally in this verification-only task.
