# 4.5 — Safety-number compare UX primitives + `meridian verify`

**Phase:** 4 — Verification & Trust + Terminal TUI Client · **Feature:** T08 — Verification & Contact Trust · **Depends on:** 4.3 · **Status:** done

## Goal
Build the compare/verify UX on top of T03's already-landed safety-number computation
(`apps/crypto/src/fingerprint.rs`), and freeze it into conformance vectors — the last piece before any
client can actually run a verification.

## Scope
- **In:** `meridian verify <mrd1-id>` CLI command: 60-digit number + QR display
  (`meridian_identity::qr::render_terminal`, already exists — no new QR primitive needed),
  `--scan-file` headless compare (`decode_luma`, already exists), calls `trust.mark_verified` on match.
  Freeze `fingerprint.rs`'s output into `test-vectors/` fixtures: order-independence
  (`safety_number(a,b) == safety_number(b,a)`), byte-identical output for fixed inputs — future
  browser/mobile clients must match byte-for-byte.
- **Out:** the TUI's Verify screen (4.22, consumes this); trust-state transitions beyond `mark_verified`
  (4.3/4.4 own those).

## Deliverables
1. `apps/cli/src/verify.rs` (or equivalent): `meridian verify` command + `--scan-file`.
2. `test-vectors/`: new safety-number fixture, generated via `cargo run -p xtask -- vectors` (never
   hand-edited).
3. Tests: order-independence, vector byte-identity, CLI round-trip (generate → scan → verified).

## Risks / notes
- No new crypto here — `fingerprint.rs` computation is frozen, not changed. If this task seems to need
  a new primitive, that's a planning defect per root CLAUDE.md — stop and raise it.

## Status
Done. New `apps/cli/src/verify.rs`: `meridian verify <id> [--scan-file <path>]`, calling only
already-frozen `meridian_crypto::fingerprint::{safety_number,display_groups}` and
`meridian_identity::qr::{render_terminal,decode_luma}` — no new cryptographic construction, per the
task's own risk note. Interactive mode prints the number+QR and requires an explicit `y`/`yes` (fails
closed on non-TTY, blank, EOF, or any other input); `--scan-file` does a full exact-string compare of
the decoded digits against the locally computed number (no prefix/fuzzy match). Either path, on
success, calls the existing `TrustStore::mark_verified` (4.3/4.4, unchanged) and persists.

The vector-freeze deliverable (`test-vectors/safety-numbers-v1.json` + `tools/xtask/src/vectors/
safety_numbers.rs` + `apps/crypto/tests/conformance.rs`'s `safety_number_vectors_match_real_computation`)
was **already landed by task 1.6** and confirmed still adequate against current `fingerprint.rs` — no
new vector work needed here, only verified.

Combined **reviewer** pass (required) passed clean on every checked angle (no new crypto, fail-closed
confirm, exact-match compare, clean unknown-contact error, `image` dependency addition scoped
correctly, vector-freeze genuinely adequate) with two non-blocking test-coverage suggestions, both
applied before closing: extracted the y/N confirm parse into a pure `is_affirmative` function with 4
new direct unit tests covering the fail-closed cases (blank, explicit no, garbage, only-exact-y/yes) —
this gates `TrustState::Verified`, the system's strongest trust guarantee, so it now has regression
coverage independent of a real TTY; and strengthened the unknown-contact integration test to assert no
contact record was created at all (not just that verification didn't succeed).
