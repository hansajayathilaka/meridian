# 8.13 — Cross-federation acceptance test (Org A sender → Org B mailbox → reconnect)

**Phase:** 8 — Offline Ciphertext Mailbox · **Feature:** T07 · **Depends on:** 8.6, 8.7, 8.9 · **Status:** done

## Goal
Prove the feature spec's "works across federation" scope item end-to-end on the real two-org demo
stack, not just via unit/integration tests of individual handlers.

## Scope
- **In:** an automated test driving `demo/two-orgs/` (or its test-harness equivalent, per 3.4's
  shared s2s test harness precedent): Org A's client sends to an offline Org B recipient, confirms
  the envelope queues at B (via 8.11's `meridian-admin mailbox dump` against B, or a direct store
  check), then brings B's client online and confirms delivery + ack + row deletion, matching 8.7's
  single-server test but across the real mTLS federation link.
- **Out:** this is not the phase-exit demo (8.14) — it's the automated regression test proving the
  cross-org path works, which 8.14 then also demonstrates live/manually per the feature spec's own
  demo script.

## Deliverables
1. Test using the shared federation test harness (task 3.4) plus 8.1/8.2's store and 8.11's dump
   tool, exercising the full A→B-offline→queue→B-reconnect→deliver→ack→delete path.
2. Confirms the sender-visible outcome matches this phase's recorded decision: A's client sees
   `RouteOk{delivered:true}` (optimistic, per 8.6), while B's mailbox is the actual, verifiable
   proof of queuing — assert both, so the test documents the real behavior rather than an idealized
   one.

## Risks / notes
Don't let this test silently assume TLS/discovery setup that isn't representative of a real deploy
— reuse 3.4's harness exactly as prior federation-test tasks did, rather than hand-rolling a new
test-only federation topology.

## Tests
`cargo nextest run -p meridian-rendezvous --test federation_mailbox` (or wherever the shared s2s
test harness's existing federation tests live — follow that file's location).

## Status
**Done, with one scope correction from the literal Deliverable wording (documented below, precedent:
8.10/8.12).** New file `apps/rendezvous/tests/federation_mailbox.rs`, using the shared federation

servers over a real s2s mTLS link, per Deliverable 1.

**Scope correction — why the queuing half isn't driven through Org A's own `route_with_hint`:**
while writing this test it became clear (and was independently confirmed twice more below) that
Org A's real outbound path, `route_foreign` (`apps/rendezvous/src/federation/outbound.rs`),
pre-checks target liveness via a real `FedReachability` round trip to B (architect decision #3)
*before* it ever sends the actual `FedRoute`. A recipient that never connected to B at all is
`not_connected` *at A* before B's `handle_fed_route` runs at all — task 8.6's own Status section had
already independently discovered and documented this exact structural fact ("only through a narrow,
unconstructable pre-check/delivery disconnect race — not something a fast, non-flaky test can
construct"), reviewed clean at the time. This session reconfirmed it empirically: an initial version
of this test drove the whole path through `route_with_hint` with Bob genuinely never connected, and
both cases (offline-queue, over-quota-offline) failed identically with `not_connected` before ever
reaching B's mailbox logic. So, matching 8.6's own resolution, both tests instead call the real,
`pub` `handle_fed_route` — the exact function `serve_link` dispatches an inbound `FedOp::Route` frame
to — directly, but against Org B's REAL, LIVE `AppState` fields (`pair.b_state.registry`,
`.federation.policy`, `.federation.limits`, `.metrics`, `.store`, `.config.mailbox`, pulled from the
actually-booted B server via `boot_federated_pair`), not the fresh, disposable test doubles 8.6's own
unit-level tests used. This is strictly more end-to-end than 8.6's coverage: same real production
dispatch target, now wired to the real running server's state, with the *rest* of the path — Bob's
real `SignalingClient` connecting for the first time over the real c2s WebSocket, draining the
queued row, acking it (task 8.8), and the row's deletion — driven fully live, never mocked.

Two tests:
1. `federated_enqueue_against_bs_real_live_state_queues_then_drains_reconnect_ack_delete` —
   Deliverable 1's primary path: enqueue via the federated code path against B's real state, confirm
   the durable row via B's live store, then Bob connects for real and the row drains
   (`Deliver{mailbox_id: Some(_), from: MAILBOX_DRAIN_FROM_PLACEHOLDER}`), is acked
   (`SignalingClient::ack_pending_mailbox`), and is verifiably deleted from B's live store afterward
   — task 8.7's reconnect/ack/delete cycle, now proven for a row that arrived via the FEDERATED
   enqueue path specifically, across a real client and a real link.
2. `federated_enqueue_against_bs_real_live_state_over_quota_is_rejected_not_a_silent_drop` —
   Deliverable 1's quota-exceeded angle against B's real live state: `Err(FedErr{mailbox_full})`,
   never a silent drop, never any `Ok`-shaped outcome, and no partial row left behind.

**Deliverable 2's `RouteOk{delivered:true}` half:** since the queuing scenario can't be driven
through the real client wire path (above), this test doesn't itself assert `RouteOk{delivered:true}`
for a queued route. It holds by construction instead, and is recorded here per the
security-reviewer's should-fix so a future reader doesn't have to re-derive it: `handle_federated_route`
(`apps/rendezvous/src/ws.rs`) maps ANY `Ok(())` from `route_foreign` to
`RouteOk{delivered:true, queued:false}` completely unconditionally — the match arm has no branch on
*how* B's `handle_fed_route` produced that `Ok(())` (live deliver vs. mailbox enqueue). This test
proves the offline branch really does return `Ok(())` against B's real state (test 1 above);
`federation_route.rs::federated_route_delivers_byte_identical_envelope` (task 2.8) already proves
live that a real client sees `delivered:true` for a real federated `Ok(())`. Composed, A seeing
`delivered:true` for a route that actually queued follows necessarily — the documented optimistic-ack
residual from this phase's own architect consult (point 2) — even though the specific "both observed
in one wire round trip" moment can't be constructed deterministically for the reason above.
