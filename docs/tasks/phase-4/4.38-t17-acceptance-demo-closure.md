### Evidence 2 — the new two-process regression test, and the defect it found
`apps/tui/tests/live_session_e2e.rs` (new, registered in `apps/tui/Cargo.toml` with `harness = false` —
see that file's own module doc for the full design rationale: two literal, separately-launched OS
processes, not two in-process actors sharing the process-global `$MERIDIAN_HOME`, driving the real
`meridian_tui::worker::dispatch`/`run_inbound_loop` — the exact functions `crate::run_worker`'s live
event loop calls — end to end over a real in-process `meridian-rendezvous`). Both peers are OS-keystore
accounts (via the sanctioned `install_mock_keystore()` pattern `run_worker_contacts.rs`/
`run_worker_trust.rs`/`run_worker_chat.rs`/`inbound_delivery.rs` already use), specifically so the
already-known file-backed gap above doesn't block it — this test's job is to reach *past* that gap and
prove (or disprove) the rest of the flow. It doesn't currently pass:

Reproduced consistently across multiple runs (not a flake — different random accounts each time, same
failure every time). **Root cause, traced fully, not guessed:** `SignalingClient::publish_bundle`'s own
doc comment says it "[r]eturns the generated bundle *and its secret scalars* for the caller to persist."
`apps/cli/src/main.rs::cmd_register` (the exact call sequence `worker::handle_publish_bundle` mirrors)
never persists them — a real, pre-existing gap in the CLI too, but a harmless one there, because
`apps/cli/src/chat.rs::run` (the CLI's actual "start chatting" entry point) unconditionally republishes
its **own** fresh bundle — `client.publish_bundle(...)` immediately followed by
`state.vault.set_bundle(...)` and `save_state(...)` — every single invocation, before it is ever capable
of receiving anything. **`meridian-tui` has no equivalent step anywhere** — grepped the whole crate:
`Effect::PublishBundle` is dispatched exactly once, from `apps/tui/src/screens/onboarding.rs`, and
nowhere else (not `Screen::Main`'s construction, not `inbound_handoff`/`run_inbound_loop`'s spawn, not a
later `Unlock`/`LoadSession`). The one bundle a T17-onboarded account ever publishes is therefore always
the vault-less one, and it is the only bundle a peer can ever X3DH-initiate against — when they do,
`meridian_core::chat::ChatState::open_inbound` cannot resolve the OTK/SPK secret scalar (`PrekeyVault`
never had them) and fails closed with `ChatError::UnknownPrekey`, which `process_inbound_delivery` drops
silently (an `eprintln!` only — the exact line visible in peer a's stderr above). **This blocks the T17
demo's core "peer sees a message request" step for every account type**, not just file-backed — this is
a materially different, more fundamental defect than the one Evidence 1 reproduces, discovered only
because this task built genuine two-process coverage that (correctly) refuses to route around it.

### Evidence 3 — why OS-keystore couldn't also be confirmed via a live PTY session
Confirmed directly, not assumed: `keyring::Entry::new(...)` in this sandbox fails with "no secret
service provider or dbus session found" (matches `tests/load_session.rs`'s own already-documented
precedent). Attempted to fix this properly rather than accept it immediately: installed `gnome-keyring`
+ `dbus-x11` via `apt-get` (network reachable through the environment's proxy) and tried
`dbus-launch`/`gnome-keyring-daemon --login`/`--unlock` in several combinations — every attempt failed to
bind a working control socket in this specific sandbox (spurious "address already in use" against a
freshly-created, empty directory, suggesting a sandboxing restriction on the daemon's own fork/bind
behavior, not a fixable configuration issue). Concluded this is a genuine environment limitation, not
worth further engineering effort to route around, and relied instead on Evidence 2's own OS-keystore
coverage (via the sanctioned in-process mock, exercising the identical `worker.rs` code paths) for that
account type — the root cause found there (missing bundle republish) lives entirely in `worker.rs`/
`meridian-core`, not in any screen, so there is no reason to expect a real OS-keystore account driven via
an actual `meridian tui` PTY session to behave any differently.
