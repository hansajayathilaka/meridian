# 6.4 — `eid` replay-dedup key

**Phase:** 6 — Envelope v2 · **Feature:** ADR 0016 (C7, second half) · **Depends on:** 6.3 · **Status:** pending

## Goal
Add the envelope-level dedup key `wire-protocol.md` specifies but today's implementation lacks, per
ADR 0016 C7 and the Phase-2/Phase-3 carry-forward obligation (task 2.13 only bounded a replay's harm to
one failed decrypt; full dedup via `eid` is this task's job — see
[docs/tasks/README.md](../README.md)'s "Live carry-forwards" and
[2.8](../phase-2/2.8-federated-route-reachability.md)).

## Scope
- **In:** `apps/envelope/src/envelope.rs` — add `eid: [u8; 16]` to `MessageEnvelope` v2.
  `apps/core/src/chat.rs` — a bounded, sealed-at-rest "recently seen `eid`" structure consulted in
  `open_bytes`.
- **Out:** server-side dedup (explicitly out of scope per task 2.8's "no s2s dedup" and `route`'s
  opaque-blob contract — the server never decodes envelopes); wiring `eid` into `apps/tui`/`apps/cli`'s
  own local-store `history/`/`outbox/` dedup (ADR 0021 already notes this as a separate future
  migration, not this task's job).

## Deliverables
1. `eid` field on `MessageEnvelope` v2, generated once in `seal_bytes` and reused verbatim on
   prekey-preamble re-attach for the same logical message (so a genuine unconfirmed-initiator
   retransmit dedups against itself, mirroring `ChatContent::Text.id`'s existing pattern and
   `data-model.md`'s "outbox... idempotent by eid").
2. A bounded seen-`eid` set in `ChatState`, consulted early in `open_bytes`, dropping a genuinely
   redelivered envelope without reprocessing it as new.
3. Explicit written decision (record in this task's Outcome section) on whether `eid` sits inside or
   outside the C3 canonical AAD. Recommendation: **outer plaintext, not part of the AAD** — the ADR's
   canonical AAD formula (`"mrd.env/2" ‖ AD ‖ prekey_preamble ‖ enc_header`) does not include it, and
   `eid` carries no confidentiality/authenticity requirement of its own (it is a dedup convenience, not
   a security boundary — see Risks).

## Risks / notes
- **This is a real design gap, not resolved by any existing doc — do not silently invent a security
  property `eid` doesn't have.** ADR 0016's R2 ("loss of the cheap pre-filter") stays the accepted
  residual: `eid` dedup is a redelivery/duplicate-processing convenience, explicitly *not* required to
  be a pre-crypto DoS filter. Framing it as a security boundary in code comments or docs would
  overclaim.
- `TODO: confirm` with **architect**: `eid`'s exact generation scheme (sender-random vs.
  content-derived — proposed: sender-random 128 bits), and the seen-set's bound/eviction policy
  (proposed: mirror `MAX_PENDING_REQUESTS`'s precedent — a fixed-size LRU, not literally unbounded).
  No design doc specifies these; an earlier draft of `wire-protocol.md §3` that had an `eid` field was
  itself disclaimed as wrong on a different axis (missing `sender_pub`), so it cannot be trusted as a
  template.
- Must not regress a genuine unconfirmed-initiator retransmit (same `eid`, same content, sent because
  the initiator hasn't seen a reply yet) into being treated as an attack or silently dropped in a way
  that breaks delivery — write a test for this exact case, not just the malicious-replay case.
- A flood of distinct `eid`s must not grow `ChatState` unboundedly — same test shape as
  `message_request_flood.rs`'s existing precedent (task 3.10).

## Tests
```
cargo nextest run -p meridian-core --test chat_manager
cargo nextest run -p meridian-core --test eid_dedup
```
New `apps/core/tests/eid_dedup.rs`: a redelivered envelope (byte-identical, including `eid`) is
recognized and dropped without a second full decrypt attempt; a legitimate unconfirmed-initiator
retransmit is not treated as an attack; the dedup store is provably bounded under a flood of distinct
`eid`s.
