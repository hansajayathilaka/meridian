# 3.10 — Bound `pending_requests` against a stranger flood

**Phase:** 3 — Review of Phase 2 · **Feature:** review fix (F5) · **Depends on:** — · **Status:** done

## Goal
The message-request gate must stop being an unbounded, stranger-driven at-rest storage amplifier.

## Scope
- **In:** cap `pending_requests` (evict-oldest or refuse beyond N); bound `intro` size at insertion;
  drop the associated `Session` when a request is evicted.
- **Out:** server-side rate limiting of first-contact envelopes; the ctrl-frame loophole (3.11).

## Deliverables
1. `apps/core/src/chat.rs` (L296/L543/L601) — `MAX_PENDING_REQUESTS`, `MAX_INTRO_LEN`, and eviction
   that also removes the orphaned session.
2. `apps/core/tests/message_request_gate.rs` extended (or a new `message_request_flood.rs`) — N+K
   distinct fresh identity keys each sending one first-contact envelope leaves `ChatState` bounded,
   no orphaned sessions, and **an accepted request survives eviction pressure**.

## Risks / notes
- OTK-free X3DH is legal (`used_opk: None`), so nothing client-side rate-limits the flood today —
  that is why this is unbounded.
- **Eviction is itself an attack surface:** a flood must not be able to evict a legitimate pending
  request from a real contact. If the chosen policy admits that, state the residual explicitly
  rather than hiding it. An eviction policy that discards a *decided* request is a regression.
- **`TODO: confirm` the cap value** if it is not derivable from a design doc — do not invent it silently.

## Outcome

**`apps/core/src/chat.rs`**: added `pub const MAX_PENDING_REQUESTS: usize = 256` and
`pub const MAX_INTRO_LEN: usize = 4096` (4 KiB), plus a new private `ChatState::request_order:
Vec<[u8; 32]>` tracking arrival order of the currently-*undecided* `pending_requests` keys (oldest
first). Since this crate is deliberately clock-free (wasm32 target, no `SystemTime`), "oldest" is a
plain insertion sequence, not a timestamp — same constraint `PrekeyVault::set_bundle`'s doc comment
already documents.

`open_inbound_gated`'s first-contact branch now routes through a new `insert_pending_request`,
which evicts the single oldest entry in `request_order` (`evict_oldest_pending`, dropping both the
`MessageRequest` *and* its `Session`) whenever `pending_requests.len() >= MAX_PENDING_REQUESTS`
before inserting the new one. `request_order` is pruned in the same call by every removal path —
`accept_request`, `reject_request`, and `evict_oldest_pending` itself — so it only ever contains
keys for requests that are *currently* pending. That is the whole eviction-safety argument: an
accepted or rejected request is removed from `request_order` in the same call that decides it, so
`evict_oldest_pending` structurally cannot reach back and discard a decision the user already made
— it can only ever pick from the genuinely-undecided set. Oversized intros are *capped*, not
dropped: a new `cap_intro`/`truncate_utf8` pair truncates `ChatContent::Text`'s `body` (at a UTF-8
char boundary) to `MAX_INTRO_LEN` bytes when the encoded plaintext exceeds it, reusing
`open_bytes`'s already-measured plaintext length rather than re-encoding to check. Dropping the
request outright was rejected: `apps/cli/src/session_connect.rs`'s `note_message_request` (and the
general `ChatError::MessageRequest` contract every caller relies on) assumes the error always
corresponds to a real queued entry — `.expect("ChatError::MessageRequest just inserted this
request")` would panic if capping ever meant "sometimes there's nothing to look up." `Receipt` is
untouched (its `ack` is a fixed 16 bytes, never approaches the cap); a future `ChatContent` variant
with its own unbounded field would need its own arm in `cap_intro` — flagged in that function's doc
comment as a manual invariant, not something the type system enforces.

A new `ChatState::reconcile_request_order` (called from `open_at_rest` right after deserializing)
repairs `request_order` against `pending_requests` for state sealed before this task
(`#[serde(default)]` leaves the new field empty regardless of `pending_requests`'s contents) and as
defense-in-depth against any other drift: it drops stale order entries and appends any pending
request missing from the order, in `pending_requests`'s own key order (a deterministic fallback,
not a claim of true historical arrival order, for exactly the requests this crate never had a clock
to timestamp in the first place). **This fallback order is not neutral: it is attacker-influenceable**,
since `pending_requests` is keyed by the sender's freely-mintable identity key (OTK-free X3DH costs
an attacker nothing — the exact fact this task exists to mitigate), so an attacker can grind a
numerically-large-prefix key to make a planted pre-upgrade entry look "most recently arrived" in the
reconstructed order, at a genuinely older legitimate request's expense if eviction pressure hits
during that one reconciliation. Stated explicitly as a residual (see below) rather than left implicit
in "deterministic fallback."

**Cap values (both `TODO: confirm` — no design doc gives numeric limits for §3.5's request queue or
its "short encrypted intro"):**
- `MAX_PENDING_REQUESTS = 256`. Chosen to comfortably exceed what a legitimate user could plausibly
  need — someone who posts their ID publicly and fields, say, a few dozen simultaneous first
  contacts — while still being a small, fixed multiple of one session's footprint regardless of how
  large the flood actually is. Nothing in `system-design.md §3.5`,
  `docs/architecture/features/06-cross-org-federation.md`, or task 2.10/2.14 gives a numeric queue
  depth; the closest existing precedent (prekey bundles cap at ≤100 one-time prekeys,
  `MAX_ONE_TIME_PREKEYS`) bounds a different resource and isn't reusable here (OTK-free X3DH is
  exactly what makes this flood free regardless of that cap), so 256 was picked directly rather than
  derived.
- `MAX_INTRO_LEN = 4096` bytes (4 KiB), bounding `ChatContent::Text`'s `body` string itself — final
  encoded `mrd.chat/1` size for a capped intro is `MAX_INTRO_LEN` bytes plus the small fixed
  CBOR/id framing overhead around `body` (tens of bytes), not exactly `MAX_INTRO_LEN` encoded
  bytes. Generous for a genuine one-line/one-paragraph greeting (an order of magnitude past a
  typical chat message) while keeping a single request's worst-case contribution small relative to
  `apps/rendezvous/src/federation/link.rs`'s `MAX_FRAME_LEN` (1 MiB, the wire-level ceiling a single
  envelope is already bound by upstream of this, per review finding F14). No design doc numerically
  bounds "a short encrypted intro" either, so this too was picked rather than derived.

**Tests:** `apps/core/tests/message_request_flood.rs` (new file, 4 tests):
`flood_of_distinct_identities_leaves_pending_requests_bounded_no_orphaned_sessions` (`MAX_PENDING_REQUESTS
+ 8` distinct fresh identity keys, each completing OTK-free X3DH and sending one first-contact
envelope, leaves `pending_requests().count() == MAX_PENDING_REQUESTS`, the oldest 8 senders with
neither a pending request nor a session, and the most recent `MAX_PENDING_REQUESTS` senders with
both intact — proved non-vacuous by temporarily short-circuiting `insert_pending_request`'s
eviction check to `if false && ...` and confirming this test fails
(`left: 264, right: 256`) before reverting), `oversized_intro_is_truncated_not_dropped` (a
16 KiB intro still gates as `ChatError::MessageRequest`, with the queued entry's `intro` truncated
to ≤ `MAX_INTRO_LEN` bytes and a genuine prefix of the original — never fabricated content),
`short_intro_is_untouched` (an ordinary intro is byte-for-byte unchanged — capping is a bound, not a
blanket truncation), and `accepted_request_survives_eviction_pressure_after_the_flood` (a real
contact's request is gated then accepted *before* a `MAX_PENDING_REQUESTS + 32` flood runs; after
the flood, the accepted contact still has no resurrected pending request, still has its live
session, and a follow-up message from them still delivers normally — proving eviction never reaches
a decided request even under sustained pressure).

`cargo nextest run -p meridian-core --test message_request_gate`: 7/7 pass (unchanged, no
regression). `cargo nextest run -p meridian-core --test message_request_flood`: 4/4 pass (~36s
wall, dominated by `MAX_PENDING_REQUESTS`-scale asymmetric-crypto cost in an unoptimized debug
build — inherent to actually exercising the cap, not incidental test slop). Full
`cargo nextest run -p meridian-core`: 64/64 pass (63 plus the new
`chat::tests::reconcile_request_order_repairs_desynced_legacy_state` crate-private unit test added

`cargo clippy -p meridian-core --all-targets -- -D warnings` both clean. `cargo build -p
meridian-cli` also verified clean (unaffected — `MessageRequest`'s public shape and
`ChatError::MessageRequest`'s contract are both unchanged).

**Residual, stated rather than hidden (as the Risks section asked for):** eviction only ever
removes a request that is still in `pending_requests` at the moment it runs — a genuinely accepted
or rejected request can never be evicted, by construction (see above). But a request the user has
*seen* (displayed by the CLI's `y/n` prompt) and is actively deciding on is, until the moment
`accept_request`/`reject_request` actually executes, still an ordinary undecided entry in
`request_order` — it has no special protection over any other pending request just because a human
is currently looking at it. `apps/cli/src/chat.rs`'s event loop (`tokio::select!` between stdin
lines and `client.next_deliver()`) drives a single, account-wide `ChatState` shared across every
peer, not one scoped to the contact currently being chatted with: while a user is at the "message
request from X — accept? y" prompt for one sender, unrelated inbound envelopes (including a
concurrent flood from other minted identities) keep being processed by the same loop and can evict
X's still-undecided request out from under the user before they finish typing their answer. This is
not a bypass of the invariant this task set out to guarantee (an *accepted* request is safe, and is
proven safe under this exact pressure by the new test) — it is a real, narrower race between
"displayed to the user" and "decided by the user" that a sufficiently fast, sufficiently large flood
can win. Closing it would need either scoping `awaiting_request` protection into `ChatState` itself
(e.g. a small "currently prompted" exemption list) or moving the accept/reject decision earlier
(display-then-immediately-decide), both of which are UX/behavior changes out of this task's scope
(cap + evict + bound intro) and arguably Feature 08's territory (the polished accept/decline UX both
2.10 and 2.14 deferred there). Flagged here rather than silently accepted.

**Second residual, added at review sign-off (security-reviewer finding):**
`reconcile_request_order`'s fallback ordering for a legacy/desynced `pending_requests` (used once,
from `open_at_rest`, only when `request_order` doesn't already account for every pending key) is
`pending_requests`'s own `BTreeMap` key order — and that key is the sender's self-chosen, freely
mintable X3DH identity key, not a neutral tiebreak. An attacker who can influence *when* a legacy
blob gets reconciled (e.g. around an upgrade boundary) can grind an identity key with a
numerically-large prefix so a planted pre-upgrade request sorts last (i.e. "most recently
arrived") in the repaired order, pushing a genuinely older legitimate request to the front of the
eviction queue instead. This is narrow and one-time: it only affects the single reconciliation
call on state that predates this task or has otherwise desynced, it can never touch an
already-decided request (the same lockstep argument as above), and it doesn't affect anything
inserted after upgrade (`insert_pending_request` records real arrival order via `request_order`
directly). Not closed in this task — stated explicitly per the Risks section's directive rather
than left implicit under "deterministic fallback."

`reconcile_request_order_repairs_desynced_legacy_state`, directly in `apps/core/src/chat.rs`
exercising the actual repair loop (populates `pending_requests` directly with `request_order`
left empty, calls `reconcile_request_order`, asserts ascending-key repaired order, then asserts
`evict_oldest_pending` picks the lowest key and drops its session) — test-engineer's finding that
