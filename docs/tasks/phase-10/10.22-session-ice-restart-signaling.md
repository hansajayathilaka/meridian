# 10.22 — `P2pSession::ice_restart` real signaling (symmetric, glare-safe, layered fingerprint check)

**Phase:** 10 — File Transfer Stream · **Feature:** T09 (fix) · **Depends on:** 10.19, 10.20, 10.21 ·
**Status:** pending

## Goal
Make `P2pSession::ice_restart` actually restore connectivity after a real network change, per
[ADR 0025](../../adr/0025-ice-restart-renegotiation.md)'s full decision: one symmetric, bounded,
glare-safe method that seals and tolerantly sends an `IceRestartOffer`/`Answer` round trip, then
verifies the result with a layered fingerprint check. This is the task that actually closes the gap
tasks 10.15/10.17 live-reconfirmed.

## Scope
- **In:** `apps/core/src/session.rs`'s `P2pSession::ice_restart` — new signature (breaking change; see
  ADR 0025's Cons): `async fn ice_restart(&mut self, relay: &mut dyn SignalRelay, store: &dyn
  SecretStore, handle: &KeyHandle, chat: &mut ChatState) -> Result<(), SessionError>`. Logic, per the
  ADR's Decision:
  1. Call `transport.ice_restart` (10.19's real primitive) to get a fresh local offer.
  2. Seal it as `SignalContent::IceRestartOffer` (10.20's wire type) and send it via `relay`'s new
     tolerant method (10.21) — **except** when the identity-key tie-break (reuse the existing
     `dial`/`answer` convention: the lexicographically-smaller of `self.our_ik`/`self.peer_ik`
     initiates) says this side should instead wait briefly for an incoming offer first. Both sides run
     the same method; the tie-break only decides which branch each side takes internally.
  3. The offerer awaits an `IceRestartAnswer` (bounded timeout — reuse or mirror `ANSWER_TIMEOUT`'s
     existing rationale in this same file) via `relay.recv()`. The answerer, on receiving an
     `IceRestartOffer`, calls the transport's real primitive on its own side, `set_remote_description`
     with the peer's offer, generates its own answer, seals + tolerantly sends `IceRestartAnswer`.
  4. Whichever side ends up processing the peer's SDP: `set_remote_description`, add the peer's new
     ICE candidates, then the **layered fingerprint check**: (a) the ordinary asserted-vs-negotiated
     cross-check on the restart offer/answer's own `dtls_fp` (reuse `verify_fingerprint`'s existing
     logic/shape), unweakened; (b) a new, distinct assertion that the result still equals `self.local_fp`/
     `self.remote_fp` (the session's own cached values from the original handshake) — a mismatch here
     is the new `SessionError::RestartFingerprintDrift`, never conflated with `FingerprintMismatch`.
  5. On success, the session's already-open data channels should be flowing again (nothing about them
     changes — only ICE/DTLS renegotiates); ratchet/`ChatState` is untouched throughout (invariant 5,
     already true of today's no-op and must stay true).
- **Out:** any automatic detection of *when* to call this (ADR 0025 explicitly defers this). Also out:
  the still-separately-scoped `StreamType::on_reconnect` hook / automatic `send_resume_bitmap` trigger
  (task 10.9's own carry-forward) — the caller still manually invokes those after `ice_restart()`
  returns, exactly as task 10.9/10.15 already established; this task does not add that hook.

## Deliverables
1. `P2pSession::ice_restart`'s new signature and full signaling logic.
2. `SessionError::RestartFingerprintDrift` (new variant, distinct from `FingerprintMismatch`).
3. `docs/api/core-api-contracts.md`'s `P2pSession::ice_restart` entry updated to the new signature.
4. Tests: (a) both sides calling `ice_restart` concurrently (glare) resolves deterministically via the
   tie-break, ends with one, coherent, non-conflicting SDP exchange; (b) a real network interruption
   (reuse `LoopbackTransport`'s or a real-backend test's ability to simulate a cut, whichever this
   crate's existing test infra supports) followed by `ice_restart()` on both sides actually restores
   data-channel flow — a message sent after the restart is received; (c) a deliberately corrupted/
   substituted `dtls_fp` in a restart offer is rejected exactly like the original handshake's
   fingerprint check (unweakened); (d) a test proving the *layered* check's own new arm fires
   correctly — inject a scenario where the negotiated fingerprint doesn't match the session's cached
   value even though the asserted one matches (e.g. via a test-only transport double), confirming
   `RestartFingerprintDrift` fires rather than a silent pass.

## Risks / notes
This is the highest-stakes task in this fix — it's a live, in-place renegotiation of an active,
already-authenticated session's transport layer, and the fingerprint check is the last line of defense
against a substituted DTLS identity. Do not weaken either fingerprint check to make a test pass; if a
test can't pass without weakening one, the test's own setup is wrong, not the check. Get **security-
reviewer** involved explicitly (see Reviews) given this touches identity/session/crypto-adjacent
invariants per CLAUDE.md's own rule ("before touching identity, keys, signaling... read the threat
model").
