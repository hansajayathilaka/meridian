# 5.10 — Drain/flush-on-shutdown hook for `Effect::PersistHistory`

**Phase:** 5 — Review of Phase 4 · **Feature:** review fix (F10) · **Depends on:** — · **Status:** done

## Goal
Close the `PersistHistory` drain-window flake found by 4.51's own test-engineer pass during restart
probing: a message that just rendered live can fail to survive a restart if the process is killed within
~2s of appearing, because its async write to `history.jsonl` hasn't landed on disk yet.

## Scope
- **In:** `apps/tui/src/lib.rs::run()` (no drain/flush hook currently exists on shutdown), and
  `apps/tui/src/worker.rs` near `run_persist_history`. Give history-persist effects a drain window or an
  explicit flush-on-shutdown hook before process exit.
- **Out:** Any other effect's shutdown durability — scoped to `PersistHistory` only, the one this
  finding names; a broader shutdown-durability audit is a separate concern if warranted later.

## Deliverables
1. A drain window or flush-on-shutdown hook ensuring in-flight `PersistHistory` writes complete before
   the process exits.
2. A regression test reproducing the current gap (kill within ~2s of a message rendering, confirm it's
   currently lost) that flips to passing once the fix lands.

## Risks / notes
Confirmed still present and still untested by this review's test-engineer pass — no reproduction test
exists anywhere in the current tree.

## Status
**Done.** Root cause confirmed by direct reasoning about `run`'s async scheduling, not just the finding's
own empirical "~2s" description: `Effect::PersistHistory` reaches the worker task over an unbounded
`mpsc` channel that `tokio::spawn` merely *enqueues* — the spawned `run_worker` task is not actually
polled until the caller's own task yields at an `.await`. `run`'s old shutdown path (`drop(guard);
Ok(())`, right after the `loop { .. }` breaks on `app.should_quit()`) had no intervening await between
sending the final effect and returning, so a `PersistHistory` effect dispatched in the same tick that
triggered quit could still be sitting unpolled in the channel — or the worker task mid-flight on an
earlier effect — when the process went on to exit, losing the write entirely (not just under some
timing window; deterministically so, in the worst case).

**Fix (`apps/tui/src/lib.rs::run()`):** a `pending_persist_history: u32` counter, incremented at both
`effect_tx.send` call sites whenever the dispatched effect is `Effect::PersistHistory`, decremented in
the main loop whenever the received event is `is_persist_history_ack` (a new private predicate matching
`AppEvent::Worker(WorkerEvent::Completed(Effect::PersistHistory(_)) | WorkerEvent::Failed(Effect::
PersistHistory(_), _))` — both count, since a *failed* write is still a worker done attempting it,
nothing left to wait on). Right before `run` returns, a new `drain_pending_persist_history` awaits
(bounded by a new `PERSIST_HISTORY_DRAIN_TIMEOUT` = 2s, matching the finding's own named window) until
that counter reaches zero, reading real acks off the existing `worker_rx` channel. `apps/tui/src/
worker.rs` needed no functional change: `handle_persist_history`'s `WorkerEvent::Completed`/`Failed` ack
already *is* the completion signal the drain needs, because `run_persist_history` is a synchronous,
non-yielding write (no `.await` inside it) — by the time the ack is sent, the write has already landed,
so "acked" and "durable" are the same moment. Only a doc comment was added there recording why.

**Chose a bounded counter+drain over a full `JoinHandle` join** on the worker task: the worker's effect
queue is strictly FIFO, so a `PersistHistory` effect queued behind one that can genuinely hang (e.g. the
already-documented, unbounded `SignalingClient::connect` inside prekey-bundle republish) would make an
unbounded join on the whole task hang shutdown indefinitely for a concern this task's own Scope
explicitly excludes ("Out: any other effect's shutdown durability"). The bounded drain instead waits only
for `PersistHistory`'s own acks specifically, giving up after 2s if the queue is stuck behind something
else — trading a vanishingly rare residual loss for a shutdown that always terminates.

**Residual, deliberately out of this task's Scope (recorded, not silently dropped):**
`terminal::spawn_signal_watch`'s `SIGINT`/`SIGTERM` handler calls `std::process::exit` directly, never
returning through `run`'s new drain at all — a `PersistHistory` effect in flight at the moment of a
signal is still lost. The task file names only `lib.rs::run()` and `worker.rs` as in-scope, and the "Out"
note allows deferring "a broader shutdown-durability audit" — closing the signal path would need its own
task (the signal handler would have to be handed the pending counter/drain fn, and await it before
`std::process::exit`).

**Deliverable 2 (regression test), `apps/tui/tests/persist_history_drain.rs`.** `run` itself cannot be
driven from a test (its own doc comment: real-terminal-only), so the test drives the real pieces `run`'s
shutdown path is built from — `run_worker`/`drain_pending_persist_history`/`is_persist_history_ack` —
through a new `meridian_tui::test_support` seam (mirroring `terminal::test_support`'s existing
`#[cfg(any(test, feature = "test-support"))]` shape exactly, via thin `pub` wrapper fns rather than `pub
use`, so the underlying items stay private to normal, non-test callers). One test wires a real
`effect_tx`/`effect_rx`/`run_worker` exactly like `run` does, sends one `Effect::PersistHistory` against
a real OS-keystore-backed account/`MERIDIAN_HOME`, and — deterministically, no `sleep`, relying on the
same "spawn only enqueues, does not poll" fact the bug itself turns on — asserts the sealed
`history/<peer>.jsonl` reflects *no* write immediately after the send (reproducing the gap: this is
exactly the state `run`'s old shutdown path could have returned the process from), then calls
`drain_pending_persist_history` and asserts the write is now durably on disk (closing the gap). Verified
by hand that this reproduction is real, not a tautology: with the drain call commented out, the same test
fails at the final `assert_eq!` with `left: []` (no history), confirming the assertion genuinely depends
on the fix. A second test pins `is_persist_history_ack`'s exact match set (`Completed`/`Failed` for
`PersistHistory`, nothing else).

No wire/protocol/crypto change. No new dependency. `apps/tui` still depends only on `meridian-core` per

existing shutdown path, not a new user-visible feature; no `SurfaceRegistry` registration needed. Scope
honored: only `Effect::PersistHistory` gets shutdown durability; every other effect's behavior on quit is
byte-for-byte unchanged (confirmed by the full, unmodified `cargo test -p meridian-tui` suite staying
green). `rendezvous`/`meridian-proto` untouched.

### Review round
**code-reviewer** (PASS, no blocking findings) independently re-verified the counter correctness (traced
every producer/consumer of `pending_persist_history`), the root-cause claim (confirmed the TUI runs on a
`current_thread` tokio runtime — `apps/cli/src/main.rs` — so a spawned task genuinely cannot progress
until the caller yields at an `.await`, matching the fix's premise), the regression test's genuineness (by
independently commenting out the drain call and confirming failure), and the `test_support` seam's
production isolation. One **should-fix, not blocking**: this task's own Scope (deliberately) leaves
`spawn_signal_watch`'s `SIGINT`/`SIGTERM` path (`apps/tui/src/terminal.rs`) bypassing the drain entirely
via `std::process::exit` — recommended making that gap explicit rather than letting the tracker read F10
as fully closed. **Resolution:** already named accurately in this file's own "Residual" paragraph above;
ratified here as a known, deliberately out-of-scope carry-forward rather than a new fix-task — this
task's Scope explicitly permits deferring "a broader shutdown-durability audit," and ordinary in-terminal
Ctrl-C is unaffected (crossterm's raw mode disables `ISIG`, so it never reaches the signal handler at
all; only an external `kill`/supervisor/orchestration `SIGTERM` does). Carried forward in
[phase-5/README.md](./README.md#residual-carried-forward-by-510s-review) for a future task to pick up if
warranted, rather than spawning one now for a boundary the task itself pre-declared out of scope.
