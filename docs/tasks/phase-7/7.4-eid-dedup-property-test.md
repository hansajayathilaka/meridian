# 7.4 — Property test for `eid` dedup bound + duplicate detection

**Phase:** 7 — Review of Phase 6 · **Feature:** review fix (F6) · **Depends on:** — · **Status:** pending

## Goal
Add randomized/property coverage alongside the existing three example-based cells in
`apps/core/tests/eid_dedup.rs`, so the dedup bound and duplicate-detection invariants hold across
generated sequences, not just the three hand-picked scenarios.

## Scope
- **In:**
  - `apps/core/Cargo.toml` — add `proptest = { workspace = true }` to `[dev-dependencies]` (already
    pinned at the workspace root, `Cargo.toml:84`, and already used by `apps/identity` — wiring an
    already-vetted dependency into a new crate's dev-deps, not introducing a new one).
  - `apps/core/tests/eid_dedup.rs` — a new property-test block covering:
    1. Exact-duplicate detection regardless of arrival order: a random interleaving of genuinely fresh
       envelopes and re-deliveries of already-delivered ones; every re-delivery must be
       `Err(ChatError::DuplicateEnvelope)`, every fresh one must succeed, in any interleaving.
    2. `seen_eids_len(&state) <= MAX_SEEN_EIDS` as an invariant across randomized sequence lengths (the
       exact-at-cap boundary is already covered by the existing
       `seen_eid_set_is_bounded_under_a_flood_of_distinct_eids` cell; this property generalizes across
       smaller random lengths/duplicate rates rather than re-proving that same boundary).
- **Out:** Growing `seen_eids` costs one genuine X3DH handshake per new entry (by design, per 6.4's
  Decision 3 — an attacker cannot grow it for free). Keep case count and per-case sequence length small
  (e.g. 8–16 cases, sequences bounded to a few dozen entries) so total handshake count stays well under
  `MAX_SEEN_EIDS` and runtime stays in the single-digit-seconds range — do not attempt a full
  `MAX_SEEN_EIDS`-sized flood inside every generated case.

## Deliverables
1. The `Cargo.toml` dev-dependency addition.
2. The new property test(s) in `eid_dedup.rs`, additive only — the three existing cells are unchanged.

## Risks / notes
Non-vacuity matters here: confirm each property actually fails when its invariant is broken (revert the
dedup check / cap logic locally and confirm red), the same discipline 6.4's own review applied — don't
just trust the property compiles and passes.

## Tests
`cargo nextest run -p meridian-core --test eid_dedup`.
