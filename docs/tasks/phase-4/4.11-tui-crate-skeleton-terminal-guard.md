# 4.11 — `apps/tui` crate skeleton + terminal guard

**Phase:** 4 — Verification & Trust + Terminal TUI Client · **Feature:** T17 — Terminal TUI Client · **Depends on:** 4.1 · **Status:** done

## Goal
Stand up the `meridian-tui` crate with its Elm-style runtime split and terminal-restoration guard —
first, per the feature spec's own risk note, because a crash that leaves raw mode on is the single most
damaging bug class in a TUI.

## Scope
- **In:** new `apps/tui` crate per ADR 0020: `App` owning all state, synchronous pure `update`, pure
  `render`, screen stack; event loop over `crossterm` events + a tokio worker channel + 250ms tick
  ([tui-client.md §4](../../architecture/tui-client.md#4-runtime-structure)); `Effect` as the only path
  to network/keystore/disk, executed by a worker task reporting back as `AppEvent`; RAII terminal guard
  (raw mode + alternate screen) whose `Drop` restores them, installed with a panic hook and
  `SIGINT`/`SIGTERM` handler.
- **Out:** any screen content (4.16+); config/store (4.14/4.15); the `meridian tui` subcommand wiring
  itself (4.12, though this crate is what it wires to).

## Deliverables
1. `apps/tui/src/app.rs` (or equivalent): `App`, `AppEvent`, `Effect`, `update`, `render` skeleton
   (screens are empty/placeholder at this point).
2. `apps/tui/src/terminal.rs`: RAII guard + panic hook + signal handler.
3. **Panic-restores-terminal test** — force a panic mid-render, assert raw mode and alternate screen are
   undone. Ships in this task per the spec's explicit risk note.
4. Update `docs/architecture/diagrams/build-target-topology.mermaid` to show `meridian-cli` →
   `meridian-tui` → `meridian-core` (it currently draws `meridian-cli` reaching the terminal directly,
   predating ADR 0020 — flagged stale by that ADR's Consequence section).

## Risks / notes
- **Terminal restoration is a reliability invariant, not a nicety** — this is why it ships with its own
  test in the very first task rather than being folded into a later one.
- `render` and `update` must never await or perform I/O — this is what makes `ratatui::backend::TestBackend`
  snapshot testing possible for every later screen task.

## Tests
`cargo nextest run -p meridian-tui`

## Status
Done. New `apps/tui` crate (`meridian-tui`): `App`/`AppEvent`/`Effect`/`update`/`render` skeleton
(pure, no I/O/await — `TestBackend`-testable), `TerminalGuard` RAII terminal restoration (raw mode +
alt screen; panic hook; `SIGINT`/`SIGTERM` watch), depends on `meridian-core` only per ADR 0020.
`tools/lint-tui-no-cli.sh` (ADR 0020 condition 3's follow-up, wired into CI) mechanically enforces the
dependency direction. `build-target-topology.mermaid` updated.

**security-reviewer** (required) found one Medium-severity real gap, fixed in place: `restore_once`
used a swapped `AtomicBool` flag, which guarantees exactly-once execution but not *ordering* — a
concurrent caller that lost the race returned immediately without waiting for the winner's actual
restoration syscalls to finish, so `spawn_signal_watch`'s `std::process::exit` right after could fire
before a racing panic-hook/`Drop` restoration on another thread completed. Replaced with
`std::sync::Once::call_once`, which blocks losing callers until the winner's closure returns; added
`concurrent_restore_blocks_until_winner_finishes`, a channel-synchronized test proving the block (not
just no-double-toggle). Also fixed a nit while in the file: `SIGTERM` now exits `143`
(`128+15`) instead of reusing `SIGINT`'s `130`. Non-blocking follow-ups noted for later, not
implemented here: a pty-backed test for real `CrosstermOps` (no TTY in CI), an explicit note/test for
the `panic=abort` claim, and tracking panic/`.expect()` message content as a future scrollback-leak
audit item once real (non-placeholder) data lands in `Effect` payloads.

**test-engineer** (required) found one real bug via a scratch probe, fixed in place before this task
closed: `TerminalGuard::install` didn't roll back `enable_raw_mode` if the subsequent
`enter_alternate_screen` call failed, leaving raw mode stuck on with no guard ever constructed to
restore it — no panic needed, an ordinary I/O error sufficed. Fixed with an early rollback + `Err`
return; added `failed_alt_screen_entry_rolls_back_raw_mode` covering it. Also added a doc note on
`install_panic_hook` about the process-global panic hook's implications for future tests in the same
binary. Non-blocking follow-ups noted, not implemented: a real-TTY pty smoke test, a double-install
guard/test, and revisiting whether `WorkerEvent::Completed` should carry a correlation id instead of
the full `Effect` once payloads carry real (sensitive) content.

`cargo test -p meridian-tui` (11 unit/integration tests, including both new regression tests) and
`cargo test --workspace` pass; `cargo clippy --workspace --all-targets -- -D warnings` and `cargo fmt
--check` clean; `bash tools/lint-tui-no-cli.sh` and `bash tools/check-docs.sh` pass.
