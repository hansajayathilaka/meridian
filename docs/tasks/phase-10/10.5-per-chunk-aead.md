# 10.5 — Per-chunk AEAD (`k_f`, nonce = chunk index)

**Phase:** 10 — File Transfer Stream · **Feature:** T09 · **Depends on:** 10.3 · **Status:** pending

## Goal
Encrypt each 64 KiB file chunk under the per-file key `k_f` (generated once per file, sealed under the
ratchet in the manifest — task 10.6's job to seal/unseal it) with the nonce derived from the chunk
index, per `docs/api/wire-protocol.md` §6: "`mrd.file/1` chunk body: `{i: uint, data: bstr}`, AEAD key
= per-file `k_f`, nonce = `i`".

## Scope
- **In:** `apps/streams/src/chunk.rs` (or similar): seal/open one chunk using `chacha20poly1305`
  (already a workspace dependency via `meridian-crypto`; approved for direct use here per the
  crypto-protocols skill's "AEAD = XChaCha20-Poly1305") directly inside `meridian-streams` — deliberately
  **not** routed through `meridian-crypto`, since this is ordinary per-file symmetric encryption with a
  key already derived/sealed elsewhere, not ratchet/session state, and keeping it in `meridian-streams`
  keeps the "additive stream type, zero core-crate edits" contract clean.
- **Out:** `k_f` generation/sealing under the ratchet (task 10.6), the sender/receiver loops that call
  this per chunk (10.7/10.8).

## Deliverables
1. `seal_chunk(k_f, i, data) -> Vec<u8>` / `open_chunk(k_f, i, sealed) -> Result<Vec<u8>>` (or
   equivalent) in `apps/streams`.
2. Tests: round-trip seal/open; tampered ciphertext is rejected; wrong index is rejected (confirms the
   nonce actually binds to `i`, not just a fixed/reused value).

## Risks / notes
`docs/api/wire-protocol.md` §6 says "nonce = `i`" but does not pin the exact byte layout (chacha20poly1305
nonces are 12 bytes for the standard construction, 24 for XChaCha — the crypto-protocols skill names
XChaCha20-Poly1305 as the chosen AEAD elsewhere, but this specific per-chunk construction needs its own
explicit pin since `i` alone as a 4- or 8-byte counter zero-padded to the nonce width is the natural
reading but is not written down anywhere yet). `TODO: confirm` — this task's Outcome must record the
exact encoding (recommended: `XChaCha20-Poly1305`, 24-byte nonce = `i` as an 8-byte little-endian
counter followed by 16 zero bytes, matching this codebase's other little-endian-length-prefix
conventions — but confirm against whatever `chacha20poly1305` crate API is actually used and pin
whichever is simplest to implement correctly). **Never reuse a nonce for two different chunks under the
same `k_f`** — since `i` is the chunk index and each file's chunks are indexed once, this holds by
construction as long as `k_f` is never reused across two different files (task 10.6's job to guarantee
fresh `k_f` per file).
