# 4.23 — Key-change adversarial test

**Phase:** 4 — Verification & Trust + Terminal TUI Client · **Feature:** T17 — Terminal TUI Client · **Depends on:** 4.22 · **Status:** done

## Goal
Prove, end-to-end through the TUI (not just at the core-module level 4.4 already tests), that flipping a
verified contact's key blocks the composer with no send path anywhere in the UI.

## Scope
- **In:** programmatically flip a verified contact's key (simulating a key-change event arriving over
  the wire), drive the TUI's `update` function through the resulting state, assert the composer is
  disabled and no keyboard path, palette command, or hidden action sends a message.
- **Out:** the underlying gate logic (4.4 owns and tests that); this task is UI-level, exhaustive over
  the TUI's own input surface.

## Deliverables
1. `apps/tui/tests/key_change_adversarial.rs`: scripted key-change → assert composer blocked, assert
   every input path (keyboard shortcuts, palette entries) that could send is inert.

## Tests
`cargo nextest run -p meridian-tui --test key_change_adversarial`

## Reviews
- **security-reviewer** — required.
- **test-engineer** — required; this is an adversarial-shaped test needing exhaustive input-surface
  coverage, not a sampled check.

## Status
Done. `apps/tui/tests/key_change_adversarial.rs` proves, end-to-end through the TUI (not just at 4.4's
core-module level), that flipping a verified contact's key blocks the composer with no send path
anywhere in the UI — composing already-reviewed building blocks (4.20's `dispatch_gated_send` choke
point, 4.4's `TrustStore::observe_key_change`/`can_send`) rather than testing new gate logic. Sweeps the
TUI's real input surface at two layers: `chat::handle_key` directly (5,940 cases — every practical
`KeyCode` including the enhancement-flag-only variants × every `KeyModifiers` bit including
`SUPER`/`HYPER`/`META` × every reachable focus/mode combination, restructured to avoid inflating the
count with focus-invariant `AwaitingAck` duplicates) and the real `App::update` entry point (2,376 cases,
covering the two global hotkeys and confirming no bypass exists above the screen layer). A reusable
palette-command checker, with a negative control proving it isn't vacuous, covers the (currently
unwired) palette surface. No genuine bypass was found — the exercise confirmed 4.20's existing gate
wiring already holds; no source files were changed.

**Review (both `security-reviewer` and `test-engineer` required, run in parallel — "adversarial-shaped
test needing exhaustive input-surface coverage, not a sampled check"):** no safety-blocking findings from
either pass. The security-reviewer's one note (the retry-path's `Blocked` short-circuit is never
exercised by this file's own fixture, since it never seeds a `Failed` entry — that exact scenario is
covered instead by 4.20's own `screens_chat.rs::retry_re_checks_the_gate_and_refuses_if_now_blocked`) is
now documented explicitly in the module doc rather than left implicit. The test-engineer's review found
the underlying safety sound but the "exhaustive" claim oversold in several fixable ways, all closed:
the documented case count was arithmetically wrong (undercounted "~89 keycodes" against an actual 123,
now 132 after also closing the coverage gap itself); the keycode/modifier enumeration was missing real
variants (`CapsLock`/`ScrollLock`/`NumLock`/`PrintScreen`/`Pause`/`Menu`/`KeypadBegin`,
`SUPER`/`HYPER`/`META`); `ChatFocus`/start-mode enumeration was a hand-maintained literal with no
compile-time guard against silently losing coverage if a variant were added later, now backed by
exhaustive `match`es with no wildcard arm; and the focus×mode crossing inflated the headline count with
cases that don't add distinct coverage (verified against `chat.rs`'s own dispatch order — `AwaitingAck`
modes never consult `state.focus`), now restructured to only cross focus with the one mode that actually
branches on it. The loose `checked > N` floor assertions were replaced with `assert_eq!` against the
real enumeration sizes, so the doc comment and the enforced count can never drift apart again.

`cargo test -p meridian-tui --test key_change_adversarial` (7/7), `cargo test -p meridian-tui` (full
suite), `cargo test -p meridian-cli --bins`, `cargo fmt --check`, `cargo clippy --workspace --all-targets
-- -D warnings`, and `bash tools/lint-tui-no-cli.sh` all clean.
