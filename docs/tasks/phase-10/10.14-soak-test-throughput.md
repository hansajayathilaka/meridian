# 10.14 — Soak test: 1 GiB / 10 GiB transfers + throughput report

**Phase:** 10 — File Transfer Stream · **Feature:** T09 · **Depends on:** 10.10, 10.13 ·
**Status:** done

**User surface:** none — pure test infrastructure and a report doc.

## Goal
Run the feature spec's named soak test — 1 GiB and 10 GiB transfers on the netns rig under the 1%
loss / 80 ms RTT profile — and produce a throughput report. This is explicitly named as feeding
ADR-6's SCTP-over-DTLS-vs-QUIC question with real numbers: "Ship the numbers, don't hide them."

## Scope
- **In:** automated soak runs at both sizes under task 10.13's profile, byte-perfect delivery
  verification (BLAKE3 match), a throughput report (MB/s achieved, comparison against the ceiling
  `system-design.md` §5.1 flags as a risk for SCTP-over-DTLS).
- **Out:** any transport-layer change in response to the numbers — this task reports, it does not
  redesign. If the numbers reveal something ADR-6-relevant, record it as a carry-forward for a future
  `/spike`, not a scope-creep fix here.

## Deliverables
1. Soak test automation (likely a shell/Rust harness driving two CLI instances across the netns rig).
2. Throughput report (markdown or similar, checked in or linked from this task's Outcome) covering both
   the 1 GiB and 10 GiB runs.

## Risks / notes
This is a long-running test (10 GiB under 1% loss/80ms RTT will take real wall-clock time) — likely an
`--ignored`-by-default test per the task 3.12 CI precedent, run in a scheduled/manual job rather than
every CI push.

## Tests
The soak harness itself; `cargo nextest run --ignored` (or equivalent) for the automated portion.

## Reviews
**test-engineer** + **devops**.

## Outcome
Built `tools/soak-file-transfer.sh` (`loopback`/`netns` subcommands, both driving real `meridian` CLI
processes with real identities, no test-only shortcuts) and `.github/workflows/soak-file-transfer.yml`
(scheduled + `workflow_dispatch`, mirroring task 10.13's own precedent). The soak run itself surfaced a
**headline finding that supersedes the throughput numbers this task set out to produce**: before any
loss/RTT profile ever comes into play, the real `WebRtcTransport` cannot send a single full 64 KiB
`mrd.file/1` chunk at all — `webrtc-sctp`'s default `max_message_size` (65536 bytes) is smaller than a
full chunk plus its AEAD/ratchet/CBOR overhead once sealed for the wire, so every multi-chunk transfer
fails deterministically with `outbound packet larger than maximum message size`. This is not a
throughput ceiling ADR 0006 already priced in — it's a correctness bug blocking any real number from
being produced at any size, on any network condition. Full write-up, including the honest "not
attempted"/"not practical in this sandbox" rows for 1 GiB/10 GiB and the loopback-only 60000-byte data
point that actually completed: [docs/testing/soak-file-transfer-throughput.md](../../testing/soak-file-transfer-throughput.md).
**Independently, concurrently corroborated by task 10.15's own kill/resume harness**, which hit the
identical error via a completely different driver — two independently-built harnesses landing on the
same specific error is strong evidence this is real, not an artifact of either harness's setup.

Per this task's own explicit scope ("this task reports, it does not redesign"), the fix was not applied
here — it was promoted to its own owned task, [10.18](./10.18-sctp-max-message-size-fix.md), rather
than left as an unowned carry-forward, since it blocks task 10.17's phase-exit demo from running over
real transport at all.

Both named reviewers (**test-engineer**, **devops**, run as one combined pass alongside task 10.15)
returned **PASS**, conditioned on one should-fix that was closed in a same-task follow-up: the report
and the harness script's own code comment both claimed `tools/netns-kill-resume.sh` (task 10.15) shared
the exact "`timeout N wait "$pid"` always fails with exit 127" bug this task found while building its
own harness — the review found that claim stale/false, since 10.15's script already independently
implements the correct `kill -0` polling fix. Corrected in both places rather than left as an inaccurate
cross-task claim in checked-in docs/comments. The review otherwise independently verified: the loopback
harness never fabricates a throughput number for a run that didn't verify byte-perfect delivery
(confirmed by live-running it at both 60000 bytes and 2 MiB); the `netns` subcommand correctly reuses
task 10.13's own `need_root()`/`need_netem()` gating with no drifted duplicate logic; the CI workflow is
honestly documented as expected-red until 10.18 lands; and `shellcheck -x`/`bash -n` are both clean.
