# 4.7 — Message-request UX finalization (from T06)

**Phase:** 4 — Verification & Trust + Terminal TUI Client · **Feature:** T08 — Verification & Contact Trust · **Depends on:** 4.3, 4.6 · **Status:** done

## Goal
Close the loop between T06/task 2.10's first-contact gate (already implemented in
`apps/core/src/chat.rs`: `MessageRequest`, `pending_requests`, `accept_request`, `reject_request`) and
T08's trust module: accepting a request TOFU-pins a real `Contact`.

## Scope
- **In:** glue code in `trust.rs`/CLI wiring the existing `chat.rs` request primitives to `trust.rs`:
  `accept_request` → TOFU-pin a `Contact` + offer petname assignment inline; `reject_request` leaves no
  trace (no contact created, no state retained).
- **Out:** any change to `chat.rs`'s existing `MessageRequest` machinery — this task is glue only, not a
  rework of 2.10's gate. The TUI's Requests screen (4.21).

## Status
Done. `apps/core/src/chat.rs`'s `MessageRequest`/`accept_request`/`reject_request` machinery is
untouched — this task is glue only, in `apps/cli/src/chat.rs`. Found (via the required review, not
assumed) that the real gap wasn't "accept never TOFU-pins" but the opposite: `run()`'s startup
`trust.observe` fired unconditionally, TOFU-pinning the sender before the user ever saw a still-gated
first-contact request, defeating `reject_request`'s "no trace" guarantee. Fixed by deferring the pin to
`answer_request`'s accept branch (which now also offers a TTY-gated inline petname prompt, reusing
`contact.rs`'s `prompt_petname` via a `pub(crate)` visibility change) for exactly the case that can
produce an undecided request.

Combined **reviewer** pass (required) caught a second-order version of the same bug the first fix
introduced: gating the early `observe` on `state.has_session(&peer_ik)` alone wasn't sufficient, because
`ChatState::open_inbound_gated` installs the responder's ratchet session as a side effect of processing
the first prekey envelope *before* deciding whether to gate the content into `pending_requests` — so a
session already exists for an undecided request, and a process restart while still undecided would
silently pin the sender on the next invocation's startup. The reviewer reproduced this with a throwaway
test before reporting it. Fixed with `state.has_session(&peer_ik) && state.pending_request(&peer_ik)
.is_none()`; a permanent regression test (`restarting_without_deciding_a_pending_request_does_not_tofu_pin`)
was added alongside the original accept/reject pair to lock in the guarantee (spawn → gate → restart
without deciding → assert still no `Contact` record).

`cargo test -p meridian-cli --test request_finalization` (3/3, including the new restart regression),
`cargo test -p meridian-cli --test two_orgs_walkthrough --test contact_mgmt --test chat_demo --test
verify` (no regression on adjacent coverage), `cargo fmt --check`, and `cargo clippy --workspace
--all-targets -- -D warnings` all clean.
