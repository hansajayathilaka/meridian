# 2.15 — Thread the peer's org hint into live signaling/chat routing

**Phase:** 2 — Cross-Org Federation · **Feature:** on-the-fly (surfaced by 2.9's code review) · **Depends on:** 2.8, 2.9 · **Status:** done

## Goal
Cross-org **bundle fetch** is hint-aware (tasks 2.7/2.9), but cross-org **routing** is not: no live
CLI path ever calls `SignalingClient::route_with_hint` with an actual hint, so a route to a peer at a
different org is never federated — the server treats an absent hint as local-only and returns
`not_connected`. This task makes the P2P signaling handshake and ongoing chat delivery hint-aware the
same way the bundle fetch already is, so `docs/architecture/features/06-cross-org-federation.md`'s own
walkthrough (`meridian chat mrd1:<bob>@org-b.test`) can actually complete cross-org, end to end.

## Background
Surfaced during task 2.9's code-reviewer pass: `apps/core/src/signal_relay.rs`'s `RendezvousRelay::send`
calls `self.client.route(*to, blob)`, and `apps/cli/src/chat.rs`'s `route_tolerant` also calls plain
`client.route(to, blob)`. `SignalingClient::route` (`apps/signaling/src/client.rs`) hardcodes
`hint: None`. The only caller anywhere in the tree that ever invokes `route_with_hint` with a real
`Some(hint)` is a server-side test (`apps/rendezvous/tests/federation_route.rs`) driving
`SignalingClient` directly. Consequence: task 2.9's own `SessionError::FedDenied/FedUnreachable/
NotFoundAtHint` variants are currently unreachable outside their unit tests — verified only by hand-
constructing `SignalError::FedDenied{..}` directly, never triggered through a live path.

Escalated to **architect**, who confirmed the gap is real (not a 2.9 regression — pre-existing since
2.7/2.8) and binding per already-accepted design: `system-design.md` §3.3 step 2 requires the client's
own server "to federate a prekey fetch **and subsequent signaling envelopes**" (not just the fetch),
and §3.4's per-request-only reachability rules out any server-side caching of the hint as an
alternative fix — the client must supply it on every routed call. Architect called for a new numbered
task (this one), sequenced before 2.11 (whose demo needs real cross-org routing) and 2.12 (the phase
exit gate, whose acceptance criteria are cross-org chat), rather than folding the fix into 2.9 (would
reopen an already-narrow, nearly-closed review) or into 2.11 (wrong agent/reviewer lineup — 2.11 is
devops-owned with no rust-dev/test-engineer in its review list, and this is a cross-crate protocol
fix touching `meridian-core` and `meridian-cli`).

## Scope
- **In:** `RendezvousRelay` gains a `hint: Option<String>` field set at construction (each instance
  already wraps one client for one fixed peer relationship, so this needs no `SignalRelay` trait
  change and no `MemRelay` churn); `send()` calls `self.client.route_with_hint(*to, self.hint.clone(),
  blob)` instead of `route`. `apps/cli/src/session_connect.rs` constructs `RendezvousRelay::new` with
  `Some(peer_hint.clone())` (the hint is already parsed from `mrd1:<id>@org-b.test` and already
  threaded into `fetch_with_retry` two lines away — this task extends the same value to the relay).
  `apps/cli/src/chat.rs`'s `route_tolerant` gains a `hint: &str` parameter, calling
  `client.route_with_hint(to, Some(hint.to_string()), blob)`; `ChatArgs::peer_hint` (already present)
  threads through the same call chain it already reaches for `fetch_with_retry`
  (`send_text`/`deliver_content`/`handle_inbound`/`answer_request`, whichever actually call
  `route_tolerant` — confirm the exact call graph while implementing). `route_tolerant`'s error
  handling surfaces `FedDenied`/`FedUnreachable` through the same non-security-flavored copy
  `federation_error_line` already gives the fetch path (an ongoing chat's routing failure deserves the
  same diagnosability 2.9 gave the initial fetch), rather than collapsing them into the generic
  `"routing message: {e}"` string.
- **Out:** the CLI-copy deduplication noted (non-blocking) in 2.9's review — `federation_error_line`
  is currently hand-rolled three times with already-drifted wording; fold that dedup in here only if
  it falls out naturally while touching `chat.rs`/`session_connect.rs`, otherwise leave it a separate
  nit. Multi-hint IDs and contact tokens (T08/T14, per 2.9's own Out-of-scope).

## Deliverables
1. `apps/core/src/signal_relay.rs`: `RendezvousRelay` carries and uses a hint.
2. `apps/cli/src/session_connect.rs`: `RendezvousRelay::new` constructed with the real peer hint.
3. `apps/cli/src/chat.rs`: `route_tolerant` threads the hint through to `route_with_hint`, and its
   error path surfaces federation errors as diagnosably as the fetch path already does.
4. A real end-to-end cross-org test (two `meridian-rendezvous` test instances, federation configured,
   mirroring `federation_route.rs`'s harness) asserting `to_hint` actually reaches the wire and a live
   route/chat-envelope delivery succeeds across orgs — the exact hole 2.9's review found ("the only
   caller anywhere that invokes `route_with_hint` with `Some(hint)` is a server-side test").

## Risks / notes
- Do not weaken 2.6's federation-edge rate limits or 2.8's per-request reachability semantics while
  threading the hint through — this task only makes an existing, already-reviewed server-side code
  path reachable from the client; it must not add new server-side behavior.
- Confirm the exact call sites that reach `route_tolerant` in `chat.rs` before wiring — the task
  description above is a sketch from the architect's read of the code, not a verified call graph;
  implementer should trace it directly.

## Outcome
`apps/core/src/signal_relay.rs`'s `RendezvousRelay` gained a `hint: Option<String>` field set once
at construction; `send()` now calls `route_with_hint` instead of the hint-less `route()`.
`apps/cli/src/session_connect.rs` passes the real peer hint at its one construction site.
`apps/cli/src/chat.rs`'s `route_tolerant` gained `hint`/`peer_label` parameters threaded through the
real call chain (`run → send_text`/`handle_inbound`/`deliver_content`/`answer_request →
route_tolerant`), traced by reading, not guessed. `federation_error_line` gained an `action: &str`
parameter so 2.9's non-security-flavored copy is reused verbatim for routing failures instead of
reinvented. New end-to-end test `apps/cli/tests/federation_route_hint.rs`: two real
`meridian-rendezvous` instances over a real s2s mTLS link, a real `meridian chat` subprocess for
Alice, a raw `SignalingClient` for Bob who never registers at Alice's org — provable only if the hint
reached the wire.

**Reviews:** security-reviewer — APPROVE; confirmed the hint is never cached/reused across peers
(one `RendezvousRelay`/one hint per CLI invocation), discloses nothing beyond what 2.7/2.9 already
established (the server already branches on `to_hint` since task 2.8, unmodified here), doesn't touch
2.6/2.8 server-side rate-limit/reachability semantics (confirmed zero diff in
`apps/rendezvous/src/federation/`), and that the reachability/security-copy distinction from 2.9
holds for the routing path too. test-engineer — PASS; mutation-tested the reclassification by
reverting the hint threading and confirming `federation_route_hint.rs` fails, then restoring it.
code-reviewer — approve-with-nits, one item made contingent before closing: the `RendezvousRelay`/
`session_connect.rs` half (the P2P signaling-handshake path) had **zero** regression coverage —
proven by reverting `session_connect.rs`'s hint to `None` and showing the entire `meridian-cli` suite
still passed. Closed by adding `apps/cli/tests/session_connect_federation.rs`: two real
`meridian-rendezvous` instances with **bidirectional** s2s mTLS federation (required because the
WebRTC offer/answer handshake routes both directions), two real `meridian session connect --transport
webrtc --json` child processes, Bob and Alice each only ever known to their own home server.
Mutation-tested twice independently (by the implementer, then re-verified fresh by test-engineer,
including 8 consecutive clean runs to rule out WebRTC/ICE timing flakiness — none observed) — reverting
the fix reliably fails the test (which side errors immediately vs. hangs to the bounded 30s kill
depends on which peer draws the initiator role that run, but the required both-sides-`true` assertion
fails either way), restoring it passes again in ~7s.

Test-engineer's re-verification pass surfaced one more real gap while reproducing the mutation test:
`cargo test -p meridian-cli --features webrtc` — which now includes both new regression tests plus
the pre-existing `session_connect_webrtc.rs`/`session_demo_webrtc.rs` suites — was never wired into
`Justfile`'s `test` recipe or `.github/workflows/ci.yml`, so none of it actually runs in CI (a
pre-existing hole dating to task 1.24, not introduced here, but one that would have silently
swallowed this task's own regression test). Fixed in this task: added `cargo test -p meridian-cli
--features webrtc` alongside the existing `meridian-transport`/`meridian-core` webrtc lines in both
files; reran the full command locally to confirm it passes (10 tests across 4 binaries, ~18s).

Non-blocking follow-ups noted, not fixed: `apps/cli/tests/federation_route_hint.rs` and
`session_connect_federation.rs` both duplicate the two-org PKI/server-harness boilerplate already
present in `federation_errors.rs` (task 2.9) — the `tests/common/mod.rs` extraction flagged as
overdue since task 2.8 has now grown by two more copies; the three-way `federation_error_line`
duplication across `chat.rs`/`session_connect.rs` (noted, not fixed, in 2.9) is unchanged.

Tests: `cargo test -p meridian-core`, `cargo test -p meridian-rendezvous --test federation_route`
(6/6), `cargo test -p meridian-cli` (default features) and `cargo test -p meridian-cli --features
webrtc` (10/10, incl. both new tests) all green; `cargo clippy --workspace --all-targets -- -D
warnings` and `cargo fmt --check` clean.
