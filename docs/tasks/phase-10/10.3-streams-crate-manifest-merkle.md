# 10.3 — Scaffold `meridian-streams` + manifest schema + BLAKE3 merkle build/verify

**Phase:** 10 — File Transfer Stream · **Feature:** T09 · **Depends on:** — · **Status:** done

**User surface:** none — new crate scaffold with no consumer yet (the `StreamType` impl, task 10.6, is
the first). No TUI surface applies to this task.

## Goal
Create the crate additive stream types live in (already named in `docs/architecture/stack.md` line 71
as T09/T15/T16's home, but not yet scaffolded) and its first two building blocks: the `mrd.file/1`
manifest CBOR schema and a BLAKE3 merkle tree builder/verifier over 64 KiB chunks.

## Scope
- **In:** `apps/streams/` crate (`Cargo.toml`, `lib.rs`, added to the root `Cargo.toml` workspace
  `members`); a `manifest` module with the CBOR body `{name, size, root: bstr, key: bstr}` (per-file
  key sealed under the ratchet — sealing itself happens where the manifest is sent, not in this crate);
  a `merkle` module: build a BLAKE3 merkle tree over a file's 64 KiB chunks, compute the root, and
  verify one chunk against a subtree path.
- **Out:** the `StreamType` trait implementation (task 10.6), per-chunk AEAD (task 10.5), the sender/
  receiver engines (10.7/10.8). This task only ships the schema types and the merkle primitive with
  their own unit tests.

## Deliverables
1. `apps/streams/Cargo.toml` + `apps/streams/src/lib.rs`, added to root `Cargo.toml` `members`.
2. `apps/streams/src/manifest.rs` — the CBOR manifest type + (de)serialization round-trip test.
3. `apps/streams/src/merkle.rs` — tree build, root computation, incremental subtree verification,
   corruption-detection test (flip a byte in one chunk, assert verification fails for that chunk only).
4. New `blake3` workspace dependency (pre-approved: crypto-protocols skill, "Hash/merkle = blake3").

## Risks / notes
No document today pins the exact merkle construction (leaf shape, node ordering, odd-leaf-count
handling). `TODO: confirm` — this task's own Outcome must nail it down (recommended default: leaf =
`blake3(chunk_bytes)` per 64 KiB chunk in file order; internal node = `blake3(left ‖ right)`; an odd
trailing leaf promotes unpaired to the next level rather than duplicating itself, to avoid the classic
Merkle "duplicate last leaf" second-preimage footgun) and record the chosen shape precisely enough for
task 10.12's spec-doc section to describe it byte-for-byte (third-party implementability is an
acceptance criterion of the whole feature).

## Tests
`cargo nextest run -p meridian-streams`.

## Reviews
**code-reviewer** + **security-reviewer** (new dependency; the merkle construction is integrity-critical
— an ambiguous or malleable tree shape could let a corrupted chunk pass verification, which is exactly
the acceptance criterion task 10.16 tests against).

## Outcome
Scaffolded `apps/streams` (`meridian-streams`), registered in the root workspace, depending only on
`meridian-proto` (no core-crate edge). Shipped `manifest.rs` (`FileManifest{name, size, root: bstr,
key: bstr}`, CBOR via `meridian-proto`'s helpers) and `merkle.rs`: a BLAKE3 merkle tree over 64 KiB
chunks with domain-separated leaf/node hashing (`leaf_hash = BLAKE3(0x00‖chunk)`,
`node_hash = BLAKE3(0x01‖left‖right)`), odd-node promotion (never duplication), and incremental
subtree `verify()` that cross-checks `leaf_index`/`leaf_count` against the proof's own step pattern.
Empty-file semantics (`TODO: confirm`) are a documented placeholder (one virtual leaf `BLAKE3(b"")`)
pending task 10.12's spec. The construction is documented byte-for-byte in the module doc for 10.12 to
copy verbatim into the cross-implementation wire spec.

This task went through two review rounds before closing, both via the combined code-reviewer +
security-reviewer `reviewer` agent (the two lenses this task names):

**Round 1 (initial implementation) — FAIL (security), PASS-with-should-fix (correctness).** The
security lens found a **blocking** defect: `leaf_hash`/`node_hash` hashed leaves and internal nodes
identically with no domain separation — the classic Merkle second-preimage/type-confusion bug (same
class as a historical Bitcoin CVE, the exact issue RFC 6962 §2.1 was written to close). The reviewer
proved it exploitable with a working PoC: a forged 64-byte one-chunk "file," built from the two hash
values any legitimate proof holder can learn, produced a root bit-for-bit identical to a real multi-chunk
file's root. A should-fix flagged `MerkleProof.leaf_index`/`leaf_count` as unverified metadata —
`verify()` never checked them against the proof's actual step pattern, so a party could relabel
`leaf_index` to falsely claim a different chunk offset.

**Fix 1:** added `0x00`/`0x01` domain-separation prefixes (RFC 6962 §2.1-style) and a `leaf_index`
parity check across the proof's Left/Right/Promoted steps, each with its own regression test
(constructing the exact forged-file PoC and asserting the roots now differ; relabeling a valid proof's
`leaf_index` and asserting rejection).

**Round 2 (re-verification of the fix) — PASS (security, domain separation), FAIL (both lenses, on the
should-fix).** Independent re-derivation confirmed the domain-separation fix genuinely closes the
blocking issue (hand-verified the fixed tag byte makes a leaf preimage and a node preimage byte-unequal
regardless of chunk length, and reproduced the original PoC against a hand-reverted copy of the old
code to confirm it still collides there — proving the test is non-vacuous). But the `leaf_index` fix was
found only *partially* closed: the parity loop constrained just the low `steps.len()` bits of
`leaf_index` and never checked for unconsumed high-order bits or bounded `leaf_index` against
`leaf_count` — so an out-of-range or aliased `leaf_index` (e.g. `real_index + leaf_count.next_power_of_two()`)
congruent mod 2^height to the real index still passed. Confirmed with a working PoC (relabeling a valid
5-leaf proof's `leaf_index` to 12, out of range for `leaf_count = 5`, and to an arbitrarily large alias —
both incorrectly accepted). The existing regression test only exercised an in-range relabel and so gave
false confidence.

**Fix 2:** added `if proof.leaf_index >= proof.leaf_count { return false; }` before the step-walking loop
and `if idx != 0 { return false; }` after it (rejecting any unconsumed high-order bits), plus a
regression test reproducing the reviewer's exact aliased/out-of-range PoC shape. Verified directly
(not re-delegated to a third review round, given the fix is two narrow, independently-inspectable
one-line checks directly closing a PoC already proven and explained in full): traced the logic by hand,
confirmed the two new assertions genuinely exercise the closed gap, and re-ran the full suite (13/13
green) and `cargo clippy -p meridian-streams --all-targets -- -D warnings` (clean) myself.

No design decisions from this task need `/adr` — domain separation and index verification are both
correctness fixes to an already-approved cryptographic primitive choice (BLAKE3 merkle, pre-approved
per the crypto-protocols skill), not new architecture.
