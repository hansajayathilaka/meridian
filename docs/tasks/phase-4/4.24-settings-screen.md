# 4.24 — Settings screen

**Phase:** 4 — Verification & Trust + Terminal TUI Client · **Feature:** T17 — Terminal TUI Client · **Depends on:** 4.14 · **Status:** done

## Goal
Give the user a form over `config.toml`'s fields, reached from the command palette.

## Scope
- **In:** server URL, relay policy, theme, timestamps, bell, retention, reconnect backoff. Changes are
  written back with comments preserved, or the UI states a change is session-only (per 4.14/ADR 0021's
  "never rewritten wholesale" rule).
- **Out:** the config loading/precedence logic itself (4.14 owns it).

## Deliverables
1. `apps/tui/src/screens/settings.rs`.
2. Screen-snapshot tests; a test asserting a settings change either preserves `config.toml`'s comments
   or is clearly marked session-only, never silently one or the other.

## Tests
`cargo nextest run -p meridian-tui --test screens_settings`

## Status
Done. `apps/tui/src/screens/settings.rs` is the form over all 8 in-scope `config.toml` fields (server
URL, relay policy, theme, timestamps, bell, retention ×2, reconnect backoff). `apps/tui/src/config_write.rs`
solves 4.14's own deferred design problem — comment-preserving write-back via `toml_edit::DocumentMut`,
mutating exactly the targeted key while leaving the rest of a hand-authored file (including comments)
byte-identical — with an honest, never-silent session-only fallback (a named `ConfigWriteError`) for the
narrow cases a safe write can't be attempted at all (no file yet, malformed TOML, non-table section).
Every settings change is proven, by a dedicated test, to either genuinely persist with comments intact
or be visibly marked session-only — never ambiguously either.

**Review (combined `reviewer`, as named — "form UI over 4.14's already-reviewed config loader"):** one
blocking correctness finding, fixed and re-confirmed clean:
- **Reconnect-backoff integer overflow → self-inflicted config corruption.** The free-text backoff field
  accepted any value fitting `u64`, but the write path narrowed each element to TOML's signed `i64` via
  a lossy `as i64` cast — a value above `i64::MAX` silently wrapped negative on write. The settings
  screen reported the change as persisted successfully, but the *next launch* of `meridian tui` couldn't
  load `config.toml` at all (its own loader hard-rejects a negative value for a `Vec<u64>` field), with
  no in-app recovery path since the TUI itself wouldn't start. Reviewer reproduced it directly with
  `u64::MAX`. Fixed with a practical, comfortably-safe ceiling (24h in ms) enforced before any value ever
  reaches an `Effect`, plus a regression test that reproduces the original failure mode end-to-end
  (writes the unguarded value, confirms the real loader then rejects it) to prove the guard is
  meaningful, not just a rejection in isolation. The implementer independently caught and fixed a
  related comment-stripping bug in the write path during development (`Table::insert` resetting a
  preceding comment's decor vs. index-assignment, which doesn't) — caught by the task's own load-bearing
  round-trip test on the first run, exactly the scenario that test exists to catch.

`cargo test -p meridian-tui --test screens_settings` (grew from 20 to 21 tests during review), `cargo
test -p meridian-tui --lib config_write`, `cargo test -p meridian-tui` (full suite), `cargo test -p
meridian-cli --bins`, `cargo fmt --check`, `cargo clippy --workspace --all-targets -- -D warnings`, and
`bash tools/lint-tui-no-cli.sh` all clean. `Screen::Settings` is wired into `App`'s dispatch but not yet
reachable from live navigation (palette dispatch is task 4.25's job), consistent with 4.19–4.24's
established precedent.
