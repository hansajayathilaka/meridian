# 10.11 — TUI surface: `mrd.file/1` renderer + transfers pane + palette command

**Phase:** 10 — File Transfer Stream · **Feature:** T09 · **Depends on:** 10.6 · **Status:** done

**User surface:** this task IS the TUI surface for T09 (Definition of Done gate 9) — registered via
`apps/tui/src/surface.rs`'s extension mechanism, though see the Outcome below: a pre-existing registry
gap means it is not yet reachable by an actual running app pending a Phase-4-follow-up fix.

## Goal
Ship T09's TUI surface per Definition of Done gate 9 and the anticipated entry in
`docs/architecture/tui-client.md` §8's table ("T09 file transfer → `mrd.file/1` renderer + a transfers
pane with progress/resume"), registered entirely against `apps/tui/src/surface.rs`'s existing three-point
extension mechanism — zero edits to the TUI core (`app.rs`, the event loop, the layout engine).

## Scope
- **In:** a `MessageRenderer` for `mrd.file/1` (inline image preview via sixel/kitty where the terminal
  supports it, falling back to a text progress/summary line otherwise — and, per `surface.rs`'s
  forward-compatibility contract, this renderer itself is what makes `mrd.file/1` entries render
  meaningfully; an *older* client without this renderer already falls back to `placeholder_lines`
  automatically, no extra work needed there), an `ExtensionPane` implementing a transfers list (active/
  completed transfers, progress, a resume affordance), and a `PaletteCommand` to initiate a send from
  within the TUI.
- **Out:** any change to `apps/tui/src/app.rs`'s `Screen` enum, event loop, or layout engine — if this
  task needs any of those, the surface registry (from Phase 4, task 4.18) has a gap this task should
  flag rather than work around with a core edit.

## Deliverables
1. `MessageRenderer` impl for `mrd.file/1` in `apps/tui` (new module, e.g. `apps/tui/src/streams/file.rs`
   or similar), registered via `register_message_renderer`.
2. `ExtensionPane` transfers list, registered/reachable via a `PaletteCommand` (`PaletteAction::PushPane`).
3. Tests: renderer produces expected rows for a `mrd.file/1` `HistoryEntry`; an entry with no registered
   renderer (simulating an older client) still falls back to the placeholder (regression guard, mirrors
   `surface.rs`'s own existing test pattern); pane responds to key events per `ExtensionPane`'s contract.

## Risks / notes
Sixel/kitty detection should degrade gracefully on a terminal that supports neither — never assume
support, always have the text-only fallback path tested.

## Tests
`cargo nextest run -p meridian-tui`.

## Reviews
**reviewer** (code-reviewer for surface-registry conformance and zero-core-edit constraint;
test-engineer for the forward-compatibility/fallback coverage).

## Outcome
Added `apps/tui/src/streams/{mod,file}.rs`: `FileMessageRenderer: MessageRenderer` for `mrd.file/1`,
`TransfersPane: ExtensionPane` (active/completed transfers, progress, a resume affordance), and a
`palette_command()` (`id: "file.send"`, `PaletteAction::PushPane`) — all registered through
`surface.rs`'s three-point mechanism, mirroring `crate::app::register_builtin_commands`'s own shape.
Zero edits to `app.rs`, the event loop, or the layout engine (`git diff --stat apps/tui` shows only
`lib.rs` +1 line besides the two new files). `ImageProtocol`/`detect_image_protocol` (env-based sixel/
kitty capability detection) was originated here since no prior task built it to reuse (task 4.26 only
covers `NO_COLOR`/ASCII/narrow-width degradation).

Two real gaps were found and correctly flagged rather than worked around, per this task's own
instruction ("if this task needs [a core edit], the surface registry has a gap this task should flag"):
1. **No public registration seam.** `App`'s only call into `SurfaceRegistry` registration
   (`register_builtin_commands`) is private, invoked once from `App::new_with_config` — nothing outside
   `app.rs` can add a `PaletteCommand`/`MessageRenderer` into a *live* session today. Compounding this,
   `chat.rs::transcript_registry` builds a fresh, hardcoded registry containing only
   `ChatMessageRenderer` on every render call — a pre-existing task-4.20 gap that never reads `App`'s
   own `SurfaceRegistry` at all. Net effect: this task's surface is fully built and tested against a
   `SurfaceRegistry` directly, but is not yet reachable by an actual running client — a live transcript
   entry would still show `[unsupported: ...]`. Filed as a tracked carry-forward (Live carry-forwards,
   below) rather than left only as module-doc prose.
2. **Sixel/kitty structurally cannot reach a real terminal through `MessageRenderer` today.**
   `MessageRenderer::render` returns `Vec<Line<'static>>`, and ratatui's `Buffer::set_stringn` strips
   all control characters before drawing (pinned by this crate's own existing test) — a sixel/kitty
   escape sequence is definitionally control bytes, so no impl of this trait can ever emit one, on any
   terminal, regardless of real capability detection. `FileMessageRenderer::render` therefore always
   renders the text/progress fallback — the task's own risk note ("never assume support, always have
   the text-only fallback tested") is proven the universal case today, not a hypothetical. Also filed as
   a tracked carry-forward rather than silently absorbed.

Both mandatory review lenses (code-reviewer, test-engineer, run as one combined `reviewer` pass)
returned **PASS** on correctness, security/privacy, and architecture, independently verifying rather
than trusting claims: confirmed the registration-seam gap by reading `app.rs` directly, found and
reported the compounding `chat.rs::transcript_registry` half of that gap (not originally flagged by the
implementer); independently confirmed the sixel/kitty control-byte-stripping claim against
`ratatui-core`'s actual source and by running the cited existing test; verified `TransfersPane`'s resume
affordance only transitions local UI state (`TransferStatus::ResumeRequested`) and never fabricates a
confirmed resume, matching `tui-client.md`'s "never an optimistic checkmark the transport hasn't
confirmed" rule; ran `tools/lint-tui-no-cli.sh` directly and confirmed no forbidden dependency (e.g. on
`meridian-streams`) was introduced; and independently reproduced the implementer's claim that
`live_session_e2e`'s nextest test-listing failure is a pre-existing environment issue (via a `git stash
-u` to unmodified HEAD, reproducing the identical failure) rather than a hidden regression. Both
escalations were judged correctly scoped and non-blocking, conditioned on being recorded as explicit
tracker entries rather than only module-doc prose — done, see Live carry-forwards. 633/633
`meridian-tui` tests green (excluding the one pre-existing, unrelated `live_session_e2e` listing issue);
clippy/fmt clean; full workspace build clean.
