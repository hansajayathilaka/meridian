# 9.9 — Add `Mailbox::validate` config check

**Phase:** 9 — Review of Phase 8 · **Feature:** review fix (N1) · **Depends on:** — · **Status:** done

**User surface:** none — server config-validation addition (fail-closed at load time); no client-visible
behavior change (Definition of Done gate 9).

## Goal
Close a fail-closed-config gap: `Config::validate()` (`apps/rendezvous/src/config.rs`) only calls
`self.federation.validate()`. A `quota_mb = 0` with `ttl_days > 0` silently makes every offline route to
that org's recipients fail with `mailbox_full` immediately — an operator typo indistinguishable from
"mailbox intentionally near-full" until debugged, unlike `Federation`'s analogous footguns (e.g.
`handshake_timeout_ms == 0`), which are caught at load time with an explicit, actionable error.

## Scope
- **In:** a `Mailbox::validate` method following the `Federation::validate` precedent exactly (same
  error style/type), wired into `Config::validate()` alongside the existing `federation.validate()`
  call. Catch at minimum `quota_mb == 0` combined with a non-zero `ttl_days` (mailbox effectively
  disabled by accident) — extend to other clearly-invalid combinations if `Federation::validate`'s
  precedent suggests a broader pattern (e.g. also flag `ttl_days == 0` combined with a non-zero
  `quota_mb`, the mirror-image footgun).
- **Out:** No change to `Mailbox`'s actual field semantics or defaults — this task only adds load-time
  validation for combinations that are already meaningful but currently silent.

## Deliverables
1. `Mailbox::validate` (or equivalently-named method) added, wired into `Config::validate()`.
2. A test proving a `quota_mb = 0`/non-zero-`ttl_days` config fails validation with an actionable error,
   and that a sane config still passes.

## Risks / notes
No file overlap with other phase-9 tasks (aside from `config.rs`, which no other task touches) —
independent, can land in any order.

## Outcome
`Mailbox::validate` rejects `quota_mb == 0` combined with non-zero `ttl_days`, following
`Federation::validate`'s exact combination-check shape and error style. Deliberately does not flag
`ttl_days == 0` with non-zero `quota_mb` — architect independently verified, against both `ws.rs` and
`federation/inbound.rs`, that `ttl_days == 0` short-circuits before `quota_mb` is ever consulted on
either the local or federated route path, so the asymmetry is correct, not an oversight, and matches
`Federation::validate`'s own combination-check precedent rather than its unconditional-field-check one
(which would have wrongly rejected the legitimate fully-disabled `quota_mb=0, ttl_days=0` combo). Five
new tests, all confirmed non-vacuous.

code-reviewer + architect both PASS, zero blocking findings. Two non-blocking notes, not folded in:
- **Nit:** the doc comment/error text says `quota_mb=0` makes "every offline route... fail" — technically
  a zero-length blob would pass (`0 > 0` is false), though no real envelope is ever zero bytes in
  practice. Not worth a hedge.
- **Related, out-of-scope footgun (future N-finding candidate):** `purge_interval_secs == 0` has the same
  "no legitimate standalone 0" shape as `quota_mb`, but `mailbox_purge.rs` already fail-safes it via
  silent `.max(1)` clamping rather than `Federation`'s fail-loud-at-load pattern — inconsistent with this
  task's own precedent, but pre-existing and outside this task's "at minimum" scope. No open task owns
  this; flagged for a future `/plan-phase` if consistency is prioritized.
