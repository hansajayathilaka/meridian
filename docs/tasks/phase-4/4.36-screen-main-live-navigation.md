# 4.36 — `Screen::Main` + live navigation

**Phase:** 4 — Verification & Trust + Terminal TUI Client · **Feature:** T17 — Terminal TUI Client (gap closure) · **Depends on:** 4.29 · **Status:** pending

## Goal
Build the real post-auth home screen and wire the navigation every screen's own doc comment has been
deferring to "a future task": `Contacts` → `Chat`, `Contacts`'s `v` → real `Screen::Verify` (replacing
the "not implemented yet" stand-in from task 4.19), `Ctrl-R`'s live `pending_requests()` snapshot, and
the palette's Settings registration.

## Scope
- **In:** new `screens::main` module + `Screen::Main` variant, constructed from a `LiveSession`
  (task 4.29's type — this task can be built and tested with a fabricated `LiveSession`, zero dependency
  on Preflight existing, same incremental pattern this whole phase already used for every other screen).
  Repoint `Contacts`'s `Enter` to open `Screen::ContactDetail` via its own dedicated key and give `Chat`
  its own — per `crate::screens::contacts`'s and `Screen::Chat`'s own doc comments naming this exact
  repoint as deferred. Register a working "open Settings" palette command now that a live
  `config`/`config_path` exists.
- **Out:** Preflight (deciding *when* `Screen::Main` is reached — 4.37's job). Explicitly document that
  `Ctrl-R`'s queue reflects `pending_requests()` **as of session load**, not live arrivals during the
  running session (that's 4.35's contribution) — same honest-scoping discipline this crate already uses
  elsewhere (e.g. 4.28's own documentation of what does and doesn't work).

## Deliverables
1. `screens/main.rs`, `Screen::Main`.
2. Updated `Contacts`/`ContactDetail`/`Chat`/`Requests`/`Verify` key-dispatch routed through it.
3. Palette registration for Settings.
4. Screen-snapshot tests at 80×24 and narrow width (mirroring task 4.26's degradation-test conventions).

## Risks / notes
- Independent of 4.30–4.35's *completion* — this task can be built/tested with a fabricated `LiveSession`
  the same way every prior screen task tested against fabricated state before its own navigation task
  landed.
- Depends only on 4.29 (`LiveSession` type to construct from).
- See [4.37's own Risks/notes](./4.37-preflight-routing.md#risks--notes) for a residual gap 4.31's review
  escalated: once a live, already-unlocked session exists (this task + 4.37 together), `run_worker`'s
  already-built contacts/trust handlers (4.31/4.32) still re-derive their own store from disk per
  dispatch rather than reusing it — harmless for OS-keystore accounts, but file-backed accounts still
  fail closed on every contacts/trust action even after Preflight lands, unless a follow-up task closes
  it. Not this task's own scope to fix (it owns screen content/navigation, not `run_worker` internals),
  but worth knowing before treating 4.29–4.38 as having fully closed every angle of the T17 gap.

## Tests
`cargo nextest run -p meridian-tui --test screen_main` (new file); regression on
`screens_contacts.rs`/`screens_chat.rs`/`screens_verify.rs`/`screens_requests.rs`.
