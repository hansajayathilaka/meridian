# 9.4 — Fix drain/registration race window

**Phase:** 9 — Review of Phase 8 · **Feature:** review fix (F4) · **Depends on:** 9.1 (soft) · **Status:** done

**User surface:** none — server-internal connection-lifecycle/locking fix; no client-visible behavior
change beyond correctly delivering something live instead of mailboxing it (Definition of Done gate 9).

## Goal
Close the window between `drain_mailbox` running and `state.registry.add(...)` registering the
connection as reachable (`apps/rendezvous/src/ws.rs:90-101`). A `Route` from a third party landing in
that gap currently finds the recipient not yet registered, falls through to `queue_to_mailbox`, and then
sits mailboxed until the recipient's *next* reconnect — even though the recipient is, in wall-clock
terms, already live. This silently contradicts the "deliver on reconnect" framing for a message that
actually arrived after reconnect completed.

## Scope
- **In:** the connection-setup sequence in `apps/rendezvous/src/ws.rs` (`handle_socket` or equivalent,
  around lines 90-101). Either: (a) register the connection (`registry.add`) *before* draining, with
  drain-vs-live-delivery ordering handled via a per-recipient lock/queue rather than relying on
  registration ordering to prevent double-delivery; or (b) keep the current ordering but re-run a tiny
  incremental drain immediately after `registry.add` completes, to catch anything enqueued in the gap.
  Pick whichever integrates more cleanly with 9.1's new locking primitive (if 9.1 lands first, reuse its
  per-recipient lock rather than inventing a second one).
- **Out:** No change to the drain's own content/ordering semantics (still oldest-first, still respects
  TTL post-9.3) — this task is scoped purely to the race window, not a broader rewrite of the reconnect
  path.

## Deliverables
1. The race window is closed by one of the two approaches above.
2. A regression test demonstrating: a `Route` arriving in the (now-closed) gap between drain and
   registration is delivered live, not mailboxed — requires a deterministic way to pause execution
   between the two steps (e.g. a `#[cfg(test)]` hook or channel-based synchronization), since the race
   is naturally too narrow to hit reliably by chance.

## Risks / notes
Soft dependency on 9.1 (same file, `ws.rs`, and the recommended fix shape is the same "per-recipient
lock" primitive 9.1 introduces) — landing after 9.1 lets this task reuse that lock instead of inventing
a second one. Not hard-blocking; if 9.1 chooses the atomic-SQL-transaction shape instead of a lock for
its own fix, this task's own lock/queue can still be introduced independently.

## Tests
`cargo nextest run -p meridian-rendezvous` (new deterministic race-window regression test), `cargo
clippy -p meridian-rendezvous --all-targets --features sqlite -- -D warnings`.

## Reviews
**architect** (touches connection-lifecycle sequencing, worth checking against the delivery-guarantee
framing in the feature spec), **code-reviewer**, **test-engineer** (the deterministic reproduction of a
narrow race is the hard part of this task's acceptance).

## Outcome
Chose approach (a): register the connection (`registry.add`) before draining, closing the original
window where a `Route` landing between drain and registration found the recipient "not yet registered"
and wrongly fell through to the mailbox. Reused 9.1's `MailboxLocks` (made `pub(crate)`) for a definite
before/after ordering between the drain's read and a racing same-recipient write. New deterministic
regression test (`mailbox_drain_registration_race.rs`, reusing 9.1's `DelayedStore` technique) verified
to fail pre-fix and pass post-fix by an independent test-engineer pass.

**First review round (architect + code-reviewer) found a blocking defect**: the initial fix held the
recipient's lock shard across `drain_mailbox`'s per-row network sends, not just the store read — a
slow or adversarial reader (authenticate, then stop draining the socket) could stall that lock
indefinitely, blocking every other sender's `mailbox_enqueue_with_quota` call for that recipient (and,
at ~1/256 odds, unrelated recipients sharing the shard). Fixed by narrowing the lock's scope to just the
`mailbox_list_for_recipient` read, released before any send — the read is the only step that needed
serializing against a racing write. Re-review confirmed: the blocking defect is closed, the original F4
ordering guarantee and regression test still hold, and narrowing the lock introduces no new failure mode
(the read-then-send gap it leaves is pre-existing best-effort delivery shape, unchanged since task 8.7,
not something this task introduced).

Second-round **architect + code-reviewer PASS**, zero remaining findings. The one should-fix from the
first round (the accepted, out-of-scope `handle_route` check-then-act residual) is now recorded in
[docs/tasks/README.md](../README.md)'s Live carry-forwards rather than left only as a code comment.
