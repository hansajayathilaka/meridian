### Item 1 — `tools/lint-server-no-core.sh`: grep → `cargo tree`
Was a single grep of `apps/rendezvous/Cargo.toml` for a literal `meridian-core =` line. It saw only
*direct* deps spelled exactly that way — a transitive route, a rename, or a dep on
`meridian-identity`/`-store`/`-crypto` all passed silently.

Now a structural `cargo tree -p meridian-rendezvous -e normal,build` check, run twice (default and
`--all-features`, since `test-tamper-hook` exists and a feature is exactly what could quietly pull in
a core crate). Design choices, each deliberate:
- **Allowlist, not denylist:** anything matching `meridian-*` other than `meridian-proto` (and the
  server itself) fails. A denylist of today's crate names would miss a crate added tomorrow.
- **`-e normal,build` excludes dev-dependencies**, with the reason in a comment: the invariant is
  about what ships in the server binary, and the crate legitimately dev-depends on
  `meridian-signaling`/`-identity`/`-store` to drive a real client in integration tests. Treating that
  as a violation would make the lint unusable.
- **Fail-closed:** if `cargo tree` itself errors, that is a FAIL, never a silent pass.
- `--selftest` added (mirroring `lint-no-serde-on-blob.sh`) and wired into `Justfile` + CI.

**Proven both ways, on the real tree.** Clean run: `OK: meridian-rendezvous depends only on
meridian-proto (checked transitively, default + all features).` Then a *real* violation was planted —
adding only `meridian-signaling` to the manifest — and the lint reported **three** offenders:
```
FAIL (default features): ... contains workspace crate(s) it must not depend on:
  - meridian-identity
  - meridian-signaling
  - meridian-store
```
`-identity` and `-store` were surfaced **transitively**, which is exactly what the old grep could never
have done. Manifest reverted; `git diff --stat` clean.

### Item 2 — salted `LogId` + tracing lint
`apps/rendezvous/src/logid.rs`: `HMAC-SHA256(per-process random salt, domain ‖ input)` truncated to
8 bytes of hex. `sha2` added as a dependency (a primitive, like the existing `hmac`/`sha1`).
- **Salted, not a bare hash** — and the doc comment says *why* this specific system needs it: the
  candidate key set for a rendezvous server is *exactly the accounts it serves*, which the operator
  already holds, so `SHA256(account_pub)` would be a rename rather than a protection.
- Per-process salt also means tokens are **not correlatable across restarts**.
- **Honestly documented non-property:** tokens *are* stable and correlatable *within* one process
  lifetime — that is what makes them useful for debugging one incident — and anyone who can read
  process memory recovers the salt. `LogId` defends against log disclosure, not host compromise.
- Manual `Debug` (not derived) so `?log_id` is as safe as `%log_id`.
- 5 unit tests: stability, distinctness, salt-dependence, no-leak-in-any-rendering (`{}`, `{:?}`,
  `as_str`, plus hex-of-input), construction pinning.

`tools/lint-no-raw-id-logging.sh`: fails if a logging macro in `apps/rendezvous/src` mentions an
identifier-bearing name (`account_pub`, `target`, `nonce`, `blob`, `peer_addr`, …) without a `LogId`
wrapper. Multi-line aware (perl slurp over the macro call). Covers `tracing::*!`, bare `info!`-style
macros, and `println!`/`panic!`/`dbg!` (de facto logging on a server).
- **Limits documented in the header, not implied away:** it does *not* catch an identifier laundered
  through an intermediate binding, a `Debug`-derived struct logged whole, or a `format!` built
  elsewhere. A PASS means "the obvious mistake was not made", never "the invariant is proven".
- `--selftest` proves all four bad shapes trip and that the sanctioned `LogId` form passes.
- **A real false positive was found and fixed while writing it:** the lint flagged `logid.rs`'s own
  module doc, which shows the forbidden shape as a counter-example. A lint that flags prose gets
  deleted, so whole-line comments are now stripped before matching (newlines preserved, so line
  numbers stay accurate) and a doc-comment fixture is pinned in the selftest.
- Verified against a *real* planted violation in `metrics.rs` (caught at the right file:line), then
  reverted clean.

### Item 3 — bounded rate-limiter growth
`apps/rendezvous/src/ratelimit.rs`'s map grew forever, one entry per distinct attacker-controlled key
ever seen — an unauthenticated memory-exhaustion vector.
- **Amortised sweep:** at most one `retain` per window (tracked by `last_sweep`), so the hot path
  stays O(1) rather than becoming O(n) in tracked keys.
- **Eviction cannot reset a live budget.** An entry is dropped only when `now - start >= window` —
  precisely the condition under which the *next* `check` would reset `count` to 0 anyway. A dropped
  entry and a retained-then-reset entry are observationally identical, so no key inside its window
  (in particular none at or over its limit) is ever removed. Dropping a live counter would have
  turned a memory fix into a rate-limit **bypass**.
- **No hard cap, deliberately.** A cap must evict entries still inside their window, which *is* that
  bypass: an attacker at their limit could flood distinct keys to force eviction of their own live
  counter and reset their budget. Recorded residual: within a *single* window an attacker can still
  create one entry per key they can present — bounded by IPs they control (auth) and, for
  account-keyed limiters, by every account key first completing an IP-rate-limited handshake.
- `with_window(limit, window)` added so tests exercise expiry without sleeping a real minute;
  `tracked_keys()` is `#[cfg(test)]`.
- 3 unit tests: growth bound, no-false-eviction (a key at its limit stays rejected across 500 keys of
  churn), and the pre-existing legitimate reset after a real window elapse.

**The growth-bound test was verified to catch the old behaviour:** with the sweep short-circuited it
FAILS with `tracked=151` (all 150 keys ever seen, plus one) against the bounded expectation of ≤51.
