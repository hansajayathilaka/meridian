# 3.9 — Resolve the dead per-partner `policy` field in `federation_map.toml`

**Phase:** 3 — Review of Phase 2 · **Feature:** review fix (F7) · **Depends on:** 3.1 · **Status:** done

## Goal
An operator writing `policy = "closed"` per partner in the map must not silently get nothing.

## Scope
- **In:** architect picks one of — remove the field + its schema line (cleanest), reject/warn on
  presence, or actually enforce it. Then implement that one.
- **Out:** redesigning `FederationPolicy`.

## Deliverables
1. `apps/rendezvous/src/federation/discovery.rs` — L102/L261 (`Endpoint::policy`).
2. The documented map schema updated in the same PR (discovery/deployment doc).
3. `apps/rendezvous/tests/federation_discovery.rs` — a map containing `policy` produces the decided
   outcome (parse error / warning / enforcement), **not silence**.

## Risks / notes

## Outcome
Architect decision (of the three options this task's Scope named): **reject-on-presence**, not
"remove the field/schema line" and not "actually enforce it." Reasoning: plain removal would just
relocate the same silent-failure bug from "field nobody reads" to "unknown TOML key serde silently
drops" — an operator writing `policy = "closed"` would still get silent nothing. "Enforce" is
explicitly out of this task's Scope ("Out: redesigning `FederationPolicy`") — `FederationPolicy` is
`Open | Allowlist | Closed`, one server-wide mode with no per-partner override dimension, and
composing a genuine per-partner override in would be exactly that redesign — and it would also
silently no-op for every SRV-discovered partner, since SRV structurally can never carry a `policy`
value at all (same asymmetric-hazard shape task 3.16's review flagged for a different field).

**`apps/rendezvous/src/federation/discovery.rs`:** removed `Endpoint::policy: Option<String>`
entirely (it was parsed from `federation_map.toml` but never consulted by anything). Added
`DiscoveryError::UnsupportedPolicyField { domain: String }`, matching the existing
`MissingPin`/`InvalidEndpoint`/`DuplicateDomain` variants' field shape and message convention.
`StaticMap::from_toml_str`'s per-entry validation loop now rejects any `[[partner]]` entry that
sets `policy` at all — same fail-closed, whole-file-rejected-on-first-bad-entry posture as the
existing checks; `PartnerEntry::policy` is kept (parse-only struct) specifically so serde can still
distinguish "field present" from "field absent," which is what lets the error carry the offending
domain rather than degrading to a generic TOML-parse failure. Module doc comment rewritten to state
there is no per-partner `policy` field, replacing the stale "carried through for 2.6 to define"
framing (2.6 already defined federation policy as server-wide `FederationPolicy` in `policy.rs` —
this field was never actually going to be what 2.6 meant).

**Deliverable #2 (documented schema, same PR):** `demo/two-orgs/federation_map.toml` (the shipped
fixture task 2.11's docker-compose profile loads for real) had `policy = "allowlist"` in both
`[[partner]]` entries and a schema-comment block documenting the now-dead field — both removed,
replaced with a note pointing at `federation.policy` (server-wide, each org's own config) as the
real mechanism. `docs/architecture/data-model.md`'s schema description updated the same way.
`docs/operations/deployment.md`, ADR 0017, and `features/06-cross-org-federation.md` were checked
(grepped) and never referenced a per-partner field, so needed no edit.

**Deliverable #3 (test proving the outcome, not silence):** `apps/rendezvous/tests/federation_discovery.rs` —
new `entry_with_policy_field_is_rejected_fail_closed` asserts
`DiscoveryError::UnsupportedPolicyField { domain }` on a `policy`-bearing entry. The shared
`TWO_PARTNER_MAP` fixture's `policy = "allow"` line was removed (would otherwise fail every test
using it), and stale `.policy` assertions removed from three other tests. Two other test files
(`federation_route.rs`, `federation_outbound_policy.rs`) had `policy: None,` deleted from
`Endpoint { ... }` struct literals (compile fix only, no behavior change).

**Review — one combined `reviewer` agent call (architect + code-reviewer lenses):** both **pass**,
zero blocking findings. Confirmed: no dangling `Endpoint::policy` reference anywhere in the crate;
the new error variant's fail-closed posture is identical end-to-end to the existing ones
(`StaticMap::load` failure still panics at boot, same as `MissingPin`/`DuplicateDomain`/`Toml` —
no new partial-success path); `federation/policy.rs` and `outbound.rs`'s task-3.1 SSRF choke point
are untouched (respects the "Out: redesigning `FederationPolicy`" boundary); doc-sync sweep
(`deployment.md`, ADR 0017, feature spec, demo README/entrypoint script) confirmed complete, no
other doc referenced the dead field. Two non-blocking notes, neither actioned: (1) the new
`policy.is_some()` check runs before the `MissingPin` check, so an entry with both problems reports
`UnsupportedPolicyField` — not a defect (module posture is "one bad entry fails the file," not
"report every problem"), no test/doc claims a specific priority; (2) `docs/tasks/phase-2/2.5-federation-discovery.md`
still describes the long-abandoned DB-table shape (`domain PK, endpoint, ca_pin, policy`) —
deliberately historical scope narrative, not a live schema doc, left as-is.
