# 4.33 — Real `run_worker`: outbound chat

**Phase:** 4 — Verification & Trust + Terminal TUI Client · **Feature:** T17 — Terminal TUI Client (gap closure) · **Depends on:** 4.20 · **Status:** done

## Goal
Execute `SendMessage`/`PersistHistory` for real — the send half of the T17 demo's "both sides chat" step.

## Scope
- **In:** `run_worker` arms mirroring `apps/cli/src/chat.rs::send_text`'s seal-then-route path exactly,
  including first-send session establishment (`!state.has_session(&peer_ik)` → `fetch_with_retry` +
  `start_initiator_session`, same as the CLI). Mint `mid`/timestamp **inside the worker**, never in
  `update` (per `SendMessageRequest`'s own doc comment — this keeps `update` pure). Report
  `delivered: bool` from `route_tolerant`'s real return value, never implying store-and-forward (T07 is
  out of scope for this whole phase — the outbox stays a local retry queue and copy must say so).
  Deliberately open/close its own `SignalingClient` connection per call rather than holding one open —
  simpler, and avoids coupling to 4.35's persistent-connection design. This is a documented v1
  simplification, not a correctness gap; a later task can unify the two connection strategies if
  reconnect-per-send proves too chatty in practice.
- **Out:** the receive path (4.35 — a materially different mechanism, a persistent connection rather than
  a per-call one); navigation.

## Deliverables
1. Two `run_worker` arms: `SendMessage`, `PersistHistory`.
2. Tests for: first-send session establishment; delivered vs. offline-peer outcomes; confirmation that
   `SendGate` is never re-derived or bypassed here (the screen already checked it before dispatching —
   this task must not add a second, possibly-drifting check of its own).

## Risks / notes
- **Do not re-check the send gate inside the worker.** The screen's own `update` already computed
  `SendGate` and only dispatched `SendMessage` because it was `Ok` — a second check here risks silent
  divergence from the screen's canonical logic, exactly the class of defect the un-softenable key-change
  UI exists to prevent.
- No dependency on 4.29, 4.30, 4.31, 4.32, or any other task in this gap-closure set — independently
  testable today.

screens_chat` (regression).

## Status
Done. `apps/tui/src/worker.rs` gained real `run_worker` arms for `SendMessage`/`PersistHistory`,
mirroring `apps/cli/src/chat.rs::send_text`'s seal-then-route sequence and its first-send session-
establishment path (`fetch_with_retry` + `start_initiator_session`) exactly. The worker mints `mid`/
timestamp itself, seals via `ChatState::seal_outbound`, persists `sessions.bin` immediately afterward
(a deliberate, verified-safer tightening beyond the CLI's own ordering — the ratchet advance is fully
synchronous, so persisting before attempting delivery minimizes the crash window to the local disk write
rather than spanning the whole network round trip), then routes via `route_tolerant`. Per this task's
own scope, opens/closes its own `SignalingClient` connection per call rather than holding one open —
deliberately not coupled to task 4.35's separate, later persistent-connection design for the inbound
path. The worker has no `TrustStore` reference anywhere in its call graph — structurally, not just by
convention, `SendGate` cannot be re-checked or bypassed here; the screen's own prior check is the only
gate.

**Review (combined `reviewer` + separate `test-engineer`, as named):** the phase's most security-
sensitive execution path so far — where the un-softenable send-gate decision meets real network I/O and
ratchet advancement — held to a correspondingly high bar. Both passed cleanly overall, with one real,
cross-cutting completeness gap found and closed:
- **`resolve_server` had no path back to the server used at registration**, contradicting two
  already-written docs (`AccountConfig`'s own doc comment, `tui-client.md`) that both already promised
  "config.toml override, else the value used at registration." A user onboarding entirely through the
  TUI would hit a hard fail on their very first send — the T17 demo couldn't complete without a manual
  `config.toml` edit nothing in the UI prompts for. Fixed by adding `server: Option<String>` to the
  shared `AccountDescriptor` (`apps/core/src/account.rs`, `#[serde(default)]` for backward compatibility
  with account files predating the field — verified with a test that loads a literal legacy JSON blob
  missing the key), populated by `handle_register` (task 4.30's own code) on successful registration, with
  `resolve_server` falling back to it when `config.toml` has no override. The CLI's own registration path
  was confirmed unaffected (it takes an explicit `server` argument every invocation, no equivalent gap).
  One minor, non-blocking residual noted by the reviewer: a user who registers via `meridian-cli` and
  later switches to `meridian-tui` still hits the fail-closed path once, since only the TUI's own
  `handle_register` populates this field — worth a note for a future cross-client fast-follow, not a
  blocker here.
- A doc comment inaccurately claimed the persist-before-delivery ordering "mirrors the CLI" when it's
  actually a deliberate, safer tightening beyond it — corrected.
- `test-engineer` recommended (non-blocking) closing the one genuinely untested adversarial scenario: a
  *hard* connection failure (unreachable server), distinct from the already-tested *soft* offline-peer
  case. Added, using the same unreachable-port pattern already established in `apps/cli/tests/
  session_connect.rs`. The other two named scenarios ("desync mid-send" in particular) were confirmed
  genuinely out of scope for this task — desync is a receive-side-only concern (task 4.9's own domain,
  already covered there; task 4.35's future receive path is the only place a send-side manifestation
  could ever be observed).
