# 1.17 — ADR: deniability vs. envelope identity-key signature

**Phase:** 1 — Review of Phase 0 · **Feature:** review fix (on-the-fly decision) · **Depends on:** 1.1 · **Status:** **done** — ADR 0016 accepted (option b), interim doc-honesty edits landed

## Goal
Resolve the contradiction inside the design docs: the envelope signs every ciphertext with the identity
key (`Sign_IK{ratchet_ct}`, `docs/api/messaging-envelope-v1.md:96`) — third-party-provable authorship —
while threat-model goal 4 (`docs/security/threat-model.md:34`) claims deniability because identity-key
signatures are "confined to key distribution and signaling." Record an explicit, binding decision.

## Scope
- **In:** an ADR (via `/adr`, next number after 0015) that decides one of: (a) narrow the threat-model
  deniability claim to match the signed envelope, or (b) spec envelope v2 to drop the per-message
  identity-key signature (the ratchet AEAD already binds both identity keys). Update whichever doc the ADR
  chooses (`threat-model.md` and/or `messaging-envelope-v1.md`) to remove the contradiction.
- **Out:** implementing envelope v2 if that path is chosen (future build phase — record it as a follow-up).

## Deliverables
1. New ADR recording the deniability-vs-signature decision + rationale.
2. Edited `docs/security/threat-model.md` and/or `docs/api/messaging-envelope-v1.md` so the two agree.

## Status
**Done.** Decision recorded as **[ADR 0016](../../adr/0016-envelope-deniability.md)**: **option (b)** —
envelope **v2 drops the per-message identity-key signature**. Phase 1 lands only the doc-honesty
edits; the wire is unchanged and v2 implementation is a scheduled follow-up build task.

**architect** (decision) and **security-reviewer** (deniability property) both reviewed.
security-reviewer returned **APPROVE-WITH-CHANGES**, and found real defects in the initial reasoning —
all folded into the ADR before it was written:
- The proposed KCI residual's justification was **factually backwards**. An attacker holding a
  responder's SPK secret can *forge* a first-contact session but **cannot** read the genuine sender's
  first message (that needs `DH2 = DH(EK_A, IK_B)`). So (b) is a strict gain in attacker capability,
  not a wash — and since SDP rides the same envelope, the forgery is a media/data MITM that safety
  numbers cannot detect. Enforced SPK rotation became a binding precondition (C1, R1).
- The signature is **load-bearing for the prekey preamble** in a way not initially stated: the AEAD
  fails closed *late* (OTK consumed + session inserted before `decrypt`), so preamble mutation on a
  *genuine* envelope burns an unrelated OTK and installs a session that permanently blocks the real
  sender. Commit-on-successful-decrypt is now normative (C2, R3).
- The `AD` must be the **raw Ed25519 encodings** — the Ed25519→X25519 map drops the sign bit, so
  `A` and `−A` derive an identical root and only the AD in the AAD catches a sign-flip once the
  signature is gone (C3).
- `MessageEnvelope` has **no `v` field** at all, so a "hard flag day" had nothing to hang on (C5).
- The claimed post-decryption "AD assertion" is **tautological** as constructed (C6).
- The doc list was incomplete: [`wire-protocol.md §3`](../../api/wire-protocol.md) carried a
  **second, divergent** envelope definition (`v`/`eid`, signing input omitting `sender_pub` — itself a
  key-substitution weakness in the spec). Reconciled to the implemented format.

### Landed (docs + comments only — no wire change)
- New **ADR 0016** + index row in `docs/adr/README.md`.
- Contradiction removed in `docs/security/threat-model.md` (goal 4 + a new §1.3 residual),
  `docs/api/messaging-envelope-v1.md` (versioning note + §4), `docs/api/wire-protocol.md` §3,
  `docs/architecture/system-design.md` (§4.3 point 3, the impersonation line, limitation 7), and
  `docs/security/threat-mitigation-matrix.md` (A2 row + first-message deniability line).
- `apps/envelope/src/signal.rs`: corrected the claim that the DTLS fingerprint is "authenticated by
  the envelope's Ed25519 signature". It is not, and **was already wrong before this task** —
  `SignalContent` is ratchet *plaintext*; binding comes from the AEAD's `AD` and X3DH's `DH1`. This
  is also why removing the signature is a no-op for fingerprint binding.

### Deliberately not done (recorded disagreement)
security-reviewer wanted `.claude/skills/crypto-protocols/SKILL.md` rule 4 ("check the identity
signature before touching the payload") superseded in this pass. **Declined for the interim:** v1
still signs, and the rule is correct and load-bearing for the code that exists today — weakening it
now would tell a future session not to verify a signature the current wire depends on. Recorded as a
v2-time obligation under ADR 0016 C4 instead.
