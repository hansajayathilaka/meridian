# 4.32 — Real `run_worker`: trust & request-queue persistence

**Phase:** 4 — Verification & Trust + Terminal TUI Client · **Feature:** T17 — Terminal TUI Client (gap closure) · **Depends on:** 4.21, 4.22, 4.4 · **Status:** pending

## Goal
Execute `AcceptRequest`/`RejectRequest`/`MarkVerified`/`AcknowledgeKeyChange` for real. These four
collapse into one task, not two, because every one shares the identical "the screen already computed the
answer in-memory; the effect's execution is purely reload → replay the same deterministic mutation →
reseal → persist" shape, and none alone is large enough to be its own PR.

## Scope
- **In:** `run_worker` arms mirroring `apps/cli/src/chat.rs::answer_request`'s accept/reject order
  (`ChatState::accept_request` before `TrustStore::observe`, per task 4.7's own fix — do not reorder) and
  `apps/core/src/trust.rs::TrustStore::mark_verified`/`acknowledge_key_change`. Each arm reloads
  `trust.bin`/`sessions.bin` fresh from disk, replays the exact deterministic call the screen already
  applied in-memory, reseals, and writes — the worker never receives the live `TrustStore`/`ChatState`
  value itself over the effect channel (per the architect's settled guidance: these types are
  deliberately not `Clone`, and the worker's job is durability of an already-decided answer, not a
  second decision).
- **Out:** network I/O; navigation; live arrival of new requests while a session is running (that's
  4.35's job — this task only persists a decision the screen already made about a request already on
  screen).

## Deliverables
1. Four `run_worker` arms: `AcceptRequest`, `RejectRequest`, `MarkVerified`, `AcknowledgeKeyChange`.
2. Tests including "reject leaves no trace" (mirrors `RejectRequestRequest`'s own doc'd invariant — a
   rejected request must not persist any record of having existed) and confirmation that the
   un-softenable key-change semantics (task 4.4/4.23) stay intact end to end through a real persist
   round-trip, not just in-memory.

## Risks / notes
- **Never re-derive or second-guess the gate.** The screen already decided to mark-verified/acknowledge
  before dispatching the effect; this task's job is purely to make that decision durable, never to
  re-evaluate whether it was the right call.
- No dependency on 4.29, 4.30, 4.31, or any other task in this gap-closure set — independently testable
  today.

## Tests
`cargo nextest run -p meridian-tui --test run_worker_trust` (new file); `cargo test -p meridian-tui --test
key_change_adversarial` (regression — must stay green, no softening).
