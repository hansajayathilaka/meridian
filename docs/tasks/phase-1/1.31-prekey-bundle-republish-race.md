# 1.31 — prekey-bundle republish/fetch race on reconnect

**Phase:** 1 — Review of Phase 0 · **Feature:** on-the-fly (found during 1.27's live-rig verification) ·
**Depends on:** none · **Status:** pending

## Goal
Fix a real, reproducible race between `session_connect.rs`'s bundle republish and the peer's bundle
fetch, so two peers who both reconnect around the same time (network blip recovery, app relaunch, an
automatic reconnect timer on both ends) don't hit a hard, loud connect failure.

## Background
Found while personally re-verifying [1.27](./1.27-pcap-assertions-ci.md) against the live netns/coturn
rig: `apps/cli/src/session_connect.rs`'s `run_webrtc` republishes a fresh SPK/OTK bundle to the
rendezvous at the start of *every* `session connect` invocation (both roles), but nothing synchronizes
the peer's `fetch_with_retry` against that publish actually landing. `apps/core/src/chat.rs`'s
`PrekeyVault::set_bundle` is a single-slot overwrite (no retained prior generation), so if an
initiator's fetch lands on a bundle that was current a moment ago but has just been superseded by the
responder's in-flight republish, the initiator's X3DH init references OTK ids the responder's
freshly-regenerated vault no longer has secrets for — `error: answer: crypto/envelope error: no
matching prekey secret for incoming session`, a hard failure, not a retry.

This reproduced on ~4 of 5 full `tools/netns-nat-matrix.sh matrix` runs before 1.27 worked around it
(always cell 2 onward within one run, never cell 1 — consistent with "no prior bundle exists yet to
race against" on a brand-new identity's first-ever publish). 1.27's fix was rig-only (per-cell identity
homes, so no cell within a `matrix()` run ever has a prior bundle to race against) and does not touch
this crate — it narrows the race's reachability inside that one test harness but does not close the
underlying race in `session_connect.rs` itself, which remains reachable in real (non-test) usage.
connectivity-debugger's 1.27 review independently confirmed the mechanics and recommended tracking this
separately: "a genuine availability bug reachable in production... any time two peers with an existing
published bundle both trigger a reconnect around the same time... Impact is a hard, loud connect
failure... not a confidentiality/integrity regression, no downgrade, no auth bypass — so it's a
reliability/UX bug, not a security bug per se, but real and user-facing."

## Scope
- **In:** close the publish/fetch race for reconnects. Candidate approach (per connectivity-debugger,
  matching standard X3DH/Signal-protocol prekey rotation practice): retain the previous SPK/OTK
  generation in `PrekeyVault` for a bounded grace window after a republish, rather than single-slot
  overwrite, so a fetch that lands on the "just-superseded" bundle can still complete. Any approach must
  preserve forward secrecy (bounded generations, eventual expiry — not indefinite retention).
- **Out:** the 1.27 rig-only mitigation (already landed, stays as-is); anything to do with the wire-level
  pcap assertions or NAT-matrix rig itself.

## Risks / notes
Touches prekey/vault handling (`apps/core/src/chat.rs`), which is trust-critical crypto-adjacent state —
route through **rust-dev** with **security-reviewer** sign-off specifically on the retention-window
approach and its forward-secrecy implications before merge.

## Tests
A regression test reproducing the race deterministically (two concurrent `session_connect`-style flows
against the same identity pair, timed so the fetch lands mid-republish) — the netns rig reproduces it
empirically but is too slow/flaky for a unit-test-speed regression check.

## Reviews
**security-reviewer** (retention-window / forward-secrecy), **connectivity-debugger** (confirms the fix
against a live reconnect scenario).
