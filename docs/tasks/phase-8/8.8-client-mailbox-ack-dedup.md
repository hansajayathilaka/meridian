# 8.8 — Client-side `MailboxAck` send + redelivery-dedup confirmation

**Phase:** 8 — Offline Ciphertext Mailbox · **Feature:** T07 · **Depends on:** 8.7 · **Status:** pending

## Goal
Make the client actually ack what it received (so the server-side mailbox empties), and confirm
the already-shipped `eid` dedup (task 6.4) is what makes a duplicate redelivery harmless, per T07
deliverable 2 ("client offline-queue + dedup on redelivery, idempotent by envelope id").

## Scope
- **In:** `meridian-signaling`'s client (`apps/signaling/src/client.rs`) collects `mailbox_id`s off
  incoming `Deliver` frames that carry one, and sends `MailboxAck{ids}` once the batch has been
  handed to the caller (i.e. ack-after-processing, not ack-on-receipt — an ack before the envelope
  is durably handled would lose it on a crash between ack and processing). Confirm
  `apps/core/src/chat.rs`'s existing `eid`-based dedup (task 6.4) already rejects a redelivered
  envelope with no mailbox-specific code needed — if a gap exists (e.g. dedup state not surviving
  the reconnect that triggers redelivery), fix it here; if not, this sub-item is verification only.
- **In, added by [ADR 0024](../../adr/0024-mailbox-drain-from-attestation.md) (found while
  implementing 8.7):** `apps/core/src/chat.rs::open_bytes`'s `envelope.sender_pub != from` check
  (`ChatError::SenderMismatch`) must not reject a mailbox-drained `Deliver` — 8.7 emits a fixed
  `[0u8; 32]` placeholder for `from` on that path (never a real, persisted sender identity — see the
  ADR for why), so the check as written would reject every mailbox-drained message unconditionally.
  Relax/restructure the check for `mailbox_id.is_some()`: the real sender is `envelope.sender_pub`
  alone (already recoverable from `blob` without the server's help), authenticated the same way it
  always was — the ratchet AEAD succeeding at all — never a routing-layer `from` the server cannot
  honestly assert for a message it isn't relaying live. This is a blocking prerequisite for
  Deliverable 3 below, not an optional extra: `eid` dedup is checked strictly *after* the sender
  check in `open_bytes` today, so the redelivery-dedup test cannot even be reached without this fix.
- **Out:** no change to `eid` dedup's own mechanism (6.4/7.4 own that); no server-side change (8.7
  owns it, including the `[0u8;32]` placeholder constant in `apps/proto`); no change to the
  `SenderMismatch` check's behavior for a **live** or **federated-live** `Deliver`
  (`mailbox_id: None`) — the check keeps exactly its current meaning there; TUI-surface wiring only
  if a user-visible affordance is needed — confirm against Definition of Done gate 9 whether
  "mailbox delivered N messages while you were away" needs a TUI surface or is purely
  transport-layer and invisible to the user (likely the latter, since delivery is just "messages
  arrived," already covered by the existing chat screen — record the "no surface needed" reasoning
  explicitly per gate 9's own requirement if so).

## Deliverables
1. `MailboxAck` send path in `apps/signaling/src/client.rs`, ack-after-processing.
2. Confirmation (or fix) that `eid` dedup survives a reconnect-triggered redelivery batch.
3. `open_bytes`'s `SenderMismatch` check restructured per ADR 0024 so a mailbox-drained `Deliver`
   (`mailbox_id.is_some()`) is authenticated via `envelope.sender_pub` alone, never compared against
   the `[0u8;32]` placeholder `from` 8.7 sends. A live/federated-live `Deliver` (`mailbox_id: None`)
   keeps today's exact `envelope.sender_pub != from` check, unchanged.
4. Tests: a simulated redelivery of an already-seen `eid` is dropped, not double-processed; an ack
   is sent exactly once per batch of mailbox-tagged `Deliver`s, after (not before) they're handed to
   the caller; a crash/disconnect between receipt and ack leaves the row unacked (provable via the
   server-side test from 8.7 — reconnect redrains it); a mailbox-drained `Deliver` with the
   `[0u8;32]` placeholder `from` decrypts successfully (proving the restructured check actually
   accepts the case it must); a live `Deliver` with a genuinely forged `from` still hits
   `SenderMismatch` (proving the restructured check didn't accidentally weaken the live-path
   defense-in-depth it must keep).

## Risks / notes
Ack-after-processing vs ack-on-receipt is the one real design choice left in this task — get it
wrong (ack-on-receipt) and a client crash between ack and durable local persistence silently loses
a message, which is exactly the failure mode T07's mailbox exists to avoid. If gate-9 TUI-surface
applicability is genuinely "none needed," say so explicitly in this task's Outcome rather than
silently skipping it.

**ADR 0024's restructured `SenderMismatch` check is the single most security-relevant line in this
task** — get the `mailbox_id.is_some()` gate wrong (too broad) and a live/federated-live `Deliver`'s
forged-`from` defense-in-depth silently stops firing; get it wrong the other way (too narrow, or
missing) and every mailbox-drained message is permanently unreadable. Both directions need their own
explicit test (Deliverable 4's last two cases), not just the happy path.
