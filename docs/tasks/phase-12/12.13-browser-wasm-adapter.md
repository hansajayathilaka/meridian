# 12.13 — Browser wasm adapter

**Phase:** 12 — Browser & Desktop Clients · **Feature:** T11 · **Depends on:** 12.2, 12.11, 12.12 · **Status:** done

**User surface:** none directly — the seam the browser app shell (12.14) and screens (12.7–12.9) run
against; this is the task that finally makes the browser client real. No TUI surface applies.

## Goal
Implement `MeridianClientAdapter` (task 12.2's interface) over `meridian-wasm`'s TS bindings (12.10),
`BrowserTransport` (12.11), and `WebCryptoSecretStore` + the IndexedDB store (12.5 + 12.12) — replacing
the `apps/wasm` smoke-test stand-ins with the real production pieces.

## Scope
- **In:** `apps/web/src/lib/adapter.ts` implementing every `MeridianClientAdapter` method by calling
  into the real `meridian-wasm` bindings with the real `BrowserTransport`/`WebCryptoSecretStore`/
  IndexedDB store wired in.
- **Out:** any change to the interface itself (12.2 owns that); any change to `BrowserTransport`/the
  store (12.11/12.5/12.12 — if this task finds either insufficient, that routes back as a finding, not a
  workaround here); the app shell/screens (12.14, 12.7–12.9).

## Deliverables
1. `apps/web/src/lib/adapter.ts` — the concrete adapter.
2. An integration test against a real headless-browser IndexedDB/WebCrypto environment (not a Node
   polyfill — this is the first task where the store's real browser-platform behavior actually matters
   end to end) covering: account creation persists and survives a simulated reload, a chat round-trip
   over `BrowserTransport` between two adapter instances.

**Known blocking gap, found by task 12.5's own review, not yet resolved — read before starting this
task.** `SecretStore` is a fully synchronous trait, but every `crypto.subtle` (WebCrypto) operation is
Promise-based, and there is no safe way to block a single-threaded `wasm32-unknown-unknown` call on an
in-flight Promise without either a `SharedArrayBuffer`/`Atomics.wait` worker bridge (needs its own
worker plus `COOP`/`COEP` cross-origin-isolation headers) or Binaryen `--asyncify` — neither in scope
for 12.5. `WebCryptoSecretStore`'s `impl SecretStore` trait methods therefore deliberately return
`StoreError::Backend` rather than hang or fabricate a result; the real logic lives in inherent
`async fn store/use_key/derive_key/nonextractable` methods with the same names, callable directly but
NOT through `&dyn SecretStore`/generic `<S: SecretStore>` dispatch. This means
`meridian_identity::generate_account`/`sign` (the actual dyn-dispatch call sites production code uses,
in `apps/identity/src/keys.rs`) **will always fail** if called with a `WebCryptoSecretStore` — this
task cannot simply reuse those shared helpers as-is. Before implementing `apps/web/src/lib/adapter.ts`,
get a real architect decision on the resolution path (an async `SecretStore` companion trait for
wasm32 — mirroring `Transport`'s own already-async design in core-api-contracts.md — vs. an accepted
worker+Atomics bridge vs. formally accepting an adapter-level reimplementation of
`generate_account`/`sign`'s seed-generation/hint-validation/label logic against the async inherent
methods directly) via an ADR 0026 amendment, run as this task's own required first step — mirroring the
precedent tasks 7.5/11.8 set for a required architect pre-check landing inside the task itself rather
than a separate `/plan-phase` round. Full finding: [12.5's Outcome](./12.5-webcrypto-secret-store.md#outcome).

## Outcome
Resolved the required first-step architect pre-check via [ADR 0028](../../adr/0028-async-secretstore-bridge.md):
a new `AsyncSecretStore` trait plus `generate_account_async`/`sign_async` (sharing a single
`prepare_account` helper with the sync versions — no duplicated orchestration logic). Implemented
`apps/web/src/lib/adapter.ts` (`WasmMeridianClientAdapter`): real `generateAccount`/`currentAccount`/
`closeAccount` via genuine `crypto.subtle` through `meridian-wasm`'s now-async bindings, plus a new
`WasmTransport` — a thin, unmodified 1:1 marshaling wrapper around `BrowserTransport` (task 12.11's file
itself untouched) proving the real WebRTC substrate works end to end (two peers negotiate and exchange
bytes over a real `RTCDataChannel`, confirmed by the review's own independent 6/6 real-browser test run).

**Two structural gaps found and correctly reported rather than worked around**, per this task's own
Scope→Out instruction ("if this task finds either insufficient, that routes back as a finding, not a
workaround here"): `meridian-wasm` (task 12.10) exports identity operations only — zero `ChatState`/
`TrustStore`/session wasm-bindgen surface exists anywhere in the crate — so `sendChat`/`openConversation`/
all trust/contact/stream `MeridianClientAdapter` methods (~30 of them) fail closed with a documented
`MeridianAdapterError("unavailable", …)`; and account persistence across a page reload is structurally
blocked today, since `WebCryptoSecretStore` imports the seed as a non-extractable `CryptoKey` with no
accessor (correct by ADR 0026 design) and `IndexedDbStore`'s sealed records are JSON-only, unable to carry
a `CryptoKey` object. This means the task's own Deliverable 2 ("a chat round-trip... between two adapter
instances") is met only at the transport substrate layer, not at the `MeridianClientAdapter.sendChat`
layer — confirmed honestly tested, not fabricated: the review independently read every one of the 6
integration test bodies and confirmed the reload-persistence test asserts the honest failure
(`openAccount` correctly rejects) and the chat-round-trip test exercises `WasmTransport` directly, with a
sibling assertion in the same describe block proving `sendChat` itself still fails closed.

The combined review (code-reviewer + security-reviewer) returned **PASS** on both lenses. This gap is not
scope creep or an incomplete 12.13 — it is a pre-existing hole from task 12.10's own deliberate, previously-
reviewed scoping (identity only, session/store deliberately deferred to 12.11/12.12, which never claimed
session/chat exposure either), surfaced for the first time here since 12.13 is the first task that actually
needs it. Recommendation followed exactly: close 12.13 now (mirroring Phase 11 task 11.8's narrow-and-defer
precedent) rather than treating it as "too large for one PR," since everything in 12.13's own declared Scope
is genuinely complete, real, and tested. **A new build task is needed before real browser messaging exists**
— a `WasmSession`/`WasmChatState`-shaped `meridian-wasm` addition (composing `ChatState` + `BrowserTransport`
+ `WebCryptoSecretStore`) plus a `#[wasm_bindgen]` surface over `IndexedDbStore`, and likely a follow-up ADR
for the CryptoKey-reload-persistence question — not scoped here; pick up via a future `/plan-phase`. Task
12.14 (web app shell) has been amended to reflect this dependency honestly rather than silently assuming a
working chat substrate — see [12.14's Risks/notes](./12.14-web-app-shell.md#risks--notes).

A real, independently-verified bug was also found in `apps/wasm/src/transport.rs` (task 12.11's file, not
touched by this diff — out of scope to fix here): `local_description()` can return SDP not yet committed via
`setLocalDescription()`, with commit deferred to `local_candidates()`; a caller that sends the offer and
applies a real answer before ever calling `local_candidates()` gets the answer silently misclassified as a
fresh offer. Confirmed the real native production path (`apps/core/src/session.rs::dial_with_config`)
already avoids this by its own call order. Recorded as a tracker carry-forward (not left only in a test-file
comment) per the review's explicit recommendation, mirroring 12.11's own stream-id-modulus precedent.

Two hygiene items closed in the same pass: leftover `__screenshots__` PNG artifacts from an earlier failing
test run (harmless, untracked, but flagged since a future `git add -A` could sweep them in) are excluded via
a new `apps/web/.gitignore`; the transport.rs bug is now tracked, not just commented.
