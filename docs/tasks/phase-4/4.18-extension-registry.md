# 4.18 — Extension registry (`meridian-tui::surface`)

**Phase:** 4 — Verification & Trust + Terminal TUI Client · **Feature:** T17 — Terminal TUI Client · **Depends on:** 4.11 · **Status:** done

## Goal
Land the registry every later feature's TUI surface plugs into — the mechanism behind Definition of
Done gate 9 — so a future feature registers a renderer/command/pane without editing the TUI core.

## Scope
- **In:** three registration points per
  [tui-client.md §8](../../architecture/tui-client.md#8-extension-contract--every-feature-ships-a-tui-surface):
  (1) message renderer keyed by stream-type id, (2) palette commands + optional key bindings, (3) a pane
  or screen pushed onto the screen stack. Forward compatibility: an entry whose stream type has no
  registered renderer displays as `[unsupported: mrd.foo/1 — update your client]` rather than breaking
  the transcript.
- **Out:** any concrete renderer/command/pane beyond what T17 itself registers for `mrd.chat/1` (4.20
  registers the chat renderer against this registry, not the other way around — this task ships the
  registry and the placeholder path, not chat-specific content).

## Deliverables
1. `apps/tui/src/surface.rs`: registry types + registration API + placeholder-rendering fallback.
2. Test: an unregistered stream-type entry renders as the labeled placeholder without breaking the
   transcript or the app (an acceptance criterion of the feature spec).

## Risks / notes
- This is an architectural contract other features (T07, T09, T10, T13, T15, T16 per
  [tui-client.md §8](../../architecture/tui-client.md#8-extension-contract--every-feature-ships-a-tui-surface)'s
  table) will build against — get the registration API right the first time; a breaking change here
  later touches every feature that registered against it.

## Tests
`cargo nextest run -p meridian-tui --test surface_registry`

- **test-engineer** — required; the placeholder-fallback path is exactly the kind of thing that needs an

## Status
Done. `apps/tui/src/surface.rs` ships the architecturally load-bearing T17 extension registry
mirroring `apps/core/src/streams.rs`'s philosophy (register, never edit the core): three independent
mechanisms — `MessageRenderer` (keyed by stream-type id, falls back to the exact `[unsupported:
mrd.foo/1 — update your client]` wording for any unregistered id), `PaletteCommand`/`PaletteAction`
(an `Effect` or a pane-push factory closure), and `ExtensionPane` (reaching the screen stack via
exactly one new `Screen::Extension(Box<dyn ExtensionPane>)` variant — the only per-feature edit
`app.rs`'s core enum should ever need again). `MessageRenderer` renders task 4.15's existing
`HistoryEntry` store type directly rather than a new abstraction.

**Reviews (architect + test-engineer, required in parallel — both real, not rubber-stamped):**
- **Architect** confirmed the dependency graph and three-trait split are sound, but found two
  moderate design gaps: (1) `PaletteRegistry::find_binding`'s intended consumer — a global
  keybinding-bypass-the-palette dispatch step in `App::handle_key` — has no task that actually claims
  ownership of wiring it (4.25 only scopes the palette *screen* reading the binding table); (2)
  `MessageRenderer` binds the extension contract to the store's concrete `HistoryEntry` schema, a
  coupling that becomes a simultaneous breaking change to every registered renderer if that schema
  ever changes. Both were resolved by explicit documentation rather than redesign (no second real
  renderer exists yet to prove out an alternative shape) — a doc-comment note on each, plus a small,
  clearly-marked addendum to 4.25's own `## Scope` section naming it as the future owner of the
  dispatch wiring.
- **Test-engineer** found the original "adversarial" placeholder tests only checked
  `Line::to_string()`, never the actual ratatui rendering pipeline where control-character stripping
  really happens (`Buffer::set_stringn`) — so the forward-compat guarantee against a hostile peer's
  stream-type id (wire-influenced via `Hello.streams[].name`) carrying raw ESC/CSI/OSC bytes was
  asserted but never actually proven. Fixed with a test that renders hostile ids through a real
  `Paragraph`+`TestBackend` and inspects buffer cells directly — confirmed genuinely non-vacuous by
  reviewer cross-check against ratatui's real source. Also found and closed: no test for
  duplicate/colliding registration (now pinned as documented last-write-wins behavior), no test for
  two stacked `Screen::Extension` panes (now proven to route only to the top and reveal the correct
  one on `Esc`), and no test pinning byte-exact (non-case-normalized) stream-type-id comparison.

`cargo test -p meridian-tui` (`surface_registry.rs` grew from 12 to 17 tests during review), `cargo
test -p meridian-cli --bins`, `cargo fmt --check`, `cargo clippy --workspace --all-targets -- -D
warnings`, `bash tools/lint-tui-no-cli.sh`, and `bash tools/check-docs.sh` all clean.
