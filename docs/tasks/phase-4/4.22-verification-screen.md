# 4.22 — Verification screen

**Phase:** 4 — Verification & Trust + Terminal TUI Client · **Feature:** T17 — Terminal TUI Client · **Depends on:** 4.4, 4.5, 4.19, 4.20 · **Status:** pending

## Goal
Land the phase's central security-critical screen: 60-digit safety number + QR side by side,
mark-verified, block, and the two un-softenable key-change modals — consuming T08's real trust module
and send gate directly, never reimplementing them.

## Scope
- **In:** side-by-side safety-number + QR display (via 4.5's `meridian verify` primitives), mark-
  verified, block actions; `KeyChangeBlocked` modal (verified contact — hard stop, composer disabled,
  only Verify/Block actions, no "trust anyway"); `KeyChangeWarning` modal (pinned contact — must be
  acknowledged, Verify as primary action). Wording preserves
  [verification-ux.md](../../security/verification-ux.md)'s canonical intent verbatim in meaning — no
  screen may paraphrase it into reassurance. Both modals consume 4.4's `SendGate` directly.
- **Out:** any new trust-state logic — this screen is presentation over 4.3/4.4/4.5, not a parallel
  implementation. If this task seems to need new trust logic, that's a defect: the logic belongs in
  4.3/4.4, not here.

## Deliverables
1. `apps/tui/src/screens/verify.rs` + the two modal components.
2. Screen-snapshot tests whose checked-in text includes the canonical warning copy verbatim — these
   catch softened wording as a snapshot diff, not just a manual read.
3. Test: no dismiss-without-verify path exists from either modal (exhaustive action enumeration, not a
   sampled check).

## Risks / notes
- **This is exactly where a future "make it less annoying" change will be tempting.**
  [tui-client.md §6](../../architecture/tui-client.md#6-security--privacy-rules-binding) rule 1 and
  [verification-ux.md](../../security/verification-ux.md)'s hard prohibitions bind this screen
  specifically; the security-reviewer treats softening as blocking, not a style note.

## Tests
