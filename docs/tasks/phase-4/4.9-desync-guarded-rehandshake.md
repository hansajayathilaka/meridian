# 4.9 — Desync detection → guarded fresh-X3DH re-handshake (1.18 follow-through)

**Phase:** 4 — Verification & Trust + Terminal TUI Client · **Feature:** T08 — Verification & Contact Trust · **Depends on:** 4.3, 4.4 (hard dependency) · **Status:** done

## Goal
Implement the receiver-side desync recovery that [task 1.18](../phase-1/1.18-desync-recovery-decision.md)
deferred to Feature 08: on repeated `ChatError::Desync`, the peer that detects it fetches a fresh bundle
and re-initiates X3DH toward the same identity key, **guarded** by 4.4's key-change gate so the
re-handshake cannot be weaponized into a substituted-key oracle. This includes fixing a real bug that
would otherwise make the recovery silently not work: `open_bytes`'s stale-session short-circuit.

## Scope
- **In:**
  1. Receiver-side orchestration: on repeated `Desync`, fetch a fresh bundle and re-run
     `start_initiator_session` toward the peer's identity key, gated through 4.4's `can_send`/key-change
     path — a substituted key surfaced during this fetch is treated as an ordinary key-change event
     (block on verified, warn on pinned), never silently accepted. User-visible notice per
     [verification-ux.md](../../security/verification-ux.md).
  2. **The `open_bytes` discriminator fix.** `apps/core/src/chat.rs`'s `open_bytes` currently branches
     on `self.sessions.contains_key(&envelope.sender_pub)` to decide whether to establish a fresh
     responder session from `envelope.prekey`. When a peer holds a **stale** session with the sender
     (the normal desync case — the identity key hasn't changed, only ratchet state diverged),
     `contains_key` is `true`, so the fresh-establishment branch is skipped and the incoming, legitimate
     re-initiation is handed to the *stale* session's `decrypt`, which fails and is classified `Desync`
     again — permanently. This defeats (1) above: the counterpart never actually accepts the
     re-initiator's fresh prekey envelope. Rewrite the discriminator to key off **whether the envelope
     carries prekey material** (`envelope.prekey.is_some()`), not merely whether a session already
     exists, so a legitimate re-initiation is recognized and a fresh session is established — still
     gated by the existing v1 signature check (`verify()`, which runs before session establishment and
     covers the prekey preamble, so this does not reopen the preamble-mutation gap ADR 0016 R3/C2
     already discharged for v1) and by 4.4's key-change gate (so an attacker cannot use "I claim to be
     re-initiating" to force a silent session replacement).
  3. Update `chat.rs`'s `ChatError::Desync` doc comment, which currently states callers **must not**
     treat it as a reset/re-key trigger (task 1.18) — this task deliberately changes that invariant,
     under the guard in (1), and the comment must say so explicitly rather than going stale.
- **Out:** envelope v2 itself (deferred — see [phase README](./README.md#envelope-v2-re-deferred)). This
  task's `open_bytes` fix is **v1-scoped and non-wire-breaking**: no new AAD, no version field, still
  `mrd.env/1`, still signed. It does **not** discharge [ADR 0016 C7](../../adr/0016-envelope-deniability.md)
  — envelope v2 will still rewrite this whole function under the new AAD/commit-on-decrypt rules and
  must re-verify this behavior when it does; this task's fix and comment must say so.

## Deliverables
1. `apps/core/src/chat.rs`: rewritten `open_bytes` discriminator; updated `Desync` doc comment.
2. Receiver-side re-initiation orchestration (new function/module in `meridian-core`), gated by 4.4.
3. Tests: desync → recovery → session restored (both directions: re-initiator and counterpart); a
   substituted key presented during the recovery fetch is blocked/warned per 4.4, never silently
   accepted; the v1 signature check still rejects a mutated preamble before the new branch runs.

## Risks / notes
- **This is a hard-dependency-ordered task, not a scheduling preference.** Per 1.18's own architect
  ruling: building the automatic re-key path *before* the block/warn gate (4.4) exists hands an active
  attacker a forced-reset/prekey-depletion oracle at exactly the moment a malicious server could
  substitute a key during the bundle fetch. 4.4 must land first.
- Coordinate with [task 1.6](../phase-1/1.6-conformance-vectors.md)'s ratchet vectors if this touches
  session-establishment code paths they cover — regenerate only if actually needed, and never
  hand-edit `test-vectors/`.
- The `open_bytes` fix is deliberately narrow — resist the temptation to "just do" more of ADR 0016's
  C1–C7 here. That work is envelope v2's, tracked separately.

## Status
Done, after an unusually deep review cycle that is worth recording in full because it caught two real,
exploitable crypto bugs, not style nits.

**What shipped:** `open_bytes`'s discriminator now tries the existing session first (unchanged), and
only falls back to fresh responder establishment on `CryptoError::UndecryptableHeader` **and** a
prekey-carrying envelope — a deliberate, better-justified deviation from the literal "key off
`prekey.is_some()`" scope text, since an unconfirmed initiator re-attaches its prekey to every message
until confirmed, and a blind `prekey.is_some()` discriminator would force fresh X3DH-as-responder
(destroying skipped keys, re-consuming an OTK) on ordinary continuation traffic. `crate::desync::
attempt_recovery` (new sibling module) is the sole surface for the receiver-side re-initiation
orchestration: gated by a per-peer repeated-Desync counter (`DESYNC_RECOVERY_THRESHOLD = 5`,
`TODO: confirm`, reset on any healthy decrypt or on any *attempted* recovery regardless of outcome) and
by 4.4's `can_send` gate before touching anything; a substituted key surfaced mid-recovery routes through
`TrustStore::observe_key_change`, never silently accepted. `ChatState::replace_session_as_initiator` is
the one explicit, separately-named surface for the forced session replacement (build-then-swap:
`Session::initiate` must succeed before the stale session is removed).

**Round 1 (architect + security-reviewer + test-engineer, all required):** test-engineer required two
fixes (an N-replay-oracle-bound test; a design decision on `replace_session_as_initiator`'s removal
ordering). Architect and security-reviewer **independently found the same blocking bug**: the
`open_bytes` fallback checked only signature authenticity, never freshness — a malicious relay could
replay a peer's own original, genuinely-signed OTK-free opening envelope after the real session had
advanced, silently rolling the session back to its initial state (a forced PCS-rollback oracle,
directly contradicting threat-model goal 6, reintroducing the exact class task 1.18's guard stack
existed to prevent). Fixed with a per-peer `ek_pub` freshness record.

**Round 2 (same three lenses, re-review):** while sanity-checking the round-1 fix before spending more
review budget, the orchestrator found the freshness record was a **single scalar**, overwritten on each
new establishment, despite its own doc comment claiming stale entries were "never cleared." Architect
and security-reviewer both independently confirmed this was a second, real instance of the *same* bug
class — reachable within one ordinary long-running `meridian chat` session (which publishes its bundle
once, at startup, never mid-session) via exactly one attacker-forceable intervening re-establishment (an
attacker can trigger the *other* party's own recovery machinery to manufacture that second
establishment). Fixed by turning the freshness record into a history (`Vec<ResponderEk>`, tagging each
entry with the SPK generation it referenced) pruned in lockstep with `PrekeyVault`'s own existing
generation-expiry machinery — closing the gap precisely at the boundary the vault itself already
enforces, not via an arbitrary count cap.

**Round 3 (re-confirmation, all three lenses):** test-engineer confirmed both round-1 items now closed.
The combined architect+security pass confirmed the replay/rollback fix now holds precisely, but found a
new, distinct, lower-severity issue: the history record had no cap on distinct peer keys, so free-to-mint
OTK-free attacker identities could grow it unboundedly (an at-rest storage/availability concern, not a
re-opening of the rollback bug). Fixed by mirroring `MAX_PENDING_REQUESTS`/`evict_oldest_pending`'s
existing, already-accepted pattern exactly: `MAX_RESPONDER_SESSION_EK_PEERS = 256` with oldest-first
eviction, plus cleanup on `reject_request`/`evict_oldest_pending` (safe because the `Session` those
already remove is what the freshness record exists to protect — no session, no live freshness check to
protect).

**Round 4 (final, single-lens confirmation):** security-reviewer confirmed the growth-bounding fix is
correct, doesn't touch the already-confirmed-closed freshness-check logic, and both new tests
(oldest-first eviction, reject/evict cleanup) are genuinely rigorous. Clear to close.

`docs/api/messaging-envelope-v1.md` §3 and `ChatError::Desync`'s doc comment were updated at each round
to state precisely, without overclaiming, what is and isn't protected. `apps/core/tests/desync_recovery.rs`
grew to 15 integration tests plus 4 crate-internal unit tests in `chat.rs`, covering: both-directions
end-to-end recovery, exact threshold-boundary precision, the N-attempts-per-threshold oracle bound
(`Recovered` and `Gated` variants), single- and multi-generation replay rejection, expired-generation
replay still failing safely post-pruning, persistence round-trip of the freshness history, forced-
replacement failure-ordering, unknown-identity-surfaced non-auto-completion, and growth-cap
oldest-first eviction with reject/evict cleanup. `cargo test -p meridian-core` (full) and
`cargo test -p meridian-cli --bins` plus the `chat_demo`/`request_finalization`/`two_orgs_walkthrough`
integration suites all pass; `cargo fmt --check`, `cargo clippy --workspace --all-targets -- -D
warnings`, and `bash tools/check-docs.sh` all clean throughout.
