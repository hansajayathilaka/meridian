# 1.31 — prekey-bundle republish/fetch race on reconnect

**Phase:** 1 — Review of Phase 0 · **Feature:** on-the-fly (found during 1.27's live-rig verification) ·
**Depends on:** none · **Status:** **done** (see [Status](#status))

## Goal
Fix a real, reproducible race between `session_connect.rs`'s bundle republish and the peer's bundle
fetch, so two peers who both reconnect around the same time (network blip recovery, app relaunch, an
automatic reconnect timer on both ends) don't hit a hard, loud connect failure.

## Background
Found while personally re-verifying [1.27](./1.27-pcap-assertions-ci.md) against the live netns/coturn
rig: `apps/cli/src/session_connect.rs`'s `run_webrtc` republishes a fresh SPK/OTK bundle to the
rendezvous at the start of *every* `session connect` invocation (both roles), but nothing synchronizes
the peer's `fetch_with_retry` against that publish actually landing. `apps/core/src/chat.rs`'s
`PrekeyVault::set_bundle` is a single-slot overwrite (no retained prior generation), so if an
initiator's fetch lands on a bundle that was current a moment ago but has just been superseded by the
responder's in-flight republish, the initiator's X3DH init references OTK ids the responder's
freshly-regenerated vault no longer has secrets for — `error: answer: crypto/envelope error: no
matching prekey secret for incoming session`, a hard failure, not a retry.

This reproduced on ~4 of 5 full `tools/netns-nat-matrix.sh matrix` runs before 1.27 worked around it
(always cell 2 onward within one run, never cell 1 — consistent with "no prior bundle exists yet to
race against" on a brand-new identity's first-ever publish). 1.27's fix was rig-only (per-cell identity
homes, so no cell within a `matrix()` run ever has a prior bundle to race against) and does not touch
this crate — it narrows the race's reachability inside that one test harness but does not close the
underlying race in `session_connect.rs` itself, which remains reachable in real (non-test) usage.
connectivity-debugger's 1.27 review independently confirmed the mechanics and recommended tracking this
separately: "a genuine availability bug reachable in production... any time two peers with an existing
published bundle both trigger a reconnect around the same time... Impact is a hard, loud connect
failure... not a confidentiality/integrity regression, no downgrade, no auth bypass — so it's a
reliability/UX bug, not a security bug per se, but real and user-facing."

## Scope
- **In:** close the publish/fetch race for reconnects. Candidate approach (per connectivity-debugger,
  matching standard X3DH/Signal-protocol prekey rotation practice): retain the previous SPK/OTK
  generation in `PrekeyVault` for a bounded grace window after a republish, rather than single-slot
  overwrite, so a fetch that lands on the "just-superseded" bundle can still complete. Any approach must
  preserve forward secrecy (bounded generations, eventual expiry — not indefinite retention).
- **Out:** the 1.27 rig-only mitigation (already landed, stays as-is); anything to do with the wire-level
  pcap assertions or NAT-matrix rig itself.

## Risks / notes
Touches prekey/vault handling (`apps/core/src/chat.rs`), which is trust-critical crypto-adjacent state —
route through **rust-dev** with **security-reviewer** sign-off specifically on the retention-window
approach and its forward-secrecy implications before merge.

## Tests
A regression test reproducing the race deterministically (two concurrent `session_connect`-style flows
against the same identity pair, timed so the fetch lands mid-republish) — the netns rig reproduces it
empirically but is too slow/flaky for a unit-test-speed regression check.

## Reviews
**security-reviewer** (retention-window / forward-secrecy), **connectivity-debugger** (confirms the fix
against a live reconnect scenario).

## Status
**Done.** The race is closed by bounded prekey-generation retention in `PrekeyVault`.

### What landed
- **`apps/core/src/chat.rs`** — `PrekeyVault` now retains **exactly one** superseded generation
  (`PrevGeneration`: spk pair + remaining OTKs + an absolute `expires_at_unix`) instead of
  single-slot-overwriting on republish:
  - `set_bundle(.., now_unix)` rotates current → previous and *replaces* (so drops + zeroizes) any
    generation already sitting in the previous slot — retention can never grow into a chain.
  - `expire_previous_generation(now_unix)` drops + zeroizes the previous generation once
    `PREV_GENERATION_GRACE_SECS` (60 s) has passed.
  - `spk_secret_for` checks the current generation first, then the retained previous one, still on an
    **exact** `used_spk` match (never substituting a different SPK).
  - `take_otk_secret` removes the OTK from **both** generations, so a one-time prekey is consumed
    exactly once across generations.
  - `Otk` and `PrevGeneration` zeroize their secrets on drop (matching the 1.5 zeroization pass);
    `zeroize` added to `apps/core/Cargo.toml`.
  - New fields are `#[serde(default)]`, so a state sealed before this task still opens.
- **Time is caller-supplied, not read in core.** `meridian-core` compiles to wasm32, where
  `SystemTime::now()` is unavailable, so `set_bundle`/`expire_previous_generation` take `now_unix`.
  `apps/cli/src/main.rs` gains `now_unix()`; all four CLI call sites
  (`chat.rs`, `session_connect.rs`, `session.rs`, `opacity.rs`) pass a real clock. Expiry is stored
  absolute so it survives the at-rest seal/open round-trip.
- **Enforcement hook:** `apps/cli/src/chat.rs::handle_inbound` calls
  `expire_previous_generation(now_unix())` *before* opening a delivered blob, so the grace window is
  time-bounded inside a long-running process rather than lasting until the next republish.

### Chosen window: 60 s
Fetch → X3DH → route → deliver is single-digit seconds even over a relayed path with retries, so 60 s
covers the race with margin while staying far below any real prekey-rotation period.

### Tests (`apps/core/tests/chat_manager.rs`, `cargo test -p meridian-core --test chat_manager`)
`7 passed; 0 failed` — 3 pre-existing + 4 new:
1. `envelope_against_just_superseded_generation_still_opens` — the regression itself.
2. `superseded_generation_is_rejected_once_the_grace_window_passes` — fails **closed** past the window
   (uses the at-rest seal to snapshot the vault so both branches start from an identical state).
3. `only_one_prior_generation_is_retained` — gen N is gone after two republishes.
4. `one_time_prekey_is_single_use_across_generations` — the same OTK cannot open two sessions.

**The regression tests were verified to actually reproduce the bug**, not merely to pass: with the
previous-generation lookup in `spk_secret_for` temporarily short-circuited (simulating the pre-1.31
single-slot vault), tests 1, 2 and 4 **FAIL** (`4 passed; 3 failed`) and pass again once restored.
Test 3 passes either way by construction — it pins the retention *bound*, it is not a regression test.

### Verified
`cargo build --workspace`, `cargo build -p meridian-cli --features webrtc`,
`cargo clippy --workspace --all-targets -- -D warnings`, `cargo fmt --all`, and
`cargo test --workspace` (44 suites, `0 FAILED`) all green.

### Known residual (deliberate, not papered over)
The 60-second bound is enforced **at the points where a clock is available** — every `set_bundle`
(which also discards any generation loaded from a sealed state, so a restart never carries an aged
generation forward) and the CLI's inbound path. The bound that holds *unconditionally*, with no
caller cooperation, is the **one-generation cap**. A hypothetical embedder that loads a sealed state,
never republishes, and answers an inbound prekey handshake without calling
`expire_previous_generation` could therefore accept a previous generation older than 60 s — bounded to
one generation, but not to the window. Enforcing the window inside the lookup instead would mean
threading `now_unix` through `open_bytes`/`open_inbound` and hence through `apps/core/src/session.rs`
and its whole async API, into a crate that is deliberately clock-free for wasm. Flagged for
security-reviewer's ruling rather than silently accepted.
