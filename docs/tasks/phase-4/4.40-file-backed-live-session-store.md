# 4.40 — Thread the live-session secret store through file-backed contacts/trust/send handlers

**Phase:** 4 — Verification & Trust + Terminal TUI Client · **Feature:** T17 — Terminal TUI Client (gap closure, fix for 4.38's Defect B) · **Depends on:** 4.29, 4.31, 4.32, 4.33, 4.35, 4.37 · **Status:** pending

## Goal
Stop `apps/tui/src/worker.rs::open_account_store`'s `StoreKind::File` branch from unconditionally failing
closed, by giving the worker task a session-scoped, already-unwrapped store cache that the twelve affected
handlers consult instead of re-deriving from disk per dispatch — closing the gap task 4.37's own review
already flagged and task 4.38 reproduced live (a file-backed account reaches a genuine, connected
`Screen::Main` and then fails on its very first contacts/trust/send action).

## Scope
- **In (design-decision gate, before any code):** an **architect + security-reviewer consult, recorded in
  this task's own Status section before implementation lands.** The question: extend `OnboardingSession`
  (or a renamed/widened sibling struct — already threaded by `&mut` through every `dispatch` call for the
  worker task's whole lifetime, per `run_worker`) to cache `(Box<dyn SecretStore>, KeyHandle)` for the
  file-backed path, populated once on a successful `handle_unlock`, consulted by `open_account_store`'s
  (or its renamed successor's) `StoreKind::File` branch instead of failing closed. The consult must
  explicitly weigh: this extends decrypted key material's in-memory residency from `OnboardingSession`'s
  current narrow register→publish window to the *whole session*, until process exit (no logout/lock
  mechanism exists anywhere in this crate today — confirmed during planning). Check this doesn't
  contradict `docs/security/threat-model.md` or `docs/security/anonymity-and-retention.md`'s "must never"
  list (planning found no existing text that does, but that absence is not itself permission — the
  consult must confirm it, not assume it). **If the consult concludes a new ADR is warranted, stop and
  route through `/adr` before continuing — do not implement first and consult after.**
- **In (implementation, once the consult clears):** refactor `open_account_store` and the twelve named
  call sites (`run_add_contact`, `run_set_petname`, `run_set_user_blocked`, `run_set_policy_override`,
  `run_delete_contact` — from 4.31; `run_accept_request`, `run_reject_request`, `run_mark_verified`,
  `run_acknowledge_key_change` — from 4.32; `run_send_message`, `run_persist_history` — from 4.33/4.35) to
  consult the cache. OS-keystore behavior stays byte-for-byte unchanged (already harmless to re-derive;
  populating the cache there too is optional, for symmetry only, not required). Update
  `open_account_store`'s own doc comment (which currently names this exact gap) to describe the fixed
  state.
- **Out:** task 4.39's defect (prekey bundle republish); `run_inbound_loop`'s own independent
  re-derivation (4.35's pattern — already a one-time-per-session derivation, already correct, not this
  task's concern); any logout/lock feature (a new capability, not this fix); editing 4.37's closed Status
  section (historical record, stays as-is — this task's own Status section is where the resolution gets
  recorded).

5. `open_account_store`'s doc comment updated; `docs/tasks/phase-4/README.md`'s T17 exit-criteria bullet

## Risks / notes
- This is the load-bearing design decision in the whole 4.39–4.41 set — do not skip the consult or treat
  it as a formality. Extending in-memory key-material residency to the full session lifetime is a real
  security posture change, even if it's a defensible one (the OS-keystore path already does this
  implicitly, since a keystore-backed key can always be re-fetched without a secret; this task is closing
  the asymmetry, not introducing a wholly new exposure class) — the consult's job is to confirm that
  framing holds, not to rubber-stamp it.
- 12 call sites is a wide diff for one task; if the consult or implementation reveals the refactor doesn't
  cleanly generalize across all twelve (e.g. one handler has a materially different failure-mode
  requirement), split rather than force a one-size-fits-all cache API — note the split explicitly rather
  than silently narrowing scope.
- Mechanical overlap with 4.39: both touch `apps/tui/src/worker.rs`'s session-threading machinery
  (`OnboardingSession` or its successor). No logical dependency, but land after 4.39 merges and rebase
  onto it, to avoid a painful simultaneous diff on the same struct.

## Status
**Pre-code design consult: GO WITH MODIFICATIONS (no new ADR).** Both `architect` and `security-reviewer`
ran independently, converged on the same verdict, and both corrected the task file's own risk-note framing
before clearing it.

**Verdict rationale (both lenses agree):** the residency extension is real (`OnboardingSession` is `&mut`-
threaded through every `dispatch` call for the worker task's whole process lifetime, per `run_worker`; no
logout/lock mechanism exists anywhere in `apps/tui`) but is **not novel** — task 4.35's `inbound_handoff`/
`run_inbound_loop` (`worker.rs` ~L1562-1728) already builds a live, passphrase-holding `FileSecretStore`
for a file-backed account and keeps it resident for the rest of the process's life, unconditionally, for
every file-backed account that reaches `Screen::Main` today. 4.40 adds a second, narrower, better-scoped
occurrence of an already-shipped, already-accepted pattern — not a new exposure class. Neither
`threat-model.md` nor `anonymity-and-retention.md`'s "must never" lists are contradicted (both read in
full by both reviewers independently); the relevant residual is threat-model's already-accepted A6
("live-endpoint/rooted-device compromise... we do not claim to defeat a live implant"). The task's own
"closes an asymmetry with the OS-keystore path" framing is directionally right but imprecise — OS-keystore
re-fetchability is backstopped by the OS's own ACL/session-unlock state with near-zero material resident in
this process between calls, while the file-backed cache's re-fetchability is backstopped by this process's
own heap holding the passphrase continuously. The 4.35 precedent, not the OS-keystore analogy, is the
correct and sufficient justification recorded here.

**Required modifications, binding on the implementation:**
1. Add a **distinct** cache field on `OnboardingSession` (e.g. `live_store: Option<(Box<dyn SecretStore>,
   KeyHandle)>`) — do not repurpose or fold into the existing `pending`/`PendingConnection` machinery,
   which has different, retry-driven invalidation rules.
2. **Single-writer discipline**: only `handle_unlock`'s success path populates the cache; all twelve
   handlers only read it.
3. Cache is **`StoreKind::File`-only** — OS-keystore path stays byte-for-byte unchanged (already cheap to
   re-derive; no cache needed there).
4. The accessor returns **borrowed** `(&dyn SecretStore, &KeyHandle)`, not an owned move — the twelve
   handler functions currently take no `session` parameter at all (`open_account_store()` is a
   zero-argument free function today), so their signatures must be widened to receive the session/cache
   reference. This is the wide part of the diff the task's own risk note already anticipated; confirmed
   real by the architect's line-by-line read of all twelve call sites.
5. Name the resulting duplication explicitly in code comments (not silently): after this lands, a live
   file-backed session holds *two* independent `FileSecretStore` instances — one in this new cache
   (populated at `handle_unlock`), one already inside `run_inbound_loop`'s `InboundHandoff` (populated at
   `inbound_handoff`) — each an independent copy of the same passphrase from the same `UnlockRequest`. Not
   a new exposure class (same process, same trust boundary), but a future reader should not think there is
   only one copy. Unifying them (e.g. one shared `Arc<dyn SecretStore>`) is a larger refactor than this
   task's scope — leave as `TODO: confirm`, do not implement here.
6. Keep Deliverable 4's redaction test — `SecretStore` has no `Debug` supertrait so `Box<dyn SecretStore>`
   already can't be `{:?}`-formatted (a compile-time guarantee, not discipline), but the test should assert
   the **host struct** (`OnboardingSession`) itself has no `Debug` impl reaching the store field, mirroring
   `apps/tui/tests/run_worker_account.rs`'s `effect_debug_never_leaks_a_passphrase` and
   `apps/tui/src/session.rs`'s `LiveSession` redaction test.
7. Deliverable 4's "a second, later dispatch reuses the cache" test must be a real negative assertion (an
   instrumented/call-counting `SecretStore` test double proving **no second scrypt/age-decrypt** happens),
   not just "the operation succeeded twice."
8. `open_account_store`'s updated doc comment must cite the `inbound_handoff`/`run_inbound_loop` precedent
   as the security rationale, so a future reader doesn't have to re-derive this consult from scratch.
9. Non-blocking follow-up, not required for this task: `docs/security/threat-mitigation-matrix.md`'s A6
   row could reference 4.40's redaction/reuse tests once landed — left as a future doc-sync nit.

No new ADR required by either reviewer. Implementation may proceed under the modifications above.

---

**Implementation record (post-consult).** All nine required modifications above were followed as
written; no deviation was needed and none of the twelve call sites required splitting off a different
cache shape.

**Cache field/accessor shape landed:**
- `OnboardingSession` gained a new, distinct field — `live_store: Option<(Box<dyn SecretStore>,
  KeyHandle)>` — exactly the shape the consult named, never folded into `pending`/`PendingConnection`
  (modification 1). A hand-rolled `Debug` impl was added for `OnboardingSession` itself (it had none
  before), mirroring `crate::session::LiveSession`'s own pattern, so both `pending` and `live_store`
  show only a fixed redaction marker, never their real contents (modification 6).
- `OnboardingSession::set_live_store(&mut self, store, handle)` is the single writer — called only from
  `handle_unlock`'s `Ok` arm (modification 2). `OnboardingSession::live_store(&self) -> Option<(&dyn
  SecretStore, &KeyHandle)>` is the read-only accessor every handler goes through indirectly via
  `open_account_store`.
- `open_account_store` was widened to take `session: &OnboardingSession` and now returns a small
  `AccountStore<'a>` enum (`Owned(Box<dyn SecretStore>, KeyHandle)` for the `StoreKind::Os` branch,
  which still constructs fresh every call and is untouched behaviorally, per modification 3; or
  `Cached(&'a dyn SecretStore, &'a KeyHandle)` borrowed straight out of `session.live_store()` for
  `StoreKind::File`) with a `.parts()` method handing back the borrowed `(&dyn SecretStore, &KeyHandle)`
  pair every call site actually wants (modification 4). The enum indirection is required by ownership:
  the `Os` branch's `OsSecretStore` is built fresh inside the function and has nothing outside it to
  borrow from, so a bare borrowed return type cannot cover both branches — the enum keeps the owned
  case alive alongside the borrowed one behind one shared accessor.
- `run_unlock`'s return type widened from `Result<LiveSession, String>` to `Result<(LiveSession,
  Box<dyn SecretStore>, KeyHandle), String>` so `handle_unlock` can cache the exact store/handle it just
  built and verified, with zero redundant unwrap. `handle_unlock` now takes `session: &mut
  OnboardingSession` and calls `session.set_live_store(..)` on success — the only such call site in the
  module.
- The two-copies duplication (this cache vs. `run_inbound_loop`'s own `InboundHandoff`, built by
  `inbound_handoff`) is named explicitly in `OnboardingSession::live_store`'s own field doc comment,
  with a `TODO: confirm` on unifying them, per modification 5 — not implemented here, out of scope.
- `open_account_store`'s doc comment cites the `inbound_handoff`/`run_inbound_loop` (task 4.35)
  precedent as the security rationale, per modification 8.

**Threading into the twelve call sites (modification 4's "wide diff" prediction — confirmed, and it did
generalize cleanly).** The task file's own risk note flagged that the refactor might not generalize
uniformly across all twelve handlers; in practice it did, with no split needed. `dispatch(effect,
session: &mut OnboardingSession)` already existed and already had `session` in scope for
`Register`/`PublishBundle`/`Unlock`; the fix was mechanical for the other eleven: each `handle_*`
wrapper gained a `session: &OnboardingSession` parameter (a `&mut OnboardingSession` argument coerces
to `&OnboardingSession` at the call site inside `dispatch` — a standard Rust coercion, no explicit
reborrow syntax needed), threaded straight through to its `run_*` counterpart, which calls
`open_account_store(session)` in place of the old zero-argument `open_account_store()` and then uses the
borrowed `(store, handle)` from `.parts()` everywhere the old code used `store.as_ref()`/`&handle`.
`run_send_message`/`run_accept_request`/`run_reject_request` (already `async` for unrelated reasons —
`chat_state_lock`/network calls) needed no different treatment; the borrow lives for the whole function
body in every case, including across `.await` points, with no lifetime friction.

**One naming note, not a deviation:** the task file's own Scope/Deliverables sections say "twelve call
sites" but name exactly eleven functions (`run_add_contact`, `run_set_petname`,
`run_set_user_blocked`, `run_set_policy_override`, `run_delete_contact`, `run_accept_request`,
`run_reject_request`, `run_mark_verified`, `run_acknowledge_key_change`, `run_send_message`,
`run_persist_history`) — matching exactly the eleven pre-existing call sites of
`open_account_store()` in `worker.rs` (confirmed by grep before starting). All eleven were updated; no
twelfth call site existed to find. Read as an off-by-one in the task file's own count, not a missed
site.

`open_account_store`'s `StoreKind::File` branch, on a `None` cache, now returns "this account is
