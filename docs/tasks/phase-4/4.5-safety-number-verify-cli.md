# 4.5 — Safety-number compare UX primitives + `meridian verify`

**Phase:** 4 — Verification & Trust + Terminal TUI Client · **Feature:** T08 — Verification & Contact Trust · **Depends on:** 4.3 · **Status:** pending

## Goal
Build the compare/verify UX on top of T03's already-landed safety-number computation
(`apps/crypto/src/fingerprint.rs`), and freeze it into conformance vectors — the last piece before any
client can actually run a verification.

## Scope
- **In:** `meridian verify <mrd1-id>` CLI command: 60-digit number + QR display
  (`meridian_identity::qr::render_terminal`, already exists — no new QR primitive needed),
  `--scan-file` headless compare (`decode_luma`, already exists), calls `trust.mark_verified` on match.
  Freeze `fingerprint.rs`'s output into `test-vectors/` fixtures: order-independence
  (`safety_number(a,b) == safety_number(b,a)`), byte-identical output for fixed inputs — future
  browser/mobile clients must match byte-for-byte.
- **Out:** the TUI's Verify screen (4.22, consumes this); trust-state transitions beyond `mark_verified`
  (4.3/4.4 own those).

## Deliverables
1. `apps/cli/src/verify.rs` (or equivalent): `meridian verify` command + `--scan-file`.
2. `test-vectors/`: new safety-number fixture, generated via `cargo run -p xtask -- vectors` (never
   hand-edited).
3. Tests: order-independence, vector byte-identity, CLI round-trip (generate → scan → verified).

## Risks / notes
- No new crypto here — `fingerprint.rs` computation is frozen, not changed. If this task seems to need
  a new primitive, that's a planning defect per root CLAUDE.md — stop and raise it.

## Tests
`cargo nextest run -p meridian-cli --test verify` · `cargo test -p meridian-crypto --test conformance`
