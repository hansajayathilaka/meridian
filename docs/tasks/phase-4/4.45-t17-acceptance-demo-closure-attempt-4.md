## Risks / notes
- **Hard join on 4.42, 4.43 and 4.44** — no partial-credit path: 4.42's defect blocks demo step 4, 4.44's
  blocks step 6, and 4.43's makes every file-backed run take minutes per peer.
- **Reuse 4.41's hard-won methodology instead of re-deriving it** (full detail in that task's Status
  section):
  - **OS keystore works in this sandbox** with `apt-get update` first, then `gnome-keyring` + `dbus-x11`,
    then `gnome-keyring-daemon --components=secrets --unlock` (**not** `--start --unlock` together — the
    daemon rejects that combination) under a `dbus-launch`-started session bus with `$HOME` pointed at a
    private, empty scratch directory. 4.38's earlier "impossible here" finding was real but narrower than
    it looked. Re-verify rather than assume, and say which you observed.
  - **The initiator-role trap:** `worker::run_send_message` picks the X3DH initiator by
    `account_pub.as_slice() <= peer_pubkey.as_slice()` — a **raw-byte** comparison.
    `meridian-identity`'s base32 alphabet (`abcdefghijklmnopqrstuvwxyz234567`) makes digits sort *after*
    letters by value but *before* them in ASCII, so comparing the two `mrd1:` id **strings** disagrees
    with the app about half the time. Decode the key part properly and compare raw pubkeys. A driver that
    gets this wrong produces a real-looking but bogus "message not sent: … no prekey preamble" failure.
  - A screen-scraping driver should parse the terminal buffer (4.41 used `pyte`) and match narrow,
    single-line anchors — "mrd1 id:" and "or QR image path:" render on separate lines, and the Chat
    title's em-dash is one character.
  - Both peers must run **concurrently** (offline delivery is T07, not built — a message routed while the
    recipient isn't connected is simply dropped), synchronized once both reach a live `Screen::Main`.
- **Distinguish driver bugs from product defects before reporting anything.** 4.41 found and fixed two of

- Nothing from the driver needs to be checked in (4.41's precedent) — but the transcripts quoted in Status

### The defect: `Effect::AddContact` never reconciles into the live in-memory `TrustStore`

**Symptom.** An initiator adds a contact via the plain `n`-add flow (`Effect::AddContact`, not
`AcceptRequest`) and sends a first-contact message — this works (4.39/4.40 hold). Selecting that same
contact and pressing `v`→`v`→`y` to mark it verified, in the same live session, fails on-screen:
`could not mark verified: no contact recorded for this key`. Reproduces on the very first `v` press
right after the `n`-add, no chat needed.

**Root cause.** `apps/tui/src/app.rs::App::handle_worker` reconciles worker completions into the live
`MainState::trust` for `Effect::AcceptRequest`/`RejectRequest`/`LoadHistory`/`LoadSession` (each via its
own `apply_*` method — `apply_accepted_request` is 4.42's own fix, the exact precedent this defect is
missing) but has **no arm for `Effect::AddContact`**. `apps/tui/src/screens/main.rs::handle_worker`
forwards `AddContact` completions only into `ContactsState::entries` (the display-only join) via
`apps/tui/src/screens/contacts.rs::handle_worker`; `MainState::trust` — built once at session load and
never reloaded mid-session — never learns of it. Meanwhile `worker::run_add_contact` genuinely TOFU-pins
the peer into a **freshly loaded, disk-backed** `TrustStore` and saves `trust.bin` — the pin is durable,
just invisible to the live session. `Screen::Verify`'s `trust.mark_verified(&pubkey)`
(`apps/core/src/trust.rs`) therefore hits `TrustError::UnknownContact` against the never-updated live
copy, `Display`s as `"no contact recorded for this key"`, wrapped by `verify.rs` into the exact observed
string. A restart makes it succeed (`MainState::from_session` rebuilds `trust` fresh from `trust.bin` at
boot) — confirming this is a pure live-session staleness gap, not a persistence defect.

**Security-relevant consequence, real but calibrated.** `apps/core/src/trust.rs::TrustStore::can_send`
fails *open* (`SendGate::Ok`) for a pubkey it doesn't know — so a contact added via plain `AddContact`
is also invisible to the key-change/MITM warn-or-block gate for the rest of that live session. This is a
genuine invariant violation and should be closed by the same fix (an `apply_added_contact`, calling
`trust.observe` the way `apply_accepted_request` already does). Calibration from the independent review
pass: it is not yet an *actively exploitable* MITM window in the current build specifically, because
receive-side key-change/desync recovery isn't wired into the TUI's live inbound loop for **any** contact
yet (a separate, already-documented gap from task 4.35, `worker.rs:1871-1874`) — so nothing today
actually detects a mid-session key rotation to trigger the gate on. Both halves belong in 4.46: the
invariant break is real and worth fixing now; its exploitability today is bounded by a different,
already-tracked gap, not excused by it.

**Pre-existing, not introduced by this wave.** Confirmed via `git show a392ca7:apps/tui/src/app.rs` —
zero `Effect::AddContact` reconciliation arms existed before 4.42/4.43/4.44 started; this traces to task
4.19, when `AddContact` was introduced. Every prior exit-gate attempt (4.28/4.38/4.41) was blocked
*earlier* in the demo script — at the "open a chat with an accepted sender" step 4.42 just fixed — so
this is genuinely the first attempt whose live run could reach the code path at all, not a regression
this wave caused.

### Two secondary findings — named, not silently absorbed

**`meridian tui --export-json <path>` writes a directory, not a flat file.** Confirmed independently by
both agents and the `reviewer` pass: `apps/tui/src/store/export.rs::export_json` deliberately creates a
directory tree (`<dest>/contacts.json`, `<dest>/history/*.jsonl`, `<dest>/state.json`), permission-hardened
(0700/0600), mirroring the sealed on-disk layout — intentional, documented, correct. But the feature
spec's demo script (`docs/architecture/features/17-terminal-tui-client.md:107`) and this task's own step 7
both write the invocation as if `<path>` were a single flat JSON file (`jq '...' /tmp/dump.json`), which
genuinely fails (`jq: Could not open ...: Is a directory`). The corrected form
(`jq '...' <dest>/contacts.json`) returns `"bob"` correctly on both account types. Traced to task 4.15 —
pre-existing, not introduced by this wave. The directory layout is the more defensible design (mirrors
the sealed layout, permission-tested); recommend fixing the spec/demo-script wording, not the code, as
part of 4.46 or a lighter doc-only follow-up.

**Restart methodology for OS-keystore.** The first live-run agent's methodology (kill only the `meridian
tui` process, keep the surrounding `dbus-launch`/`gnome-keyring-daemon` session alive across a restart,
reasoning that a real desktop's session bus and keyring daemon are login-scoped and outlive any single
app's restart) was independently endorsed as sound by the `reviewer` pass from source (`worker.rs`'s OS
init path never spawns or owns the D-Bus session itself — confirmed, no such `Command::new` anywhere in
`apps/tui`/`apps/cli`). The second live-run agent could not independently reproduce this live in its own
run — it hit a different environment wall (no default Secret Service collection in a genuinely fresh
`$HOME`, and `gnome-keyring-daemon`'s interactive Prompt flow for creating one didn't drive headlessly in
the time spent) — and reports reasoned agreement with the conclusion rather than a live reproduction of
its own. Named explicitly as a narrowing, not silently dropped.
