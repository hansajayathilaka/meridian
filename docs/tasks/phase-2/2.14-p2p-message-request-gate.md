# 2.14 — Wire the message-request gate into the P2P session substrate

**Phase:** 2 — Cross-Org Federation · **Feature:** on-the-fly (surfaced by 2.10) · **Depends on:** 2.10 · **Status:** pending

## Goal
Task 2.10's first-contact message-request gate lives only in `ChatState::open_inbound` (the
relay/mailbox delivery path). A first-ever P2P dial's chat content bypasses it entirely: by the time
`P2pSession::pump` calls `open_inbound` for a `CHAT_LABEL` frame, the session was already installed
during the earlier SDP-offer exchange (`recv_sdp` → `chat.open_bytes` directly, never
`open_inbound`), so `is_first_contact` is provably always `false` on that path. `meridian session
connect <peer-id>` (`apps/cli/src/session_connect.rs`) is a real, shipped, network-facing command
that inherits this gap today — chat content over a fresh P2P session delivers with no gate, no
prompt, no safety-number-before-content.

This task makes a first-ever P2P session's chat content subject to the same gate as relay-delivered
first contact, closing the gap both architect and security-reviewer flagged during 2.10's review as
needing explicit tracking rather than an implicit "Feature 08 will handle it."

## Background
Surfaced during task 2.10's review (all three required reviewers — architect, security-reviewer,
test-engineer — independently traced and confirmed this). Architect: "not a defect in task 2.10 as
scoped... What I will not accept is this gap being left as an implicit 'Feature 08 will finish it.'"
Security-reviewer: required a tracked task (this one) plus a `docs/security/threat-mitigation-matrix.md`
correction (done as part of 2.10's own closure, see that task's Outcome) before APPROVE.

## Scope
- **In:** either (a) route the responder's SDP-offer receipt through a gate-aware check so a genuine
  P2P first contact also lands in `pending_requests` before any content flows over the data channel,
  or (b) some equivalent mechanism that achieves the same effect without restructuring the
  offer/answer handshake itself (architect: pick whichever fits `session.rs`'s existing structure —
  this task file does not mandate one approach). A pinning regression test in
  `apps/core/tests/p2p_session.rs` for whichever behavior results.
- **Out:** the finalized/polished accept-or-decline-an-incoming-call UX (Feature 08's job, same as
  2.10's CLI prompt is deliberately minimal); contact tokens/PoW stamps (T08/T14).

## Deliverables
1. A gate check reachable from the P2P session-establishment path (`apps/core/src/session.rs`),
   applied before chat content is delivered to the caller of `pump`/`recv`, not just before X3DH/OTK
   consumption (2.10's existing invariant — gating after crypto verification, not before — must be
   preserved here too, for the same reasons documented in `chat.rs`'s `open_inbound`).
2. `apps/cli/src/session_connect.rs`: wire the same accept/reject UX 2.10 added to the relay chat
   path, or an explicit, loud placeholder if the fix lands in `apps/core` first and CLI wiring is
   split into a follow-up — do not leave `session connect` silently ungated once `apps/core` has the
   mechanism.
3. `apps/core/tests/p2p_session.rs`: a test proving a first-ever P2P session's chat content is gated
   the same way 2.10's relay path is (first contact → `pending_requests`, not delivered; second
   envelope pre-accept refused; accept delivers normally).

## Risks / notes
- Same hard invariants as 2.10: entirely client-side, no new server-visible signal; gate fires after
  signature verification/session establishment (a rejected first contact still costs whatever
  handshake material was already consumed — document honestly, don't restructure the handshake to
  avoid it).
- `docs/security/threat-mitigation-matrix.md`'s "First-contact message-request gate (T06/T08)" entry
  should be updated (or reconfirmed) once this lands, since 2.10 only added the caveat that the
  mitigation was relay-path-only — this task is what actually closes that caveat.
- `TODO: confirm`: whether the fix belongs in `dial_established`/`answer_established` (gate before
  the session is usable at all) or in `P2pSession::pump`'s `open_inbound`-equivalent call (gate at
  the point content would be delivered, session already installed) — architect call.
