# 3.7 — Reuse TLS config and one link per federated message (+ SRV failover)

**Phase:** 3 — Review of Phase 2 · **Feature:** review fix (F10 + N2) · **Depends on:** 3.1, 3.3, 3.5 · **Status:** pending

## Goal
Stop re-reading the OS trust store and opening two TLS links per routed message; honour SRV
priority/weight with failover.

## Scope
- **In:** build `ClientConfig` once in `FederationRuntime` at startup; `route_foreign` dials once and
  sends `FedReachability` then `FedRoute` on the same link; `dial_foreign` iterates endpoints in SRV
  priority/weight order with failover instead of `.into_iter().next()` (N2).
- **Out:** a persistent connection pool across messages (larger change, own task if wanted); the
  budget accounting (3.5).

## Deliverables
1. `FederationRuntime` gains a cached `Arc<ClientConfig>`; `link::dial` takes it.
2. `apps/rendezvous/src/federation/outbound.rs` — single-link `route_foreign` exchange; `dial_foreign`
   failover loop.
3. `apps/rendezvous/tests/federation_route.rs` — one routed message opens **exactly one** TCP
   connection (count accepts); a first endpoint refusing connections falls through to the second;
   `federation_link_up` does not flap per message.

## Risks / notes
- A cached trust store must still **fail closed** on a rotated/absent CA — moving the load to
  startup changes *when* that failure surfaces (a deliberate side benefit; state it).
- Failover must not relax the domain pin: every candidate endpoint is pinned the same way.
- Restructures the same two functions 3.1/3.3/3.5 edit — hence last in the federation wave.
- Narrows (does not close) the pre-check TOCTOU window 2.8 documented.
