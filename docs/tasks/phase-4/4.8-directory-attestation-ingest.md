# 4.8 — Org directory-attestation ingest

**Phase:** 4 — Verification & Trust + Terminal TUI Client · **Feature:** T08 — Verification & Contact Trust · **Depends on:** 4.3, 4.6 · **Status:** done

## Goal
Let a client ingest a signed, org-issued HR-name→key mapping as **petname provenance, not key
authority** — a display-name hint the user can accept or ignore, never a substitute for verification
([system-design §3.5](../../architecture/system-design.md)).

## Scope
- **In:** client-side ingest of a signed directory-attestation artifact; verify the org's signature;
  store as a **petname suggestion with recorded provenance** (which org attested it, when), distinct
  from the user-assigned `petname` field (4.6) — never auto-applied as the display name, never treated
  as proof of identity. Schema is now settled: [docs/security/directory-attestation.md](../../security/directory-attestation.md),
  proposed and then revised to the architect+security-reviewer pass's required changes (multi-org
  suggestion storage, precise signed-byte-sequence definition, a total cross-import suggestions cap,
  a concrete `hr_name` bound) before this task's implementation deliverable started.
  A `meridian directory import <path> --org-key <hex>` CLI command is part of this task's scope (added
  after the schema review flagged its absence) — without it there is no way for a human to ever trigger
  ingest.
- **Out:** any server-side directory-issuance machinery (out of scope per the feature spec: "web-of-trust
  anything" is explicitly Out); auto-applying an attested name as `petname`; displaying suggestions in
  `contact list`/the TUI (a later task's job — see the TUI surface note below).

## Deliverables
1. Schema proposal (reviewed by architect) for the signed directory-attestation artifact — done,
   [docs/security/directory-attestation.md](../../security/directory-attestation.md).
2. `apps/core/src/trust.rs` (or a sibling module): ingest + org-signature verification + provenance-
   tagged suggestion storage, per the settled schema.
3. `meridian directory import <path> --org-key <hex>` CLI command (`apps/cli/src/directory.rs` or
   equivalent), wired into `main.rs`.
4. Tests: valid attestation → suggestion offered, never auto-applied; invalid/unsigned → rejected;
   suggestion is visually/structurally distinct from a verified petname; multi-org suggestions for one
   `account_pub` don't collide/overwrite; total-cap eviction.

## TUI surface (Definition of Done gate 9)
None **in this task** — `ingest_directory`/`directory_suggestions` are a library surface only; no
screen displays a suggestion yet (flagged explicitly, per gate 9's own "no user surface? say so" rule,
rather than silently omitted). The natural place to surface a suggestion is the contact-detail view —
task [4.19](./4.19-contact-list-detail-screens.md) (contact list + add-contact + contact detail) should
pick this up when it's planned/implemented; if it doesn't, that's a gap to flag at that point, not
silently absorbed here.

## Risks / notes
- The provenance-not-authority boundary is the entire point — a bug here would let an org's directory
  silently override a user's own petname/trust decisions, which is exactly the "key authority via
  displayname" confusion §3.5 exists to prevent.
- Do not invent a wire contract without architect sign-off — this is new ground, and a rushed schema
  here becomes someone else's wire-compat problem later.

## Status
Done, in two gated passes as the task's own risk note required. **Pass 1 (schema, pre-code):** drafted
[docs/security/directory-attestation.md](../../security/directory-attestation.md); the required
architect+security-reviewer pass returned approved-with-required-changes — multi-org suggestion storage
was internally contradictory (single-valued map vs. a "keep separate suggestions from different orgs"
requirement with no field to match on), the signed byte sequence was underspecified ("struct minus a
field" rather than a named concrete type — real cross-implementation ambiguity risk), no total cap
existed across imports (only a per-artifact one), and `hr_name` had no concrete bound. All four fixed
in the doc before any code was written; the schema's `TODO: confirm` (hold vs. drop unmatched entries)
was resolved to **held**, bounded by the new total cap. **Pass 2 (implementation):** `apps/core/src/
directory.rs` (new sibling module — kept separate from `trust.rs` so the provenance-not-authority
boundary is structural: `DirectoryStore` never imports `crate::trust::*`, never holds a `TrustStore`
reference, has no way to reach `Contact`/`TrustState` at all, not just written to avoid it), `apps/cli/
src/directory.rs` (`meridian directory import <path> --org-key <hex>`, `--org-key` required so the
trust-anchor pin can never be silently skipped), `trust.rs` gained one field + two pass-through methods
+ an `open_at_rest`-time `reconcile_total()` call. Combined **reviewer** pass (required) passed clean on
both lenses with zero required fixes — confirmed the trust-anchor check runs before signature
verification (correct ordering, no wasted work on a mismatched-key artifact), signature verification is
over the correctly-reconstructed `DirectoryAttestationSignable` bytes (not the raw artifact, not
self-referential), all bounds are enforced before per-entry work, no panic path on hostile input, and
every required test genuinely proves its named property (not a weaker proxy).

`cargo test -p meridian-core --test directory_attestation` (12/12), the full `cargo test -p
meridian-core -p meridian-cli` (clean), `cargo fmt --check`, and `cargo clippy --workspace
--all-targets -- -D warnings` all clean.
