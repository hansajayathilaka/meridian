# 3.23 — Bound `serve_link`'s idle read (no deadline on the established-link serve loop)

**Phase:** 3 — Review of Phase 2 · **Feature:** review fix (found during 3.22's coverage work, not
part of the original report) · **Depends on:** 3.2, 3.4 · **Status:** pending

## Goal
An already-handshaked federation peer that stalls or trickles a frame must not hold a `max_links`
slot forever — the accept-side serve loop needs the same kind of bounded wait every other s2s I/O
exchange in this codebase already has (task 3.2's handshake timeout, task 3.3's outbound timeouts).

## Scope
- **In:** wrap `apps/rendezvous/src/federation/inbound.rs`'s `serve_link` main-loop
  `link.recv_frame().await` in an idle-read deadline (`with_deadline`/`tokio::time::timeout`,
  mirroring the pattern `finish_handshake` and the outbound dial/request path already use), backed
  by a new, explicit config knob (do not silently reuse `handshake_timeout_ms` or
  `request_timeout_ms` — this is a genuinely different phase of the connection's lifecycle from
  either). On timeout, drop the link cleanly (same as any other link-closing path) and free its
  `max_links` permit.
- **Out:** any change to the handshake path itself (task 3.2, already bounded) or the outbound
  dial/request path (task 3.3, already bounded) — this task is the one remaining unbounded s2s I/O
  wait, not a re-audit of the ones already fixed.

## Deliverables
1. A new `Federation` config field (`serve_idle_timeout_ms` or similar — name it for what it
   actually bounds) with a documented, justified default (do not guess a round number without
   reasoning — a real reply on an established link should be fast; consider reusing 3.20's
   measurement methodology or reasoning from `request_timeout_ms`'s existing precedent).
2. `serve_link` wrapped so a peer that stalls mid-frame after handshake is dropped and its
   `max_links` permit reclaimed.
3. A test proving the fix: task 3.22's `slow_loris_after_link_established_reveals_no_idle_read_deadline`
   in `apps/rendezvous/tests/federation_link_dos.rs` currently pins the *absence* of this behavior
   (asserts nothing happens within a bounded window, then the connection resumes once trickled
   input completes) — update it (or add a sibling) to assert the connection is now dropped and the
   permit reclaimed within the new deadline, mirroring task 3.2's cases (c)/(d) "prompt drop, not
   merely eventually" mutation-proof shape.

## Risks / notes
- **Severity is worse than "an admitted partner going rogue."** In the default WebPKI mode
  (`federation.ca_bundle_path` empty), `FederationListener::finish_handshake` neither pins an
  expected domain nor calls `FederationPolicy::admit_any` before a frame is fully decoded —
  admission is checked only inside `handle_fed_fetch`/`handle_fed_route`/`handle_fed_reachability`,
  which a slow-loris connection never reaches. So in WebPKI mode, **any actor holding a TLS client
  certificate that chains to a public CA** — not necessarily an org on this server's federation
  allowlist, not necessarily one this server has ever agreed to talk to, exploitable even when
  `federation.policy = closed` — can occupy a `max_links` slot indefinitely. Private-CA/air-gap
  mode is the narrower case the original framing described (trust root is exclusively the
  operator's own CA). Frame the fix's urgency accordingly — this is closer to "any TLS-cert holder
  can starve federation link capacity" than "a known-bad but already-trusted partner."
  (3.22's security-reviewer sign-off, carried forward here rather than re-derived.)
- Bounded regardless: at most `max_links` peers can hold a slot this way, and each is capped at
  `MAX_FRAME_LEN` bytes of allocation — not an unbounded resource leak, but a real starvation
  vector against every other legitimate partner trying to open a link while slots are held.
- Found and demonstrated by task 3.22's `slow_loris_after_link_established_reveals_no_idle_read_deadline`
  test — read that test first, it already proves the gap precisely.
