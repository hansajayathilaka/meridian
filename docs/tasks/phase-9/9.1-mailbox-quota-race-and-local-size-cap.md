# 9.1 — Serialize mailbox quota check-and-enqueue; cap local route envelope size

**Phase:** 9 — Review of Phase 8 · **Feature:** review fix (F1) · **Depends on:** — · **Status:** in progress

## Goal
Close the mailbox quota's check-then-write race, re-assessed by this phase's security review as a
practically exploitable storage-exhaustion DoS against a targeted offline recipient — not merely "one
extra envelope per concurrent racer" as the original task 8.5/8.7 carry-forward characterized it. A
single free-to-create account, opening multiple connections and bursting near-simultaneous, near-maximal
`Route` frames at one offline victim, can currently overrun `quota_mb` by concurrency × envelope size.

## Scope
- **In:**
  - `mailbox_enqueue_with_quota` (`apps/rendezvous/src/store.rs:165-183`): the read (`mailbox_size_bytes_for_recipient`)
    and write (`mailbox_enqueue`) are two unserialized `Store` calls. Serialize per recipient — a
    per-recipient async lock keyed on recipient pubkey (works for both `MemoryStore` and `SqliteStore`),
    or fold the check into one atomic SQL statement/transaction for `SqliteStore` specifically. Whichever
    shape is chosen must work identically for both `Store` impls (the trait has no compare-and-swap
    primitive today — this task may add one).
  - `apps/rendezvous/src/ws.rs::handle_route`: add a per-envelope size cap on the local route path,
    matching the federated path's existing `MAX_FRAME_LEN` (1 MiB, `federation/inbound.rs`/`link.rs`)
    defense-in-depth check, which the local path currently lacks entirely.
- **Out:** A per-account connection-concurrency limit (a distinct, larger mitigation the security review
  named as a contributing factor but did not scope into this fix — `Registry::add`/`state.rs` are
  untouched here) and a per-recipient row-count cap (F2's territory, `MAILBOX_ACK_MAX_IDS`-adjacent, not
  this task). `apps/rendezvous/src/ws.rs`'s drain/registration ordering (F4, task 9.4) is a related but
  separate race — do not fold its fix in here, though 9.4 is expected to reuse whatever locking
  primitive this task introduces.

## Deliverables
1. `mailbox_enqueue_with_quota` (or its call site in `queue_to_mailbox`) is race-free under concurrent
   calls for the same recipient, in both `MemoryStore` and `SqliteStore`.
2. `handle_route` rejects an over-`MAX_FRAME_LEN` local envelope the same way `handle_fed_route` already
   does (same error shape/code).
3. A concurrency-adversarial test racing N concurrent `Route`s at one offline recipient, asserting the
   final mailbox byte total never exceeds `quota_mb` by more than one envelope's worth — re-run with
   large (near-`MAX_FRAME_LEN`) envelopes to prove the previously-documented "bounded, roughly one
   envelope" assumption actually holds post-fix (it does not pre-fix).

## Risks / notes
This is the phase's top-priority should-fix (per the review verdict) and touches both `Store` impls plus
a `ws.rs` route handler — land it first since 9.2 (quota boundary test), 9.3 (TTL filter), and 9.4 (drain
race) all touch the same function family and are sequenced after this task, either to test the final
locked behavior (9.2, hard dependency) or to avoid rebase churn / reuse the new locking primitive (9.3,
9.4, soft dependencies). Keep the lock/transaction scope narrow — do not serialize unrelated recipients'
enqueues against each other, only concurrent operations on the *same* recipient.

## Tests
`cargo nextest run -p meridian-rendezvous` (new concurrency-adversarial test + existing quota/route
suites), `cargo clippy -p meridian-rendezvous --all-targets --features sqlite -- -D warnings`.

## Reviews
**security-reviewer** (mandatory — this closes a DoS finding from the security lens), **architect**

sanity-check against the dependency-graph/trait-design conventions), **test-engineer** (the
