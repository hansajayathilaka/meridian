# 10.7 — Sender engine: chunking, backpressure, progress, multi-file batches

**Phase:** 10 — File Transfer Stream · **Feature:** T09 · **Depends on:** 10.6 · **Status:** done

**User surface:** none yet — the sender engine has no CLI/TUI surface of its own; that lands in tasks
10.10/10.11, which consume this task's progress events and own the Definition of Done's gate 9 obligation.

## Goal
Drive the actual outbound transfer: split a file into 64 KiB chunks, seal each (task 10.5), send over
the stream (via task 10.4's `send_stream_frame`), throttled by the buffered-amount watermark (task
10.2), emitting progress events, and sequencing multiple files in a batch.

## Scope
- **In:** `apps/streams/src/sender.rs` (or similar): the chunking/send loop, a low-watermark
  backpressure policy (poll `buffered_amount`, pause sends above a high watermark, resume below a low
  one — pick concrete byte thresholds and record them in the Outcome), a progress event type (`bytes
  sent / total`, throughput) the CLI/TUI can subscribe to, and multi-file batch sequencing (send
  manifests/chunks for file 2 only after file 1 completes, or interleaved — implementer's call, record
  the choice).
- **Out:** the receiver side (10.8), resume (10.9), the actual CLI/TUI progress bar rendering
  (10.10/10.11 consume the progress events this task defines).

## Deliverables
1. Sender engine in `apps/streams/src/sender.rs`.
2. Progress event type + a way to subscribe to it (channel/callback — match this crate's existing async
   idioms).
3. Tests over the loopback transport: a small multi-chunk file sends completely and in order-of-offset
   (even though the channel is unordered, the receiver must reassemble by the `i` field, not channel
   order — this task's test should deliberately interleave/reorder frames at the loopback layer to prove
   the engine doesn't assume in-order delivery).

## Risks / notes
The channel is `reliable + unordered` (task 10.6's `channel_cfg`) — chunks may arrive out of order. The
sender engine itself doesn't need to handle reordering (it just sends), but its test must simulate it to
catch an implementer accidentally assuming order. Watermark thresholds are a `TODO: confirm` design
choice — no doc pins concrete numbers; pick reasonable defaults (e.g. high watermark = a few MB, low
watermark = a fraction of that) and record the rationale, since the soak test (10.14) will validate
whether they're too conservative or too aggressive against real throughput.

## Outcome
Added `send_file`/`send_files` (sequential batch)/`send_chunk_frame` in `apps/streams/src/sender.rs`:
chunks a file into `CHUNK_SIZE` (64 KiB) pieces, seals each via task 10.5's `seal_chunk`, wraps in a new
canonical wire type `ChunkFrame{i: u64, data: Vec<u8>}` (added to `apps/streams/src/chunk.rs` — the
`{i: uint, data: bstr}` shape `docs/api/wire-protocol.md` §6 documents, CBOR via `meridian_proto`'s
existing helpers), and sends via task 10.4's `P2pSession::send_stream_frame`. Backpressure:
`SenderConfig{high_watermark: 4 MiB, low_watermark: 1 MiB, poll_interval: 5ms}` polls
`stream_buffered_amount`, pauses above high, resumes only at/below low (hysteresis, not a single
threshold, to avoid pause/resume thrash) — `TODO: confirm` these byte thresholds against task 10.14's
soak-test throughput report. Progress: `SendProgress{file_index,file_count,name,bytes_sent,total_bytes,
bytes_per_sec}` over a `tokio::sync::mpsc::UnboundedSender`, the same channel idiom `apps/core`'s own
`SessionEvent` plumbing already uses. Batch sequencing is sequential (file N+1 starts only after file
N's last chunk is sent) — avoids needing an unscoped per-file fairness/priority policy interleaving
would require. `FileSend`'s custom `Debug` redacts `k_f`/`data`.

`ChunkFrame` is placed in `chunk.rs` (not `sender.rs`) since it's the one place that pairs `seal_chunk`'s
opaque output with the wire index `i`, and both this task's sender and task 10.8's receiver (built in
parallel in the same run) import the identical type — never two independently-hand-rolled CBOR shapes
that could drift apart. 10.8's implementer found and fixed a small pre-existing compile issue in this
file while integrating (a local `Result<T>` alias fixed to `ChunkError` was shadowing
`std::result::Result`, requiring `ChunkFrame::encode`/`decode`'s `Result<_, CodecError>` signatures to
be qualified as `core::result::Result`) — reviewed and confirmed correct, minimal, and not masking a
deeper issue.

**code-reviewer** (the task's only named reviewer) returned **PASS**, with zero blocking or should-fix
findings, verified by inspection rather than trusting claims: confirmed the watermark hysteresis is a
genuine two-threshold pause/resume (the test's `[150,150,90,50,15]` sequence specifically proves no
resume at 90, between low and high — the classic thrashing bug this guards against); confirmed
`send_files` is a plain sequential `for` loop with no `tokio::spawn`, so interleaving is structurally
impossible, not just implicit; judged the `send_chunk_frame_does_not_assume_call_order_reflects_file_order`
test (which can't literally reorder in-process loopback FIFO delivery, so it instead proves
reassembly-by-`i` succeeds under scrambled call order) a legitimate proxy for the task's actual
requirement, not a gap; confirmed no logging of `k_f`/plaintext anywhere and that `Debug` impls redact
as claimed. One optional, non-blocking style nit noted (rename `chunk.rs`'s own `Result<T>` alias to
`ChunkResult<T>` so future additions don't need explicit qualification) — left as a future-pass
convenience, not required. All 51 `meridian-streams` tests (including everything from 10.1–10.8) green;
clippy/fmt clean; full workspace build clean.
