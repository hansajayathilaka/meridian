# 10.13 — netns rig: loss/RTT injection profiles

**Phase:** 10 — File Transfer Stream · **Feature:** T09 · **Depends on:** — · **Status:** done

**User surface:** none — pure test infrastructure (`tools/`, CI), no client-visible behavior. No TUI
surface applies to this task.

## Goal
Extend the existing network-namespace test rig (`tools/netns-nat-matrix.sh`, from Phase 1's NAT-traversal
work) with `tc netem` loss/latency injection, so the soak and kill/resume tests (10.14/10.15) can run
under the feature spec's named profiles: 1% loss / 80 ms RTT.

## Scope
- **In:** a `tc netem` wrapper applied to the rig's veth interfaces, parameterized by loss % and RTT,
  reusable by any future test (not file-transfer-specific — pure test infra).
- **Out:** any file-transfer test logic itself (10.14/10.15 consume this).

## Deliverables
1. Loss/RTT injection added to the netns tooling (new script or an extension of
   `tools/netns-nat-matrix.sh`).
2. A smoke test proving the injected loss/RTT is actually observed (e.g. `ping` statistics under the
   profile match the configured parameters within tolerance).

## Risks / notes
This task has no dependency on any other Phase 10 task and can run in parallel with Wave 1 — it's pure
infra.

## Tests
The smoke test above, run manually or under whatever harness convention `tools/netns-nat-matrix.sh`
already follows (`--ignored` runner precedent from task 3.12, if this needs root/netns privileges CI
doesn't grant by default).

## Reviews
**devops** + **test-engineer**.

## Outcome
Built `tools/netns-netem.sh`, a standalone `tc netem` wrapper kept separate from
`tools/netns-nat-matrix.sh` (loss/RTT injection is orthogonal to NAT-flavor emulation, and the strategy
doc names this profile as shared infra for both T09 and T10): `apply`/`clear` and `apply-pair`/`clear-pair`
primitives (splitting a configured round-trip loss%/RTT in half per veth side), a `profile <name>` lookup
wiring the feature spec's named `file-transfer` profile (1% loss / 80ms RTT), and a self-contained
`smoke`/`smoke-all` subcommand building its own throwaway veth pair and asserting observed `ping`
RTT/loss against configured values. Graceful `need_root()`/`need_netem()` skips (exit 0) when
root/CAP_NET_ADMIN or the kernel's `CONFIG_NET_SCH_NETEM` module are unavailable, matching
`netns-nat-matrix.sh`'s existing convention. A new scheduled + `workflow_dispatch`
`.github/workflows/netns-netem-smoke.yml` runs it, following task 3.12's precedent.

This sandbox's kernel lacks `CONFIG_NET_SCH_NETEM`, so no real netem-affected run was observed here;
the implementer validated the surrounding orchestration/statistics/cleanup logic by temporarily shadowing
`tc` with a no-op stub and confirming the RTT assertion correctly *fails* when netem isn't really applied
(non-vacuous), independently reproduced by both required reviewers.

Both named reviewers (**devops**, **test-engineer**) returned **PASS**, each independently re-verifying
rather than trusting claims: devops confirmed `shellcheck` cleanliness directly, validated the workflow
YAML against `capacity-check.yml`/`p2p-wire-proof.yml` conventions, and researched Ubuntu's kernel-config
annotations to substantiate (not just accept) that `ubuntu-latest` should carry `CONFIG_NET_SCH_NETEM` as
a loadable module. test-engineer independently reproduced the implementer's no-op-`tc`-stub validation,
unit-tested the ping-output parsing against realistic and edge-case (100%-loss) summaries, and did the
statistical arithmetic on the loss-tolerance band (n=1500, p=0.01) — finding it sound against pure
netem-absent detection but blind to a specific failure mode.

Two should-fix findings (one per reviewer) plus a nit were closed in a same-task follow-up commit before
this task was marked done:
- **test-engineer's should-fix** (the more significant one): the statistical loss-tolerance band
  (0.2x–3x) would not catch a "forgot to halve loss between the two veth ends" regression, since the
  buggy composed value (`2L − L²`) still lands inside the band for both the file-transfer and a
  high-loss profile. Fixed by adding a deterministic `tc -s qdisc show` assertion on each side
  immediately after `apply_netem_pair`, checked against the expected per-side half-share independent of
  the statistical ping check.
- **devops's should-fix**: the new CI job would silently `exit 0` forever if `need_netem()` ever skipped
  on `ubuntu-latest` (a runner devops's research indicates should have the module), masking a real
  regression as a permanent no-op. Fixed with a loud preflight `modprobe sch_netem` failure step before
  `smoke-all`. Also fixed devops's minor finding: the throwaway probe veth in `need_netem()` wasn't
  trap-protected against a signal landing mid-probe — added a scoped `trap ... EXIT` disarmed before the
  function returns.
- **test-engineer's nit**: `smoke`'s fixed namespace/interface names could collide under concurrent
  invocations — given the same PID-suffix treatment as `need_netem()`'s own probe interface.

Not yet independently observed: a real PASS (not just a graceful skip) on a kernel that actually has
`CONFIG_NET_SCH_NETEM` — the scheduled/`workflow_dispatch` CI job is the mechanism to observe this for
real; whoever next touches this area should confirm the first live run, per the same convention task
3.12 followed for its own not-yet-observed-on-a-real-runner caveat.
