# 3.20 — Resolve the `ROUTE_REPLY_GRACE` false-positive-success residual

**Phase:** 3 — Review of Phase 2 · **Feature:** review fix (report §"On-the-fly decisions to ratify") · **Depends on:** 3.3, 3.7 · **Status:** done

## Goal
Turn an unratified 500 ms heuristic — which converts a lost `FedErr` into a *false delivery
confirmation* to the user — into either a measured, documented bound or a reopened protocol decision.

## Scope
- **In:** measure the real reply-RTT distribution over an established link (a bench/harness, **not a
  guess**); then either (a) tighten/justify the constant with the measurement recorded in the doc
  comment and `federation-protocol-v1.md`, or (b) write an ADR reopening the "do not add a
  `FedRouteOk`" wire decision. Plus the missing boundary test.
- **Out:** unilaterally adding `FedRouteOk` to the wire without an ADR — explicitly forbidden by the
  current protocol doc.

## Deliverables
1. The measurement, recorded in the task Outcome.
2. Either the tightened constant + doc-sync, **or** `docs/adr/0020-*.md`.
3. `apps/rendezvous/tests/federation_route.rs` — a `FedErr` delayed just past the window is
   observably a false success today (pinning the residual) or is caught (if fixed).

## Risks / notes
- A false delivery confirmation is a **correctness claim made to the user**, not merely an internal
  imprecision — that is why this outranks its "nit-adjacent" appearance.
- Depends on 3.3 (the timeout framework) and 3.7 (link reuse changes the RTT profile the measurement
  must be taken against) — measuring before those land would measure the wrong system.
- `outbound.rs:257`'s comment records this as "left as a follow-up, not resolved by this task"; this
  task is that follow-up, so the comment must stop pointing at nothing.

## Outcome
Measured real reply-RTT over the real two-server-mTLS harness (N=200, isolating exactly the span
`ROUTE_REPLY_GRACE` bounds, against a `Closed`-policy B rejecting on its first in-process check):
`min=87.1ms p50=88.0ms p95=88.2ms p99=92.1ms max=92.9ms`. Root-caused the surprisingly-high
loopback floor to missing `TCP_NODELAY` on both `link::dial` and `FederationListener::bind`
(Nagle + delayed-ACK interaction with `write_frame`'s two-part write) — a real, separate finding,
documented but left unfixed as out of this task's file-scope (flagged as a follow-up: fixing it
would only make the measured floor lower, making 300ms *more* conservative, not less).

Tightened `ROUTE_REPLY_GRACE` from an unmeasured 500ms to **300ms** (measured max rounded to
100ms × 3 real-network-headroom multiplier) — a real 40% cut to the per-successful-route latency
tax while keeping >3.2× headroom over the measured max. Doc-synced the value + full measurement
into the constant's own doc comment and `federation-protocol-v1.md`. Did **not** write an ADR or
add `FedRouteOk` — the measurement supported tightening (path a), not reopening the wire decision
(path b), per the task's Scope. Added the boundary test the original 2.8 residual note asked for
(`fed_err_delayed_past_route_reply_grace_is_still_reported_as_false_success`, using a new
`spawn_delayed_fed_err_responder` test double speaking the real wire types) pinning that the
residual is **narrowed, not closed** at the new value — closing it outright still needs the
"no `FedRouteOk`" decision reopened via an ADR.

Reviews: architect + security-reviewer (combined pass) — both **pass**. architect confirmed
tightening-with-measurement was the right call, the TCP_NODELAY deferral is a legitimate scope
boundary (not a dodge) and doesn't create a correctness mismatch (only a future optimization
opportunity), and the "do not add a `FedRouteOk`" text is unretracted. security-reviewer confirmed
300ms is defensibly disclosed as a narrowing, not a close, and flagged (non-blocking, tracked for
later) that the 3× WAN-headroom multiplier is itself still a reasoned guess rather than a
WAN-measured value — worth re-measuring against real cross-org WAN RTT once federation is deployed
across genuinely distant orgs. One moderate, cheap fix applied from the review: two other files
(`config.rs`, `federation_abuse.rs`) had stale "500ms" comments outside this task's declared
file-scope; updated both to 300ms rather than leaving them to drift. test-engineer — **pass**, no
findings; independently verified the boundary test exercises the real `route_foreign` path (not a
mock), the delay margin (400ms) is comfortable without being a strawman, ran the suite 4x with 0
flakes, and confirmed the new coverage closes exactly the gap the review report flagged.
