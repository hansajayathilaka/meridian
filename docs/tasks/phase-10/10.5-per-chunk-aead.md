# 10.5 — Per-chunk AEAD (`k_f`, nonce = chunk index)

**Phase:** 10 — File Transfer Stream · **Feature:** T09 · **Depends on:** 10.3 · **Status:** done

**User surface:** none — a crate-local AEAD primitive with no consumer yet (`k_f` generation/sealing is
task 10.6; the sender/receiver loops calling this per chunk are 10.7/10.8). No TUI surface applies.

## Goal
Encrypt each 64 KiB file chunk under the per-file key `k_f` (generated once per file, sealed under the
ratchet in the manifest — task 10.6's job to seal/unseal it) with the nonce derived from the chunk
index, per `docs/api/wire-protocol.md` §6: "`mrd.file/1` chunk body: `{i: uint, data: bstr}`, AEAD key
= per-file `k_f`, nonce = `i`".

## Scope
- **In:** `apps/streams/src/chunk.rs` (or similar): seal/open one chunk using `chacha20poly1305`
  (already a workspace dependency via `meridian-crypto`; approved for direct use here per the
  crypto-protocols skill's "AEAD = XChaCha20-Poly1305") directly inside `meridian-streams` — deliberately
  **not** routed through `meridian-crypto`, since this is ordinary per-file symmetric encryption with a
  key already derived/sealed elsewhere, not ratchet/session state, and keeping it in `meridian-streams`
  keeps the "additive stream type, zero core-crate edits" contract clean.
- **Out:** `k_f` generation/sealing under the ratchet (task 10.6), the sender/receiver loops that call
  this per chunk (10.7/10.8).

## Deliverables
1. `seal_chunk(k_f, i, data) -> Vec<u8>` / `open_chunk(k_f, i, sealed) -> Result<Vec<u8>>` (or
   equivalent) in `apps/streams`.
2. Tests: round-trip seal/open; tampered ciphertext is rejected; wrong index is rejected (confirms the
   nonce actually binds to `i`, not just a fixed/reused value).

## Risks / notes
`docs/api/wire-protocol.md` §6 says "nonce = `i`" but does not pin the exact byte layout (chacha20poly1305
nonces are 12 bytes for the standard construction, 24 for XChaCha — the crypto-protocols skill names
XChaCha20-Poly1305 as the chosen AEAD elsewhere, but this specific per-chunk construction needs its own
explicit pin since `i` alone as a 4- or 8-byte counter zero-padded to the nonce width is the natural
reading but is not written down anywhere yet). `TODO: confirm` — this task's Outcome must record the
exact encoding (recommended: `XChaCha20-Poly1305`, 24-byte nonce = `i` as an 8-byte little-endian
counter followed by 16 zero bytes, matching this codebase's other little-endian-length-prefix
conventions — but confirm against whatever `chacha20poly1305` crate API is actually used and pin
whichever is simplest to implement correctly). **Never reuse a nonce for two different chunks under the
same `k_f`** — since `i` is the chunk index and each file's chunks are indexed once, this holds by
construction as long as `k_f` is never reused across two different files (task 10.6's job to guarantee
fresh `k_f` per file).

## Tests
`cargo nextest run -p meridian-streams`.

## Reviews
**security-reviewer** (mandatory — new AEAD-keying and nonce-construction code, even though it lives
outside `apps/crypto`; nonce reuse is a catastrophic AEAD failure mode).

## Outcome
Added `seal_chunk(k_f: &[u8; 32], i: u64, data: &[u8]) -> Vec<u8>` / `open_chunk(k_f, i, sealed) ->
Result<Vec<u8>, ChunkError>` in a new `apps/streams/src/chunk.rs`, using `chacha20poly1305::
XChaCha20Poly1305` directly (deliberately not routed through `meridian-crypto` — ordinary per-file
symmetric encryption with a key sealed elsewhere, not ratchet/session state). Pinned encoding,
documented byte-for-byte for task 10.12: 24-byte XChaCha nonce = 8-byte little-endian chunk index `i`
followed by 16 zero bytes; no AAD (the nonce alone binds `i`); ciphertext layout is the raw AEAD output
with no nonce prepended, since `i` already travels alongside `data` in the wire chunk body. Four tests
cover round-trip, tampered-ciphertext rejection, wrong-index rejection (proving nonce binding), and
non-colliding ciphertexts across indices for identical plaintext.

security-reviewer (mandatory) returned **PASS**, with no blocking findings, after independently tracing
(not trusting) the nonce construction (confirmed `to_le_bytes()` on a `u64` structurally cannot spill
past the first 8 bytes of the 24-byte nonce, so the "counter overflow into padding" concern the task
flagged doesn't apply regardless of file size), confirming the AEAD library usage is correct (right
key/nonce widths, decrypt failure propagates as `Err` with no garbage-plaintext path, coarse error
variant avoiding a wrong-key/wrong-index/tampered distinguishing oracle), confirming `k_f` is zeroized
on drop via the underlying `chacha20poly1305` crate's own `ZeroizeOnDrop` impl, and confirming all four
tests are genuinely non-vacuous (traced what regression each would catch). It also independently
verified the "no AAD" design choice is acceptable given context: the outer per-stream AEAD (task 10.4's
`decrypt_and_export`, keyed by `HKDF(ratchet_export, info = "mrd/stream/" ‖ type ‖ sid)`) already binds
cross-stream/cross-file ciphertext substitution at the layer above this one, and the wire spec pins no
AAD field here — adding one would be an unreviewed wire-format change beyond this task's scope. The
`k_f`-never-reused-across-files invariant remains correctly out of this task's own enforcement scope
(task 10.6's job); the reviewer's one non-blocking note — record a CSPRNG generation + freshness-test
recommendation in 10.6's own task file — is left for that task's implementer/reviewer since it can't be
addressed until `k_f` generation exists.
