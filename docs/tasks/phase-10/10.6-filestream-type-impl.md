# 10.6 — `mrd.file/1` `StreamType` implementation

**Phase:** 10 — File Transfer Stream · **Feature:** T09 · **Depends on:** 10.3, 10.4, 10.5 ·
**Status:** done

**User surface:** none yet — the registered `StreamType` shell has no CLI/TUI surface of its own; a real
send/receive UI lands in tasks 10.10/10.11, which own the Definition of Done's gate 9 obligation.

## Goal
Implement the `StreamType` trait for `mrd.file/1` and register it — the point in the phase where file
transfer becomes a real, registered stream type against the now-complete substrate (task 10.4), with
**zero diffs to any core crate**. This is the literal acceptance bar
`docs/architecture/features/09-file-transfer.md` states: "implemented purely as a stream type against
the T04 registry — no changes to core session code allowed. That constraint is the point."

## Scope
- **In:** `apps/streams/src/file.rs`: `FileStream` implementing `StreamType` — `name() = "mrd.file/1"`,
  `version() = 1`, `channel_cfg()` = reliable + unordered (`ChannelCfg { reliable: true, ordered: false,
  max_retransmits: None, .. }`, constructed directly since `ChannelCfg`'s fields are already `pub` — no
  transport-crate edit needed), `direction() = Bidir`, `mandatory() = false` (an unsupported peer simply
  can't receive files, never a session error), `on_open` — the recipient accept/reject policy hook
  (auto-accept images under a configurable size threshold, otherwise a decision the caller surfaces to
  the user/CLI/TUI to decide — this task defines the `PolicyCtx`-driven decision function; the actual UI
  prompt is 10.10/10.11's job), `on_frame` — inbound dispatch into per-transfer state (manifest receipt,
  chunk receipt handed to the receiver engine of task 10.8). Per-file key `k_f` generation (fresh random
  key per file) and sealing it under the ratchet in the manifest (via the existing chat/session
  encryption path, not a new mechanism) also land here.
- **Out:** the sender loop (10.7), the receiver loop / merkle verification wiring (10.8), resume (10.9),
  CLI/TUI surfaces (10.10/10.11). This task defines the `StreamType` shell and manifest send/seal; the
  engines that actually move bytes are separate tasks so each stays independently testable.

## Deliverables
1. `FileStream: StreamType` in `apps/streams/src/file.rs`, registered via `register_stream_type`.
2. Manifest send: generate `k_f`, build the CBOR manifest `{name, size, root, enc(k_f under ratchet)}`,
   send on `mrd.ctrl/1`'s `Open.params` (per `docs/architecture/system-design.md` §7.2 — the manifest
   rides in `Open`'s `params` field, not a separate ctrl frame).
3. `on_open` policy decision function + its own unit tests (auto-accept-below-threshold, prompt
   otherwise, first-contact interaction via `PolicyCtx::first_contact`).
4. Tests proving **zero diffs to `apps/core`, `apps/crypto`, `apps/transport`** in this task's own
   commit (the review gate; call this out explicitly in the PR description).

## Risks / notes
`PolicyCtx::first_contact` (from `apps/core/src/streams.rs`) must be honored the same way chat's
message-request gate is — a stranger sending a file before being accepted as a contact should not
silently write to disk. Confirm with the `anonymity-model` skill whether file transfer needs the same
gate chat has, or a stricter one (sensitive-type default per `stream-type-authoring` skill: "sensitive
types (tunnels, screenshare) default to prompt/allowlist, never auto-accept" — file transfer sits
between chat's auto-accept and tunnel's always-prompt; the size-threshold auto-accept for images only is
the spec's own compromise, confirm it composes correctly with first-contact).

## Tests
`cargo nextest run -p meridian-streams`.

## Reviews
**reviewer** (combined: code-reviewer for `StreamType` contract conformance and the zero-core-diff
constraint; security-reviewer for the `on_open` policy/first-contact interaction and `k_f`
generation/sealing).

## Outcome
Added `FileStream: StreamType` in `apps/streams/src/file.rs`, registered via `register_stream_type` like
any other additive type. `name()="mrd.file/1"`, `version()=1`, `channel_cfg()` = reliable+unordered
`ChannelCfg`, `direction()=Bidir`, `mandatory()` left at the trait's own default (`false`). A pure
`decide_file_offer(manifest, policy, threshold) -> FileOfferVerdict{AutoAccept|AskUser|Reject}` checks
`policy.first_contact` first and unconditionally — before the image/size heuristic is ever consulted —
so a stranger can never be auto-accepted regardless of file type or size; `on_open` resolves `AskUser`
via an injected synchronous `ask_user` hook (defaulting to always-decline), the seam tasks 10.10/10.11
wire to a real prompt. `on_frame` buffers raw bytes into a minimal `TransferState` per accepted transfer,
left deliberately thin for task 10.8 to build the real receiver on. `FileStream::build_open_params`
generates a fresh CSPRNG `k_f` (`getrandom::fill`), seals it via the *existing* `ChatState::seal_bytes`
ratchet primitive (no new mechanism, no `apps/core` edit — confirmed no such gap existed: the crate
purely depends on `meridian-core`'s public API, exactly as any third-party `StreamType` implementer
would), and builds the CBOR manifest to hand to `Open.params`. Zero diffs to `apps/core`, `apps/crypto`,
or `apps/transport` — the task's own literal acceptance bar — confirmed via `git diff --stat` both by
the implementer and independently by review.

Both mandatory review lenses (code-reviewer, security-reviewer, run as one combined `reviewer` pass)
returned **PASS**, independently re-verifying rather than trusting claims: traced `decide_file_offer`'s
branch order and `on_open`'s call into it to confirm first-contact gating is structurally unconditional
(not just documented as such), confirmed the `on_open_rejects_a_first_contact_stranger_even_with_a_permissive_ask_user_hook`
test genuinely proves this using a hook that would accept anything, traced `k_f`'s generation
(`getrandom::fill`, a genuine CSPRNG) and sealing path end-to-end through `ChatState::seal_bytes`
(confirmed no plaintext-fallback branch on a sealing failure), and confirmed the manifest-seal round-trip
test performs a real two-party X3DH handshake rather than faking the crypto. One should-fix was closed
in a same-task follow-up commit before this task was marked done: `k_f` was returned as a plain
`[u8; 32]` rather than `Zeroizing`-wrapped, inconsistent with every other place in the codebase that
carries symmetric/derived key material surviving past a single call (`apps/crypto/src/x3dh.rs`,
`apps/crypto/src/ratchet.rs`) — fixed by wrapping `fresh_k_f`'s and `build_open_params`'s return in
`zeroize::Zeroizing<[u8;32]>`, which derefs transparently so `seal_chunk` (task 10.5) and the sender
engine (task 10.7) consume it unchanged. Two clippy findings from the original implementation (a
`type_complexity` warning on the `ask_user` closure type, and a `too_many_arguments` warning on
`build_open_params`) were also fixed in the same pass: a `type AskUserFn` alias, and grouping
`name`/`size`/`root` into a small `FileMeta` struct with no behavior of its own. All 37
`meridian-streams` tests (34 pre-existing + 3 new integration) stayed green throughout, independently
re-run after every fix; clippy/fmt clean; full workspace build clean.

Two non-blocking findings, both correctly deferred rather than silently dropped:
- **Unbounded per-transfer buffering** (`TransferState.pending_chunks: Vec<Vec<u8>>` has no size/count
  cap) — task 10.8 (receiver engine) already owns "write-by-offset, incremental verification, corruption
  handling" per its own scope, and this task's `TransferState` doc comment already flags it as
  deliberately minimal; review confirms this must be a hard requirement of 10.8's own Definition of
  Done, not something that can slip further.
- **Mutex-poison edge case** (`accept()`/`on_frame` silently discard a poisoned-lock error, and `accept()`
  still unconditionally reports `Accept` even if the entry was never inserted) — currently unreachable
  (no panic occurs anywhere while either lock is held), flagged as a latent trap only if a future edit
  adds panicking work under the lock; not worth a task of its own.

Two `TODO: confirm` items were reviewed and correctly judged non-blocking, both self-flagged in the code:
the default auto-accept image-size threshold (5 MiB; the feature spec names no default `N`) and
file-extension sniffing as the "is this an image" signal (a UX heuristic only, never a security boundary
— first-contact gating and, later, task 10.8's merkle verification are the real boundaries).
