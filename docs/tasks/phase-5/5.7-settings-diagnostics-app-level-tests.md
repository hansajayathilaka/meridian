# 5.7 — App-level reconciliation tests for Settings/Diagnostics

**Phase:** 5 — Review of Phase 4 · **Feature:** review fix (F7) · **Depends on:** — · **Status:** done

## Goal
Close the App-level test coverage gap for Settings and Diagnostics — the same gap class (a live-UI
reconciliation path invisible to lower-layer tests) that took six gap-closure waves to find and fix for
contacts/requests/chat in Phase 4. Neither screen currently has a test combining a real key event, a
real worker dispatch, and reconciliation of the completed effect back into the live screen.

## Scope
- **In:** New App-level tests in the style of `apps/tui/tests/accept_to_chat.rs` (real key events, real
  `worker::dispatch`, real sealed `$MERIDIAN_HOME`) for: Settings (real key edit → real
  `Effect::SaveSetting` → confirm persisted/session-only outcome renders) and Diagnostics (`Ctrl+K` →
  real `Effect::RunDoctor` outcome rendered, including the not-on-`PATH` failure path).
- **Out:** Any production code change — this task is test-only, unless the new tests reveal an actual
  reconciliation bug (in which case, treat that as a new finding requiring its own follow-up, not silent
  in-task scope creep — flag it explicitly per this project's "report, don't quietly patch around it"
  discipline, same as 4.41/4.45/4.48's own precedent).

## Deliverables
1. `apps/tui/tests/screens_settings.rs` (or a new file) gains a real-key-event/real-worker test proving
   a setting change round-trips through the live screen.
2. `apps/tui/tests/screens_help_palette.rs` (or a new file) gains a real-key-event/real-worker test
   proving a `RunDoctor` result — including its failure path — renders in the live diagnostics pane.

## Risks / notes
If either new test finds a genuine reconciliation bug (mirroring Defect C's discovery pattern), stop and
report it rather than silently fixing it inside this test-only task — that would blur this task's scope
and its review sign-off. Report to the phase's own tracking, name it as a new finding.

## Tests
`cargo nextest run -p meridian-tui --test screens_settings --test screens_help_palette --test run_worker_settings`

## Status
**Done, test-only, no production code changed.** Four new App-level tests drive the real
`Ctrl+K`-palette → real screen → real key event → real `Effect` → real `worker::dispatch` → real
`AppEvent::Worker` round trip: two in `apps/tui/tests/screens_settings.rs` (the `Saved` and
`SessionOnly`/`ConfigWriteError::NoFile` outcomes) and two in `apps/tui/tests/screens_help_palette.rs`
(the not-on-`PATH` `RunDoctor` failure path, and a unix-only real-subprocess success path — a tiny script
on `$PATH` standing in for the real CLI binary, since `apps/tui` cannot depend on `apps/cli` per ADR
0020).

**No reconciliation bug found**, confirmed independently by both review passes against source, not just
the implementer's claim: `App::handle_worker`'s cross-screen `apply_*` special-casing (the mechanism
behind Phase 4's six gap-closure waves) only intercepts `LoadSession`/`AcceptRequest`/`AddContact`/
`RejectRequest`/`LoadHistory`. `SaveSetting` and `RunDoctor` fall through to the requesting screen's own
`handle_worker` directly — there's no separate App-owned copy to reconcile into, so that specific bug
class has no analog here.

**`test-engineer` mutation-tested this claim rather than accepting it**: skipping `Settings`'s
reconciliation entirely broke both new Settings tests (lower-layer tests stayed green — proving they're
structurally blind to this bug class, exactly why this task exists); corrupting `RunDoctor`'s rendered
content broke the success-path test — proving the suite also catches "right screen, wrong content," not
just wrong-screen routing.

**Two honest, non-blocking observations recorded here** (neither is a defect — per this task's own scope,
only a genuine bug would need a "stop and report" follow-up, and neither review found one):
1. `test-engineer` found a genuinely untested (but empirically verified safe) path: `Diagnostics::handle_key`
   accepts `Esc` unconditionally, even while `RunDoctor` is still running (unlike `Settings`, which
   correctly blocks all input including `Esc` during `SettingsMode::Saving`) — so a user can pop the
   Diagnostics pane before its worker completion arrives. Verified via a scratch test (reverted, not
   landed) that the late `WorkerEvent` is silently ignored by whichever screen resurfaces, matching every
   other screen's `_ => {}` unmatched-effect discipline — no panic, no corruption. Worth a follow-up test
   in the same style; not scope creep for this test-only task since no defect exists to fix.
2. `code-reviewer` saw one unreproduced flake (`last_persist == None` on a single run) that did not
   reproduce across ~90 subsequent runs under equal-or-heavier load, and traced it to likely
   cross-invocation build/tool contention (a concurrent `cargo fmt`/`cargo clippy` invocation against the
   same crate during that one background run), not a genuine race — no shared mutable state was found
   between the affected tests. Recorded for CI to watch, not blocking.

### Review round
`code-reviewer` — **PASS**, no blocking issues. Confirmed the new tests exercise the real App/worker/
dispatch path (no internal shortcuts), independently verified the "no cross-screen reconciliation step"
claim against `app.rs`'s actual dispatch table, confirmed `PathGuard`'s isolation is sound (process-
separated across test files, mutex-serialized within, `Drop`-safe under panic since the crate uses the
default unwind strategy), and confirmed zero production code touched repo-wide.

`test-engineer` — **PASS**, no blocking gaps. Independently mutation-tested the reconciliation claim (two
separate injected bugs, both caught). Found and empirically verified-safe the `Esc`-during-`RunDoctor`
untested path above. Confirmed `PathGuard`/`EnvGuard` isolation has no cross-test flakiness risk (20
repeated runs at `--test-threads=8`, all clean).

### Definition of Done
