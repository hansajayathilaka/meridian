# 10.6 — `mrd.file/1` `StreamType` implementation

**Phase:** 10 — File Transfer Stream · **Feature:** T09 · **Depends on:** 10.3, 10.4, 10.5 ·
**Status:** pending

## Goal
Implement the `StreamType` trait for `mrd.file/1` and register it — the point in the phase where file
transfer becomes a real, registered stream type against the now-complete substrate (task 10.4), with
**zero diffs to any core crate**. This is the literal acceptance bar
`docs/architecture/features/09-file-transfer.md` states: "implemented purely as a stream type against
the T04 registry — no changes to core session code allowed. That constraint is the point."

## Scope
- **In:** `apps/streams/src/file.rs`: `FileStream` implementing `StreamType` — `name() = "mrd.file/1"`,
  `version() = 1`, `channel_cfg()` = reliable + unordered (`ChannelCfg { reliable: true, ordered: false,
  max_retransmits: None, .. }`, constructed directly since `ChannelCfg`'s fields are already `pub` — no
  transport-crate edit needed), `direction() = Bidir`, `mandatory() = false` (an unsupported peer simply
  can't receive files, never a session error), `on_open` — the recipient accept/reject policy hook
  (auto-accept images under a configurable size threshold, otherwise a decision the caller surfaces to
  the user/CLI/TUI to decide — this task defines the `PolicyCtx`-driven decision function; the actual UI
  prompt is 10.10/10.11's job), `on_frame` — inbound dispatch into per-transfer state (manifest receipt,
  chunk receipt handed to the receiver engine of task 10.8). Per-file key `k_f` generation (fresh random
  key per file) and sealing it under the ratchet in the manifest (via the existing chat/session
  encryption path, not a new mechanism) also land here.
- **Out:** the sender loop (10.7), the receiver loop / merkle verification wiring (10.8), resume (10.9),
  CLI/TUI surfaces (10.10/10.11). This task defines the `StreamType` shell and manifest send/seal; the
  engines that actually move bytes are separate tasks so each stays independently testable.

## Deliverables
1. `FileStream: StreamType` in `apps/streams/src/file.rs`, registered via `register_stream_type`.
2. Manifest send: generate `k_f`, build the CBOR manifest `{name, size, root, enc(k_f under ratchet)}`,
   send on `mrd.ctrl/1`'s `Open.params` (per `docs/architecture/system-design.md` §7.2 — the manifest
   rides in `Open`'s `params` field, not a separate ctrl frame).
3. `on_open` policy decision function + its own unit tests (auto-accept-below-threshold, prompt
   otherwise, first-contact interaction via `PolicyCtx::first_contact`).
4. Tests proving **zero diffs to `apps/core`, `apps/crypto`, `apps/transport`** in this task's own
   commit (the review gate; call this out explicitly in the PR description).

## Risks / notes
`PolicyCtx::first_contact` (from `apps/core/src/streams.rs`) must be honored the same way chat's
message-request gate is — a stranger sending a file before being accepted as a contact should not
silently write to disk. Confirm with the `anonymity-model` skill whether file transfer needs the same
gate chat has, or a stricter one (sensitive-type default per `stream-type-authoring` skill: "sensitive
types (tunnels, screenshare) default to prompt/allowlist, never auto-accept" — file transfer sits
between chat's auto-accept and tunnel's always-prompt; the size-threshold auto-accept for images only is
the spec's own compromise, confirm it composes correctly with first-contact).
