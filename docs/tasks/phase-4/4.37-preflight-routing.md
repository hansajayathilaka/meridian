# 4.37 — Preflight routing

**Phase:** 4 — Verification & Trust + Terminal TUI Client · **Feature:** T17 — Terminal TUI Client (gap closure) · **Depends on:** 4.29, 4.36 · **Status:** done

## Goal
`App::new`/`meridian_tui::run()` actually detects existing state and routes to `Unlock`/`Onboarding`/
`Screen::Main` instead of always starting on `Onboarding`; Onboarding's/Unlock's completion pushes
`Screen::Main` (dispatching `Effect::LoadSession` where needed) instead of `Screen::Placeholder`. This is
the `Preflight` step named in `docs/architecture/diagrams/tui-screen-flow.mermaid`
(`Preflight --> Unlock: account exists, file-backed store`) that has never existed in this crate.

## Scope
- **In:** a pure `preflight_route(account: Option<AccountDescriptor>) -> InitialRoute` decision function
  (testable without I/O) plus the minimal synchronous `AccountDescriptor::load()` check inside `run()`'s
  existing setup phase (which already does synchronous config I/O before constructing `App` — same
  precedent, not a new pattern). Rewire the `Onboarding`/`Unlock` `finished` arms in
  `App::handle_key`/`handle_worker`.
- **Out:** the `run_worker` execution of `LoadSession` itself (4.29 already built it); `Screen::Main`'s
  own content (4.36 already built it).

## Deliverables
1. `preflight_route` (pure decision function).
2. Updated `App::new`/`run()`.
3. Updated `Onboarding`/`Unlock` completion-transition arms.
4. Tests covering: no `account.json` → Onboarding (regression, unchanged from today); file-backed
   existing account → Unlock; OS-keystore existing account → straight to Main via `Effect::LoadSession`;
   a wrong passphrase at Unlock retries in place per `tui-client.md` §7 (no lockout invented — this
   crate has never had one and must not gain one silently here).

## Risks / notes
- Not hard-blocked on 4.30's/4.35's completion for its own unit tests, though the full T17 demo needs
  those too — 4.38 owns confirming the whole assembled path.
- Depends on 4.29 (`Effect::LoadSession`) and 4.36 (`Screen::Main` to route to).
- **Escalated by 4.31's own review — a residual gap this task does not by itself close.** `run_worker`'s
  contacts/contact-detail effect handlers (4.31) and trust/request-queue handlers (4.32) each re-derive a
  fresh `SecretStore`/`TrustStore` from disk on every single dispatch (`worker.rs::open_account_store`),
  since at build time neither task had a live, already-unlocked session to reuse. For an OS-keystore
  account this is harmless (no secret needed to re-open it). **For a file-backed (passphrase-keyfile)
  account, `open_account_store` fails closed today with an actionable error** — there is no cached,
  already-unwrapped store anywhere for it to use. Once this task lands, `App` *will* hold exactly that
  (a `LiveSession` produced by `Effect::Unlock`'s extended outcome, per task 4.29) — but nothing
  automatically threads it into 4.31/4.32's already-built handlers; they would need to be revisited to
  accept an optional pre-unwrapped store/handle rather than always re-deriving one. **This task's own
  scope should NOT silently absorb that rewiring** (it's a second, separable concern — this task is
  entry-point routing, not a `run_worker`-internal refactor) **but must not silently ignore it either**:
  if not otherwise scheduled by the time this task lands, either (a) file a new follow-up task
  (`4.39` or into whatever phase follows) to thread the cached store through 4.31/4.32's handlers, or
  (b) confirm with 4.38 that this is explicitly, visibly carried forward (not silently shipped) if it
  remains unresolved — 4.38's own scope is verification/doc-reconciliation only, so it cannot fix this
  itself, only surface it honestly the way 4.28 surfaced the original T17 gap. Do not let this evaporate.

## Status
Done. `meridian-tui` now detects an existing account and routes to `Unlock`/straight-to-`Main`/
`Onboarding` at startup, and onboarding's/unlock's own completion pushes the real `Screen::Main`
(dispatching the right effect first) instead of `Screen::Placeholder` forever.

**`apps/tui/src/preflight.rs` (new file).** `preflight_route(account: Option<AccountDescriptor>) ->
InitialRoute` — the pure decision function (Deliverable 1): `None` → `InitialRoute::Onboarding`;
`Some(file-backed)` → `InitialRoute::Unlock(Box<UnlockState>)` (built via `UnlockState::new`, itself
pure — no I/O); `Some(OS-keystore)` → `InitialRoute::LoadSession`. Defensive fallbacks (never panics)
for a hand-corrupted file-backed descriptor: an absent `keyfile` falls back to an empty `PathBuf`, a
malformed `pubkey`/`hint` combination that can't build an `mrd1:` id falls back to the raw hex pubkey
for display — both surfaced as an actionable error downstream (`Effect::Unlock`'s own worker-side
execution) rather than here. `InitialRoute::into_screen_and_effects()` turns the decision into the
concrete `(Screen, Vec<Effect>)` `App::new_with_route` applies — `Onboarding`/`Unlock(state)` need no
effect; `LoadSession` starts on `Screen::Placeholder` (the "loading, briefly" interim screen) with one
`Effect::LoadSession` queued. 9 unit tests in this file's own `#[cfg(test)]` module cover the pure
decision and the screen/effect conversion in isolation, no `$MERIDIAN_HOME` touched anywhere.

**`apps/tui/src/lib.rs::run()` (Deliverable 2).** Added `load_existing_account() -> io::Result<Option
<AccountDescriptor>>`: checks `account::config_dir()?.join("account.json").exists()` directly first
(mirrors `worker::run_load_session`'s own "never conflate not-found with corrupt" discipline) — a
missing file is `Ok(None)`, a present-but-corrupt one is a hard `io::Error` (same "fail closed on a
malformed file, default/absent on a missing one" contract `load_config` right above it already
established for `config.toml` — one more synchronous setup-phase read, not a new pattern).
`run()` now calls this, feeds the result through `preflight::preflight_route`, and constructs the app
via the new `App::new_with_route(config, route)` (below) instead of `App::new_with_config(config)`;
the route's own initial `Vec<Effect>` is sent down `effect_tx` right after the worker task spawns, so
`Effect::LoadSession` (OS-keystore route) reaches the worker exactly like every later effect
`App::update` returns.

**`apps/tui/src/app.rs` (Deliverable 2/3).**
- `App::new_with_route(config, route) -> (Self, Vec<Effect>)` — builds via the existing, still I/O-free
  `App::new_with_config` and then overwrites the root screen from `route.into_screen_and_effects()`.
  **`App::new`/`App::new_with_config` are deliberately unchanged** (still always `Screen::Onboarding`,
  still zero I/O) — the dozens of pre-existing tests across this crate that construct an `App` this way
  with no `account.json` of their own to check keep working unchanged; `crate::run` is the one real
  caller of the new constructor.
- **Onboarding-finished arm (`App::handle_key`).** `onboarding::handle_key`'s `Success` arm never
  mutates `*state` on `finished = true` (confirmed by reading that function), so the arm now reads
  `Success::store` (see below) before overwriting the screen, and builds:
  - `StoreChoice::Os` → `Effect::LoadSession` + `Screen::Placeholder` (same "loading, briefly" role
    `Preflight`'s own OS-keystore route uses — one shared completion handler covers both origins, see
    below).
  - `StoreChoice::File { passphrase }` → `Effect::Unlock` (reusing the passphrase already typed at
    `ChooseStore`, never re-prompting) + `Screen::Unlock(UnlockState::Unlocking { .. })` — reuses
    `Screen::Unlock`'s own existing "please wait" sub-state as the interim screen rather than inventing
    a new one, so `App::handle_worker`'s `Screen::Unlock` arm (already being updated by this same task
    to reclaim a `SessionOutcome` — see below) is the *only* place that reclaim logic lives, for either
    origin (a returning user, or a freshly onboarded one). `keyfile` comes from
    `worker::default_keyfile_path()` (bumped from private to `pub(crate)` — a visibility-only change,
    zero behavior change — so `app.rs` reuses the exact same `"account.key"` path-join `worker.rs`'s
    own `GenerateAccount` execution used a moment earlier, instead of re-deriving a second copy of that
    literal that could silently drift).
  - Defensive `let ... else` fallback to the pre-4.37 bare `Screen::Placeholder` if `state` is ever
    something other than `Success` when `finished` is true (unreachable per `onboarding::handle_key`'s
    own contract, but never a panic).
- **`App::handle_worker`'s `Screen::Unlock` arm** now reclaims the `SessionOutcome` a successful
  `Effect::Unlock` carries *before* falling through to `unlock::handle_worker` (resolving task 4.29's
  own "Known gap, flagged for 4.36/4.37, Finding 3" note) — `Completed(Effect::Unlock(effect))` is
  matched directly and builds `Screen::Main(Box::new(MainState::from_session(session)))` from
  `effect.outcome.into_option()`; a defensive `None` (only ever reachable from a hand-constructed test
  event with an empty outcome, never a real worker) falls back to `Screen::Placeholder`.
  `Failed`/irrelevant events still delegate to `unlock::handle_worker` unchanged — retry-in-place,
  attempt count, **no lockout** (Deliverable 4d).
- **New top-level `Effect::LoadSession` interception in `App::handle_worker`**, ahead of any per-screen
  dispatch — no single screen "owns" this effect (it's dispatched from two different, screen-agnostic
  origins: `Preflight`'s own startup route, and the Onboarding-finished arm's OS-keystore branch), so
  matching on the *event* first is the one dispatch point covering both without duplicating logic.
  `Completed` → `App::apply_load_session_outcome` (new method): `Loaded(session)` → `Screen::Main`;
  a defensive `None`/`NoAccount` (should not be reachable in a real run — see the `TODO: confirm` below)
  falls back to `Screen::Placeholder`/`Screen::Onboarding` respectively rather than a hard panic.
- Two new App-level tests cover both onboarding-finish branches
  (`onboarding_success_enter_for_an_os_keystore_account_dispatches_load_session`,
  `onboarding_success_enter_for_a_file_backed_account_dispatches_unlock`); the pre-existing
  `unlock_screen_completes_to_placeholder_on_worker_success` was split into
  `unlock_screen_worker_completion_with_an_empty_outcome_falls_back_to_placeholder` (the defensive
  fallback the old test's hand-built empty-outcome effect actually exercised, renamed for honesty) and
  a new `unlock_screen_completes_to_main_on_worker_success_with_a_real_session` (the real success path,
  with a populated `SessionOutcome`).

**`TODO: confirm` raised, not resolved (design silence, not this task's to invent).**
`App::handle_worker`'s new top-level `Effect::LoadSession` arm has no defined behavior for a *genuine*
failure (`WorkerEvent::Failed(Effect::LoadSession(_), _)`) — e.g. a corrupt `trust.bin`/`sessions.bin`
for an OS-keystore account, or a keystore that became unavailable between `Preflight`'s own synchronous
check and the worker's async read. `docs/architecture/tui-client.md §7`'s own table has no row for this

generated over data that merely failed to *load*). Left on `Screen::Placeholder` (no more/less visible
than today's pre-existing "stuck on Generating" gap; `Ctrl+Q` still quits cleanly) rather than inventing
a new error screen, which is real screen content outside this task's own "routing, not screen content"
scope. Flagged in the code (`app.rs::handle_worker`'s own comment) and here, not silently absorbed.

One non-blocking nit was raised and fixed before closing: `apply_load_session_outcome`
(`apps/tui/src/app.rs`) unconditionally overwrote `self.screens.last_mut()` on a completed
