# 4.1 — ADR 0020: TUI packaging

**Phase:** 4 — Verification & Trust + Terminal TUI Client · **Feature:** T17 — Terminal TUI Client · **Depends on:** — · **Status:** pending

## Goal
Ratify, as a binding ADR, how the terminal client is packaged: a new crate, its entry point, and its
feature-gating — so every subsequent T17 task builds against a settled shape instead of improvising one.

## Scope
- **In:** ADR 0020 deciding (a) a new `apps/tui` crate (`meridian-tui`) owning all ratatui/crossterm
  code; (b) a thin `meridian tui` subcommand in `meridian-cli` behind a default-on `tui` feature, so
  `--no-default-features` builds (used by demo/CI) stay lean; (c) the dependency direction —
  `meridian-cli` depends on `meridian-tui`, `meridian-tui` depends on `meridian-core` only, never on
  `meridian-cli` (no cycle). Record the two rejected alternatives from
  [tui-client.md §1](../../architecture/tui-client.md#1-shape-of-the-thing): a standalone
  `meridian-tui` binary, and folding the TUI directly into `meridian-cli`.
- **Out:** the store/config formats (4.2); any code.

## Deliverables
1. `docs/adr/0020-tui-packaging.md` — status `Accepted`, options considered, decision, binding
   conditions, residual risks.
2. `docs/adr/README.md` — index entry.

## Risks / notes
- The dependency direction matters for 4.13 (extracting `$MERIDIAN_HOME`/`AccountDescriptor` helpers
  into `meridian-core`) — get it right here so 4.13 isn't retrofitted.
- `tui-client.md §1`'s table is the recorded intent this ADR ratifies; deviate only with a stated reason.
