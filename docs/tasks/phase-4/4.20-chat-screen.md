# 4.20 — Chat / conversation screen

**Phase:** 4 — Verification & Trust + Terminal TUI Client · **Feature:** T17 — Terminal TUI Client · **Depends on:** 4.4, 4.15, 4.19 · **Status:** done

## Goal
Land the main conversation experience: scrollback, composer, delivery state, restart-persistent
history — gated by T08's send rules so a blocked contact cannot be messaged from this screen either.

## Scope
- **In:** conversation pane with scrollback, multi-line composer, per-message delivery state, unread
  markers, restart-persistent history via 4.15's store, local dedup by `mid`. Composer consults 4.4's
  `can_send` gate before every send — `Blocked`/`Warn` states surface here even though the modal UI
  itself is 4.22's. Failure copy for an offline peer (pre-T07) must say "not delivered — offline" and a
  retry action, **never** "will deliver later" ([tui-client.md §7](../../architecture/tui-client.md#7-what-the-user-sees-when-things-go-wrong)).
- **Out:** the Verify screen and its modals (4.22); message-request queue (4.21).

## Deliverables
1. `apps/tui/src/screens/chat.rs`.
2. Screen-snapshot tests; a test asserting a `Blocked` contact's composer refuses to enqueue a send
   (defense in depth alongside 4.4's own gate test — this one is UI-level); a test asserting no
   "delivered when they come online" language appears anywhere in failure copy.

## Tests
`cargo nextest run -p meridian-tui --test screens_chat`

## Reviews
- **security-reviewer** — required; this is where 4.4's send-gate actually gets wired into the UI a
  human uses, and where a "make sending less annoying" regression would first appear.

## Status
Done. `apps/tui/src/screens/chat.rs` is the main conversation screen: scrollback, multi-line composer,
per-message delivery state, unread markers, restart-persistent history via task 4.15's sealed store,
local dedup by `mid`, and — the task's headline requirement — the composer consults
`meridian_core::trust::TrustStore::can_send` before every send, via a single `dispatch_gated_send`
choke point every send/retry/acknowledge path funnels through. `mrd.chat/1` renders through task 4.18's
own `MessageRenderer` extension registry, as that task anticipated. `Screen::Chat` is added but
deliberately not yet wired into navigation from the Contacts pane — that's left to a later task,
consistent with the `Screen::Placeholder`/`Screen::Unlock` precedent of landing a screen before its
entry point exists.

**Review (security-reviewer, sole required reviewer — this is where 4.4's send-gate meets the UI a
human uses):** two real Medium findings, one Low, all fixed and re-confirmed:
- **Cross-conversation worker-event contamination.** `handle_worker` accepted a `SendMessage`
  completion/failure for *any* peer, not just the screen's own — always persisting into `state
  .peer_pubkey`'s history regardless of which peer's request actually completed, and unconditionally
  clearing the in-flight-send guard. Latent today (unreachable pending navigation wiring) but would
  have let a stale send resolution from one conversation silently write into a different, currently-open
  conversation's transcript and sealed history once reachable. Fixed with a `request.peer_pubkey ==
  state.peer_pubkey` guard; the module's own doc comment, which had overclaimed this protection before
  it existed, now accurately describes it.
- **Hostile-hint injection into failure copy.** `offline_failure_copy` sourced its label via
  `peer_label()`, which falls back to `contact.hint` — wire-populated, attacker-influenced, never
  content-validated (per `trust.rs`'s own threat-model invariant, unlike `petname`, which is
  structurally never wire-derived) — so a malicious peer/signaling server could inject
  store-and-forward-implying text directly into the exact copy this task's own dedicated tests exist to
  police, and those tests only ever exercised benign fixed inputs. Fixed with a new
  `failure_copy_label()` used only for this security-sensitive copy (petname or truncated-pubkey,
  never `hint`); the composer/header title's own use of `peer_label()` was left untouched as an
  explicitly-scoped, reviewer-confirmed-reasonable decision (a "who you're talking to" label, never
  delivery-status copy).
- **Low, fixed anyway:** a second worker report for an already-recorded `mid` with a different outcome
  could leave `failure_reasons` out of sync with the displayed entry state; gated the mutation on
  `insert_deduped`'s real return value.

**One Low/informational residual, explicitly non-blocking, flagged for whoever wires `Screen::Chat`
into real navigation:** the peer-pubkey-only correlation closes cross-*peer* contamination but not a
narrower same-peer case — if a screen instance is torn down (`Esc`) with a send still in flight and a
fresh instance for the *same* peer is opened and sends again before the original resolves, the stale
completion would still clear the new instance's in-flight guard (a UI-guard inconsistency, not a
content/key/metadata exposure). Cheap fix when picked up: also correlate on the in-flight request's
body (or a real request id, once one exists), mirroring `worker_event_for_a_different_peer_is_silently_ignored`'s
test shape with a same-peer/different-body case.

`cargo test -p meridian-tui` (`screens_chat.rs` grew from 35 to 38 tests during review), `cargo test -p
meridian-cli --bins`, `cargo fmt --check`, `cargo clippy --workspace --all-targets -- -D warnings`, and
`bash tools/lint-tui-no-cli.sh` all clean.
