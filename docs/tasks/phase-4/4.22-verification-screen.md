# 4.22 — Verification screen

**Phase:** 4 — Verification & Trust + Terminal TUI Client · **Feature:** T17 — Terminal TUI Client · **Depends on:** 4.4, 4.5, 4.19, 4.20 · **Status:** done

## Goal
Land the phase's central security-critical screen: 60-digit safety number + QR side by side,
mark-verified, block, and the two un-softenable key-change modals — consuming T08's real trust module
and send gate directly, never reimplementing them.

## Scope
- **In:** side-by-side safety-number + QR display (via 4.5's `meridian verify` primitives), mark-
  verified, block actions; `KeyChangeBlocked` modal (verified contact — hard stop, composer disabled,
  only Verify/Block actions, no "trust anyway"); `KeyChangeWarning` modal (pinned contact — must be
  acknowledged, Verify as primary action). Wording preserves
  [verification-ux.md](../../security/verification-ux.md)'s canonical intent verbatim in meaning — no
  screen may paraphrase it into reassurance. Both modals consume 4.4's `SendGate` directly.
- **Out:** any new trust-state logic — this screen is presentation over 4.3/4.4/4.5, not a parallel
  implementation. If this task seems to need new trust logic, that's a defect: the logic belongs in
  4.3/4.4, not here.

## Deliverables
1. `apps/tui/src/screens/verify.rs` + the two modal components.
2. Screen-snapshot tests whose checked-in text includes the canonical warning copy verbatim — these
   catch softened wording as a snapshot diff, not just a manual read.
3. Test: no dismiss-without-verify path exists from either modal (exhaustive action enumeration, not a
   sampled check).

## Status
Done. `apps/tui/src/screens/verify.rs` is the phase's central security-critical screen: 60-digit safety
number + QR side by side, mark-verified, block, and the two un-softenable key-change modals. Modal
selection is a pure, uncached `TrustStore::can_send` match — `Blocked` → hard stop, Verify/Block only;
`Warn` → Verify (primary)/Acknowledge/Block — never a screen-local reconstruction of the block/warn
decision. Both modals render `SendGate`'s own carried `blocked_reason`/`warn_reason` strings verbatim,
never re-derived. Two exhaustive sweep tests (~3,700 keycode × modifier × mode combinations each) prove
no key sequence clears `Blocked`/`PinnedKeyChanged` except the legitimate confirmed path.

**Review (security-reviewer, sole required reviewer — explicitly "the phase's central security-critical
screen... softening is blocking, not a style note"):** one round of real findings, all fixed and
re-confirmed clean:
- **Critical:** the banner's own anti-truncation fix was defeated by its own layout clamp — the region
  reserved for the canonical warning text was re-capped to guarantee the number/QR pane 3 rows, at the
  direct expense of clipping the security banner at short terminal heights (a resize the client never
  re-checks mid-session). The clipped tail would drop the interception-possibility clause and the
  Verify/Block instruction while leaving the benign "reinstalled or switched devices" explanation
  visible — a hard-prohibition violation produced by rendering, not wording. Fixed by removing the
  artificial cap: the banner always gets the full height its content needs, and the number/QR pane
  absorbs whatever space is left, shrinking first. A regression test at 80×12 (verified to genuinely
  fail against the pre-fix clamp) now pins this.
- **Medium:** the `Blocked` banner header was hardcoded to "KEY CHANGE — SENDS BLOCKED" for every
  blocked cause, including a purely local, user-initiated block (task 4.6) — falsely implying a
  key-change/interception incident for a routine local block. Fixed to derive the header from the live
  `user_blocked` flag, matching whichever reason text actually renders beneath it.
- **Medium:** the module doc overclaimed that every action reverts to a "safer-or-equal" trust state on
  an unpersisted crash; `Block`'s false→true direction is a genuine fail-open exception (a crash before
  the persist effect lands silently reverts to unblocked), inherited from the shared local-apply-then-
  persist-later pattern this screen shares with `contact_detail.rs`. Fixed by correcting the doc to
  disclose the asymmetry rather than overclaiming; closing the underlying gap is out of this task's
  scope.

**Non-blocking note carried to task 4.26 (terminal-constraint degradation):** at heights shorter than
the banner content itself needs, the fix's `.min(area.height)` still clips — an unavoidable physical
floor, not a defect of this fix. 4.26's current deliverables (narrow-width collapse, `NO_COLOR`, ASCII
fallback) don't yet name "banner taller than the terminal"; worth that task considering a minimum-height
guard or scrollable banner content for the extreme case.

`cargo test -p meridian-tui` (`screens_verify.rs` grew from 25 to 27 tests during review), `cargo test
-p meridian-cli --bins`, `cargo fmt --check`, `cargo clippy --workspace --all-targets -- -D warnings`,
and `bash tools/lint-tui-no-cli.sh` all clean. `Screen::Verify` is wired into `App`'s dispatch but not
yet reachable from live navigation — `contacts.rs`'s `v` key still shows its 4.19-era placeholder,
deferred to a future navigation-wiring task, consistent with 4.19–4.21's precedent.
