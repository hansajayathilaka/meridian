# 12.4 — `meridian-signaling` WebSocket transport seam

**Phase:** 12 — Browser & Desktop Clients · **Feature:** T11 (substrate completion, not the feature
itself) · **Depends on:** 12.1 · **Status:** done

**User surface:** none — internal substrate seam, no user-visible behavior change on the native path.
No TUI surface applies.

## Goal
Close the second half of the wasm32-buildability gap the architect consult found (see
[phase-12/README.md](./README.md#architect-consult-substratestoresigning-decisions-settled-before-task-breakdown)
point 3): `meridian-signaling`'s `SignalingClient` hardcodes `WebSocketStream<MaybeTlsStream<TcpStream>>`
(via `tokio-tungstenite`), which has no `wasm32-unknown-unknown` story at all. Introduce a small internal
trait so a browser build can swap in the browser's native `WebSocket` (via `web-sys`/
`wasm-bindgen-futures`) while native builds keep `tokio-tungstenite` byte-for-byte unchanged. This is
**not** one of the two frozen `core-api-contracts.md` traits (`Transport`/`SecretStore`) — it is an
internal implementation seam local to `meridian-signaling`, so it raises no stability-policy question.
Passing `cargo check -p meridian-signaling -p meridian-core --target wasm32-unknown-unknown` here is
what finally proves the full `meridian-core` wasm32 build green, closing the arc 12.1 started.

**This finding and its fix shape were settled by an architect consult during `/plan-phase`** — this task
file implements that decision, it does not re-open it.

## Scope
- **In:** a new internal `WsConnection`-style trait inside `meridian-signaling`; `SignalingClient`
  refactored to use it instead of the hardcoded stream type, with an unchanged public API; a native impl
  wrapping the existing `tokio-tungstenite` stream unchanged (byte-identical handshake/wire behavior —
  no conformance-vector changes); a `wasm32` impl wrapping the browser's native `WebSocket` via
  `web-sys`/`wasm-bindgen-futures`; `Cargo.toml`'s `[target.'cfg(target_arch = "wasm32")'.dependencies]`
  split (drops `tokio-tungstenite`/`rustls` there, adds `wasm-bindgen`/`web-sys` for that target only).
- **Out:** any browser-UI-specific reconnect/backoff policy beyond what `SignalingClient` already does
  natively; the browser `Transport` shim (12.11, a separate trait entirely); any change to the WSS wire
  handshake itself.

## Deliverables
1. `apps/signaling/src/ws_transport.rs` — the `WsConnection` trait + native/wasm impls.
2. `apps/signaling/Cargo.toml` — target-conditional dependency split.
3. `SignalingClient` refactored onto the trait, public API unchanged.
4. `cargo check -p meridian-signaling -p meridian-core --target wasm32-unknown-unknown` passing (new
   `just`/CI step, extends 12.1's).
5. **Carried in from 12.1's review:** `apps/core/src/session.rs` still calls `std::time::Instant::now()`
   at three sites (`start` in the ICE-restart path, `attempt_start` in `dial` and `answer`;
   `apps/streams/src/sender.rs` has a fourth). They compile on wasm32 but panic at runtime there.
   Route them through a wall-clock-safe shim (e.g. `wasmtimer::std::Instant` on wasm32 via
   `crate::timer`) — mind that tokio's `Instant` follows a paused test clock, so decide per site
   whether the native path should keep `std::time::Instant`. If any site is deliberately left, say so
   in the Outcome.

## Outcome
`cargo check -p meridian-signaling -p meridian-core --target wasm32-unknown-unknown` passes — `meridian-core`
now builds for wasm32 for the first time, closing the arc 12.1 started (also clippy `-D warnings` on that
target). `just check-wasm32` and the CI lint step cover all eight crates.

**What landed.** `apps/signaling/src/ws_transport.rs`: an internal `pub(crate) trait WsConnection`
(`connect`/`send_binary`/`recv`/`close`), a native impl wrapping the unchanged `tokio-tungstenite` stream,
a wasm32 `BrowserWs` over `web_sys::WebSocket` (callbacks feed a channel, so `wasm-bindgen-futures` was not
needed), and a cfg `PlatformWs` alias (no `dyn`, so native keeps its exact `Send` behaviour). `SignalingClient`
is on the trait with an unchanged public API; native `connect`, the test-CA helper, TLS config, size limits
and close/error mapping were diffed and are unchanged (`cargo test -p meridian-cli --test wss_tls`, a real
TLS handshake, still passes). `Cargo.toml`: native-only table keeps the former tokio feature set plus
`tokio-tungstenite`/`rustls`; the wasm32 table adds `wasm-bindgen`, `js-sys`, `web-sys`, `send_wrapper`
(all MIT/Apache-2.0, in `deny.toml`'s allow-list by reading it — `cargo deny` not installed here).

**Real error set vs. the task's enumeration.** Beyond `mio`/`tokio-tungstenite`, `meridian-core`'s
`SignalRelay: Send` failed (12 errors): the browser's `WebSocket`/`Closure` handles are `!Send`.

**On-the-fly decision (for ratification; no ADR judged needed):** keep the JS handles in a
`send_wrapper::SendWrapper` (sound on wasm32's single thread: panics on foreign-thread deref, leaks on
foreign-thread drop; the channel receiver sits outside the wrapper) rather than relaxing the internal
`SignalRelay` to `?Send`. No frozen contract (`Transport`/`SecretStore`) was touched. 12.11 faces the same
question for `Transport` — guidance recorded in its Risks/notes.

**Deliverable 5 (`Instant` sites).** `apps/core/src/timer.rs` gained `WallInstant` (native = `std::time::Instant`,
wasm32 = `wasmtimer::std::Instant`); the three `session.rs` sites use it. Native deliberately keeps std's
`Instant` there, since those sites report real elapsed time and tokio's would turn them into virtual time
under `start_paused` tests. The fourth site, `apps/streams/src/sender.rs`, is **deliberately left**:
`meridian-streams` depends on core and cannot reach its `pub(crate)` seam; it must be routed when streams
goes to wasm32 (owner recorded in 12.9's notes).

**Security review fixes.** The combined review (architecture PASS, security PASS, correctness PASS, no
blockers) raised a memory-DoS surface: `BrowserWs`' receive channel was unbounded with no size cap, unlike
native's tungstenite caps/TCP backpressure. Fixed: a pure `recv_budget` policy (1 MiB per message, 4 MiB /
256 messages queued; `TODO: confirm` the cap against the server's largest real routed envelope), size read
*before* copying out of the JS heap, fail-closed (one terminal error + `close()`) on overflow, with five
native unit tests on the policy. `js_err` no longer embeds the raw `JsValue` (a `SyntaxError` can embed
the URL). A wasm32-only compile-time `Send` assertion on `PlatformWs`/`SignalingClient` and their futures
caught a real latent defect on its first run (`BrowserWs::connect` held `Closure` locals across an
`.await`) — fixed by moving setup into a synchronous `open_socket`.

**Open items, owned elsewhere (stated, not claimed away):**
- **No headless-browser WebSocket harness** (the task's `TODO: confirm`, resolved as deferred): wasm32
  coverage is `cargo check` + clippy + the `Send` assertion only. `BrowserWs` — open, binary frames,
  close, error, drop, and the overflow-close wiring — has **never run in a browser**; 12.13's adapter tests
  are the first place it can.
- Inline signing on wasm32 (no `spawn_blocking`): safe only if the browser `SecretStore`'s `sign` never needs
  a multi-second KDF — `TODO: confirm` carried into 12.5.
- Plaintext `ws://` is allowed on native and browser alike (threat-model A3 lists TLS downgrade; not a
  regression) — wss-only policy for the browser build carried into 12.12/12.13. Browser `connect` has no
  internal timeout — carried into 12.13.
- Browser `send_binary` applies no `bufferedAmount` backpressure (fine for small request/response frames).

didn't change native behavior); `cargo check -p meridian-signaling -p meridian-core --target
wasm32-unknown-unknown` (new).
