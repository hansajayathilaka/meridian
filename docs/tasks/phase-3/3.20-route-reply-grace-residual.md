# 3.20 — Resolve the `ROUTE_REPLY_GRACE` false-positive-success residual

**Phase:** 3 — Review of Phase 2 · **Feature:** review fix (report §"On-the-fly decisions to ratify") · **Depends on:** 3.3, 3.7 · **Status:** pending

## Goal
Turn an unratified 500 ms heuristic — which converts a lost `FedErr` into a *false delivery
confirmation* to the user — into either a measured, documented bound or a reopened protocol decision.

## Scope
- **In:** measure the real reply-RTT distribution over an established link (a bench/harness, **not a
  guess**); then either (a) tighten/justify the constant with the measurement recorded in the doc
  comment and `federation-protocol-v1.md`, or (b) write an ADR reopening the "do not add a
  `FedRouteOk`" wire decision. Plus the missing boundary test.
- **Out:** unilaterally adding `FedRouteOk` to the wire without an ADR — explicitly forbidden by the
  current protocol doc.

## Deliverables
1. The measurement, recorded in the task Outcome.
2. Either the tightened constant + doc-sync, **or** `docs/adr/0020-*.md`.
3. `apps/rendezvous/tests/federation_route.rs` — a `FedErr` delayed just past the window is
   observably a false success today (pinning the residual) or is caught (if fixed).

## Risks / notes
- A false delivery confirmation is a **correctness claim made to the user**, not merely an internal
  imprecision — that is why this outranks its "nit-adjacent" appearance.
- Depends on 3.3 (the timeout framework) and 3.7 (link reuse changes the RTT profile the measurement
  must be taken against) — measuring before those land would measure the wrong system.
- `outbound.rs:257`'s comment records this as "left as a follow-up, not resolved by this task"; this
  task is that follow-up, so the comment must stop pointing at nothing.
