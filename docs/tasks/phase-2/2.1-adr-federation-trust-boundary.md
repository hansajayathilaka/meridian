# 2.1 — ADR 0017: federation trust boundary (peer auth + cross-org `from` attestation)

**Phase:** 2 — Cross-Org Federation · **Feature:** T06 — Cross-Org Federation · **Depends on:** 1.32 · **Status:** done

## Goal
Decide, and record as a binding ADR, **what the receiving server is entitled to believe** about a
federated request: which name the peer certificate must authenticate, and who attests the origin
account (`from`) across the trust boundary. Nothing that shapes s2s bytes may be written before this
lands — retrofitting provenance into a published `federation-protocol-v1` is a wire break with
conformance vectors already generated.

## Scope
- **In:** ADR 0017 covering (a) peer-certificate identity — which name must appear in the peer cert,
  the `@hint` domain from the ID or the SRV target host, in **both** WebPKI and private-CA modes, and
  how an operator pins a partner; (b) cross-org `from` attestation — whether `fed_route` carries an
  origin account at all, and what server B may assert in the `Deliver` it pushes to Bob; (c) what
  constitutes "origin server identity" for the federation-edge rate limits. It must explicitly
  **scope-correct [ADR 0016](../../adr/0016-envelope-deniability.md) residual R4**, whose "the routing
  `from` is taken from the authenticated WebSocket session" is true single-hop and **false federated**,
  and state that DNS SRV is a *discovery* mechanism only, never an identity authority
  ([ADR 0001](../../adr/0001-identity-scheme.md)).
  Also in: flip [ADRs 0001–0008](../../adr/README.md) from `Proposed` to `Accepted` — this phase rests
  on 0002, and ADR 0017 must not inherit a `Proposed` parent.
- **Out:** The wire contract itself (2.2), the c2s extension (2.3), and every behavioural task
  (2.4–2.12). No code changes at all.

## Risks / notes
- **The forcing problem.** `Deliver { from: bstr[32], blob }`
  ([rendezvous-protocol-v1 §4](../../api/rendezvous-protocol-v1.md)) is required by the client —
  `apps/core/src/chat.rs` hard-rejects `envelope.sender_pub != from` with `SenderMismatch`. But
  [wire-protocol.md §4](../../api/wire-protocol.md)'s `fed_route{to, envelope}` carries **no** `from`,
  and server B cannot derive one: the envelope is opaque to it, and decoding it would require
  `meridian-envelope`, which the server must never depend on. As specified, the forwarding path is
  **not implementable**. This ADR must resolve it.
- A third divergent shape exists: [wire-protocol.md §2](../../api/wire-protocol.md) lists
  `deliver {from_server, blob}` — a different field from the implemented `Deliver{from}`. Name which
  is canonical; the reconciliation edit itself belongs to 2.2/2.3.
- **Private-CA impersonation is the whole air-gap trust model.** If the peer cert is not pinned to the
  domain that was *intended* to be dialled, any cert issued by the federation-private CA impersonates
  any org.
- `TODO: confirm` is not acceptable in this task's output for (a), (b) or (c) — resolving them is the
  task. `TODO: confirm` elsewhere in the ADR is fine.

## Status

**Done.** [ADR 0017](../../adr/0017-federation-trust-boundary.md) resolves all three forced questions:

- **(a) Peer-cert identity** — verification target is the hint/discovery domain, never the literal SRV
  target hostname, in both WebPKI and private-CA modes; `federation_map.toml` entries must carry an
  explicit pinned identity (SAN/CN) per partner, with a missing/malformed pin treated as a fail-closed
  config error (C4, added per security review — see below).
- **(b) Cross-org `from` attestation** — `fed_route` gains a server-asserted `from: bstr[32]` field
  (C1/C2), resolving the forcing problem (the federated path was not implementable as specified).
  Framed as the same "server testimony" trust category ADR 0016 R4 already accepts, extended one hop;
  bounded because the client-side `SenderMismatch` check still holds cross-hop, so a malicious origin
  server can misattribute only among its own accounts, never forge one it doesn't control.
- **(c) Rate-limit identity** — origin server keyed to the cryptographic mTLS peer identity, origin
  account keyed to the asserted `from` (explicitly documented as testimony, not a guarantee, bounded by
  the per-server ceiling).

Also landed: [ADR 0016](../../adr/0016-envelope-deniability.md) R4 scope-corrected to single-hop with a
pointer to ADR 0017 for the federated case; [ADRs 0001–0008](../../adr/README.md) flipped
`Proposed` → `Accepted` (status-line only).

- **security-reviewer** — ✅ APPROVE-WITH-CHANGES, both required changes applied:
  1. **C4** now states a missing/malformed pinned identity in a `federation_map.toml` entry is a
     fail-closed config error, never a silent fallback to "chains to the trusted CA" with no name
     check (that fallback would reopen the exact impersonation hole this ADR exists to close).
  2. **New C7** requires s2s mTLS to terminate **in-process**, never at a proxy/VIP upstream of the
     server — otherwise (a)'s peer-identity guarantee is void, since an unauthenticated hop between
     "whatever terminated TLS" and the server could assert any peer identity. This resolves task
     [2.4](./2.4-s2s-mtls-link.md)'s open `TODO: confirm` on termination point (updated to point here)
     and is recorded as a deliberate departure from [ADR 0008](../../adr/0008-infra-topology.md)'s
     proxy/VIP termination for c2s (safe there only because c2s identity comes from the post-TLS `Auth`
     signature, a second factor s2s does not have).
