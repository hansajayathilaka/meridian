# 5.3 — Fix `contacts.json` trust staleness + cover `export_json`

**Phase:** 5 — Review of Phase 4 · **Feature:** review fix (F3) · **Depends on:** 5.4 · **Status:** done

## Goal
Make `--export-json` show a verified contact's real trust state. Today `run_mark_verified` only writes
`trust.bin`; `contacts.json`'s own `trust` field goes stale, and `export_json` never reads `trust.bin`
at all — so an exported dump reports `"trust": "pinned"` for a contact the live UI correctly shows as
"verified."

## Scope
- **In:** Either `apps/tui/src/worker.rs::run_mark_verified` (write-through the `trust` field into
  `contacts.json` on verify) **or** `apps/tui/src/store/export.rs::export_json` (join `trust.bin` the
  same way `apps/tui/src/screens/main.rs::build_contact_entries` already does for the live UI) — pick
  one; do not do both redundantly. Whichever is chosen, `export_json`'s zero existing test coverage
  (currently only its `chmod`-helper unit tests) must be closed.
- **Out:** Any change to `trust.bin`'s own on-disk format, or to the live in-memory join
  `build_contact_entries` already performs correctly.

## Deliverables
1. The chosen fix (write-through or export-time join) landed.
2. An integration test that first pins today's wrong output (documents the current bug precisely) then
   flips to asserting the correct value once the fix lands in the same PR — not a separate follow-up.
3. `export_json`'s document-mirroring logic gets real test coverage beyond the `chmod` helpers.

## Risks / notes
**Must land after 5.4** — both this task and 5.4 touch `run_mark_verified`'s body if the write-through
approach is chosen; land 5.4's `spawn_blocking` shape change first and rebase this task's smaller
addition on top, avoiding a simultaneous diff on the same function. If the export-time-join approach is
chosen instead (touching only `store/export.rs`), this ordering constraint relaxes, but land after 5.4
anyway to keep the review sequence simple and avoid re-deciding mid-phase.

## Status
**Done.** Fix approach chosen: **write-through**, not export-time join. `run_mark_verified`
(`apps/tui/src/worker.rs`) now reloads `contacts.json`, patches the matching row's `trust` field via the
existing `to_trust_label` helper (the same one `upsert_contact_record` already uses for the live-UI join,
confirmed no label/format mismatch), and saves — inside the same `spawn_blocking` closure task 5.4
already established, reusing the already-open store/handle rather than a second `decrypt_seed()` unwrap.
Mirrors `run_set_petname`'s existing shape for the `petname` field exactly. `export_json` itself and
`build_contact_entries`'s live-UI join were left untouched, per Scope.

**Bug-pinning test**: `run_worker_trust.rs`'s new test independently confirmed (by both the `reviewer`
pass and `test-engineer`, each reverting just the write-through and rerunning in isolation) to fail with
the exact wrong value the bug describes (`left: Pinned, right: Verified`) against pre-fix code, then pass
once restored — satisfying the task's explicit "pin then flip, same PR" requirement.

**`export_json` coverage gap closed**: three new tests in `apps/tui/tests/store.rs`
(`export_json_tests` module) exercise real sealed-store round trips — plaintext-matches-sealed-source,
skip-absent-but-always-write-state.json, and the empty-history-dir-with-no-`.jsonl`-files branch — closing
what was previously zero real coverage of the document-mirroring logic beyond `chmod`-helper unit tests.

**A genuine gap surfaced by review, tracked not fixed here**: `run_acknowledge_key_change`
(`apps/tui/src/worker.rs`) has the identical staleness bug — it mutates `TrustState` to `Pinned` or
`Blocked` and calls `save_trust`, but never touches `contacts.json`. A contact escalated from
`PinnedKeyChanged` to `Blocked` via that path still shows `"trust": "pinned"` in `--export-json`. This is
outside this task's literal Scope (which named only `run_mark_verified`), so the general
"`contacts.json`.trust can disagree with `trust.bin`" problem is not fully closed — only this one
instance is. **Tracked as a new follow-up task, [5.14](./5.14-acknowledge-key-change-trust-staleness.md)**,
rather than silently left unnoted or silently folded in here.

A narrow, inherited (not newly introduced) crash window is also noted, not fixed: a crash between the
`save_trust` and `contacts::save` calls leaves the two documents disagreeing until the next mutation —
the same shape `run_set_petname` already established precedent for; no atomicity guarantee exists
anywhere in this write-through pattern today, and this task doesn't change that.

**One investigated-and-not-reproduced flake**: `test-engineer` observed the new bug-pinning test fail
intermittently (~35-45% of trials) in its very first observation window, with the exact wrong-value
signature the fix targets — then could not reproduce it again across 100+ subsequent runs under varied
load, and found no logical race in the synchronization on code review (a `std::sync::Mutex`-backed
`EnvGuard` held across the test's full async lifetime including the `spawn_blocking` await). Independently
re-verified here: 15/15 isolated single-test runs and 20/20 full-file default-multithreaded runs, all
green, zero reproductions. Treated as transient sandbox noise (consistent with this project's own 4.49
precedent for a similarly non-reproducible one-off), not a defect — but recorded here rather than
silently dismissed, in case it recurs in real CI.
