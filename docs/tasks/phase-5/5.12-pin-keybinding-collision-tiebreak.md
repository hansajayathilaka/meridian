# 5.12 — Pin `find_binding`'s keybinding-collision tie-break contract

**Phase:** 5 — Review of Phase 4 · **Feature:** review fix (N7) · **Depends on:** — · **Status:** done

## Goal
`find_binding`'s tie-break on colliding keybindings is currently unpinned ("current, unexamined
behavior"), unlike `register`'s already-documented last-write-wins rule. Low risk today since only T17's
own commands are registered, but risk grows as more features register via the Definition of Done gate 9
extension contract — pin the contract explicitly before a second real feature lands and collides.

## Scope
- **In:** `apps/tui/src/surface.rs::find_binding` (lines ~334–338). Decide and document the tie-break
  (registration-order error, or an explicit collision registry) and pin it with a test.
- **Out:** Any change to `register`'s own already-documented last-write-wins contract.

## Deliverables
1. `find_binding`'s tie-break behavior documented as explicitly as `register`'s already is.
2. A test in `apps/tui/tests/surface_registry.rs` pinning the chosen behavior.

## Risks / notes
This is a genuine (if small) policy decision on the extension registry's contract, not a doc-only nit —
give it its own architect look rather than folding it into the 5.13 nit sweep.

## Tests
`cargo nextest run -p meridian-tui --test surface_registry`

## Reviews
**architect** + **code-reviewer** (combined `reviewer` call — this is the extension-registry contract
gate-9 features depend on).

## Status

**Tie-break chosen: id-lexicographic order — the matching command whose `PaletteCommand::id` sorts
lowest wins, independent of registration order.**

Reasoning: `PaletteRegistry::find_binding` was already a bare `BTreeMap::values().find(...)` over a
map keyed by `id`. That is not actually "undefined"/"unexamined" behavior as the old doc comment
claimed — it is fully deterministic: for a given set of registered ids, the same command wins every
time regardless of the order `register` was called in, because `BTreeMap` iterates in ascending key
order rather than insertion order. Kept this behavior as the pinned contract rather than changing it,
because:
- It is already the least-surprising default available without extra bookkeeping: reproducible,
  order-independent, and requires no new state.
- A "last write / most-recently-registered wins" rule (consistent with `register`'s own contract)
  would need extra insertion-order tracking that `find_binding`'s current data shape (a plain
  `BTreeMap`) does not carry — adding that would be a larger change than this pin scopes, and would
  risk masking a real collision behind "whichever feature happened to initialize last" rather than
  something a future feature author can reason about from their own `id` choice alone.
- Treating a collision as a hard error at registration time was considered and rejected for this task:
  it would change `PaletteRegistry::register`'s own contract (unconditional last-write-wins on `id`
  collision today), which is explicitly out of scope per this task's Scope. Left as a documented
  escape hatch to revisit if real-world binding collisions between shipped features turn out to be
  common.

Doc comment added to `find_binding` (`apps/tui/src/surface.rs`, replacing the old "undefined... just
documented as the current, unexamined behavior" language):

```rust
/// **Tie-break contract for two commands sharing a [`KeyBinding`] (pinned, review finding N7):**
/// of every registered command whose [`PaletteCommand::keybinding`] matches `key`, the one whose
/// [`PaletteCommand::id`] sorts lowest in byte-lexicographic order wins — a bare
/// `BTreeMap::values().find(...)` walking [`BTreeMap`]'s natural ascending key order (the same
/// order [`Self::iter`] walks). This is deterministic and **independent of registration order**:
/// unlike [`Self::register`]'s last-write-wins contract, which depends on *when* a command
/// registers, this one depends only on *what id* it registers under. A future feature author
/// picking an `id` for a command with a [`KeyBinding`] should not assume "mine wins on collision"
/// without checking whether some other registered id sorts lower and claims the same binding —
/// picking an id is the only lever a caller has over this outcome.
///
/// This is the registry's actual, pre-existing behavior (a bare `BTreeMap` lookup), kept as-is
/// and pinned rather than changed: it is already fully deterministic and reproducible (same
/// registered ids always produce the same winner, regardless of registration order), which is a
/// reasonable default for an additive registry where independently-developed features cannot see
/// each other's code. Deliberately **not** changed to a hard error on collision at registration
/// time here — that would be a bigger design decision than this pin scopes, since it would also
/// change [`Self::register`]'s own contract (out of scope for this fix); revisit toward that if
/// real-world binding collisions between shipped features turn out to be common enough to warrant
/// rejecting them outright. Pinned by `surface_registry.rs`'s
/// `find_binding_tie_break_is_lowest_id_wins` test.
```

Test added (`apps/tui/tests/surface_registry.rs::find_binding_tie_break_is_lowest_id_wins`): registers
two commands sharing one `KeyBinding`, with the lexicographically higher id registered *first* and the
lower id registered *second*, then asserts the lower id wins — and repeats with registration order
reversed to prove the outcome tracks `id`, not call order. Also asserts both commands remain registered
(a keybinding collision is not an id collision, so neither is silently dropped by `register`).

No change to `PaletteRegistry::register`'s own last-write-wins contract or implementation; no change to
`app.rs` (out of scope, and a sibling task 5.11 was concurrently touching that file).

### Review round
**reviewer** (architect + code-reviewer combined pass) — **PASS on both lenses, no blocking findings.**
Independently verified the technical claim rather than trusting the report: confirmed `commands` really
is a `BTreeMap<String, PaletteCommand>` (not a `HashMap`, whose iteration order would make the whole
pinned contract false), confirmed `find_binding`'s implementation itself is untouched by the diff (only
its doc comment changed), and reproduced with a standalone program that `BTreeMap::values().find(...)`
genuinely walks ascending key order — the "lowest id wins, independent of registration order" claim
holds. Architect lens judged the contract sound for the gate-9 extension registry (deterministic,
inspectable by any future command author via their own `id` choice, no hidden cross-feature coupling)
and confirmed rejecting a hard registration-time error was the right scope call given `register`'s own
contract is explicitly out of scope here. Code-reviewer lens confirmed the new test is a genuine pin (a
naive first- or last-registered-wins tie-break would each fail one of the test's two registration-order
variants) and that it also asserts the losing command stays registered (collision ≠ drop). Scope
discipline confirmed: `register`'s own contract and `app.rs` (5.11's concurrent, unrelated work) both
untouched.
