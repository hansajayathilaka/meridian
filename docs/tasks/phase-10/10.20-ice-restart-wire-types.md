# 10.20 — Wire types: `SignalContent::IceRestartOffer`/`IceRestartAnswer`

**Phase:** 10 — File Transfer Stream · **Feature:** T09 (fix) · **Depends on:** — · **Status:** pending

## Goal
Add the two new `SignalContent` variants [ADR 0025](../../adr/0025-ice-restart-renegotiation.md)
decided on, so a later task can seal and send an ICE-restart offer/answer the same way the original
dial/answer handshake seals `SdpOffer`/`SdpAnswer`.

## Scope
- **In:** `apps/envelope/src/signal.rs`'s `SignalContent` enum — add `IceRestartOffer{sdp, dtls_fp,
  ice}` and `IceRestartAnswer{sdp, dtls_fp, ice}`, identical field shape to the existing `SdpOffer`/
  `SdpAnswer` variants (same types, same `bytes_vec` CBOR encoding for `sdp`). Doc-sync
  `docs/api/wire-protocol.md` §3's Content union to list them alongside `sdp_offer`/`sdp_answer`,
  citing ADR 0025 for why this tier (session-substrate `SignalContent`) is correct rather than
  `mrd.ctrl/1`'s `CtrlFrame`.
- **Out:** any conformance-vector suite for these variants — ADR 0025's own Cons section already notes
  `SignalContent` isn't conformance-vectored today (unlike the envelope itself); don't invent one out
  of scope here. Also out: any session-layer logic that actually constructs, sends, or handles these
  variants (that's 10.21/10.22's job) — this task only adds the type and its `encode`/`decode` coverage
  via the existing round-trip test pattern already covering `SdpOffer`/`SdpAnswer`.

## Deliverables
1. `SignalContent::IceRestartOffer`/`IceRestartAnswer` variants.
2. Encode/decode round-trip test(s) for both new variants, mirroring whatever existing test already
   covers `SdpOffer`/`SdpAnswer`'s round trip in `apps/envelope`'s own test suite.
3. `docs/api/wire-protocol.md` §3 updated.

## Risks / notes
This is a pure additive enum-variant change (Rust `serde`-derived CBOR) — check whether `SignalContent`
uses an externally-tagged, internally-tagged, or array-positional CBOR representation (whichever
`meridian_proto::encode`/`decode` + the enum's own `#[derive]` produce) and confirm adding two new
variants at the *end* of the enum can't silently renumber/reinterpret any existing variant's encoding
if the representation is positional. If it's the externally-tagged default serde CBOR map/variant-name
representation (the common case, and what an unremarkable `#[derive(Serialize, Deserialize)]` on an
enum produces), this is safe regardless of variant order — confirm which one applies here before
declaring this risk closed.

`cargo nextest run -p meridian-envelope` (new round-trip tests); existing suite stays green.
