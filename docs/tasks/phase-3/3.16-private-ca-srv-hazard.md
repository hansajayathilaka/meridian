# 3.16 — Warn on private-CA trust anchors under SRV discovery

**Phase:** 3 — Review of Phase 2 · **Feature:** review fix (F6) · **Depends on:** — · **Status:** pending

## Goal
Stop the SRV demo from modelling the pattern that reopens ADR 0017 (a)'s Option-A impersonation hole
under a *shared* private CA.

## Scope
- **In:** prominent documentation that a private-CA trust anchor requires `discovery = static` with a
  mandatory `pinned_identity` **regardless of how the CA is installed** (ADR 0017 +
  `docs/operations/deployment.md` + a header comment in `demo/two-orgs/docker-compose.srv.yml`); a
  startup warning when `srv` is configured and the resolved trust anchor is not a public root, **if
  detectable**.
- **Out:** changing `validate`'s existing fail-closed rule (`srv` + non-empty `ca_bundle_path`);
  making the demo use static discovery — it demonstrates SRV on purpose.

## Deliverables
1. The doc edits above.
2. Optionally `apps/rendezvous/src/config.rs` — the startup warning + a unit test.
3. A `TODO: confirm` if detectability is unresolved.

## Risks / notes
- `validate` keys only on `ca_bundle_path`, so it **cannot see** a private CA installed into the OS
  trust store — which is exactly what `demo-entrypoint.sh` does (`update-ca-certificates`) with an
  empty `ca_bundle_path`. The demo itself is benign (cooperative orgs, one cert each); the hazard is
  a *shared, multi-org* private CA in production.
- If a non-public root is **not** reliably detectable, say so in the task file — do not fake a check
  that gives false assurance.
