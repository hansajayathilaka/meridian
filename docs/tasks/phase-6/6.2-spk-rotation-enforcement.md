# 6.2 — SPK rotation enforcement: trigger + monitoring in both long-running client loops

**Phase:** 6 — Envelope v2 · **Feature:** ADR 0016 (C1, parts 2–3/3) · **Depends on:** 6.1 · **Status:** done

## Goal
Make rotation actually happen without user action, and make staleness observable. This is the
"enforced, monitored" half of C1 — the compensating control ADR 0016 requires before v2 ships, since
dropping the per-message signature (6.3) makes first-contact authentication rest entirely on X3DH's
`DH1 = DH(IK_A, SPK_B)`, and an attacker holding a stale SPK secret can forge a first-contact session
(R1).

## Scope
- **In:** both long-running client loops — `apps/tui/src/worker.rs`'s inbound loop and
  `apps/cli/src/chat.rs`'s `run` loop — gain a periodic `rotation_due` check (task 6.1) that
  republishes via the existing republish machinery (`apps/tui/tests/republish_bundle.rs` documents
  today's event-triggered path — confirmed by direct read: neither loop has a timer/interval branch
  today, so this is new work in *both* binaries, not a shared single change). A monitoring/warning
  surface for an overdue SPK.
- **Out:** the predicate itself (6.1, dependency); the crypto/AAD rewrite (6.3).

## Deliverables
1. Rotation-check wiring in `apps/tui/src/worker.rs` and `apps/cli/src/chat.rs::run`, debounced so it
   fires on a real interval, not every loop tick (a full republish costs ~101 signing ops per
   `apps/tui/tests/republish_bundle.rs`'s own documentation — over-triggering burns OTKs and signing
   time unnecessarily).
2. A monitoring/warning surface: at minimum a log line (and, if **architect** calls for it during
   review, a TUI status/diagnostics affordance) once the generation is overdue past a grace multiple
   of `SPK_ROTATION_INTERVAL_SECS`.
3. **A short design note in this task's Outcome section stating the chosen fail-open/fail-closed
   behavior** for a client that has been offline/unable to rotate past the interval (e.g. does the
   client keep using the stale SPK and only warn, or refuse to accept new sessions under it?) — this
   is explicitly named by **architect** consult as a security-relevant default, not a style choice.
4. Test harness using an injected/fake clock proving: a simulated long session that outlives
   `SPK_ROTATION_INTERVAL_SECS` republishes automatically with no user action; a session under the
   interval never triggers an extra publish.

## Risks / notes
- **`TODO: confirm` with architect**: does "monitored" (C1/R1) require a new server-side metric off

## Outcome

Implemented in exactly the two files this task's own Scope names — `apps/tui/src/worker.rs` and
`apps/cli/src/chat.rs` — plus one new test file, `apps/tui/tests/spk_rotation.rs`. Task 6.1's
`PrekeyVault::rotation_due`/`generation_age_secs`/`SPK_ROTATION_INTERVAL_SECS` are called, never
touched; `apps/core/src/chat.rs` has zero diff. No envelope/AAD/wire code touched.

### Mechanism, per loop

Both loops gain a `tokio::time::interval_at`-driven `tokio::select!` arm — deliberately
`interval_at` with a first deadline one full `SPK_ROTATION_CHECK_INTERVAL_SECS` (3600s, one hour)
out, **not** plain `tokio::time::interval` (whose first `tick()` resolves immediately on creation).
This was a real defect caught while writing the tests, not a style choice: an immediate first check
would mean every single session start pays a real connect + 101-signature republish attempt whenever
`rotation_due` happened to read `true` right at that instant — which several existing test fixtures
in this codebase do, by design, for unrelated reasons (e.g. `apps/tui/tests/inbound_delivery.rs::
publish_own_bundle` seeds a fixed, already-old `spk_published_at`). An immediate first tick would
have turned every one of those fixtures into an unwanted extra network round trip and 101 signing
ops on every test run — exactly the over-triggering this task's own file warns against, just
surfaced at session-start time instead of at steady-state. `SPK_ROTATION_CHECK_INTERVAL_SECS = 3600`
(one hour) was chosen because `SPK_ROTATION_INTERVAL_SECS` (task 6.1: one week) is week-scale, so
hourly polling is generous headroom — worst case ~1h of extra staleness beyond the target interval
before the first check notices, negligible against R1's already-bounded compromise window — while
staying well clear of `PREV_GENERATION_GRACE_SECS`'s 60s reconnect-race cadence.
`MissedTickBehavior::Delay` (not the default `Burst`) on both intervals: a week-scale staleness
check has no "catch up" obligation after this loop was blocked for a while (a long reconnect stall,
a slow stdin reader); one prompt check once live again is what's wanted, never a burst of them.

- **`apps/tui/src/worker.rs::run_inbound_loop`**: the interval is created once, outside the outer
  reconnect `loop`, so its cadence keeps counting across reconnects rather than restarting from zero
  on every drop. The `while let Ok(deliver) = client.next_deliver().await` loop became
  `loop { tokio::select! { ... } }` with the tick as a second arm, calling the new
  `check_spk_rotation(store, handle, account_pub, server, now_unix)`. This only actually fires while
  a connection is live (it needs one to republish); while disconnected the reconnect loop is already
  retrying on its own short backoff, and the interval simply keeps ticking in the background.
  `check_spk_rotation` loads the vault, checks `rotation_due`, and — only when due — republishes via
  a new `republish_bundle_at(..., now_unix)`, an explicit-time sibling of the existing, already-tested
  `republish_bundle` (now a thin real-clock wrapper around it, so its own signature and all nine of
  its existing call sites/tests are byte-for-byte unchanged). This split was necessary, not
  cosmetic: `republish_bundle`'s original internal `now_unix()` read real wall-clock time regardless
  of what `now_unix` `check_spk_rotation` was checking `rotation_due` against, which — caught by the
  fake-clock tests below — silently broke a simulated multi-week session (the republish would stamp
  the vault with real "now", not the simulated timestamp, so every following simulated check read
  the wrong age). Threading the same `now_unix` through both the decision and the action is also the
  more correct design in production, mirroring `PrekeyVault::set_bundle`'s own "caller supplies now"
  precedent from task 6.1.
- **`apps/cli/src/chat.rs::run`**: same interval shape, added as a third `tokio::select!` arm
  alongside the existing `rx.recv()`/`client.next_deliver()` arms, calling the new
  `rotate_spk_if_due(server, state, store, handle, account_pub, now_unix)`. Unlike the TUI, this
  deliberately opens its **own** short-lived connection to `server` rather than reusing `run`'s
  persistent `client` — the rendezvous server already supports multiple simultaneous connections per
  account (`apps/rendezvous/src/state.rs`'s own multi-device connection list), so this is not a new
  risk, it costs one extra handshake roughly once a week, and it keeps the function testable the
  same proven way (an unreachable-address fail-open test) without needing to force a failure on
  `run`'s live, already-open connection mid-loop (whose `close()` takes `self` by value, so it
  cannot be "broken and later reused" from inside a running loop anyway). `rotate_spk_if_due` never
  touches disk itself — it mutates `state.vault` in place, and `run`'s own post-select
  `save_state`/`save_trust` calls persist that exactly like any other in-loop state change.

Confirmed by direct read before starting: neither loop had a timer/interval branch before this task
— this was genuinely new work in both binaries, not a shared change (`meridian-cli` and
`meridian-tui` are separate crates with no shared "long-running client loop" module).

### Monitoring/warning surface (deliverable 2)

`warn_if_spk_overdue` (implemented separately in each file, same logic) logs an `eprintln!` once the
generation is overdue past `SPK_ROTATION_WARN_GRACE_MULTIPLE = 2` × `SPK_ROTATION_INTERVAL_SECS` —
i.e. a *second* consecutive missed/failed rotation window, not the first. Chosen so a single
transient miss (one offline check, one connect failure) does not itself warn — only a generation
that has now gone a full extra `SPK_ROTATION_INTERVAL_SECS` without successfully rotating does,
mirroring `PREV_GENERATION_GRACE_SECS`'s own "grace before enforcement" shape one level up. Unknown
age (`generation_age_secs` returning `None` — never published, or a vault sealed before task 6.1)
always warns immediately: unknown age is already the fail-safe "due-now" case task 6.1 established,
and if the following republish attempt also fails, the age stays unknown on every subsequent check
until one finally succeeds — the one case that most needs a human to notice, not less.

**Revised after review — a log-only surface did not clear the bar for the TUI half of this
deliverable.** The combined `reviewer` agent (architect + security-reviewer lenses) made the call the
task file's own Scope reserved for it: `apps/tui/src/terminal.rs` runs the TUI in an alternate screen
(crossterm `EnterAlternateScreen` on stdout only), so a stderr `eprintln!` mid-session is either
invisible or corrupts the display — `docs/architecture/tui-client.md`'s own text already documents
this exact pattern (used elsewhere in `worker.rs` for a dropped envelope) as a known "no user-visible
signal" defect. Given that documented precedent, `eprintln!`-only does not clear "monitored" for the
TUI. The CLI side is unaffected by this finding (a plain scrolling terminal is not alt-screen-buffered,
so its `eprintln!` genuinely is visible there) and was not touched by the fix below.

**Fix**: added a small, additive TUI status surface mirroring the crate's existing
`AppEvent::ConnectionStatus` → `App` field → accessor pattern exactly, rather than inventing a new
one:
- `apps/tui/src/statusbar.rs`: new `SpkRotationStatus` enum (`Healthy` / `UnknownAge` /
  `Overdue { multiples, age_secs }`) — the same "small closed enum, not a raw string" shape
  `ConnectionState` already uses in this module.
- `apps/tui/src/app.rs`: `AppEvent::SpkRotationOverdue(SpkRotationStatus)` (doc-commented like
  `ConnectionStatus`); a private `App` field + `pub fn spk_rotation_overdue(&self) ->
  SpkRotationStatus` accessor; an `App::update` arm that stores it (pure, no `Effect`s, per this
  module's I/O-free invariant) and forwards it to whichever `Screen::Extension` pane is current, plus
  seeding a freshly opened pane with the already-known status.
- `apps/tui/src/surface.rs`: `ExtensionPane` gained one new **default no-op** method,
  `sync_spk_rotation_overdue`, so every existing implementer (including the test suite's
  `CounterPane`) is unaffected — additive, not breaking.
- `apps/tui/src/screens/diagnostics.rs`: `DiagnosticsPane` overrides `sync_spk_rotation_overdue` to
  store the status and renders a new "spk rotation (adr 0016 c1)" section at the top of the pane,
  following the file's existing render/styling conventions (dim "on schedule" when healthy; a red
  warning line with the exact same fail-open wording as the log line when overdue or unknown-age).
- `apps/tui/src/worker.rs`: `warn_if_spk_overdue`'s threshold decision extracted into a pure
  `spk_overdue_status(age) -> SpkRotationStatus` helper (byte-identical `eprintln!` behavior,
  refactored not changed); `run_inbound_loop`'s existing hourly rotation-tick arm now also derives the
  same status via a second, read-only `load_chat` at the same `now_unix` and pushes
  `AppEvent::SpkRotationOverdue` on the worker→App channel alongside the unchanged `eprintln!` and
  `check_spk_rotation` call — `check_spk_rotation`'s own signature/return type were kept frozen
  (`apps/tui/tests/spk_rotation.rs` calls it directly with today's exact shape) rather than threading
  a channel through it, so the log line and the TUI status derive from the identical
  `spk_overdue_status` helper and can never drift apart. This doubles the local (no-network) vault
  read on the hourly tick — negligible next to this task's own "hourly polling is generous headroom"
  reasoning, and does not touch the actual over-triggering concern (extra *republish*/signing cycles).

**What a TUI user now sees**: opening Diagnostics (command palette → Diagnostics) shows a bold "spk
rotation (adr 0016 c1)" heading followed by one line — `on schedule` (dim) when healthy, or e.g.
`overdue: 3x the target rotation interval (~10h stale) — continuing with the stale key (fail-open)`
in red for a known-age overdue generation, or the equivalent unknown-age wording — clearing back to
"on schedule" automatically once a rotation succeeds. Five new render/sync tests in
`diagnostics.rs`'s test module, four new `App::update`/accessor tests in `app.rs`'s, one new test in
`statusbar.rs`. `apps/tui/tests/spk_rotation.rs` and `apps/cli/src/chat.rs` were not touched by this
fix, per the fix's own constraints.

### Decision 1 — fail-open with escalating warning (recommended default, adopted as-is)

**Adopted the task file's recommended default: fail-open with escalating warning.** A client that
has been offline/unable to rotate past `SPK_ROTATION_INTERVAL_SECS` keeps using the stale SPK
generation — it is never cleared, corrupted, or refused — and a failed rotation attempt (logged by
`check_spk_rotation`/`rotate_spk_if_due` themselves, e.g. "continuing with the stale generation
(fail-open)... ") simply leaves the existing generation in service so the loop keeps accepting new
first-contact sessions under it. `warn_if_spk_overdue` above is the escalation: silent until the 2x
grace multiple, then loud, and louder in what it reports (the exact multiple-of-interval overdue) the
longer it persists. A republish is automatically retried on every subsequent hourly check for as
long as the generation stays due — "republishes automatically the moment connectivity allows" is not
aspirational, it falls directly out of the same debounced periodic check that enforces rotation in
the first place, with no separate retry machinery needed.

Reasoning, mirroring task 6.1's own "unknown-age = due-now, fail-safe" call: refusing to accept new
first-contact sessions entirely under a stale-but-otherwise-fine SPK generation would be a much
bigger availability regression (a client unable to reconnect to its rendezvous server — travel,
outage, firewall change — would stop being reachable by *anyone new* at all, indefinitely) than the
bounded compromise-window cost ADR 0016's R1 already accepts as C1's residual risk. R1 itself frames
the compensating control as "enforced signed-prekey rotation (target ~weekly, monitored...)" — a
bound on the *window*, not a promise that the window is always exactly one week; a client that
genuinely cannot reach the network cannot rotate under any design, fail-open or fail-closed, so
fail-closed there would only ever remove availability, never actually shrink the compromise window
below "however long this client stays unreachable" — the client is already accepting that risk by
being offline. This was implemented as described (never a TODO or a partial behavior) and is
asserted directly by `apps/tui/tests/spk_rotation.rs::
a_failed_republish_leaves_the_stale_generation_in_service_fail_open` and
`apps/cli/src/chat.rs::tests::rotation_failure_leaves_the_stale_generation_in_service_fail_open`.

### Decision 2 — "monitored" scope: client-side enforcement + local warning satisfies this task

**Adopted the task file's recommended default:** client-side enforcement (the periodic check itself)
plus local warning (`warn_if_spk_overdue`) satisfies this task's "monitored" obligation under ADR
0016 C1/R1; a new server-side metric off `prekeys.rotated_at` is out of scope here. Reasoning:
`prekeys.rotated_at` already exists server-side, so the server already has the data to build a
metric off of whenever devops wants one — nothing about landing this task narrows or forecloses that
option. This task's own file scope is explicitly the two client loops (`apps/tui`, `apps/cli`), never
`apps/rendezvous` or devops config, and `tools/metrics-allowlist.txt`/`docs/operations/monitoring.md`
were deliberately not touched, per the task file's own instruction. **Carry-forward (devops-owned,
flagged, not implemented here):** a server-side metric/alert off `prekeys.rotated_at` — e.g. "count
of accounts whose most recent `rotated_at` is older than N × the rotation interval" — would give an
operator-side view independent of any single client's own honesty about reporting its staleness, and
should be scheduled as its own task against `apps/rendezvous`/`tools/metrics-allowlist.txt`/
`docs/operations/monitoring.md` when devops prioritizes it.

### Tests (deliverable 5)

`apps/tui/tests/spk_rotation.rs` (4 tests) and `apps/cli/src/chat.rs::tests` (3 new tests, alongside
the pre-existing `gate_lines` coverage) are structured identically, one per binary since this is
genuinely separate code: both drive the real, already-tested republish machinery (a real in-process
`meridian-rendezvous` server, a real registered `MemorySecretStore` account) but with `now_unix`
supplied entirely by the test as a fake clock — no `tokio::time::pause`, no real waiting, and (per
the `republish_bundle_at` split above) no real-wall-clock leakage into the stamped result either.
Each pair covers:
1. **Never republishes under the interval** — checks spread across the whole interval (including
   the instant before the threshold) each read `NotDue`, and the vault's own publish timestamp never
   moves (asserted directly, not just "no error returned").
2. **A simulated long session that outlives the interval republishes automatically, and the
   debounce/no-over-triggering property** — a fake-clock-driven sequence spanning *two* full
   `SPK_ROTATION_INTERVAL_SECS` periods: not-due just before the first threshold, `Rotated` at the
   threshold with no user action, `NotDue` again at the very next check immediately after (proving a
   rotation is never immediately followed by another one — the debounce this task's Risks section
   calls out as its own defect class, not a rider on the happy-path test), not-due through most of
   the second interval, then `Rotated` again a full second interval later (proving this is a real
   recurring check across a long session, not a one-shot fuse).
3. **Fail-open against an unreachable server** — `RotationFailed` with a connect-stage error message,
   the stale generation's publish timestamp is provably untouched, and `rotation_due` still reads
   `true` afterward (the next check will retry, this failure does not permanently suppress rotation).

`cargo nextest` is not installed in this environment; used `cargo test` instead, per the task file's
own substitution note.

**test-engineer review pass (non-vacuity + debounce-property verification, per this task's own
Reviews requirement) found and fixed two real gaps, both in test code only:**
1. Both `assert_vault_published_at_is`/`assert_state_published_at_is` helpers checked
   `generation_age_secs(expected) == Some(0)`, which — because `generation_age_secs` computes a
   `saturating_sub` — only ever proves `published_at >= expected`, silently passing whenever the real
   `published_at` moved *forward* past the expected value. That is exactly what an erroneous early
   republish does, so every "must not have republished" assertion across all 6 original tests was
   less rigorous than intended. Proven empirically (not just by inspection): test-engineer
   temporarily reintroduced the `interval`-vs-`interval_at` first-tick bug and confirmed the
   pre-fix helper still reported success despite a real unwanted republish firing. Fixed by anchoring
   the check against a sentinel `check_now = u64::MAX / 2` so the subtraction can never saturate and
   the comparison pins an exact value; re-verified both fault-injection experiments now fail correctly
   post-fix.
2. The `interval_at`-vs-`interval` first-tick fix itself had no test at the actual timer-wiring level
   — all 3 original TUI tests called `check_spk_rotation` directly, bypassing `run_inbound_loop`'s
   real `tokio::select!`/`interval_at` construction entirely. Added
   `rotation_timer_does_not_fire_on_the_very_first_tick_even_when_already_overdue` (the 4th
   `spk_rotation.rs` test), which spawns the real `run_inbound_loop` with a generation seeded 4
   intervals overdue and asserts no republish lands within a real 2s window — verified falsifiable by
   reverting `interval_at` to `interval` and confirming the test fails.
