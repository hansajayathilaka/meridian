# 4.4 — Key-change handling: block/warn semantics

**Phase:** 4 — Verification & Trust + Terminal TUI Client · **Feature:** T08 — Verification & Contact Trust · **Depends on:** 4.3 · **Status:** done

## Goal
Implement the un-softenable key-change gate — a verified contact's key/device-record change blocks
sends until re-verification; a pinned contact's change prominently warns — as core logic every client
calls, with no client-side override path.

## Scope
- **In:** extend `trust.rs` with key-change detection against a contact's pinned-key history;
  `can_send(peer) -> SendGate { Ok, Warn(reason), Blocked(reason) }`; org-configurable pinned→block
  escalation; canonical wording sourced **verbatim in meaning** from
  [verification-ux.md](../../security/verification-ux.md) (no paraphrase into reassurance). Wire the
  gate into `apps/cli/src/chat.rs`'s send path so the reference/demo CLI doesn't silently lag the TUI's
  block semantics (the CLI is the scriptable surface every acceptance demo runs through — it must
  enforce the same invariant, not just display it later in 4.22).
- **Out:** the TUI's modal UI (4.22 consumes this gate, doesn't reimplement it); desync recovery (4.9,
  which depends on this landing first — see that task's Risks); device-list-change detection beyond
  what the key-change path already covers structurally (T13 multi-device deepens it later).

## Deliverables
1. `trust.rs`: `SendGate`, key-change detection, escalation config.
2. `apps/cli/src/chat.rs`: send path consults `can_send`, surfaces the canonical wording on `Blocked`/`Warn`.
3. Tests: verified→key-change→blocked (no bypass path), pinned→key-change→warn-then-acknowledge,
   org-config escalation pinned→block.

## Risks / notes
- **This is the phase's central un-softenable-UX invariant.** [verification-ux.md](../../security/verification-ux.md)'s
  hard prohibitions (no auto-dismiss, no "remember my choice", no burying the block) apply to the *gate*,
  not just the UI painted on top of it — a gate with a silent bypass makes any UI's warning theater.
- CLI wiring here is a deliberate addition beyond T08's literal working-output script, so the reference
  client doesn't lag the TUI — note this if a reviewer reads it as scope creep, it isn't.

## Status
Done. `trust.rs` gains `TrustState::{Blocked, PinnedKeyChanged}`, `observe_key_change` (caller-supplied
previous/new-pubkey correlation — `TrustStore` cannot safely infer "same human, new key" from raw key
material or from `hint`, which is shared across contacts; the routing/session layer is what actually
has a reason to believe two keys continue one conversation, and this same shape is designed to be
reusable by T13's device-list-change detection later without a structural change), `can_send` /
`SendGate{Ok,Warn,Blocked}`, `acknowledge_key_change` (re-pins from `PinnedKeyChanged` only; hard-errors
on `Blocked` — the load-bearing half of "no bypass"), and an org-configurable
`escalate_pinned_key_change`. `apps/cli/src/chat.rs`'s send path funnels every outbound text send
(typed input + the flush queue) through a new `send_gated`, so the reference CLI enforces the same
invariant the TUI will later display (4.22). Canonical `Blocked`/`Warn` wording preserves
verification-ux.md's intent (benign explanation + interception possibility + pause/block + Verify path)
in substance, each carrying a `TODO: confirm` per that doc's own note on final copy.

**security-reviewer** (required, told to treat softened key-change UX as blocking) found one real,
concrete bypass, fixed in place before this task closed: `acknowledge_key_change` only checked the
contact's *current* state against `PinnedKeyChanged`, never `escalate_pinned_key_change` itself — so an
org flipping escalation on as an incident response (e.g. "we suspect an active MITM, force hard-block")
could be silently defeated by an ordinary `acknowledge` call on an already-outstanding warning, in the
gap before the next observed key change (`observe_key_change`'s own doc already said escalation only
"tightens... on the next observed change," and nothing enforced the retroactive case). Fixed:
`acknowledge_key_change` now also force-transitions an in-flight `PinnedKeyChanged` contact straight to
`Blocked` (returning `NotAcknowledgeable`, never a silent re-pin) whenever escalation is on at call
time, regardless of whether a new key change has been observed since. Added
`escalation_flipped_on_while_a_warning_is_already_outstanding_blocks_on_acknowledge_attempt` covering
exactly this sequence. Everything else the review checked — no bypass path for `Blocked` itself, faithful
canonical wording, genuine (not display-only) CLI enforcement with every text-send path traced to one
funnel, the `Warn`-hold/re-flush logic, `ConflictingContact`'s non-mergeable refusal, and the
delivery-receipt gating exemption — passed as implemented.

Advisory (non-blocking) items the review surfaced, tracked here rather than in code changes since none
are required for this task: real detection triggers (an address-book layer noticing "same contact, new
key") don't exist yet in the shipped CLI — `observe_key_change`/escalation are currently reachable only
from tests, which is expected and by design (task 4.10's `meridian-mitm-sim` is what wires and proves
real triggers end-to-end, not this task); the CLI's `answer_key_change_warning` reads the next typed
chat line as accept/decline, so a coincidental "y"/"yes" typed as ordinary chat text while a warning is
outstanding could accidentally acknowledge it (not attacker-triggerable; worth an unambiguous token or
deferring fully to 4.22's TUI modal); held-but-unsent messages during an outstanding warning are
unpersisted locals (a restart silently drops them, though the trust gate itself still re-applies
correctly on restart since that *is* persisted); the receive side prints inbound text with no inline
`Blocked`/`PinnedKeyChanged` marker for a pure receiver who never sends (verification-ux.md only
mandates gating sends, so not a doc violation, but worth confirming with design for 4.22).

`cargo test -p meridian-core --test key_change_gate` (10/10, including the new regression test),
`cargo test -p meridian-core -p meridian-cli` (full suites), `cargo fmt --check`, and `cargo clippy
--workspace --all-targets -- -D warnings` all clean.
