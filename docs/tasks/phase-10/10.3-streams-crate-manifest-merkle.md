# 10.3 — Scaffold `meridian-streams` + manifest schema + BLAKE3 merkle build/verify

**Phase:** 10 — File Transfer Stream · **Feature:** T09 · **Depends on:** — · **Status:** pending

## Goal
Create the crate additive stream types live in (already named in `docs/architecture/stack.md` line 71
as T09/T15/T16's home, but not yet scaffolded) and its first two building blocks: the `mrd.file/1`
manifest CBOR schema and a BLAKE3 merkle tree builder/verifier over 64 KiB chunks.

## Scope
- **In:** `apps/streams/` crate (`Cargo.toml`, `lib.rs`, added to the root `Cargo.toml` workspace
  `members`); a `manifest` module with the CBOR body `{name, size, root: bstr, key: bstr}` (per-file
  key sealed under the ratchet — sealing itself happens where the manifest is sent, not in this crate);
  a `merkle` module: build a BLAKE3 merkle tree over a file's 64 KiB chunks, compute the root, and
  verify one chunk against a subtree path.
- **Out:** the `StreamType` trait implementation (task 10.6), per-chunk AEAD (task 10.5), the sender/
  receiver engines (10.7/10.8). This task only ships the schema types and the merkle primitive with
  their own unit tests.

## Deliverables
1. `apps/streams/Cargo.toml` + `apps/streams/src/lib.rs`, added to root `Cargo.toml` `members`.
2. `apps/streams/src/manifest.rs` — the CBOR manifest type + (de)serialization round-trip test.
3. `apps/streams/src/merkle.rs` — tree build, root computation, incremental subtree verification,
   corruption-detection test (flip a byte in one chunk, assert verification fails for that chunk only).
4. New `blake3` workspace dependency (pre-approved: crypto-protocols skill, "Hash/merkle = blake3").

## Risks / notes
No document today pins the exact merkle construction (leaf shape, node ordering, odd-leaf-count
handling). `TODO: confirm` — this task's own Outcome must nail it down (recommended default: leaf =
`blake3(chunk_bytes)` per 64 KiB chunk in file order; internal node = `blake3(left ‖ right)`; an odd
trailing leaf promotes unpaired to the next level rather than duplicating itself, to avoid the classic
Merkle "duplicate last leaf" second-preimage footgun) and record the chosen shape precisely enough for
task 10.12's spec-doc section to describe it byte-for-byte (third-party implementability is an
acceptance criterion of the whole feature).

## Tests
`cargo nextest run -p meridian-streams`.

## Reviews
**code-reviewer** + **security-reviewer** (new dependency; the merkle construction is integrity-critical
— an ambiguous or malleable tree shape could let a corrupted chunk pass verification, which is exactly
the acceptance criterion task 10.16 tests against).
