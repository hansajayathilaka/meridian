# 4.14 — `meridian-tui::config`

**Phase:** 4 — Verification & Trust + Terminal TUI Client · **Feature:** T17 — Terminal TUI Client · **Depends on:** 4.2, 4.11, 4.13 · **Status:** done

## Goal
Load `config.toml` per ADR 0021's ratified format, so every later screen task reads settings the same
way.

## Scope
- **In:** figment-based loading: `Toml::file(config.toml)` merged with
  `Env::prefixed("MERIDIAN_TUI__").split("__")`, mirroring `apps/cli/src/policy.rs` and
  [ADR 0018](../../adr/0018-rendezvous-config-loading.md)'s pattern. Precedence: CLI flags > env >
  `config.toml` > defaults. Missing file → defaults apply (not an error); malformed file → fail closed.
  Schema per [tui-client.md §5](../../architecture/tui-client.md#5-local-store--configuration)
  (`[ui]`, `[history]`, `[network]`, `[keys]`).
- **Out:** the store (4.15); the Settings screen's write-back behavior (4.24, which consumes this).

## Deliverables
1. `apps/tui/src/config.rs`: figment loader, schema types, precedence resolution.
2. Tests: precedence order, missing-file defaults, malformed-file fail-closed, env-var override.

## Tests
`cargo nextest run -p meridian-tui --test config`

## Reviews
- **reviewer** (combined) — config loading with a precedent pattern to follow (ADR 0018), low novelty.

## Status
Done. `apps/tui/src/config.rs` loads `$MERIDIAN_HOME/tui/config.toml` with figment
(`Toml::file` → `Env::prefixed("MERIDIAN_TUI__").split("__")` → an explicit `cli_overrides:
&[(String, String)]` seam, last-merge-wins — CLI > env > file > defaults), mirroring
`apps/cli/src/policy.rs`/ADR 0018 exactly. Missing file → `TuiConfig::default()` (no error);
malformed file (bad TOML, or a value outside a closed enum) → hard `Err`, fail closed. Schema
(`[account]`, `[ui]`, `[history]`, `[network]`, `[keys]`) matches tui-client.md §5 / ADR 0021
condition 3 field-for-field; `theme`/`timestamps`/`bell`/`network.policy` are real enums, `[keys]`
stays a free-form `BTreeMap<String, String>`. No `cli_overrides` caller exists yet
(`meridian-tui` has no `clap` flags of its own — out of scope here, per the task's own
boundary) — the seam exists so a future flag parser can plug in without a signature change.

**Review (combined `reviewer`, as named):** found one real issue in the first pass — none of the
schema structs had `#[serde(deny_unknown_fields)]`, so the module doc's claim that a renamed/removed
field "is a figment-reported error at load time" was false: `#[serde(default)]` alone silently
*discards* an unrecognized key instead of erroring, exactly the silent-data-loss failure ADR 0021's
migration story rules out. Fixed by adding `deny_unknown_fields` to all five schema structs (not the
enums, not the free-form `[keys]` map) and rewriting the doc to attribute the guarantee to that
attribute explicitly rather than asserting it unexplained; added two regression tests
(`unknown_top_level_field_fails_closed`, `unknown_field_in_a_section_fails_closed` — the latter is
the realistic future-rename shape: a stale field inside an otherwise-recognized section). Reviewer
re-verified the fix directly (including reverting it locally to confirm the new tests are load-bearing,
and auditing figment's `Env` key-casing against the plain snake_case field names to rule out a
legitimate env/CLI override being misclassified as unknown) and signed off clean on all three lenses
(correctness/architecture/security) with no further findings.

`cargo test -p meridian-tui` — 25/25 pass (11 unit + 13 `tests/config.rs` + 1 `terminal_guard.rs`).
`cargo fmt --check`, `cargo clippy --workspace --all-targets -- -D warnings`, and
`tools/lint-tui-no-cli.sh` (meridian-tui still depends only on meridian-core) all clean.
`cargo test -p meridian-cli --bins` confirmed nothing downstream broke.
