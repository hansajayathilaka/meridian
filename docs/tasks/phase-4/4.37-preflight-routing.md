# 4.37 — Preflight routing

**Phase:** 4 — Verification & Trust + Terminal TUI Client · **Feature:** T17 — Terminal TUI Client (gap closure) · **Depends on:** 4.29, 4.36 · **Status:** pending

## Goal
`App::new`/`meridian_tui::run()` actually detects existing state and routes to `Unlock`/`Onboarding`/
`Screen::Main` instead of always starting on `Onboarding`; Onboarding's/Unlock's completion pushes
`Screen::Main` (dispatching `Effect::LoadSession` where needed) instead of `Screen::Placeholder`. This is
the `Preflight` step named in `docs/architecture/diagrams/tui-screen-flow.mermaid`
(`Preflight --> Unlock: account exists, file-backed store`) that has never existed in this crate.

## Scope
- **In:** a pure `preflight_route(account: Option<AccountDescriptor>) -> InitialRoute` decision function
  (testable without I/O) plus the minimal synchronous `AccountDescriptor::load()` check inside `run()`'s
  existing setup phase (which already does synchronous config I/O before constructing `App` — same
  precedent, not a new pattern). Rewire the `Onboarding`/`Unlock` `finished` arms in
  `App::handle_key`/`handle_worker`.
- **Out:** the `run_worker` execution of `LoadSession` itself (4.29 already built it); `Screen::Main`'s
  own content (4.36 already built it).

## Deliverables
1. `preflight_route` (pure decision function).
2. Updated `App::new`/`run()`.
3. Updated `Onboarding`/`Unlock` completion-transition arms.
4. Tests covering: no `account.json` → Onboarding (regression, unchanged from today); file-backed
   existing account → Unlock; OS-keystore existing account → straight to Main via `Effect::LoadSession`;
   a wrong passphrase at Unlock retries in place per `tui-client.md` §7 (no lockout invented — this
   crate has never had one and must not gain one silently here).

## Risks / notes
- Not hard-blocked on 4.30's/4.35's completion for its own unit tests, though the full T17 demo needs
  those too — 4.38 owns confirming the whole assembled path.
- Depends on 4.29 (`Effect::LoadSession`) and 4.36 (`Screen::Main` to route to).
- **Escalated by 4.31's own review — a residual gap this task does not by itself close.** `run_worker`'s
  contacts/contact-detail effect handlers (4.31) and trust/request-queue handlers (4.32) each re-derive a
  fresh `SecretStore`/`TrustStore` from disk on every single dispatch (`worker.rs::open_account_store`),
  since at build time neither task had a live, already-unlocked session to reuse. For an OS-keystore
  account this is harmless (no secret needed to re-open it). **For a file-backed (passphrase-keyfile)
  account, `open_account_store` fails closed today with an actionable error** — there is no cached,
  already-unwrapped store anywhere for it to use. Once this task lands, `App` *will* hold exactly that
  (a `LiveSession` produced by `Effect::Unlock`'s extended outcome, per task 4.29) — but nothing
  automatically threads it into 4.31/4.32's already-built handlers; they would need to be revisited to
  accept an optional pre-unwrapped store/handle rather than always re-deriving one. **This task's own
  scope should NOT silently absorb that rewiring** (it's a second, separable concern — this task is
  entry-point routing, not a `run_worker`-internal refactor) **but must not silently ignore it either**:
  if not otherwise scheduled by the time this task lands, either (a) file a new follow-up task
  (`4.39` or into whatever phase follows) to thread the cached store through 4.31/4.32's handlers, or
  (b) confirm with 4.38 that this is explicitly, visibly carried forward (not silently shipped) if it
  remains unresolved — 4.38's own scope is verification/doc-reconciliation only, so it cannot fix this
  itself, only surface it honestly the way 4.28 surfaced the original T17 gap. Do not let this evaporate.
