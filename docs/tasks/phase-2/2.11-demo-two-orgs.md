# 2.11 — `demo/two-orgs/`: two full stacks, private CA, both discovery modes

**Phase:** 2 — Cross-Org Federation · **Feature:** T06 — Cross-Org Federation · **Depends on:** 2.4, 2.5, 2.7, 2.8 · **Status:** done

## Goal
`cd demo/two-orgs && docker compose up` brings up `org-a.test` + `org-b.test` (rendezvous + coturn ×2),
a private CA, and no internet — the feature spec's working output, actually runnable.

## Scope

  per-org configs; the static map plus a local DNS service so SRV mode is genuinely exercised; CA
  wiring; a scripted walkthrough; `just two-orgs` repointed.
- **Out:** the assertions themselves (2.12). This task delivers the stack and a runnable script;
  2.12 turns it into a gate.

**Bugs found and fixed by actually running the stack (not just inspecting it):**
- `infra/deploy/bootstrap-ca.sh` issued the two per-org private keys `0600` (openssl's default).
  The rendezvous container drops privilege to a non-root `meridian` uid (10001) via `gosu`
  (`apps/rendezvous/docker-entrypoint.sh`) *before* the federation TLS listener opens that key
  (`apps/rendezvous/src/main.rs`), so both rendezvous containers panicked on boot with `Permission
  denied` the instant federation was enabled — 100% of the time, in both discovery modes. Fixed by
  `chmod 644`-ing the two leaf keys after issuance (dev-only key material in a gitignored
  directory; the CA key itself is untouched, still `0600`, and is never mounted into any
  container).
- Repo root had no `.dockerignore`. Every image here (`apps/*/Dockerfile`,
  `demo/two-orgs/Dockerfile.rendezvous`) builds with the workspace root as context, and `COPY . .`
  was shipping the multi-GB `/target` build-cache directory into every build — added one.

**Real end-to-end evidence** (`bash demo/two-orgs/run-walkthrough.sh static`, then `srv`, then
`just two-orgs`, each a clean run from a fresh CA + fresh accounts, each exiting 0):
```

sending from bob to alice: "hello-across-orgs-<random>"
confirmed: bob's message was routed cross-org and delivered while alice was online
confirmed: the cross-org message landed in alice's message-request queue, not auto-delivered
confirmed: after accepting, alice received the message content end-to-end: "hello-across-orgs-<random>"
confirmed: real cross-org P2P session established for both sides (DTLS fingerprint verified) — "path":"direct"

confirmed: grep -c plaintext == 2 (exactly the benign startup banner, 0 real leaks)

```
`srv` mode additionally confirmed `_meridian-fed._tcp.org-b.test SRV → rendezvous-b:8444` via a
real `dig` query against the demo's own dnsmasq. `bash tools/check-docs.sh` passes (1632 relative
links checked, 0 broken). Every run tears its stack down cleanly (`docker ps -a` empty on exit).

**The "plaintext" gotcha (documented in README.md, worth restating here):** a literal
`grep -c plaintext` on the servers' logs — as the feature spec's illustrative demo script
suggests — is a trap: `meridian-rendezvous`'s own startup line ("…holds no plaintext by
construction") contains that literal word and would read as a false failure. The script instead
greps for the run's actual random message *body* (a strictly stronger assertion) and separately
confirms any literal "plaintext" occurrences are accounted for exactly by that one banner line per
server.

**Sandbox-only note (not part of the deliverable):** this test environment's outbound HTTPS goes
through a TLS-intercepting proxy that neither `rust:1-slim`'s rustup nor `alpine:3`'s `apk` trust by
default, which broke the Docker build in *this environment specifically* (`UnknownIssuer` /
"server certificate not trusted"). Verified by temporarily patching in the proxy's CA, confirming
all three runs above, then reverting both Dockerfiles back to their exact pre-patch content
(diffed to confirm) before finishing — no proxy-trust code remains in either Dockerfile.
