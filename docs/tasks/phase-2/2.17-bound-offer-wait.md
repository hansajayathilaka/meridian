# 2.17 — Bound the answerer's wait for an offer (`recv_sdp`, mirror of 1.33)

**Phase:** 2 — Cross-Org Federation · **Feature:** carried-in defect (surfaced by 2.12's review) · **Depends on:** — · **Status:** pending

## Goal
`answer_with_config`'s two `recv_sdp(...).await?` calls (`apps/core/src/session.rs`, the initial
offer wait and the relay-fallback second wait) have no timeout, so a peer that calls `answer()` for
an offer that never arrives hangs indefinitely with no diagnostic — the same defect class task 1.33
fixed for the dialer's wait for an answer, on the opposite side of the handshake.

## Background
Surfaced during task 2.12's review (security-reviewer and architect independently found and
confirmed the same gap via mutation testing on the cross-org abuse suite's continuity test, using a
`Closed` federation policy to make a dial's route get rejected server-side before any offer ever
reaches the answering side). `ANSWER_TIMEOUT`'s own doc comment (`apps/core/src/session.rs`) already
states explicitly that it bounds *"the dialer's wait specifically — the responder's wait for the
offer is unchanged."* Task 1.33's own Scope explicitly excluded this ("Out: ... changing the
responder path, which already fails fast") — but that exclusion rested on 1.28's specific scenario,
where the responder *does* receive bytes (a rewritten offer) and rejects immediately on signature
failure. Federation introduces a materially different failure mode 1.33 never covered: the route
gets rejected server-side (closed policy, allowlist miss, rate limit) so **no bytes ever arrive** at
the answering side at all, and `recv_sdp`'s bare `loop { relay.recv().await?; ... }` blocks forever
with nothing to reject.

Both reviewers independently concluded: real, not already covered by 1.33's exclusion (which applies
to a different failure mode), availability-only (DoS-class, inside threat-model goal 6's conceded "a
malicious server can deny service"), and requires its own tracked task rather than staying as prose
in an agent's review summary — mirroring how 2.9's review spawned 2.15 and 2.10's spawned 2.14.

## Scope
- **In:** a bounded wait on both of `answer_with_config`'s `recv_sdp` call sites (the initial offer
  wait and the relay-fallback second wait), with a distinct, diagnosable `SessionError` variant (e.g.
  `OfferTimeout`) — same taxonomy discipline as 1.33's `AnswerTimeout`. A test proving the timeout
  fires and is distinguishable from tampering/rejection.
- **Out:** retry/backoff policy; changing the dialer path (already bounded by 1.33); any change to
  fail-closed session-establishment semantics — a timeout must mean "no session," never a degraded
  one, exactly as 1.33 required for its side.

## Risks / notes
- **Timeout value:** start from 1.33's own corrected value (`ANSWER_TIMEOUT` = 30s, sized to sit
  outside the real WebRTC backend's up-to-20s `GATHER_TIMEOUT` — trickle ICE isn't supported, so both
  sides gather full candidates before sending SDP). The answerer's bound likely wants the same
  reasoning and possibly the same constant; architect call on whether to share `ANSWER_TIMEOUT` or
  introduce a distinctly-named-but-equal `OFFER_TIMEOUT` for clarity at call sites.
- Must not weaken fail-closed behaviour, identically to 1.33's own risk note.
- Check whether this reopens any OTK-consumption/amplifier consideration analogous to 1.33's noted
  residual (does waiting to answer consume anything of the answerer's own that a hostile/absent dial
  could drain repeatedly?) — confirm or rule out explicitly, don't leave it unexamined.
- `apps/cli/tests/two_orgs_walkthrough.rs`'s continuity test (task 2.12) is where this gap was found;
  consider whether its harness should gain a positive assertion once this lands (a closed-policy dial
  now produces a diagnosable answerer-side error instead of a silent hang), though that's this task's
  call, not mandated.

## Tests
`cargo nextest run -p meridian-core` (timeout fires, error is distinguishable) · confirm
`two_orgs_walkthrough.rs`'s closed-policy scenario (if one exists after 2.12) still passes and ideally
gets tightened the way 1.33 tightened `relay_rewrite.rs`.

## Reviews
- **architect** — timeout value + error surface, mirroring 1.33's own review.
- **security-reviewer** — fail-closed preserved; confirm/rule out the OTK-consumption-amplifier
  question above.
