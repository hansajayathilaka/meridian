# 2.7 — Federated prekey fetch, both sides (§3.3 steps 2–4)

**Phase:** 2 — Cross-Org Federation · **Feature:** T06 — Cross-Org Federation · **Depends on:** 2.3, 2.4, 2.5, 2.6 · **Status:** done

## Goal
Alice's client asks **her own** server for `K_B@org-b`; server A dials org-b and returns the bundle
**byte-identically**; Alice's existing `verify_bundle` remains the only trust anchor. Clients never
touch the foreign server.

## Scope
- **In:** server B's inbound `fed_fetch_bundle` handler (policy + limits + store lookup); server A's
  outbound path from c2s `Fetch{hint}`; `meridian-signaling` and `meridian-cli` plumbing for the hint;
  `meridian fetch-bundle --id mrd1:…@org-b` working cross-org.
- **Out:** envelope forwarding and reachability (2.8); error taxonomy and copy (2.9).

## Deliverables
1. `apps/rendezvous/src/federation/inbound.rs` (`handle_fed_fetch`) and `outbound.rs`
   (`fetch_foreign_bundle`).
2. `apps/rendezvous/src/ws.rs`: `handle_fetch` branches on `fetch.hint` — absent or equal to own
   domain → local; otherwise → federated.
3. `apps/signaling/src/client.rs`: `fetch_bundle(target, hint, tamper)`; call-site updates in
   `apps/cli` and `apps/core`.
4. `apps/rendezvous/tests/federation_fetch.rs`: two in-process servers over mTLS; happy path; bundle
   bytes **identical** to what B stored; `closed`/non-allowlisted origin → `fed_denied`; unknown key
   at B → `not_found_at_hint`; rate limit trips.

## Risks / notes
- **Routing invariant.** This is the one place a client could be tempted to dial a foreign server
  directly. Add an explicit test asserting the client opens exactly **one** WebSocket, to its own
  server.
- **Dependency trap.** Server A must forward the bundle as opaque bytes and must **not** call
  `meridian_signaling::verify_bundle` — that pulls `meridian-signaling` → `meridian-identity` →
  `meridian-store` and breaks `tools/lint-server-no-core.sh` (exactly the transitive route task 1.20's
  structural rewrite was built to catch). It is also *wrong*: §3.3 step 4 puts verification at the
  client, and verifying at A would let a bug there mask a substitution at B.
- The own-domain short-circuit prevents a server federating to itself.
- `TODO: confirm`: whether an unknown key at B returns `not_found_at_hint` or a generic failure — the
  distinction is an existence oracle across orgs. Inherits 2.6's rejection-reason decision.
- **Inherited from 2.5's security review (required).** `outbound.rs`'s dial-out path MUST thread
  `discovery::Endpoint::pinned_identity` — when `Some` (private-CA/air-gap mode, per ADR 0017 C4) —
  into `link::dial()`'s `expected_domain` identity-verification parameter, **not** just the discovery
  `domain` hint. `Endpoint`'s own doc comment (`apps/rendezvous/src/federation/discovery.rs`) explains
  why: under a private CA a self-asserted hint domain is not itself a trust boundary — any org
  enrolled under that CA can present a cert whose SAN matches any domain a caller merely hoped to
  reach, which is exactly the impersonation hole ADR 0017 (a)'s rejected "Option A" describes. Add a
  test proving a peer cert matching the hint `domain` but **not** `pinned_identity` is rejected.

## Outcome
`apps/rendezvous/src/federation/outbound.rs`/`inbound.rs` (new): server A's dial-out
(`fetch_foreign_bundle`, pinning to `Endpoint::pinned_identity` when `Some` per the requirement
inherited from 2.5's review) and server B's inbound handler (`handle_fed_fetch`, `origin_domain`
always the mTLS-authenticated `link.peer_domain`, tasks 2.6's policy/limits as their first real
callers). No bundle verification server-side either direction — that stays client-side per §3.3
step 4, and `meridian-signaling` is never imported into this crate. `ws.rs`'s `handle_fetch`
branches on `fetch.hint`; federated replies reuse 2.3's pre-existing `fed_denied`/`fed_unreachable`/
`not_found_at_hint`/`rate_limited` codes, no new ones invented. `main.rs`/`state.rs`: this is the
first task to actually run tasks 2.4/2.5's previously-inert s2s listener/dialer in a live server.

**Reviews:** architect — consistent on §3.3 conformance, dependency graph, and task placement; one
required revision — the federation bind-failure path originally only logged and let c2s continue,
inconsistent with `build_federation_runtime`'s own fail-loud panic and this codebase's established
"never silently weaker" posture (task 1.12 precedent) — fixed: the s2s listener now binds
synchronously and fatally, before the c2s listener. security-reviewer — APPROVE-WITH-CHANGES, two
required fixes: `federated_fetch_error_reply` was interpolating server A's internal dial
host/pinned-identity string into client-visible error text on failure (an ordinary transient
outage, no attack needed, would have leaked it) — fixed to use only the client's own hint; and
`inbound.rs`'s module doc now records the residual that keying the fetch rate limit on `req.target`
doesn't defend against an origin spraying arbitrary targets. code-reviewer — approve-with-nits,
independently found the same error-message leak. test-engineer — PASS; mutation-tested both
critical tests (single-websocket routing invariant, pinned-identity-vs-hint-domain rejection) and
confirmed both are genuinely non-vacuous.

Tests: `cargo nextest run -p meridian-rendezvous --test federation_fetch` (6/6 pass, including a new
assertion that the fixed error path doesn't leak the pin string), full `meridian-rendezvous` suite
103/103 pass, `cargo test --workspace` green, clippy/fmt clean, `lint-server-no-core.sh` and
`lint-no-raw-id-logging.sh` pass. `cargo nextest run -p meridian-signaling` (in the task's own Tests
list) reports "no tests to run" — pre-existing, `meridian-signaling` has never had its own test
file; coverage is entirely via other crates' integration tests.
