# 12.5 — `WebCryptoSecretStore` (`apps/store`, wasm32-gated)

**Phase:** 12 — Browser & Desktop Clients · **Feature:** T11 · **Depends on:** 12.1 · **Status:** done

**User surface:** none directly — foundational store primitive consumed by the browser adapter (12.13)
and the account-creation flow inside 12.7. No TUI surface applies.

## Goal
Implement [ADR 0026](../../adr/0026-browser-client-local-store.md)'s browser `SecretStore`: a new
`WebCryptoSecretStore`, mirroring `apps/store/src/os.rs`'s/`file.rs`'s existing impl shape, backed by
non-extractable WebCrypto `CryptoKey`s. This is the first `SecretStore` impl in the tree that can
honestly report `nonextractable() == true`.

## Scope
- **In:** `apps/store/src/webcrypto.rs`, `wasm32`-gated, implementing `SecretStore` exactly per
  `core-api-contracts.md`'s frozen signature: `store()` imports the given raw seed via
  `SubtleCrypto.importKey('raw', ..., extractable: false, ...)` and discards the JS reference to the raw
  bytes immediately afterward — no code path may export or log the raw seed after import; `use_key`
  computes signing/DH results via `crypto.subtle`'s non-extractable-key operations, returning only the
  computed output; `derive_key` computes a domain-separated HKDF-Expand output via `crypto.subtle`,
  returning **extractable** raw bytes (this is deliberate per ADR 0026 — the derived per-purpose sealing
  key is allowed to exist as raw WASM memory; only the *base account key* stays non-extractable
  throughout); `nonextractable()` returns `true`.
- **Out:** IndexedDB record sealing/schema (that's a separate module, task 12.12, per the ADR's
  crate-placement split — `meridian-crypto`'s `at_rest::seal`/`open` needs both `meridian-store` and
  `meridian-crypto`, which would cycle if placed inside `apps/store` itself); any browser `Transport`
  work (12.11); any UI.

## Deliverables
1. `apps/store/src/webcrypto.rs` — `WebCryptoSecretStore`.
2. `apps/store/Cargo.toml` — `wasm32`-gated `web-sys`/`js-sys`/`wasm-bindgen` dependencies.
3. Tests round-tripping `store`/`use_key`/`derive_key`.
4. A negative test asserting the raw seed never appears as an extractable `CryptoKey` — e.g. attempting
   `crypto.subtle.exportKey` against the stored key and asserting it throws/rejects.

## Risks / notes
This is genuinely new, security-load-bearing code (ADR 0026 binding condition 1) — keep the diff
narrowly scoped to exactly what the ADR specifies; do not invent additional convenience methods on the
trait or bypass paths that could return raw key material.

## Outcome
Implemented `WebCryptoSecretStore` in `apps/store/src/webcrypto.rs`, wasm32-gated. `store()` imports the
seed as three separate non-extractable `CryptoKey`s (one per algorithm WebCrypto binds a key to: Ed25519/
`sign`, X25519/`deriveBits` — derived via a clamped SHA-512(seed) scalar, PKCS#8-wrapped since WebCrypto's
`"raw"` import only accepts *public* OKP keys — and HKDF/`deriveBits`), discarding every local reference
to the raw seed/intermediates afterward. `use_key`/`nonextractable` match ADR 0026 exactly; `derive_key`
deliberately returns extractable raw bytes (only the base account key stays non-extractable throughout).
Verified via `wasm-bindgen-test` against a real, version-matched headless Chromium (not a Node polyfill or
JS-level enforcement stand-in) — 6/6 tests passing, including a negative test confirming
`crypto.subtle.exportKey` genuinely rejects for all three imported keys.

**A genuine architecture gap was found and correctly not silently resolved**: `SecretStore`'s frozen
trait is fully synchronous, but every `crypto.subtle` operation is Promise-based, and there is no safe
way to block a single-threaded `wasm32-unknown-unknown` call on an in-flight Promise without a
`SharedArrayBuffer`/`Atomics.wait` worker bridge (needs its own worker + `COOP`/`COEP` headers) or
Binaryen `--asyncify`, neither in scope here. The real logic lives in inherent `async fn store/use_key/
derive_key/nonextractable` methods (same names, so method-call syntax resolves to these); the actual
`impl SecretStore for WebCryptoSecretStore`'s three secret-touching trait methods deliberately return a
`StoreError::Backend` explaining the caller must use the async methods directly, rather than hang or
fabricate a result.

The combined review (security-reviewer + architect + code-reviewer) returned **PASS on all three lenses
for this task's own scope** — condition 1 implemented faithfully, no invented trait change, no bypass
path — after independently verifying the sync/async technical claim (confirmed no task-scoped alternative
exists, and that `Transport`, the sibling frozen trait, is already async throughout, suggesting
`SecretStore` was modeled without noticing this mismatch). The review flagged this as **load-bearing, not
cosmetic**: `meridian_identity::generate_account`/`sign` — the actual `&dyn SecretStore` call sites
production code uses — will always fail against a `WebCryptoSecretStore`, so task 12.13 cannot reuse
those shared helpers as-is without a resolution. Recorded as 12.13's own required first step (an architect
consult via an ADR 0026 amendment, mirroring the 7.5/11.8 precedent for a pre-check landing inside the
task itself) rather than blocking 12.5's own completion — see
[12.13's Risks/notes](./12.13-browser-wasm-adapter.md#risks--notes).

Two should-fix/nit findings were closed in a same-task follow-up commit: the SHA-512 digest intermediate
in the X25519-conversion path (secret-equivalent pre-clamp scalar material) is now wrapped in
`zeroize::Zeroizing`, matching the function's own doc claim and this crate's established discipline; a
stale `StoreError::Backend` doc comment was corrected to cover its new wasm-specific meaning; and the
`sync_trait_methods_are_honest_not_hanging` test now exercises `use_key`/`derive_key` through dyn dispatch
too, not just `store`. Re-verified clean (`cargo check`/`clippy`/`fmt` for `meridian-store` wasm32 target,
native suite 5/5 no regression); the live browser re-run was skipped for this follow-up since no
version-matched Chromium+ChromeDriver pair remained available in the sandbox at that point (the original
6/6 pass was independently confirmed by the review's own source-level read, though not re-executed by the
reviewer directly for the same environment-brittleness reason).
