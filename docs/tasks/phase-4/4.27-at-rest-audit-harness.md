# 4.27 — At-rest audit harness

**Phase:** 4 — Verification & Trust + Terminal TUI Client · **Feature:** T17 — Terminal TUI Client · **Depends on:** 4.15, 4.16, 4.19, 4.20, 4.22 · **Status:** done

## Goal
Prove, end to end, that no file the TUI writes ever contains a message body, petname, key material, or
contact-identifying content (pubkey, `mrd1:` id) in plaintext — the on-disk counterpart to
`demo opacity-audit`, and one of T17's explicit acceptance criteria. Per
[ADR 0021](../../adr/0021-client-local-store-config-formats.md) condition 2, `state.json` specifically
must contain none of these — its conversation reference is an opaque, non-identifying handle only.

## Scope
- **In:** script a full conversation headlessly (onboard → add contact → chat → verify) driving the
  `App::update` function directly (no real terminal needed, since `update`/`render` are pure), then scan
  every file the run wrote and assert none contains a message body, petname, key material, or
  contact-identifying content (pubkey hex, `mrd1:`-prefixed id) in plaintext.
- **Out:** the store's sealing implementation itself (4.15 owns it) — this task is the audit that
  exercises it under realistic usage, not a redesign.

## Deliverables
1. `apps/tui/tests/at_rest_audit.rs` (or a harness under `harnesses/`, matching `demo opacity-audit`'s
   pattern): scripted conversation + file scan + assertion.

## Risks / notes
- **Failing this test is a security defect, never something to relax.** If it fails, the leak gets fixed
  in the store (4.15) or the screen writing the offending data — the audit itself never gets loosened.

## Tests
`cargo nextest run -p meridian-tui --test at_rest_audit`

## Reviews
- **security-reviewer** — required.
- **test-engineer** — required; harness design/coverage.

## Status
Done. `apps/tui/tests/at_rest_audit.rs` scripts a full headless conversation (onboard → add contact with
a petname → open the conversation → send an outbound message → simulate one inbound message → leave a
pending outbox entry → verify the contact → write one `config.toml` setting) and recursively scans every
file under the resulting `$MERIDIAN_HOME` for plaintext message bodies, the petname, the contact's
pubkey/`mrd1:` id (both string and raw-byte forms), asserting zero matches — plus a dedicated ADR
0021-condition-2 check that `state.json`'s conversation reference is the opaque 16-byte handle, never the
peer's identity. Since `run_worker` has remained a no-op stub through every task in this phase, the
harness plays a minimal real "worker" itself: for each `Effect` the scripted `App::update` sequence
produces, it calls the actual store function (`contacts::save`, `history::append`, `outbox::save`,
`state::save`, `TrustStore::seal_at_rest`, `config_write::write_setting_at`, etc.) against a real temp
directory — `run_worker` itself untouched. A non-vacuity test proves the scan primitive itself would
catch an injected leak. No genuine leak was found.

**Review (both `security-reviewer` and `test-engineer` required, run in parallel):** one HIGH security
finding, one LOW security finding, and two non-blocking test-engineering notes, all fixed and
re-confirmed clean:
- **HIGH:** the harness originally sealed `ChatState::default()` — an empty vault, empty session map —
  into `sessions.bin`, so the audit's own explicit "key material" acceptance criterion
  (`docs/testing/strategy.md` §5b) was formally unverified for the one file that would realistically hold
  it: no SPK/OTK secrets, no peer-keyed session, zero key-material markers anywhere in the scan. Distinct
  from `opacity.rs`'s wire-envelope audit and `apps/crypto/tests/at_rest.rs`'s synthetic-bytes mechanism
  test — no test anywhere previously sealed a real, populated session to disk and scanned it. Fixed by
  running a genuine X3DH exchange (real bundle generation, real signature-verified session establishment,
  deliberately OTK-free so the OTK secret stays unconsumed at seal time) so `sessions.bin` seals a
  populated `PrekeyVault`/`Session` with real SPK secret, OTK secret, and session header-key markers
  added to the scan. The security-reviewer independently traced the full X3DH/ratchet chain — including
  the specific claim that a session's header key is promoted verbatim from `nhkr` into `hkr` on the first
  ratchet step, confirmed happens before this harness's own seal call — to confirm the fix is genuinely
  sound, not superficial.
- **LOW:** the "sealed files are really ciphertext, not just JSON that happens not to match" sanity
  check used a JSON-parseability test for `trust.bin`/`sessions.bin`, which are CBOR pre-seal — raw CBOR
  essentially never parses as JSON regardless of whether encryption ran, so the check was vacuous for
  those two files specifically (would pass identically even if sealing were silently skipped). Fixed
  with a genuinely falsifiable direct CBOR-decode-should-fail check against the real types.
- **Minor, also fixed:** a module-doc overclaim about which effects execute "for real" (only
  `PersistHistory` does; `SendMessage`'s own outcome is fabricated exactly like the faked network
  effects, just previously without the same explicit callout), and a vacuous length-only assertion that
  tested nothing beyond what the type system already guaranteed.

`cargo test -p meridian-tui --test at_rest_audit` (2/2), `cargo test -p meridian-tui` (full suite),
`cargo test -p meridian-cli --bins`, `cargo fmt --check`, `cargo clippy --workspace --all-targets -- -D
warnings`, and `bash tools/lint-tui-no-cli.sh` all clean.
