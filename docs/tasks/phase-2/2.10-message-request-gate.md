# 2.10 — First-contact message-request gate (client-side, §3.5)

**Phase:** 2 — Cross-Org Federation · **Feature:** T06 — Cross-Org Federation · **Depends on:** — · **Status:** done

## Goal
A first envelope from an unknown key lands in a segregated message-request state showing the sender's
key/safety-number and the encrypted intro; no further envelopes are accepted until the user accepts.

## Scope
- **In:** request state in `apps/core` chat state; accept/reject; the accept prompt in the CLI;
  persistence inside the sealed-at-rest `ChatState`.
- **Out:** contact tokens and PoW stamps (explicitly T08/T14); the finalized UX, which Feature 08
  consumes "from T06"; **any** server-side component.

## Deliverables
1. `apps/core/src/chat.rs`: `MessageRequest`, `pending_requests`, `accept_request` / `reject_request`,
   and the gate in `open_inbound`.
2. `apps/cli/src/chat.rs`: the `message request from mrd1:<alice>… — accept? y` prompt from the
   feature spec's demo script.
3. `apps/core/tests/message_request_gate.rs`: first contact is gated; a second envelope pre-accept is
   refused; post-accept flows normally; the gate survives the at-rest seal/open round trip; rejection
   does not leak whether the key is known.

## Risks / notes
- **Hard invariant: this gate is client-side only.** A server-side "have these two talked before?"
  table is a materialized contact graph —
  [anonymity-and-retention.md](../../security/anonymity-and-retention.md) must-never #2. Any proposal
  to put it in `meridian-rendezvous` must be refused and routed to the architect.
- It must not become an OTK-depletion oracle: gating happens **after** signature verification and
  session establishment, so a rejected first contact still consumes an OTK. Record that honestly
  rather than restructuring the handshake around it.
- `TODO: confirm`: exactly where the T06/T08 line falls on the request-queue UX. Keep T06 minimal —
  Feature 08 owns finalization.
- `TODO: confirm`: which side holds the queue. [system-design.md §3.5](../../architecture/system-design.md)
  says first-contact envelopes land in "a segregated 'message request' state" without saying where;
  this task asserts client-side, and the architect should confirm that reading is binding.
- Genuinely parallel — touches only `apps/core` and `apps/cli`, zero server overlap. Can start
  immediately.

## Outcome
`apps/core/src/chat.rs`: `MessageRequest`, `ChatState::pending_requests` (part of the same
sealed-at-rest struct, `#[serde(default)]` so old state still opens), `accept_request`/
`reject_request`, gate inside `open_inbound` only — `open_bytes`'s crypto/verification path is
untouched, so a rejected first contact still consumes the OTK it cost (documented honestly, not
restructured around, matching the precedent set at task 1.33). `apps/cli/src/chat.rs`: the
`y/n` + safety-number accept/reject prompt. Both `TODO: confirm` items resolved as the task
anticipated: client-side-only (confirmed **binding**, not just asserted, by architect — a
server-side queue would be a materialized contact graph per anonymity-and-retention.md must-never
#2) and `open_inbound`-only scope (confirmed acceptable for this task's literal deliverables).

**Known gap, tracked not hidden:** the gate is structurally inert on the P2P session-signaling path
(`session connect` bypasses it — the crypto session installs via `open_bytes` before any chat
content flows). All three reviewers independently traced and confirmed this is real and already
reachable via a shipped command, not hypothetical. Tracked as
[2.14](./2.14-p2p-message-request-gate.md) rather than left as an implicit "Feature 08 will handle
it." `docs/security/threat-mitigation-matrix.md`'s mitigation entry corrected to caveat the current
coverage; a regression test in `apps/core/tests/p2p_session.rs` pins today's ungated behavior so
2.14 changes it deliberately.

**Reviews:** architect — consistent; confirmed both open questions, required 2.14 be tracked
explicitly. security-reviewer — APPROVE-WITH-CHANGES; same required tracking + the
threat-mitigation-matrix caveat, both applied. test-engineer — PASS, no required fixes; mutation-tested
the new suite (non-vacuous) and the four pre-existing test files' auto-accept shims (legitimate, none
mask a gating bug).

Tests: `cargo nextest run -p meridian-core --test message_request_gate` (7/7 pass),
`cargo nextest run -p meridian-cli` (25/25 pass), full `meridian-core` suite 53/53 pass, clippy/fmt
clean on both crates.
