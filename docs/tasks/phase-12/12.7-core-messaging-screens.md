# 12.7 — Core messaging screens: chat + contacts + message-requests

**Phase:** 12 — Browser & Desktop Clients · **Feature:** T11 · **Depends on:** 12.2 · **Status:** done

**User surface:** this task **is** a client surface (browser + desktop, once wired by 12.14/12.15) — the
new-platform equivalent of the terminal client's existing chat/contacts/message-request screens (Phase
4, tasks 4.19–4.21). No TUI surface applies to *this* task: those TUI screens already exist and are
unaffected; T11 adds a second and third rendering of the same already-shipped capability, not a new one
(see [phase-12/README.md](./README.md#architect-consult-substratestoresigning-decisions-settled-before-task-breakdown)
point 5).

## Goal
Build the account-creation, contact-list, 1:1 chat send/receive, and first-contact message-request
accept/reject screens as Svelte components against `MeridianClientAdapter` (task 12.2), tested against
its fake implementation — reusable unmodified by both the browser (12.14) and desktop (12.15) shells.

## Scope
- **In:** account creation flow; contact list + add-contact; 1:1 chat view (send/receive, transcript);
  the message-request queue/accept/reject gate — T08's existing state machine surfaced in the UI, no new
  protocol logic. Bundled as one task because the message-request queue is a visible state *within* the
  chat/contacts view, not an independent screen — the same "forced, tightly-coupled" reasoning Phase 4
  used to bundle T08+T17 rather than split them.
- **Out:** verification/safety-number UI (12.8); file-transfer UI (12.9); wiring to a real backend
  adapter (that's the app-shell tasks 12.14/12.15 — this task only wires the *fake* adapter for its own
  tests); any new core-level operation beyond what 12.2's interface already exposes.

## Deliverables
1. `shared-ui/src/lib/screens/Chat.svelte`, `Contacts.svelte`, `MessageRequests.svelte` + their view-model
   stores.
2. Component tests against `FakeMeridianClientAdapter` covering: create account, add contact, send/
   receive a chat message, accept/reject a message request.

## Risks / notes
Trust-state UI must honor the block-on-verified invariant (system-design.md §4.4/D06) even before the
real verification screen (12.8) lands in the same phase — do not let this task's chat view silently
allow sending to an unverified-and-blocked contact; surface the existing `TrustState` from
`core-api-contracts.md` faithfully.

## Outcome
Landed under `shared-ui/src/lib/screens/` (not the task's literal `src/screens/`: 12.2 put everything under
`src/lib/` and the package entry is `src/lib/index.ts`; 12.8/12.9's deliverable paths were updated to
match): `AccountCreate`, `Contacts`, `Chat` (a thin `{#key peerId}` wrapper over `ChatConversation`, so each
peer gets its own view-model), `MessageRequests`, their Svelte 5 runes view-models, `copy.ts` (adapter
error codes → fixed UI strings; thrown messages are never rendered) and `safe-call.ts`. All written against
`MeridianClientAdapter` only — no new core operation was needed. 109 tests, `svelte-check` and `eslint`
clean.

**Trust invariant (D06).** Every send, retry included, goes through one choke point (`sendBody`) that
queries `getSendGate` fresh and proceeds only on exactly `ok`; the composer renders only for `ok` and
fails closed on `warn`, `blocked`, loading, a failed query, and an unknown gate kind. The gate `reason` is
rendered verbatim as a text node. Accept on a message request yields an *unverified* contact.

**Review (code-reviewer + security-reviewer, one combined pass):** both PASS, no blockers. The review
found and reproduced one real security should-fix (S1): `refreshGate()` returned its result even when a
newer query had superseded it, so a held-in-flight `ok` could still authorise a send after a
`trust-changed` flipped the gate to `warn` — only the adapter's mandatory re-check would have stopped it.
Fixed (a superseded or disposed query returns `null` and aborts the send) with a test for the exact race
and for query failure/unknown-kind/never-answering at send time; mutation-checked (removing the guard
fails the new tests). Also fixed: a delivery receipt arriving before `sendMessage` resolved was lost
(C1), stale header/trust label (C2: `syncContact` from the prop), a throwing shell callback being shown
as an operation failure (C3), and the nits (neutral "device storage" wording, passphrase cleared on radio
switch, duplicate-key `{#each}` safety, brittle test query).

**Not in scope, left for later tasks (stated, not claimed away):** account *unlock* for a locked account
(`loadAccount` returns `locked`); `registerAccount`/`publishBundle` UI (no server URL/invite entry —
`TODO: confirm` for the shells, 12.14/12.15); contact-detail actions (rename, block, delete, policy
override — so the UI cannot yet set a user-block; tests drive it through the adapter); an
acknowledge-key-change action for `warn`, which is a dead end until 12.8's Verify screen lands (there is
deliberately no "trust anyway"). `TODO: confirm`: whether a real adapter's `sendMessage` also writes the
transcript (the view-model upserts by `mid`, so either works); whether the hint is required at account
creation; core's grouping format for a request's `safetyNumber` (shown verbatim). The fake records a queued
message as history state `pending` while the view shows `sent` + a queued notice (per `tui-client.md` §7);
they would differ only on a history reload, which no test exercises. JS strings can't be zeroised: the
passphrase state is cleared on every path, but the engine's copy can't be guaranteed gone.
