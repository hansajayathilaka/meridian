# 12.17 — {CLI, browser, desktop}² interop matrix CI job

**Phase:** 12 — Browser & Desktop Clients · **Feature:** T11 · **Depends on:** 12.14, 12.15 · **Status:** in progress

**User surface:** none directly — CI verification infrastructure. No TUI surface applies.

## Goal
Ship the feature spec's deliverable 2: a CI job driving the {CLI, browser, desktop}² interop matrix
(chat, file, verify — 9 cells) proving cross-implementation interop, using the already-shipped CLI
(T04–T09) unmodified as one leg.

## Scope
- **In:** a new CI workflow (`.github/workflows/interop-matrix.yml`) and driver script(s) under
  `harnesses/interop-matrix/`, spinning up the rendezvous stack (reusing `demo/two-orgs`-style
  orchestration where applicable), and driving each of the 9 {sender, receiver} × {chat, file, verify}
  combinations across `apps/cli`, a headless-browser instance of `apps/web` (12.14), and
  `apps/desktop`'s debug build (12.15).
- **Out:** fixing any interop defect this job discovers beyond what's clearly a CI-harness bug — a real
  cross-client interop defect found here is a new finding for the phase-exit task (12.20) to record and
  potentially spin off a fix-task for, mirroring Phase 10/Phase 8's own precedent of not lowering the bar
  when a live check finds a real gap.

## Deliverables

2. `harnesses/interop-matrix/run.sh` (or per-cell scripts) driving all 9 cells.
3. 9/9 green on a clean run.

**Known, confirmed browser↔native interop defect, found by task 12.11's own review — read before
running the chat/file cells.** `apps/wasm/src/transport.rs`'s `stream_id_for_label` uses modulus `1_000`
while `apps/transport/src/webrtc_backend.rs`'s native equivalent uses modulus `65_534` — for the same
channel label (e.g. `"mrd.ctrl/1"`), the two pure functions compute different negotiated SCTP stream ids
almost always (~1/65 coincidence chance). A pre-negotiated data channel needs both sides to agree on the
numeric id, so a real browser↔native session is expected to fail to line up `mrd.ctrl/1` (and any other
label) until this is reconciled — likely by widening the browser-side modulus back to match, once
whatever caused Chrome to reject the wider range (task 12.11's own finding: `RTCPeerConnection::
createDataChannel` throws `OperationError` for at least one 65,534-range id) is root-caused. This is a
tracked carry-forward (see [tracker](../README.md#live-carry-forwards-not-owned-by-any-open-task)), not
something to silently work around inside this task's own harness — expect the browser↔CLI/browser↔desktop
cells to need this fixed first, or file a dedicated fix-task if this task's own run surfaces it live.

**Known, confirmed blocker found by task 12.13's own review — read before scoping the matrix.** The
browser leg (`apps/web`, task 12.14) is real for account creation and proves the WebRTC transport
substrate end to end, but `meridian-wasm` exports identity operations only — zero `ChatState`/
`TrustStore`/session wasm-bindgen surface exists. Every browser-involved cell of this matrix (browser as
sender or receiver, for chat/file/verify) is therefore expected to fail today, not because of a CI-harness
bug, but because the underlying capability doesn't exist yet — a new `WasmSession`/`WasmChatState` wasm
crate addition is needed first (not scoped to any open task; see
[12.13's Outcome](./12.13-browser-wasm-adapter.md#outcome)). Building this task's full literal 9/9 matrix
today would mean either (a) fabricating passing cells that don't test real functionality, or (b) building
real infrastructure for combinations that cannot pass until that follow-up lands. Per this repo's own
precedent for narrowing a task's deliverable when a genuine capability gap blocks it (tasks 11.8, 12.13),
this task should build the real, working parts now rather than block entirely: a real, green
CLI×desktop sub-matrix (both are full native `meridian-core`, no known gap) for chat/file/verify, plus a
real, green browser smoke-test (account creation + raw `BrowserTransport` connectivity, mirroring 12.13's
own already-passing test) — with the browser-messaging cells explicitly reported as blocked-on-a-named-
gap in the workflow's own output/summary, not silently skipped or faked green. Treat "9/9 green" as this
task's aspirational literal wording, not its actual acceptance bar today — the real bar is: every cell
that CAN genuinely pass, does; every cell that can't, says so and names why.
