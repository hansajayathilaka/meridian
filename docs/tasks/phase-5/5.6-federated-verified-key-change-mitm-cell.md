# 5.6 — Federated mitm-sim cell: verified-contact key-change block

**Phase:** 5 — Review of Phase 4 · **Feature:** review fix (F6) · **Depends on:** 5.5 · **Status:** done

## Goal
Close the coverage gap in T08's trust-state matrix (task 4.10): it has no federated (cross-org) cell
for an already-**verified** contact's key-change block. The existing federated cell (from task 2.12)
only proves fresh-contact (TOFU) rejection. A2×2 (colluding org servers) is a named threat-model
adversary — this is a real, not hypothetical, coverage gap.

## Scope
- **In:** A new `harnesses/mitm-sim` cell combining 2.12's two-server (colluding-org) topology with
  4.10's verified-contact key-substitution assertion.
- **Out:** Any new trust-state-machine logic — this is coverage only, exercising already-correct logic
  in a federated configuration it hasn't been proven against yet.

## Deliverables
1. A new mitm-sim cell: two colluding federated servers attempt a key substitution against an
   already-verified cross-org contact; asserts the client fails closed (`TrustState::Blocked` / no
   session installed), mirroring the existing single-org verified cell's assertion shape.
2. `harnesses/mitm-sim/README.md` updated to list this cell, keeping the "Not modelled" section
   accurate.

## Status
**Done.** New `apps/cli/tests/mitm_federated_verified_contact.rs` combines 2.12's real two-server
colluding-org topology with a genuinely-`Verified` contact state (reached via the real `contact add` +
`verify --scan-file` CLI round trip), closing the gap: neither 2.12 (federated, TOFU-only) nor 4.10
(verified, single-org-only) previously covered this state × topology combination.

**Two tests, two layers**:
1. **Fetch layer** — a real federated bundle fetch from the malicious, colluding org attempts a genuine
   key substitution (`apps/rendezvous/src/auth.rs::substitute_bundle`, confirmed by `test-engineer`'s
   mutation testing to generate an independently-derived key and re-sign under it, not merely corrupt a
   signature). Asserts `SignalError::BundleVerification` fails closed, and that the pre-existing Verified
   trust record survives byte-identical. That second half is honestly documented (mirroring
   `mitm_preexisting_contact.rs`'s own precedent, per a should-fix both review passes independently
   raised) as currently a **structural** guarantee — `fetch-bundle` never touches `TrustStore` today —
   not an empirically-exercised proof, while still being real regression coverage against a future
   refactor that wires it in.
2. **Decision-gate layer** — drives `meridian_core::desync::attempt_recovery` directly (a live fetch
   structurally cannot deliver a substituted bundle, confirmed sound by security-reviewer against
   `verify_bundle`'s exact-key pinning). The security-reviewer found this test's call shape/assertions
   are functionally identical to the pre-existing single-org `Verified` cases (`desync_recovery.rs`,
   `session.rs`), since `attempt_recovery` is I/O-free and topology-agnostic — the "federated" framing
   here is narrative, not an exercised property. This directly contradicted `harnesses/mitm-sim/README.md`'s
   own stated reasoning for *not* adding a federated **pinned**-case decision-gate cell ("would be
   vacuous, code-identical"). Resolved by relabeling this test honestly as a **topology-agnostic
   regression-consistency pin** (completing the fetch+decision-gate pairing for the `Verified` state,
   with real mutation-testing-confirmed regression value) rather than claiming federation-specific
   coverage, and reconciling the README's two paragraphs under one consistent rationale instead of
   asserting contradictory things about symmetric cases.

**Coverage-only, as scoped**: `apps/core/src/trust.rs` confirmed byte-for-byte untouched by every review
pass. The new `allow_test_tamper` config flag (`apps/rendezvous/src/config.rs`) predates this task
(1.12/1.28/2.12); this task's only touch is a new test-harness helper
(`boot_federated_pair_bidirectional_with_b_tamper`) arming it for this crate's own dev-dependency graph —
confirmed by security-reviewer to introduce no new production surface, still gated behind the
`test-tamper-hook` cargo feature (off in normal/release builds, CI-enforced).

`harnesses/mitm-sim/README.md` updated with the new cell's row and a reconciled scope-boundary
explanation.

### Review round
`security-reviewer` — **PASS**, no blocking issues (a first pass without shell access did a thorough
static read and correctly flagged both should-fix findings from source inspection alone; both closed
above). Confirmed `trust.rs` untouched, `allow_test_tamper` correctly test-gated, no anonymity/"must
never" list violation (diff touches zero production code).

`test-engineer` — **PASS**, no blocking issues. Independently mutation-tested both tests: disabling

genuinely load-bearing, not vacuous, despite test 2's topology-agnostic nature. Confirmed the new harness
helper doesn't regress its three existing callers (ran all three explicitly). Confirmed this is a
genuinely new state × topology cell, not a copy-paste of existing coverage.
