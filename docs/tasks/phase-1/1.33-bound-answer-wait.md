# 1.33 — Bound the dialer's wait for an answer (`recv_sdp`)

**Phase:** 1 — Review of Phase 0 · **Feature:** on-the-fly (surfaced by 1.28) · **Depends on:** — ·
**Status:** pending

## Goal
`recv_sdp` (`apps/core/src/session.rs`) awaits the peer's offer/answer with **no timeout**, so a
dialer whose answer never arrives hangs indefinitely with no diagnostic. Bound it and surface a
distinct, diagnosable error.

## Background
Found running 1.28's adversarial test: with a hostile relay rewriting routed blobs, the **responder**
rejects immediately (`SessionError::Chat(ChatError::BadSignature)`), but the **dialer** then waits
forever for an answer that will never come. Confirmed by security-reviewer, which added two reasons
this is a defect rather than a design choice:

1. **The codebase already treats this exact pattern as a bug elsewhere.** `session.rs`'s bounded
   `transport.selected_path()` wait carries the comment *"without this, that failure mode hangs
   `dial`/`answer` forever instead of erroring out cleanly"*. The signaling-side await is the same
   class of unbounded wait, left unbounded — an inconsistency.
2. **It is reachable with no adversary at all, and leaks resources.** A peer that is simply offline or
   never answers produces the identical hang, and while hung the dialer holds a live transport
   session / ICE agent / UDP sockets — exactly what the per-attempt cleanup elsewhere in `session.rs`
   works to avoid.

**Severity: availability only.** Nothing is downgraded and no session is established, so this sits
inside threat-model goal 6's conceded "a malicious server can deny service". It is a
reliability/diagnostics defect, not a security one.

## Scope
- **In:** a bounded wait in `recv_sdp` with a distinct `SessionError` variant (e.g. `AnswerTimeout`)
  so the failure is diagnosable and distinguishable from tampering; close the connection on it; a
  test. Once it lands, 1.28's `relay_rewrite.rs` can tighten its dialer arm from `StillWaiting` to
  the new error and drop most of its 10-second `SIDE_TIMEOUT`.
- **Out:** retry/backoff policy; changing the responder path, which already fails fast.

## Risks / notes
Must not weaken fail-closed behaviour: a timeout is "no session", never a degraded one. Worth one
sentence in the write-up — while hung, the dialer has already consumed one of the responder's OTKs
from the fetched bundle, so a hostile relay can repeat this as an OTK-depletion amplifier. Bounded
per-source per §3.5, so no new invariant break, but it belongs in the record.

## Tests
`cargo nextest run -p meridian-core` (timeout fires, error is distinguishable) · 1.28's
`relay_rewrite.rs` tightened afterwards.
