# 3.2 — Un-wedge the inbound s2s listener: concurrent, time-bounded accept

**Phase:** 3 — Review of Phase 2 · **Feature:** review fix (F2 + N5, **blocking**) · **Depends on:** — · **Status:** done

## Goal
One silent TCP connection to :8444 must not stop every other partner from federating.

## Scope
- **In:** split `FederationListener::accept` into a raw `tcp.accept()` (in the loop) plus a
  per-connection `finish_handshake` (mTLS + `FedHello`) spawned under `tokio::time::timeout`; a
  semaphore cap on concurrent in-handshake connections and on total live `serve_link` tasks (N5);
  config knobs with documented defaults.
- **Out:** outbound/dial timeouts (3.3); malformed-CBOR / unknown-op fuzzing of `serve_link` (3.22);
  per-peer link fairness beyond a global cap.

## Deliverables
1. `apps/rendezvous/src/federation/link.rs` — `FederationListener::accept_raw()` +
   `finish_handshake(tcp, peer_addr)`; a shared `with_deadline` helper that 3.3 reuses.
2. `apps/rendezvous/src/federation/inbound.rs` — `run_federation` (L412) loops on `accept_raw`,
   spawns handshake + `serve_link`, holds an `Arc<Semaphore>` permit for the link's lifetime; drops
   on permit exhaustion with a rate-limited stderr line carrying **no raw identifiers**.
3. `apps/rendezvous/src/config.rs` — `federation.handshake_timeout_ms`,
   `federation.max_concurrent_handshakes`, `federation.max_links`; fail-closed validation + unit
   tests alongside the existing `config.rs` test block.
4. `apps/rendezvous/tests/federation_link_dos.rs` — (a) a raw `TcpStream::connect` that sends
   nothing, then a legitimate mTLS dial completes **within a bounded assert**; (b) a connection
   stalled mid-length-prefix is dropped by the handshake timeout; (c) `max_concurrent_handshakes`
   stallers still leave the listener serving.

## Outcome
`FederationListener::accept` split into `accept_raw()` (bare TCP accept, stays in the loop) and
`finish_handshake(tcp, peer_addr)` (mTLS + `FedHello`, spawned per connection under a shared
`with_deadline` timeout helper — deliberately generic so 3.3's outbound path can reuse it). `run_federation`
now spawns each accepted connection into its own task gated by two independent
`Arc<Semaphore>`s: `handshake` (`max_concurrent_handshakes`, released the instant `finish_handshake`
resolves) and `link` (`max_links`, held for `serve_link`'s full lifetime) — a judgment call, since the
task file left one-vs-two semaphores open; two was chosen to map 1:1 to the two config knobs and to
let a stalled handshake and a long-lived link apply independent backpressure. Both use non-blocking
`try_acquire`: exhaustion drops the connection immediately (no queueing) via a rate-limited,
identifier-free stderr line (`DropRateLimiter`, ≤1 line/sec, static reason string only — no IP, no
cert CN/SAN).

New `federation.{handshake_timeout_ms,max_concurrent_handshakes,max_links}` config knobs, fail-closed
validated (reject 0). **`TODO: confirm`** — defaults 10_000 ms / 64 / 256 are the task file's proposed
values, not grounded in any existing design doc; flagged in `config.rs` comments at both the field
declarations and `Default` impl.

`apps/rendezvous/tests/federation_link_dos.rs` (new, 4 tests): (a) a silent TCP connection doesn't
wedge a subsequent legitimate mTLS dial; (b) a mid-length-prefix stall is dropped by the handshake
deadline; (c) exhausting `max_concurrent_handshakes` drops the next connection *promptly* (near-instant,
distinguishable from waiting out the full handshake timeout) then recovers once a slot frees; (d) new —
exhausting `max_links` (with the handshake cap kept generous) drops the next connection promptly
*after* it completes a full handshake, proving it's the link cap being exercised, not the handshake cap.

**Two-round review, both closed:**
1. Combined `reviewer` agent (security-reviewer + architect + code-reviewer lenses) — **pass, zero
   findings**. Confirmed: the permit check happens inline before `tokio::spawn` (no unbounded task
   spawn from a connect/disconnect flood); no new dependency, `meridian-rendezvous` still depends only
   on `meridian-proto`; ADR 0017 C7 preserved (mTLS still terminates in-process); permit RAII holds
   correctly across early returns/panics; `DropRateLimiter`'s mutex serializes concurrent drops
   (closes the double-log bug the implementer caught and fixed during self-review). One pre-existing,
   out-of-scope observation noted but not actioned: the (unchanged) inbound rejection log can
   interpolate `LinkError::DomainMismatch` cert strings — predates this task, not a 3.2 regression.
2. **test-engineer mutation-check** — found two real coverage gaps via actual mutation (not just
   review-by-reading): (i) test (c) as originally written still passed when `handshake_slots` was
   patched to 1,000,000 permits (i.e., an unenforced cap), because it only asserted eventual recovery,
   never that the cap blocked anything; (ii) `max_links` (N5's other half) had zero test coverage.
   Both closed in a follow-up round: (c) strengthened to assert the over-cap connection is rejected
   *promptly* (a `try_acquire`-failure-shaped signal), and new test (d) added for `max_links`. Both
   fixes independently re-verified by mutation (patching the respective semaphore to 1,000,000 permits
   and confirming the strengthened/new test now fails) before being accepted.

No source seam was needed for the added tests — both are exercised black-box via connection/read
behavior (`serve_link`'s post-handshake read is what naturally holds a link permit open).
