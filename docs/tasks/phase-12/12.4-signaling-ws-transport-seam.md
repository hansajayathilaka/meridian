# 12.4 — `meridian-signaling` WebSocket transport seam

**Phase:** 12 — Browser & Desktop Clients · **Feature:** T11 (substrate completion, not the feature
itself) · **Depends on:** 12.1 · **Status:** pending

**User surface:** none — internal substrate seam, no user-visible behavior change on the native path.
No TUI surface applies.

## Goal
Close the second half of the wasm32-buildability gap the architect consult found (see
[phase-12/README.md](./README.md#architect-consult-substratestoresigning-decisions-settled-before-task-breakdown)
point 3): `meridian-signaling`'s `SignalingClient` hardcodes `WebSocketStream<MaybeTlsStream<TcpStream>>`
(via `tokio-tungstenite`), which has no `wasm32-unknown-unknown` story at all. Introduce a small internal
trait so a browser build can swap in the browser's native `WebSocket` (via `web-sys`/
`wasm-bindgen-futures`) while native builds keep `tokio-tungstenite` byte-for-byte unchanged. This is
**not** one of the two frozen `core-api-contracts.md` traits (`Transport`/`SecretStore`) — it is an
internal implementation seam local to `meridian-signaling`, so it raises no stability-policy question.
Passing `cargo check -p meridian-signaling -p meridian-core --target wasm32-unknown-unknown` here is
what finally proves the full `meridian-core` wasm32 build green, closing the arc 12.1 started.

**This finding and its fix shape were settled by an architect consult during `/plan-phase`** — this task
file implements that decision, it does not re-open it.

## Scope
- **In:** a new internal `WsConnection`-style trait inside `meridian-signaling`; `SignalingClient`
  refactored to use it instead of the hardcoded stream type, with an unchanged public API; a native impl
  wrapping the existing `tokio-tungstenite` stream unchanged (byte-identical handshake/wire behavior —
  no conformance-vector changes); a `wasm32` impl wrapping the browser's native `WebSocket` via
  `web-sys`/`wasm-bindgen-futures`; `Cargo.toml`'s `[target.'cfg(target_arch = "wasm32")'.dependencies]`
  split (drops `tokio-tungstenite`/`rustls` there, adds `wasm-bindgen`/`web-sys` for that target only).
- **Out:** any browser-UI-specific reconnect/backoff policy beyond what `SignalingClient` already does
  natively; the browser `Transport` shim (12.11, a separate trait entirely); any change to the WSS wire
  handshake itself.

## Deliverables
1. `apps/signaling/src/ws_transport.rs` — the `WsConnection` trait + native/wasm impls.
2. `apps/signaling/Cargo.toml` — target-conditional dependency split.
3. `SignalingClient` refactored onto the trait, public API unchanged.
4. `cargo check -p meridian-signaling -p meridian-core --target wasm32-unknown-unknown` passing (new
   `just`/CI step, extends 12.1's).
