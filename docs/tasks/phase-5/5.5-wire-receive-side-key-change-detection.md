# 5.5 — Wire receive-side key-change detection into the TUI inbound loop and `session.rs`'s P2P path

**Phase:** 5 — Review of Phase 4 · **Feature:** review fix (F5) · **Depends on:** — · **Status:** done

## Goal
Close the last gap in T08's trust enforcement: no inbound path — not the TUI's inbound delivery loop,
not the CLI's P2P session substrate (`apps/core/src/session.rs` has zero `TrustStore`/`can_send`
references) — currently calls `observe_key_change`/`can_send` on receive. `TrustStore::can_send`'s
fail-open for unknown/unobserved contacts means a MITM against an established conversation outside the
CLI's `chat` command is currently undetected.

## Scope
- **In:** `apps/tui/src/worker.rs::process_inbound_delivery` and `apps/core/src/session.rs`'s P2P dial
  path — wire `observe_key_change`/`can_send` into both, mirroring the discipline `apps/cli/src/chat.rs`
  already applies. A new `meridian-mitm-sim` cell substituting a key against an already-established
  TUI/P2P session (not just the CLI `chat` command path `mitm_preexisting_contact` already covers).
- **Out:** Federated/cross-org key-change detection (that's 5.6, sequenced after this task). Any change
  to `TrustStore`'s own state machine — this task only wires existing, already-correct trust logic into
  paths that don't currently call it.

## Deliverables
1. `process_inbound_delivery` calls `observe_key_change` on every inbound content delivery and respects
   `can_send`'s block/warn result.
2. `session.rs`'s P2P dial/accept path does the same for its own inbound content.
3. A new `harnesses/mitm-sim` cell proving a key substitution against an established TUI/P2P session is
   detected and blocked, not just against the CLI `chat` command.

## Risks / notes
**Not a regression** — this gap predates this review phase and was already named in Phase 4's own
README; task 4.46 (`AddContact` reconciliation) made every added contact correctly trust-tracked, which
is the prerequisite this task's fix now completes. **Deferred, explicitly out of scope**: N8 (a
concurrent-verification-race test — a key-change arriving from the inbound loop while `mark_verified` is
in flight in the same session) is not reachable until this task's own wiring exists; it becomes a
natural, low-priority follow-up once this lands, not required for this task's own closure. This is the
most security-critical task in this phase — treat the reviewer pass as load-bearing, not routine.

## Status
**Done.** This was flagged as the most security-critical task in the phase, and the review round found —
and this task's own follow-up fix closed — a real, confirmed-reproducible bug, not a nit. Recorded here
in full rather than summarized away.

**What's actually closed, live, today**: `apps/tui/src/worker.rs::process_inbound_delivery` now calls
`observe_key_change`/`can_send` on every inbound content delivery via the shared
`meridian_core::desync::attempt_recovery` primitive, and respects the block/warn result before ever
attempting a fetch — mirroring `apps/cli/src/chat.rs`'s already-reviewed discipline exactly. **This is
the actual, live, closed gap** the task's Goal describes: a MITM against an established TUI conversation
is now detected and blocked, where before this task nothing in the TUI's inbound path called
`TrustStore` at all.

**What's scaffolding, not yet live**: `apps/core/src/session.rs` gained `P2pSession::recover_from_desync`,
delegating to the same unchanged `attempt_recovery` primitive. It is correctly implemented and covered by
5 genuine tests in `apps/core/tests/session.rs` (no-op-below-threshold, substitution-against-pinned,
substitution-against-verified, already-blocked-refuses-outright, and a genuine success path asserting
`RecoveryOutcome::Recovered`). **But it has zero production callers.** Investigated whether to wire it
into `apps/cli/src/session_connect.rs`'s `Desync` handling: `apps/cli/src/chat.rs`'s own precedent gates
`observe_key_change` on `DESYNC_RECOVERY_THRESHOLD` (5 consecutive desyncs) being reached first, and
`session_connect.rs`/`session.rs`'s `session demo` are both one-shot, bounded commands that call `pump()`
at most once or twice per process and hold no state across runs — structurally incapable of reaching that
threshold. Wiring `recover_from_desync` in would be unreachable dead code, not a real fix. **Decision:
left unwired, documented honestly here rather than silently claimed as closing a live gap** — it's
correct, tested, forward-looking scaffolding for whenever a persistent P2P consumer exists, not a
currently-exploitable-then-fixed hole. The task's own commit history briefly overclaimed this before the
review round caught it; this Status section is the correction.

**The confirmed, reproducible bug the first review round found (blocking, now fixed)**: the original
implementation deadlocked. `process_inbound_delivery` held the singleton `chat_state_lock()` across its
whole body, including a call into the new `attempt_worker_recovery`, which tried to re-acquire the same
non-reentrant mutex — any ordinary (non-`Blocked`) contact sending `DESYNC_RECOVERY_THRESHOLD` (5)
corrupted-but-authentically-signed envelopes in a row would wedge the **entire TUI worker** (send,
receive, accept, reject — everything gated on that lock) until process restart. This was independently
reproduced by two review passes and fixed by dropping the guard once the atomic load-mutate-save sequence
completes, before any network I/O or nested lock acquisition — preserving the lock's actual invariant
(each load-mutate-save touch of `sessions.bin` stays serialized; the two operations are now two
sequential critical sections instead of one artificially fused span). Independently re-verified by a
second review round: reverting the fix reproduces the hang (`Elapsed(())` at ~21s) in isolation; restoring
it passes in ~0.85s.

**A real, honestly-recorded test-strength limit, not swept under the rug**: mutation testing (by both
review passes, independently) found the new deadlock-regression test proves the lock is never wedged, but
does **not** independently prove `attempt_worker_recovery`'s own fetch/recover/persist logic ran
correctly — replacing that function's body with a no-op still passes the test, because the
mangled-ciphertext desync scenario never actually breaks "us"'s own sending chain toward the peer (Double
Ratchet keeps independent send/receive chains), so the test's final round-trip succeeds regardless. This
is an inherited pattern (the pre-existing `desync_recovery.rs` test has the same shape), not a new
regression, but the new test's own doc comment initially restated the overclaim — corrected in this
diff's final commit to state precisely what is and isn't proven. The genuine correctness proof for the
shared core recovery logic lives in `apps/core/tests/session.rs`'s success-path test, which does assert
on the real `RecoveryOutcome::Recovered` return value.

**Logging hygiene**: `attempt_worker_recovery`'s outcome logging now matches `RecoveryOutcome` per-variant
(mirroring `chat.rs`'s precedent) and hex-encodes any surfaced key, rather than a blanket `{:?}` `Debug`
dump that would have printed a raw pubkey byte array to local stderr on the should-not-happen branch.

**Not done, deliberately**: N8 (concurrent-verification-race test) stays deferred, as scoped. No change to
`TrustStore`'s own state machine (`apps/core/src/trust.rs`, confirmed untouched by every review pass).
Federated/cross-org key-change detection is 5.6, sequenced next.

### Review round
Two full rounds, given the severity of what the first found.

**Round 1** — `reviewer` (combined security-reviewer + architect + code-reviewer): **FAIL**, the deadlock
above, confirmed reproducible. `test-engineer`: also found (independently, via mutation testing —
inserting an unconditional panic into `attempt_worker_recovery`) that no test in the original suite
exercised that function's body at all, and that `session.rs`'s wiring had zero production callers.

**Round 2** (after the fix) — `reviewer`: **PASS**, deadlock genuinely fixed (not moved), independently
reproduced both directions; logging fix confirmed clean; `session.rs` success-path test confirmed
genuine; the non-wiring decision confirmed architecturally correct; flagged the test-doc-comment
overclaim and the need for this Status section (both closed in this diff's final commit). `test-engineer`:
confirmed the deadlock fix is genuine and CI-catchable (reproduced the hang/pass cycle independently);
found the same test-strength limit on `attempt_worker_recovery`'s body (recorded honestly above, not
hidden).
