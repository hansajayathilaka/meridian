# 7.2 — Zeroize discarded/peeked OTK and SPK secret copies

**Phase:** 7 — Review of Phase 6 · **Feature:** review fix (F3, F4) · **Depends on:** — · **Status:** pending

## Goal
Close two secret-handling gaps in `apps/core/src/chat.rs`'s `PrekeyVault`/responder-session code
family: a discarded-without-zeroizing OTK secret in `commit_responder_otk` (F3, new — introduced by
task 6.3's peek/commit split), and un-`Zeroizing`-wrapped peeked SPK/OTK secret locals in
`establish_responder_session_provisional` that are now routinely attacker-triggerable under C2 (F4, a
pre-existing carry-forward from `docs/tasks/README.md`'s Live carry-forwards, left unowned since 6.3).

## Scope
- **In:** `apps/core/src/chat.rs`, two adjacent functions:
  - `commit_responder_otk` (~line 1847): `let _ = self.vault.take_otk_secret(&opk);` discards the
    returned `[u8;32]` without zeroizing. Fix using the `zeroize::Zeroize` trait already imported
    (line 34): zeroize the returned secret before it drops.
  - `establish_responder_session_provisional` (~line 1799): `spk_secret`/`opk_secret` locals are plain
    `[u8;32]`/`Option<[u8;32]>` stack copies from `PrekeyVault::peek_spk_secret`/`peek_otk_secret`. Wrap
    in `zeroize::Zeroizing<[u8;32]>` at the point of receipt; adjust the `Session::respond(...)` call
    site for the resulting deref/unwrap.
- **Out:** No behavior change — decrypt outcomes, error variants, and commit ordering must be
  byte-identical before/after. No new dependency (`zeroize` is already a direct `meridian-core`
  dependency, `apps/core/Cargo.toml:26`).

## Deliverables
1. `commit_responder_otk` zeroizes the discarded OTK secret before drop.
2. `establish_responder_session_provisional`'s `spk_secret`/`opk_secret` wrapped in `Zeroizing`.
3. No new test file — zeroization of short-lived stack memory isn't independently observable via the
   existing test harness; acceptance rests on code review + unchanged regression behavior across the
   adversarial suites listed below.

## Risks / notes
Touches the same file as 7.1 (`apps/core/src/chat.rs`) but disjoint line ranges (7.1: ~1652-1665 + a new
test cell; 7.2: ~1799-1851) — safe to land independently/in parallel, no merge-order requirement.
