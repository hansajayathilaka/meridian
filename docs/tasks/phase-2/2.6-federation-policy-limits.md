# 2.6 — Federation policy (`open | allowlist | closed`) + edge rate limits

**Phase:** 2 — Cross-Org Federation · **Feature:** T06 — Cross-Org Federation · **Depends on:** 2.4 · **Status:** done

## Goal
A pure, unit-testable decision layer: may this origin server federate with us, and is it within
budget — **per origin server and per origin account**, not either alone.

## Scope
- **In:** `FederationPolicy` + allowlist; `admit(origin_domain) -> Decision`; two rate limiters reusing
  `apps/rendezvous/src/ratelimit.rs`; config and defaults; the outbound policy check.
- **Out:** wiring into handlers (2.7, 2.8); client-visible error copy (2.9).

## Deliverables
1. `apps/rendezvous/src/federation/policy.rs`: `FederationPolicy`, `Decision`, `FederationLimits`.
2. `apps/rendezvous/src/config.rs`: `policy`, `allowlist`, `fed_fetch_per_origin_per_min`,
   `fed_route_per_origin_per_min`, `fed_per_origin_account_per_min`.
3. `apps/rendezvous/tests/federation_policy.rs`: `closed` rejects everything **including** allowlisted
   domains; `allowlist` is **exact-match** — `evil-org-b.test` must not match `org-b.test`; `open`
   admits; per-origin and per-account budgets are independent; rate-limit keys are hashed via
   `logid::LogId` before any log line.

## Risks / notes
- Rate-limit keys are attacker-controlled. The growth-bound argument from task 1.20 (the amortised
  sweep that provably cannot reset a live budget) must be shown to still hold with a **third** key
  class.
- Per-origin-account limiting means the server holds `(origin_domain, account_key)` counters. They are
  transient and unlogged, but security-reviewer must confirm this is not a materialized cross-org
  contact graph ([anonymity-and-retention.md](../../security/anonymity-and-retention.md) must-never
  #2). The existing per-account limiters are the precedent.
- The claimed origin **account** is unverifiable across the boundary per ADR 0017 — so a per-account
  limit is only as good as the partner's honesty. That is bilateral by design
  ([ADR 0002](../../adr/0002-federation-mechanism.md) consequences), but it must be written down
  rather than assumed.
- `TODO: confirm`: default federation rate-limit values.
  [monitoring.md](../../operations/monitoring.md) already records federation thresholds as unspecified
  in the source documents.
- `TODO: confirm`: how much of a rejection reason may be relayed to the originating client.
  Distinguishing `closed` vs `allowlist` vs `rate_limited` vs `not_found` leaks Org B's policy **and**
  target-account existence, which §3.5's anti-enumeration stance cares about. 2.9 consumes the answer.

## Outcome
`apps/rendezvous/src/federation/policy.rs`: `FederationPolicy` (open/allowlist/closed — closed
structurally cannot consult allowlist state, allowlist is exact-match via `HashSet::contains`) and
`FederationLimits` wrapping three `RateLimiter` instances (task 1.20's amortised-sweep type, reused
not reinvented) for per-origin-fetch, per-origin-route, and per-origin-account budgets. `config.rs`
gained `FederationPolicyMode` (defaults `Closed`) and the five new `Federation` fields with
documented default rate-limit values (300/600/30 per minute). Deliberately unwired from any `fed_*`
handler (2.7/2.8's job) and builds no client-visible rejection copy (2.9's job) — `Decision`/
`RejectReason` carry internal structure only.

**Reviews:** architect — consistent; confirmed the pure-decision-layer task boundary was planned in
advance, not improvised, and that ADR 0002's bilateral-abuse framing plus ADR 0017 C5's key shape are
both implemented correctly. security-reviewer — APPROVE-WITH-CHANGES; traced all six required checks
against code (not narrative) and found one required gap: `policy.rs`'s module doc claimed
`tools/lint-no-raw-id-logging.sh` already enforces `LogId`-wrapping for `origin_domain`/
`origin_account`, but the lint's pattern didn't include them — fixed. code-reviewer — request-changes;
found a real bug via direct reproduction: `FederationLimits::check` spent the shared per-origin
budget on every call including from an already-over-budget account, so one claimed account's
rejected retries could starve every other account behind the same origin — the exact failure mode
the per-account budget exists to prevent. Fixed by checking the account budget first; a pinning test
added that fails under the old ordering.

Tests: `cargo nextest run -p meridian-rendezvous --test federation_policy` (15/15 pass), clippy/fmt
clean, `lint-no-raw-id-logging.sh` and `lint-server-no-core.sh` pass.
