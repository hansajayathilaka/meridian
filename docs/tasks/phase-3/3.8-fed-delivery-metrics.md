# 3.8 — Count federated deliveries in `envelopes_routed_total`

**Phase:** 3 — Review of Phase 2 · **Feature:** review fix (F8 + N4) · **Depends on:** 3.4 · **Status:** done

## Goal
Ops dashboards stop under-counting exactly the traffic Phase 2 added.

## Scope
- **In:** route inbound federated delivery through `deliver_one` (or call `metrics.envelope_routed()`
  there); replace `handle_fed_route`'s full CBOR re-encode-to-measure with `req.envelope.len()` (N4).
- **Out:** any new metric name or label. The allowlist is binding and there must be **no per-partner
  label** — that would materialize the cross-org contact graph (anonymity-and-retention must-never #2).

## Deliverables

2. A test in `apps/rendezvous/tests/federation_route.rs` asserting the counter increments once per
   federated delivery **and** that no new label appears.

## Outcome
`handle_fed_route` built and delivered a `Deliver` frame identically to the local (same-server)
route path, but discarded `registry.send_to`'s result and never called `metrics.envelope_routed()`
the way `ws.rs`'s `deliver_one` does for local routes — every federated delivery, the entire point
of Phase 2, silently went uncounted in `meridian_envelopes_routed_total` while local deliveries
were counted normally (F8). Fixed by adding a `metrics: &Metrics` parameter to `handle_fed_route`
and calling `envelope_routed()` when `send_to` succeeds — the minimal change given how much this
function's signature had already grown across 3.5/3.6, over the alternative of threading a full
`AppState` through to reuse `deliver_one` directly. No new metric name, no new label (in
particular no per-partner label, the anonymity-and-retention must-never the task's own Risk note
calls out).

Also replaced the same function's oversized-envelope defense-in-depth check — which re-encoded the
entire `FedFrame` via CBOR just to measure its length — with a direct `req.envelope.as_bytes().len()`
check (N4). Documented as a slightly more permissive approximation (undercounts by the fixed
`to`/`from` 64 bytes plus CBOR framing overhead) than the old full re-encode; acceptable because
`link::read_frame`'s cap on the real wire path is the load-bearing check, confirmed by reading it
directly — it rejects an oversized frame on the raw wire length prefix before `FedFrame::from_bytes`
ever runs, so this in-function check only ever guards non-wire/direct callers.

**Review (security-reviewer + code-reviewer, combined pass): clean, zero findings.** Confirmed
`Metrics::envelope_routed()` stays a bare, argument-free counter with zero labels, and the new
parameter is used for exactly one call site — no `origin_domains`/`metering_key`/`req.from`/
`req.to` threaded alongside it. The new no-new-label test scrapes a real `/metrics` endpoint after
a real two-server federated delivery (not a mock) and would genuinely fail if a `peer_domain` label
were added later. `tools/metrics-allowlist.txt` has zero diff. `bs_defense_in_depth_oversized_check_rejects_directly`
still meaningfully exercises rejection under the new measurement basis. Both new tests confirmed
non-vacuous by reasoning through the pre-fix code path.

**Tests:** `cargo nextest run -p meridian-rendezvous --test federation_route` 11/11; full `cargo
nextest run -p meridian-rendezvous` 160/160 (2 pre-existing `#[ignore]`s unrelated). `cargo clippy
-p meridian-rendezvous --all-targets --all-features` clean; `cargo fmt --check` clean; `bash
tools/lint-metrics-allowlist.sh` passes (this script only greps for `counter!`/`gauge!` macro
calls and finds 0 matches since `metrics.rs` is hand-rendered by design — a pre-existing scaffold

is the new HTTP-scrape test).
