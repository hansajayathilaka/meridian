# 8.2 — SQLite mailbox migration + `SqliteStore` impl

**Phase:** 8 — Offline Ciphertext Mailbox · **Feature:** T07 · **Depends on:** 8.1 · **Status:** done

## Goal
Make the mailbox durable across a server restart under the `sqlite` feature — losing reachability
only, never confidentiality, matching the rest of this store (rendezvous-protocol-v1.md §7/§8).

## Scope
- **In:** a new migration in `apps/rendezvous/src/store/sqlite.rs` creating the `mailbox` table
  exactly as specified in `data-model.md` (`id INTEGER PK`, `recipient_pub`, `blob BLOB`,
  `arrived_at`, `expires_at`, `size_bytes`), plus a `recipient_pub` index (list-for-recipient is
  the hot path); implement 8.1's trait methods against it via `sqlx`.
- **Out:** Postgres (still a later flag, unaffected by this task); route-path wiring (8.5/8.6);
  purge scheduling (8.9) — this task only proves the SQL is correct in isolation.

## Deliverables
1. Migration file adding `mailbox` (naming/location matching the existing `accounts`/`prekeys`
   migrations' convention in the same directory).
2. `SqliteStore`'s mailbox trait methods.
3. Integration tests (feature-gated `sqlite`) mirroring 8.1's in-memory test set exactly, so both
   backends are provably interchangeable — enqueue/list/delete-scoped-by-recipient/size-accounting.

## Risks / notes
Keep the schema byte-for-byte what `data-model.md` already documents — this doc was written
*before* this task specifically so the migration has no design decisions left to make. If a real
constraint (e.g. an index) isn't already named in `data-model.md`, add it in code and update that
doc's note rather than silently diverging (Definition of Task §6: sync docs on schema change).

## Tests
`cargo nextest run -p meridian-rendezvous --features sqlite --lib store::sqlite::`

## Reviews
- **security-reviewer** — schema matches the documented at-rest shape exactly (no extra columns
  that would widen what threat A7 learns).
- **code-reviewer** — migration correctness, parity with the in-memory impl's test set.

## Status
**Done.** Added a `mailbox` table migration to `SqliteStore` matching `data-model.md`'s schema
byte-for-byte (`id INTEGER PK AUTOINCREMENT`, `recipient_pub`, `blob BLOB`, `arrived_at`,
`expires_at`, `size_bytes`), plus a `recipient_pub` index (`idx_mailbox_recipient_pub`, not
previously named in `data-model.md` — added there per Definition of Task §6). Implemented all five
of 8.1's `Store` trait mailbox methods against it via runtime `sqlx` queries, matching
`MemoryStore`'s semantics exactly: `mailbox_delete_by_ids` scopes by both `recipient_pub` and `id`
in one atomic `DELETE ... WHERE recipient_pub = ?1 AND id IN (...)` built via `sqlx::QueryBuilder`
(bound parameters, no string interpolation) — a mismatched id is a silent 0-row no-op. `size_bytes`
is derived server-side from `blob.len()`, never caller-supplied. `blob` is bound/read as raw bytes
only, confirmed by `tools/lint-no-serde-on-blob.sh`.

7 integration tests mirror 8.1's in-memory suite exactly (enqueue/list ordering, delete scoped to
matching recipient + no-op for another recipient's id/unknown recipient, purge-expired boundary,
per-recipient size summation), plus one new durability test proving the actual point of this task:
a mailbox row survives dropping and reconnecting to the same file-backed DB.

### Review round
**reviewer** (security-reviewer + code-reviewer lenses) — **PASS**, zero blocking findings. Verified
the schema against `data-model.md`, the atomic recipient-scoped delete query directly, `size_bytes`
non-spoofability, opaque-blob discipline, and full parity with `MemoryStore`'s test set and edge
cases. One non-blocking should-fix, carried forward into task 8.7 (not this task's scope): a very
large `MailboxAck.ids` list could hit SQLite's bound-parameter limit via the unbounded
`QueryBuilder` — 8.7 (the only caller of this method with attacker-controlled input) should cap/chunk
the id list before calling it.
