# 4.15 — `meridian-tui::store`

**Phase:** 4 — Verification & Trust + Terminal TUI Client · **Feature:** T17 — Terminal TUI Client · **Depends on:** 4.2, 4.11, 4.13 · **Status:** done

## Goal
Land the sealed local JSON store — contacts, history, outbox — plus the deliberately-unsealed
`state.json`, per ADR 0021, with migrations and `--export-json`.

## Scope
- **In:** `contacts.json`, `history/<peer-pubkey-hex>.jsonl` (append-only), `outbox.json` — all sealed
  via `meridian_crypto::at_rest::seal` under the `SessionStoreKey/v1`-derived key
  ([tui-client.md §5](../../architecture/tui-client.md#5-local-store--configuration) schemas);
  `state.json` unsealed but constrained (no petname, message body, or key material — view geometry +
  conversation index only, an invariant this task's own tests check ahead of 4.27's full audit);
  migrations (version field per file, `.bak` before forward-migrating, refuse to open a newer schema
  than understood); `meridian tui --export-json <path>`.
- **Out:** UI screens consuming the store (4.16+); config (4.14, parallel).

## Deliverables
1. `apps/tui/src/store/`: `contacts.json`, `history/*.jsonl`, `outbox.json` (sealed), `state.json`
   (unsealed, constrained) types + read/write.
2. Migration machinery: version check, `.bak`, refuse-newer-schema error.
3. `--export-json` implementation.
4. Tests: sealed round-trip for each sealed file; `state.json` contains none of the prohibited fields
   (structural test, not just a manual check); forward migration from a v0 fixture; refuse-to-open on a
   fabricated newer-version fixture.

## Risks / notes
- This is the store the full at-rest audit (4.27) later exercises end-to-end — get the sealed/unsealed
  boundary exactly right here, since 4.27 is a should-never-need-to-relax test.

## Tests
`cargo nextest run -p meridian-tui --test store`

## Reviews
- **security-reviewer** — required; sealing correctness and `state.json`'s no-secrets invariant are
  exactly ADR 0021's binding conditions.

## Status
Done. `apps/tui/src/store/` (`contacts.rs`, `history.rs`, `outbox.rs`, `state.rs`, `mod.rs`,
`migrate.rs`, `export.rs`) implements the sealed local store — `contacts.json`, per-peer
`history/<peer>.jsonl`, `outbox.json`, all sealed via `meridian_crypto::at_rest::seal` under the
same `STORE_KEY_INFO`-derived key `sessions.bin`/`trust.bin` already use — plus the deliberately
unsealed, constrained `state.json`. Shared migration harness: version check, `.bak`-before-rewrite
(now itself crash-safe via `atomic_write`, not a raw write), hard refusal on a newer-than-understood
schema. `meridian tui --export-json <path>` (flag in `apps/cli/src/tui.rs`/`main.rs`, logic in
`apps/tui/src/store/export.rs`) is the sole plaintext-export path.

**Security review (required, sole named reviewer) — round 1 found three real issues, closed in a
fix pass, round 2 confirmed clean:**
1. **HIGH — ADR 0021 condition 2 violation.** `state.json`'s `last_conversation` stored the raw
   32-byte contact pubkey, letting anyone with mere filesystem read access (no account key) learn
   exactly which contact a device last talked to — exactly what condition 2's opaque-handle design
   exists to prevent. Fixed: `ContactRecord::conv_handle: Option<[u8; 16]>`, a purely random
   (`getrandom`, never derived/hashed from the pubkey) 128-bit token minted once per contact and
   persisted in the *sealed* `contacts.json`; only that token — a distinct byte length from a pubkey
   by construction — is mirrored into `state.json`. The structural no-leak test was strengthened to
   reject any byte-array leaf that is pubkey-shaped (32 bytes) or byte-identical to a real fixture
   pubkey, not just string leaves — closing the gap in the test itself, not only the schema.
2. **MEDIUM — unhardened `--export-json` output.** Exported plaintext (contacts/history/outbox)
   inherited the process umask. Fixed: `chmod 0700`/`0600` applied immediately after each
   create/write on Unix. Round 2 noted one honestly-documented residual (write-then-chmod leaves a
   brief window before the mode lands, vs. create-with-mode atomically) — logged as a non-blocking
   LOW follow-up, not required to close this task.
3. **MEDIUM — unbound sealed history files.** Every `history/<peer>.jsonl` shared one key and an
   identical schema with no peer-identity field, so filesystem-write-level access could swap two
   peers' sealed files and have both decrypt cleanly under the wrong identity, silently
   misattributing a transcript. Fixed: each sealed document now opens with a `HistoryHeader {
   peer_pubkey }` line, verified against the caller's requested peer on every read
   (`StoreError::PeerMismatch` on mismatch, propagated hard, never swallowed). Regression test
   swaps real ciphertext bytes on disk and confirms both directions fail closed.

Also fixed alongside (LOW, non-blocking per the reviewer, folded in anyway): `.bak` writes now go
through the same `atomic_write` temp-file+rename helper as live documents, not a raw `fs::write`.

Fail-closed on AEAD/decode failure (ADR 0021 condition 5b — never silently treated as "no data
yet"), the `.bak`-before-migrate ordering, and the hard refuse-newer-schema check were all confirmed
correct in round 1 and untouched by the fixes. `cargo test -p meridian-tui` (18 lib + 22
`tests/store.rs` + 13 `tests/config.rs` + 1 `terminal_guard.rs`), `cargo test -p meridian-cli` (full
suite, including the new `--export-json` flag), `cargo fmt --check`, `cargo clippy --workspace
--all-targets -- -D warnings`, and `bash tools/lint-tui-no-cli.sh` all clean.
