# 12.9 — File transfer screen

**Phase:** 12 — Browser & Desktop Clients · **Feature:** T11 · **Depends on:** 12.2, 12.7 · **Status:** done

**User surface:** browser + desktop file-transfer screen (wired by 12.14/12.15) — the new-platform
equivalent of the terminal client's existing `mrd.file/1` TUI surface (Phase 10, task 10.11). No TUI
surface applies to this task (already shipped, unaffected; see the phase-wide "no TUI task" note in
[phase-12/README.md](./README.md#architect-consult-substratestoresigning-decisions-settled-before-task-breakdown)
point 5).

## Goal
Build drag-drop send, a progress UI, and the receive/accept-policy hook for `mrd.file/1`, wired against
the already-shipped stream type (T09/Phase 10) purely through `MeridianClientAdapter` — zero new
protocol logic and zero registry/core changes (Definition of Done gate 6: additive stream types touch
the registry only, which this task doesn't touch at all since `mrd.file/1` is already registered).

## Scope
- **In:** drag-drop / file-picker send UI; per-transfer progress display; receive prompt +
  accept/reject with the existing auto-accept-below-size-threshold policy hook (per the feature spec).
- **Out:** any change to `apps/streams`, the resume/bitmap protocol, or merkle verification — this
  screen only calls the adapter's already-defined file-transfer operations; the known, already-tracked
  gap that `mrd.file/1`'s per-chunk merkle proof delivery isn't fully wired into the real send path yet
  (Phase 11 fix-task 11.8's residual) is inherited as-is, not re-litigated or silently worked around
  here.

## Deliverables
1. `shared-ui/src/lib/screens/FileTransfer.svelte`.
2. Component tests against the fake adapter: send-initiate, progress updates, receive-accept,
   receive-reject.

## Risks / notes
**Carried in from 12.4:** `apps/streams/src/sender.rs` still calls `std::time::Instant::now()` (compiles on wasm32, panics at runtime). `meridian-streams` depends on `meridian-core`, so it can't reach core's `pub(crate)` `timer::WallInstant` seam. Whichever task first brings `meridian-streams` onto wasm32 (12.10/12.13 if the browser adapter links it) must route this site through a wasm-safe clock — decide there and record it.

Do not claim or imply stronger corruption-detection guarantees in the UI than the underlying protocol
currently provides (the 11.8 residual above) — a progress/success indicator should reflect what the
adapter actually reports, not an assumed stronger property.

## Outcome
Landed `FileTransfer.svelte` (a `{#key adapter}{#key peerId}` wrapper) over `FileTransferPanel.svelte`, a
`FileTransferViewModel` (`file-transfer.svelte.ts`) and pure display helpers (`transfer-view.ts`), with
`FILE_COPY` and the `file-send`/`file-answer` error contexts in `copy.ts`. Written against
`MeridianClientAdapter` only: drag-drop and file-picker send (a browser `File` is passed by reference as
`FileSource.blob`, never read in TS; a `path` source only through a shell-supplied `pickPaths`), a
per-transfer progress list (`listTransfers` + `transfer` events, scoped to the peer), and
choose-then-confirm accept/reject of incoming `file-offer`s. 269 `shared-ui` tests (79 new here),
`svelte-check` and `eslint` clean.

**Safety properties.** Every send — picker, drop, `pickPaths`, each file of a batch — re-queries
`getSendGate` and proceeds only on exactly `ok`; a superseded/disposed/failed/unknown result returns
`null` and never authorises (the bug class 12.7's review found in Chat, avoided here by construction and
mutation-checked). Receiving offers is deliberately not gated by the send gate (there is a test). An
accept/reject applies to the offer it was issued for; a stale, answered, or re-announced offer can't be
resurrected, and a duplicate id can't change the name/size under the user. Wire strings (filenames, failure
reasons, peer label) go through `displayText` — control, bidi, zero-width, and other invisible/spoofing
characters shown as `[U+XXXX]`, length capped with the extension kept visible, truncation done *before*
the regex so a 100 MB name stays cheap — and render only as text nodes; there is no `{@html}`, `href`,
`download`, `src` or `createObjectURL` anywhere (grep-verified).

**No overclaiming (the 11.8 residual, inherited as-is).** "Transfer complete" renders only for
`status === 'completed'`; the screen says progress is a byte count, not an integrity check, and that a
transfer can still fail after all bytes arrive because the whole file is checked only once, at the end
(`stream-types-v1.md`'s Known gap). No copy uses "verified", "intact", "secure" or "anonymous" (a test
asserts it). A terminal failure is sticky (failed never flips to completed).

**Review (code-reviewer):** PASS, no blockers; the reviewer ran 10 mutations itself. Fixed in this commit:
files dropped while a batch was sending were silently discarded (now a fixed notice, nothing sent); a
tautological drag test (and untested drag-swallow behaviour) rewritten with real assertions; a missing
reject-then-replayed-offer test; `start()` idempotence; the invisible-character set and truncation in
`displayText`; an unknown direction no longer reads as "Incoming".

**Adapter gaps flagged, no core op invented:** the adapter has no auto-accept-threshold get/set, so there is
no threshold UI (an offer already means core's verdict was "ask the user"; auto-accepted receives show only
as `transfer` events); no `listOffers`, so an offer announced before the screen mounted is invisible; no
"cancelled" status and no resume/cancel op (the UI says so explicitly); no delivery of a received file's
bytes (no save/download, per `adapter.ts`'s own list). The screen is peer-scoped, so a global transfers
pane would be a different component — `TODO: confirm` with 12.14. `TODO: confirm` whether core's
`failureReason` is a fixed string or peer-influenced (it's rendered as capped text either way), and whether
`completed` on the *send* side means the receiver finished. The `sender.rs` `Instant` carry-in from 12.4
did not apply here (this task is pure TS); it stays owned by whichever task first links `meridian-streams`
into the wasm build (12.10/12.13).
