# 3.21 — Nit sweep

**Phase:** 3 — Review of Phase 2 · **Feature:** review fix (N1, N3) · **Depends on:** 3.4 · **Status:** done

## Goal
Remove attacker-controlled text from client-facing copy, and fix two comments that actively mislead.

## Scope
- **In:**
  - **N1** — `apps/rendezvous/src/ws.rs:357,535`: drop the foreign `FedErr.msg` from client-facing
    text, using only the mapped local code's fixed copy. (Preferred over "the remote server said: …",
    which still forwards attacker-chosen text into the victim's UI.)
  - **N3** — `apps/cli/Cargo.toml`'s comment says `rustls-tls-webpki-roots` while the workspace
    enables `-native-roots`; `apps/rendezvous/Dockerfile:28` claims the `bind` default is
    `0.0.0.0:8443` when the compiled default is `127.0.0.1:8443` (the 0.0.0.0 comes from the baked
    example toml).
- **Out:** N2 (folded into 3.7), N4 (folded into 3.8), N5 (folded into 3.2).

## Deliverables
1. The three edits above.
2. A test in `apps/cli/tests/federation_errors.rs` asserting a hostile `FedErr.msg` does **not**
   appear in the client-visible string.

## Risks / notes
- N1 is a real (if low-severity) surface: a hostile partner picks the string, and 2.9's taxonomy
  already sanitizes the *code* but not this free-form field.
- N3 is comments only — but both comments describe trust-root and bind-address behaviour, where a
  wrong comment is worse than none.


## Reviews
- **security-reviewer** — N1 only (attacker-controlled UX text).
- **code-reviewer**.

## Outcome
**N1:** `ws.rs`'s `federated_fetch_error_reply` and `federated_route_error_reply` no longer read
`FedErr.msg` for client-facing text — both now match on the already-sanitized local `code` and
return only fixed, static per-branch copy. Added
`hostile_foreign_fed_err_msg_never_reaches_the_client` to `apps/cli/tests/federation_errors.rs`, a
rogue-B test speaking the real s2s wire protocol (new `meridian-proto` dev-dependency on
`apps/cli`) that drives the real compiled CLI binary and asserts a hostile `FedErr.msg` never
surfaces. **N3:** corrected the `Dockerfile` HEALTHCHECK comment to distinguish the image's actual
bind (`0.0.0.0:8443`, from the baked-in example TOML) from `config.rs`'s own compiled-in default
(`127.0.0.1:8443`, loopback-only fail-closed); the `apps/cli/Cargo.toml` `rustls-tls-webpki-roots`
comment the finding described turned out already removed by an earlier task (3.13) — verified via
`git log`, nothing left to fix, left untouched rather than inventing a change.

Reviews: security-reviewer (N1) + code-reviewer (N1+N3), combined pass — both **pass**, zero
blocking findings. The reviewer independently ran the mutation-check rather than trusting the
implementer's report: reverted one `ws.rs` arm, confirmed the new test fails with the hostile
string visible in output, restored the fix, confirmed it passes. Traced the fixed copy end-to-end
through the CLI's own display code to confirm no other passthrough reintroduces the leak. One
non-blocking hygiene note (stale `Cargo.lock`, predating this task from 3.13's uncommitted
dependency additions) — fixed by including the regenerated lockfile in this commit.
