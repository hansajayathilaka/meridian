# 12.1 — `wasm32` substrate: toolchain + `getrandom` backend + timer seam

**Phase:** 12 — Browser & Desktop Clients · **Feature:** T11 (substrate completion, not the feature
itself) · **Depends on:** — · **Status:** pending

**User surface:** none — cross-cutting build-configuration and substrate work with no user-visible
behavior change. No TUI surface applies to this task.

## Goal
Make the workspace's leaf crates (`meridian-store`, `meridian-identity`, `meridian-crypto`,
`meridian-proto`, `meridian-envelope`, `meridian-transport`) actually compile for
`wasm32-unknown-unknown`, closing the first half of the substrate gap an architect consult found before
this phase's task breakdown (see [phase-12/README.md](./README.md#architect-consult-substratestoresigning-decisions-settled-before-task-breakdown)
point 3): `meridian-store`'s `getrandom 0.3` has no wasm backend configured, `wasm32-unknown-unknown`
isn't in `rust-toolchain.toml`'s target list, and `apps/core/src/session.rs` calls `tokio::time`
directly, which has no working driver off `wasm32-unknown-unknown` without a browser-event-loop
executor. This task closes everything **except** `meridian-signaling`/`meridian-core` themselves — task
12.4 closes the signaling half and is what finally proves the full `meridian-core` wasm32 build green.

**This finding and its fix shape were settled by an architect consult during `/plan-phase`** — this task
file implements that decision, it does not re-open it.

## Scope
- **In:**
  1. Add `wasm32-unknown-unknown` to `rust-toolchain.toml`'s `targets` list.
  2. Configure `meridian-store`'s `getrandom 0.3` `wasm_js` backend opt-in (the crate's `wasm_js`
     Cargo feature plus the required `--cfg getrandom_backend="wasm_js"` rustflag, via
     `.cargo/config.toml`'s `[target.wasm32-unknown-unknown]` section).
  3. Replace the direct `tokio::time::timeout`/`tokio::time::Instant` calls in
     `apps/core/src/session.rs` with a small internal, `cfg`-gated seam (native → unchanged
     `tokio::time`; `wasm32` → a wasm-compatible substitute) — do not change any native-path behavior.
  4. Run `cargo check -p meridian-store -p meridian-identity -p meridian-crypto -p meridian-proto
     -p meridian-envelope -p meridian-transport --target wasm32-unknown-unknown` and treat the real
     error set as authoritative, not the enumerated list above — the workspace's root `tokio`
     dependency (`["rt-multi-thread","macros","net","sync","time","io-util"]`) may unify features
     across crates in a way that surfaces more than the two named `tokio::time` call sites (e.g.
     `net`/`rt-multi-thread` are hard-incompatible with `wasm32-unknown-unknown`, which has no
     epoll/real threads). If so, split the workspace `tokio` dependency per-crate via
     `[target.'cfg(target_arch = "wasm32")'.dependencies]` rather than re-scoping this task — this is
     discovery, not scope creep, per the architect consult's own "verify, don't assume" instruction.
- **Out:** `meridian-signaling` and `meridian-core` themselves (task 12.4 closes that arc); any
  browser-specific `Transport`/`SecretStore` implementation (tasks 12.5/12.11/12.12); any browser UI.

## Deliverables
1. `rust-toolchain.toml` — `wasm32-unknown-unknown` added to `targets`.
2. `apps/store/Cargo.toml` + `.cargo/config.toml` — `getrandom` `wasm_js` backend wiring.
3. `apps/core/src/session.rs` — timer seam (native path behavior unchanged, proven by existing tests
   staying green).
4. A `just`/CI step running the six-crate `cargo check --target wasm32-unknown-unknown` command above.

## Risks / notes
The `tokio` feature-unification risk above is real and should be investigated first, before writing any
fix — run the `cargo check` command as literally the first step and read the actual error output before
touching `session.rs`. If a per-crate `tokio` feature split is needed, keep it minimal (only the
features each crate's non-wasm32 code path actually needs) rather than disabling more than necessary.

Do not touch `meridian-crypto`'s `Cargo.toml` beyond what's strictly required for this check to pass —
that crate's own CLAUDE.md requires security-reviewer sign-off on *any* change there, so keep the diff
narrow and explainable.

## Tests
`cargo check -p meridian-store -p meridian-identity -p meridian-crypto -p meridian-proto
-p meridian-envelope -p meridian-transport --target wasm32-unknown-unknown` (new, must pass);
`cargo test -p meridian-core -p meridian-transport -p meridian-store` (existing native suites, must stay
green — proves the timer seam didn't change native behavior).
