# 10.8 — Receiver engine: write-by-offset, incremental verification, corruption handling

**Phase:** 10 — File Transfer Stream · **Feature:** T09 · **Depends on:** 10.6 · **Status:** done

**User surface:** none yet — the receiver engine has no CLI/TUI surface of its own; that lands in tasks
10.10/10.11, which own the Definition of Done's gate 9 obligation.

## Goal
Reassemble an incoming file from out-of-order, AEAD-sealed chunks: open each chunk (task 10.5), write it
at its offset, verify it incrementally against the manifest's merkle root (task 10.3), and — this is the
acceptance-criterion-bearing path — detect a corrupted chunk and discard/re-request it **without ever
writing it to disk**.

## Scope
- **In:** `apps/streams/src/receiver.rs` (or similar): open+verify+write-by-offset for each inbound
  chunk frame, incremental subtree verification (a chunk failing its merkle check is never written),
  bookkeeping of which offsets have been received (feeds task 10.9's resume bitmap), a corrupted-chunk
  signal the sender-facing side can turn into a re-request.
- **Out:** the actual re-request wire mechanism (that's resume, task 10.9 — this task only detects and
  reports "chunk `i` failed verification," it doesn't decide how re-request is signaled on the wire).

## Deliverables
1. Receiver engine in `apps/streams/src/receiver.rs`.
2. Tests: full-file reassembly from out-of-order chunks; a deliberately bit-flipped chunk is rejected by
   AEAD open *or* merkle verification (both paths tested) and is never written to the destination file
   (assert the on-disk/in-memory buffer for that offset stays empty/untouched, not just that an error is
   returned).

## Risks / notes
Two independent integrity checks exist (per-chunk AEAD from 10.5, and merkle subtree verification from
10.3) — a tampered ciphertext should fail AEAD open before merkle is even consulted; a chunk that opens
fine but doesn't match the expected subtree hash (e.g. a chunk from the wrong file/offset re-sent) must
also be rejected. Test both failure paths distinctly, not just "some error occurs."

## Tests
`cargo nextest run -p meridian-streams`.

## Reviews
**reviewer** (combined: security-reviewer — this is the integrity path the "corrupted chunk never
written" acceptance criterion depends on; code-reviewer — reassembly/offset-bookkeeping correctness).

## Outcome
Added `FileReceiver::new(manifest, k_f)`/`receive_frame(frame_bytes, proof) -> Result<u64, ReceiveError>`
in `apps/streams/src/receiver.rs`, built directly on task 10.7's canonical `ChunkFrame` wire type
(landed in parallel in the same run — converged on one shared type rather than each task hand-rolling
its own CBOR shape). Per inbound frame: decode `ChunkFrame`, bounds-check `i` against the manifest's
`leaf_count`, call `open_chunk` (AEAD authentication — must fail here for a tampered ciphertext, before
merkle is ever consulted), cross-check `proof.leaf_index == i` (defense-in-depth against a frame/proof
mismatch — see below), then `crate::merkle::verify` (integrity against the expected subtree position) —
only on full success is the chunk inserted into the reassembly map and its offset recorded.
`ReceiveError{Malformed,OutOfRange,Crypto{i},Corrupt{i}}` represents the AEAD-failure and
merkle-failure paths as distinct variants. `received_offsets() -> &BTreeSet<u64>` exposes bookkeeping
for task 10.9's future resume bitmap; `reassemble()`/`is_complete()` round out the read surface. Manual
`Debug` never prints `k_f` or plaintext chunk bytes.

Both mandatory review lenses (security-reviewer, code-reviewer, run as one combined `reviewer` pass
alongside task 10.7 since they share `chunk.rs`'s `ChunkFrame`) returned **PASS**, with zero blocking or
should-fix findings — independently traced the actual order of operations (decode → range check → AEAD
open → proof/index cross-check → merkle verify) to confirm AEAD and merkle failures are genuinely
distinct code paths, not two tests funneling through one generic error; confirmed both failing tests
assert directly against `chunk(i).is_none()`/`!received_offsets().contains(&i)` rather than merely "an
Err was returned"; and — the review's most substantive finding — confirmed the `proof.leaf_index == i`
cross-check is a real, necessary defense-in-depth measure rather than redundant with task 10.3's
already-fixed leaf-index-aliasing protection: `merkle::verify` only validates a proof's *internal*
consistency, it never learns the wire frame's own claimed index `i`, so without this explicit check an
attacker could pair a frame claiming index `i` with a validly-hashed proof for a genuinely different
leaf position in the same tree, placing correctly-hashed-but-wrong-position data at the wrong reassembly
offset — this check is what closes that gap, and it composes correctly with (does not circumvent) 10.3's
own fix. Also confirmed no `.unwrap()`/`.expect()`/panicking indexing on attacker-controlled input
anywhere in non-test code, and no logging of `k_f`/plaintext/file contents. One optional, non-blocking
nit noted: `i as usize >= self.leaf_count` truncates `u64` to `usize` before bounds-checking, which on a
32-bit target could let a crafted high-bit-only-differing index pass the check before failing later at
the AEAD stage instead — benign (not exploitable, just a slightly misleading error path on an unusual
target), left as optional polish. All 51 `meridian-streams` tests (everything from 10.1–10.8) green
throughout; clippy/fmt clean; full workspace build clean.
