# 8.8 — Client-side `MailboxAck` send + redelivery-dedup confirmation

**Phase:** 8 — Offline Ciphertext Mailbox · **Feature:** T07 · **Depends on:** 8.7 · **Status:** done

## Goal
Make the client actually ack what it received (so the server-side mailbox empties), and confirm
the already-shipped `eid` dedup (task 6.4) is what makes a duplicate redelivery harmless, per T07
deliverable 2 ("client offline-queue + dedup on redelivery, idempotent by envelope id").

## Scope
- **In:** `meridian-signaling`'s client (`apps/signaling/src/client.rs`) collects `mailbox_id`s off
  incoming `Deliver` frames that carry one, and sends `MailboxAck{ids}` once the batch has been
  handed to the caller (i.e. ack-after-processing, not ack-on-receipt — an ack before the envelope
  is durably handled would lose it on a crash between ack and processing). Confirm
  `apps/core/src/chat.rs`'s existing `eid`-based dedup (task 6.4) already rejects a redelivered
  envelope with no mailbox-specific code needed — if a gap exists (e.g. dedup state not surviving
  the reconnect that triggers redelivery), fix it here; if not, this sub-item is verification only.
- **In, added by [ADR 0024](../../adr/0024-mailbox-drain-from-attestation.md) (found while
  implementing 8.7):** `apps/core/src/chat.rs::open_bytes`'s `envelope.sender_pub != from` check
  (`ChatError::SenderMismatch`) must not reject a mailbox-drained `Deliver` — 8.7 emits a fixed
  `[0u8; 32]` placeholder for `from` on that path (never a real, persisted sender identity — see the
  ADR for why), so the check as written would reject every mailbox-drained message unconditionally.
  Relax/restructure the check for `mailbox_id.is_some()`: the real sender is `envelope.sender_pub`
  alone (already recoverable from `blob` without the server's help), authenticated the same way it
  always was — the ratchet AEAD succeeding at all — never a routing-layer `from` the server cannot
  honestly assert for a message it isn't relaying live. This is a blocking prerequisite for
  Deliverable 3 below, not an optional extra: `eid` dedup is checked strictly *after* the sender
  check in `open_bytes` today, so the redelivery-dedup test cannot even be reached without this fix.
- **Out:** no change to `eid` dedup's own mechanism (6.4/7.4 own that); no server-side change (8.7
  owns it, including the `[0u8;32]` placeholder constant in `apps/proto`); no change to the
  `SenderMismatch` check's behavior for a **live** or **federated-live** `Deliver`
  (`mailbox_id: None`) — the check keeps exactly its current meaning there; TUI-surface wiring only
  if a user-visible affordance is needed — confirm against Definition of Done gate 9 whether
  "mailbox delivered N messages while you were away" needs a TUI surface or is purely
  transport-layer and invisible to the user (likely the latter, since delivery is just "messages
  arrived," already covered by the existing chat screen — record the "no surface needed" reasoning
  explicitly per gate 9's own requirement if so).

## Deliverables
1. `MailboxAck` send path in `apps/signaling/src/client.rs`, ack-after-processing.
2. Confirmation (or fix) that `eid` dedup survives a reconnect-triggered redelivery batch.
3. `open_bytes`'s `SenderMismatch` check restructured per ADR 0024 so a mailbox-drained `Deliver`
   (`mailbox_id.is_some()`) is authenticated via `envelope.sender_pub` alone, never compared against
   the `[0u8;32]` placeholder `from` 8.7 sends. A live/federated-live `Deliver` (`mailbox_id: None`)
   keeps today's exact `envelope.sender_pub != from` check, unchanged.
4. Tests: a simulated redelivery of an already-seen `eid` is dropped, not double-processed; an ack
   is sent exactly once per batch of mailbox-tagged `Deliver`s, after (not before) they're handed to
   the caller; a crash/disconnect between receipt and ack leaves the row unacked (provable via the
   server-side test from 8.7 — reconnect redrains it); a mailbox-drained `Deliver` with the
   `[0u8;32]` placeholder `from` decrypts successfully (proving the restructured check actually
   accepts the case it must); a live `Deliver` with a genuinely forged `from` still hits
   `SenderMismatch` (proving the restructured check didn't accidentally weaken the live-path
   defense-in-depth it must keep).

## Risks / notes
Ack-after-processing vs ack-on-receipt is the one real design choice left in this task — get it
wrong (ack-on-receipt) and a client crash between ack and durable local persistence silently loses
a message, which is exactly the failure mode T07's mailbox exists to avoid. If gate-9 TUI-surface
applicability is genuinely "none needed," say so explicitly in this task's Outcome rather than
silently skipping it.

**ADR 0024's restructured `SenderMismatch` check is the single most security-relevant line in this
task** — get the `mailbox_id.is_some()` gate wrong (too broad) and a live/federated-live `Deliver`'s
forged-`from` defense-in-depth silently stops firing; get it wrong the other way (too narrow, or
missing) and every mailbox-drained message is permanently unreadable. Both directions need their own
explicit test (Deliverable 4's last two cases), not just the happy path.

## Status
**Done.** `apps/signaling/src/client.rs`'s `SignalingClient` gained a `pending_mailbox_acks: Vec<u64>`
accumulator: `next_deliver()` pushes `deliver.mailbox_id` onto it (no network I/O) whenever a
returned `Deliver` carries one, and a new `ack_pending_mailbox()` drains the accumulator into one
batched `MailboxAck{ids}` request (a no-op when empty; on request failure the ids are restored for
retry). Callers (`apps/tui/src/worker.rs::process_inbound_delivery`, `apps/cli/src/chat.rs`'s chat
loop) call it only after their own durable persistence (`save_chat`/`save_state`) has actually
succeeded — this is the ack-after-processing discipline the task's Risks/notes named as the one real
design decision here.

`apps/core/src/chat.rs::open_bytes` gained a `mailbox_drained: bool` parameter per ADR 0024: the
`envelope.sender_pub != from` check is now `if !mailbox_drained && ...`, and a new
`ChatState::open_inbound_from_mailbox` (thin wrapper, `mailbox_drained: true`) sits alongside the
unchanged `open_inbound` (`mailbox_drained: false`). Every existing call site (the P2P substrate in
`session.rs`, every raw test) passes `false` explicitly, preserving prior behavior byte-for-byte.
Building this surfaced a second, non-obvious bug in `open_inbound_gated`'s own bookkeeping (the
pending-request map, first-contact detection, and `MessageRequest::sender_ik`), which used the
routing-layer `from` directly — correct only because `from == envelope.sender_pub` was previously
always enforced. Fixed by decoding `sender_pub` from the blob once, up front, and keying all local
bookkeeping off that instead of `from` (safe before authentication succeeds: it can only affect map
lookups, never a state mutation, since nothing commits before `open_bytes`'s own AEAD decrypt).

**Gate 9 (TUI surface): none needed, confirmed.** A mailbox-drained message surfaces through the
same `InboundEvent::Message`/chat-screen path as any live delivery — there is no new user-facing
concept ("messages arrived" is already covered), so no new TUI surface was added; this is the
"purely transport-layer and invisible to the user" case the task's own Scope anticipated.

### Review round
**reviewer** (security-reviewer + code-reviewer + test-engineer) — first PASS on the ADR 0024
restructuring and the pre-existing `Store`-trait-forwarding fix (two test-only `Store` doubles in
`apps/tui/tests/run_worker_chat.rs`/`run_worker_account.rs` were missing the 5 mailbox methods added
task 8.1, causing `send_to_an_offline_peer_completes_with_delivered_false` to hard-fail once this
task's own full-`meridian-tui`-suite run first exercised the offline-mailbox path against them —
fixed by forwarding all 5 to `self.inner`, predates 8.8, not scope creep). Two real findings, both
fixed in this same commit:
- **BLOCKING** — `open_inbound_gated`'s own internal bookkeeping fix stopped at `ChatState`'s
  boundary: every caller (`worker.rs`, `cli/src/chat.rs`) still used the raw `deliver.from` —
  correct on the live path, but the mailbox-drain placeholder for a mailbox-drained one — for
  everything downstream of the `open_inbound*` call: the display/history event's `peer_pubkey`
  (silently misfiling a mailbox-drained message from an *existing* contact into a shared, all-zero
  pseudo-conversation instead of that contact's real history, with different senders colliding into
  the same bucket), the pending-request lookup (a panic in the CLI, a silent no-op event in the
  TUI), and the auto-ack's `seal_outbound` target (`NoSession` in the CLI, propagated by an
  unguarded `?` and terminating the whole process — a crash-loop DoS, since the mailbox row is never
  acked before the crash, so the identical redrain-and-crash repeats every reconnect until TTL
  expiry). Fixed by deriving `effective_from` once per delivery (`envelope.sender_pub`, read via the
  same cheap parse) in both `worker.rs` and `cli/src/chat.rs`, and using it everywhere "the peer's
  identity" is needed downstream of the open call — never `deliver.from` — while still passing the
  literal `deliver.from` into `open_inbound_from_mailbox`'s own `from` parameter (the wire value the
  now-restructured check itself reasons about). Regression-tested end-to-end through the real
  `process_inbound_delivery`/`run_inbound_loop` caller path (not just `ChatState`-level unit tests):
  `apps/tui/tests/inbound_delivery.rs::mailbox_drained_delivery_from_an_existing_session_files_under_the_real_sender_not_the_placeholder`
  — non-vacuity independently confirmed (reverting to `deliver.from` makes it fail exactly as
  predicted, then restored byte-identical).
- **SHOULD-FIX** — `SignalingClient::pending_mailbox_acks` batches across the whole connection, not
  per-delivery: if delivery A's local persistence transiently failed (`persisted == false`),
  `worker.rs` correctly skipped *its own* `ack_pending_mailbox()` call, but A's id stayed queued and
  a *later*, unrelated delivery B's successful flush would sweep it up anyway — acking A's row
  despite A never having been made durable. Fixed with a new
  `SignalingClient::discard_pending_mailbox_ack(id)`, called by `worker.rs` on `persisted == false`
  to withdraw exactly this delivery's own id before it can ride along in a later flush.
  Regression-tested: `apps/rendezvous/tests/mailbox_client_ack.rs::discard_pending_mailbox_ack_withdraws_only_the_named_id`.
  (`apps/cli/src/chat.rs` was already immune — its `?` on `save_state`/`save_trust` ends the whole
  loop on the same failure, so no later delivery can ever sweep up an earlier one.)
