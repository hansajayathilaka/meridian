# 12.8 — Verification screen: QR camera-scan safety-number compare

**Phase:** 12 — Browser & Desktop Clients · **Feature:** T11 · **Depends on:** 12.2, 12.7 · **Status:** done

**User surface:** browser + desktop verification screen (wired by 12.14/12.15) — the new-platform
equivalent of the terminal client's existing verification screen (Phase 4, task 4.22). No TUI surface
applies to this task (already shipped, unaffected; see the phase-wide "no TUI task" note in
[phase-12/README.md](./README.md#architect-consult-substratestoresigning-decisions-settled-before-task-breakdown)
point 5).

## Goal
Build a camera-capture (MediaDevices) + QR decode/encode screen comparing the local and remote
`safety_number` outputs (`core-api-contracts.md`), marking `mark_verified` on a confirmed match — this
is T11's realization of the spec's own acceptance walkthrough step ("chat + 200 MB file transfer
browser↔CLI; safety numbers match on both, verified by QR").

## Scope
- **In:** QR display of the local safety number; camera-scan + decode of the remote peer's; visual
  compare UI; the `mark_verified` call on confirmed match, exactly as `core-api-contracts.md` already
  defines it.
- **Out:** any change to the underlying `safety_number`/`mark_verified` core functions (already frozen,
  T08) — this task only builds a UI over them; camera-permission-denied fallback UX beyond a basic error
  state is a nice-to-have, not required for this task's acceptance.

## Deliverables
1. `shared-ui/src/lib/screens/Verification.svelte`.
2. Component tests: QR decode/compare logic unit-tested against known fixture values (the T08 safety-
   number fixtures per the spec's own acceptance criterion — "identical safety numbers across platforms
   for the same key pair"); camera access itself mocked, not exercised in this task's own test suite.

## Risks / notes
**Carried in from 12.2's review:** the adapter has only `renderQrText` (core's `render_terminal`) — no pixel/SVG QR render. If this screen needs a graphical QR, that is a new `meridian-core`-level op: flag it back, don't invent it. Also `markVerified(peerId)` takes no proof, so this screen is the only guard that the safety numbers actually matched.

This is a safety-critical UX surface (D06) — do not let a partial/ambiguous QR scan result in a
false-positive `mark_verified` call. Mirror the terminal client's own verification screen (4.22)'s
match/mismatch state handling rather than inventing new UX semantics.

## Outcome
Landed `Verification.svelte` (a `{#key adapter}{#key scanner}{#key peerId}` wrapper) over
`VerificationPanel.svelte` and a `VerificationViewModel` (`verification.svelte.ts`), the injectable
`QrScanner` interface (`src/lib/qr-scanner.ts` — the shell supplies the real MediaDevices→luma scanner; a
scanner only returns frames, never a verdict), and `VERIFY_COPY` in `copy.ts` lifted from the CLI/TUI
wording. QR decoding and safety-number computation stay in the adapter (`decodeQr`, `getSafetyNumber`);
the screen only compares strings. 190 `shared-ui` tests (64 new here + 17 from review fixes),
`svelte-check` and `eslint` clean.

**The safety-critical rule.** `confirmVerified()` is the **only** call site of `markVerified` (grep-verified
twice). It runs only from `matched` (an exact `===` match of a 60-ASCII-digit scan against the adapter's
number for *this* peer — no trimming, normalisation, or fuzzy match) or `manual` (the explicit out-of-band
"digits match" path), only on an explicit click, and re-fetches `getSafetyNumber` and aborts if the digits
changed, the check object was replaced, or the screen was disposed. A full-length wrong number sets a
sticky MISMATCH state, closes the manual path, and offers no "verify anyway"; partial / garbled / grouped /
fullwidth-digit / ID-QR payloads are never a match and never clear a mismatch. A malformed adapter number
(empty, wrong length, or a `display` that disagrees with `digits`) fails closed — so `"" === ""` cannot
match. `warn` (pinned-key-changed) can be acknowledged only behind a confirm on a *freshly re-queried*
`warn` gate and never calls `markVerified`; `blocked` has no acknowledge path, only re-verification.

**Review (security-reviewer + code-reviewer, one combined pass):** both PASS, no blockers, **no
false-positive `markVerified` path found** (the reviewer ran 14 mutations itself; 11 caught, 2 survivors
were redundant defence, 1 was a real test gap). All should-fix items fixed in this commit and
mutation-rechecked: `scanner.stop()` throwing no longer skips the unsubscribe or leaves stale `scanning`
state; the shared `decoding` flag became a per-scan slot with a 5 s decode timeout (a hung decode could
starve a restarted scan); the surviving "partial scan clears the mismatch" mutation now fails 4 tests; the
view-model is rebuilt when the adapter or scanner is swapped; a key-changed *and* locally-blocked contact
still gets the KEY CHANGE header (the key-change message isn't softened); `Object.hasOwn` on shell-supplied
failure reasons.

**Ratified (decisions made during implementation, none needing an ADR):** a scan match needs an extra
explicit confirm click where the CLI auto-marks (stricter); a non-60-digit or ID-QR payload is a neutral
"not a complete safety number" hint, not a MISMATCH alarm; a mismatch disables the manual path until an
exact scan; a Block/unblock action (behind a confirm, applying the direction shown) was added though
slightly beyond this task's literal Scope, because `verification-ux.md` and 4.22 put it on this screen.

**Follow-up for the architect (not done here):** `markVerified(peerId)` takes no proof, so there is an
unavoidable check-then-mark window between the UI's fresh `getSafetyNumber` re-check and core marking
*whatever key is currently pinned*. A core-level `mark_verified(peer, expected_digits)` that checks inside
core would close it; it is a `meridian-core` API change outside this task and mirrors the CLI's own gap.

**Gaps, stated rather than claimed away:** the adapter offers only `renderQrText`, so the local QR is a
monospace `<pre>` block — whether a text QR is reliably camera-scannable on screen is untested
(`TODO: confirm` for 12.13/12.14; a pixel/SVG render would be a new core op, not invented here). The camera
path itself (the shell's real `QrScanner`) is untested in this suite by design. The T08 fixture test
(`test-vectors/safety-numbers-v1.json`, 5 vectors) checks the screen's contract with real values — verbatim
display, exact-digits payload, exact scan matches, one digit off doesn't — **not** cross-platform
computation equality; that belongs to core's conformance suite and 12.13/12.18. No typed-digits manual entry
(it would need whitespace normalisation in TS). The sticky mismatch lives in the view-model, so leaving and
re-entering the screen reopens the manual path (consistent with the CLI). Shell wiring (12.14/12.15):
supply the real scanner (must release the camera on `stop()`); route `Chat`'s `onverify(contact)` to
`<Verification {adapter} {contact} {scanner} onverified onclose />`.
