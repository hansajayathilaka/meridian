# 10.2 — `Transport::buffered_amount` backpressure primitive

**Phase:** 10 — File Transfer Stream · **Feature:** T09 · **Depends on:** — · **Status:** done

**User surface:** none — a read-only backend primitive with no consumer yet (task 10.7's sender engine
is the first to poll it). No TUI surface applies to this task.

## Goal
Add a generic way for the substrate (and, through it, any bulk stream type) to read a data channel's
outbound buffer level, so sends can be throttled to a low-watermark instead of flooding the channel —
the feature spec's "backpressure via `bufferedAmount` watermarks" requirement, which is unimplementable
today because `meridian_transport::Transport` has no such method at all.

## Scope
- **In:** one new `Transport` trait method, e.g. `fn buffered_amount(&self, s: &SessionHandle, ch:
  &ChannelId) -> Result<u64>` (byte count currently queued for send on that channel), implemented for
  both backends: `apps/transport/src/webrtc_backend.rs` (the real `webrtc-rs` `RTCDataChannel::
  buffered_amount()`) and `apps/transport/src/loopback.rs` (a value consistent with the loopback
  fabric's own in-memory queue depth for that channel — need not model real network buffering, just be
  non-trivially exercisable by a test that sends faster than it drains).
- **Out:** any low-watermark event/callback mechanism, threshold configuration, or actually pausing a
  sender — this task only adds the read primitive. Task 10.7 (sender engine) is the first consumer that
  polls it to throttle.

## Deliverables
1. `Transport::buffered_amount` added to the trait in `apps/transport/src/lib.rs`.
2. Implementations in `webrtc_backend.rs` and `loopback.rs`.
3. Tests exercising both backends: a real value that changes as data is sent/drained.

## Risks / notes
This is an **additive** method on a `core-api-contracts`-documented, semver-stable trait
(`docs/api/core-api-contracts.md` §"Stability policy": "Traits above are semver-stable from Phase 1").
Adding a method to a trait that already has other implementors (only these two exist today, both in
this crate) is safe here, but flag for architect review that this doesn't silently change any existing
method's contract — it is purely additive. If the trait gains a default-method fallback vs. a
mandatory new method, pin that choice here (a mandatory method is preferred — both existing backends
are in-tree and can implement it directly; a default silently returning `0` would be a footgun for
would-be third-party `Transport` implementors mentioned in `docs/architecture/stack.md`).

`TODO: confirm` whether `buffered_amount` should return `Result<u64>` (fallible, matching every other
method on this trait) or a bare `u64` (backends can't meaningfully fail this query in practice) —
prefer `Result<u64>` for consistency with the rest of the trait unless the implementer finds a strong
reason not to.

## Outcome
Added `async fn buffered_amount(&self, s: &SessionHandle, ch: &ChannelId) -> Result<u64>` to `Transport`
(`apps/transport/src/lib.rs`) as a mandatory method — `async` rather than the task sketch's sync
signature, because the real backend (`webrtc-rs`'s `RTCDataChannel::buffered_amount()`) is itself async,
and the trait already splits sync/async per-method based on what a real backend needs; kept `Result<u64>`
per the task's own preference for consistency with the rest of the trait. Implemented for both backends:
`webrtc_backend.rs` delegates directly to `RTCDataChannel::buffered_amount()`; `loopback.rs` tracks an
`Arc<AtomicU64>` per channel, incremented in `send()` before enqueue and decremented in `recv()` exactly
when the peer dequeues. The third in-tree `Transport` implementor (`LeakyTransport`,
`apps/core/tests/p2p_session.rs`) got a one-line delegating impl so the workspace keeps compiling.

Both mandatory review lenses (architect, code-reviewer, run as one combined `reviewer` pass) returned
**PASS**, independently re-tracing the loopback counter's increment/decrement points, confirming the
webrtc backend's byte (not message) units and the async choice against the trait's existing sync/async
split logic, and re-running the full test/clippy/build matrix rather than trusting the implementer's
claims. One non-blocking should-fix — the task's own explicit ask for whether `core-api-contracts.md`'s
"Stability policy" section needed a more explicit versioning note for this addition — was closed in the
same commit: a one-sentence addendum now documents that core traits may still gain mandatory methods
pre-1.0 while only in-tree implementors exist, citing this task as the precedent.
