# 2.9 — Client-side federation error taxonomy: clean `closed` error + the stale-hint case

**Phase:** 2 — Cross-Org Federation · **Feature:** T06 — Cross-Org Federation · **Depends on:** 2.7, 2.8, 1.33 · **Status:** done

## Goal
Every federation failure surfaces at the client as a distinct, diagnosable, **non-security** message.
Specifically: a `closed`-policy org produces a clean error rather than a hang, and the stale-hint case
(Bob re-registered at org-c) reports "unreachable at hint" and **never** a security warning.

## Scope
- **In:** `SignalError` / `SessionError` variants for `fed_denied`, `fed_unreachable`,
  `not_found_at_hint`; CLI copy; the hard distinction between a *reachability* failure and a
  *verification* failure; no hangs on any path.
- **Out:** retry/backoff; multi-hint IDs (Phase 3 by spec).

## Deliverables
1. `apps/signaling/src/error.rs` and `apps/core/src/session.rs`: new variants, kept **distinct** from
   `BundleVerification`.
2. `apps/cli/src/chat.rs`, `session_connect.rs`, `main.rs`: the user-facing copy.
3. `apps/cli/tests/federation_errors.rs`: `closed` org → clean non-zero exit with a named cause and
   **no hang**; stale hint → "unreachable at hint"; an assertion that **neither** path emits
   verification or security-warning copy.

## Risks / notes
- [ADR 0001](../../adr/0001-identity-scheme.md)'s consequence is the whole point of this task: a stale
  hint degrades **reachability, never security**. Conflating the two trains users to dismiss real
  key-substitution warnings — and [verification-ux.md](../../security/verification-ux.md) makes
  security copy canonical and un-softenable.
- **Depends on 1.33.** Without the bounded `recv_sdp` wait, "clean client-side error" is a hang. 1.33
  supplies the bounded wait plus a distinct error variant that this task extends to the federated
  cases.
- Inherits 2.6's unresolved `TODO: confirm` on how much rejection reason may be relayed. If the answer
  is "collapse `closed`/`allowlist`/`not_found` into one code to avoid leaking Org B's policy and
  target existence", this task must still produce a *diagnosable* message — name the ambiguity in the
  copy rather than inventing a precision the wire does not carry.

## Outcome
New `SignalError`/`SessionError` variants `FedDenied`/`FedUnreachable`/`NotFoundAtHint`
(`apps/signaling/src/error.rs`, `apps/core/src/session.rs`), kept structurally distinct from
`BundleVerification`/`FingerprintMismatch` everywhere (doc comments name the invariant explicitly). A
new `classify_federation_error(e, hint)` helper reclassifies a generic `SignalError::Server` using
the wire code (`fed_denied`/`fed_unreachable`/`not_found_at_hint`), populating only the
caller-supplied hint — never a server-internal string. `apps/core/src/signal_relay.rs`'s
`map_signal_error` mirrors the same three variants into `SessionError`. CLI-facing copy added in
`apps/cli/src/{main,chat,session_connect}.rs`: `fetch_with_retry` retries local `not_found` and
`NotFoundAtHint` (bounded, ≤10s) but stops immediately on `FedDenied`/`FedUnreachable` (retrying a
policy denial or unreachable peer would be pointless and could act as a probing amplifier). Per 2.6's
already-collapsed `closed`/`allowlist`/`not_found` wire code, the copy names the ambiguity rather than
inventing wire precision that doesn't exist; the stale-hint case is similarly honest that "never
registered" and "re-registered elsewhere" are indistinguishable from one wire response.
`apps/cli/tests/federation_errors.rs` (new) drives two real in-process rendezvous servers over a real
s2s mTLS link and the real `meridian` binary as a subprocess, with a wall-clock-bounded kill-on-hang
helper: closed-policy org → clean non-zero exit, named cause, no hang; stale hint → "unreachable at
hint", with an explicit assertion that neither path emits any of `docs/security/verification-ux.md`'s
canonical security-copy vocabulary. Collateral: `apps/rendezvous/tests/{federation_fetch,
federation_route}.rs` updated to match the newly-distinct variants (assertions preserved, not
loosened).

**Reviews:** security-reviewer — APPROVE; verified the reachability/security split is structural, the
hint pipeline leaks nothing server-internal (traced back through 2.7's already-sanitized wire `msg`),
2.6's collapsed rejection reason isn't over-reconstructed client-side, and the bounded retry never
retries `FedDenied`/`FedUnreachable`. Non-blocking follow-up noted: `fetch_foreign_bundle`/`dial` in
`apps/rendezvous/src/federation/{outbound,link}.rs` (pre-existing, from 2.7/2.8) have no
`tokio::time::timeout` wrapper, so a foreign server that accepts the s2s connection but never replies
could still hang server A — not exercised by either of 2.9's own test scenarios. test-engineer —
PASS; mutation-tested every load-bearing claim (reclassification, direct conflation, security-copy
leak, and the kill-on-hang mechanism itself) by breaking the corresponding code and confirming the
tests fail, then restoring it; confirmed the two scenarios reach the code paths they claim to.
code-reviewer — approve-with-nits; found three should-fix items, none blocking: (1) the CLI-facing
`federation_error_line` rendering is hand-rolled three times (`main.rs`, `chat.rs`,
`session_connect.rs`) rather than shared, and the wording has already drifted between them — should
be extracted into one shared function; (2) `fetch_with_retry`'s retry-vs-stop logic is correct by
inspection but untested for the `chat`/`connect` paths (only the one-shot `fetch-bundle` path is
covered) — route to test-engineer for a follow-up; (3) a real architectural gap, **not a 2.9
regression**: `route_with_hint` is never called with an actual hint from any live path
(`RendezvousRelay::send` and `chat::route_tolerant` both hardcode `hint: None`), so this task's own
`SessionError` federation variants are currently unreachable outside their unit tests, and cross-org
chat/session routing doesn't work end-to-end yet. Escalated to **architect**, who confirmed the gap
(traced end-to-end, cited `system-design.md` §3.3 step 2 and §3.4 as already requiring hint-carrying
signaling envelopes, not just the bundle fetch) and called for a new task — **2.15**, inserted before
2.11 — rather than folding the fix into 2.9 (would reopen an already-narrow, nearly-closed review) or
into 2.11 (wrong agent/reviewer lineup for a cross-crate protocol fix). Items (1) and (2) are recorded
here as non-blocking follow-ups, not yet filed as separate numbered tasks.
