# 3.3 — Bound every outbound s2s I/O exchange

**Phase:** 3 — Review of Phase 2 · **Feature:** review fix (F3, **blocking**) · **Depends on:** 3.2 · **Status:** pending

## Goal
A black-holed partner must not hang the originating client's WebSocket session or leak a pinned task
plus TLS link.

## Scope
- **In:** a connect timeout on `link::dial`'s `TcpStream::connect` (L355); a timeout on the TLS
  handshake + `exchange_hello`; a per-exchange timeout on `fetch_foreign_bundle`'s (L118) and
  `reachable_foreign`'s (L429) reply receives; surfaced as `fed_unreachable`; cancellation of the
  awaited work when the client ws session drops.
- **Out:** `ROUTE_REPLY_GRACE`'s value (3.20); the inbound accept path (3.2); link reuse (3.7).

**Why this is split from 3.2/F2:** different code paths (dial-side vs accept-side), different threat
(partner-induced local resource leak vs unauthenticated remote DoS), different tests, independently
revertable. They share only the `with_deadline` helper 3.2 introduces.

## Deliverables
1. `apps/rendezvous/src/federation/link.rs` — `dial` reads a `FederationTimeouts`;
   `tokio::time::timeout` around connect, TLS, and `exchange_hello`; new `LinkError::Timeout { phase }`.
2. `apps/rendezvous/src/federation/outbound.rs` — every reply receive awaited under a per-exchange
   timeout; mapped to `FED_UNREACHABLE`.
3. `apps/rendezvous/src/config.rs` — `federation.connect_timeout_ms`,
   `federation.request_timeout_ms` (**`TODO: confirm` defaults** — proposed 5_000 / 10_000).
4. `apps/rendezvous/tests/federation_timeouts.rs` — a listener that accepts TCP and never handshakes
   → fetch returns `fed_unreachable` within bound; a peer that completes `FedHello` then never
   replies → same; the link gauge / task count returns to baseline after the client disconnects
   (**no leak**).

## Risks / notes
- Must not introduce a **timing oracle** distinguishing "policy denial" (3.1) from "timeout" — a
  denial is immediate and a timeout is not, which is already observable; keep the client-visible
  codes as 2.9 defined them and note the residual rather than papering over it.
- Cancellation-on-disconnect is the part most likely to be asserted vacuously; prove the task count
  actually drops.
