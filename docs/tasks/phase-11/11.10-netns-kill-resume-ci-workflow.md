# 11.10 — Add scheduled/`workflow_dispatch` CI for `netns-kill-resume.sh`

**Phase:** 11 — Review of Phase 10 · **Feature:** review fix (F10) · **Depends on:** — · **Status:** done

**User surface:** none — CI-only task (Definition of Done gate 9 doesn't apply).

## Goal
Give the kill/resume rig (`tools/netns-kill-resume.sh`) the same scheduled CI coverage its two sibling
rigs already have, now that the SCTP-fix rationale for deliberately omitting it (task 10.15's own call)
no longer holds.

## Scope
- **In:** a new `.github/workflows/netns-kill-resume.yml`, scheduled + `workflow_dispatch`, mirroring
  `netns-netem-smoke.yml`/`soak-file-transfer.yml`'s structure (root/`NET_ADMIN` needs, the same
  fail-loudly-if-netem-unexpectedly-unavailable preflight, a distinct cron offset from the existing
  scheduled jobs to avoid runner-queue contention).
- **Out:** no change to `tools/netns-kill-resume.sh` itself (already fixed by task 10.23 — this task only
  wires CI around it).

## Deliverables
1. `.github/workflows/netns-kill-resume.yml` running `tools/netns-kill-resume.sh run` (and its `probe`
   companion if the workflow should also exercise that), on a schedule offset from the existing scheduled
   jobs plus `workflow_dispatch`.

## Risks / notes
`TODO: confirm` desired cadence — weekly, matching the existing scheduled jobs' own unresolved cadence
question (no on-call rotation exists yet to action a red run, per the operations runbook's own open
item) — not a new gap this task needs to resolve, just the same carried-forward one. Flag (don't fix) the
separately-scoped, non-blocking post-restart readiness race 10.23's own re-run found on the smaller
`probe` companion script if this workflow chooses to run `probe` too — out of this task's scope.

## Tests
The new workflow itself is the deliverable; no `cargo nextest` command applies. Confirm the workflow YAML
is well-formed (`actionlint` if available, or a structural read against the existing sibling workflows).

## Reviews
**devops** (mandatory — CI workflow structure), **code-reviewer**.

## Outcome
Shipped `.github/workflows/netns-kill-resume.yml`: scheduled (Monday 10:00 UTC, offset from the four
existing scheduled jobs) + `workflow_dispatch`, building both driver examples (`--features webrtc`),
running `run` then `probe`, with a `netns/veth`-specific fail-loudly preflight (adapted from the
siblings' netem-modprobe preflight — this rig needs no netem) and an `if: always()` teardown.

Two review rounds surfaced real findings, both fixed in same-task follow-up commits:
- **devops** (round 1): `timeout-minutes: 15` was too tight against the script's own worst-case
  internal wait budget (~7.5 min for `run`+`probe`) plus two uncached `--features webrtc` builds —
  widened to 20, matching `soak-file-transfer.yml`'s build-to-runtime headroom ratio.
- **code-reviewer** (round 1, blocking): running `probe` as a hard step would make this job
  permanently red — `probe` reproduces a known, still-open, non-blocking post-restart DTLS/SCTP
  readiness race (task 10.23: 4/4 fail, not fixed by 10.24), distinct from the two historical gaps
  this workflow exists to confirm are fixed. Fixed with `continue-on-error: true` on the `probe` step
  plus a documenting comment, mirroring `soak-file-transfer.yml`'s own "EXPECTED TO BE RED"
  convention, so `probe`'s known failure can never mask a real regression in `run`.
- **code-reviewer** (round 1, should-fix): the preflight only tested netns/veth object creation, not
  link-state toggling — the actual capability `need_veth_linkstate()` checks. Fixed by adding an
  `up`/`down`/`up` toggle to the preflight.

Zero blocking or should-fix findings survived a final pass. `tools/netns-kill-resume.sh` itself
received no changes (out of scope, confirmed still correct post-10.23).
