# 10.4 — Generalize the session substrate to drive a second stream type

**Phase:** 10 — File Transfer Stream · **Feature:** T09 (substrate completion, not the feature itself)
· **Depends on:** 10.1, 10.2 · **Status:** done

**User surface:** none — core-crate substrate completion with no user-visible behavior change (chat/ctrl
are unaffected; the first real consumer is task 10.6). No TUI surface applies to this task.

## Goal
Complete the generic multi-stream machinery `apps/core/src/session.rs` was always meant to have but
never finished: today, `open_stream`/`handle_ctrl`'s `Open`/`Accept` arms negotiate a stream over
`mrd.ctrl/1` but never actually open a second WebRTC data channel, and `pump`'s demux only recognizes
the two hardcoded `CTRL_LABEL`/`CHAT_LABEL` channels — anything else is force-decoded as a ctrl frame.
This task makes the substrate able to drive **any** registered stream type generically, which every
future stream type (T10/T15/T16) needs identically, not just `mrd.file/1`.

**This finding and its fix shape were settled by an architect consult during `/plan-phase`** (see
[phase-10/README.md](./README.md)'s dependency-check/decisions section for the full record) — this task
file implements that decision, it does not re-open it.

## Scope
- **In:**
  1. Symmetric, explicit `transport.add_data_channel(...)` on **both** sides for a non-chat/ctrl
     stream — the responder calls it when deciding `OpenDecision::Accept` (alongside sending
     `CtrlFrame::Accept`), the initiator calls it on receiving `CtrlFrame::Accept`. Both derive the same
     channel label/negotiated id from the stream id (mirroring `CTRL_LABEL`/`CHAT_LABEL`'s existing
     `stream_id_for_label`-style symmetric pattern in `apps/transport/src/webrtc_backend.rs` — confirmed
     necessary because negotiated data channels do not fire an `ondatachannel`-equivalent event on a
     side that never called `add_data_channel` itself, and the loopback test transport also needs both
     sides to have called it to populate `P2pSession::labels`).
  2. Generalize `labels: HashMap<ChannelId, &'static str>` to hold dynamically-registered stream-type
     names (not `&'static str`-only), and add a `ChannelId ⇄ StreamId` bookkeeping map.
  3. Generalize `pump`'s demux: resolve a `ChannelId` to its stream type via the new label map, decrypt
     the frame generically (using task 10.1's export primitive, keyed by the stream's `type`/`sid`), and
     call the registered `StreamType::on_frame` with the decrypted bytes. Chat and ctrl keep their
     existing special-cased paths unchanged (no behavior change for `mrd.chat/1`).
  4. A new generic outbound path, `P2pSession::send_stream_frame(sid, bytes) -> Result<...>`, that
     encrypts (via 10.1's export) and sends on the stream's data channel — the only way a `StreamType`
     impl can ever push bytes out, since `on_frame` is synchronous with no return channel.
  5. A `buffered_amount`-backed backpressure query exposed alongside `send_stream_frame` (consumes
     task 10.2), so a sender engine (task 10.7) can throttle without this task inventing throttling
     policy itself.
- **Out:** **zero file-transfer-specific logic.** No mention of `mrd.file/1`, chunks, manifests, or
  merkle trees anywhere in this diff — this task must be reviewable as pure substrate completion that
  any future stream type benefits from identically. The `mrd.file/1` `StreamType` implementation itself
  is task 10.6 and must show zero diffs to this crate.

## Deliverables
1. Symmetric data-channel open on Open/Accept in `apps/core/src/session.rs`.
2. Generalized `labels` map + `ChannelId ⇄ StreamId` bookkeeping.
3. Generic decrypt-and-dispatch in `pump` for any non-chat/ctrl channel.
4. `P2pSession::send_stream_frame` + backpressure query.
5. Tests using the existing test-only `Exotic`-style stream type (already present in
   `apps/core/src/streams.rs`'s own test module) driven end-to-end over the loopback transport: open,
   accept, send a frame each way, confirm `on_frame` fires with correctly decrypted bytes, confirm
   backpressure query reflects a synthetic buffered-amount.

## Risks / notes
This is a `meridian-core::session` (core crate) change — legitimate per the architect consult (T04's own
scope note in `open_stream`'s doc comment already anticipated "T09 is the first second stream type to
drive it"), but the review gate below must explicitly confirm no file-type-specific logic leaked in;
treat any diff outside the generic label/dispatch/backpressure machinery as a review-blocking finding.

`docs/architecture/system-design.md` line ~202 says "the initiator opens" the data channel — this task's
actual (symmetric) implementation is more precise than that prose; task 10.12 records the `/doc-sync`
correction, this task does not need to edit system-design.md itself.

`cargo nextest run -p meridian-core`.

## Reviews
**reviewer** (combined pass: architect lens — mandatory, must explicitly confirm zero file-type-specific
logic landed in `session.rs`/`streams.rs`; security-reviewer lens — the generic decrypt-and-dispatch
path is new security-relevant code even though it reuses 10.1's already-reviewed primitive).

## Outcome
Generalized `apps/core/src/session.rs`'s substrate to drive any registered stream type generically.
Symmetric `transport.add_data_channel(...)` on both Open/Accept sides (label = `format!("{ty}#{sid}")`,
matching the existing `CTRL_LABEL`/`CHAT_LABEL` pattern); generalized `labels: HashMap<ChannelId,
String>` plus new `channel_of_stream`/`stream_channels`/`pending_opens` bookkeeping; a three-way `pump`
demux (chat/ctrl unchanged, any other label → generic decrypt via new `ChatState::open_stream_frame` +
registered `StreamType::on_frame` dispatch); `P2pSession::send_stream_frame`/`stream_buffered_amount` as
the only outbound path plus a backpressure query; new `Session::encrypt_and_export`/`decrypt_and_export`
wrappers in `apps/crypto/src/session.rs` over task 10.1's ratchet primitives; new
`ChatState::seal_stream_frame`/`open_stream_frame` bypassing the `MessageEnvelope`/eid/prekey wrapper
(sound because stream frames only ever flow post-handshake-confirmation). Along the way, fixed a latent
pre-existing bug: `Accept`'s `SessionEvent::StreamOpened` always reported `CHAT_LABEL` regardless of
which stream was actually accepted, masked by the one existing test that discarded the field.

Two on-the-fly interim decisions, both flagged for task 10.12 to formalize rather than silently
re-litigated: the `info` byte encoding for the HKDF export (`b"mrd/stream/" ‖ type ‖ sid.to_be_bytes()`
— task 10.1 explicitly deferred this exact layout here); and calling `encrypt_and_export`/
`decrypt_and_export` on every stream frame rather than once at OPEN as `stream-types-v1.md`'s current
prose reads — architect review confirmed this isn't a smell but is actually corroborated by task 10.5's
own already-reviewed design (10.5's security-reviewer explicitly assumed 10.4's per-frame ratchet export
as the outer AEAD layer above per-chunk AEAD), so `stream-types-v1.md`'s "once at OPEN" text is the stale
artifact, not this diff.

Both mandatory review lenses (architect, security-reviewer, run as one combined `reviewer` pass)
returned **PASS**, independently confirmed via direct grep (not trusting the implementer's own) that
zero file-transfer-specific logic landed in the diff, confirmed the symmetric channel-open shape against
both the real webrtc-rs backend's negotiated-channel semantics and the loopback transport, confirmed
`pending_opens` is the right minimal bookkeeping choice rather than a wire-protocol gap (`Accept`
carrying no type is correct by design — the initiator already knows what it asked for), traced the
`seal_stream_frame`/`open_stream_frame` bypass's safety directly through the `confirmed` flag rather
than trusting the doc comment, and confirmed the generic dispatch path fails closed on malformed/unknown
frames with no panics. One should-fix was closed in a same-task follow-up commit before this task was
marked done: the discarded per-frame HKDF export (`_exported: [u8; 32]`, unused since no consumer exists
yet) was left unzeroized at both call sites — fixed by zeroizing it explicitly before it drops, extending
`apps/crypto`'s zeroize-secret-material discipline to this call site even though it lives in
`apps/core`. All 159 `meridian-core` tests (plus 182 combined with `meridian-crypto`) stayed green
throughout, independently re-run after the fix; clippy/fmt clean.

Two non-blocking findings carried forward, neither owned by an open task:
- **Stale doc prose** — `stream-types-v1.md`'s "Stream framing" section still describes a single
  derive-at-OPEN key with a separate per-frame symmetric AEAD, not the nested per-frame-outer
  (`encrypt_and_export`)/per-chunk-inner (task 10.5's `seal_chunk`) construction actually being built;
  `apps/transport/src/webrtc_backend.rs`'s own module doc still describes the pre-10.4 "only two
  channels ever" behavior as current. Both are squarely inside task 10.12's already-planned doc-sync
  scope (10.12 depends on both 10.4 and 10.6) — flagged explicitly for whoever picks it up, not a new
  carry-forward needing its own task.
- **`CtrlFrame::Close` doesn't clean up the new per-stream bookkeeping or tear down the data channel** —
  dormant today (`Close` is receive-only, never sent anywhere in the tree), but will become live the
  moment 10.6/10.9 start sending `Close` on transfer completion/cancellation. Not in this task's scope;
  flagged for whoever implements `Close`-sending (likely 10.9's resume/redial work or 10.6/10.7's
  transfer-completion path) to purge `labels`/`channel_of_stream`/`stream_channels` for that `sid`.
