# 7.1 — Flag-day hard-reject test coverage

**Phase:** 7 — Review of Phase 6 · **Feature:** review fix (F1, F2) · **Depends on:** — · **Status:** done

## Goal
Prove `ChatError::UnsupportedEnvelopeVersion` (ADR 0016 C5/R5) actually fires — both for a
structurally v2-shaped envelope carrying a wrong `v` value (F1, blocking), and for the real flag-day
scenario of a genuine v1-shaped blob (F2, should-fix). The enforcement code itself
(`apps/core/src/chat.rs:1660-1665`) was independently confirmed correct by all four Phase-7 reviewers;
this task is about proving it, not fixing it.

## Scope
- **In:** `apps/core/tests/chat_manager.rs` — two new test cells (see Deliverables). If cell 2 confirms
  that a genuine v1-shaped blob fails at codec decode rather than at the version check (expected), a
  one-line precision edit to `docs/api/messaging-envelope-v1.md`'s already-rewritten C5/R5 receiver-rules
  paragraph, scoping "clean, diagnosable hard error" to structurally v2-shaped envelopes with a wrong `v`.
- **Out:** No production code change in `apps/core/src/chat.rs` is expected — if either new test reveals
  a genuine defect, stop and flag it rather than silently patching around it; that would be a new finding,
  not this task's scope.

## Deliverables
1. **Wrong-`v`, v2-shaped envelope test**: take a genuine opening envelope (`Party::send`/`seal_bytes`),
   decode via `MessageEnvelope::from_blob`, set `.v` to a non-2 value (e.g. `1`), re-encode via
   `.to_blob()`, feed to `open_bytes` directly (not the `Party::recv`/`open_inbound` wrapper — avoids the
   message-request gate). Assert `Err(ChatError::UnsupportedEnvelopeVersion(1))`, and assert OTK pool
   depth and the receiver's serialized state are byte-identical before/after (same technique as
   `eid_dedup.rs`/`preamble_mutation.rs`). Add a positive control: the genuine `v:2` envelope still
   succeeds.
2. **Genuine v1-shaped blob test**: feed the `"no-prekey"` vector's `blob_hex` from
   `test-vectors/envelope-v1.json` directly into `open_bytes` (via `hex::decode` + `from_blob`), and pin
   the *exact* error variant that surfaces — expected `ChatError::Codec(_)`, since a v1 blob has no `v`
   field to decode as `u16` and fails before the version check ever runs.
3. Conditional on (2)'s outcome: the `messaging-envelope-v1.md` precision edit described above.

## Risks / notes
`open_bytes` must not be given a chance to touch OTK pool state or install a session on either new
negative-path test — assert this explicitly, not just the returned error variant, mirroring the
byte-identical-state discipline `commit_on_decrypt_independent.rs` already established for C2.

## Status
**Done.** Added two cells to `apps/core/tests/chat_manager.rs` plus a new `Party::recv_raw` helper
(drives `ChatState::open_bytes` directly, bypassing `open_inbound`'s message-request gate, matching
`eid_dedup.rs`/`commit_on_decrypt_independent.rs`'s own precedent):

- `wrong_v_on_v2_shaped_envelope_is_hard_rejected_by_open_bytes` (F1) — mutates only `v` on a genuine
  envelope to a non-2 value, asserts `Err(ChatError::UnsupportedEnvelopeVersion(1))` with OTK-pool
  depth and full serialized state byte-identical before/after, plus a positive control (genuine `v:2`
  envelope still opens, consumes exactly one OTK).
- `genuine_v1_shaped_blob_fails_at_codec_decode_not_the_version_check` (F2) — feeds
  `test-vectors/envelope-v1.json`'s `"no-prekey"` vector's real blob through `open_bytes`; empirically
  confirmed (not assumed) that it fails with `ChatError::Codec(_)` before the version check is ever
  reached, since v1 has no `v`/`eid` fields to decode.

Conditional doc edit landed: `docs/api/messaging-envelope-v1.md` §4's C5/R5 receiver-rules paragraph
now scopes the "clean, diagnosable hard error" claim to structurally-v2-shaped-but-wrong-version
envelopes, noting a genuine v1-shaped blob fails earlier at codec decode with a distinguishable but
different diagnostic (`ChatError::Codec`).

**No production code changed** — `apps/core/src/chat.rs` untouched; both new tests fire exactly as
ADR 0016/the review predicted, so nothing needed escalating.

**Falsifiability, independently verified by test-engineer**: temporarily neutralized `open_bytes`'s

green — the new coverage is genuinely falsifiable, not tautological.
