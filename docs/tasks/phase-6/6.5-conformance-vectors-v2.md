# 6.5 — Conformance vectors: `ratchet-v2.json` + `envelope-v2.json`

**Phase:** 6 — Envelope v2 · **Feature:** ADR 0016 (vector obligation) · **Depends on:** 6.3, 6.4 · **Status:** done

## Goal
Freeze the v2 wire/ratchet construction as byte-identical fixtures, per the crypto-protocols skill's
Definition of Done and ADR 0016's "Follow-up build task" obligation: changing the ratchet AAD changes
the *ratchet message* construction, so `ratchet-v1.json` gets a `ratchet-v2.json` sibling alongside a
new `envelope-v2.json`.

## Scope
- **In:** `tools/xtask/src/vectors/envelope.rs` (new `generate_envelope_v2`, alongside the retained,
  untouched `generate_envelope` for v1), `tools/xtask/src/vectors/ratchet.rs` (new `ratchet-v2.json`
  generator reflecting the new AAD/preamble-parameterized `encrypt`/`decrypt`), `apps/crypto/tests/conformance.rs`.
- **Out:** the implementation being vectorized (6.3, 6.4 — this task freezes it, doesn't change it).

## Deliverables
1. `test-vectors/envelope-v2.json`, `test-vectors/ratchet-v2.json` — v1 files retained, never
   hand-edited, per the ADR/skill's "vectors are canonical" rule.
2. `apps/crypto/tests/conformance.rs` updated to load and assert both `-v2.json` files alongside the
   existing `-v1.json` loads.
3. A harness-integrity check for the new AAD construction, analogous to the existing
   `x3dh.rs::divergent_kdf_label_does_not_match_committed_vector` pattern — proof that the conformance
   harness actually catches drift in the domain-tag/preamble-in-AAD construction, since that is exactly
   the kind of silent-drift risk this test class exists to catch.

## Risks / notes
- Low implementation risk (mechanical regeneration), but the vectors are only as correct as 6.3/6.4's
  implementation — a mistake there just freezes a bug here. This task's review should re-derive at
  least one vector by hand against the ADR's canonical AAD formula, not just trust the generator output.

## Tests
```
cargo run -p xtask -- vectors
cargo nextest run -p meridian-crypto --test conformance
```
Run `cargo run -p xtask -- vectors` twice and diff — must be byte-identical (determinism check,
mirroring existing v1 discipline).

## Outcome

**Implemented.** Both new v2 conformance-vector files exist and are consumed by
`apps/crypto/tests/conformance.rs`, exactly per scope:

- **`tools/xtask/src/vectors/envelope.rs`** — `generate_envelope()` (v1) is untouched and remains a
  documented permanent no-op (there is no way to construct a v1-shaped `MessageEnvelope` from
  current code — v1/v2 is a hard flag day). New `generate_envelope_v2()` builds the real v2
  `MessageEnvelope` (`v`, `sender_pub`, `eid`, `prekey`, `ct`) for the same three prekey-shape cases
  v1 covered (`no-prekey`, `prekey-no-opk`, `prekey-with-opk`), encodes each via the crate's real
  `MessageEnvelope::to_blob()` (deterministic CBOR, ciborium), and writes
  `test-vectors/envelope-v2.json`. The generator also round-trips `from_blob(to_blob(_))` against
  itself before ever writing the file, as a sanity check on the generator (not a substitute for
  `conformance.rs`'s independent re-derivation, which is what actually gates drift).
- **`tools/xtask/src/vectors/ratchet.rs`** — new `generate_ratchet_v2()`, parallel in structure to
  the v1 generator (same transcript: an opening message, three out-of-order deliveries exercising
  the skipped-key path, and a reply riding a CSPRNG-seeded DH-ratchet step), using fresh, dedicated
  `*V2` fixture structs so `ratchet-v1.json`'s exact shape and content are untouched. Two new
  deterministic quantities were added, both read from real code, never reimplemented:
  - `initial_state.baked_ad_hex` — `"mrd.env/2" ‖ AD`, read back via the real, public
    `DoubleRatchet::associated_data()` getter (the fixed AAD component baked in at construction,
    ADR 0016 C3).
  - `transcript[].preamble_hex` / `aad_prefix_hex` — every step now threads a real preamble through
    `encrypt`/`decrypt` (non-empty, presence-flag-encoded, on the session-opening message; empty on
    continuation messages, matching how a real X3DH preamble is only attached to a session's
    opening message(s)); `aad_prefix_hex` = `baked_ad ‖ preamble` for that step. Both are pinned on
    **every** step regardless of `chain_key_pinned`, because — unlike chain/message keys and the
    ciphertext/header — neither depends on `dh_ratchet`'s random keypair draw or `header_seal`'s
    random nonce. The full per-message AAD (`aad_prefix ‖ enc_header`) stops short of being pinned
    for the same reason ciphertext/header ciphertext never were: `enc_header` carries a random
    nonce.
- **`apps/crypto/tests/conformance.rs`** — `ratchet_v2_vectors_match_real_derivation` (sibling of
  the v1 test: re-derives `alice_initial_root/cks/nhks` via `test_support::dh`/`kdf_rk`, checks
  `baked_ad_hex` against the real `associated_data()`, checks every step's `aad_prefix_hex` against
  `associated_data() ‖ preamble`, drives each step through the real `encrypt`/`decrypt` with its
  recorded preamble, and checks chain-key continuity exactly as the v1 test does).
  `envelope_vectors_match_real_encoding` is un-ignored and rewritten against `envelope-v2.json` (the
  v1 body, and the `#[ignore]`, are gone — `envelope-v1.json` itself is untouched and stays
  committed as a frozen historical record with no live re-derivation consumer, since v2 cannot
  construct a v1-shaped envelope at all).

### Harness-integrity check

New test `ratchet_v2_aad_harness_catches_domain_tag_and_preamble_drift`, directly analogous to
`x3dh.rs::divergent_kdf_label_does_not_match_committed_vector`: it first confirms the *real*
construction (`DoubleRatchet::associated_data()`) matches the committed `baked_ad_hex` (so the test
proves something), then computes two classes of deliberately-wrong construction and asserts neither
reproduces the committed vector:

1. **Domain-tag drift** — the raw X3DH `AD` alone, with no `"mrd.env/2"` prefix at all. This stands
   in for "the old v1 construction" specifically because v1's AAD never carried a domain tag in the
   first place (the ADR's own account: v1's ratchet AAD was `AD ‖ enc_header`), so "drop/omit the
   domain tag" and "regress to the v1 shape" are the same wrong value here. Asserted to not equal
   `baked_ad_hex`.
2. **Preamble drift** — targeting the session-opening step's non-empty preamble two ways: (a)
   omitting the preamble from the AAD entirely (`baked_ad` alone), and (b) substituting a
   locally-recomputed preamble (`0xFF` bytes of the same length) for the genuinely-received one —
   the exact "helpfully recomputes what it expects" regression `DoubleRatchet::decrypt`'s own doc
   comment warns against. Both asserted to not equal the committed `aad_prefix_hex` for that step.

Every "correct" value used in this test comes from `DoubleRatchet::associated_data()` (real, public
API); only the deliberately-wrong comparison values are hand-built from raw bytes — the AAD
construction itself (`bake_ad`/`message_aad`/`AAD_DOMAIN`) is crate-private and was never
reimplemented here, matching the task's traceability requirement.

### Determinism check

`cargo run -p xtask -- vectors` run twice; `diff`'d both new files byte-for-byte against each other
across the two runs — identical both times (including after a `cargo fmt` pass in between, which
reformats generator source but cannot itself change generated output). No wall-clock or non-fixed
RNG input feeds either generator: all keys/plaintexts/preambles are fixed byte patterns, matching
the existing v1 discipline.

### v1 byte-identity confirmation

`sha256sum test-vectors/{envelope,ratchet}-v1.json` taken before any change and re-checked after
every subsequent generator run (including the final one) — identical throughout:
`envelope-v1.json` = `97faec38…8725`, `ratchet-v1.json` = `3424f26c…5382`. `generate_envelope()`
(v1) never calls `write_json` at all (confirmed: `cargo run -p xtask -- vectors`'s own output lists
`ratchet-v1.json` as written — since `generate_ratchet()` is unchanged and still runs — but never
lists `envelope-v1.json`, since `generate_envelope()` is a no-op).

### Deviations / follow-ups for review

- No production code was touched (confirmed: `git status` shows only
  `apps/crypto/tests/conformance.rs` and `tools/xtask/src/vectors/{envelope,ratchet,mod}.rs`,
  plus the two new committed vector files).
- **Fixed after review** (was a should-fix): `ratchet.rs`'s `preamble0` was initially hand-built as
  raw bytes rather than via `meridian_envelope::preamble_aad_bytes` directly, on a mistaken premise
  (this Outcome originally said "`meridian-crypto` does not depend on `meridian-envelope`" — true,
  but irrelevant: the generator lives in the **`xtask`** crate, not `meridian-crypto`, and `xtask`
  already depends on `meridian-envelope`, confirmed by `envelope.rs`'s own generator in this same
  directory already importing it). Now calls `preamble_aad_bytes(&Some(Prekey{ek_pub, used_spk,
  used_opk: None}))` directly — eliminates the "hand-reproduced shape could silently diverge from
  production" risk this task's own Risks section warns about. Regenerated and confirmed
  byte-identical to the pre-fix committed vectors (sha256 unchanged for both `-v2.json` files),
  which independently corroborates review's hand-derivation match. `meridian-crypto`'s own
  `session.rs::preamble_bytes` copy is unaffected by this fix and remains F15's necessary
  hand-kept twin (that crate genuinely cannot take the dependency).
- Full per-message AAD (including `enc_header`) is never byte-pinned in `ratchet-v2.json`, same
  determinism-boundary reason as v1's ciphertext/header-ciphertext. Only the deterministic prefix
  (`baked_ad ‖ preamble`) is pinned. This was a deliberate design choice to keep the vector
  byte-identical across runs, flagged here in case review wants a different boundary.
