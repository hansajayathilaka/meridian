# 10.18 — Fix: real `WebRtcTransport` can't send a full 64 KiB `mrd.file/1` chunk

**Phase:** 10 — File Transfer Stream · **Feature:** T09 (fix; benefits any future stream type sending a
large single frame) · **Depends on:** 10.7 · **Status:** done

## Goal
Fix a functional defect independently discovered and corroborated by tasks 10.14 (soak test) and 10.15
(kill/resume automation): the real `WebRtcTransport` cannot send a single full 64 KiB `mrd.file/1`
chunk — every transfer needing more than one chunk fails deterministically, over plain loopback, with
no network impairment involved:
```
error: <name>: session error while sending a chunk: transport error: transport backend error:
outbound packet larger than maximum message size
```
This is not a throughput ceiling (the kind ADR 0006 already accepted as a known SCTP-over-DTLS cost) —
it is zero bytes per second for any real multi-chunk file, over any network condition, because the
wiring cannot move a single full-size chunk at all. It must be fixed before task 10.17's phase-exit
demo can run the feature's real acceptance demo over actual WebRTC.

## Root cause
`mrd.file/1` chunks a file into 64 KiB (65536-byte) pieces and sends each as one transport message (no
separate length prefix — SCTP already frames messages). Each chunk is per-chunk AEAD-sealed under its
own key, then the whole frame is ratchet-sealed again (one Double Ratchet step per frame) before CBOR
framing — so the actual bytes handed to the SCTP data channel for one "full" chunk are 65536 bytes of
plaintext plus per-chunk AEAD overhead plus the outer ratchet header/tag plus CBOR framing overhead:
comfortably more than 65536 bytes total. `apps/transport/src/webrtc_backend.rs`'s `WebRtcTransport::new()`
builds its `SettingEngine` with no SCTP max-message-size override, so `webrtc-rs`/`webrtc-sctp`'s own
default applies (`SctpMaxMessageSize::DEFAULT_MESSAGE_SIZE = 65536`). Two `webrtc-rs` peers with neither
side configuring a larger value (exactly the CLI↔CLI, terminal-client scenario `meridian send` is built
for — no browser involved to negotiate a larger `a=max-message-size`) negotiate that same 65536-byte
ceiling, which every full chunk then narrowly exceeds.

Confirmed independently by two different harnesses hitting the identical error: task 10.14's
`tools/soak-file-transfer.sh loopback` (a 2 MiB file fails immediately on the first full chunk; a
60000-byte single-chunk file completes and verifies byte-perfect) and task 10.15's
`apps/cli/examples/kill_resume_netns_drive.rs` (a different driver, built directly against
`P2pSession`/`WebRtcTransport`, hit the same error on its own ~1.5 MiB test file). Full write-up:
[docs/testing/soak-file-transfer-throughput.md](../../testing/soak-file-transfer-throughput.md).

## Scope
- **In:** `apps/transport/src/webrtc_backend.rs`'s `WebRtcTransport::new()` — configure a larger
  negotiated SCTP max-message-size via `webrtc-rs`'s `SettingEngine::set_sctp_max_message_size_can_send`
  (and the matching receive-side setting if `webrtc-rs`/`webrtc-sctp` requires it symmetrically — check
  the crate's actual API), comfortably above 65536 bytes plus the measured framing overhead (e.g.
  256 KiB, a size several real-world WebRTC stacks already default to). A regression test proving a
  full multi-chunk `mrd.file/1` transfer now completes over the real `WebRtcTransport` (not
  `LoopbackTransport`, which never had this problem since it doesn't model SCTP framing limits at
  all) — extend or add to `apps/transport/tests/`'s existing real-backend test suite (check what's
  already there, e.g. whatever task 10.10's own `session_connect_webrtc` test or similar exercises,
  for the established pattern of driving two real `WebRtcTransport` instances).
- **Out:** the separate, pre-existing, already-documented gap that `WebRtcTransport::ice_restart` does
  not fulfill the "resumable... ICE restarts on network change" promise (module doc, lines 70–91 of
  the same file) — that is architect-review territory needing a ctrl-channel renegotiation design, not
  a config value, and is unrelated to this chunk-size defect. Do not touch `ice_restart` in this task.
  Also out of scope: any change to `mrd.file/1`'s own chunk size (64 KiB stays as pinned in
  `docs/api/stream-types-v1.md`) — the fix is entirely on the transport's own negotiated ceiling, not
  the wire-level chunk size.

## Deliverables
1. `SettingEngine` configuration change in `apps/transport/src/webrtc_backend.rs`'s `WebRtcTransport::new()`.
2. A real-backend regression test proving a multi-chunk file transfer (at least 2–3 chunks) completes
   byte-identical over two real `WebRtcTransport` instances — this is the test that was impossible to
   write correctly before this fix (it would have failed for the right but undesired reason).
3. Re-run of task 10.14's `tools/soak-file-transfer.sh loopback` at a multi-chunk size (e.g. 2 MiB) to
   confirm the fix in situ, and an update to `docs/testing/soak-file-transfer-throughput.md` recording
   the now-real throughput number(s) this unblocks (1 GiB if practical in this environment; if not,
   note honestly what was actually re-measured, same honesty discipline as task 10.14 itself).

## Risks / notes
Increasing `max_message_size` is a local negotiation parameter (each SCTP association's own configured
ceiling, part of the DCEP/SCTP handshake, not a `mrd.file/1`-specific wire change) — it doesn't touch
`meridian-proto`'s wire types or require a conformance-vector update, but it IS a change to
`meridian-core`'s dependency `meridian-transport`, a shared substrate every stream type rides on, so it
warrants architect sign-off alongside code-reviewer (not because the fix is architecturally novel, but
because `apps/transport` is exactly the kind of shared-substrate crate this repo's own discipline says
should get a second look before a config change lands). Check whether `webrtc-rs`'s
`set_sctp_max_message_size_can_send` needs a matching value on both dial and answer paths (it should be
symmetric, but confirm empirically with the new regression test — a value set on only one side that
still negotiates asymmetrically would be a subtle, easy-to-miss regression this task must not introduce).

## Outcome

### The fix turned out to need three parts, not the one originally scoped
Reading `webrtc-rs` 0.17.1's own source (not just its public API docs) surfaced two additional,
undocumented gaps beyond the config value this task's Scope named:

1. `SettingEngine::set_sctp_max_message_size_can_send(SctpMaxMessageSize::Bounded(262144))` (256 KiB)
   in `WebRtcTransport::new()` — raises this side's own send ceiling. Byte-value reasoning: a measured
   full on-the-wire `mrd.file/1` chunk is 65665 bytes for one of the first 24 chunks of a file (65536
   plaintext + 16 chunk-AEAD tag + 14 CBOR `ChunkFrame` framing + 1 frame-kind discriminator + 2
   ratchet header-length prefix + 80 encrypted ratchet header + 16 ratchet AEAD tag) — CBOR's
   variable-length chunk-index encoding grows the 14-byte figure by a few bytes for a chunk later in a
   very large file, still comfortably inside 256 KiB's ~4x headroom.
2. **Found by reading source, not anticipated in this task's own Scope**: `webrtc-rs` 0.17.1's SDP
   writer never emits `a=max-message-size` in outgoing SDP on either side under any `SettingEngine`
   configuration, so a peer always reads the RFC default (65536) as "what the peer can receive,"
   making #1 alone silently ineffective (`min(65536, can_send) == 65536`). Fixed by
   `with_max_message_size_attr` appending the attribute to the SDP text lazily, at the
   `Transport::local_description()` read boundary — not at write time, because `set_local_description`
   independently validates the text against its own internal snapshot byte-for-byte, so mutating
   earlier fails with `ErrSDPDoesNotMatchOffer`/`ErrSDPDoesNotMatchAnswer` (confirmed empirically).
3. **Found via a failing regression test, a second undocumented gap**: even with #1–#2 fixed,
   `RTCDataChannel::on_message`'s internal read loop uses a fixed, non-configurable 65535-byte buffer
   and closes the channel outright (no error either side) on anything larger. Fixed via
   `SettingEngine::detach_data_channels()` plus a new `detached_channel_read_loop` driving each
   channel's own reads with a `SCTP_MAX_MESSAGE_SIZE`-sized buffer.

New regression test: `multi_chunk_file_transfer_completes_over_real_sctp`
(`apps/transport/tests/webrtc_backend.rs`), sending three real 65665-byte messages in both directions
over one connected real pair — proves the fix is symmetric (identical for both dial and answer roles,
since `WebRtcTransport::new()` is the single shared constructor for both). `ice_restart` is untouched.
Re-ran task 10.14's own harness: `tools/soak-file-transfer.sh loopback --size-mib 2` now **PASSes**
(previously **BLOCKED**), plus a `--size-mib 64` run, both sha256-identical — recorded in
[docs/testing/soak-file-transfer-throughput.md](../../testing/soak-file-transfer-throughput.md). A 1
GiB run needs a longer-running environment than this sandbox reliably provides; noted honestly as such
rather than fabricated.

### Review: PASS, with one finding investigated and closed, two applied
The combined architect + code-reviewer pass verified the SDP-mutation safety (placement, idempotency,
and that `local_description()`'s attribute-appended text is what actually reaches the peer while the
pristine cached text is what reaches `set_local_description`, tracing the real call sites in
`apps/core/src/session.rs`) and the detach-model safety (`RTCDataChannel::handle_open` never spawns a
competing internal read loop when `detach_data_channels` is set, so nothing discards data before this
backend's own detach; `buffered_amount()`/`send()` are unaffected by detach state) against the actual
`webrtc-rs`/`sdp` crate source, not just this task's own claims. Three findings:

1. **[correctness, investigated]** The reviewer observed one ~31-minute hang in a pre-existing,
   unmodified test (`meridian-core`'s `ice_restart_keeps_the_live_channel_flowing`) while running the
   required test matrix under heavy concurrent system load (several parallel `cargo`/`clippy`
   invocations on this sandbox's 4 vCPUs), not reliably reproduced (clean in 6 of 7 runs). Investigated
   directly: reproduced the same class of stall — 3 of 6 runs of `meridian-core`'s webrtc test suite
   failed to complete within 120s under equivalent concurrent load — **on the pre-fix tree** (`git
   stash` back to before this task's changes), where it normally completes in 15–50s. This is strong
   evidence the stalling is a **pre-existing characteristic of real-network WebRTC tests under severe
   CPU starvation on this specific sandbox** (plausibly ICE/SCTP retry-timer backoff compounding when
   the runtime can't service timers promptly), not a regression this task's detach/read-loop change
   introduced. Not fixed here (out of scope — a systemic test-infra/robustness gap, not specific to the
   SCTP fix): `Transport::recv()` has no bounded timeout anywhere in its call chain, so a genuinely
   stalled network path hangs forever with no error on either side instead of failing loudly and fast.
   Recorded as a Live carry-forward in `docs/tasks/README.md` for a future task to add a bounded
   timeout at the `Transport::recv()`/test-harness level. One additional, corroborating data point
   surfaced during this same investigation: `send_immediately_before_close_is_still_delivered`
   (itself a pre-existing, unmodified timing-race regression test with its own 5-second
   `tokio::time::timeout`) failed once immediately after a round of heavy self-induced contention,
   then passed cleanly in 5 immediate reruns with no contention — consistent with the same
   contention-sensitivity class, not a deterministic regression. This task's fix does add one extra
   scheduling hop to the delivery path (the spawned `detached_channel_read_loop` task forwarding
   through an `mpsc` channel, versus the previous direct library callback), which is a plausible,
   non-alarming reason that test's own timing margin could occasionally be exercised under extreme
   contention — flagged here for the same future timeout-hardening task to consider, not treated as
   a blocker given the clean reruns.
2. **[documentation, non-blocking, applied]** The "byte-exact 65665" framing overclaimed precision —
   CBOR's variable-length chunk-index encoding actually grows the on-wire size by a few bytes for
   chunks at index ≥24/≥256/≥65536. Fixed in the module doc, the `SCTP_MAX_MESSAGE_SIZE` doc comment,
   the regression test's own comments, and this throughput doc — all now say "one of the first 24
   chunks" rather than claiming exactness for every chunk. Not a functional bug (256 KiB leaves ~196
   KiB of headroom regardless), purely a documentation-precision fix for a future maintainer re-tuning
   the constant.
3. **[architecture, non-blocking, applied]** `with_max_message_size_attr` unconditionally appended the
   attribute with no guard against a future `webrtc-rs` upgrade that fixes the upstream SDP-writer gap
   this function works around, which would then produce a duplicate/conflicting line. Added a
   `debug_assert!` guarding against exactly that, with a comment naming the upgrade-time risk directly.
