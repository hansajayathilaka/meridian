# 12.9 — File transfer screen

**Phase:** 12 — Browser & Desktop Clients · **Feature:** T11 · **Depends on:** 12.2, 12.7 · **Status:** done

**User surface:** browser + desktop file-transfer screen (wired by 12.14/12.15) — the new-platform
equivalent of the terminal client's existing `mrd.file/1` TUI surface (Phase 10, task 10.11). No TUI
surface applies to this task (already shipped, unaffected; see the phase-wide "no TUI task" note in
[phase-12/README.md](./README.md#architect-consult-substratestoresigning-decisions-settled-before-task-breakdown)
point 5).

## Goal
Build drag-drop send, a progress UI, and the receive/accept-policy hook for `mrd.file/1`, wired against
the already-shipped stream type (T09/Phase 10) purely through `MeridianClientAdapter` — zero new
protocol logic and zero registry/core changes (Definition of Done gate 6: additive stream types touch
the registry only, which this task doesn't touch at all since `mrd.file/1` is already registered).

## Scope
- **In:** drag-drop / file-picker send UI; per-transfer progress display; receive prompt +
  accept/reject with the existing auto-accept-below-size-threshold policy hook (per the feature spec).
- **Out:** any change to `apps/streams`, the resume/bitmap protocol, or merkle verification — this
  screen only calls the adapter's already-defined file-transfer operations; the known, already-tracked
  gap that `mrd.file/1`'s per-chunk merkle proof delivery isn't fully wired into the real send path yet
  (Phase 11 fix-task 11.8's residual) is inherited as-is, not re-litigated or silently worked around
  here.

## Deliverables
1. `shared-ui/src/screens/FileTransfer.svelte`.
2. Component tests against the fake adapter: send-initiate, progress updates, receive-accept,
   receive-reject.

## Risks / notes
Do not claim or imply stronger corruption-detection guarantees in the UI than the underlying protocol
currently provides (the 11.8 residual above) — a progress/success indicator should reflect what the
adapter actually reports, not an assumed stronger property.

## Tests
`pnpm --filter shared-ui test`.

## Reviews
**code-reviewer**.

## Outcome
Shipped `FileTransfer.svelte` + `fileTransferStore.ts`: drag-drop/file-picker send, per-transfer progress,
and an inline accept/reject prompt for any transfer in the `"offered"` state.

**Deliberate deviation from the 12.7/12.8 precedent, recorded here as instructed rather than silently
taken**: unlike 12.7's `listMessageRequests` gap (documented but left unbacked, since a listing omission
had a workaround), this task extended `shared-ui/src/lib/adapter.ts`/`fake-adapter.ts` (task 12.2's owned
files) with `acceptTransfer`/`rejectTransfer`, because the gap was structurally load-bearing, not a nice
to have: `FileTransferSummary.state: "offered"` already existed in the type union, but zero code path
anywhere in the tree — including the already-shipped `apps/desktop/ui` adapter (task 12.6) — ever produced
or resolved it. This task's own Goal explicitly requires "the receive/accept-policy hook," which cannot
exist without an accept/reject method somewhere the screen can call. Also patched `apps/desktop/ui/src/
adapter.ts` (task 12.6's file) with fail-closed, GAP-documented stubs for the two new methods so it keeps
compiling — the real desktop backend has no live async round trip for this yet (`FileStream::with_ask_user`
is a synchronous closure the CLI satisfies with a blocking terminal prompt, structurally unusable from a
GUI event loop), left as an explicit, flagged gap rather than worked around.

Corruption-detection overclaim (this task's own named risk) avoided: `transferStateLabel` never renders
"verified"/"corruption-free" — `FileTransferSummary`'s doc comment now explicitly states `"complete"` is
transport-level completion only, and a dedicated test proves the UI never makes a stronger claim than the
adapter reports.

The review (code-reviewer, the task's sole named lens) returned **PASS**, zero blocking findings, after
independently confirming the interface-extension was genuinely load-bearing (not scope creep) — grepped
the pre-diff tree to verify zero code path produced `"offered"` before this task, confirmed the desktop
adapter's new stubs are genuinely fail-closed and match 12.6's own established GAP-comment convention, and
re-ran task 12.6's full 39-test suite to confirm the cross-task edit didn't break its already-closed work.
84/84 `shared-ui` tests passing (78 pre-existing + 6 new), `tsc`/`svelte-check` clean in both packages, zero
changes to `apps/streams`/resume/bitmap/merkle logic.
