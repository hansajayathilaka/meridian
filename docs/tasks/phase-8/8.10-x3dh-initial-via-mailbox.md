# 8.10 — X3DH-initial-message-via-mailbox coverage

**Phase:** 8 — Offline Ciphertext Mailbox · **Feature:** T07 · **Depends on:** 8.5, 8.7 · **Status:** done

## Goal
Prove the async first-contact case (system-design §4.2) actually works through the mailbox: Alice
initiates X3DH against Bob's bundle while Bob is offline; Bob's first message back to Alice, on
reconnect, must decrypt correctly via the mailbox path exactly as it would via a live route.

## Scope
- **In:** an integration test sending a `Prekey`-bearing envelope (the opening X3DH message) to an
  offline recipient, letting it queue (8.5), then delivering it on reconnect (8.7), and confirming
  the recipient's session establishes and decrypts correctly — exercising wire-protocol.md's
  transport-independence invariant ("the same Envelope bytes are valid whether carried over WSS
  routing, the mailbox, s2s federation, or a data channel") for the one case that's genuinely new
  here (mailbox).
- **Out:** no code changes expected — this task exists to *prove* the invariant holds for the
  mailbox transport, not to build new X3DH/session logic. If it finds a gap (e.g. `Prekey` handling
  assumes a live connection somewhere), fixing that gap is in scope for this task, since "found a
  defect while writing the intended test" is normal here (matches this project's own precedent,
  e.g. task 6.3's desync short-circuit fix found the same way).

## Deliverables
1. Integration test: offline first-contact → mailbox-queued `Prekey` envelope → reconnect delivery
   → successful X3DH completion + first message decrypt, from both directions (Bob's reply flowing
   back to Alice the same way if Alice also goes offline mid-handshake — the acceptance criterion's
   "out-of-order mailbox delivery decrypts (skipped-message keys, from T03)" case).
2. If a gap is found: the fix, plus a regression test proving the specific failure mode.

## Risks / notes
This is the task most likely to surface an implicit "recipient is live" assumption baked into
existing X3DH/session-establishment code (most of which was written and tested against T03/T04's
always-connected scenarios). Treat any such finding as a real defect, not scope creep.

## Tests
New test(s) under `apps/rendezvous/tests/` or `apps/core/tests/` (whichever crate the existing
X3DH/mailbox-adjacent integration tests already live in — follow that precedent).

## Reviews
- **security-reviewer** — confirms no session-establishment invariant weakens when the opening
  message's transport is the mailbox rather than a live route.
- **test-engineer** — non-vacuity of the out-of-order/skipped-message-key case.

## Status
**Done, no defect found — no code changes.** The task's Tests section suggested
`apps/rendezvous/tests/` or `apps/core/tests/`; neither crate actually has both a real
`SignalingClient`/`ChatState` (needs `meridian-core`, which `apps/rendezvous` deliberately never
depends on) and a spinnable real `meridian-rendezvous` server (`apps/core`'s dev-dependencies have
neither) at once, so no test here can drive both. Task 8.8 already established the crate that does
have both — `apps/tui/tests/inbound_delivery.rs` — including a `spawn_server_with_store` helper
added specifically for direct mailbox-row seeding. Both new tests landed there instead (mirroring
8.12's precedent for a Tests-section suggestion that didn't fit the real crate layout).

Two tests, covering Deliverable 1's two cases:
1. `x3dh_opening_message_delivered_via_mailbox_establishes_the_session_and_gates_as_a_request` — a
   real peer X3DH-initiates against "us"'s real published bundle, seals the opening
   `Prekey`-bearing envelope, and it's seeded directly into the mailbox (simulating "us" genuinely
   offline — never connected). "Us"'s real `run_inbound_loop` then connects for the first time;
   task 8.7's drain-on-`AuthOk` delivers it, and it correctly surfaces as `InboundEvent::MessageRequest`
   keyed by the real sender (not `MAILBOX_DRAIN_FROM_PLACEHOLDER`) — task 2.10's first-contact gate
   applies identically regardless of transport. After accepting, one more message from the peer
   over a **fresh live connection** decrypts normally, proving the mailbox-established session is
   byte-for-byte interoperable with the live path (the actual transport-independence claim).
2. `out_of_order_mailbox_drained_delivery_decrypts_via_skipped_message_keys` — a `ChatState`-level
   test proving the Double Ratchet's skipped-message-key mechanism (already shipped under T03)
   composes correctly with `open_inbound_from_mailbox`'s `mailbox_drained=true` authentication path:
   two envelopes are sealed on an established session, and the later one is opened first (forcing a
   skipped key to be retained for the earlier one's counter), then the earlier one is opened and
   must still decrypt using that retained key.

### Review round
**security-reviewer** — PASS, one should-fix (fixed in this same commit): test 2's doc comment
called both envelopes "steady-state, non-prekey," which is inaccurate — since "us" never replies
within the test, the peer's session never confirms, so both envelopes still carry the reused X3DH
prekey preamble. The reviewer traced `open_bytes` directly and confirmed the conclusion this
comment was defending (the fresh-provisional-session fallback is genuinely unreachable, since
`self.sessions.contains_key(&sender_pub)` is already true) still holds — only the stated premise
was wrong. Comment corrected to state the real reason precisely (same-header-key continuity across
both opens, since no DH ratchet turn occurs without a confirmed reply) rather than "no prekey."

**test-engineer** — PASS, zero findings, non-vacuity independently confirmed for both tests **by
actually breaking the mechanism and observing a real, correctly-located failure**, then restoring:
- Test 2: temporarily stopped `Ratchet::skip_message_keys` from retaining the derived key —
  reran, got a hard failure exactly at the second (`blob_a`) open with `Crypto(Crypto)`, confirming
  retention specifically (not just derivation) is what the test depends on; the first
  (`blob_b`) open still succeeded on its own, as expected. Restored, reran green. Also confirmed,
  by execution tracing (not just reading), that both prekey-bearing opens take the
  existing-session branch, never the fresh-provisional-session fallback — directly answering the
  task's own named non-vacuity concern.
- Test 1: temporarily made `drain_mailbox` (task 8.7, `apps/rendezvous/src/ws.rs`) a no-op —
  reran, the test correctly timed out and panicked at exactly the `recv_inbound(...).expect(...)`
  call site. Restored, reran green.
No should-fix or blocking findings from either reviewer beyond the one doc-comment fix above.

One transient timing failure was observed once during this task's own verification (a 10s
`recv_inbound` timeout under heavy, unrelated concurrent load — two review agents plus recent
back-to-back full-workspace builds were competing for CPU/disk at that moment); six consecutive
reruns afterward (isolated and as part of the full suite) were all clean, confirming this was
environmental contention, not a structural flake in the test.
