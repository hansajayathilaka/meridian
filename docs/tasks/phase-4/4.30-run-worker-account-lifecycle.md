# 4.30 — Real `run_worker`: account lifecycle

**Phase:** 4 — Verification & Trust + Terminal TUI Client · **Feature:** T17 — Terminal TUI Client (gap closure) · **Depends on:** 4.16, 4.17 · **Status:** done

## Goal
Execute `GenerateAccount`/`Register`/`PublishBundle`/`Unlock` for real, unblocking the exact hang task
4.28 reproduced empirically: `meridian tui` hanging forever on "Generating your identity…" because
`run_worker` never called into `meridian-core`. This is the highest-value single task in the gap-closure
set — it turns a completely stuck onboarding into a runnable session, even before live navigation
(4.36/4.37) exists.

## Scope
- **In:** replace `run_worker`'s unconditional stub with a real per-`Effect` dispatch (later tasks in
  this gap-closure set extend the same dispatch with more arms) and implement these four arms, mirroring
  `apps/cli/src/main.rs::cmd_new`/`cmd_register`'s exact call sequence (`generate_account`,
  `AccountDescriptor::save`, `SignalingClient::connect`, `publish_bundle`). Reuse **one** live
  `SignalingClient` across `Register` → `PublishBundle` within a single onboarding run — never
  reconnect between them — per `RegisterRequest`'s own doc comment, so an invite token is never
  double-redeemed.
- **Out:** `LoadSession`/`Screen::Main` wiring (4.29/4.36/4.37 own when a screen transition follows);
  the outbound/inbound chat effects; contacts/trust/settings effects (4.31/4.32/4.34).

## Deliverables
1. Real `run_worker` arms for `GenerateAccount`, `Register`, `PublishBundle`, `Unlock`.
2. A small `SignalingClient` reuse mechanism scoped to one onboarding run (not a persistent
   session-lifetime connection — that's 4.35's different, larger concern).
3. Tests dispatching each effect directly (no live screen stack required) against a local
   `meridian-rendezvous` test instance (mirroring existing `apps/cli` integration tests), asserting real
   `account.json`/keystore/registration/bundle-publish side effects.

## Risks / notes
- **Never let `StoreChoice::File`'s passphrase appear in a log or error, even inside the worker.** This
  crate's existing hand-rolled `Debug` redaction covers `Effect`'s own `Debug` impl — verify no
  `format!("{effect:?}")`-shaped logging path exists anywhere in the new `run_worker` code that could
  bypass it.
- No dependency on 4.29 or any other task in this gap-closure set — independently testable today by
  dispatching effects directly.
- Mechanical note: 4.30–4.34 all extend the same `run_worker` `match` statement. They are logically
  independent and can be authored/reviewed in any order, but must land as sequential commits (standard
  `/next-task` batch discipline — commit one before starting the next).

## Status
Done. `apps/tui/src/worker.rs` (new) replaces `run_worker`'s task-4.11 stub with a real per-`Effect`
dispatch, implementing `GenerateAccount`/`Register`/`PublishBundle`/`Unlock` for real — mirroring
`apps/cli/src/main.rs::cmd_new`/`cmd_register`'s exact call sequences. This is the specific fix for the
hang 4.28 reproduced empirically ("Generating your identity…" never resolving). Every other `Effect`
variant still falls through to the original placeholder-echo behavior, in scope for 4.31–4.34.

`OnboardingSession` is a single-slot cache, keyed by `account_pub`, threaded through `run_worker`'s whole
process lifetime: `handle_register` opens and caches one live `SignalingClient` (plus, after review, the
one unwrapped `SecretStore` needed for bulk bundle-signing); `handle_publish_bundle` reuses both without
reconnecting or re-unwrapping, never re-redeeming the invite token, and only removes the cache entry once
the publish actually succeeds. New test file `run_worker_account.rs` (8 tests) dispatches each effect
directly against a temp `$MERIDIAN_HOME` and a real in-process `meridian-rendezvous` server, including a
`CountingStore` proving Register→PublishBundle reuses exactly one connection, and a
passphrase-redaction sweep over `Effect::Debug`.

**Review (combined `reviewer`, as named):** three real findings, all fixed and re-confirmed clean:
- **Correctness (blocking):** the connection cache was consumed *before* the fallible `publish_bundle`
  call ran, so every `PublishBundle` failure masked the real error behind "no active registration
  session," and the screen's own "Enter retry" UI could never actually succeed on any attempt. Fixed by
  deferring cache removal to the success path only — a retry now reuses the same still-open connection.
- **Test coverage (blocking):** the exact "Register succeeds, then PublishBundle itself fails" scenario
  the bug lived in was untested. Fixed with a new test using a `CountingStore` variant that fails exactly
  one publish call, proving both that the real error surfaces (not the masking message) and that a
  successful retry reuses the connection (`register_calls` stays at 1). The reviewer independently
  mutation-tested this by reverting the fix and confirming the new test fails — a genuine regression
  guard, not a vacuous assertion.
- **Correctness (minor):** the File-store path was unwrapping its scrypt-protected key twice per
  onboarding run (once at register, once at publish) instead of once, deviating from the CLI's own
  single-unwrap pattern this module's doc comments claimed to mirror exactly. Fixed by caching the
  unwrapped store alongside the connection, reused by both call sites.

`cargo test -p meridian-tui --test run_worker_account` (8/8), `cargo test -p meridian-tui` (full suite),
`cargo test -p meridian-cli --bins` (21/21), `cargo fmt --all -- --check`, `cargo clippy --workspace
--all-targets -- -D warnings`, and `bash tools/lint-tui-no-cli.sh` all clean. New dependencies: `keyring`
(production, mirrors the CLI's own OS-keystore init) and dev-only `meridian-rendezvous`/`meridian-proto`/
`async-trait`/tokio's `net` feature — confirmed correctly scoped by the reviewer.
