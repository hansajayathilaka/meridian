## Part 1 — real `meridian send`, real rendezvous, real WebRTC, multi-chunk, byte-identical (re-run)

Same scenario as [10.17's Part 1](./10.17-demo-transcript.md#part-1--real-meridian-send-real-rendezvous-real-webrtc-multi-chunk-byte-identical):
a real, fresh two-identity, two-process run (real `meridian id new`, a real in-process
`meridian-rendezvous::serve`, real `WebRtcTransport` host-candidate direct path) sending a genuine
208953-byte `/dev/urandom` file (4 chunks: 3 full 64 KiB + 1 short). Driver: a throwaway,
uncommitted `#[test]` under `apps/cli/tests/` (10.17's own precedent — nothing from the driver is
checked in; deleted after this run). Unlike 10.17's driver, both sides are spawned symmetrically
(neither is assumed in advance to be the initiator/sender): `send.rs`'s own role tie-break compares
raw account public-key bytes, which does not necessarily agree with a lexicographic comparison of
the *encoded* `mrd1:...` id strings — the actual role is observed from each side's own stdout, not
predicted. (A first version of this driver *did* predict the role from the encoded id strings and
was genuinely flaky — ~50% failure, "unexpected signaling payload during answer" on both sides,
because both processes independently and correctly computed themselves as the raw-byte initiator
against the *wrong* predicted role. This was a bug in the throwaway test harness, not in
`send.rs`/`meridian-core` — recorded here for anyone re-deriving this driver later, not filed as a
tracker finding since nothing shipped is affected.)
