# 10.16 — Corrupted-chunk adversarial test

**Phase:** 10 — File Transfer Stream · **Feature:** T09 · **Depends on:** 10.8 · **Status:** done

**User surface:** none — test-only, no production code changed.

## Goal
Prove, at the acceptance-criterion level (not just task 10.8's own unit tests), that an injected
corrupted chunk is detected by AEAD/merkle, triggers a re-request, and is never written to the
destination file — across the full sender→wire→receiver path, not just the receiver engine in
isolation.

## Scope
- **In:** an adversarial test that injects a bit-flip into a chunk somewhere between sender and receiver
  (at the loopback-transport or netns layer, not by calling the receiver's internal API directly — the
  point is to prove the whole pipeline's behavior, complementing task 10.8's narrower unit tests), and
  asserts: the corrupted chunk is rejected, a re-request occurs (via task 10.9's resume mechanism or a
  narrower in-stream re-request if the implementation adds one), the corrupted bytes are never present
  in the destination file at any point (not just "eventually corrected"), and the transfer ultimately
  completes with a verified match once the good chunk arrives.
- **Out:** the detection logic itself (10.5/10.8 already built and unit-tested it) — this task is the
  end-to-end adversarial proof.

## Deliverables
1. Adversarial corrupted-chunk test, likely in `apps/streams/tests/` as an integration test distinct
   from 10.8's unit tests.

## Risks / notes
This overlaps in spirit with task 10.8's own tests but is deliberately kept separate and later in the
sequence: 10.8's tests are unit-level (does the receiver engine reject one bad chunk in isolation?),
this task is the acceptance-criterion-level adversarial proof the feature spec explicitly names.

## Tests
`cargo nextest run -p meridian-streams` (integration test target).

## Reviews
**security-reviewer** + **test-engineer**.

## Outcome
Added `apps/streams/tests/corrupted_chunk_adversarial.rs`, extending the established two-party test
harness (real X3DH, real `P2pSession` over `LoopbackTransport`, real `FileStream`) to prove the full
sender→wire→receiver pipeline — not task 10.8's own narrower unit tests, which call the receiver
engine's API directly with pre-corrupted bytes — rejects a corrupted chunk, never writes it, and
recovers via task 10.9's resume mechanism. A test-only helper reproduces `send_chunk_frame`'s real
construction byte-for-byte (real `seal_chunk` AEAD, real `ChunkFrame::encode`, real `tag_frame` wire
framing) and flips one ciphertext byte only after all real sealing/framing, so the corrupted frame still
crosses a real ratchet-seal, a real transport hop, a real ratchet-open, and real `FileStream::on_frame`
buffering — only the final chunk-level AEAD-open is wrong. "Never written" is checked against live
`FileReceiver` state at two points (immediately after rejection, and again after a later unrelated good
chunk arrives, proving persistence rather than an instant-after check), and the resume path drives the
real `watch_resume`/`send_resume_bitmap`/`send_missing_chunks` primitives end-to-end before a final
byte-identical `reassemble()` check.

Both required review lenses (security-reviewer, test-engineer, run as one combined `reviewer` pass)
returned **PASS** with zero blocking or should-fix findings, independently verifying rather than
trusting the implementation's own report: confirmed the injection helper genuinely reproduces
`send_chunk_frame` byte-for-byte before the deliberate corruption (not a shortcut that makes the test
easier to pass than the real pipeline allows); confirmed the corrupted byte lands inside the AEAD
output (the crate's own established corruption model, matching `chunk.rs`'s and `receiver.rs`'s
existing tests, not a novel pattern invented for this test); confirmed the failure is genuinely
`ReceiveError::Crypto` (chunk-level AEAD), not an earlier decode error or a later merkle mismatch that
would prove something weaker; confirmed both "never written" checkpoints hit real `FileReceiver`
accessors; confirmed the resume path calls the actual production functions, not test doubles; and
confirmed no logging of `k_f` or plaintext anywhere. All 67 `meridian-streams` tests (everything from
10.1–10.16) green; clippy/fmt clean; full workspace build clean. No production code in `apps/streams/src/`
was touched.
