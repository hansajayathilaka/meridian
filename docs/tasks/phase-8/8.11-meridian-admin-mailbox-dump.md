# 8.11 — `meridian-admin mailbox dump <pubkey>`

**Phase:** 8 — Offline Ciphertext Mailbox · **Feature:** T07 · **Depends on:** 8.1, 8.2 · **Status:** done

## Goal
Build the feature spec's "honesty demo" tool: make concrete, to an operator, exactly what threat
A7 can see about a mailbox — sizes, timestamps, opaque blobs, nothing else — rather than leaving
that claim as prose.

## Scope
- **In:** a new binary crate `apps/admin` (`meridian-admin`, added to the workspace `members` list)
  with a `mailbox dump <pubkey>` subcommand that opens the server's configured store (same
  `Store` trait/config as `meridian-rendezvous`, read-only access — no new store methods beyond
  8.1/8.2's `mailbox_list_for_recipient`) and prints, per row: size in bytes, `arrived_at`,
  `expires_at`, and the blob rendered as an opaque marker (e.g. `<opaque, N bytes>`) — never
  attempting to parse or display its contents.
- **Out:** no other `meridian-admin` subcommands beyond `mailbox dump` — do not scope-creep into a
  general admin CLI here; if other operator tooling is wanted later, that's a future task's job.
  No web/dashboard surface (T14's territory, deliberately deferred). **No TUI surface** —
  Definition of Done gate 9 exemption, recorded explicitly per its own requirement: this is
  operator/infra tooling run against a server's on-disk store, not a client-side, end-user-facing
  feature the terminal client could meaningfully expose (`meridian-tui` has no concept of "another
  org's rendezvous database" to inspect).

## Deliverables
1. `apps/admin` crate + `mailbox dump <pubkey>` subcommand.
2. A test (or the phase's demo script itself, if this project's convention is demo-as-test for CLI
   tools — check `apps/cli`'s own precedent) proving the tool never deserializes/decodes `blob`
   (reuse `tools/lint-no-serde-on-blob.sh`'s enforcement pattern, or an equivalent static check, for
   this new crate too).
3. Sample output matching the feature spec's demo script shape (`3 envelopes | 1.2 KiB, 0.9 KiB,
   4.1 KiB | ts … | contents: <opaque>`).

## Risks / notes
This tool exists specifically to make an honest claim concrete — resist any temptation to add a
"preview first N bytes" or similar convenience flag; the feature spec's own Risks/notes line says
"do not let convenience features creep in... the mailbox's entire security argument is its poverty
of function," and that applies as much to its inspection tooling as to the mailbox itself.

## Status
**Done.** New binary crate `apps/admin` (`meridian-admin`), one subcommand:
`meridian-admin --config <path> mailbox dump <hex-pubkey>`. Opens the same on-disk store a real
`meridian-rendezvous` deployment uses (`Config::load` + `default_store`, matching the server
binary's own `--config` flag exactly) and prints, per row: id, human-readable size, `arrived_at`,
`expires_at`, and `<opaque, N bytes>` — never reading `blob` beyond the server-computed
`size_bytes`. Read-only: the only `Store` call is 8.1's `mailbox_list_for_recipient`, no new store
methods. Exactly one subcommand, no preview/search/convenience flags, per the feature spec's
"poverty of function" constraint. `tools/lint-no-serde-on-blob.sh` now scans `apps/admin` too.

### Review round
**reviewer** (security-reviewer + code-reviewer lenses) — **PASS**, zero blocking findings.
Independently confirmed the output is bounded to exactly what `data-model.md` documents threat A7
as learning, that `blob` is never touched beyond `size_bytes`, and that no cross-recipient
leakage is possible. One non-blocking should-fix, **fixed in this same commit**: the task file
didn't record an explicit Definition of Done gate 9 (TUI surface) exemption — added above.

**devops** — CLI ergonomics **PASS** (help text, error messages, exit codes, `--config` parity
with the server binary all verified by running the binary directly), with one **should-fix, fixed
in this same commit**: `default_store`'s SQLite backend opens with `create_if_missing(true)` —
correct for the server's own bootstrapping, but wrong for a read-only honesty tool. A typo'd
`--config` path or a `database_url` resolved from the wrong working directory would otherwise
silently create a fresh, empty database and report "0 envelopes" indistinguishable from a
genuinely empty mailbox — exactly the failure an operator in an incident/audit is least equipped
to catch by other means. Fixed with a new `require_existing_database` check in `main.rs`,
run before opening the store: refuses to proceed (exit 1, clear message, no file created) unless
the configured SQLite file already exists; an in-memory URL is exempted (inherently ephemeral).
Manually verified end-to-end: a missing-file config now fails closed with no stray file created,
where it previously silently reported an empty mailbox.
