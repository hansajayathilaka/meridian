# 4.8 — Org directory-attestation ingest

**Phase:** 4 — Verification & Trust + Terminal TUI Client · **Feature:** T08 — Verification & Contact Trust · **Depends on:** 4.3, 4.6 · **Status:** pending

## Goal
Let a client ingest a signed, org-issued HR-name→key mapping as **petname provenance, not key
authority** — a display-name hint the user can accept or ignore, never a substitute for verification
([system-design §3.5](../../architecture/system-design.md)).

## Scope
- **In:** client-side ingest of a signed directory-attestation artifact; verify the org's signature;
  store as a **petname suggestion with recorded provenance** (which org attested it, when), distinct
  from the user-assigned `petname` field (4.6) — never auto-applied as the display name, never treated
  as proof of identity. `TODO: confirm` the exact signed-artifact wire/file schema: it is **not**
  specified anywhere in `docs/` today, and this task defines it rather than guessing — architect sign-off
  on the schema is required before implementation, not after.
- **Out:** any server-side directory-issuance machinery (out of scope per the feature spec: "web-of-trust
  anything" is explicitly Out); auto-applying an attested name as `petname`.

## Deliverables
1. Schema proposal (reviewed by architect) for the signed directory-attestation artifact.
2. `apps/core/src/trust.rs` (or a sibling module): ingest + org-signature verification + provenance-
   tagged suggestion storage.
3. Tests: valid attestation → suggestion offered, never auto-applied; invalid/unsigned → rejected;
   suggestion is visually/structurally distinct from a verified petname.

## Risks / notes
- The provenance-not-authority boundary is the entire point — a bug here would let an org's directory
  silently override a user's own petname/trust decisions, which is exactly the "key authority via
  displayname" confusion §3.5 exists to prevent.
- Do not invent a wire contract without architect sign-off — this is new ground, and a rushed schema
  here becomes someone else's wire-compat problem later.

## Tests

## Reviews
- **architect** — required; new data shape/schema with no prior spec.
- **security-reviewer** — required; the provenance-vs-authority boundary is a trust-model invariant.
