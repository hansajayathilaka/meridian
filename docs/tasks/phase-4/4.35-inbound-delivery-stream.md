# 4.35 — Inbound delivery stream

**Phase:** 4 — Verification & Trust + Terminal TUI Client · **Feature:** T17 — Terminal TUI Client (gap closure) · **Depends on:** 4.29 · **Status:** done

## Goal
Give the TUI a live receive path. This is a **third gap**, found during planning this task set, not
named in either of the two originally known gaps (worker stub, missing navigation): there is no
mechanism anywhere in this crate's `AppEvent`/`Effect`/`WorkerEvent` model for the network to *push*
something into a running session — every existing `Effect` is a request the UI dispatches and a worker
completes once. `apps/tui/src/screens/chat.rs`'s own module doc already says so plainly: "No
receive-path wiring either: there is no `Effect`/`WorkerEvent` for an inbound message arriving live in
this task." But the T17 demo script's own middle step — "peer runs `meridian tui` too and sees a message
request… accept → both sides chat" — is structurally impossible without this.

## Scope
- **In:** a new push-shaped event (e.g. `AppEvent::Inbound(...)`), deliberately **not** squeezed into the
  existing `Effect`/`WorkerEvent::Completed(Effect)` shape, since it answers no dispatched effect — routed
  by `App::update` to whichever screen it's relevant to (an open `Screen::Chat` for that peer →
  `insert_deduped` + dispatch `Effect::PersistHistory`; otherwise the request queue / a pending-count
  refresh). `run_worker` (extending 4.29's `LoadSession` execution) opens **one** persistent
  `SignalingClient` for the life of the session and forwards `client.next_deliver()` onto the existing
  worker→`App` channel. Auto-sends delivery receipts on receipt of `ChatContent::Text`, mirroring
  `apps/cli/src/chat.rs::deliver_content`'s auto-ack — never gated by `SendGate`, since a receipt only
  acknowledges content already seen, it does not send new content.
- **Out:** any UI for "new message arrived while I'm elsewhere" beyond the minimum needed for the demo (a
  fuller notification affordance is a candidate for a later, separate task — state this narrowing
  explicitly, don't silently under-scope it).

## Deliverables
1. `AppEvent::Inbound` (or equivalent) variant.
2. The persistent receive-loop spawned from `run_worker`, held open for the session's lifetime.
3. `Screen::Chat`/`Screen::Requests` handling for the new event.
4. Tests covering: an inbound `MessageRequest` while `Screen::Requests` isn't open surfaces on next
   `Ctrl-R`; an inbound chat message while `Screen::Chat` for that peer is open appends live and dedups
   correctly against a racing outbound `PersistHistory`; a malformed/adversarial inbound envelope is
   dropped, never crashes the loop or the UI (mirrors `apps/cli/src/chat.rs::handle_inbound`'s
   reject-loudly-never-trust behavior).

## Risks / notes
- **This is the architecturally novel task in the whole gap-closure set.** Flag for explicit architect
  sign-off on the persistent-connection lifecycle (opened once at session-load time, held inside the
  worker task, never re-derived per effect — distinct from 4.33's deliberately per-call connections)
  before implementation lands, even though no new ADR is warranted: this operationalizes
  `tui-client.md` §4's already-stated backpressure/coalescing property, not a new architectural stance.
- **Security-sensitive**: decrypting arbitrary attacker-controlled envelopes live, `MessageRequest`
  gating, and must never bypass `SendGate` for the auto-ack path (an ack is not new user-composed
  content, so it is exempt from the gate by design — confirm this exemption is scoped exactly to acks
  and nothing else).
- Depends only on 4.29 (needs `LiveSession`'s account/store context to know who to listen as). Logically
  related to but not blocked by 4.33 (shares the seal/route pattern conceptually, not code).

## Status
Done. Gives `meridian-tui` a live inbound-message receive path, per the architect-approved design (no
new ADR needed — this operationalizes tui-client.md §4's already-stated backpressure/coalescing
property).

**`AppEvent::Inbound(Box<InboundEvent>)`** (`apps/tui/src/app.rs`) — a new, push-shaped event kept
separate from `WorkerEvent::Completed(Effect)` since it answers no dispatched effect, exactly as
scoped. `InboundEvent` has three variants — `MessageRequest`, `Message { peer_pubkey, entry }`,
`Receipt { peer_pubkey, ack }` — all already-decrypted content; `App::update`/`App::handle_inbound`
never touch ciphertext or a `SecretStore`, preserving this crate's I/O-free `update` invariant.
Routing (`App::handle_inbound`): an open `Screen::Chat` for the matching peer gets `insert_deduped` +
`Effect::PersistHistory` via a new `crate::screens::chat::handle_inbound_message` (reuses
`insert_deduped` unchanged, exactly as that function's own doc comment always anticipated); otherwise
`Effect::PersistHistory` still fires unconditionally (restart-persistence must not depend on which
screen happens to be open) but nothing is appended live. An open `Screen::Requests` gets a
`MessageRequest` appended directly (deduped by `sender_ik`); otherwise it joins a new
`App::pending_inbound_requests` buffer, drained into the next `Screen::Requests` that opens
(`Ctrl+R` or Contacts' own `r`) — this task's own named "surfaces on next Ctrl-R" deliverable. A
`Receipt` updates a matching open `Screen::Chat`'s `Sent` row to `Delivered` in memory only (no
disk-persistence effect exists for an in-place update — an explicit, documented narrowing, mirroring
`retry_last_failed`'s own prior "no history-mutation effect in this task's scope" judgment call).

**`worker::run_inbound_loop`** (`apps/tui/src/worker.rs`) — the persistent receive loop, spawned
exactly once per session by `crate::run_worker` (`apps/tui/src/lib.rs`) immediately after a
*successful* `Effect::LoadSession`/`Effect::Unlock`, via a new `worker::inbound_handoff` that peeks
(never consumes) the resulting `WorkerEvent` and independently re-derives the
`SecretStore`/`KeyHandle`/`account_pub`/`server` needed — never touching the `LiveSession` the event
itself carries (that reclaim is still 4.36/4.37's job, unchanged). Holds one
`meridian_core::signaling::SignalingClient` open for the life of the session, forwarding
`next_deliver()` results as `AppEvent::Inbound`. **Architect's condition, implemented, not skipped:**
reconnects with backoff from `config.toml`'s `[network] reconnect_backoff_ms`, surfacing
`AppEvent::ConnectionStatus` transitions; `crate::statusbar::ConnectionState` gained a
`Reconnecting { attempt, max }` variant rendering tui-client.md §7's literal `● reconnecting (n/m)`
wording (tested). The loop never gives up — past the configured backoff steps it keeps retrying at
the last configured interval.

**Auto-ack (task's own named deliverable):** `worker::process_inbound_delivery` auto-sends a
`ChatContent::Receipt` for every decrypted `ChatContent::Text`, mirroring
`apps/cli/src/chat.rs::deliver_content` exactly. **Never gated by `SendGate`** — structurally, not by
omitted call: this function has no `TrustStore` handle in scope to have gated with (it only reads
`trust.bin` read-only, to resolve a federation routing hint for the ack). Deliverable (d)'s test
(`auto_ack_still_replies_even_though_trust_bin_marks_the_sender_blocked`) is the falsifiable proof,
mirroring task 4.33's own `send_succeeds_even_though_trust_bin_marks_the_peer_blocked` pattern one
direction earlier.

**Adversarial input:** every non-success `meridian_core::chat::ChatError` (`BadSignature`,
`SenderMismatch`, `UnknownPrekey`, `NoSession`, `Desync`, `RequestPending`, codec/crypto/store errors)
is dropped and logged (`eprintln!`, no content/keys), never forwarded, never a panic — mirrors
`apps/cli/src/chat.rs::handle_inbound`'s reject-loudly-never-trust catch-all exactly. Covered by
deliverable (c)'s test, which also proves the loop keeps correctly processing later legitimate input
after the garbage.

**Concurrency fix found and closed during this task (not pre-existing scope, but a real, load-bearing
correctness gap task 4.33's own file explicitly flagged as deferred here):** `sessions.bin` is one
serialized document covering every peer's session; without coordination, this loop's own
load-mutate-save and the ordinary effect-dispatch loop's (`run_send_message`/`run_accept_request`/
`run_reject_request`) could race and silently clobber each other's write. Added a module-level
`chat_state_lock()` (`tokio::sync::Mutex` behind a `OnceLock`, never a blocking `std::sync::Mutex` —
`run_send_message` holds it across real network `.await` points) and threaded it through all four
call sites — a deliberately minimal-diff choice (a lock behind a function, not a new parameter
threaded through every existing signature or through `dispatch` itself, which ~30 existing test call
sites construct directly).

**Bug found and fixed while building the integration tests, not merely test-scoped:** a contact
accepted via `Effect::AcceptRequest` is TOFU-pinned with an **empty** hint (`run_accept_request`'s own
documented "`MessageRequest` carries no advisory hint" contract). The auto-ack's routing hint lookup
was passing that empty string through as `Some(String::new())`, which `meridian-rendezvous`'s own
`handle_route` treats as *any* non-matching hint — i.e. a foreign-domain federation attempt — instead
of a local delivery, so every auto-ack to a message-request-originated contact would have silently
misrouted in a real deployment. Fixed by filtering an empty (but present) hint to `None` before
calling `route_with_hint`.

**Tests:** `apps/tui/tests/inbound_delivery.rs` (new file, 5/5 passing) — a real, in-process
`meridian-rendezvous` server, a real OS-keystore-backed "us" account, and a real peer identity driven
directly through `meridian_core::chat::ChatState`/`SignalingClient`, mirroring `apps/cli`'s own chat

  `a_racing_outbound_persist_history_dedups_against_a_same_mid_inbound_message` — deliverable (b).
- `malformed_inbound_envelope_is_dropped_and_the_loop_keeps_running` — deliverable (c).
- `auto_ack_still_replies_even_though_trust_bin_marks_the_sender_blocked` — deliverable (d).

Full crate suite green: `cargo test -p meridian-tui --all-targets` (all pre-existing suites unchanged,

**Narrowing/deviation notes (stated explicitly, per this task's own norm):**
- **This mechanism is fully built and directly tested (at the `run_worker`/`worker::dispatch` boundary,
  same pattern as every 4.30–4.34 "real execution" task before it), but is not yet reachable end to end
  from a live `meridian tui` process.** `Effect::LoadSession`/`Effect::Unlock` — the only two events
  `worker::inbound_handoff` triggers on — are never actually dispatched in a live run today: `App::new`
  still unconditionally starts on `Screen::Onboarding` (no `Preflight` step exists yet), and
  `Screen::Unlock` is not constructed by any live navigation path either (tui-client.md §10). This is
  the identical, already-documented gap every screen before its own navigation task carried; 4.36
  (`Screen::Main` + live navigation) and 4.37 (Preflight routing) are what will actually reach this
  code from a real session — 4.35 was scoped to depend only on 4.29, not on either of those.
- `worker::run_inbound_loop` does not publish or republish a prekey bundle itself — it only connects
  and listens. A session's receivability depends on whatever bundle onboarding (or a later republish
  mechanism, out of scope here) already put on the server. Not a regression: `run_inbound_loop` was
  never scoped to own bundle publishing.
- Automatic desync recovery (task 4.9's receiver-side re-handshake, `meridian_core::desync::
  attempt_recovery`) is **not** wired into this loop — explicitly named out of scope in the task file's
  own risk notes ("Logically related to but not blocked by 4.33... not this module's concern yet," true
  for 4.9's own recovery mechanism too). A repeated desync from the same peer is simply dropped here,
  same as any other rejection.
- Reconnect status is live App state (`AppEvent::ConnectionStatus` → `App::connection_status()`) and a
  tested rendering primitive (`statusbar::ConnectionState::Reconnecting`), but — same "no Screen::Main
  yet" gap as everything else in this crate pre-4.36 — is not yet plumbed into any screen that renders
  persistently across the whole session. `crate::screens::diagnostics::DiagnosticsPane` is the one
  screen that already renders a `StatusBarInfo`, but wiring it to this task's live connection state
  (rather than its own `StatusBarInfo::default()`) is left to whichever future task threads real session
  state into that pane — not invented here.
- `worker::inbound_handoff` returns `None` (loop never starts, no error surfaced anywhere) if
  `resolve_server` can't resolve a rendezvous server yet (an account loaded/unlocked but never
  registered through a worker that persisted `account.json`'s `server` field). `TODO: confirm`: no
  design doc read for this task specifies whether that should instead be a visible, named failure —
  flagged in `inbound_handoff`'s own doc comment, not resolved here.
- `chat_state_lock()` is coarse-grained: `run_send_message` holds it for its whole body, including
  network calls, not just the disk critical section — a deliberate, documented v1 trade-off (see that
  function's own doc comment) rather than restructuring its already-reviewed control flow.
