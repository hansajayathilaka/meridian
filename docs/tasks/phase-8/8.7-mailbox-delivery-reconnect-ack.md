# 8.7 — Delivery-on-reconnect push + `MailboxAck` handling (server)

**Phase:** 8 — Offline Ciphertext Mailbox · **Feature:** T07 · **Depends on:** 8.1, 8.2, 8.3, 8.5 · **Status:** done

## Goal
Deliver a recipient's queued mail the moment they reconnect, and delete it once acknowledged —
closing the loop 8.5/8.6 opened.

## Scope
- **In:** in `apps/rendezvous/src/ws.rs`'s connection handler, immediately after `AuthOk` is sent
  (before entering the normal frame read loop), drain the authenticated account's mailbox rows via
  8.1's `mailbox_list_for_recipient`, pushing each as `Deliver{from, blob, mailbox_id: Some(id)}` in
  `arrived_at`/`id` order. Add an `Op::MailboxAck` handler: on `MailboxAck{ids}`, call
  `mailbox_delete_by_ids` scoped to the connection's own `account_pub` (never trust `ids` alone —
  the store method's recipient-scoping from 8.1 is what makes this safe), reply `MailboxAckOk{}`.
- **Decided by [ADR 0024](../../adr/0024-mailbox-drain-from-attestation.md) (architect consult,
  forced by this task's own implementation):** `from` on a mailbox-drained `Deliver` is a fixed
  `[0u8; 32]` placeholder, never a real sender identity — `MailboxEntry` (8.1/8.2) gains **no** new
  column. Persisting the sender server-side (the obvious-looking alternative) would be a durable,
  queryable contact graph, contradicting data-model.md's mailbox-schema note and
  anonymity-and-retention.md's must-never #2 outright. The corresponding client-side
  `SenderMismatch` fix this placeholder requires is out of this task's scope (server-side only) —
  it now belongs to [8.8](./8.8-client-mailbox-ack-dedup.md), which the ADR's Consequences section
  folds it into.
- **Out:** client-side sending of `MailboxAck` (8.8 — client code lives in a different crate);
  purge-job scheduling (8.9, separate concern from delivery); no change to the live-route
  (`Deliver` without `mailbox_id`) path at all.

## Deliverables
1. Post-`AuthOk` mailbox drain in the connection handler.
2. `Op::MailboxAck` server handler + `MailboxAckOk` reply.
3. Tests: a client with N queued rows receives exactly N `Deliver` frames with `mailbox_id` set, in
   arrival order, before any other traffic; sending `MailboxAck{ids}` deletes exactly those rows and
   no others (including: acking an id belonging to a *different* account's row is a no-op, proving
   the recipient-scoping holds end-to-end, not just at the store layer); a client that never acks
   keeps the rows (deletion is ack-driven, not push-driven) — confirmed via a reconnect that redrains
   the same still-unacked rows.

## Risks / notes
The "never trust `ids` alone" invariant is the single most security-relevant line in this task —
name it explicitly in the PR description and make sure the test in Deliverable 3 (cross-account ack
is a no-op) actually exercises the attack shape (a connected account acking ids it was never sent),
not just a same-account partial ack.

**Carried forward from task 8.2's review:** `mailbox_delete_by_ids` binds one SQL parameter per id
via `QueryBuilder` with no cap, so a very large `MailboxAck.ids` list could eventually hit SQLite's
bound-parameter limit (`SQLITE_MAX_VARIABLE_NUMBER`) and surface as an opaque `StoreError::Backend`.
Cap or chunk the id list here before calling the store method (a `MailboxAck` frame is
attacker/client-controlled input) rather than passing it through unbounded.

## Status
**Done.** `handle_socket` now drains the authenticated account's queued mailbox rows (via 8.1's
`mailbox_list_for_recipient`) immediately after `AuthOk`, strictly before `state.registry.add`
registers the connection as reachable — so a live route arriving concurrently on another
connection can never interleave with the drain. Each row pushes as
`Deliver{from: MAILBOX_DRAIN_FROM_PLACEHOLDER, blob, mailbox_id: Some(id)}`, in `arrived_at`/`id`
order. A new `Op::MailboxAck` handler deletes exactly the acked rows via 8.1's
`mailbox_delete_by_ids`, scoped to the connection's own `account_pub` — never trusting `ids`
alone — and always replies `MailboxAckOk{}`.

**A real design gap surfaced mid-implementation and was resolved via an architect consult, not
guessed at:** pushing `Deliver{from, ...}` needs a sender identity, but the original sender's
connection may be long gone by drain time. The obvious fix (persist a `from_pub` column on the
mailbox row) was tried, then reverted on discovering it directly contradicts
`data-model.md`'s "no sender columns on mailbox rows" note and
`anonymity-and-retention.md`'s must-never #2 ("never store a server-side contact graph") — a
persisted sender on a row that can live 14 days is exactly that graph, and
`meridian-admin mailbox dump` (8.11) would make it queryable. **[ADR 0024](../../adr/0024-mailbox-drain-from-attestation.md)**
settles this: never persist sender identity server-side; `Deliver.from` on a mailbox-drained push
is a fixed `[0u8;32]` sentinel (`MAILBOX_DRAIN_FROM_PLACEHOLDER`, `apps/proto/src/msg.rs`), never
a real assertion. `MailboxEntry` gained **no** new column — `mailbox_enqueue`'s signature is
unchanged from 8.1/8.2. The client-side consequence (the `SenderMismatch` check in
`apps/core/src/chat.rs` would otherwise reject every mailbox-drained message) is out of this
task's server-side scope; the ADR folds it into task 8.8's Scope instead, with 8.8's own file
amended accordingly. Until 8.8 ships, mailbox-drained messages are undecryptable client-side — a
functionality gap, not a security one (fails closed).

`MailboxAck`/`MailboxAckOk` (task 8.3) were never added to `tools/lint-no-serde-on-blob.sh`'s
control-plane allowlist, since nothing decoded them until this task — fixed alongside, confirmed
via the lint's own `--selftest` (still catches real violations, no false positives).
