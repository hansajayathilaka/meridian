# 7.6 — Resolve the `eid` / mailbox naming collision before T07 planning

**Phase:** 7 — Review of Phase 6 · **Feature:** review fix (N1) · **Depends on:** — · **Status:** done

## Goal
Actually resolve — not just re-flag — the naming collision between task 6.4's
`MessageEnvelope::eid` (client-side dedup key, unauthenticated outer plaintext) and T07's planned
`mailbox` table's `eid BLOB` primary key (`docs/architecture/data-model.md`), before a future
`/plan-phase` for T07 can silently pick a colliding or ambiguous name.

## Scope
- **In:**
  - `docs/architecture/data-model.md` (mailbox table definition) — either (a) confirm the mailbox PK is
    deliberately independent of the envelope's `eid` and rename it to avoid the collision (e.g.
    `mailbox_id`/`dedup_key`), or (b) if it's meant to be *derived from* the envelope's `eid`, work out
    and record how that squares with the server's "never decode an opaque envelope" invariant
    (`apps/proto`'s opaque-blob contract, `apps/rendezvous`'s "no structured (de)serialization of opaque
    payloads" rule) — this is the real design question the existing carry-forward bullet poses but
    doesn't answer.
  - `docs/tasks/README.md`'s Live carry-forwards — replace the still-open bullet with the resolved
    decision (or a pointer to a new ADR addendum, if the resolution is substantive enough to bind future
    implementers — architect's call).
- **Out:** No code changes (T07 doesn't exist in code yet). No re-litigation of ADR 0016 itself.

## Deliverables
1. The resolved `data-model.md` note.
2. The updated `docs/tasks/README.md` carry-forward bullet (or a new ADR addendum).

## Status
**Done.** Decision: the mailbox's primary key is **not** `MessageEnvelope::eid` and must not be
derived from it — renamed to `id INTEGER PK`, server-assigned sequential, matching the existing
`one_time_prekeys.id` shape elsewhere in `docs/architecture/data-model.md`. The envelope's `eid`
(task 6.4, client-side replay-dedup) stays inside the opaque `blob` column, which the server never
decodes — deriving the mailbox PK from it would require violating that invariant, which is real and
structurally enforced (`apps/rendezvous` doesn't even depend on the `meridian-envelope` crate that
defines the type, plus `tools/lint-no-serde-on-blob.sh` as defense-in-depth), not just documented.
Dedup on redelivery stays a client-side concern per T07's own feature spec deliverable 2 and task
2.8's pre-existing "no s2s dedup" — the server never needs to read `eid` at all.

Updated `docs/architecture/data-model.md`'s mailbox table definition with the renamed PK and a
decision comment cross-referencing task 6.4, plus `docs/tasks/README.md`'s carry-forward bullet from
"open question" to resolved.

**No new ADR** — this applies ADR 0007 (mailbox scope, the governing ADR for `mailbox`'s "ADR-7"
comment tag) and the pre-existing opaque-blob invariant consistently, resolving an accidental naming
collision inside a not-yet-implemented table. T07 has no code yet, so nothing shipped changes.
