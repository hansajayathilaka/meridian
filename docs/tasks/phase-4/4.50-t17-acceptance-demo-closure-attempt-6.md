### Run 2 (test-engineer, genuinely independent, FAIL)
Built its own PTY driver from scratch (not reused from any prior transcript), independently
re-derived the environment setup (found and root-caused its own new wrinkle: a scratchpad `$HOME`
path over 108 bytes silently truncates/collides the keyring's AF_UNIX control-socket bind — fixed

independently-reproduced defect via its own adversarial probing across ~15 fresh two-peer trials:

**First-contact message delivery is non-deterministically silent or very slow (70s–260s, once a
clean fully-waited 260s timeout with zero interference) when the X3DH initiator is
OS-keystore-backed and the responder is file-backed**, even though the sender receives a genuine
server-acknowledged `RouteOk{delivered: true}` from the rendezvous server within ~1–11s. The
reverse direction (file-backed sender → OS-keystore responder) was reliable across 9/9 trials
(~0.2–12s). Disambiguated from a simple "connects later" theory by reversing onboarding order —
the file-backed peer still failed to receive despite connecting first, pinning the correlation to
**file-backed store as the responder**, not connection order. Root cause not conclusively pinned
by Run 2 alone; leading hypothesis was the single-threaded `tokio::runtime::Builder::new_current_thread()`
(`apps/cli/src/main.rs`) being starved by the file-backed store's synchronous scrypt work, though a
passive zero-interference wait also once took ~90s and a gentle 8s-interval poll also failed at
150s in 2 of 3 trials.

### Reviewer (combined) — consistency pass, PASS on consistency; corroborates Run 2's defect as plausible but not fully root-caused
Independently re-read task 4.49's actual diff (`git show`) against both live runs' and 4.49's own
Status section's claims: fully consistent, no leftover TODOs beyond one pre-existing, unrelated one,
code matches prose field-for-field. Independently confirmed the `run_mark_verified`/`run_set_petname`
latency finding straight from `apps/store/src/file.rs` (`decrypt_seed()` called on every
`use_key`/`derive_key`, no caching, unlike `MemorySecretStore`'s plain `HashMap` lookup or
`OsSecretStore`'s cheap keychain call).

On Run 2's new defect, independently traced the implicated code (`apps/tui/src/worker.rs`,
`apps/store/src/file.rs`, `apps/cli/src/main.rs`, `apps/core/src/chat.rs`, `apps/crypto/src/x3dh.rs`,
`apps/signaling/src/client.rs`, `apps/rendezvous/src/ws.rs`/`lib.rs`) and reached an independent,
partially corroborating, partially correcting judgment:
- Confirmed the runtime really is single-threaded (`apps/cli/src/main.rs`,
  `tokio::runtime::Builder::new_current_thread()`) and that no call site anywhere wraps a
  `FileSecretStore` unwrap in `spawn_blocking` — every scrypt unwrap runs synchronously, non-yielding,
  on the one thread the whole async runtime (including the inbound WS read loop) depends on.
- Traced the exact cost for a file-backed responder's first-contact path
  (`process_inbound_delivery` → `establish_responder_session` → `x3dh::respond`, one `use_key`/Dh
  call, then `save_chat`'s `derive_key` reseal): **exactly two** synchronous scrypt unwraps, not
  three — first contact takes the `Err(ChatError::MessageRequest)` arm, so no auto-ack `sign()` is
  invoked for the intro itself. At 4.43's own measured ~1.4–1.6s/unwrap, that's ~2.8–3.2s of
  blocking per envelope — a real, mechanistically well-grounded hazard, and one that cleanly
  explains the *directional* asymmetry Run 2 found (`OsSecretStore` does a cheap keychain lookup
  with no KDF, so an OS-keystore responder never blocks this way regardless of sender type).
- **This is not an accidental oversight** — `InboundHandoff::store`'s own doc comment
  (`apps/tui/src/worker.rs`) already states the trade-off explicitly: a file-backed account's
  `store` field is deliberately the raw `FileSecretStore` rather than a cached `MemorySecretStore`,
  "which is the right trade for a loop that signs once per received envelope and would otherwise
  hold a raw seed resident forever" — a conscious 4.43-era choice to bound raw-seed residency over
  minimizing latency, whose reliability consequence (not just slowness) is only now measured under
  a live two-peer repro for the first time.
- **Correction for 4.51's problem statement**: the ~3s-per-envelope mechanism verified from source
  only accounts for a fraction of the observed 70–260s range on its own. No ping/pong
  keepalive/idle-timeout exists anywhere in this codebase (`apps/signaling/src/client.rs`,
  `apps/rendezvous/src/ws.rs`/`lib.rs`) that would force a reconnect, so if reconnects are
  compounding the delay, the trigger is most likely below this codebase (OS/sandbox TCP behavior
  under a stalled reader), not anything the app enforces — unconfirmed either way. Also: `run_inbound_loop`
  is a blocking `await` on `client.next_deliver()`, not a busy-poll loop — describing the mechanism
  as "polling" would misdirect a fix; the real mechanism is a small number of long, fully synchronous,
  non-yielding scrypt calls with no `spawn_blocking`.
- **Verdict on the defect itself: independently corroborated as plausible and directionally
  correct — root cause not fully closed.** Recorded as such rather than as a confirmed root cause.

### The sixth defect, filed as task 4.51 (not fixed here)
Non-deterministic, sometimes multi-minute silent first-contact delivery failure to a file-backed
responder from an OS-keystore initiator, most plausibly caused by uncached, non-`spawn_blocking`'d
scrypt unwraps blocking the single-threaded tokio runtime's inbound read loop — the same underlying
mechanism as the already-known `run_mark_verified`/`run_set_petname` latency finding, worth scoping
as one shared fix per the reviewer's corroboration above, likely requiring its own
architect + security-reviewer consult (mirrors 4.40's/4.43's precedent, since caching the decrypted
seed for the inbound loop's lifetime revisits the exact residency trade-off `InboundHandoff::store`'s
doc comment already reasons about). Root cause not fully closed — 4.51 should also rule out a
reconnect-storm compounding factor (watch for `ConnectionState::Reconnecting`) and remeasure
`decrypt_seed()`'s actual wall time in-sandbox before finalizing scope.
