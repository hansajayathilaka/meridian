# 10.23 re-run — kill/resume on the real netns/veth rig, against the fixed `ice_restart`

This re-runs task 10.17's own Part 2 scenario (network cut → `ice_restart()` → resume, over the real
`WebRtcTransport` backend, real netns/veth, no simulation anywhere) now that tasks 10.19–10.22 have
replaced `ice_restart`'s old local-only no-op with a real, symmetric SDP offer/answer round trip
(ADR 0025). Both `apps/cli/examples/kill_resume_netns_drive.rs` and
`apps/cli/examples/netns_ice_restart_probe.rs` were updated for this task to call the new signature
with a freshly-(re)connected `SignalRelay` scoped to just the restart attempt (see this task's own
report for the exact diff and why a genuine reconnect doesn't fully apply to their file-based
`FileRelay` test double).

## Pre-flight fix: the `IFNAMSIZ` self-check bug task 10.17 worked around is now fixed for real

Task 10.17 found that `tools/netns-kill-resume.sh`'s own `need_veth_linkstate` pre-flight self-check
built probe interface names as `kr-probe-a-$$`/`kr-probe-b-$$` (`$$` = the invoking shell's PID) — 11
characters of fixed prefix plus a PID that is 5+ digits on this sandbox, exceeding Linux's
15-usable-byte `IFNAMSIZ` limit, so `ip link add` itself failed and the self-check wrongly reported
"basic netns/veth link up/down is not usable in this environment — skipping" even though the
capability genuinely works. Task 10.17 worked around this out-of-line (a throwaway copy with only the
pre-flight calls no-op'd) rather than fix the checked-in script, and left it as an unowned
carry-forward.

This task fixes it for real in the checked-in script: `need_veth_linkstate` now zero-pads the PID to
6 digits (`kr-a-016738`, always well under the 15-byte cap) instead of no-op'ing around the bug in a
separate copy. **Correction**: this task's first attempt zero-padded via truncation
(bash's `${pid: -6}`), which code review caught and live-reproduced as a real bug — that expression
returns an *empty string*, not the PID, for any PID under 6 digits (effectively every real
invocation), collapsing every probe pair to the same constant name and creating a genuine
namespace-collision risk between concurrent runs. Corrected to `printf '%06d'`-style zero-padding,
which has no such collapse. Reproduced first,
confirming the bug was still present before the fix:

```
$ ip link add kr-probe-a-16738 netns test-ns1 type veth peer name kr-probe-b-16738 netns test-ns2
Error: argument "kr-probe-b-16738" is wrong: "name" not a valid ifname
```

and confirmed fixed after the change — `tools/netns-kill-resume.sh run`/`probe` below both ran
directly, unmodified, with no throwaway workaround copy needed this time.

Note that both sides' `ice_restart()` calls themselves returned `Ok` — meaning the full ADR 0025

underlying data channel does not actually resume carrying traffic immediately once `ice_restart()`
returns, in this smaller probe's particular call pattern.

### Diagnosis: this is very likely a readiness race, not a repeat of the old no-op gap

Three pieces of live evidence gathered while investigating this failure (see this task's own report
for the full commands):

1. **Plain IP connectivity between the two namespaces recovers immediately and cleanly** after the
   veth is brought back up — a `ping` round-trips with 0% loss right after restore, before
   `ice_restart()` is ever called. The network fabric itself is not the problem.
2. **Correction (found by this task's own test-engineer review, which independently re-measured
   with sub-10ms-granularity polling rather than the coarser one-shot `ip -s link show` check used
   here originally): the sending side's interface does NOT show zero additional traffic** — real,
   reproducible TX/RX activity (roughly 6–13 packets, ~1 KB) occurs precisely in the window between
   `ice_restart()` returning `Ok` and the failed send, consistent with fresh ICE connectivity checks
   actively running. This *sharpens* rather than overturns the readiness-race diagnosis: traffic is
   flowing at the ICE level, yet the message still never arrives — meaning the race is at the
   DTLS/SCTP association layer sitting above ICE (which must itself re-establish before a data
   channel can carry anything), not "nothing on the wire at all." The original one-shot measurement
   likely missed this narrow window; the corrected, independently-reproduced finding is the one to
   trust.
3. **Inserting a 3-second sleep immediately after `ice_restart()` returns `Ok`, before sending**
   (a throwaway, uncommitted diagnostic edit, reverted immediately after this test) made the probe
   **pass reliably**. This is strong evidence that `ice_restart()`'s `Ok` return — which, per ADR
   0025/task 10.22, means only that the *signaling* round trip and fingerprint checks succeeded —
   does not yet guarantee the underlying ICE/DTLS/SCTP path has actually re-converged enough to
   carry traffic, and there is no synchronization point in `P2pSession::ice_restart` today that waits
   for that (ADR 0025 itself notes `WebRtcTransport` still only wires
   `on_peer_connection_state_change` for the *original* `Connected` transition, not a post-restart
   reconnection signal). A caller that sends immediately after `Ok` — as this probe deliberately
   does, to test exactly that boundary — can race this and silently lose the message, with **no local
   error** telling it so (the same class of symptom task 10.15's original probe first observed,
   though the specific cause is now different: not "no real restart happens" but "a real restart
   happens, signaling succeeds, but the data path's own readiness isn't observable to the caller").

**Why `run` passes but `probe` doesn't**: `kill_resume_netns_drive.rs`'s sender does not send
anything immediately after `ice_restart()` returns — it enters a `pump()` polling loop waiting for
the receiver's resume bitmap first, which incidentally gives the connection more real wall-clock time
to finish reconverging before either side's own next send is attempted. `netns_ice_restart_probe.rs`
sends immediately, which is precisely why it (correctly) catches a race window `run`'s own timing
happens not to hit.

**This is reported as a genuine finding, not silently worked around.** No sleep, retry, or other
timing shim was added to either example or to `P2pSession::ice_restart` itself to make this probe
pass — doing so would mask a real gap (the missing post-restart readiness signal) rather than fix it,
and this task's own scope (caller wiring + honest re-run reporting) does not include redesigning
`ice_restart`'s readiness contract. This is recorded here as a new candidate follow-up, distinct from
and in addition to ADR 0025's own already-tracked residual (the mutual-timeout glare race) and the
still-separately-open `StreamType::on_reconnect` carry-forward.
