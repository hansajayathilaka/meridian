# 10.21 — Tolerant (mailbox-eligible) restart delivery

**Phase:** 10 — File Transfer Stream · **Feature:** T09 (fix) · **Depends on:** 10.20 ·
**Status:** pending

## Goal
Give `SignalRelay` a way to send an envelope tolerantly — treating "queued to the peer's mailbox"
(T07/[ADR 0007](../../adr/0007-offline-mailbox.md)) as a normal, non-error outcome rather than the
existing hard-fail `SignalRelay::send`'s "peer is not currently connected" error — per
[ADR 0025](../../adr/0025-ice-restart-renegotiation.md)'s decision that restart signaling must not
require holding a relay connection open for a session's full lifetime.

## Scope
- **In:** `apps/core/src/session.rs`'s `SignalRelay` trait — add a new method (e.g.
  `send_tolerant(&mut self, to: &[u8; 32], blob: Vec<u8>) -> Result<RouteOutcome, SessionError>`, name
  and exact shape at the implementer's discretion, but it must surface "delivered live" vs. "queued to
  mailbox" as distinct, non-error outcomes and only error on a genuine failure) alongside the existing
  hard-fail `send`, which stays unchanged for the original dial/answer contract (ADR 0025's Option B
  rejection explains why that contract must stay hard-fail). `RendezvousRelay`
  (`apps/core/src/signal_relay.rs`) implements it via `SignalingClient::route_with_hint_detailed`
  (already built for T07, returns exactly `RouteOutcome{delivered, queued}` — do not duplicate this
  logic, call through to it). `MemRelay` (the in-process test double, also in `session.rs`) needs a
  reasonable tolerant-send simulation too, since it's what most of this phase's own tests construct
  sessions against — check how it currently models delivery and extend it consistently (e.g. it may
  already always "deliver," in which case tolerant-send trivially always returns `delivered: true`;
  confirm rather than assume).
- **Out:** anything that actually calls this new method with a real `IceRestartOffer`/`IceRestartAnswer`
  payload (that's [10.22](./10.22-session-ice-restart-signaling.md)'s job) — this task only builds the
  relay-level primitive and proves it round-trips both outcomes (delivered vs. queued) in isolation,
  with a placeholder/arbitrary blob if needed for the test.

## Deliverables
1. `SignalRelay`'s new tolerant-send method + `RendezvousRelay`/`MemRelay` implementations.
2. Tests proving both outcomes: a live peer receives it immediately (`delivered: true`), an offline
   peer's send returns `queued: true` without erroring (mirror whatever the existing `meridian-rendezvous`
   mailbox test harness already uses to put a peer "offline" for T07's own tests — don't invent a new
   offline-simulation mechanism).

## Risks / notes
Don't touch `RendezvousRelay::send`/`map_route_result`'s existing hard-fail behavior — it's correct for
the dial/answer contract this task doesn't touch (ADR 0025 is explicit that Option B, reusing that
contract, was rejected specifically because it's *supposed* to stay hard-fail for a fresh dial). This
task adds a sibling method, not a behavior change to the existing one.

## Tests
`cargo nextest run -p meridian-core` (new tolerant-send tests, both outcomes); existing suite stays
green.
