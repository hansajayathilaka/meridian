# 4.6 — Petname assignment + contact management CLI

**Phase:** 4 — Verification & Trust + Terminal TUI Client · **Feature:** T08 — Verification & Contact Trust · **Depends on:** 4.3 · **Status:** done

## Goal
Land petname assignment as a strictly local, wire-never operation, with a CLI surface to manage
contacts — the reference implementation the TUI's contact list (4.19) builds on.

## Scope
- **In:** `meridian contact add/list/rename/block`; petnames are assigned only by explicit local user
  input, never populated from a QR payload, an `mrd1:` ID, or any wire field ([system-design §3.1](../../architecture/system-design.md)).
- **Out:** directory-attestation petname *suggestions* (4.8, which layers provenance-not-authority on
  top of this); the TUI's Add Contact screen (4.19).

## Deliverables
1. `apps/cli/src/contact.rs` (or equivalent): `add/list/rename/block` subcommands over `trust.rs`.
2. Test: adding a contact whose QR/ID payload contains a name-like string never populates `petname` —
   only an explicit `--petname`/prompt input does.

## Risks / notes
- This is a threat-model invariant (display names are never taken from the wire), not a style
  preference — a spoofed "petname" arriving via any wire path is exactly the kind of thing a malicious
  peer or server would try.

## Status
Done. `apps/core/src/trust.rs` gains `Contact::petname: Option<String>` and
`Contact::user_blocked: bool`, written only by `set_petname`/`set_user_blocked`. `user_blocked` is a
deliberately separate field from `TrustState::Blocked` (task 4.4's verified-contact key-change hard
block, clearable only by `mark_verified`) — reusing that state for user-initiated blocking would risk
either an unclearable user-block or a user "unblock" accidentally clearing a real key-change incident;
keeping them orthogonal means neither can affect the other in either direction, and both fields survive
`observe_key_change`'s contact migration since neither is wire-derived. `apps/cli/src/contact.rs`:
`meridian contact add/list/rename/block` over `trust.rs`.

**security-reviewer** (required — petnames-never-from-wire is a threat-model invariant, first enforced
here) found **no wire-leak** on any of the 6 checked angles: traced every write to `Contact::petname`
(only `set_petname`, called only from `add`'s `--petname`/prompt and `rename`; `TrustStore::contacts` is
private with no `&mut` accessor, so the invariant is structurally enforced, not just conventional);
confirmed `observe`/`observe_key_change` are petname- and `user_blocked`-blind (the migration moves the
whole `Contact`, never rebuilding it from a literal that could carry a wire value); confirmed the
`user_blocked`/`Blocked` separation holds in every state-mutating method with no bypass either
direction; confirmed `contact block` never touches `state`; confirmed `MAX_PETNAME_LEN` truncation is
UTF-8-safe like `MAX_HINT_LEN`'s precedent. Required two test additions before closing (both added, no
code changes needed): `apps/core/tests/contact_management.rs` (5 tests) covering the
`user_blocked`/`Blocked` orthogonality claims end-to-end (both directions of non-interference,
survival across `observe_key_change`'s migration, `UnknownContact` on both setters) and a new
`bound_tests` module inside `trust.rs` (4 tests) proving `bounded_petname`/`bounded_hint` truncate at a
UTF-8 char boundary rather than splitting a multi-byte character.

One should-fix, non-blocking messaging note tracked for a future task (not required to close this one):
when a contact is both `user_blocked` and key-change `Blocked`, `can_send` always shows only the
user-block reason, never surfacing the underlying key-change/interception event underneath — the send
is still correctly blocked (no bypass), but verification-ux.md's "loud" intent for a key-change block
could go unnoticed by a user who already knew about their own local block. Needs either combining both
reasons or an explicit design sign-off that this precedence is intentional — flagged for whichever task
next touches `can_send`'s messaging (4.22's TUI modal is a natural point to resolve it).

`cargo test -p meridian-core -p meridian-cli` (all suites, including the new `contact_management` and
`bound_tests`), `cargo fmt --check`, and `cargo clippy --workspace --all-targets -- -D warnings` all
clean.
