# 5.4 — `spawn_blocking`-wrap `run_mark_verified`/`run_set_petname`'s synchronous `decrypt_seed()`

**Phase:** 5 — Review of Phase 4 · **Feature:** review fix (F4) · **Depends on:** — · **Status:** done

## Goal
Move `run_mark_verified` and `run_set_petname`'s synchronous, file-backed `decrypt_seed()` scrypt
unwrap off the single-threaded tokio runtime — the exact class of hazard task 4.51 fixed for six other
call sites, deliberately split off there because `live_store` is read by thirteen handlers and wrapping
all of them would have been a disproportionately wider diff than 4.51's own scope. This task closes the
two highest-impact of those thirteen (measured live at 4.52: ~3.7–4.1s UI-thread block for
`run_mark_verified`, masked by the optimistic in-memory flip).

## Scope
- **In:** `apps/tui/src/worker.rs::run_mark_verified` (lines ~1449–1460) and `::run_set_petname` (lines
  ~977–1000). Apply 4.51's precedented shape: widen the relevant store handle to
  `Arc<dyn SecretStore>`, wrap the `decrypt_seed()`-driving call in `spawn_blocking`, `.await` it.
- **Out:** Generalizing to all thirteen `live_store`-routed handlers — 4.51 explicitly scoped that as
  disproportionate; this task takes only the two the review report names as highest-impact. The
  remaining eleven stay a named, unowned residual (do not silently expand or silently drop the scope).

## Deliverables
1. `run_mark_verified` and `run_set_petname` both run their `decrypt_seed()` unwrap via
   `spawn_blocking`, matching 4.51's `InboundHandoff::store`/`run_inbound_loop` pattern.
2. A falsifiable concurrency test per call site (4.51's own precedent: each of its four new tests was
   confirmed to fail when its `spawn_blocking` wrap was reverted) — or, if a live-run timing measurement
   is more practical for these two UI-driven handlers, a recorded before/after measurement mirroring
   4.52's own reporting discipline.
3. Per 4.51's own binding rule, self-assess in this task's own file whether a security consult is
   required — a `spawn_blocking`-only fix (no residency extension) needs none, matching 4.51's
   determination; state the assessment explicitly rather than skipping it.

## Risks / notes
This task **must land before 5.3** — both touch `run_mark_verified`'s exact body, and 5.3 adds new
write-through logic that should build on this task's already-async-safe shape rather than the reverse
(mirrors this project's own 4.43-before-4.42 precedent: land the mechanical, no-open-design-question
shape change first).

## Status
**Done.** `run_mark_verified` and `run_set_petname` (`apps/tui/src/worker.rs`) now run their entire
load→mutate→save sequence — the `decrypt_seed()`-driving `TrustStore`/`contacts` load and save — inside
one `tokio::task::spawn_blocking` closure per call, matching 4.51's "one wrap spanning the whole
sequence" pattern exactly (mirrors `process_inbound_delivery`, not per-call wrapping).

**Mechanism:** `OnboardingSession::live_store` widened from `Option<(Box<dyn SecretStore>, KeyHandle)>`
to `Option<(Arc<dyn SecretStore>, KeyHandle)>` — representation-only; the existing borrow-shaped
`live_store()` accessor is unchanged (`Arc` derefs to `&dyn SecretStore` exactly like `Box` did), so the
other `open_account_store`-routed handlers see zero behavior change. A new, additive
`open_account_store_owned()` (mirroring 4.51's own `connect_owned`/`handshake_owned` precedent — a
second, parallel entry point rather than a widened signature for every existing caller) gives both target
functions an owned `(Arc<dyn SecretStore>, KeyHandle)` to move into the `'static + Send` closure.

**Self-assessment (binding, per 4.51's rule): does NOT extend key residency.** Pure execution-context
change only — same call sites, same number of `decrypt_seed()` calls (once per `TrustStore::open_at_rest`/
`seal_at_rest`), just on a `spawn_blocking` thread instead of the single-threaded runtime.
`FileSecretStore` holds only `path`/`passphrase`, never a resident decrypted seed; `decrypt_seed()`
re-derives from disk on every call and the result is a `Zeroizing` buffer scoped to that one call.
Independently confirmed by the `reviewer` pass via source trace, not taken on faith. **No
security-reviewer consult required**, per the task's own binding rule.

**Falsifiable tests, not timing measurement** (chosen because, unlike `run_unlock`, these two functions
take an injectable store — the precise `SlowStore`-double technique from 4.51 was directly reusable): a
`SlowStore` test double sleeping 150ms per `use_key`/`derive_key` races a 10ms heartbeat against each
function's ~300ms blocking window, asserting ≥8 ticks. Both were independently falsified twice — once by
the implementer, once again by `test-engineer` from scratch — reverting each `spawn_blocking` wrap made
its heartbeat test fail deterministically (`observed 0`), restored and reconfirmed green both times.
`test-engineer` additionally stress-tested the timing margin under 4×/8× CPU oversubscription (8 runs,
0 flakes) and confirmed the ~73% slack (only ~80ms of the ~300ms window needed) holds under real
contention.

**Scope held**: only these two of the `live_store`-routed handlers were touched. The remaining ones stay
task 4.51's named, unowned residual — this task does not silently expand or drop that scope. Two doc
comments in `worker.rs` previously reused 4.51's original "eleven remaining" figure without re-verifying
against current source (the `reviewer` pass found the live count has since grown, since new handlers like
`run_set_policy_override`/`run_persist_receipt` were added after 4.51's own snapshot); reworded to state
the count has grown and must be re-measured rather than assumed, instead of asserting a second number
that would itself go stale.

**Gate 9:** no new TUI surface — pure reliability fix to an existing surface's backing handlers, same "no
surface" reasoning 4.51 itself used.

### Review round
`reviewer` (combined architect + code-reviewer) — **PASS**, no blocking issues. Architect confirmed the
`Arc` widening is representation-only (`SecretStore: Send + Sync` satisfies `spawn_blocking`'s bound), the
wrap spans the whole sequence not per-call, and `open_account_store_owned` is purely additive with zero
impact on other callers. Code-reviewer independently traced `FileSecretStore` and `TrustStore::open_at_rest`/
`seal_at_rest` from source to confirm the residency self-assessment holds, confirmed correct
`JoinError`/inner-`Result` error propagation (no silent swallowing), and independently reverted+restored
both `spawn_blocking` wraps to confirm the tests are genuinely falsifiable. Two cosmetic nits noted (an
`Arc::from(Box<dyn Trait>)` allocation-reuse doc-comment overclaim with no security implication; the
stale "eleven" count) — both closed above; one architecture observation (intentional, labeled duplication
of the `StoreKind::Os` branch between `open_account_store`/`open_account_store_owned`, matching 4.51's own
duplication precedent, not required to consolidate now).

`test-engineer` — **PASS**. Independently re-ran the falsification itself (not trusting the implementer's
report), confirmed the same deterministic failure signature, and stress-tested the heartbeat-racing
technique's margin under real scheduler contention. Full crate suite green throughout.
