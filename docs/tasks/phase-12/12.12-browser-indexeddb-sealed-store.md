# 12.12 — Browser IndexedDB sealed store (`apps/wasm`)

**Phase:** 12 — Browser & Desktop Clients · **Feature:** T11 · **Depends on:** 12.10, 12.5 · **Status:** done

**User surface:** none directly — the persistence layer behind "browser refresh restores sessions"
(the feature spec's own acceptance criterion), consumed by the browser adapter (12.13). No TUI surface
applies.

## Goal
Implement [ADR 0026](../../adr/0026-browser-client-local-store.md)'s binding conditions 2–5: the
IndexedDB record-sealing/schema module living in `apps/wasm` (not `apps/store`, per the ADR's own
crate-placement split recorded in [phase-12/README.md](./README.md#architect-consult-substratestoresigning-decisions-settled-before-task-breakdown) —
`meridian-crypto`'s `at_rest::seal`/`open` is needed here, and `meridian-crypto` already depends on
`meridian-store`, so putting this in `apps/store` alongside 12.5's trait impl would cycle).

## Scope
- **In:** one IndexedDB object store per ADR-0021-style bucket (`identity`, `sessions`, `contacts`,
  `history`, `outbox`), each record `meridian_crypto::at_rest::seal`/`open`-wrapped (unmodified,
  compiled to WASM) under a key from task 12.5's `WebCryptoSecretStore::derive_key` with a
  purpose-specific `info` string; schema versioning (`"v"` field, forward migration, fail-closed on a
  newer-than-understood version) and fail-closed-on-AEAD-failure behavior matching ADR 0021 conditions
  5/5b exactly; the unsealed `state`-equivalent record restricted to view geometry + opaque conversation
  handles per condition 4, with a content-scanning test mirroring the existing 4.27/8.12 at-rest-audit
  harness precedent.
- **Out:** the `WebCryptoSecretStore` trait impl itself (12.5 — this task only *consumes* it);
  cross-tab/multi-window IndexedDB concurrency beyond what the browser's own transaction model already
  guarantees (no bespoke locking layer needed unless testing finds a real gap — flag rather than
  preemptively build one).

## Deliverables
1. `apps/wasm/src/store/indexeddb.rs`.
2. Round-trip tests: seal/open for each bucket; version-refusal (open a record whose `"v"` exceeds what
   the running build understands, assert fail-closed); AEAD-failure-is-fatal (corrupt a sealed record,
   assert the store surfaces a hard error rather than silently reinitializing to empty — the same
   condition-5b property ADR 0021 protects `pinned_key_history` with, here protecting the browser's own
   pinned-key trust state).
3. A browser-side at-rest-audit test extending the 4.27/8.12 pattern: scan the unsealed `state`-equivalent
   record for petname/body/key/contact-identifier-shaped content and assert none is present.

## Risks / notes
This is the property that makes ADR 0026's whole design honest — do not let the AEAD-failure-is-fatal
test become a "reinitialize on any error" shortcut; verify the specific failure mode (auth failure vs.
`NotFound`) is distinguished exactly as ADR 0021 condition 5b requires.

## Tests
`wasm-bindgen-test` (or the runner confirmed by 12.10/12.5) exercising the round-trip, version-refusal,
AEAD-failure, and at-rest-audit-scan cases above.

## Reviews
**security-reviewer** (mandatory, ADR 0026); **architect** (confirms exact ADR conformance,
particularly the sealing-boundary and fail-closed conditions); **code-reviewer**.

## Outcome
Implemented `apps/wasm/src/store/indexeddb.rs`: five buckets (identity/sessions/contacts/history/outbox),
each `meridian_crypto::at_rest::seal`/`open`-wrapped (unmodified) under a key from
`WebCryptoSecretStore::derive_key` (called as the async inherent method directly, per task 12.5's own
documented sync/async gap — never through `&dyn SecretStore`), with a distinct `info` string per bucket.
`get_sealed` genuinely distinguishes `NotFound` (`Ok(None)`, no AEAD operation attempted) from an AEAD
authentication failure (`Err(IndexedDbError::SealedRecordCorrupt)`, a dedicated variant, only reachable
after a record was actually found) — the property the task's own Risks/notes calls out as "what makes
ADR 0026's whole design honest." Schema versioning fails closed on a newer-than-understood `"v"`. The
unsealed `StateRecord` is structurally restricted to view geometry + an opaque conversation handle — no
petname/body/key/contact-identifier field exists on the type at all, not just absent from an instance.

The combined review (security-reviewer + architect + code-reviewer) returned **PASS** on all three
lenses, zero blocking findings, after specifically stress-testing the two properties the task names as
most likely to fail quietly: (1) the AEAD-failure-is-fatal test flips one real ciphertext byte (in the
Poly1305 tag, confirmed past the nonce prefix) in an actually-written sealed record and asserts the
specific error variant — reasoned through the counterfactual that a `.unwrap_or_default()` shortcut would
fail this test; (2) the at-rest-audit scanner's non-vacuity is proven by a companion test that deliberately
injects a leak via a test-only raw bypass write and confirms the scanner catches it, mirroring task 4.27's
own review-mandated non-vacuity requirement. Also independently confirmed domain separation (a key derived
for one bucket genuinely cannot open another bucket's sealed bytes, not just "five buckets exist") and
re-reproduced the real headless-Chrome test run (8/8 lib + 2/2 audit-test). No `WebCryptoSecretStore`
(12.5) or `at_rest` (apps/crypto) changes — confirmed absent from the diff.
