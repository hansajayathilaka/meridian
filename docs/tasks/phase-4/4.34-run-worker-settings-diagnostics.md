# 4.34 — Real `run_worker`: settings & diagnostics

**Phase:** 4 — Verification & Trust + Terminal TUI Client · **Feature:** T17 — Terminal TUI Client (gap closure) · **Depends on:** 4.24, 4.25 · **Status:** done

## Goal
Execute `SaveSetting`/`RunDoctor` for real.

## Scope
- **In:** `run_worker` arms wrapping already-built functions — `crate::config_write::write_setting_at`
  (task 4.24) and `crate::screens::diagnostics::run_doctor_binary`/`parse_doctor_json` (task 4.25). This
  task is almost entirely "call the already-built function from `run_worker` instead of nothing."
- **Out:** palette registration for Settings (4.36's job — it needs a live `config_path` to construct a
  `SettingsState` from, which doesn't exist until `Screen::Main`/`LiveSession` do).

## Deliverables
1. Two `run_worker` arms: `SaveSetting`, `RunDoctor`.
2. Tests confirming comment-preserving `config.toml` write-back still works end to end through a real
   worker dispatch, and the doctor-binary-not-found path still surfaces honestly (never a silent no-op).

## Risks / notes

  already done and reviewed in 4.24/4.25; this task is wiring, not new logic.
- No dependency on 4.29–4.33 or any other task in this gap-closure set — independently testable today.

## Status
Done. Added two `run_worker` `dispatch` arms — `Effect::SaveSetting` → `handle_save_setting` (calls
`crate::config_write::write_setting_at`), `Effect::RunDoctor` → `handle_run_doctor` (calls
`crate::screens::diagnostics::run_doctor_binary`, which already internally calls `parse_doctor_json`, so
no separate call was needed) — replacing what used to fall through into the placeholder
`other => WorkerEvent::Completed(other)` catch-all arm. Both follow the same fail-closed `Ok`/`Err` →
`Completed`/`Failed` shape as every other arm in this file; `ConfigWriteError`'s four variants and
`run_doctor_binary`'s own honest error strings are surfaced verbatim, never swallowed. As scoped, this
was pure wiring onto two already-built, already-reviewed functions — no new logic.

New test file `apps/tui/tests/run_worker_settings.rs` (4 tests), dispatching directly against
`meridian_tui::worker::dispatch` (no channel plumbing needed — neither request type touches
`$MERIDIAN_HOME`/an account/a `SecretStore`): comment-preserving write-back proven end to end through a
real worker dispatch (not just calling `write_setting_at` directly), a second sequential write composing
correctly on top of the first, a missing-config-file failing closed without fabricating a file, and
doctor-binary-not-found failing closed honestly rather than silently no-opping.

**Review (`reviewer`, correctness + subprocess-invocation-safety + architecture combined):** the wiring,
fail-closed error handling, and test quality all held up clean — confirmed exactly `SaveSetting`/
`RunDoctor` were pulled out of the catch-all with every other `Effect` variant unaffected;
`run_doctor_binary`'s internal `parse_doctor_json` call already handles malformed doctor output as a
distinct, line-numbered error with no separate handling needed; `RunDoctorRequest::binary` is only ever
constructed from a fixed constant (`"meridian"`) with no shell interpolation or attacker-influenced path
— `SaveSetting`'s config write has no way to redirect what `RunDoctor` later executes; all 4 new tests
genuinely exercise the real `run_worker` dispatch path with meaningful comment-preservation assertions
(top comment, field-adjacent comment, untouched key + its inline comment, old value truly gone not
shadowed).

One correctness finding: this task's own wiring left three doc-comment blocks stale — module docs in
`apps/tui/src/screens/diagnostics.rs` and `apps/tui/src/config_write.rs`, plus the `dispatch` catch-all's
comment in `apps/tui/src/worker.rs`, still asserted in present tense that `SaveSetting`/`RunDoctor` were
"not yet wired into `run_worker`" — a specific, checkable claim about *today's* behavior that this task's
own diff made false, in the exact files whose functions it just wired (distinct from the batch's
consistently-deferred, already-known-stale `docs/architecture/tui-client.md §10` status survey, left for
4.38 as established by every prior task in this set). Separately, the catch-all's own comment attributed
its one remaining unhandled variant (`Effect::FetchBundle`) to "later gap-closure task 4.35," but 4.35's
actual scope is a brand-new `AppEvent::Inbound` push path that never touches this `dispatch` match — so
`FetchBundle` would have stayed silently unhandled and unexplained even after 4.35 lands. Both fixed:
`diagnostics.rs`/`config_write.rs` now state the wiring landed as of task 4.34; the catch-all comment now
names `FetchBundle` directly as the sole remaining placeholder variant rather than attributing its gap to
a task that will never touch it.

all green), `cargo fmt --all -- --check`, `cargo clippy --workspace --all-targets -- -D warnings`, and
