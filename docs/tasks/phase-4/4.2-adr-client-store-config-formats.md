# 4.2 — ADR 0021: client-local store & config formats

**Phase:** 4 — Verification & Trust + Terminal TUI Client · **Feature:** T17 — Terminal TUI Client · **Depends on:** — · **Status:** pending

## Goal
Ratify, as a binding ADR, the at-rest posture and format of everything the TUI writes to disk, so the
store (4.15) and config (4.14) tasks implement a decided shape rather than each inventing one.

## Scope
- **In:** ADR 0021 deciding (a) JSON documents sealed with `meridian_crypto::at_rest::seal`
  (XChaCha20-Poly1305) under the key derived from the account key via `STORE_KEY_INFO` — the same
  mechanism `sessions.bin` already uses — for `contacts.json`, `history/*.jsonl`, `outbox.json`; (b)
  `state.json` deliberately **unsealed** but constrained to contain no petname/message body/key
  material (view geometry + conversation index only) — an invariant the at-rest audit (4.27) checks;
  (c) TOML for `config.toml`, human-edited, never rewritten wholesale by the app; (d) explicit
  `meridian tui --export-json <path>` as the **only** unsealed-export mechanism. Record the rejected
  alternative `store.encrypt = false` (a persistent-plaintext opt-out) with reasoning — realizes
  [data-model.md §2](../../architecture/data-model.md#2-client-local-store-encrypted-via-secretstore-key)
  for the terminal client. Full schemas proposed in
  [tui-client.md §5](../../architecture/tui-client.md#5-local-store--configuration) are what this ADR
  ratifies or amends.
- **Out:** packaging (4.1); any code.

## Deliverables
1. `docs/adr/0021-client-local-store-config-formats.md` — status `Accepted`, options considered,
   decision (including the rejected `store.encrypt = false` alternative), binding conditions, residual
   risks.
2. `docs/adr/README.md` — index entry.

## Risks / notes
- This is the ADR the security-reviewer will hold every later T17 store/config task against — get the
  sealing boundary (what's sealed vs. `state.json`'s exception) unambiguous.
- Migration policy (refuse-to-open a newer schema version, `.bak` before forward-migrating) belongs here
  too, since it's a format decision, not an implementation detail.
