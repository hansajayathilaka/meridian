# 11.3 — Bound/restructure `mrd.file/1`'s `pending_chunks` buffer and its O(n) rescan

**Phase:** 11 — Review of Phase 10 · **Feature:** review fix (F3, N1) · **Depends on:** — · **Status:** done

**User surface:** none — internal receiver-side data-structure hardening in `meridian-streams`/the CLI's
`run_responder`; no client-visible behavior change beyond removing a resource-exhaustion shape, so no TUI
surface applies (Definition of Done gate 9).

## Goal
Bound `mrd.file/1`'s inbound chunk buffer so a duplicate/retransmitted or flooding peer can't grow it
unboundedly, and fix the O(n) full-buffer rescan that shares the same root cause.

## Scope
- **In:** `apps/streams/src/file.rs`'s `TransferState::pending_chunks`/`on_frame` — replace the unbounded
  `Vec<Vec<u8>>` with an index-keyed structure (e.g. a `BTreeMap<u64, Vec<u8>>`, mirroring
  `apps/streams/src/receiver.rs::FileReceiver`'s already-correct approach) so a duplicate chunk index
  overwrites/ignores rather than appends; `apps/cli/src/send.rs::run_responder`'s `distinct_chunk_indices`
  (N1) updated (or removed) to read the new structure's key set directly instead of rescanning a `Vec` on
  every pump event.
- **Out:** no change to per-chunk AEAD/merkle verification itself (that engine is `FileReceiver`,
  untouched here — see 11.8/F8 for its live-wiring gap); no change to wire chunk framing.

## Deliverables
1. `TransferState::pending_chunks` (or its renamed replacement) restructured in
   `apps/streams/src/file.rs`; `on_frame` updated to insert-or-ignore by chunk index.
2. `apps/cli/src/send.rs`: `distinct_chunk_indices` removed or simplified to read the new structure's own
   key set; `run_responder`'s completion check updated accordingly.
3. Updated existing tests that assert on `pending_chunks`'s old `Vec<Vec<u8>>` shape (e.g.
   `on_frame_strips_the_tag_byte_leaving_pending_chunks_byte_for_byte_identical`,
   `on_frame_buffers_only_for_a_stream_this_side_accepted`) — necessary churn from the type change, not
   scope creep.
4. New test: a duplicate/retransmitted chunk frame for the same index does not grow the buffer past one
   entry for that index.

## Risks / notes
A map keyed by a validated in-range chunk index is already inherently bounded by the manifest's own leaf
count once an out-of-range check applies — this may fully satisfy F3's DoS concern without an additional
artificial cap. **Resolved (implementation + review):** `on_frame` now rejects an out-of-range index up
front, before ever buffering it, rather than deferring to `finalize_transfer` — confirmed correct (chunk
math matches `receiver.rs::FileReceiver`'s own byte-for-byte) and sufficient to close F3 on its own.

## Tests
`cargo nextest run -p meridian-streams`; `cargo nextest run -p meridian-cli`.

## Reviews
**code-reviewer**, **security-reviewer** (resource-exhaustion/DoS hardening on a peer-controlled buffer).

## Outcome
`TransferState::pending_chunks` restructured from `Vec<Vec<u8>>` to `BTreeMap<u64, Vec<u8>>`, mirroring
`receiver.rs::FileReceiver`'s existing approach. `on_frame` now rejects an out-of-range chunk index up
front (before buffering), closing F3's DoS concern directly rather than deferring to `finalize_transfer`.
`apps/cli/src/send.rs`'s `distinct_chunk_indices` (N1) removed; `run_responder`'s completion check and
`finalize_transfer` read the map's own key set/values directly.

**Deliberate deviation from the literal "insert-or-ignore" wording, reviewed and accepted**: the
implementation uses plain overwrite (`BTreeMap::insert`, last-write-wins) rather than first-write-wins,
because strict ignore-on-duplicate broke `corrupted_chunk_adversarial.rs`'s existing task-10.16
acceptance test — a corrupted chunk buffered first, then a legitimate resend of the same index with
corrected bytes, must supersede the bad copy for resume's corrupted-chunk recovery to work. Review traced
`on_frame` (pure pre-verification staging, no AEAD/merkle check runs there) and confirmed overwrite
introduces no verification bypass and closes F3 identically to ignore (bounded by leaf count either way);
also confirmed no new griefing angle versus the prior unbounded-`Vec` status quo, which already didn't
deduplicate.

Combined code-reviewer/security-reviewer pass: **PASS, zero blocking findings**. One non-blocking
test-quality nit (a now-tautological assertion in `sender_engine.rs`, decoding a map entry by the same
key used to insert it) was fixed in the same commit rather than carried forward. Full suite green:
`meridian-streams` 70/70, `meridian-cli` 91–97/97 (one CLI test occasionally flakes under parallel load,
confirmed pre-existing and unrelated to this diff — reproduces identically on the pre-change tree),
clippy clean (including `--features webrtc` covering the gated netns example).
