# 5.2 — Diagnostics-surfaced repair action for `run_accept_request`'s partial-failure window

**Phase:** 5 — Review of Phase 4 · **Feature:** review fix (F2) · **Depends on:** — · **Status:** done

## Goal
Close the standing, twice-instantiated partial-failure gap in `run_accept_request`: give a durably
trusted-but-unreachable peer (from a failed `contacts.json` write, or task 4.49's failed
`history.jsonl` intro write) a real on-screen repair path, instead of a permanently silent dead end.

## Scope
- **In:** `apps/tui/src/worker.rs::run_accept_request` (lines ~1304–1373) — its own doc comment already
  sketches the design direction: a repair action rebuilding rows missing for an existing `trust.bin`
  contact, explicitly distinct from the delete-tombstone case. A diagnostics-surfaced trigger for that
  repair (`apps/tui/src/screens/diagnostics.rs`) and the effect wiring to invoke it (`app.rs`).
- **Out:** Automatic/silent retry on next accept-request attempt (ADR 0001 forbids a hint-less manual
  re-add, and this project's own "do not resurrect a case that should not self-heal automatically"
  discipline, already applied to the analogous missing-history-entry case, applies here too — the
  repair must be an explicit, surfaced action, not implicit).

## Deliverables
1. A named repair function distinguishing "peer exists in `trust.bin` but is missing its
   `contacts.json` row" from "peer exists but is missing its accepted-intro history entry" — both
   covered, since 4.49 introduced the second instance of this class.
2. A diagnostics-screen affordance that surfaces repairable contacts and triggers the repair.
3. Tests reproducing both partial-failure shapes on disk and proving the repair heals them without
   touching an already-healthy contact or resurrecting a deleted one.

## Risks / notes
The retry-succeeds branch (pin already applied) is already well tested
(`run_worker_trust.rs:526`, `accept_request_retry_after_a_partial_failure_still_completes_the_pin`) —
do not duplicate that coverage, extend around it. Be careful the repair action cannot be triggered
against a contact the user has explicitly deleted (tombstone) — that's the exact case this task must
stay distinct from.

## Status
**Done.** New `Effect::ScanRepairableContacts`/`Effect::RepairAcceptedContact` (app.rs) handled by
`scan_repairable_contacts`/`run_repair_accepted_contact` (worker.rs), mirroring the existing
`RunDoctorEffect` request/outcome/dispatch shape exactly — no new architectural mechanism. A diagnostics
screen affordance (`screens/diagnostics.rs`) surfaces repairable contacts and triggers repair, entirely
inside the pre-existing `ExtensionPane`-delegated `handle_key`/`handle_worker` functions — zero
`App::handle_worker` core-routing edits, so Definition of Done gate 9 is satisfied intrinsically.

**Eligibility gate:** only `trust.bin` contacts with `hint == ""` (the marker `run_accept_request` stamps
on accept-created contacts) are ever repair-candidates. Verified sound: `validate_hint` rejects an empty
hint, so every `AddContactRequest.hint` is provably non-empty, and `TrustStore::observe`/
`observe_key_change` only overwrite `contact.hint` `if !hint.is_empty()` — a real contact's hint can never
be reset to `""` later.

**Repair-vs-tombstone predicate:** `history.jsonl` emptiness, not `contacts.json` row presence, is the
signal. `DeleteContactRequest` only ever removes the `contacts.json` row (never `trust.bin`/
`history.jsonl`), so this direction is sound — the repair path can never resurrect a genuinely deleted
contact, independently confirmed by review via static trace of `run_accept_request`'s write ordering and
`run_delete_contact`'s scope, and by `test-engineer`'s mutation test (loosening the guard broke exactly
one test, the tombstone-resurrection one). The **converse** is not exhaustive — an un-repaired,
genuinely-missing-row contact can still receive further inbound messages before repair runs (inbound
`Text` delivery persists to `history.jsonl` unconditionally once a session exists, gated only on
`sessions.bin`), which flips `history_empty` to `false` while the row is still legitimately missing. This
is a **false-negative** (an over-cautious refusal of a genuine repair candidate), not a safety-property
violation — it fails safe in the direction that matters. Found by the `reviewer` pass; closed by
rewording the refusal (no longer asserts "explicitly deleted" as fact — names both possibilities
honestly) and expanding the module doc comment to name this as a second, explicit ambiguity alongside the
pre-existing Receipt-vs-lost-intro one. **The gating logic itself was not changed** — only the
message/docs, per the review's own "not blocking" verdict.

**Recovery:** the `contacts.json` row is fully recoverable (rebuilt via the existing
`upsert_contact_record`, a pure mirror of the `trust.bin` record). The `history.jsonl` intro is not
recoverable — the original `MessageRequest` is consumed the moment `chat.accept_request` first runs — so
an honest placeholder entry is appended instead, mirroring `screens/requests.rs::intro_summary`'s
existing "(not a text message — a delivery receipt)" convention.

**Every guard is re-derived independently** inside `run_repair_accepted_contact` (reloads `trust`,
`contacts_doc`, `history` fresh from disk; only `pubkey` crosses the UI→worker boundary from the scan
result) — confirmed by review, not just claimed.

### Review round

repair against a healthy contact directly, bypassing the scan filter), and — the crux — independently
mutation-tested the tombstone-resurrection guard and the `hint == ""` eligibility gate, confirming each
breaks exactly the test meant to catch it.
