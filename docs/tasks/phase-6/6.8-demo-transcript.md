# 6.8 demo transcript — two-party CLI chat + wire-byte envelope-v2 proof

Two independent pieces of evidence, both against the **real, unmodified `target/debug/meridian`
binary** built from this branch (`cargo build --workspace`, task 6.8's own gate run) and the real
`meridian-rendezvous::serve` server code (in-process, `MemoryStore`, real WebSocket) — the exact
bring-up `apps/cli/tests/chat_demo.rs` uses in CI, just run standalone so the transcript could be
captured to disk. The driver code lived entirely outside the repo (a throwaway scratch crate under
the session's scratchpad, depending on `meridian-proto`/`meridian-envelope`/`meridian-rendezvous`
by absolute path) — nothing from it is checked in, per this codebase's task-4.52 precedent ("nothing
from the driver needs to be checked in — but the transcripts quoted must be real output, not
reconstructed"). Both runs below are that real, unedited output.

## Part 1 — live two-party CLI chat: message round trip + delivery receipts

Real `meridian id new` for two accounts, then two real `meridian chat --json` subprocesses talking
through the in-process rendezvous. This is the T03 demo script's own pattern
([03-e2ee-messaging-relayed.md](../../architecture/features/03-e2ee-messaging-relayed.md)) driven
non-interactively.

receipts — `chat.rs`'s `Receipt`/`"event":"receipt"` flow (auto-sent on every received message, task

**What this proves:**
- Every one of the 67 `Route`/`Deliver` frames the audit's scripted conversation produced (opening
  X3DH messages carrying a `prekey` preamble, the T04 SDP/fingerprint/ICE-marker probe as frame#67 —
  the larger 261-byte `ct`, and steady-state ratchet messages with `prekey_present=false`) decodes
  successfully as a `MessageEnvelope` with `v == 2` — never absent, never `1`.
- `MessageEnvelope::from_blob` is `meridian-envelope`'s real `decode::<MessageEnvelope>` (strict CBOR
  struct decoding, `apps/envelope/src/envelope.rs`), so a successful decode into this type is already
  proof the blob carries exactly the v2 field set: `v`, `sender_pub`, `eid`, `prekey`, `ct` — the type
  has no `sig` field to carry one even if a legacy sender tried to send it, and there is no separate,
  looser decode path in the live code that would accept a `sig`-bearing v1 shape instead (confirmed
  independently by task 6.8's own grep sweep, see the task's Outcome section).
- 0 of 67 envelopes carried any other `v` value — no v1/v2 interop, consistent with ADR 0016 R5's hard
  flag day.
