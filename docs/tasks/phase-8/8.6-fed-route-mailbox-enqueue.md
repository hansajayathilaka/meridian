# 8.6 — `handle_fed_route` mailbox enqueue on offline recipient

**Phase:** 8 — Offline Ciphertext Mailbox · **Feature:** T07 · **Depends on:** 8.1, 8.3, 8.5 · **Status:** done

## Goal
Make a cross-org federated route to an offline recipient queue at the recipient's home server,
instead of silently dropping — closing a real gap in today's code (`handle_fed_route` currently
calls `registry.send_to` and returns `Ok(())` unconditionally, dropping the envelope entirely if
nobody is connected).

## Scope
- **In:** `apps/rendezvous/src/federation/inbound.rs::handle_fed_route`: same TTL/quota-aware
  enqueue logic as 8.5 (share the enqueue helper rather than duplicating it), but the
  success/failure shape differs because `FedRoute` is fire-and-forget: on enqueue success, still
  return `Ok(())` (silent success — matches today's shape, now actually durable instead of a
  silent drop); on quota breach, return `Err(FedErr{code: mailbox_full, ..})` — a legitimate
  exception to "fire-and-forget on success" since federation-protocol-v1.md §2 already says
  "failure is reported only via `FedErr`." Add a new match arm in `ws.rs`'s
  `federated_route_error_reply` mapping fed `mailbox_full` through to a local `Err{mailbox_full}`
  (not squashed into `fed_unreachable`).
- **Out:** no `federation-protocol-v1.md` wire change (settled: `FedRoute`/`FedErr` shapes are
  unchanged, only a new error-code string and new server-side behavior on an existing `Ok(())`
  path) — do not add a `FedRouteOk`, that decision stays closed. Recording the sender-visible
  consequence (A's `RouteOk` to Alice stays optimistic `{delivered:true, queued:false}` even when B
  queued rather than delivered live) is this task's doc-sync responsibility, not a wire change.

## Deliverables
1. `handle_fed_route`'s enqueue-on-offline logic + `mailbox_full` `FedErr` path.
2. `federated_route_error_reply`'s new `mailbox_full` match arm (`ws.rs`).
3. Tests: federated route to an offline recipient at B enqueues in B's store and A still gets
   `RouteOk{delivered:true}` (the accepted optimistic-success residual, tested and documented, not
   just asserted); federated route when B's mailbox is full for that recipient → A gets
   `Err{mailbox_full}` end-to-end.
4. `docs/api/federation-protocol-v1.md` §2/§4 updated: note that an offline recipient is now a
   *durable* queue at B rather than a silent drop, and that this doesn't change the wire shape or
   reopen "no `FedRouteOk`" — cite this phase's architect consult.

## Risks / notes
This task closes a genuine pre-existing correctness gap (silent message loss on a federated route
to an offline recipient) as a side effect of building the mailbox — call this out explicitly in the
task's Outcome, since it's a real behavior change beyond "add the mailbox," not just plumbing.
Confirm `route_foreign`'s `ROUTE_REPLY_GRACE`-based inference (task 3.20) still behaves sensibly
once B might reply late with a genuine `FedErr{mailbox_full}` instead of nothing — a full mailbox at
B should not be silently swallowed into the existing "no reply within the grace window ⇒ assume
success" inference; confirm `FedErr` always beats the grace-window timeout regardless of code.

## Status
**Done.** Closes a genuine pre-existing correctness gap: `handle_fed_route` used to call
`registry.send_to` and return `Ok(())` unconditionally, silently dropping the envelope forever if
the recipient was offline. Now, `send_to == false` falls through to the same TTL/quota-aware
enqueue logic 8.5 built for the local route path — extracted into a new shared
`store::mailbox_enqueue_with_quota` helper (`MailboxEnqueueOutcome` + `MAILBOX_QUOTA_BYTES_PER_MB`)
so the quota math lives in exactly one place; `ws.rs::queue_to_mailbox` (8.5) was refactored to
call it too rather than keep its own duplicate copy. `ttl_days == 0` at B still silently drops
(unchanged pre-8.6 behavior — mailbox genuinely disabled, no wire-visible signal for it). On
enqueue success, still `Ok(())` — fire-and-forget stays intact, no `FedRouteOk`, ever. On quota
breach, `Err(FedErr{code: mailbox_full})` — a legitimate, documented exception to fire-and-forget.
A new `ws::federated_route_error_reply` match arm maps `fed_error_codes::MAILBOX_FULL` through to
the same client-visible `error_codes::MAILBOX_FULL` the local route path (8.5) already produces.

Since `route_foreign`'s own `reachable_foreign` pre-check gates the entire target-liveness axis
before a real `FedRoute` is ever sent, `handle_fed_route`'s offline branch is not reachable through
the real A-to-B wire path in a deterministic test — only through a narrow, unconstructable
pre-check/delivery disconnect race. Two new tests in `federation_route.rs` call `handle_fed_route`
directly with a hand-built `FedRoute`, mirroring the exact precedent already set by
`bs_defense_in_depth_oversized_check_rejects_directly` in the same file: one proves
enqueue-success + `Ok(())` + a row appears in B's store (the "A still gets `RouteOk{delivered:true}`"
claim, since that mapping in `handle_federated_route` is pre-existing/unconditional/untouched by
this task); the other proves quota-exceeded + `Err{mailbox_full}` + no row created. A third,
in-crate `#[cfg(test)]` unit test in `ws.rs` directly proves the `federated_route_error_reply`
mapping, for the same underlying reachability reason. `handle_fed_route`'s own doc comment and
`docs/api/federation-protocol-v1.md` §2/§4 were updated to describe the new behavior — including
the sender-visible optimism gap (a federated sender never learns whether B delivered live or
queued) as a documented widening of the already-accepted `ROUTE_REPLY_GRACE` false-positive
residual, not a new one, per the phase-8 architect consult's point 2.
