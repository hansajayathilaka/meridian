# 12.7 — Core messaging screens: chat + contacts + message-requests

**Phase:** 12 — Browser & Desktop Clients · **Feature:** T11 · **Depends on:** 12.2 · **Status:** done

**User surface:** this task **is** a client surface (browser + desktop, once wired by 12.14/12.15) — the
new-platform equivalent of the terminal client's existing chat/contacts/message-request screens (Phase
4, tasks 4.19–4.21). No TUI surface applies to *this* task: those TUI screens already exist and are
unaffected; T11 adds a second and third rendering of the same already-shipped capability, not a new one
(see [phase-12/README.md](./README.md#architect-consult-substratestoresigning-decisions-settled-before-task-breakdown)
point 5).

## Goal
Build the account-creation, contact-list, 1:1 chat send/receive, and first-contact message-request
accept/reject screens as Svelte components against `MeridianClientAdapter` (task 12.2), tested against
its fake implementation — reusable unmodified by both the browser (12.14) and desktop (12.15) shells.

## Scope
- **In:** account creation flow; contact list + add-contact; 1:1 chat view (send/receive, transcript);
  the message-request queue/accept/reject gate — T08's existing state machine surfaced in the UI, no new
  protocol logic. Bundled as one task because the message-request queue is a visible state *within* the
  chat/contacts view, not an independent screen — the same "forced, tightly-coupled" reasoning Phase 4
  used to bundle T08+T17 rather than split them.
- **Out:** verification/safety-number UI (12.8); file-transfer UI (12.9); wiring to a real backend
  adapter (that's the app-shell tasks 12.14/12.15 — this task only wires the *fake* adapter for its own
  tests); any new core-level operation beyond what 12.2's interface already exposes.

## Deliverables
1. `shared-ui/src/screens/Chat.svelte`, `Contacts.svelte`, `MessageRequests.svelte` + their view-model
   stores.
2. Component tests against `FakeMeridianClientAdapter` covering: create account, add contact, send/
   receive a chat message, accept/reject a message request.

## Risks / notes
Trust-state UI must honor the block-on-verified invariant (system-design.md §4.4/D06) even before the
real verification screen (12.8) lands in the same phase — do not let this task's chat view silently
allow sending to an unverified-and-blocked contact; surface the existing `TrustState` from
`core-api-contracts.md` faithfully.

## Tests
`pnpm --filter shared-ui test`.

## Reviews
**code-reviewer**; **security-reviewer** (block-on-verified/trust-state UI must honor the D06 invariant).

## Outcome
Shipped four Svelte screens under `shared-ui/src/screens/`: `Chat`, `Contacts`, `MessageRequests`, and
`CreateAccount` (the account-creation-flow deliverable, resolved as a fourth small dedicated screen —
mirroring the TUI's own unlock-before-contacts ordering — since the task's Scope→In prose names it even
though the literal Deliverables list only enumerates the first three), each with a thin view-model store
(`stores/{chat,contacts,messageRequests,account}Store.ts`) driving it against `MeridianClientAdapter`.
D06 (block-on-verified) is enforced in three independent layers: the composer is disabled whenever
`sendGate.kind !== "ok"`, `chatStore.send()` re-reads `sendGateState(peer)` immediately before calling
`sendChat` rather than trusting the last-rendered value, and `FakeMeridianClientAdapter.sendChat` itself
independently recomputes the gate — proven by a regression test that blocks a contact *after* the screen
already rendered an "ok" gate (simulating a cross-tab block) and confirms the stale-render path is still
caught by the pre-send re-check. The `listMessageRequests` gap (no bulk enumeration method on
`MeridianClientAdapter`, only a live `onMessageRequest` subscription) was found and deliberately not
worked around by extending 12.2's owned adapter files — documented in-code instead, with the honest
limitation that only requests received while the screen is mounted are shown.

The combined review (code-reviewer + security-reviewer) returned **PASS** on both lenses, zero blocking
findings, after independently re-running the full suite (52/52 — 32 pre-existing + 20 new — `tsc`,
`svelte-check` all clean) and tracing the stale-render regression test line-by-line to confirm the catch
is genuinely due to the independent re-check, not incidental. The `vitest.config.ts`
`resolve.conditions: ["browser"]` fix (needed because vite-plugin-svelte compiles components in SSR mode
under Node even with `environment: "jsdom"` set, silently turning `onMount` into a no-op) was confirmed
load-bearing, not a red flag — `Contacts.svelte`'s initial `listConversations()` load depends on it.
