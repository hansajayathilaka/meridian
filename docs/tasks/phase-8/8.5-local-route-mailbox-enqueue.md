# 8.5 — `handle_route` local mailbox enqueue (TTL/quota-aware)

**Phase:** 8 — Offline Ciphertext Mailbox · **Feature:** T07 · **Depends on:** 8.1, 8.3 · **Status:** done

## Goal
Make a same-server `Route` to an offline recipient actually queue, instead of failing — the core
behavior change T07 exists to make.

## Scope
- **In:** `apps/rendezvous/src/ws.rs::handle_route`'s not-connected branch (currently always
  `Err{not_connected}`): if `config.mailbox.ttl_days == 0`, keep today's `Err{not_connected}`
  unchanged (TTL=0 = pure-P2P, genuinely disabled); else attempt `Store::mailbox_enqueue`
  (recipient, blob, `expires_at = now + ttl_days`) — on success reply `RouteOk{delivered:false,
  queued:true}`; on quota breach reply `Err{mailbox_full}` (never a `RouteOk`).
- **Out:** federated route path (8.6 — same logic, different function, reviewed separately since
  the federated failure-reporting shape differs); delivery-on-reconnect (8.7); the
  `allow_test_route_*` tamper-hook interactions (`test-tamper-hook` feature) — confirm they still
  compile and behave sanely with the new branch, but no new tamper mode is in scope here.

## Deliverables
1. `handle_route`'s not-connected branch rewritten per Scope above.
2. Tests: offline + `ttl_days>0` + under quota → `RouteOk{queued:true}` and a row appears in the
   store; offline + `ttl_days==0` → unchanged `Err{not_connected}`, no row created; offline + over
   quota → `Err{mailbox_full}`, no row created (or the oldest/rejected row per whatever eviction
   policy the store enforces — confirm 8.1 rejects rather than evicts, since the feature spec says
   "quota exceeded" surfaces as an error, not silent eviction).
3. `docs/api/rendezvous-protocol-v1.md` §4 updated: the "an offline recipient is `not_connected`"
   line corrected to describe the new queued/mailbox_full outcomes, TTL=0 exception noted.

## Risks / notes
Don't let this branch double-count against `envelopes_routed_total` (that metric means "delivered
live," per task 3.8's own precedent) — a queued envelope is a distinct outcome, not a delivery;
confirm with 3.8's task file if a new mailbox-specific metric belongs on the allowlist here or is
out of scope for this task (if so, flag it as a carry-forward rather than inventing one silently).

## Status
**Done.** `handle_route`'s not-connected branch now takes three outcomes: `ttl_days == 0` stays the
unchanged pre-T07 `Err{not_connected}`; offline + `ttl_days > 0` + under quota enqueues via 8.1's
`Store::mailbox_enqueue` and replies `RouteOk{delivered:false, queued:true}`; over quota replies
`Err{mailbox_full}` (never a `RouteOk`), no row created. Quota is checked via
`mailbox_size_bytes_for_recipient` before enqueueing (8.1's store doesn't enforce it itself). `MB`
is interpreted as binary MiB (no design doc pins this down; documented as a disambiguation, not an
invented requirement, consistent with the codebase's one other size precedent — 7.5's KiB chunking).
`envelopes_routed_total` is not incremented for a queued (non-live) outcome, per task 3.8's
"delivered live only" precedent — confirmed the metric call lives solely inside `deliver_one`.

A pre-existing test (`route_to_offline_peer_errors`) was renamed to
`route_to_offline_peer_errors_when_mailbox_disabled` and now sets `ttl_days = 0` explicitly, since
the config default (`ttl_days = 14`) means an offline route now queues by default rather than
erroring — a legitimate adaptation to the new default, not a coverage loss (it still asserts the
true not_connected path and zero rows created). Two new tests cover the queuing-success and
over-quota-rejection outcomes, asserting both the wire reply and store row presence/absence via a
new `spawn_with_store` test helper. `docs/api/rendezvous-protocol-v1.md` §4/§8 updated to describe
the three-way outcome, replacing stale "not_connected, mailbox is T07" language.

### Review round
**reviewer** (security-reviewer + architect + code-reviewer lenses) — **PASS** on all three, zero
blocking findings. Independently re-ran the full test suite, the `test-tamper-hook` build, clippy,
and fmt rather than trusting the implementer's report. Confirmed exact conformance to the phase-8
architect consult's points 4/5, the already-shipped 8.3 wire shapes, and the non-double-counting
metric invariant.

One should-fix, **not blocking**, no task in this phase currently owns it — recorded as a live
carry-forward in [docs/tasks/README.md](../README.md): the quota check
(`mailbox_size_bytes_for_recipient` then `mailbox_enqueue`) is read-then-write across two
unserialized store calls, so two connections routing to the same offline recipient concurrently can
both pass the quota check and both insert, overrunning `quota_mb` by a bounded amount (roughly one
extra envelope per concurrent racer, not unbounded). One optional nit (also not blocking):
`body.blob.0` is cloned unconditionally on every `Route`, even when the recipient is live and the
clone goes unused — a minor always-pay allocation, not a correctness issue.
