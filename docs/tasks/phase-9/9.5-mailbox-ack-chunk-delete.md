# 9.5 — Chunk `MailboxAck` delete into sub-999-parameter batches

**Phase:** 9 — Review of Phase 8 · **Feature:** review fix (F2) · **Depends on:** — · **Status:** done

**User surface:** none — server-internal SQL-batching defense-in-depth fix; no client-visible behavior
change (Definition of Done gate 9).

## Goal
Close two related gaps in `MAILBOX_ACK_MAX_IDS` handling (`apps/rendezvous/src/ws.rs:220-267`): the
4096-id truncation-with-silent-`MailboxAckOk{}` path has zero test coverage, and a full 4096-id batch
plus the recipient bind is 4097 bound SQL parameters — which would itself error on a SQLite build
compiled with the older `SQLITE_MAX_VARIABLE_NUMBER = 999` default, defeating the cap's purpose.

## Scope
- **In:** `handle_mailbox_ack`'s delete path — chunk the `DELETE` into sub-999-bound-parameter batches
  (accounting for the recipient bind alongside the id list) so it cannot exceed SQLite's conservative
  compiled variable limit regardless of build configuration. Add a test proving an id past the
  `MAILBOX_ACK_MAX_IDS` cap survives (is not deleted) and the client still receives `MailboxAckOk{}`
  with no error signal, matching the already-documented "fails safe" behavior.
- **Out:** Do not change the 4096-id cap itself, the "no client-visible signal for a truncated batch"
  behavior, or add a row-count quota (that's the `docs/tasks/README.md` carry-forward candidate list for
  8.8/8.9-adjacent work, not this task — this task only makes the existing cap/truncation actually safe
  and tested, not redesign it).

## Deliverables
1. `handle_mailbox_ack`'s delete chunks into batches safely under 999 bound parameters per batch.
2. A test sending a >4096-id `MailboxAck` including one real, currently-queued id past the cap boundary,
   asserting: `MailboxAckOk{}` is returned, and the real row past the truncation boundary is *not*
   deleted (survives for the next reconnect's drain).

## Risks / notes
Same file as 9.1/9.4 (`ws.rs`) but a disjoint function (`handle_mailbox_ack` vs `handle_route`/connection
setup) — no hard ordering dependency, sequenced here simply to finish the `ws.rs`-touching tasks in one
pass.

## Tests
`cargo nextest run -p meridian-rendezvous`, `cargo clippy -p meridian-rendezvous --all-targets --features sqlite -- -D warnings`.

## Reviews
**code-reviewer** (SQL parameter-chunking correctness), **test-engineer** (the truncation-boundary test
is the acceptance proof).

## Outcome
`SqliteStore::mailbox_delete_by_ids` now chunks into batches of `MAILBOX_DELETE_MAX_IDS_PER_BATCH = 900`
(900 ids + 1 recipient bind = 901, under SQLite's conservative `SQLITE_MAX_VARIABLE_NUMBER = 999`
default), issuing one DELETE per chunk and summing `rows_affected()`. `MemoryStore` untouched
(`Vec::retain` has no bound-parameter limit). code-reviewer + test-engineer both PASS, zero blocking
findings.

Two non-blocking items surfaced, not folded in:
- **Should-fix (code-reviewer):** each chunk's DELETE autocommits independently — no transaction wraps
  the whole batch, so a mid-batch failure leaves earlier chunks' rows already deleted while the client
  sees a bare error, not partial success. Benign given `mailbox_delete_by_ids`'s existing idempotent
  "id naming an already-deleted row is a silent no-op" contract (a client retry re-acks safely), but
  worth a doc note or follow-up if cross-chunk atomicity is ever assumed elsewhere.
- **Coverage gap (test-engineer):** this sandbox's bundled SQLite (`libsqlite3-sys`, ≥3.32.0) defaults
  `SQLITE_MAX_VARIABLE_NUMBER` to 32766, not the old 999 — confirmed empirically by disabling chunking
  entirely (raising the batch size to 10,000) and observing the new full-cap test still pass. Neither
  new test can currently prove chunking is load-bearing IN THIS ENVIRONMENT; the fix remains correct
  defensive practice for any deployment linking an older/stricter SQLite (e.g. some Linux
  system-`libsqlite3` packages still ship 999), matching the task's own reasoning for why the fix exists
  regardless of what any one build enforces. Closing this fully would need a test asserting the
  chunk-boundary math itself (e.g. instrumenting/counting statements issued, independent of whether the
  linked SQLite would reject an unchunked one) — flagged for whoever next touches this function, not
  scoped into this task.
