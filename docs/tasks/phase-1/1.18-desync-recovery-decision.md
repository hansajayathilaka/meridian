## Status
**Done.** **architect** scope call: **defer** receiver-side auto-recovery; document the spec'd
behaviour; follow-up owned by **Feature 08**.

### Why deferred (not a scheduling preference — a dependency-order blocker)
The spec's wording had been misread. The *safe* half already works: the peer that **knows** it lost
state has no session, so it fetches a bundle and re-initiates X3DH — that is implemented
(`start_initiator_session`) and the counterpart accepts it as an ordinary prekey message. The
dangerous half — a receiver reacting to *undecryptable traffic* by tearing down a healthy session —
was never specified, and would hand an active attacker (A2) three things: a PCS-rollback /
skipped-key-destruction oracle, forced OTK consumption feeding the prekey-depletion channel, and a
forced re-key at a moment of the attacker's choosing — where the re-handshake's bundle fetch is
exactly where a malicious server substitutes a key. Since goal 2's "verified ⇒ fails closed" half is
already deferred to Feature 08, building the automatic re-key path first **inverts the dependency
order**.

### Landed
- `docs/api/messaging-envelope-v1.md` §3 — the desync bullet rewritten: rejection leaves the
  receiving session **untouched**; recovery is driven only by the peer that knows it lost state; a
  healthy peer needs user/operator action; receiver-side renegotiation is deferred, with the reason.
- `docs/architecture/system-design.md` §10 — the failure-mode entry no longer promises "automatic
  re-handshake via fresh X3DH with a user-visible notice" as if shipped.
- `docs/architecture/features/03-e2ee-messaging-relayed.md` — a "Desync-recovery scope" note in the
  same honest style as the existing F9 note, so deliverable 1 is not read as met.
- `docs/architecture/features/08-verification-trust.md` — receiver-side desync detection → guarded
  fresh-X3DH re-handshake added to Scope "In:", with why it cannot precede block-on-key-change.

### Two cheap in-scope code items (fixes, not features)
- **`ChatError::Desync`** (`apps/core/src/chat.rs`) — `CryptoError::UndecryptableHeader` now
  classifies distinguishably instead of collapsing into `ChatError::Crypto`, so desync is
  *diagnosable*. This changes **no rejection decision** (the envelope is dropped either way), which is
  why it does not violate this task's "Out: changing the fail-closed error paths that already exist".
  The variant's doc comment states that callers MUST NOT treat it as a reset/re-key trigger.
- **Regression test** `undecryptable_envelope_is_rejected_without_touching_the_session`
  (`apps/core/tests/chat_manager.rs`): builds a live session, holds a message back so a
  **skipped-message key** is retained, then feeds an *authentic* (re-signed as the real sender)
  envelope whose ratchet header opens under neither header key. Asserts it classifies as `Desync`,
  that the whole `ChatState` is **byte-identical** before and after (deterministic CBOR — `seal_at_rest`
  is unusable for this, its AEAD nonce is random), and that the held-back message still opens from its
  retained skipped key. This is the test that stops a future contributor adding the oracle.
- `ciborium` added to `apps/core` dev-dependencies for the byte-identical comparison.
