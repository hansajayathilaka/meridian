# 10.9 — Resume protocol: in-stream missing-range bitmap + redial integration

**Phase:** 10 — File Transfer Stream · **Feature:** T09 · **Depends on:** 10.7, 10.8 · **Status:** done

**User surface:** none yet — the resume primitives have no CLI/TUI surface of their own; tasks
10.10/10.11 consume them, and 10.11's own TransfersPane stubs a resume affordance pending this task
(now landed).

## Goal
After a session drops mid-transfer and redials (ICE restart, session substrate invariant — ratchets and
now stream-level state outlive the transport), let the receiver tell the sender which byte ranges are
still missing so the sender resumes instead of re-sending the whole file.

## Scope
- **In:** a resume message carrying a missing-range bitmap, sent **in-stream** over `mrd.file/1`'s own
  already-open data channel (via task 10.4's `send_stream_frame`, handled in `FileStream::on_frame`
  itself) — **not** a new `CtrlFrame` variant. `docs/api/wire-protocol.md` §5 documents `Resume = {sid,
  bitmap: bstr}` as a ctrl frame, but `apps/envelope/src/ctrl.rs`'s `CtrlFrame` enum has no such variant
  today, and adding one would force `session.rs::handle_ctrl`'s exhaustive match to grow a
  file-transfer-specific arm — exactly the core-crate leakage task 10.4's review gate exists to reject.
  Resume-in-stream is the reading consistent with the settled substrate design; task 10.12 records the
  wire-protocol.md doc correction. Also: wiring the receiver's redial/session-restart signal (from
  `P2pSession::ice_restart`/session-reestablishment) to trigger sending this resume message once the
  stream is live again.
- **Out:** the sender/receiver engines themselves (10.7/10.8, already landed) — this task only adds the
  resume message schema, its handling, and the redial trigger.

## Deliverables
1. Resume message CBOR schema in `apps/streams` (in the `mrd.file/1` message family, not
   `meridian-proto`/`meridian-envelope`).
2. Sender-side: on receiving a resume message, skip already-acknowledged ranges and only send what's
   missing.
3. Receiver-side: on reconnect, send the current missing-range bitmap before expecting more chunks.
4. A loopback-transport test simulating a mid-transfer disconnect + redial + resume, asserting the
   acceptance criterion: resume never re-sends more than 2% of already-delivered data.

## Outcome
Added `apps/streams/src/resume.rs`: the resume message rides **in-stream** over `mrd.file/1`'s own
data channel, never as a new `CtrlFrame` variant. Every in-stream frame now carries a one-byte
discriminator (`tag: u8 ‖ body: bytes`) — `FRAME_TAG_CHUNK` (`0x00`, body unchanged from 10.7/10.8's
`ChunkFrame`) or `FRAME_TAG_RESUME` (`0x01`, body a new `ResumeRequest{bitmap: Vec<u8>}`, CBOR
`{bitmap: bstr}`, no `sid` field since the channel is already scoped to one transfer).
`ResumeRequest::bitmap` is exactly `ceil(leaf_count/8)` bytes, one bit per chunk index, LSB-first
within each byte, `1`=missing/`0`=received; trailing bits past `leaf_count` are always ignored on
read, never fabricating an out-of-range index (tested adversarially: truncated bitmaps under-report,
never over-report). `sender::send_missing_chunks`/`send_resume_bitmap` do the actual skip-already-
acknowledged resend and bitmap-send; `FileStream::watch_resume(sid)` lets a caller subscribe to
inbound resume frames.

**Redial-wiring gap, found and correctly descoped rather than closed with a core-crate edit**:
`P2pSession::ice_restart()` preserves data channels/ratchet state but emits no `SessionEvent` and
calls into no `StreamType` hook — `StreamType` has only `on_open`/`on_frame`, no `on_reconnect`.
Automatically triggering "receiver sends its resume bitmap once the stream is live again after
redial" would require adding that hook to `meridian-core`, which is out of this task's own
"additive stream type, zero core-crate edits" scope. Instead, `send_resume_bitmap`/`watch_resume` are
exposed as explicit calls an application-level session-lifecycle layer makes itself immediately after
its own `ice_restart()` returns. Filed as a tracked carry-forward (see Live carry-forwards below) —
adding `StreamType::on_reconnect` (or a `SessionEvent::Reconnected` variant) is real follow-up work
for a future `/plan-phase`, not silently absorbed.

Both mandatory review lenses (architect, test-engineer, run as one combined `reviewer` pass) returned
**PASS**. The architect lens explicitly **ratified** the in-stream-not-ctrl-frame design (confirmed
`apps/envelope/src/ctrl.rs`/`apps/core/src/session.rs::handle_ctrl` are byte-for-byte untouched,
confirmed the tag-byte discriminator is sound and minimal) and explicitly judged the redial-wiring gap
correctly descoped within this task's own boundary — conditioned on the carry-forward actually being
filed in the tracker rather than left only as module-doc prose (done, see below). The test-engineer
lens independently confirmed the `≤2%` re-send acceptance test is a real, non-vacuous measurement
(a genuine `ice_restart()`, a real partial delivery, an exact byte-count comparison — the implementer's
0%-resent result is a strictly-stronger-than-required outcome, correctly disclosed as such, not an
inflated claim) and flagged one non-blocking should-fix — the original test only covered a contiguous
missing-chunk prefix/suffix split, not the arbitrary non-contiguous sets `ResumeRequest`/
`send_missing_chunks` are documented to handle — closed in a same-task follow-up commit: a new test
exercising a scattered missing set (`{2,5,9}` out of 13 chunks) asserting the resent index set is
exactly the missing set (not a superset), zero already-delivered bytes are resent, and the reassembled
file is byte-identical. All `meridian-streams` tests (66, everything from 10.1–10.9) green throughout;
clippy/fmt clean; full workspace build clean.
