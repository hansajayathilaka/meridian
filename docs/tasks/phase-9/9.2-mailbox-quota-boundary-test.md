# 9.2 — Quota exact-at-cap boundary test

**Phase:** 9 — Review of Phase 8 · **Feature:** review fix (F6) · **Depends on:** 9.1 · **Status:** in progress

## Goal
Prove `mailbox_enqueue_with_quota`'s exact-at-cap boundary (`current_bytes + blob.len() > quota_bytes`,
a deliberate strict-`>` choice — filling the quota exactly is allowed) behaves as designed. Today this
boundary is entirely untested; the only existing quota tests use `quota_mb = 0`, which only proves the
"obviously over" case.

## Scope
- **In:** a unit test in `apps/rendezvous/src/store.rs`'s `mod tests`, calling
  `mailbox_enqueue_with_quota` directly (not through the `ws.rs`/route-handler layer) with two cases:
  `current_bytes + blob.len() == quota_bytes` → `Queued`; `current_bytes + blob.len() == quota_bytes + 1`
  → `QuotaExceeded`. Run against both `MemoryStore` and `SqliteStore` if the existing test harness
  already parameterizes over both backends (match whatever pattern the surrounding quota tests use).
- **Out:** No production code change — this task is test-only. If 9.1's fix changes
  `mailbox_enqueue_with_quota`'s signature or return type, write this test against the post-9.1 shape.

## Deliverables
1. Two new unit test cases (exact-boundary allow, one-byte-over reject) against
   `mailbox_enqueue_with_quota`, covering both `Store` backends in scope.

## Risks / notes
**Hard dependency on 9.1**: this test targets the exact function 9.1 modifies for locking/serialization.
Land after 9.1 so the test exercises the final, race-fixed behavior rather than needing a rewrite.
