# 4.3 — Trust module + contact store core

**Phase:** 4 — Verification & Trust + Terminal TUI Client · **Feature:** T08 — Verification & Contact Trust · **Depends on:** — · **Status:** done

## Goal
Land the core, client-agnostic trust state machine — `new → pinned (TOFU) → verified`, plus
`blocked` — as a new `meridian-core` module, so every client (CLI now, TUI in this phase, browser/mobile
later) consumes the same state rather than each growing its own.

## Scope
- **In:** new `apps/core/src/trust.rs`: `TrustState` enum (`New | Pinned | Verified | Blocked`),
  `Contact` record (pubkey, id/hint, trust state, pinned-key history with first/last-seen), TOFU-pin on
  first contact, `mark_verified`, sealed-at-rest persistence following `chat.rs`'s `ChatState`
  pattern (via `meridian_crypto::at_rest`). `docs/api/core-api-contracts.md`'s already-specified
  `trust_state`/`mark_verified` surface is the target API — implement to it, don't redesign it.
- **Out:** key-change detection/blocking (4.4); safety-number compare UX (4.5); petnames (4.6);
  message-request wiring (4.7); directory attestation (4.8); desync recovery (4.9). This task is pure
  state + storage, no key-change logic yet.

## Deliverables
1. `apps/core/src/trust.rs`: `TrustState`, `Contact`, `TrustStore` (sealed persistence).
2. Tests: TOFU-pin-on-first-contact, `mark_verified` transition, sealed round-trip.

## Risks / notes
- `apps/core/src/streams.rs`'s `PolicyCtx` doc comment already anticipates this ("Minimal by design in
  T04 (T08 grows the trust surface)") — check whether `PolicyCtx` needs a trust-state accessor once this
  lands, but don't wire it here (that's 4.4).
- No key-change detection here — a contact whose key changes while still `New`/`Pinned` is out of scope
  until 4.4.

## Tests
`cargo nextest run -p meridian-core --test trust_store`

## Reviews
- **reviewer** (combined) — new core module, no wire/crypto change, moderate stakes; the security-
  critical parts (key-change blocking) land in 4.4 with dedicated security-reviewer sign-off.

## TUI surface (Definition of Done gate 9)
None — this task is core-only state/storage with no user-facing behavior of its own. The trust state
this module tracks first becomes visible to a user via 4.5 (safety-number compare UX) and the T17
verification/contact-list screens (4.19, 4.22), which are the tasks that own gate 9 for this surface.
