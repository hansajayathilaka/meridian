# 6.7 — Doc-sync: describe envelope v2 as shipped

**Phase:** 6 — Envelope v2 · **Feature:** ADR 0016 (C4) · **Depends on:** 6.3, 6.4 · **Status:** done

## Goal
Close out C4 and ADR 0016's "Consequences" doc list, now that v2 exists to describe accurately.
Includes corrections outside the ADR's originally-scoped doc set that its own security-review-flagged
architecture consult (this phase's planning pass) found: two `apps/rendezvous` files and one
`apps/core` file carry security-reasoning prose that goes stale, and in one case actively misleading,
the moment the signature disappears.

## Scope
- **In:**
  - `docs/security/threat-model.md` (goal 4 + §1.3 — v2 now meets weak/Signal-grade deniability,
    single-hop, per R4's precise scope — not more).
  - `docs/security/threat-mitigation-matrix.md` (A2 row + the "moot for envelope v1... not deniable at
    all" line).
  - `docs/architecture/system-design.md` (§4.3, §7.1, limitation 7).
  - `docs/api/messaging-envelope-v1.md` §4 rewritten to the v2 shape (no `sig`, `v: 2`, `eid`); §2/§3's
    AAD description updated to the canonical C3 formula; the versioning note updated from "v2 already
    decided... implementation deferred" to "shipped."
  - `docs/api/wire-protocol.md` §3 — same envelope-shape reconciliation; mark the two "known
    deviations" (missing `v`, missing `eid`) as closed.
  - `.claude/skills/crypto-protocols/SKILL.md` rule 4 — narrow "check the identity signature on an
    envelope before touching its payload" to what's still true: bundle-signature verification remains
    load-bearing (X3DH, threat-model goal 2). Do **not** blanket-delete the "verify before decrypt"
    principle — it still holds for bundles and device records, only the per-message envelope signature
    is gone.
  - `.claude/skills/api-contracts/SKILL.md`, `.claude/skills/webrtc-nat-traversal/SKILL.md`,
    `apps/CLAUDE.md`, `apps/rendezvous/CLAUDE.md` — check each for envelope-signature-specific language
    (the ADR names all four) and correct without weakening the still-true bundle-signature rule.
  - **`apps/rendezvous/src/route_tamper.rs`** (module doc): currently asserts "`MessageEnvelope` has
    four fields and its signing input covers `sender_pub + prekey + ct`... every byte is either signed
    or is the signature" — this v1-specific "impossibility" argument is gone under v2 (there is no
    `sig` field, no separate signature-verify step). Correct to describe the new AEAD-based reasoning.
  - **`apps/rendezvous/src/auth.rs`** (`rewrite_routed_blob` doc): same stale argument, same fix.
  - **`apps/core/src/session.rs`** (`ANSWER_TIMEOUT` doc, ~line 89–92): currently describes a hostile
    relay's rewrite-and-drop as "an OTK-depletion amplifier" — 6.3's commit-on-successful-decrypt fix
    makes OTK consumption conditional on decrypt success, which improves this specific residual. Update
    the note to describe the improvement, not just leave the old claim standing.
  - **`apps/cli/tests/relay_attacks.rs`** (comment near line 5): same stale "stopped at the signature
    check" claim as `route_tamper.rs`, in a test-file comment rather than a spec doc.
- **Out:** code changes (6.3, 6.4, 6.6 own those); roadmap/tracker unblock (6.8's job).

## Deliverables
All doc/comment edits listed above.

## Risks / notes
- **Overcorrecting rule 4 into "signatures don't matter" would be a real regression** — bundle
  signatures, device records, and rendezvous auth signatures are all untouched by ADR 0016 and remain
  load-bearing. The edit must narrow, not remove, the rule.
- **Do not overclaim v2's deniability beyond R4's stated scope**: single-hop only; participation is
  still non-deniable (prekey-bundle signatures, rendezvous auth signature, device records); the
  federated case is one hop further per ADR 0017 and is *not* fully resolved by this ADR alone.
- These doc/comment corrections were surfaced by this phase's own architecture-review pass, not by the
  original ADR text — a reviewer re-reading ADR 0016 alone would miss the `apps/rendezvous` and
  `apps/core/src/session.rs` sites; don't drop them from scope on that basis.
