# 3.5 — Stop the reachability pre-check from double-spending route budgets

**Phase:** 3 — Review of Phase 2 · **Feature:** review fix (F4) · **Depends on:** 3.4 · **Status:** done

## Goal
One federated message must cost one route unit and one per-account unit, not two — ordinary
cross-org chat currently throttles at ~30 msg/min (≈1 message per 2 s).

## Scope
- **In:** exempt 2.8's internal reachability pre-check from `check_route` (preferred — it is not a
  client-driven op) **or** re-ratify the defaults ×2; re-derive `federation_abuse.rs`'s budget
  arithmetic; correct the stale 2.6 rationale comment at `config.rs:280`.
- **Out:** changing the limiter data structure; 3.7's single-dial change (which does not fix the
  accounting on its own).

## Deliverables
1. `apps/rendezvous/src/federation/{outbound,inbound}.rs` — the accounting change.
2. `apps/rendezvous/src/config.rs` — doc comments stating the **true** per-message cost.
3. New cases in `apps/rendezvous/tests/federation_abuse.rs` — N sustained cross-org messages under
   the documented budget all succeed; the documented org-wide route throughput is actually
   achievable; per-account counters bump once per message.

## Risks / notes
- The exemption must not be reachable by any client-driven op — otherwise it becomes a free
  rate-limit bypass, inverting the fix.
- This changes what ADR 0017 C5's per-account axis actually meters; architect must ratify rather
  than have it assumed.

## Outcome
Took the **preferred** Scope option: `handle_fed_reachability` no longer calls `check_route`.
`handle_fed_route` is now the sole caller of `check_route` (keyed on the real sender, `req.from`),
so one logical routed message costs exactly one `route_per_origin` unit and one
`per_origin_account` unit. The original bug was actually two distinct defects, not one: the
org-wide `route_per_origin` budget really was spent twice per message (as the Goal describes), but
the `per_origin_account` axis was worse than "double-spent on the same account" — the pre-check's
account charge was keyed on `req.target` (the **recipient**), a different key than
`handle_fed_route`'s `req.from` (the **sender**), so a recipient's inbound capacity from an origin
was capped *in aggregate across every sender addressing them*, not per sender.

**Three review rounds, all closed:**
1. Combined `reviewer` pass (architect + security-reviewer + code-reviewer, per this task's own
   required Reviews) found the double-spend fix correct, but ruled the exemption **not** an
   acceptable residual as first implemented: `FedOp::Reachability` is task 2.8's own independent
   wire op, indistinguishable on the wire from `route_foreign`'s internal pre-check, so removing
   `check_route` from `handle_fed_reachability` made reachability probing **completely unmetered
   for any federated peer** — contradicting `docs/architecture/system-design.md` §3.5 and
   `docs/api/wire-protocol.md` §4's documented "rate-limits per requesting server and per
   requesting account" guarantee, and reopening a presence-enumeration / global-link-budget
   exhaustion surface only loosely bounded by task 3.2's (global, not per-peer) connection caps.
   Architect ruled ADR 0017 C5 itself is **not** contradicted (arguably clarified — C5's text
   already scoped "origin account" to `FedRoute.from` specifically).
2. Fixed by giving `FedOp::Reachability` its own dedicated `reachability_per_origin` limiter
   dimension (keyed on `origin_domain` alone, no account axis — mirrors how `check_fetch` already
   reads `FedFetchBundle`'s identical "no requester-account field" shape), rather than either zero
   metering or reusing `route_per_origin`. Explicit scope growth beyond this task's original two
   named alternatives (exempt vs. re-ratify ×2) — flagged as such via `TODO: confirm` on the new
   `federation.fed_reachability_per_origin_per_min` config knob. Re-review verified this closes the
   security gap: wired end-to-end through `serve_link`'s real dispatch path, genuinely independent
   `RateLimiter` instance, non-vacuous test confirmed by mutation (stubbing out the check and
   watching the new test fail). `system-design.md`/`wire-protocol.md` were left unedited after
   re-review confirmed the fix makes the codebase's behavior *more* consistent with those docs'
   existing claims, not less (both docs already describe the federation API in aggregate, not
   op-by-op, so `fed_reachability` regaining a per-server-if-not-per-account axis doesn't newly
   contradict either).
3. That same re-review round found the fix's own chosen default (300) introduced a **new**
   correctness bug: `route_foreign`'s reachability pre-check is mandatory and uncached (spent once
   per real routed message, no subscription/caching), so with reachability's default (300) below
   `fed_route_per_origin_per_min`'s default (600), real achievable throughput was capped at
   `min(600,300)=300`/min — reintroducing this task's own "halved throughput" symptom via a new
   mechanism, and leaving Deliverable 3 unmet at the shipped defaults. The existing throughput
   regression test didn't catch this because it scaled only the route side down (20) while leaving
   reachability at its full 300 default, hiding the coupling. Fixed by raising
   `fed_reachability_per_origin_per_min`'s default to 600 (equal to route's — the minimum the
   coupling allows) and adding fail-closed cross-field validation in `Federation::validate()`
   rejecting `reachability < route`, so an operator who lowers one without the other gets a clear
   startup error rather than a silent throughput cap. The throughput test now derives its
   scaled-down budgets from `Federation::default()`'s real ratio between the two limits rather than
   an independently-chosen pairing, so a regression of this exact bug would shrink the test's
   derived reachability budget below its route budget too, and fail. A final targeted re-review
   found one remaining stale value (the shared test harness's `FederatedPairOpts::default()` still
   paired reachability=300 with route=600, since `boot_federated_pair` builds a `Federation`
   directly and bypasses `Federation::validate()`) — fixed in a follow-up commit.

**Per-message cost, post-fix:** one `route_per_origin` unit + one `per_origin_account` unit (keyed
on the real sender) for the real `FedRoute` delivery; one `reachability_per_origin` unit (keyed on
origin domain alone, independent dimension) for the mandatory pre-check — never coupled to route's
budget as long as `fed_reachability_per_origin_per_min >= fed_route_per_origin_per_min`, now
enforced fail-closed at config-load time.
