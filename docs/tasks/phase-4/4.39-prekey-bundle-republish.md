# 4.39 — Prekey bundle republish + vault persistence on session start

**Phase:** 4 — Verification & Trust + Terminal TUI Client · **Feature:** T17 — Terminal TUI Client (gap closure, fix for 4.38's Defect A) · **Depends on:** 4.29, 4.35, 4.37 · **Status:** implemented, pending review

## Goal
Every T17 session, of either account type, republishes a fresh prekey bundle and persists its secret
scalars into `sessions.bin`'s `PrekeyVault` once per session start, so a peer's first-contact message can
actually be decrypted — closing the more fundamental of the two defects task 4.38 found live (`no code
path in meridian-tui ever republishes a prekey bundle with vault-persisted secrets`).

## Scope
- **In:** a new async step, wired into `apps/tui/src/lib.rs::run_worker`'s existing `inbound_handoff`
  branch, executed exactly once per session (the existing `inbound_started` one-shot guard already
  covers this), immediately before `tokio::spawn(worker::run_inbound_loop(...))`: connect a
  `SignalingClient` using `handoff.store`/`handoff.handle` (both already derived there for both account
  types), call `publish_bundle`, then load-mutate(`chat.vault.set_bundle(...)`)-save (`save_chat`)
  `sessions.bin` under the existing `chat_state_lock()` — mirroring `apps/cli/src/chat.rs::run`'s exact
  connect→publish→vault-persist→save sequence, not inventing a new one. Flip
  `apps/tui/tests/live_session_e2e.rs`'s `LIVE_E2E_RUN` opt-in gate to always-on (that test's own module
  doc names this as exactly the follow-up obligation that removes the gate).
- **Out:** task 4.40's defect (file-backed accounts failing closed on contacts/trust/send); onboarding's
  own original `handle_publish_bundle` (`apps/tui/src/screens/onboarding.rs`) — left as-is, its bundle is
  harmlessly superseded moments later by this task's republish, exactly mirroring how the CLI's own
  `cmd_register` gap is harmless because `chat.rs::run` republishes immediately after; any bundle-lifecycle
  or OTK-exhaustion policy change; any new `Effect`/wire type.

## Deliverables
1. A new, named async function performing connect → publish → vault-persist (site: `apps/tui/src/worker.rs`
   or `lib.rs`, implementer's call — document the choice).
2. Wiring into `run_worker`'s existing one-shot `inbound_handoff` branch.
3. `LIVE_E2E_RUN` gate removed from `apps/tui/tests/live_session_e2e.rs`; the test passes unconditionally
   under plain `cargo test -p meridian-tui --test live_session_e2e`, with its assertions unweakened.
4. New narrow tests at the `worker::dispatch`/`inbound_handoff` boundary (mirroring 4.30–4.35's own
   pattern): the republished secrets are actually resolvable by `ChatState::open_inbound`; the republish
   fires exactly once per session, not re-triggered by a later, unrelated effect dispatch.
5. `tui-client.md` §11's findings language and `docs/tasks/phase-4/README.md`'s T17 exit-criteria bullet
   updated to state Defect A is closed and Defect B (→ 4.40) is what remains — the exit-criteria checkbox
   itself stays unflipped (that's 4.41's job, once both defects are closed and re-verified).

## Risks / notes
- 4.35's own Status section already named this exact gap and pre-approved the shape ("a later republish
  mechanism, out of scope here... not a regression: `run_inbound_loop` was never scoped to own bundle
  publishing") — this task is an application of that already-approved design, not a new architectural
  stance. The `reviewer`/architect lens should confirm this reading, not re-litigate 4.35's own
  persistent-connection lifecycle decision from scratch.
- `inbound_handoff` is currently synchronous and documented as "never a new round trip" — keep it that
  way; add the republish as its own new, separately-testable async function called from `run_worker`
  rather than folding it into `inbound_handoff` and making that function's contract do double duty.
- `TODO: confirm` is expected and acceptable for republish-failure UX (no design doc specifies whether a
  failed republish should be a visible status vs. log-only-and-still-listen) — use judgment, document the
  choice made, don't invent a new screen/effect to resolve it.
- Both account types are covered by construction, since `inbound_handoff` already independently derives a
  working `(store, handle, account_pub, server)` for both OS-keystore and file-backed accounts at exactly
  this point.

## Status
Done. Reviewed and closed — see the review outcome below.

**Site chosen:** `apps/tui/src/worker.rs::republish_bundle` — a new, `pub async fn`, placed between
`inbound_handoff` and `run_inbound_loop` (both of which it sits conceptually between). Takes
`store: &dyn SecretStore, handle: &KeyHandle, account_pub: [u8; 32], server: &str` — the same shape
[`InboundHandoff`] carries, by reference/value rather than `&InboundHandoff`, so `run_worker` can borrow
`handoff.store`/`handoff.handle` for this call and *then* still move the whole `handoff` into
`run_inbound_loop` right after. Body mirrors `apps/cli/src/chat.rs::run`'s exact
connect → `publish_bundle` → `chat.vault.set_bundle(...)` → `save_chat` sequence, under
`chat_state_lock()` for the load-mutate-save portion (same discipline every other `sessions.bin`
handler in this module already uses), with a best-effort graceful `client.close()` on both the success
and failure path.

**Wiring:** `apps/tui/src/lib.rs::run_worker` now calls `worker::republish_bundle` inside the existing
`if !inbound_started { if let Some(handoff) = worker::inbound_handoff(&outcome) { ... } }` branch,
immediately before `tokio::spawn(worker::run_inbound_loop(...))` — so it runs exactly once per session,
guarded by the same `inbound_started` one-shot flag, for both account types (`inbound_handoff` already
independently derives a working handoff for `Os`/`File`; `republish_bundle` itself has no
account-type branching of its own — verified directly by this task's own new
`inbound_handoff_also_produces_a_working_handoff_for_a_file_backed_account` test).

**Republish-failure UX (`TODO: confirm`, as pre-flagged by the task file):** logged to stderr
(`eprintln!` in `run_worker`) and otherwise swallowed — `run_inbound_loop` is spawned regardless of
whether the republish succeeded. No design doc specifies a visible-status vs. log-only choice here;
log-only-and-still-listen was chosen because a transient republish failure must not prevent the
persistent receive loop from serving already-established sessions/ordinary replies, and this task's own
scope explicitly rules out inventing a new screen/effect to resolve the ambiguity more richly.

**`live_session_e2e.rs`:** `LIVE_E2E_RUN` gate removed; the orchestrator branch always runs. The test
now passes unconditionally (`cargo test -p meridian-tui --test live_session_e2e`), with its assertions
unweakened — confirmed by re-running it repeatedly. Two additional things had to change to get there,
both documented inline in the file itself:
- Since this test drives `worker::dispatch`/`run_inbound_loop` directly rather than through
  `run_worker`'s own event loop, it can't inherit the new wiring for free — each peer (`run_initiator`/
  `run_responder`) now calls `worker::republish_bundle` itself, once, immediately before starting its
  own persistent inbound loop, mirroring exactly what `run_worker`'s wiring now does.
- **Found and fixed a pre-existing, previously-unexercised bug** in `run_initiator`: its own
  `spawn_inbound(other_pub, server, service, handle)` call connected using the *peer's* pubkey as
  `account_pub` instead of its own (`SignalingClient::connect`'s `account_pub` argument must match the
  identity actually signing the auth challenge, or the server-side signature check fails). This was
  never previously reached: before this task's fix, the responder always failed first (`UnknownPrekey`
  on `AcceptRequest`), so the initiator's own subsequent `spawn_inbound` call was never exercised with
  real data. Fixed by threading the initiator's own `account_pub` through as a new `own_pub` parameter.
  Flagged here as an explicit, justified deviation from "touch only what the task names" — required to
  make deliverable 3 (test passes unconditionally, assertions unweakened) actually true.

**New narrow tests:** `apps/tui/tests/republish_bundle.rs` (new file), three tests:
1. `republished_secrets_are_resolvable_by_chat_state_open_inbound` — deliverable (a): a real peer
   fetches "us"'s republished bundle, X3DH-initiates, and "us"'s freshly-written `sessions.bin` opens
   the envelope cleanly (`Ok`/`Err(ChatError::MessageRequest)`, never `Err(ChatError::UnknownPrekey)`).
2. `republish_only_fires_once_per_session_via_the_inbound_started_guard` — deliverable (b): replays
   `run_worker`'s own `inbound_started` guard against a real dispatched sequence (`LoadSession`, an
   unrelated `PublishBundle`, a second `LoadSession`) and counts exactly one real `republish_bundle`
   call.
3. `inbound_handoff_also_produces_a_working_handoff_for_a_file_backed_account` — a fast, no-network-bulk-
   publish check that `inbound_handoff`'s `Effect::Unlock` branch is structurally correct too (see the
   finding below for why this test never calls the real `republish_bundle` against a file-backed store).

**Genuine finding, out of this task's fix-scope (documented, not swept under the rug).**
`republish_bundle` mirrors `apps/cli/src/chat.rs::run`'s own `publish_bundle(store, handle,
DEFAULT_OTK_COUNT)` call exactly — 101 real signatures (1 SPK + 100 OTKs). For a **file-backed**
account, `handoff.store` is a raw, per-call-scrypt-unwrapping `FileSecretStore` (`worker::
inbound_handoff`'s `Effect::Unlock` branch builds one fresh per handoff — correct and cheap for
`run_inbound_loop`'s own one-signature-per-delivery use, which is all it was built for). Driving 101
signatures through it re-runs a full scrypt KDF unwrap on *every single signature* — reproduced live
while writing this task's own tests: a real republish against a file-backed account took over 90 seconds
and climbing before being killed. This is a **performance** defect, not a correctness one (no data is
leaked, nothing is signed wrong), but a fix would mean caching an already-unwrapped store across the
101 signatures for this one call — exactly the "extending in-memory key residency" security-posture
question `docs/tasks/phase-4/README.md` already reserves for task 4.40's own load-bearing architect +
security-reviewer consult (`worker.rs`'s session-threading machinery). Left unfixed here, deliberately,
rather than inventing an unreviewed answer to that exact question; flagged for whoever picks up 4.40 (or
a dedicated follow-up) to consider alongside it. In the meantime a file-backed account's session start
is genuinely slow the first time a peer needs to reach it — degraded, not broken (the onboarding-time
bundle is still live on the server until the slow republish eventually completes or fails).
