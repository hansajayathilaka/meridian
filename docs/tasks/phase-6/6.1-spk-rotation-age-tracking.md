# 6.1 — SPK rotation policy: age tracking + rotation-due predicate

**Phase:** 6 — Envelope v2 · **Feature:** ADR 0016 (C1, part 1/3) · **Depends on:** — · **Status:** pending

## Goal
Give `PrekeyVault` a notion of "how stale is my current signed-prekey generation" so a caller can
decide to rotate. ADR 0016 C1 requires enforced, monitored SPK rotation to become real, with tests,
*before* envelope v2 ships — it is v2's compensating control for R1 (key-compromise impersonation on
the opening message), not an aspiration. Today no code anywhere tracks publish time or answers
"is this generation overdue" — this task builds that primitive; 6.2 acts on it.

## Scope
- **In:** `apps/core/src/chat.rs::PrekeyVault` — a publish-timestamp field, a rotation-due predicate,
  and the rotation-interval constant.
- **Out:** anything that *acts* on the predicate (republishing, warning, monitoring — task 6.2);
  server-side metrics (flagged for 6.2, not built here); the crypto/AAD rewrite (6.3).

## Deliverables
1. `PrekeyVault`: new `spk_published_at: Option<u64>` field (parallel to `spk_public`/`spk_secret`),
   set by whatever call already publishes a fresh bundle (`set_bundle` or its equivalent — confirm the
   exact call site by reading the current method, don't guess the name).
2. `SPK_ROTATION_INTERVAL_SECS: u64` constant next to the existing `PREV_GENERATION_GRACE_SECS`.
   `TODO: confirm` the exact value with **architect** — ADR 0016 only says "~weekly, monitored" as a
   target, no numeric requirement. Proposed default: `7 * 24 * 3600`.
3. `PrekeyVault::rotation_due(&self, now_unix: u64) -> bool` and
   `PrekeyVault::generation_age_secs(&self, now_unix: u64) -> Option<u64>`.
4. `#[serde(default)]` on the new field, mirroring `PrekeyVault::previous`'s own precedent, so a
   `ChatState` sealed by pre-6.1 code still deserializes without panicking.

## Risks / notes
- **Unknown-age semantics is a real decision, not a formality.** A state sealed before this task
  deserializes with `spk_published_at: None`. `TODO: confirm` with **architect**: does `rotation_due`
  treat "unknown age" as due-now (fail-safe: rotate promptly, one extra publish) or not-due (avoid a
  surprise mass-republish across every existing session on upgrade)? Record the decision and reasoning
  in this task's Outcome section — this is exactly the kind of security-relevant default ADR 0016 asks
  not to leave implicit (it's a component of R1's compensating control).
- Pure metadata addition — no crypto/wire-format change, no vector churn expected. If vectors move,
  that's a signal this task went wider than intended.
- This task is independent of 6.3 (the AAD/wire rewrite) and can be developed in parallel with it.

## Tests
```
cargo nextest run -p meridian-core --lib
```
New unit tests: `rotation_due` is `false` immediately after publish, `true` once
`now_unix - spk_published_at >= SPK_ROTATION_INTERVAL_SECS`; the chosen unknown-age default is
asserted explicitly (not left to fall out of whatever the code happens to do); a `ChatState` sealed
without the new field deserializes without panicking.
