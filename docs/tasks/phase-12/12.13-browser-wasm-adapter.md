# 12.13 — Browser wasm adapter

**Phase:** 12 — Browser & Desktop Clients · **Feature:** T11 · **Depends on:** 12.2, 12.11, 12.12 · **Status:** pending

**User surface:** none directly — the seam the browser app shell (12.14) and screens (12.7–12.9) run
against; this is the task that finally makes the browser client real. No TUI surface applies.

## Goal
Implement `MeridianClientAdapter` (task 12.2's interface) over `meridian-wasm`'s TS bindings (12.10),
`BrowserTransport` (12.11), and `WebCryptoSecretStore` + the IndexedDB store (12.5 + 12.12) — replacing
the `apps/wasm` smoke-test stand-ins with the real production pieces.

## Scope
- **In:** `apps/web/src/lib/adapter.ts` implementing every `MeridianClientAdapter` method by calling
  into the real `meridian-wasm` bindings with the real `BrowserTransport`/`WebCryptoSecretStore`/
  IndexedDB store wired in.
- **Out:** any change to the interface itself (12.2 owns that); any change to `BrowserTransport`/the
  store (12.11/12.5/12.12 — if this task finds either insufficient, that routes back as a finding, not a
  workaround here); the app shell/screens (12.14, 12.7–12.9).

## Deliverables
1. `apps/web/src/lib/adapter.ts` — the concrete adapter.
2. An integration test against a real headless-browser IndexedDB/WebCrypto environment (not a Node
   polyfill — this is the first task where the store's real browser-platform behavior actually matters
   end to end) covering: account creation persists and survives a simulated reload, a chat round-trip
   over `BrowserTransport` between two adapter instances.

**Known blocking gap, found by task 12.5's own review, not yet resolved — read before starting this
task.** `SecretStore` is a fully synchronous trait, but every `crypto.subtle` (WebCrypto) operation is
Promise-based, and there is no safe way to block a single-threaded `wasm32-unknown-unknown` call on an
in-flight Promise without either a `SharedArrayBuffer`/`Atomics.wait` worker bridge (needs its own
worker plus `COOP`/`COEP` cross-origin-isolation headers) or Binaryen `--asyncify` — neither in scope
for 12.5. `WebCryptoSecretStore`'s `impl SecretStore` trait methods therefore deliberately return
`StoreError::Backend` rather than hang or fabricate a result; the real logic lives in inherent
`async fn store/use_key/derive_key/nonextractable` methods with the same names, callable directly but
NOT through `&dyn SecretStore`/generic `<S: SecretStore>` dispatch. This means
`meridian_identity::generate_account`/`sign` (the actual dyn-dispatch call sites production code uses,
in `apps/identity/src/keys.rs`) **will always fail** if called with a `WebCryptoSecretStore` — this
task cannot simply reuse those shared helpers as-is. Before implementing `apps/web/src/lib/adapter.ts`,
get a real architect decision on the resolution path (an async `SecretStore` companion trait for
wasm32 — mirroring `Transport`'s own already-async design in core-api-contracts.md — vs. an accepted
worker+Atomics bridge vs. formally accepting an adapter-level reimplementation of
`generate_account`/`sign`'s seed-generation/hint-validation/label logic against the async inherent
methods directly) via an ADR 0026 amendment, run as this task's own required first step — mirroring the
precedent tasks 7.5/11.8 set for a required architect pre-check landing inside the task itself rather
than a separate `/plan-phase` round. Full finding: [12.5's Outcome](./12.5-webcrypto-secret-store.md#outcome).
