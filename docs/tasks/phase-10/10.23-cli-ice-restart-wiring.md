# 10.23 — CLI/demo wiring for the new `ice_restart` signature

**Phase:** 10 — File Transfer Stream · **Feature:** T09 (fix) · **Depends on:** 10.22 ·
**Status:** done (task itself fully executed) — **verdict: the primary scenario (`run`) now genuinely
passes live; the smaller `probe` companion still fails, for a new, distinct reason**; see Outcome.

## Goal
Update every existing caller of `P2pSession::ice_restart` to the new signature (10.22), and re-run the
existing kill/resume test scenarios for real, now against a transport that can actually recover.

## Scope
- **In:** `apps/cli/src/session_connect.rs`, `apps/cli/src/send.rs` (if either calls `ice_restart`
  directly or would need to for a real scenario), `apps/cli/examples/kill_resume_netns_drive.rs` and
  `apps/cli/examples/netns_ice_restart_probe.rs` (task 10.15's drivers — update both to pass a fresh
  `SignalRelay` per ADR 0025's "reconnect transiently, don't hold open" decision, likely a short-lived
  reconnect to the rendezvous right before calling `ice_restart`, mirroring how `dial`/`answer` are
  each given a fresh relay). Re-run `tools/netns-kill-resume.sh run`/`probe` for real, live, on this
  sandbox's netns/veth rig — this is the same scenario tasks 10.15/10.17 already built and ran; it
  should now actually pass instead of hitting the documented timeout.
- **Out:** any new CLI-visible user surface or command (this is a fix to an existing capability's
  correctness, not a new feature — no new TUI/CLI command needed here, per CLAUDE.md's Definition of
  Done gate 9 "no user surface? say so explicitly").

## Deliverables
1. Every caller updated to the new `ice_restart` signature; builds clean with and without
   `--features webrtc`.
2. A live, real re-run of `tools/netns-kill-resume.sh run` and `probe` (root/netns available in this
   sandbox), pasted as real transcript output (mirroring task 10.17's own demo-transcript convention)
   proving the network-cut → restart → resume scenario now actually completes: the transfer finishes
   and both ends' content matches (BLAKE3 root + `sha256sum`, the demo script's own wording).

## Risks / notes
If the real re-run surfaces *any* new defect (not the already-fixed `ice_restart` gap), record it
honestly rather than working around it silently — same discipline every task this phase has followed.
This task's own acceptance criterion is the live re-run actually passing; if it doesn't, stop and
report exactly what's still broken rather than declaring victory.

## Tests
`cargo build --workspace --features webrtc` and `cargo build --workspace` (both clean);
`tools/netns-kill-resume.sh run` and `probe`, live, both PASS.

## Outcome

Every caller updated to the new `ice_restart` signature per ADR 0025's "reconnect transiently, don't
hold open" pattern:

- **`apps/cli/examples/kill_resume_netns_drive.rs`, `apps/cli/examples/netns_ice_restart_probe.rs`**
  (task 10.15's drivers): the dial-time `FileRelay` is now dropped immediately after `dial`/`answer`
  establish the session (mirroring production's `client.close()`), and a *fresh* `FileRelay` is
  constructed right before each `ice_restart()` call, used only for that one bounded attempt, then
  dropped again — `FileRelay::new`/`FileRelay::reconnect` split, the latter carrying the
  already-consumed inbox read offset forward (not resetting to `0`) since this file-based double is a
  raw append-only byte stream, not a real recipient-keyed mailbox: resetting the offset would
  re-decrypt already-consumed dial-time envelopes through the ratchet a second time, a self-inflicted
  failure with no analogue for a real `SignalingClient` reconnect. This keeps the call-site *shape*
  honest for anyone later copying this pattern into `session_connect.rs`/`send.rs`, even though a
  genuine network reconnect doesn't map onto this particular test double (no real connection to drop —
  see the files' own updated doc comments).
- **`apps/cli/src/session_connect.rs`, `apps/cli/src/send.rs`**: confirmed neither calls
  `ice_restart` and neither should — ADR 0025 explicitly defers automatic detection/triggering of
  *when* to restart to a separate, later follow-up, and no `StreamType::on_reconnect`/`SessionEvent`
  hook exists yet to learn "the network changed" without a `meridian-core` change (still the same
  tracked carry-forward `apps/streams/src/resume.rs`'s module doc has named since task 10.9). No
  production wiring added here — confirmed correctly out of scope, not silently skipped.
- **`tools/netns-kill-resume.sh`**: the `IFNAMSIZ` pre-flight self-check bug task 10.17 found and
  worked around out-of-line (a throwaway copy) is fixed for real in the checked-in script this time —
  `need_veth_linkstate` now zero-pads its probe interface names to 6 digits (`kr-a-016738`, always
  well under the 15-byte cap) instead of the unbounded `$$` that overflowed on this sandbox's
  5-digit PIDs. This task's own first attempt at the fix instead *truncated* via bash's `${pid: -6}`
  — code review caught, and live-reproduced, that this returns an **empty string** (not the whole
  value) for any PID under 6 digits, i.e. effectively every real invocation given Linux's default
  `pid_max` of 32768, collapsing every probe pair to the same constant name and creating a genuine
  namespace-collision risk between concurrent runs (`/run/netns/kr-lsa-` colliding across two
  processes, confirmed live). Corrected to zero-pad via `printf '%06d'`, which preserves per-PID
  differentiation for short PIDs without truncation risk for long ones (`kr-a-4194304` at Linux's
  7-digit `pid_max` ceiling is still only 12 bytes). Reproduced the original `IFNAMSIZ` failure first
  (`ip link add kr-probe-a-16738 ... peer name kr-probe-b-16738` → "not a valid ifname"), confirmed
  the (corrected) fix resolves it with no collision risk, then ran `run`/`probe` directly against the
  real, unmodified script — no throwaway workaround copy needed this time. The script's
  header/failure-message comments were also updated to reflect that both previously-documented gaps
  (SCTP max-message-size, task 10.18; `ice_restart` no-op, tasks 10.19–10.22) are now fixed and no
  longer expected on a live run.

**Live re-run verdict** (full transcript: [10.23-demo-transcript.md](./10.23-demo-transcript.md)):

- **`tools/netns-kill-resume.sh run` — PASS, live, real, 3/3 consecutive clean runs.** This is the
  exact scenario task 10.17's own Part 2 found broken (sender never received the receiver's resume
  bitmap, receiver never received the resent chunks, after a no-op `ice_restart()`). It now genuinely
  completes end-to-end over a real 15-second veth cut: the resume bitmap is delivered over the
  *renegotiated* data channel, exactly the missing 9/24 chunks are resent (`resend_ratio=0`), and the
  final file's BLAKE3 root and independently-computed `sha256sum` match on both ends. This closes the
  specific defect `docs/tasks/README.md`'s "Live carry-forwards" entry and ADR 0025 both name.
- **`tools/netns-kill-resume.sh probe` — FAIL, live, real, reproducible (4/4 runs).** A genuine,
  newly-observed defect, distinct from the fixed no-op: both sides' `ice_restart()` calls return `Ok`
  (the full ADR 0025 signaling round trip and layered fingerprint check genuinely succeed on both
  sides), but a chat message sent by the offerer *immediately* after `ice_restart()` returns is never
  received by the peer, even after waiting up to 90s. Live diagnostic evidence (plain IP connectivity
  recovers cleanly and immediately post-restore; the sender's own network interface shows zero
  additional packets transmitted between the restart completing and the failed send; a throwaway,
  reverted 3-second sleep inserted between `ice_restart()` returning and the send made the probe pass
  reliably) points to a readiness race: `ice_restart()`'s `Ok` return means the *signaling* layer
  succeeded, not that the underlying ICE/DTLS/SCTP path has actually reconverged enough to carry
  traffic yet, and nothing today gives a caller a way to know when it has (ADR 0025 itself already
  notes `WebRtcTransport` only wires the connection-state callback for the *original* `Connected`
  transition). `run`'s own sender happens not to hit this window because it polls for the receiver's
  resume bitmap first rather than sending immediately, incidentally buying enough real time for the
  path to reconverge; `probe`'s send-immediately pattern is precisely what exposes the race. No sleep,
  retry, or other timing shim was added to ship this task's own deliverable — that would mask, not
  fix, the gap. Recorded as a new candidate follow-up (a post-restart readiness signal), separate from
  ADR 0025's own already-tracked mutual-timeout glare residual and the still-open
  `StreamType::on_reconnect` carry-forward.

### Review round: one real bug found and fixed, one evidentiary correction, one doc gap closed
**code-reviewer returned FAIL** on the first pass: this task's own `IFNAMSIZ` fix in
`tools/netns-kill-resume.sh` used bash's `${pid: -6}` to "truncate" the PID to 6 digits — but that
expression returns an **empty string**, not the value, for any PID under 6 digits (effectively every
real invocation given Linux's default `pid_max`), collapsing every probe pair to the identical name
`kr-a-`/`kr-lsa-` and reintroducing exactly the collision risk this fix was supposed to eliminate.
Live-reproduced by the reviewer as a genuine `/run/netns/kr-lsa-` collision between two concurrently
running instances. Fixed by zero-padding via `printf '%06d'` instead of truncating — verified
correct for short PIDs (`016738`), long PIDs (`4194304`, still only 12 bytes, under Linux's 7-digit
`pid_max` ceiling), confirmed via `shellcheck -x` and a fresh live re-run of `run` (still PASS, real
sha256 match, root differing per run as expected). Both the task file's own prose (this section) and
the demo transcript's corresponding claim were corrected to match.

**test-engineer returned PASS**, independently reproducing `run` (3/3, with genuinely different
sha256 hashes each run — proof these are real transfers, not a replayed transcript) and `probe`
(5/5, exceeding the originally-claimed 4/4) live, and independently corroborating the readiness-race
diagnosis via their own throwaway sleep-insertion experiment. One evidentiary correction: the
transcript's "zero additional packets transmitted" claim did not hold under the reviewer's own
sub-10ms-granularity re-measurement — real ICE-level traffic genuinely flows in the exact window
between `ice_restart()` returning `Ok` and the failed send, which *sharpens* rather than overturns
the diagnosis (the race is at the DTLS/SCTP layer above ICE, not "nothing happening at all").
Corrected in the transcript. The reviewer also recommended the `probe` readiness-race finding get
its own dedicated bullet in `docs/tasks/README.md`'s "Live carry-forwards" section rather than living
only inside this task file and the transcript — added.
