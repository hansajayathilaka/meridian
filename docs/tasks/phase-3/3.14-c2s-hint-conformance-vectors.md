# 3.14 — Conformance vectors for the c2s hint extension

**Phase:** 3 — Review of Phase 2 · **Feature:** review fix (F20) · **Depends on:** — · **Status:** in review

## Goal
`Fetch{hint}` / `RouteBody{to_hint}` / the new federation error codes are byte-protected on the
WASM/mobile targets, not only in a Rust unit test.

## Scope
- **In:** c2s fixtures generated by `tools/xtask/src/vectors/`; the new federation error codes.
- **Out:** vectoring the whole historic c2s frame set — a **pre-existing** gap the hint change merely
  widened. Record it as carried forward; do not silently expand this task into it.

## Deliverables
1. `tools/xtask/src/vectors/` — c2s generator additions.
2. Committed `test-vectors/` fixtures.
3. The consumer assertion wired into the existing conformance test.

## Risks / notes
- Vectors are **canonical wire artefacts** — never hand-edited; regenerate via xtask and commit the
  diff. A change here needs architect + security-reviewer sign-off per the CI gate's own error text.
- Backward-compat is already proven at the proto level (`roundtrip.rs:96`); this task extends that
  proof across targets, it does not replace it.

## Outcome
Added `tools/xtask/src/vectors/c2s.rs` (wired into `generate()` in `mod.rs`), mirroring
`federation.rs`'s existing `build_vector` pattern: every vector's `frame_hex` is produced by the real
`meridian_proto::Frame::new`/`to_bytes` encode path (deterministic CBOR, fixed byte patterns), not
hand-crafted. Generates `test-vectors/c2s-v1.json` — 7 vectors: `Fetch` with `hint` absent and
present, `RouteBody` with `to_hint` absent and present, and one `ErrBody` vector each for the three
federation error codes task 2.9 added (`fed_denied`, `fed_unreachable`, `not_found_at_hint`). Scope
match: hint fields + the *new* federation error codes only, per this task's own Scope — the full
historic c2s frame set stays the pre-existing gap `roundtrip.rs` already covers and this task does
not widen into (noted in the fixture's own `note` field so a future reader doesn't mistake the
narrower scope for an oversight).

**Deliverable 3 correction — the task's own Tests section names the wrong crate.** `Fetch`/
`RouteBody`/`ErrBody`/`error_codes` are `meridian-proto` types; `meridian-crypto`'s
`tests/conformance.rs` (the file named in this task's Tests section) doesn't import
`meridian-proto`'s frame types at all and only re-derives *cryptographic* fixtures (x3dh/ratchet/
envelope/safety-numbers) — wiring a c2s wire-encoding assertion into it would be a foreign-crate
reach-around, not "the existing conformance test" in any meaningful sense. Also worth recording:
`federation-v1.json` (the s2s sibling this task's vectors were modeled on) has **no** load-and-assert
consumer at all today — only the xtask regen+`git diff --exit-code` self-consistency check, which is
real (it exercises the actual `FedFrame` encode path) but is a different, weaker proof than an
independent load-fixture-and-re-derive test. Rather than either force-fit into `meridian-crypto` or
settle for the same self-consistency-only bar as federation, this task adds
`apps/proto/tests/conformance.rs` (new file, same naming/shape as `meridian-crypto`'s), which loads
`c2s-v1.json`, reconstructs each `Fetch`/`RouteBody`/`ErrBody` from its committed hex/plain fields,
re-derives `frame_hex` through the real `Frame::new`/`to_bytes`, and asserts byte-for-byte equality —
holding the c2s vectors to the same "independent re-derivation" bar `x3dh_vectors_match_real_derivation`
etc. already hold the crypto vectors to. `meridian-proto/Cargo.toml` gained a `serde_json`
dev-dependency (workspace-pinned) to parse the fixture, same shape as `meridian-crypto`'s own
`conformance.rs`.

**CI invocation:** no `ci.yml` edit, but for a more precise reason than the task's own note states.
`cargo run -p xtask -- vectors && git diff --exit-code -- test-vectors/` (already in the "Conformance
vectors" step) covers the new `c2s-v1.json` automatically since `generate()` now calls
`c2s::generate_c2s()`. The new **consumer** test, `apps/proto/tests/conformance.rs`, isn't behind any
Cargo feature, so it's already covered by the general `cargo test --workspace` step (`ci.yml` line
52) — not by the "Conformance vectors" step's explicit `cargo test -p meridian-crypto --test
conformance` line, which only runs the crypto crate's own conformance binary and never touches
`meridian-proto`. Both paths land in CI either way; no workflow edit needed, matching this task's own
claim, just via a different mechanism than the Tests section implies.

**Mutation-check (test-engineer gate):** ran twice, independently, both confirmed then restored to
the clean xtask-generated state. (1) Corrupted `err-fed-denied`'s `code` field in the committed JSON
→ `apps/proto/tests/conformance.rs`'s own "recognized `error_codes` constant" assertion fired (red).
(2) Restored, then flipped one byte of a `frame_hex` value directly → the core `frame_hex` equality
assertion fired (red), confirming the byte-comparison itself — not just the auxiliary constant
check — is non-vacuous. Both times restored to byte-identical with `cargo run -p xtask -- vectors`'s
output and reverified green.
