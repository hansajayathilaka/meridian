# 3.16 — Warn on private-CA trust anchors under SRV discovery

**Phase:** 3 — Review of Phase 2 · **Feature:** review fix (F6) · **Depends on:** — · **Status:** done

## Goal
Stop the SRV demo from modelling the pattern that reopens ADR 0017 (a)'s Option-A impersonation hole
under a *shared* private CA.

## Scope
- **In:** prominent documentation that a private-CA trust anchor requires `discovery = static` with a
  mandatory `pinned_identity` **regardless of how the CA is installed** (ADR 0017 +
  `docs/operations/deployment.md` + a header comment in `demo/two-orgs/docker-compose.srv.yml`); a
  startup warning when `srv` is configured and the resolved trust anchor is not a public root, **if
  detectable**.
- **Out:** changing `validate`'s existing fail-closed rule (`srv` + non-empty `ca_bundle_path`);
  making the demo use static discovery — it demonstrates SRV on purpose.

## Deliverables
1. The doc edits above.
2. Optionally `apps/rendezvous/src/config.rs` — the startup warning + a unit test.
3. A `TODO: confirm` if detectability is unresolved.

## Risks / notes
- `validate` keys only on `ca_bundle_path`, so it **cannot see** a private CA installed into the OS
  trust store — which is exactly what `demo-entrypoint.sh` does (`update-ca-certificates`) with an
  empty `ca_bundle_path`. The demo itself is benign (cooperative orgs, one cert each); the hazard is
  a *shared, multi-org* private CA in production.
- If a non-public root is **not** reliably detectable, say so in the task file — do not fake a check
  that gives false assurance.

## Reviews
- **security-reviewer** — required; ADR 0017 admission-boundary hazard.

## Outcome
Added a clarifying note under ADR 0017 (a)/C4 (plus an R5 residual-risks entry cross-referencing
it), a deployment.md §9.2 paragraph, and header-comment warnings in `demo/two-orgs`'s
`docker-compose.srv.yml` and `demo-entrypoint.sh` (with an inline pointer at the actual
`update-ca-certificates` call), stating the private-CA-requires-static-discovery rule applies
regardless of how the CA became a trust anchor. Investigated the startup-warning deliverable and
concluded detection is **not reliably possible** from anywhere in the process — neither
`Federation::validate` (no field to key on) nor a runtime OS-trust-store read (no provenance to
distinguish public vs. private roots without false positives) — recorded in a `config.rs` comment
rather than implemented, per the task's own "do not fake a check that gives false assurance"
instruction. `validate`'s existing fail-closed rule is unchanged.

Reviews: security-reviewer + architect (combined pass) — both **pass**; two non-blocking
suggestions applied (an R5 residual-risks cross-reference in ADR 0017, and rewording the `config.rs`
comment since the investigation is closed, not an open question). devops — **pass**; one nit
applied (inline warning pointer next to the actual `update-ca-certificates` line).
