# 4.44 — Load a chat's persisted transcript when the chat screen opens

**Phase:** 4 — Verification & Trust + Terminal TUI Client · **Feature:** T17 — Terminal TUI Client (gap closure; predicted "Defect D", traced in source at plan time, not yet reproduced live) · **Depends on:** 4.36, 4.42 (land-after only) · **Status:** pending

## Goal
Make the live TUI actually show a conversation's restart-persistent history: opening a chat loads the
peer's real, sealed transcript instead of starting empty — the T17 acceptance criterion "restart restores
contacts, **history**, and ratchet state; no re-handshake, no duplicate messages (local dedup by message
id)" and the demo script's `pkill meridian-tui && meridian tui` step both depend on it.

## Why this task exists before the defect was observed live
This gap was **traced in source during `/plan-phase`, not reproduced live**. Three exit-gate attempts
(4.28, 4.38, 4.41) have each found exactly one defect, fixed it, and then found the next one at the *next*
demo-script step. The step immediately after 4.42's fix is the restart-restore step — and the source says
plainly that it cannot pass:

- `apps/tui/src/screens/main.rs::handle_key`'s `ContactsAction::OpenChat` arm constructs every chat as
  `ChatState::new(entry.pubkey, entry.hint, trust, Vec::new(), entry.unread)` — a literal empty
  `Vec<HistoryEntry>`.
- **No code path anywhere in `apps/tui/src` loads per-peer history into a screen.** The only caller of
  `crate::store::history::load_or_default` in the crate is `apps/tui/src/store/export.rs`.
- `screens/main.rs`'s own module doc admits it: *"Loading it would need either widening `LiveSession` or a
  new `Effect::LoadHistory` this task never adds."*

Scoping it now costs one task. Discovering it at the exit gate costs a whole extra gate cycle, because
that gate's own rules would (correctly) force a fifth attempt. **Deliverable 1 is a reproducing test, so
the task proves itself before changing anything** — if it does not reproduce, the task closes cheaply and
honestly as not-a-defect.

## Scope
- **In (verify first, then fix — in that order):**
  1. **Reproduce the defect before fixing it.** Turn the trace above into an observed failure (a failing
     test, or a documented live run). **If it does not reproduce — if some path already loads history —
     say so honestly, record the evidence, and close the task as not-a-defect. Do not manufacture a fix
     for a gap that isn't there.**
  2. **Then fix it**, choosing between the two shapes `screens/main.rs`'s own doc comment already names:
     widen `LiveSession` (task 4.29's type) to carry per-peer history, or add a new `Effect::LoadHistory`
     round trip executed by the worker. Record the choice and its rationale in the Status section. Reuse
     `crate::store::history::load_or_default` — never a second, divergent reader.
  3. The transcript must be correct on **both** paths a chat opens: after a restart, and on a re-open
     within the same session (`Esc` out of a chat and back in, which today discards the popped
     `ChatState`'s entries).
- **Out:** unread-count semantics, read receipts and delivery-state backfill for historical rows;
  surfacing a live inbound message when no matching `Screen::Chat` is open (4.41's traced gap in
  `app.rs::handle_inbound`, also scoped out of 4.42 — still deferred); history retention/pruning
  (`history.retain_days`, per the T17 spec's own note that prune-on-start is opt-in and must never
  silently delete); the sealed history file format itself; 4.42's and 4.43's concerns; any new wire type
  or crypto.

## Deliverables
1. A **reproducing test** (kept afterwards as the regression test) proving a chat opened over a peer with
   existing on-disk history renders that history — failing before the fix, passing after.
2. The chosen load path, implemented, with the rationale recorded in the Status section. **If the chosen
   shape widens `LiveSession`'s contract, get the architect lens on it before landing** — that type is
   task 4.29's, and several screens' doc comments describe its contract.
3. `screens/main.rs`'s `Vec::new()` history argument replaced by the real load, and that module's own
   "history is not loaded here" doc note rewritten to describe the fixed state rather than the gap.
4. Tests: entries render in the correct order after a restart; **dedup by message id holds** (reuse
   `chat::insert_deduped`, and assert that an inbound message arriving live for a peer whose history was
   just loaded is not double-listed); a re-open within the same session shows the transcript; nothing
   about the sealed-at-rest guarantees changes (`cargo test -p meridian-tui --test at_rest_audit` stays
   green, extended only if the new path writes anything — it should not).
5. A redaction check: the loaded transcript is message plaintext in memory — assert that whatever type now
   carries it is not `Debug`-reachable in a way that prints bodies, mirroring
   `crate::session::LiveSession`'s own redaction test and
   `run_worker_account.rs::effect_debug_never_leaks_a_passphrase`.

## Risks / notes
- **No I/O in `update`.** This crate's Elm split is explicit that `crate::screens`'s `update`/`handle_key`
  never performs I/O directly (`tui-client.md` §4, restated in `screens/main.rs`'s module doc). A fix that
  reads `history.jsonl` inside `handle_key` would violate that boundary — which is exactly why the
  `Effect::LoadHistory` shape exists as a candidate. Architect lens owns this call.
- **History is message plaintext.** Loading it widens what a live process holds in memory and what a
  panic/`Debug` could print. Security-reviewer lens; Deliverable 5 is not optional.
- **Unbounded growth.** `history.retain_days = 0` (no pruning) is the default per the T17 spec, so a long
  conversation's file can be large; if the chosen shape would load it synchronously on the UI path,
  consider a tail/cap — but **do not invent a retention policy**; if no design doc settles the bound,
  record a `TODO: confirm` rather than guessing.
- **Definition of Done gate 9 (TUI surface):** satisfied intrinsically — this is T17's own chat screen.
  No `SurfaceRegistry` registration is added.
- Logically independent of 4.42, but land **after** it: both touch how a `ChatState` is constructed and
  how `App` manages the screen stack, and a simultaneous diff there is the same trap the phase README
  already called out for 4.39/4.40's shared `worker.rs` machinery.

## Status
**Done.** The traced gap reproduced exactly as predicted (`ChatState::new(..., Vec::new(), ...)`,
Deliverable 1's `tests/history_load.rs::opening_a_chat_with_existing_history_on_disk_renders_it` failed
before the fix, empty transcript against real seeded on-disk history), and the fix closes it: opening a
chat — first time, after a restart, or a same-session re-open — now shows the real, sealed transcript
`crate::store::history::load_or_default` reads back.

**The chosen shape: a new `Effect::LoadHistory` round trip, not widening `LiveSession`.** The task's own
Deliverable 2 conditional — "if the chosen shape widens `LiveSession`'s contract, get the architect lens
on it before landing" — never fires: `apps/tui/src/session.rs` has a genuinely zero-line diff (`git diff
--stat` confirms it; `reviewer` independently verified this). `LiveSession` still carries only what task
4.29 gave it (`account`, `trust`, `chat`, `contacts`) — no new per-peer history field was added there or
anywhere in its contract. So no pre-landing architect consult was required by the task's own rule, and
none was held.

**Why this shape.** `crate::store::history::load_or_default` does real file I/O and needs a
`SecretStore`/`KeyHandle` to unseal `history/<peer>.jsonl` — exactly the kind of call this crate's Elm
split forbids inside `handle_key`/`update` (the "no I/O in `update`" boundary, `tui-client.md` §4,
restated in `screens/main.rs`'s own module doc). Widening `LiveSession` would only front-load *all*
contacts' full transcripts at session-load time — a strictly worse fit for both the I/O boundary (still
a worker-side read, now for every contact at once instead of lazily per open) and the unbounded-growth
risk below. `ContactsAction::OpenChat` (`screens/main.rs::handle_key`) instead pushes `Screen::Chat` with
`entries: Vec::new()` (unchanged — the screen still opens instantly) and dispatches one
`Effect::LoadHistory { peer_pubkey }` alongside it; a real worker (`worker::run_load_history`) executes
`load_or_default` — the same reader `crate::store::export` already uses, never a second, divergent one —
and reports the transcript back via `WorkerEvent::Completed(Effect::LoadHistory(_))`.
`App::apply_loaded_history` then merges `loaded` into whichever `Screen::Chat` matches the peer, walking
the **whole** screen stack (not just the top) so a `Ctrl-R` pushing `Screen::Requests` on top of an
already-open `Screen::Chat` mid-flight still resolves correctly — see that method's own doc comment and
the dedicated regression test added in the review round below. A re-open (`Esc` then `Enter` again)
dispatches a fresh `Effect::LoadHistory` rather than caching anything, so `Screen::Chat`'s in-memory
`entries` staying non-authoritative (task 4.36's existing "Esc discards the popped `ChatState`'s entries"
behavior) is no longer a problem: the disk read is always re-run, and `chat::insert_deduped` merges any
live-arrived-in-the-meantime entries in on top, deduped by `mid`.

**The `history.retain_days`/unbounded-growth risk note: no `TODO: confirm` needed.** The risk note's own
trigger condition — "if the chosen shape would load it synchronously on the UI path" — never fires,
because the load is genuinely asynchronous: `Effect::LoadHistory` is dispatched and returned from
`handle_key` without ever being awaited inside `update` (`update` stays synchronous and I/O-free
throughout, per the crate's own invariant), `Screen::Chat` renders immediately with `Vec::new()`, and the
real transcript is merged in only later, on the worker's completion round trip. Both `reviewer` and
`test-engineer` independently verified this reasoning by tracing the dispatch/merge split (`handle_key`
→ `Vec<Effect>` returned, never awaited; `App::apply_loaded_history` only ever runs from
`App::handle_worker`, never from `handle_key`) and confirmed it holds; no retention/tail/cap policy was
invented here.

### Review round

Both `reviewer` (architect / security-reviewer / code-reviewer combined) and `test-engineer` passes
returned **PASS on every lens, no blocking findings** — should-fix items only, all closed in this round:

1. This Status section itself (was "Pending.") — filled in above.
2. **Regression test for the `Ctrl-R`-behind-an-open-chat interleaving**
   (`tests/screen_main.rs::a_load_history_completion_lands_correctly_behind_an_interleaved_ctrl_r_requests_screen`).
   `App::apply_loaded_history`'s own doc comment already justified its whole-stack walk by citing this
   exact scenario — the same defect *class* `App::apply_accepted_request` was found missing in task
   4.42's own review round (Finding 1) — but nothing exercised it. New test: open a chat (dispatches
   `Effect::LoadHistory`), `Ctrl-R` (pushes `Screen::Requests` on top while the load is still in
   flight), complete the pending load, and assert the transcript lands correctly on the `Screen::Chat`
   frame underneath once `Screen::Requests` is popped back off — not lost, not misrouted.
3. **Test coverage for the history-load failure path** (`App::note_history_load_failure`, wired from
   `WorkerEvent::Failed(Effect::LoadHistory(...), message)`) — previously zero coverage anywhere in the
   diff. Two new tests:
   `a_failed_load_history_surfaces_a_notice_on_the_matching_open_chat` (a failed load surfaces the
   worker's message as a notice on the still-open matching `Screen::Chat`, with `entries` left
   untouched) and `a_failed_load_history_for_an_already_popped_chat_is_a_safe_no_op` (the same failure
   arriving after that `Screen::Chat` has already been popped is a safe no-op, not a panic or a
   misdirected write).
4. **Permanent regression test for the same-mid-in-both-loaded-and-in-flight-live-arrival dedup case**
   (`same_mid_in_both_loaded_and_a_still_in_flight_live_arrival_is_deduped_not_doubled`) — the exact race
   `apply_loaded_history`'s own doc comment names (a message already flushed to disk by the time the
   read ran, also separately delivered live *before* the load completes, same `mid`) had no permanent
   test; `test-engineer` had confirmed a throwaway version passing but reverted it as investigative. Made
   permanent here, asserting the entry appears exactly once in the final transcript.
5. **Doc-comment tightening (nit).** `apply_loaded_history`'s doc previously said a live inbound is
   "only appended to an *open* `Screen::Chat`'s own `entries` if one is open" — the actual check in
   `App::handle_inbound` is `self.screens.last_mut()`, i.e. only if `Screen::Chat` is literally on top
   of the stack, not "open" anywhere in it. Reworded to say so precisely, and cross-referenced explicitly
   against 4.41's already-deferred "no unread indication while no matching chat is open" gap (a live
   inbound arriving while `Screen::Requests` sits on top during that same interleaving window is not
   captured into `chat.entries`, but is still persisted to disk unconditionally — nothing lost or
   duplicated, not a new regression).
6. **Redaction-test honesty (nit, left as-is).** `load_history_effect_carries_no_key_material_and_is_not_redacted`'s
   sentinel-absence check isn't wired to any actual field, so a future field adding key material
   wouldn't make it start failing on its own. Both review passes judged this acceptable as shipped — the
   type genuinely carries no secret today, matching the un-redacted-body precedent
   `PersistHistoryEffect`/`SendMessageEffect` already set — and no cheap strengthening was found, so this
   was left unchanged per the review guidance not to spend real effort here.
