# 4.32 — Real `run_worker`: trust & request-queue persistence

**Phase:** 4 — Verification & Trust + Terminal TUI Client · **Feature:** T17 — Terminal TUI Client (gap closure) · **Depends on:** 4.21, 4.22, 4.4 · **Status:** done

## Goal
Execute `AcceptRequest`/`RejectRequest`/`MarkVerified`/`AcknowledgeKeyChange` for real. These four
collapse into one task, not two, because every one shares the identical "the screen already computed the
answer in-memory; the effect's execution is purely reload → replay the same deterministic mutation →
reseal → persist" shape, and none alone is large enough to be its own PR.

## Scope
- **In:** `run_worker` arms mirroring `apps/cli/src/chat.rs::answer_request`'s accept/reject order
  (`ChatState::accept_request` before `TrustStore::observe`, per task 4.7's own fix — do not reorder) and
  `apps/core/src/trust.rs::TrustStore::mark_verified`/`acknowledge_key_change`. Each arm reloads
  `trust.bin`/`sessions.bin` fresh from disk, replays the exact deterministic call the screen already
  applied in-memory, reseals, and writes — the worker never receives the live `TrustStore`/`ChatState`
  value itself over the effect channel (per the architect's settled guidance: these types are
  deliberately not `Clone`, and the worker's job is durability of an already-decided answer, not a
  second decision).
- **Out:** network I/O; navigation; live arrival of new requests while a session is running (that's
  4.35's job — this task only persists a decision the screen already made about a request already on
  screen).

## Deliverables
1. Four `run_worker` arms: `AcceptRequest`, `RejectRequest`, `MarkVerified`, `AcknowledgeKeyChange`.
2. Tests including "reject leaves no trace" (mirrors `RejectRequestRequest`'s own doc'd invariant — a
   rejected request must not persist any record of having existed) and confirmation that the
   un-softenable key-change semantics (task 4.4/4.23) stay intact end to end through a real persist
   round-trip, not just in-memory.

## Risks / notes
- **Never re-derive or second-guess the gate.** The screen already decided to mark-verified/acknowledge
  before dispatching the effect; this task's job is purely to make that decision durable, never to
  re-evaluate whether it was the right call.
- No dependency on 4.29, 4.30, 4.31, or any other task in this gap-closure set — independently testable
  today.
- **Review follow-up (retroactive-escalation persistence — sibling gap tracked, not yet fixed
  everywhere).** `apps/core/src/trust.rs::TrustStore::acknowledge_key_change`'s escalation branch
  mutates `contact.state` to `Blocked` and *then* returns `Err(TrustError::NotAcknowledgeable)` — a
  real state change riding along on the `Err` path. `apps/tui/src/worker.rs::run_acknowledge_key_change`
  now snapshots the contact's state before/after the call and persists whenever it actually changed,
  regardless of `Ok`/`Err`, closing this for the TUI worker path. `apps/tui/src/screens/verify.rs`'s
  `apply_action`'s `Acknowledge` arm and `apps/cli/src/chat.rs`'s `answer_key_change_warning` have the
  identical pattern — a mutation on the `Err` path that their own callers' `save_trust` calls, gated on
  a successful return, never persist. This is currently dormant everywhere (`set_escalate_pinned_key_change`
  has no production caller yet — confirmed by grep across the whole tree), which is exactly why it is
  worth flagging now: `verify.rs` and `apps/cli/src/chat.rs` need their own follow-up fix once escalation
  is ever wired to a real operator-facing toggle, so this doesn't silently ship as a live bypass then.

## Status
Done. `apps/tui/src/worker.rs` gained real `run_worker` arms for `AcceptRequest`/`RejectRequest`/
`MarkVerified`/`AcknowledgeKeyChange`, each a single reload-fresh → replay-the-already-decided-mutation →
reseal → write round-trip, mirroring `apps/cli/src/chat.rs::answer_request`'s accept/reject order
(including the task-4.7 `accept_request`-before-`observe` fix) and `apps/core/src/trust.rs`'s
`mark_verified`/`acknowledge_key_change` exactly. None of these handlers re-derives or second-guesses a
gate the screen already decided.

**Review (combined `reviewer`, as named) found two real, security-relevant defects**, both fixed and
re-confirmed clean by hand-tracing every reachable code path:
- **Persistence gap in the retroactive-escalation force-block:** `TrustStore::acknowledge_key_change`'s
  escalation branch mutates a contact to `Blocked` and *then* returns `Err` — but the worker only
  persisted on `Ok`, so that force-block was silently discarded, never reaching `trust.bin`. Currently
  dormant (`set_escalate_pinned_key_change` has no production caller anywhere in the tree yet), which is
  exactly why it mattered to close now rather than after a future task wires up a real toggle. Fixed by
  snapshotting the contact's state before/after the call and persisting whenever it actually changed,
  regardless of `Ok`/`Err` — verified this doesn't turn into an unconditional resave (the genuinely-
  no-mutation case still leaves `trust.bin` byte-for-byte unchanged). The original test claiming to cover
  this scenario didn't actually exercise the mutating branch; rewritten to genuinely walk it. The
  identical dormant pattern in `apps/tui/src/screens/verify.rs`'s `apply_action` and `apps/cli/src/
  chat.rs::answer_key_change_warning` was deliberately left unfixed (out of this task's file scope) and
  recorded above so it isn't silently forgotten once escalation ever gets a real toggle.
- **Partial-failure idempotency gap in `AcceptRequest`:** the accept path writes `sessions.bin` then
  `trust.bin` as two separate saves; if the first succeeded but the second failed, a UI retry of the same
  effect would see nothing left to "accept" and silently skip the `TrustStore` pin entirely while still
  reporting success — a live session with no `Contact` record backing it. Fixed by additionally pinning
  whenever a session exists but no matching contact record does yet (using `ChatState::has_session` to
  distinguish a genuine partial-failure retry from a phantom/never-accepted sender, which would otherwise
  look identical from the trust-store side alone), preserving the existing "no unrelated pin on an
  already-fully-completed or phantom retry" guarantee.

`cargo test -p meridian-tui --test run_worker_trust` (12/12), `cargo test -p meridian-tui --test
key_change_adversarial` (7/7, the phase's central security regression suite, unaffected), `cargo test -p
meridian-tui` (full suite), `cargo test -p meridian-cli --bins` (21/21), `cargo fmt --all -- --check`,
`cargo clippy --workspace --all-targets -- -D warnings`, and `bash tools/lint-tui-no-cli.sh` all clean.
"Reject leaves no trace" (`RejectRequestRequest`'s own doc'd invariant) and un-softenable key-change
persistence through a genuinely fresh `TrustStore::open_at_rest` reload were both independently confirmed
by the reviewer, not just asserted by the test suite.
