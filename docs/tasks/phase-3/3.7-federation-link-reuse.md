# 3.7 — Reuse TLS config and one link per federated message (+ SRV failover)

**Phase:** 3 — Review of Phase 2 · **Feature:** review fix (F10 + N2) · **Depends on:** 3.1, 3.3, 3.5 · **Status:** done

## Goal
Stop re-reading the OS trust store and opening two TLS links per routed message; honour SRV
priority/weight with failover.

## Scope
- **In:** build `ClientConfig` once in `FederationRuntime` at startup; `route_foreign` dials once and
  sends `FedReachability` then `FedRoute` on the same link; `dial_foreign` iterates endpoints in SRV
  priority/weight order with failover instead of `.into_iter().next()` (N2).
- **Out:** a persistent connection pool across messages (larger change, own task if wanted); the
  budget accounting (3.5).

## Deliverables
1. `FederationRuntime` gains a cached `Arc<ClientConfig>`; `link::dial` takes it.
2. `apps/rendezvous/src/federation/outbound.rs` — single-link `route_foreign` exchange; `dial_foreign`
   failover loop.
3. `apps/rendezvous/tests/federation_route.rs` — one routed message opens **exactly one** TCP
   connection (count accepts); a first endpoint refusing connections falls through to the second;
   `federation_link_up` does not flap per message.

## Risks / notes
- A cached trust store must still **fail closed** on a rotated/absent CA — moving the load to
  startup changes *when* that failure surfaces (a deliberate side benefit; state it).
- Failover must not relax the domain pin: every candidate endpoint is pinned the same way.
- Restructures the same two functions 3.1/3.3/3.5 edit — hence last in the federation wave.
- Narrows (does not close) the pre-check TOCTOU window 2.8 documented.

## Outcome
Three independent fixes, all restructuring the same outbound dial/route path tasks 3.1 (SSRF
policy check), 3.3 (timeouts), 3.5 (rate-limit accounting), and 3.6 (multi-SAN identity) already
modified:

1. **Cached TLS config.** `link::dial()` no longer rebuilds `rustls::ClientConfig` (re-reading and
   re-parsing the CA bundle/cert chain/private key from disk) on every outbound dial —
   `FederationRuntime` now builds it once at startup, fail-closed and loud on a bad/rotated/absent
   CA. Documented tradeoff, not silently absorbed: this moves a misconfigured cert from "breaks on
   the next dial" to "breaks at boot," matching this codebase's existing misconfiguration posture.
2. **Single-link `route_foreign`.** Used to open two separate TCP+TLS links per one logical routed
   message (one for the internal `FedReachability` pre-check, a second for the real `FedRoute`).
   Now dials once and sends both frames sequentially over the same link (`reachable_on_link`
   extracted from `reachable_foreign`, which stays a public standalone entry point as a thin
   wrapper over `dial_foreign` + `reachable_on_link`). Narrows, but per this task's own Scope does
   not close, the pre-check-to-route TOCTOU window task 2.8 already documented — stated explicitly
   in a doc comment, not overclaimed.
3. **SRV failover (N2).** `dial_foreign` used to try only the first `Discovery::resolve`d endpoint
   and give up. Now iterates every candidate (already SRV priority/weight ordered by `resolve`,
   not re-sorted here) with failover on address-resolution or dial failure. Every candidate is
   pinned exactly the same way, recomputed fresh per iteration from that candidate's own
   `pinned_identity` — never reused or relaxed across a failed attempt.

**Review (security-reviewer + architect + code-reviewer, combined pass): one trivial nit, closed
in the same task.** Traced the domain-pin invariant directly: `expected_domain` is genuinely
recomputed inside the failover loop body per-candidate, and `link::dial`'s full rustls
hostname-verification + belt-and-suspenders SAN/CN re-check runs unweakened for every candidate.
Confirmed task 3.1's SSRF choke point (`policy.admit(hint_domain)`) still fires exactly once per
`dial_foreign` call, before discovery/dial, unaffected by the failover loop or the single-link
restructuring (route_foreign calling dial_foreign once instead of twice makes this check fire
*less* often per message, strictly tighter than before). Confirmed tasks 3.5 (B-side rate-limit
accounting, `inbound.rs`) and 3.6 (multi-SAN extraction/verification, `link.rs`'s SAN logic) are
both structurally untouched by this restructuring. Confirmed the new tests are non-vacuous — the
exactly-one-TCP-connection and N-not-2N-link-open tests count real `accept()`s at an external
counting proxy, and the failover test exercises the second candidate's real mTLS handshake
end-to-end, all of which would read differently against the pre-fix two-dial/no-failover code.
One nit found and fixed: `federation_route.rs`'s new SRV-failover test needed the same
`install_discovery` test seam `federation_outbound_policy.rs` (task 3.1) already had locally;
the move into the shared harness left the original local copy in place rather than deleting it
(byte-for-byte duplicate, not a functional bug, but the harness's doc comment inaccurately said
"promoted" when it was actually just duplicated) — `federation_outbound_policy.rs` now imports
the shared copy instead of keeping its own.
