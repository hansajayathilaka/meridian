# 4.29 — `Effect::LoadSession` + `LiveSession` assembly

**Phase:** 4 — Verification & Trust + Terminal TUI Client · **Feature:** T17 — Terminal TUI Client (gap closure) · **Depends on:** 4.13, 4.15, 4.3 · **Status:** done

## Goal
Give `App` a real, owned `LiveSession { account, trust, chat, contacts }` — the live in-memory session
state screens need once wired into real navigation — and the effect that populates it from disk (or
empty, for a brand-new account), per the architect-blessed shape: moved via `self.session.take()` between
`App` and whichever screen is on top of the stack, never cloned (`TrustStore`/`ChatState` are deliberately
not `Clone`).

## Scope
- **In:** a new `LiveSession` struct (`app.rs` or a new `session.rs`); a new `Effect::LoadSession` variant
  + payload; `run_worker` execution that resolves the right `SecretStore` (Os/File) for an existing
  `account.json`, loads `trust.bin`/`sessions.bin`/`contacts.json`/`state.json`, and reports a populated
  `LiveSession` back via `WorkerEvent::Completed`; extends `Effect::Unlock`'s outcome to carry the loaded
  session directly for the file-backed path, so a live passphrase is never re-threaded across two effect
  round-trips (this crate's existing hand-rolled `Debug` redactions already treat that class of exposure
  as dangerous — don't reintroduce it here).
- **Out:** any screen wiring or navigation decision about *when* to dispatch `LoadSession` (4.36/4.37's
  job); network I/O (account generation/registration/bundle-publish stay in 4.30); the outbound/inbound
  chat effects (4.33/4.35).

## Deliverables
1. `LiveSession` struct bundling `account: AccountDescriptor`, `trust: TrustStore`, `chat: ChatState`,
   `contacts: ContactStore` (exact field set per what `Screen::Main`/`Chat`/`Verify`/`Requests` actually
   need — confirm against each screen's own constructor before finalizing).
2. `Effect::LoadSession` / `LoadSessionEffect` (request: which `SecretStore` kind + `$MERIDIAN_HOME`;
   outcome: populated `LiveSession` or a typed failure).
3. `Effect::Unlock`'s outcome extended to optionally carry a `LiveSession` for the file-backed path.
4. `run_worker`'s account/session-resolution helper (the File-vs-OS-keystore `SecretStore` choice —
   `apps/cli/src/main.rs::load_store`'s logic, reimplemented here since `meridian-tui` cannot depend on
   `meridian-cli`; `TODO: confirm` with architect whether this resolution belongs in `meridian-core`
   instead as a shared helper both crates call, rather than being duplicated).
5. Tests (temp `$MERIDIAN_HOME`, mirroring `apps/tui/tests/at_rest_audit.rs`'s `EnvGuard` pattern):
   no `account.json` → empty/`None` session; existing OS-keystore account → real load; existing
   file-backed account → real load given a passphrase; corrupt/wrong-key `trust.bin`/`sessions.bin` →
   fail closed, never silently reinitialized (mirrors `TrustStore::open_at_rest`'s existing contract).

## Risks / notes
- **Never let a live passphrase cross more than one effect round-trip.** This is why `Unlock`'s own
  outcome is extended rather than adding a second `LoadSession` dispatch for the file-backed path.
- **Fail closed on a corrupt/wrong-key sealed file.** A `LoadSession` that silently treats a decrypt
  failure as "no session" would be a serious regression — surface it as a hard error the caller (4.37's
  Preflight) must handle explicitly, never a quiet reinitialize.
- `TODO: confirm`: whether the File-vs-OS-keystore `SecretStore` resolution belongs in `meridian-core` as
  a shared helper rather than duplicated between `apps/cli` and `apps/tui` — flagged by planning, not
  resolved here; use judgment and record the decision in this task's own Status section.
- No dependency on any other task in this gap-closure set (4.30–4.38) — independently testable today.

## Status
Done. New `apps/tui/src/session.rs::LiveSession { account, trust, chat, contacts }` — the live, owned,
move-only session state screens will need once wired into real navigation (4.35/4.36/4.37), confirmed
against each of `Screen::Chat`/`Verify`/`Requests`/`Settings`'s own doc comments rather than guessed.
`state.json` deliberately excluded (unsealed, no `Screen::*` doc names it as a gap this bundles). New
`Effect::LoadSession` for the OS-keystore/no-account cases; `Effect::Unlock`'s outcome extended to carry
a loaded `LiveSession` directly for the file-backed path, so a passphrase never crosses more than one
effect round-trip. `run_worker`'s loaders distinguish "file doesn't exist" (safe default) from "file
exists but won't decrypt/parse" (hard, fail-closed error) throughout.

**Review (combined `reviewer`, as named) caught a real, empirically-reproduced defect**, not merely a
theoretical one: the original design wrapped `LiveSession` in a `SessionOutcome` newtype whose `Clone`
impl **panicked** if ever called on a populated value, justified by an appeal to `App::current_screen`'s
existing `.expect()` invariant. The reviewer showed that comparison didn't hold — `current_screen`'s
invariant is encapsulation-enforced (a private field, two mutators, neither capable of violating it);
`SessionOutcome`'s depended on every future call site voluntarily not doing something the types freely
permitted — and proved it by building a throwaway palette command wrapping a populated outcome, which
compiled clean and crashed the whole TUI process on a single `F1` press. Fixed by redesigning
`PaletteAction::Effect` into a factory (`Arc<dyn Fn() -> Effect>`, mirroring `PaletteAction::PushPane`'s
already-established shape) rather than a stored, clonable value — this let the panicking `Clone` impl be
deleted outright rather than merely narrowed, turning the hazard into a compile error: the reviewer
independently re-attempted their own original repro against the fix and confirmed it now fails to build
(`LiveSession` isn't `Clone`, so a repeatable `Fn` factory structurally cannot smuggle an owned session
through). Also fixed: a missing symmetric fail-closed guard on `run_unlock` for OS-keystore accounts
(mirroring `run_load_session`'s existing one), and two documentation gaps (this task's own required
Status write-up, and a discoverability note for 4.36/4.37 that a successful `Unlock`'s `LiveSession` is
currently reclaimed by nothing — `App::handle_worker`'s `Screen::Unlock` arm still discards it, since
wiring `App` to actually hold `Option<LiveSession>` is explicitly out of this task's own scope).

`cargo test -p meridian-tui --test load_session` (5/5 + 1 correctly `#[ignore]`d, no OS keychain in this
sandbox), `cargo test -p meridian-tui --test run_worker_account` (8/8), `cargo test -p meridian-tui`
(full suite), `cargo test -p meridian-cli --bins` (21/21), `cargo fmt --all -- --check`, `cargo clippy
--workspace --all-targets -- -D warnings`, and `bash tools/lint-tui-no-cli.sh` all clean.

**Judgment call recorded (review fix, Finding 2): the File-vs-OS-keystore `SecretStore` resolution
stays duplicated in `meridian-tui` (`apps/tui/src/worker.rs`), not extracted into `meridian-core` as a
shared helper.** `worker.rs` already had this exact duplication precedent *before* this task, in
`open_store`/`open_store_for_bulk_signing` (task 4.30) — both explicitly documented as mirroring
`apps/cli/src/main.rs::load_store`'s logic "reimplemented here since `meridian-tui` cannot depend on
`meridian-cli`". This task's own `run_load_session` (the `match descriptor.store { StoreKind::Os =>
..., StoreKind::File => Err(...) }` branch) and `run_unlock`'s symmetric guard just extend that same
already-established, already-duplicated resolution pattern for the two new effects, rather than
introducing a second, differently-shaped mechanism alongside the first. Extracting a shared
`meridian-core` helper now would mean either (a) leaving `open_store`/`open_store_for_bulk_signing`
un-migrated while a new core helper exists only for `run_load_session`/`run_unlock` (two resolution
paths coexisting, worse than one duplicated one), or (b) migrating all four call sites in the same
pass — a cross-cutting `meridian-core` API change out of scope for a gap-closure task whose own Scope
section is `LiveSession` assembly, not a `SecretStore`-resolution refactor. Revisit if/when a third
crate (or a fifth call site) needs this same resolution and the duplication becomes a real maintenance
cost — not resolved as "never move it," just not this task's call to make unilaterally.
