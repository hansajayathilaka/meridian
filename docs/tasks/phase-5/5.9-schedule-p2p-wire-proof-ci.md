# 5.9 — Scheduled CI workflow for `demo/p2p-wire-proof`

**Phase:** 5 — Review of Phase 4 · **Feature:** review fix (F9) · **Depends on:** — · **Status:** done

## Goal
`demo/p2p-wire-proof/` (out-of-band PR #73) substantiates Meridian's headline "no server sees plaintext,
direct P2P" claim, but has no CI trigger at all — its own README says so explicitly. Give it a scheduled
run, mirroring task 3.12's precedent for the rendezvous Docker build gate, rather than leaving the
project's single most load-bearing architectural claim purely human-run indefinitely.

## Scope
- **In:** A new scheduled (weekly, or on-release) GitHub Actions workflow running
  `demo/p2p-wire-proof/run-wire-proof.sh`. `docs/testing/strategy.md`'s stated model already has a
  scheduled soak/ops bucket this fits.
- **Out:** Folding this into the unprivileged `test-harnesses` blocking gate — the demo needs
  `NET_ADMIN`/`NET_RAW` + Docker, capabilities a plain `cargo test` runner doesn't have; this must stay
  a separate, non-blocking scheduled workflow, same shape as 3.12's own precedent.

## Deliverables
1. A new `.github/workflows/*.yml` workflow, `schedule`-triggered (and `workflow_dispatch` for manual
   runs), running the existing demo script unchanged.
2. `docs/testing/strategy.md` and/or `demo/p2p-wire-proof/README.md` updated to reflect it's no longer
   purely human-run.

## Risks / notes
Needs a runner with the demo's own privilege requirements (`NET_ADMIN`/`NET_RAW`, Docker) — confirm the
CI runner used for this workflow actually has them (same class of consideration 1.25's netns topology
work already resolved for the NAT-matrix harness; reuse that precedent rather than re-deriving it).

## Tests
Manual `workflow_dispatch` trigger to confirm the new workflow runs green before merge; no unit/nextest
command applies (infra-only change).

## Reviews
**security-reviewer** (privileged-runner grant, scheduled-secret handling) + **code-reviewer**. Best
implemented by the **devops** agent per this project's own convention for CI/infra changes.

## Status
**Done.** New `.github/workflows/p2p-wire-proof.yml`: `schedule:` (weekly, Monday 07:00 UTC — offset an
hour from `capacity-check.yml`'s existing Monday 06:00 UTC slot) + `workflow_dispatch:`, `permissions:
contents: read` only, runs the existing `demo/p2p-wire-proof/run-wire-proof.sh` unmodified, with a
belt-and-suspenders `if: always()` cleanup step and an `if: failure()` capture-directory artifact upload
for debugging a red scheduled run. Kept as a fully separate, non-blocking workflow — not folded into
`test-harnesses` — per Scope.

**Privilege shape confirmed genuinely different from 1.25's precedent, not just assumed to transfer**:
the demo's `NET_ADMIN`/`NET_RAW` requirement is scoped to a single Docker *container* (`docker run
--network host --cap-add NET_ADMIN --cap-add NET_RAW`, the `monitor` sidecar) — no host root needed, only
a dockerd that permits `--cap-add` (standard, unprivileged Docker behavior, a lesser ask than
`--privileged`, which the script never uses). This is materially narrower than 1.25/`nat-matrix`'s
host-root netns rig. Confirmed by the `reviewer` pass reading the script/compose file directly, not
trusting the report.

**Validated statically only** — no live GitHub Actions run possible from this sandbox: `yamllint` and
`actionlint` (including shellchecking every `run:` block) both clean against the new file and against
existing workflows as a baseline; `bash -n` on the unmodified demo script; manual line-by-line tracing of
the script's actual tool/capability requirements against what the workflow provides. The `reviewer` pass
independently reproduced all of this rather than trusting the implementer's claims, and correctly named
what static validation can't catch (whether the runner's Docker daemon accepts this cap-add/network-host
combo live, Docker Hub rate-limiting on GH's shared IP pool, real end-to-end timing) as a residual risk —
the same category 3.12 itself carried forward, mitigated by a `workflow_dispatch` trial run before merge
per this task's own Tests section.

**One should-fix closed**: added `timeout-minutes: 30` (the `reviewer` pass's own suggestion) as
defense-in-depth against a hung scheduled job silently eating the default 360-minute cap — this job's
release build + compose stack + retries should finish in single-digit minutes.

`demo/p2p-wire-proof/README.md` and `docs/testing/strategy.md` §6 updated to reflect this is no longer
purely human-run.

### Review round
`reviewer` (combined security-reviewer + code-reviewer + architect) — **PASS**, no blocking findings on
any lens. Security: confirmed the capability grant is container-scoped (no `sudo`/`--privileged`
anywhere), `contents: read` matches 3.12's least-privilege precedent, no secrets referenced (the shared
TURN secret is generated fresh per run inside the script), and the failure-only capture artifact contains
no identity key material — only pcaps/logs/canned demo markers, and only surfaces in the exact failure
scenario (an actual leak) it exists to debug. Architecture: genuinely mirrors 3.12's shape, correctly kept
separate from the blocking gate, no ADR contradiction. Code-reviewer: independently reran `actionlint`/
`yamllint` and confirmed the script is byte-for-byte unmodified; one cosmetic nit (yamllint's line-length
warnings are pre-existing repo-wide noise, not new) and the `timeout-minutes` should-fix, both addressed.
