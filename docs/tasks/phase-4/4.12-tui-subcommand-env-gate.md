# 4.12 — `meridian tui` subcommand + environment gate

**Phase:** 4 — Verification & Trust + Terminal TUI Client · **Feature:** T17 — Terminal TUI Client · **Depends on:** 4.11, 4.1 · **Status:** done

## Goal
Wire `meridian-tui` into `meridian-cli` as the `meridian tui` subcommand behind ADR 0020's default-on
`tui` feature, and make the entry point refuse gracefully on an environment that cannot render a TUI.

## Scope
- **In:** `meridian tui` subcommand, feature-gated `tui` (default on); `TERM=dumb` / non-TTY stdout / a
  terminal smaller than 80×24 → a plain-text message naming the equivalent headless CLI command, exit
  code 1, never a garbled screen; verify `cargo build -p meridian-cli --no-default-features` still
  builds and existing demos still run (the dependency-weight risk the feature spec calls out).
- **Out:** screen content; the size-degradation *within* a valid session (4.26, which handles resize
  after entry, not entry refusal).

## Deliverables
1. `apps/cli/src/tui.rs` (or equivalent) subcommand + `tui` feature flag wiring in `Cargo.toml`.
2. Environment-gate check + refusal message.
3. Test: `--no-default-features` build succeeds; a non-TTY/`TERM=dumb`/undersized-terminal invocation
   exits 1 with the CLI-equivalent message, never panics or garbles output.

## Tests
`cargo nextest run -p meridian-cli` · `cargo build -p meridian-cli --no-default-features`

## Reviews
- **reviewer** (combined) — subcommand wiring + a refusal path; moderate stakes, no trust/crypto surface.

## Status
Done. `meridian tui` wired into `meridian-cli` behind a default-on `tui` feature
(`meridian-tui = { optional = true }`, `tui = ["dep:meridian-tui"]`); the subcommand and its module are
genuinely `#[cfg(feature = "tui")]`-gated, not just unreachable, so `--no-default-features` excludes
`meridian-tui`/`ratatui`/`crossterm` entirely (confirmed via `cargo tree`). Pure `check_environment`
gate (`TERM=dumb` → non-TTY → undersized `<80×24`, fails closed on an undetermined size) runs before
anything touches the terminal — `TerminalGuard::install`/raw mode only happen after the gate passes,
inside `meridian_tui::run()`. Refusal is plain text + exit 1, naming the real `meridian chat <id>
--json` equivalent. `.github/workflows/ci.yml` gained an ongoing CI step asserting the
`--no-default-features` exclusion via `cargo tree`, not just a one-time local check.

Combined **reviewer** pass (required) found no blocking issues — correctness, architecture, and (light,
per the task's own framing) security/privacy all passed on the first read. One trivial nit applied:
`unknown_size_is_refused_not_assumed_ok` now also asserts the refusal message names the headless
equivalent, matching its sibling tests. `cargo build -p meridian-cli --no-default-features` +
`cargo tree` (no meridian-tui/ratatui/crossterm), `cargo test -p meridian-cli` (all pass, including 7
`tui::tests::*` covering the exact 80×24/79×24/80×23 boundaries), `cargo fmt --check`, and `cargo
clippy --workspace --all-targets -- -D warnings` all clean.
