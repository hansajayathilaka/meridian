# 8.7 — Delivery-on-reconnect push + `MailboxAck` handling (server)

**Phase:** 8 — Offline Ciphertext Mailbox · **Feature:** T07 · **Depends on:** 8.1, 8.2, 8.3, 8.5 · **Status:** pending

## Goal
Deliver a recipient's queued mail the moment they reconnect, and delete it once acknowledged —
closing the loop 8.5/8.6 opened.

## Scope
- **In:** in `apps/rendezvous/src/ws.rs`'s connection handler, immediately after `AuthOk` is sent
  (before entering the normal frame read loop), drain the authenticated account's mailbox rows via
  8.1's `mailbox_list_for_recipient`, pushing each as `Deliver{from, blob, mailbox_id: Some(id)}` in
  `arrived_at`/`id` order. Add an `Op::MailboxAck` handler: on `MailboxAck{ids}`, call
  `mailbox_delete_by_ids` scoped to the connection's own `account_pub` (never trust `ids` alone —
  the store method's recipient-scoping from 8.1 is what makes this safe), reply `MailboxAckOk{}`.
- **Out:** client-side sending of `MailboxAck` (8.8 — client code lives in a different crate);
  purge-job scheduling (8.9, separate concern from delivery); no change to the live-route
  (`Deliver` without `mailbox_id`) path at all.

## Deliverables
1. Post-`AuthOk` mailbox drain in the connection handler.
2. `Op::MailboxAck` server handler + `MailboxAckOk` reply.
3. Tests: a client with N queued rows receives exactly N `Deliver` frames with `mailbox_id` set, in
   arrival order, before any other traffic; sending `MailboxAck{ids}` deletes exactly those rows and
   no others (including: acking an id belonging to a *different* account's row is a no-op, proving
   the recipient-scoping holds end-to-end, not just at the store layer); a client that never acks
   keeps the rows (deletion is ack-driven, not push-driven) — confirmed via a reconnect that redrains
   the same still-unacked rows.

## Risks / notes
The "never trust `ids` alone" invariant is the single most security-relevant line in this task —
name it explicitly in the PR description and make sure the test in Deliverable 3 (cross-account ack
is a no-op) actually exercises the attack shape (a connected account acking ids it was never sent),
not just a same-account partial ack.

**Carried forward from task 8.2's review:** `mailbox_delete_by_ids` binds one SQL parameter per id
via `QueryBuilder` with no cap, so a very large `MailboxAck.ids` list could eventually hit SQLite's
bound-parameter limit (`SQLITE_MAX_VARIABLE_NUMBER`) and surface as an opaque `StoreError::Backend`.
Cap or chunk the id list here before calling the store method (a `MailboxAck` frame is
attacker/client-controlled input) rather than passing it through unbounded.
