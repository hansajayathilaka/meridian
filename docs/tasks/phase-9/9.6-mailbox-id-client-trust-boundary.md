# 9.6 — Document/validate client trust in `Deliver.mailbox_id`

**Phase:** 9 — Review of Phase 8 · **Feature:** review fix (F3) · **Depends on:** — · **Status:** done

**User surface:** none — client-internal trust-boundary documentation + a private-function refactor for
testability; no client-visible behavior change (Definition of Done gate 9).

## Goal
Resolve the unreasoned trust boundary in `next_deliver` (`apps/signaling/src/client.rs:437-457`): the
client unconditionally accumulates any `Deliver.mailbox_id` it receives — whether from a genuine mailbox
drain or an ordinary live delivery the server happened to tag — into `pending_mailbox_acks`, later
flushed as a real `MailboxAck`. Bounded by `mailbox_delete_by_ids`'s `(recipient_pub, id)` scoping (a
buggy/malicious server can at most trick the client into acking one of its **own** genuine queued rows,
never another account's), but this is architecturally the same class of question ADR 0024 already
reasoned through for `Deliver.from` — and unlike that case, nothing here documents or tests the decision.

## Scope
- **In:** either (a) add client-side validation that ties an acked `mailbox_id` to an actual observed
  drain event (e.g. only accumulate `mailbox_id`s received during/immediately after a recognized drain
  batch, not from every `Deliver` indiscriminately), or (b) explicitly document this as an accepted,
  bounded trust boundary — mirroring ADR 0024's own reasoning about `Deliver.from` — with a comment at
  the call site and a note in the mailbox feature spec or ADR 0024 itself explaining the bound (self-row
  loss only, no cross-account capability, no confidentiality break). Decide which approach during
  implementation; either is acceptable, but the task is not done until one of them lands with a test.
- **Out:** No change to `Deliver.from`'s existing ADR-0024 sentinel handling — this task is scoped to
  `mailbox_id`, a distinct field with distinct (weaker, currently unexamined) trust semantics.

## Deliverables
1. Either client-side validation for `mailbox_id` provenance, or an explicit, tested/documented
   acceptance of the bounded trust boundary.
2. A test constructing a live (non-drained) `Deliver` that carries a `mailbox_id`, proving the chosen
   behavior (rejected/ignored if validation was added; accepted-and-documented if the trust boundary was
   ratified instead).

## Outcome
Chose approach (b): ratified as an accepted, bounded trust boundary rather than adding client-side
validation (the wire protocol has no drain-batch marker to validate against, and the bound is already
narrow — `mailbox_delete_by_ids`'s `(recipient_pub, id)` scoping means the worst case is a client acking
one of its own genuine rows early, never another account's, never a confidentiality break). Extracted
the accumulation logic into a private, unit-tested `record_mailbox_ack` with a doc comment naming the
decision, mirrored in a new `docs/architecture/features/07-offline-mailbox.md` section. ADR 0024 itself
left untouched (accepted ADRs are immutable per `docs/adr/README.md`).

security-reviewer + architect + test-engineer all PASS. One non-blocking should-fix (closed in the same
pass): the write-up now explicitly distinguishes `mailbox_id`'s live stateful-mutation risk (an acked id
drives a real server-side `DELETE`) from `Deliver.from`'s cryptographically inert forgery risk, and ties
the residual to the threat model's already-accepted A2 capability rather than merely asserting "same
class of question."
