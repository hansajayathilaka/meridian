### 2. CLI two-party demo (envelope-v2-only wire proof)

Full transcript: [6.8-demo-transcript.md](./6.8-demo-transcript.md).

- **Live two-party chat**: two real `meridian chat --json` subprocesses (built from this branch),
  talking through a real in-process `meridian-rendezvous::serve` (the same bring-up
  `apps/cli/tests/chat_demo.rs` uses in CI), exchanged a first-contact message-request, a message round
  trip in both directions, and delivery receipts in both directions. This CLI has **no separate
  "confirm-close" command** distinct from delivery receipts — the receipt flow (`"event":"receipt"`,
  task 2.10/4.4) is the acknowledgement flow that exists, and both directions were exercised.
- **Wire-byte proof**: `meridian demo opacity-audit` (T03 deliverable 3) was run to capture the exact
  `Frame`-encoded `Route`/`Deliver` bytes a rendezvous server routes for a scripted conversation driven
  through the same `ChatState`/`meridian-envelope` code path `chat.rs` uses. A standalone decoder
  (depending on the real `meridian-proto`/`meridian-envelope` crates by path, not a reimplementation)
  split the transcript back into 67 individual frames and decoded every `Route`/`Deliver` body's blob as
  a `MessageEnvelope`: **67/67 decoded successfully with `v == 2`, 0 with any other value.** A successful
  decode into `MessageEnvelope` is itself proof of the v2 field shape (`v`, `sender_pub`, `eid`,
  `prekey`, `ct`) — the type has no `sig` field to carry one, and there is no looser/alternate decode
  path in the live code that would accept a `sig`-bearing v1 shape instead.
