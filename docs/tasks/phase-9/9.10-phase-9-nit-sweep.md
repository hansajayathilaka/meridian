# 9.10 — Nit sweep: mailbox-drain proptest, `purge_loop` coverage, double-ack no-op test

**Phase:** 9 — Review of Phase 8 · **Feature:** review fix (N3, N4, N5) · **Depends on:** 9.1, 9.3 (soft)
· **Status:** done

**User surface:** none — test-only coverage additions across three files; no production code change
(Definition of Done gate 9).

## Goal
Close three small, independent test-coverage nits found by this phase's review, bundled into one task
following the precedent of Phase 3's 3.21 and Phase 5's 5.13 nit sweeps (each item is cheap and
test-only; bundling avoids three near-trivial PRs).

## Scope
- **In (three independent items, each a separate test addition):**
  1. **N3** — `apps/core/tests/eid_dedup.rs`: Phase 7's `eid_dedup_holds_under_random_interleavings`
     proptest only drives the live path (`recv_raw`). Extend it (or add a sibling proptest) covering
     `recv_raw_mailbox` (`mailbox_drained: true`) under randomized interleavings, including mixed
     live/mailbox-arrival-order cases (e.g. a message delivered once live, then redelivered via a later
     mailbox drain after a session hiccup) — the ADR 0024 sender-check bypass on this path is new attack
     surface worth the same randomized treatment the live path already got.
  2. **N4** — `apps/rendezvous/src/mailbox_purge.rs`: only the pure `run_purge_once` is tested; the
     scheduled `purge_loop` wrapper has zero coverage. Add a `#[tokio::test(start_paused = true)]` test
     using `tokio::time::pause`/`advance` proving its two documented behavioral claims: the first tick
     fires immediately, and a single purge-pass failure is not fatal to the loop.
  3. **N5** — `apps/rendezvous/src/store.rs` (or wherever the existing mailbox-ack store tests live): add
     a test double-acking an already-deleted same-account row (ack `[id]` once — deletes; ack `[id]`
     again from the same connection) confirming the second ack is a silent no-op, not an error.
- **Out:** No production code changes expected for any of the three items (all describe existing,
  believed-correct behavior that's simply unproven) — if implementation reveals one of them is actually
  broken, split that item into its own task rather than silently fixing it here beyond scope.

## Deliverables
1. Extended/new `eid`-dedup proptest covering the mailbox-drain path (N3).
2. `purge_loop` scheduling test (N4).
3. Double-ack no-op test (N5).

## Risks / notes
Soft dependency on 9.1 and 9.3: N5's new store.rs test and any mailbox-state setup in N3's extended
proptest should exercise the final race-fixed (9.1) and TTL-filtered (9.3) code paths, avoiding a
rewrite if those land first. Not hard-blocking — each of the three items is independent of the other two
and of 9.1/9.3's actual fixes, just sequenced last to minimize rebase churn.

## Tests
`cargo nextest run -p meridian-core -- eid_dedup`, `cargo nextest run -p meridian-rendezvous`.

## Reviews
**test-engineer** (all three items are test-coverage work), **code-reviewer** (light pass, given the
bundled scope).

## Outcome
All three items landed with no production code change. N3 extends task 7.4's `eid`-dedup proptest to
cover `recv_raw_mailbox` under randomized live/mailbox interleavings. N4 adds paused-clock tests proving
`purge_loop`'s first-tick-immediate and survives-one-failure claims. N5 proves a double-ack of an
already-deleted row is a silent `Ok(0)`, not an error.

test-engineer PASS on all three, each independently confirmed non-vacuous via mutation testing — N3 in
particular (the task's own "hard part") was verified by neutralizing the mailbox-path dedup check in
`chat.rs` and watching the proptest catch it with a shrunk 6-step counterexample, restored afterward.
code-reviewer (light pass) PASS, zero blocking/should-fix findings; one non-blocking observation: the two
new `mailbox_purge.rs` tests flaked intermittently only under heavy concurrent `cargo` invocations
sharing one `target/` dir during review (not reproduced across ~95 subsequent clean runs), attributed to
build-cache contention rather than real test-logic flakiness — worth a comment or `debug_assert` on the
`yield_now()` spin-count budget if it's ever observed to flake for real in CI.
