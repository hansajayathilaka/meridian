# 4.42 — Post-accept path to chat/verify with a message-request sender (Defect C)

**Phase:** 4 — Verification & Trust + Terminal TUI Client · **Feature:** T17 — Terminal TUI Client (gap closure, fix for 4.41's Defect C) · **Depends on:** 4.32, 4.36, 4.37, 4.40 · **Status:** pending

## Goal
Make the responder side of a first-contact exchange usable: after accepting a message request in the
live TUI, the sender is reachable through on-screen affordances alone — open a chat, reply, and open the
verification screen — for both account types, and still reachable after a restart. This closes the third
defect the phase's exit gate found (task 4.41, Defect C), the remaining blocker on T17's own acceptance
criterion "a user with **no prior state** reaches a delivered, verified message using only on-screen
affordances."

## The design decision — already made, at plan time
4.41 declined to choose the fix shape, calling it "a genuine design decision, not a mechanical fix"
belonging behind the same kind of pre-code consult task [4.40](./4.40-file-backed-live-session-store.md)
held. **That consult ran during the `/plan-phase` call that created this file** (architect lens; the
security question turned out not to be load-bearing — see below). Its outcome is recorded here and is
**binding on the implementation**. Do not re-litigate it; re-open it only if implementation genuinely
contradicts it, and say so explicitly if you do.

**Verdict: no new ADR, and no further pre-code consult.** Unlike 4.40, nothing here extends key-material
residency or shifts a security posture — `run_accept_request` already TOFU-pins before any decrypt, and
the fix adds one more sealed document write under the `(store, handle)` it already holds.

### The finding that decides the shape
`meridian_core::trust::TrustStore::observe(sender_ik, "", now)` — what `run_accept_request` calls — creates
a `Contact` with **`hint == ""`**. And `apps/identity/src/id.rs::to_id_string` calls `validate_hint`
first, which rejects an empty hint (`HintError::Empty`). So `Contact::id_string()` **fails** for every
accept-observed sender. Three consequences, all load-bearing:

1. **The "show the sender's full `mrd1:` id in the request detail so the user can re-add via `n`"
   workaround is structurally impossible**, not merely un-implemented. `MessageRequest` carries no hint
   (by design — see `screens/requests.rs`'s module doc and `AcceptRequestRequest`'s own doc comment), the
   responder genuinely does not know it, and `n`'s form goes through `parse_id`, which requires a
   canonical `key@hint`. There is no string the UI could render that `n` would accept. 4.41 framed this
   as a UI omission; it is not.
2. Therefore **`Effect::AcceptRequest` is the only code path that can ever create a `contacts.json` row
   for this peer.** Shape A below is not one of two options — it is the only option for the row.
3. The synthesized row must carry **`id: String::new()`, `hint: ""`**. **Do not invent a hint-less
   `mrd1:` form** — that would touch `meridian-identity` (wire-critical, conformance-vectored) and
   contradict [ADR 0001](../../adr/0001-identity-scheme.md)'s self-certifying-key + routing-hint identity.
   That path would need a superseding ADR and must be refused here. Display degrades correctly with zero
   new rendering work: `screens/contacts.rs::ContactEntry::display_label` already falls back
   petname → hint → `short_pubkey`, so the row renders as the same fingerprint the Requests pane showed.

### The three pieces, and which are required
- **Shape A — synthesize a `contacts.json` row on accept. REQUIRED.** `worker.rs::run_accept_request`
  additionally upserts a display row for the sender (the existing `worker::upsert_contact_record` is the
  natural vehicle) and saves it, so `screens/main.rs::build_contact_entries`'s existing join surfaces the
  sender and every existing affordance (`Enter` → chat, `v` → verify, `i` → detail) works unchanged.
  **This does not violate the "locally-deleted contact stays deleted" invariant.** That invariant is
  about the *direction of the join* — `contacts.json` is the display backbone so a stale `TrustStore`
  record *alone* can never resurrect a row. Shape A does not change the join; it adds a **writer** behind
  an **affirmative user act**, which is exactly what `run_add_contact` already does (`trust.observe` +
  `upsert_contact_record`). Accept is the responder-side twin of add; treating them differently is the
  anomaly. Adversarial case is clean: delete → row gone, trust record survives → a *new* request from
  that peer, accepted, recreates the row. Correct — the user affirmatively accepted.
- **Piece C — in-memory propagation into the live `Screen::Main`. REQUIRED, and neither candidate shape
  in 4.41 considered it.** `MainState` owns in-memory `trust` + `chat` + `contacts.entries`, built once by
  `MainState::from_session` at preflight; **nothing re-reads `contacts.json` mid-session**. So Shape A
  alone fixes this only *after a restart* — reproducing 4.41's live symptom one restart later. Every
  mechanism needed already exists:
  - Widen `AcceptRequestEffect.outcome` from `Option<()>` to `Option<AddedContact>` (`app.rs`) —
    `AddedContact` already carries exactly the post-`observe` fields, and `AcceptRequestRequest`'s doc
    comment already anticipates this task.
  - `App` then, for whichever `Screen::Main` is on the stack (the stack-walk idiom already exists in
    `App::reclaim_trust`): `main.trust.observe(sender_ik, "", added.added_at)` — replaying the persisted
    mutation in memory using the **worker-supplied** timestamp, keeping `App::update` pure (no
    `SystemTime::now()` in `crate::screens`/`App`); this is what makes `v` → `Screen::Verify` →
    `mark_verified` work, since without it `TrustStore::mark_verified` errs `UnknownContact`.
    Then `contacts::apply_update(&mut main.contacts, ContactEntry::from_added(added), false)`
    (`apply_update` already pushes when absent), and `main.chat.accept_request(&sender_ik)` — in-memory
    only. Without that last call, a request *restored from `sessions.bin`* at session load stays in
    `main.chat.pending_requests()` forever and **re-appears** on the next `r`/`^R`, because
    `App::requests_snapshot` rebuilds from that in-memory copy. `main.chat` is never saved back here, so
    there is no clobber risk.
- **Shape B — an `OpenChat`-style transition from `Screen::Requests`. OPTIONAL, and severable.** Once
  A+C land, B is *not* required to satisfy the acceptance criterion: Esc → the row is now in Contacts →
  `Enter` opens Chat, `v` opens Verify. Ship it for flow quality, but it is the only piece needing a new
  mechanism (`requests::handle_worker` returns a bare `Vec<Effect>` today, so B needs a new
  `RequestsAction` enum plus an `App` arm reaching down the stack for `Screen::Main`'s `trust`, mirroring
  `MainAction::OpenChat`). **If the diff gets wide, split B into its own follow-up task rather than
  dropping A or C.**

**Why B alone was never sufficient:** `docs/architecture/tui-client.md` §2's screen table routes Verify
via `v` on a *selected contact*, and `Screen::Chat` has no verify affordance at all (no `v`/`OpenVerify`
binding exists in `screens/chat.rs`). So the demo's "`^V` shows the same 60-digit safety number on both →
mark verified" step is reachable on the responder **only through a contacts-list row**. B alone also
leaves the peer absent from `--export-json` and absent after restart.

## Scope
- **In:** Shape A + piece C (both required), Shape B (optional, severable), in `apps/tui` only, plus the
  screen-level test coverage in Deliverables 3–5. The **end-state properties** below are what the tests
  must prove:
  1. After a real `Effect::AcceptRequest` completes, the accepted sender is reachable from the live UI
     using on-screen affordances only: a `Screen::Chat` for that sender can be opened and a reply sent,
     and `Screen::Verify` for that sender can be opened showing the same 60-digit safety number the
     request detail pane showed.
  2. The same holds after a restart (a fresh `App` built from on-disk state only).
  3. The accepted sender's trust state is exactly what `TrustStore` says (TOFU `pinned`, from
     `trust.observe(sender_ik, "", now)`), never `verified`, never fabricated by the UI — read back from
     the real post-mutation `Contact`, mirroring `run_add_contact`'s own "never an assumed fresh-TOFU
     shape" rule (task 4.19 Finding 1).
  4. A request restored from `sessions.bin` and then accepted does **not** re-appear on the next `r`/`^R`
     (the `main.chat.accept_request` half of piece C).
- **Out:** the ~188 s file-backed prekey republish (task
  [4.43](./4.43-file-backed-republish-performance.md) — different code path, different concern); loading
  a chat's persisted transcript when a chat opens (task [4.44](./4.44-chat-history-load-on-open.md) —
  this task must not silently absorb it, and its tests must not depend on it); **surfacing a live inbound
  message when no matching `Screen::Chat` is open** (4.41's traced gap in `app.rs::handle_inbound`'s
  `InboundEvent::Message` arm) — Shape A *mostly* dissolves this, since the sender becomes a real
  contact, but the "no unread indication while no chat is open" half survives; named here, deliberately
  deferred, not silently absorbed. Also out: any new wire type, protocol or crypto change; any change to
  the trust state machine, to `verification-ux.md`'s wording, or to the key-change block/warn gate;
  offline delivery (T07); inventing any hint-less `mrd1:` id form (see the ADR 0001 guardrail above).

## Deliverables
1. Shape A: `run_accept_request` upserts and saves the sender's `contacts.json` row (`id: String::new()`,
   `hint: ""`), **idempotent under retry** — mirroring the existing `accepted || pin_still_owed` rule so a
   same-effect retry never creates a row for a sender with no session. The write must go through
   `crate::store::contacts::save` (sealed via `at_rest::seal`) per
   [ADR 0021](../../adr/0021-client-local-store-config-formats.md); no schema change; `conv_handle` stays
   `None` until a conversation is first opened.
2. Piece C: `AcceptRequestEffect.outcome` widened to `Option<AddedContact>`, plus the `App` stack-walk
   replaying `trust.observe` (worker-supplied timestamp), `contacts::apply_update`, and
   `main.chat.accept_request` into the live `Screen::Main`.
3. **Screen-level test coverage — the level `live_session_e2e.rs` structurally cannot reach.** 4.41's
   `test-engineer` pass confirmed that test never touches `apps/tui/src/screens/`, which is exactly why
   three exit-gate attempts passed while the live UI was broken. Minimum: a test driving **real key
   events** through `App` — open Requests with a queued request, `a`, `y`, await the real
   `Effect::AcceptRequest` completion, `Esc`, then assert the sender is reachable (Contacts row present),
   a reply actually dispatches `Effect::SendMessage` for that peer, and `Screen::Verify` is reachable and
   renders the same safety number. Site: extend `apps/tui/tests/screens_requests.rs` /
   `apps/tui/tests/screen_main.rs`, or a new `apps/tui/tests/accept_to_chat.rs` — implementer's call,
   documented.
4. A **restart** test: rebuild session state from disk only (the pattern `apps/tui/tests/preflight.rs` and
   `apps/tui/tests/live_session_file_backed.rs` already use) and assert the accepted sender is still
   present/reachable — end-state property 2.
5. Coverage for end-state properties 3 and 4: the rendered trust state is the real `TrustStore` one
   (`pinned`, not `verified`), `run_accept_request` stays idempotent under a repeated dispatch (extend
   `apps/tui/tests/run_worker_trust.rs`), and an accepted-then-restored request does not re-appear.
6. **Record the resolution — do not leave it floating.** `screens/main.rs::build_contact_entries`'s
   standing `TODO: confirm` (introduced by task 4.36 in `fda008c`: "no design doc … resolves whether an
   accepted message-request sender should get a synthesized `contacts.json` row") is resolved in place,
   citing this task. Add the accept transition to `docs/architecture/tui-client.md` §2's "Reached by"
   column. Decide-or-explicitly-defer the accepted `intro` → transcript question that
   `AcceptRequestRequest`'s doc comment hands to this task.
7. `docs/tasks/phase-4/README.md`'s T17 exit-criteria bullet updated to record Defect C as closed. **The
   checkbox itself stays unflipped** — that flip belongs to
   [4.45](./4.45-t17-acceptance-demo-closure-attempt-4.md), exactly as 4.39/4.40 left it for 4.41.

## Risks / notes
- **This is the phase's blocking defect.** Three exit-gate attempts in a row each found a real defect; do
  not treat the coverage as decorative. The specific failure mode that let this ship undetected —
  worker-level tests green while the screen layer had no path at all — is named in Deliverable 3 and must
  actually be closed, not narrated.
- **`MainState.trust` is moved, not cloned.** `screens/main.rs::handle_key` `std::mem::take`s
  `state.trust` when building a `Chat`/`Verify` screen and relies on reclaim-on-pop. Any new construction
  path must respect the same discipline — a second, divergent in-memory `TrustStore` copy is exactly the
  bug class `App::reclaim_trust` exists to prevent.
- **Trust is security-critical here.** An accepted request produces a TOFU pin, nothing more. Any UI
  implying more (a "verified" glyph, a skipped safety-number step, a dismissible key-change warning) is a
  blocking finding for `security-reviewer` per T17's spec and `docs/security/verification-ux.md`.
- **Do not weaken any existing assertion** to make the new path fit, here or in 4.39's/4.40's tests. In
  particular the three `*_fails_closed_with_an_actionable_message` tests in `run_worker_contacts.rs`,
  `run_worker_trust.rs` and `run_worker_chat.rs` must keep passing unmodified.
- **`upsert_contact_record` carries its own `TODO: confirm`** about re-add semantics for `added_at`,
  `policy_override`, `conv_handle` and `unread`. That note now applies to the accept path too — restate it
  accurately rather than silently changing its meaning.
- **Doc inconsistency to flag, not to "fix" in code:** feature spec 17 says `^V`, `tui-client.md` §2 says
  `v` on a selected contact, and the code implements `v`. Route through `/doc-sync`; do not change the
  keybinding to match the spec prose.
- **The CLAUDE.md "additive surfaces register via the TUI extension contract, never by editing the TUI
  core" rule does not apply here.** Requests/Main/Contacts are T17 core screens; this repairs their
  existing wiring rather than adding a feature surface. Definition of Done gate 9 is satisfied
  intrinsically, in the same sense 4.36/4.40 were. No `SurfaceRegistry` registration is added.
- No logical dependency on 4.43 or 4.44; all three touch disjoint code paths. Land order only matters to
  avoid a simultaneous diff — see the phase README's dependency order.
