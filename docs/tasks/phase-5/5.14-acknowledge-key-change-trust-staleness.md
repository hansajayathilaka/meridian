# 5.14 — `run_acknowledge_key_change` has the same `contacts.json` trust-staleness bug as F3

**Phase:** 5 — Review of Phase 4 · **Feature:** review fix (follow-up to F3, found by 5.3's own review) ·
**Depends on:** 5.3 · **Status:** done

## Goal
Close the second instance of the trust-staleness bug 5.3 fixed for `run_mark_verified`.
`run_acknowledge_key_change` (`apps/tui/src/worker.rs`) mutates `TrustState` to `Pinned` (normal ack) or
`Blocked` (escalation) via `TrustStore::acknowledge_key_change` and calls `save_trust`, but never touches
`contacts.json`. A contact that was `PinnedKeyChanged` (mirrored into `contacts.json` as `Pinned`, per
`to_trust_label`'s approximation) that gets escalated to `Blocked` still shows `"trust": "pinned"` in
`--export-json` — the exact bug class 5.3 exists to close, reproduced in a code path 5.3's Scope didn't
name.

## Scope
- **In:** `apps/tui/src/worker.rs::run_acknowledge_key_change` — apply 5.3's own write-through pattern
  (reload `contacts.json`, patch the matching row's `trust` field via the existing `to_trust_label`
  helper, save), inside whatever async/blocking shape the function already has. Consider, as part of
  this task, whether an export-time join in `apps/tui/src/store/export.rs::export_json` (5.3's own
  rejected alternative) would close this and any *future* instance of the same bug class at once,
  instead of requiring a write-through patch at every trust-mutating call site — 5.3's review round
  flagged this as worth revisiting now that a second instance has been found, but did not decide it.
- **Out:** Any change to `trust.bin`'s own on-disk format, or to the live in-memory join
  `build_contact_entries` already performs correctly. Any change to `run_mark_verified`/`run_set_petname`
  (5.3/5.4's own scope, already closed).

## Deliverables
1. The chosen fix (write-through mirroring 5.3, or an export-time join superseding both) landed.
2. A bug-pinning test mirroring 5.3's own discipline: first proves today's wrong output (a `Blocked`
   escalation still reads `"trust": "pinned"` after export), then flips to asserting the correct value
   once the fix lands, in the same PR.
3. If an export-time join is chosen instead of write-through, this task's own file should record why —
   including whether it also lets 5.3's write-through be simplified or left as harmless redundant
   belt-and-suspenders (implementer's call, documented either way).

## Risks / notes
Mirrors 5.3's own inherited, not-newly-introduced crash-window risk (a crash between the two writes
leaves the documents briefly disagreeing) if write-through is chosen again — same accepted precedent, not
a new concern.

## Status
**Done.** Fix approach chosen: **export-time join, superseding both 5.3's write-through and the
need for a second write-through in `run_acknowledge_key_change`** — not a mirror of 5.3's pattern.

**Why the join over a second write-through.** This is the *second* independent instance of the
identical bug (5.3 for `run_mark_verified`, this task for `run_acknowledge_key_change`'s escalation
branch), and the task's own Scope explicitly asked whether an export-time join would close "this and
any *future* instance of the same bug class" rather than requiring a write-through patch at every
trust-mutating call site reviewed by hand, forever. Given a second instance surfaced without anyone
adding a new trust-mutating handler — it was found in an *existing* handler 5.3's own Scope simply
didn't name — the write-through pattern demonstrably does not scale as a review discipline: every
future trust-mutating call site would need an implementer/reviewer to remember this exact pattern.
An export-time join closes the bug class structurally at its one true choke point
(`apps/tui/src/store/export.rs::export_json`) instead: it is now correct by construction for *any*
call site that mutates `trust.bin`, present or future, including ones nobody remembers to special-case.

**Mechanism.** `export_json` now loads `trust.bin` (reusing `crate::worker::load_trust`, widened
from private to `pub(crate)`) immediately before serializing `contacts.json`, and overwrites each
row's `trust` field with `crate::worker::to_trust_label(contact.state)` for any pubkey with a
matching `trust.bin` record — the exact join `crate::screens::main::build_contact_entries` already
performs for the live UI, reusing its exact `TrustState -> TrustLabel` mapping function (also widened
to `pub(crate)`) rather than a second, independently-maintained copy. A row with no matching
`trust.bin` record (an inconsistent store) is left at whatever `contacts.json` already had — the same
defensive fallback `build_contact_entries` uses, never a hard error. A `trust.bin` that exists but
fails to open (tamper/corruption/wrong key) is a hard `StoreError` (new `StoreError::TrustLoad`
variant in `apps/tui/src/store/migrate.rs`) that aborts the whole export — fails closed, matching
this store family's existing `SealFailure` doctrine, rather than silently falling back to a possibly
stale `contacts.json` value.

**`run_acknowledge_key_change` itself is untouched** — no write-through, no `spawn_blocking` change.
With the join in `export_json`, a write-through there would be pure dead work on every call (the
exported value is always overwritten regardless of what `contacts.json` says). Investigated per this
task's own Scope note: it currently runs synchronously (not `spawn_blocking`-wrapped) — this is *not*
new to this task; it's the pre-existing, explicitly documented residual from task 5.4's own Status
("only these two [`run_mark_verified`/`run_set_petname`] ... touched. The remaining ones stay task
4.51's named, unowned residual" — `run_acknowledge_key_change` was never one of the two 5.4 scoped
in). Since this task's chosen fix makes zero functional changes to `run_acknowledge_key_change`'s
body, there is nothing new here to wrap, and doing so would be unrelated scope creep against a
function this task's Scope only asked about, not to necessarily change.

**5.3's write-through in `run_mark_verified` was deliberately left in place, not removed or
simplified** — explicitly permitted either way by this task's own Scope. It is now genuinely
redundant for `export_json`'s purposes (the join overwrites it regardless), but it is **not** dead
weight: `build_contact_entries`'s defensive fallback (a `trust.bin` record missing entirely) still
reads `contacts.json`'s own `trust` field, so keeping it accurate still has real value outside the
export path. Left as harmless belt-and-suspenders, not simplified away, to avoid re-touching an
already-reviewed, already-closed task's function for a change that isn't required.

**Bug-pinning test**: `tests/run_worker_trust.rs`'s new
`acknowledge_key_change_escalation_is_not_stale_in_export_json` reuses the exact escalation fixture
`acknowledge_key_change_under_escalation_force_blocks_and_still_fails_closed` already proves persists
to `trust.bin` (a `PinnedKeyChanged` contact force-blocked via `set_escalate_pinned_key_change` +
a real `AcknowledgeKeyChange` dispatch), asserts `contacts.json`'s own row is still stale at `Pinned`
(fixture sanity — `run_acknowledge_key_change` deliberately gets no write-through), then calls the
real `export_json` and asserts the exported row reads `Blocked`. Verified by hand, same discipline as
5.3: temporarily reverted the `join_live_trust` call in `export_json`, reran just this test, and
confirmed it fails with the exact wrong value the bug describes (`left: Pinned, right: Blocked`),
then restored the fix and reconfirmed green.

**Gate 9:** no new TUI surface — a persistence/export correctness fix to an existing surface's
backing plumbing, same "no surface" reasoning 5.3/5.4 themselves used.
