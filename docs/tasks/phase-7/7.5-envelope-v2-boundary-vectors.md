# 7.5 — Boundary-case conformance vectors for `envelope-v2.json`

**Phase:** 7 — Review of Phase 6 · **Feature:** review fix (F7) · **Depends on:** — · **Status:** done

## Goal
Add boundary-shape vectors to `test-vectors/envelope-v2.json` beyond the existing three
near-identical-`ct` cases, so the conformance suite exercises edge shapes, not just one canonical case.

## Scope
- **In:** `tools/xtask/src/vectors/envelope.rs`'s `generate_envelope_v2` — add to the `cases` list:
  1. An empty-`ct` boundary case (`ct: vec![]`).
  2. A large-`ct` boundary case, paired with the existing maximal-preamble shape (`prekey-with-opk`
     already covers the largest *preamble* variant, since `Prekey`'s fields are fixed-width 32-byte
     arrays — there's no smaller/larger preamble shape to add; the genuinely untested boundary is `ct`
     length). `TODO: confirm` with architect: no design doc specifies a maximum envelope/`ct` size —
     propose a representative "large" size (e.g. 65535 bytes) rather than inventing one silently; get
     architect sign-off on the exact byte count before regenerating.
  Regenerate via `cargo run -p xtask -- vectors`; the existing three vectors must stay byte-identical
  (confirm via `git diff`) — only new vectors are added.
- **Out:** `tools/xtask/src/vectors/ratchet.rs`/`ratchet-v2.json` — F7's finding names only
  `envelope-v2.json`/`envelope.rs`; `ratchet-v2.json` already varies its preamble per-step and has no
  analogous thin-coverage gap. If broader `ratchet.rs` vector coverage turns out to be warranted, that's
  a scope expansion beyond this finding and belongs in a future review, not silently folded in here.

## Deliverables
1. Updated `generate_envelope_v2` with the two new cases.
2. Regenerated `test-vectors/envelope-v2.json`.

## Risks / notes
The `TODO: confirm` on the large-`ct` byte count is a real open question, not a rubber-stamp — get
architect sign-off on the specific size before regenerating, not after.

## Status
**Done.** Pre-start architect consult (this task's own required first step, per its `TODO: confirm`)
decided: **65536 bytes (64 KiB)** for the large-`ct` boundary vector — matches the codebase's one
existing "large payload" constant (`mrd.file/1`'s file-transfer chunk size,
`docs/api/stream-types-v1.md:104`) and is the first value requiring ciborium's 4-byte CBOR length
prefix under RFC 8949's canonical encoding (a real codec-class boundary, not an arbitrary round
number). Both new vectors (`ct-empty`, `ct-large`) pair with the same maximal `prekey-with-opk`
preamble shape rather than varying it, since `Prekey`'s fields are fixed-width with no interaction bug
to catch against `ct` length.

Added to `tools/xtask/src/vectors/envelope.rs`'s `generate_envelope_v2`: a `maximal_prekey()` closure
(deduplicating the `prekey-with-opk` field values) and two new cases, `ct-empty`/`ct-large`.
Regenerated `test-vectors/envelope-v2.json` via `cargo run -p xtask -- vectors` — the three existing
vectors stay byte-identical (26 insertions, 0 deletions; only the two new vector objects appended).
`ratchet.rs`/`ratchet-v2.json` untouched, per F7's declared scope.

### Review round
`reviewer` (combined architect + code-reviewer; architect mandatory, conformance-vector changes are
wire-critical) — **PASS**, no findings. Architect independently re-derived rather than trusted every

files); sanity-checked 65536 against the repo's one existing hard size ceiling (the 1 MiB federation
frame limit) to confirm no collision. Code-reviewer confirmed the three pre-existing vectors' `ct`
values are byte-identical to before, `maximal_prekey()` produces the same struct as the inlined
literal it replaced, and no dead code/clippy smell.
