# 4.31 — Real `run_worker`: contacts & contact-detail persistence

**Phase:** 4 — Verification & Trust + Terminal TUI Client · **Feature:** T17 — Terminal TUI Client (gap closure) · **Depends on:** 4.19 · **Status:** done

## Goal
Execute `AddContact`/`ImportContactQr`/`SetPetname`/`SetUserBlocked`/`SetPolicyOverride`/`DeleteContact`
for real, so the Contacts and Contact Detail screens' actions actually persist.

## Scope
- **In:** `run_worker` arms for these six effects, mirroring `apps/cli/src/contact.rs::cmd_add`/
  `cmd_rename`/`cmd_block` and — direct prior art — `apps/tui/tests/at_rest_audit.rs`'s own hand-rolled
  worker logic for this exact group (same `TrustStore::observe` → conditional `set_petname` order, same
  "read the real post-`observe` `Contact` back, never assume a fresh-TOFU shape" discipline
  `AddedContact`'s own doc comment already requires).
- **Out:** navigation (Contacts/ContactDetail screens already push/pop correctly once reached — reaching
  them live is 4.36/4.37's job).

## Deliverables
1. Six `run_worker` arms: `AddContact`, `ImportContactQr`, `SetPetname`, `SetUserBlocked`,
   `SetPolicyOverride`, `DeleteContact`.
2. Tests per effect against a real temp store, including the re-add-of-already-known-contact edge case
   `AddedContact`'s own doc comment calls out explicitly (must not regress TOFU state or petname on a
   duplicate add).

## Risks / notes
- **Petname is never derived from wire content** — reconfirm this worker path only ever writes the
  petname the screen already validated locally, never anything sourced from the peer.
- No dependency on 4.29, 4.30, or any other task in this gap-closure set — independently testable today.

## Tests
`cargo nextest run -p meridian-tui --test run_worker_contacts` (new file).

## Reviews
- **reviewer** (combined: security-reviewer for the petname-never-from-wire and real-trust-state
  invariants; code-reviewer for correctness).

## Status
Done. `apps/tui/src/worker.rs` gained real `run_worker` arms for `AddContact`/`ImportContactQr`/
`SetPetname`/`SetUserBlocked`/`SetPolicyOverride`/`DeleteContact`, mirroring `apps/cli/src/contact.rs`'s
own call sequences, plus the QR-decode path from `verify.rs`. Each effect is a single, complete
load-mutate-save disk round-trip (no `LiveSession` needed — that's later tasks' job); `open_account_store`
resolves `StoreKind::Os` accounts directly and fails closed with an actionable message for
`StoreKind::File` accounts, since no cached, already-unwrapped store exists anywhere yet for that path
(see the escalation note below). `AddedContact`'s re-add correctness (task 4.19 Finding 1: real
post-`observe`/post-`set_petname` values, never an echo of the request, never clobbering an existing
petname on a blank re-add) is preserved end to end. New `image` dependency (PNG-only, workspace-pinned,
matching `apps/cli`'s own) for QR decoding.

**Review (combined `reviewer`, as named):** clean pass on all lenses (correctness, security, architecture)
with two findings worth closing before finalizing, both fixed:
- **Test-coverage gap:** the "re-add an already-present contact" path only ever exercised the *insert*
  branch of `upsert_contact_record` (via a `DeleteContact` first) — the *update-in-place* branch (the one
  actually carrying the task's own flagged judgment call about which fields survive a re-add) had zero
  coverage. Fixed with a new test that re-adds a still-present contact with no delete in between,
  confirming `TrustStore`-owned fields update while purely-local `contacts.json` fields
  (`added_at`/`policy_override`) survive untouched.
- **Assertion strength:** one "only touches contacts.json" test compared four hand-picked `Contact`
  fields instead of full-document/byte equality, unlike its sibling test for the opposite direction.
  Tightened to full sealed-`trust.bin`-bytes equality.

**Escalated, not silently dropped:** the reviewer flagged that `open_account_store`'s file-backed-account
fail-closed behavior — correct and honestly documented for *this* task — risks becoming a permanent,
unshipped limitation once 4.36/4.37 give `App` a live, already-unlocked session: nothing yet threads that
cached store into 4.31/4.32's handlers, so a passphrase-keyfile TUI user would still be unable to manage
contacts even after Preflight lands, unless a task explicitly closes it. Recorded as a Risks/notes item on
both [4.36](./4.36-screen-main-live-navigation.md#risks--notes) and
[4.37](./4.37-preflight-routing.md#risks--notes)'s own task files rather than left implicit, so 4.38 can
verify it was actually addressed (or explicitly, visibly carried forward) rather than quietly shipped.

`cargo test -p meridian-tui --test run_worker_contacts` (17/17), `cargo test -p meridian-tui` (full
suite), `cargo test -p meridian-cli --bins` (21/21), `cargo fmt --all -- --check`, `cargo clippy
--workspace --all-targets -- -D warnings`, and `bash tools/lint-tui-no-cli.sh` all clean. The reviewer
also independently reproduced and confirmed a proactive flakiness fix (a `keyring` v4 one-time
platform-detection race in the test harness, unrelated to production code) — empirically verified as a
genuine race-elimination, not a probability reduction.
