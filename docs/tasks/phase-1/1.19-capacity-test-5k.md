## Status
**Done** — both halves of the task's "or": the referenced `--ignored` test now exists **and** the

### Landed
- `apps/rendezvous/tests/rendezvous.rs`: `capacity_concurrent_connections`, `#[ignore]`d, targeting
  5,000 by default and overridable via `MERIDIAN_CAPACITY_CONNS`. The old 250-connection smoke test and
  the capacity run now share one `hold_n_concurrent_connections(n)` helper, so both measure the same
  thing. The **dangling comment reference is gone** — it pointed at
  `cargo test --release -- --ignored capacity`, which matched no test.
- `preflight_fd_limit()` reads `/proc/self/limits` and aborts with the exact `ulimit -n` value to set,
  instead of dying partway through with an opaque `EMFILE`. No-ops off Linux.
- `docs/architecture/features/02-rendezvous-mvp.md`: a "Capacity status" section; the acceptance line
  now points at it rather than asserting 5k unqualified.

### Measured
**2,000 concurrent authenticated WSS connections**, held simultaneously, server reporting
`meridian_connections_active 2000`, in **0.82 s** (release, 4-vCPU dev container).

**5k was not achievable here, and the reason is the sandbox, not the server.** This container's fd
limit is 4096 **hard** (`ulimit -Hn` = 4096, so it cannot be raised), and the test drives both ends
in-process at ~2 fds per connection — a ceiling of ~2,000. The preflight correctly refused the 5k run:

```
fd limit too low for a 5000-connection capacity run: soft limit is 4096, need >= 10064
(~2 fds per in-process connection). Raise it (`ulimit -n 10064`) or set MERIDIAN_CAPACITY_CONNS
to a target this box can hold.
```

So **5k is neither demonstrated nor disproven** — the server showed no strain at 2k, but the criterion
stays open until the test is run on a box with the fds. That is recorded in the spec rather than
quietly downgraded to 2k or left looking proven.
