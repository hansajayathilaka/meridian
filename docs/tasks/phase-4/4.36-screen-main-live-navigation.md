# 4.36 — `Screen::Main` + live navigation

**Phase:** 4 — Verification & Trust + Terminal TUI Client · **Feature:** T17 — Terminal TUI Client (gap closure) · **Depends on:** 4.29 · **Status:** pending

## Goal
Build the real post-auth home screen and wire the navigation every screen's own doc comment has been
deferring to "a future task": `Contacts` → `Chat`, `Contacts`'s `v` → real `Screen::Verify` (replacing
the "not implemented yet" stand-in from task 4.19), `Ctrl-R`'s live `pending_requests()` snapshot, and
the palette's Settings registration.

## Scope
- **In:** new `screens::main` module + `Screen::Main` variant, constructed from a `LiveSession`
  (task 4.29's type — this task can be built and tested with a fabricated `LiveSession`, zero dependency
  on Preflight existing, same incremental pattern this whole phase already used for every other screen).
  Repoint `Contacts`'s `Enter` to open `Screen::ContactDetail` via its own dedicated key and give `Chat`
  its own — per `crate::screens::contacts`'s and `Screen::Chat`'s own doc comments naming this exact
  repoint as deferred. Register a working "open Settings" palette command now that a live
  `config`/`config_path` exists.
- **Out:** Preflight (deciding *when* `Screen::Main` is reached — 4.37's job). Explicitly document that
  `Ctrl-R`'s queue reflects `pending_requests()` **as of session load**, not live arrivals during the
  running session (that's 4.35's contribution) — same honest-scoping discipline this crate already uses
  elsewhere (e.g. 4.28's own documentation of what does and doesn't work).

## Deliverables
1. `screens/main.rs`, `Screen::Main`.
2. Updated `Contacts`/`ContactDetail`/`Chat`/`Requests`/`Verify` key-dispatch routed through it.
3. Palette registration for Settings.
4. Screen-snapshot tests at 80×24 and narrow width (mirroring task 4.26's degradation-test conventions).

## Risks / notes
- Independent of 4.30–4.35's *completion* — this task can be built/tested with a fabricated `LiveSession`
  the same way every prior screen task tested against fabricated state before its own navigation task
  landed.
- Depends only on 4.29 (`LiveSession` type to construct from).
- See [4.37's own Risks/notes](./4.37-preflight-routing.md#risks--notes) for a residual gap 4.31's review
  escalated: once a live, already-unlocked session exists (this task + 4.37 together), `run_worker`'s
  already-built contacts/trust handlers (4.31/4.32) still re-derive their own store from disk per
  dispatch rather than reusing it — harmless for OS-keystore accounts, but file-backed accounts still
  fail closed on every contacts/trust action even after Preflight lands, unless a follow-up task closes
  it. Not this task's own scope to fix (it owns screen content/navigation, not `run_worker` internals),
  but worth knowing before treating 4.29–4.38 as having fully closed every angle of the T17 gap.

## Status
Done. Gives `meridian-tui` a real `Screen::Main` hub, tested throughout against a fabricated
`LiveSession` per this task's own scope note (zero dependency on Preflight/task 4.37, zero dependency
on a real `run_worker`).

**`crate::screens::main` (new file, `apps/tui/src/screens/main.rs`)** — `MainState`/`MainAction`/
`handle_key`/`handle_worker`/`render`/`render_with_ctx`, plus the join
`crate::screens::contacts`'s own module doc named as belonging to "a future `Screen::Main`/`Preflight`
step": `build_contact_entries(trust: &TrustStore, contacts: &ContactsDocument) -> Vec<ContactEntry>`
drives off `contacts.contacts` (not `trust.contacts()`), so a contact whose local display row was
removed by `Effect::DeleteContact` stays absent even though its `TrustStore` record survives, matching
that effect's own documented semantics. `MainState::from_session` builds this from a real
`crate::session::LiveSession` (task 4.29) and keeps `account`/`trust`/`chat` on the screen directly —
finally giving `App` the live `TrustStore` every other screen's own doc comment had been waiting on.
Renders the already-built `crate::screens::contacts` pane (via a new, purely additive
`contacts::render_in(state, frame, area, ctx)` — `render_with_ctx` is now a one-line wrapper around it,
so every pre-existing call site/snapshot test is untouched) above a `crate::statusbar` row — **not**
tui-client.md §2's full three-region mockup composite, which §10 already documents as out of scope for
any one task; this is "the real home screen" in the sense of live navigation, not a pixel-for-pixel
mockup realization.

**Key repoint — resolved per the doc comments, not the (differently-worded) task-file prose.** The
task file's own "Repoint `Contacts`'s `Enter` to open `Screen::ContactDetail`... and give `Chat` its
own" sentence reads, taken literally, as the opposite of what `crate::screens::contacts`'s and
`crate::app::Screen::Chat`'s own doc comments unambiguously specify ("a future task repointing `Enter`
at this screen [`Screen::Chat`]... giving `ContactDetail` its own dedicated key at that point" —
`Screen::Chat`'s doc comment, verbatim; `crate::screens::contacts`'s own doc comment says the same
thing about itself). Per this task's own instruction to read those doc comments "for the exact
deferred intent," this task follows them: **`Enter` now opens `Screen::Chat`; `i` ("info") is
`ContactDetail`'s new dedicated key.** No design doc pins the exact letter for the latter — flagged
as a `TODO: confirm`-shaped judgment call in `contacts.rs`'s own comment on that match arm, for the
reviewer. `v` now opens a real `Screen::Verify` (replacing task 4.19's "not implemented yet" stand-in
notice, which is now removed along with its `ContactsState::notice`-setting code path). Both key
repoints only *return* the new `ContactsAction::OpenChat`/`OpenVerify` variants —
`crate::screens::contacts` still has no live `TrustStore`/`account` of its own to build a real
`Screen::Chat`/`Screen::Verify` from; only `crate::screens::main::handle_key` (which owns both) does
that construction, moving `MainState::trust` out via `std::mem::take` (mirrors the manual "Reclaim the
(unmutated by chat) TrustStore back out of the popped Chat screen" idiom
`apps/tui/tests/at_rest_audit.rs` already used by hand). A standalone `Screen::Contacts` (pushed
without a backing `Screen::Main`, e.g. in its own pre-existing tests) treats both new actions as a
no-op — documented in `App::handle_key`'s `Screen::Contacts` arm — since it genuinely has nothing to
build either child screen from.

**Reclaim-on-pop, generalized (`App::reclaim_trust`, `apps/tui/src/app.rs`).** `Screen::Chat`'s and
`Screen::Verify`'s own `Esc`-pop arms now search the screen stack for a `Screen::Main` and move the
popped screen's own (possibly-mutated) `TrustStore` back into it, then rebuild that one contact's
`ContactEntry` row (`crate::screens::main::refresh_entry`) from the live post-mutation `Contact` —
preserving the display-only fields (`policy_override`/`added_at`/`last_activity_at`/`unread`) from
whatever row already existed. Without this, a `Screen::Verify` mark-verified would leave `Screen::
Main`'s own contacts list showing a stale trust glyph until some future full reload; confirmed by
`v_opens_verify_and_marking_verified_is_reflected_in_mains_contacts_list_after_esc`
(`apps/tui/tests/screen_main.rs`). A no-op (the `TrustStore` is simply dropped) if no `Screen::Main` is
on the stack — the same "pushed directly in a test" case every other screen already tolerates.
`App::apply_contact_update` (the existing `ContactDetail`-pops-back-into-`Contacts` reconciliation) was
extended the same way, for `Screen::Main`'s own embedded contacts list.

**`Ctrl-R`/Contacts' own `r` — live snapshot, scoped exactly as the task file's own Out-of-scope note
specifies.** `App::requests_snapshot` (new) searches the stack for a `Screen::Main`, reads its
`chat.pending_requests()` (a `meridian_core::chat::ChatState` read, in-memory only, never mutated
afterward by this task), and merges it with whatever is still queued in `App::pending_inbound_requests`
(task 4.35's live-arrivals buffer), deduped by `sender_ik`. Both the global `Ctrl-R` handler and
`Screen::Main`'s own `MainAction::OpenRequests` (from the embedded Contacts pane's `r`) now call this
one shared helper, so the two dispatch paths can never diverge. **Explicitly documented narrowing,
exactly as the task file's own Out-of-scope note requires:** this is a snapshot *as of session load* —
`MainState::chat` is populated once at construction and never mutated by this module afterward, so
accepting/rejecting a request in an opened `Screen::Requests` (task 4.21, unchanged) does not reach
back into it; a second `Ctrl-R` later in the same run could show an already-decided entry again
alongside anything genuinely new. Live arrivals *during* the running session remain entirely task
4.35's own, already-built mechanism.

**Settings palette command (deliverable 3).** `crate::surface::PaletteAction` gained a third variant,
`PushScreen(Arc<dyn Fn() -> Screen + Send + Sync>)` — the `Screen::Settings` counterpart to `PushPane`,
for first-party built-in screens that predate the extension registry and are deliberately not
`ExtensionPane`s (task 4.25's own `Screen::Settings` doc comment named exactly this gap: "registering a
working 'open Settings' command would need a real, already-loaded `TuiConfig`/`config_path`... `App`
has no live config anywhere yet"). `App::new_with_config` always has one now, so
`register_builtin_commands` (extended with a `config`/`config_path` parameter) registers `nav.settings`
alongside the pre-existing `nav.diagnostics`. Idempotent via `std::mem::discriminant` (works for any
`Screen`, unlike `PushPane`'s title-based check, without needing `Screen: PartialEq` — deliberately not
derived, per that type's own doc comment) — confirmed by
`settings_is_reachable_end_to_end_from_the_palette_and_is_idempotent`.

**Onboarding/unlock completion — deliberately left untouched, not an oversight.** `App::handle_key`'s
onboarding-finished and unlock-finished branches still swap to `Screen::Placeholder`, exactly as
before this task. `crate::session::LiveSession::empty`'s own doc comment ("a future navigation task can
call this directly once onboarding finishes") and the "Known gap, flagged for 4.36/4.37" note on
`Unlock`'s `handle_worker` arm both read as anticipating this task doing that wiring too — but the
task's own Scope/Out-of-scope text limits this task to "deciding *when* `Screen::Main` is reached" only
for `Preflight` (task 4.37), and onboarding/unlock's own completion target is naturally bundled with
that same startup-routing decision in practice (4.37 needs to touch both call sites anyway to also
handle "account already exists at startup"). Treated as a judgment call, not silently dropped — see
`Screen::Main`'s own doc comment in `app.rs` for the precise, explicit statement of this boundary.

**Narrowing this task's own construction path introduces (stated explicitly, not just inherited):**
- **`Screen::Chat` opened from `Screen::Main` always starts with an empty transcript.**
  `crate::session::LiveSession` (task 4.29) deliberately carries no per-peer history, and loading one
  is I/O this crate's `update` never performs directly; doing so would need either widening
  `LiveSession` or a new `Effect::LoadHistory`, both real `run_worker`/store-loading changes outside
  "screen content/navigation" — this task's own explicit boundary (mirrors the boundary this task's own
  Risks/notes already draw around the unrelated `run_worker`-rederivation gap). Restart-persistent
  history itself is unaffected; only this screen's own *initial* load of it is deferred.
- A `TrustStore` contact with no matching `contacts.json` row at all (reachable only via
  `Effect::AcceptRequest`'s own `TrustStore::observe`, which never touches `contacts.json`) is invisible
  to `build_contact_entries` entirely — a pre-existing, orthogonal gap this task did not introduce and
  does not resolve (`TODO: confirm` left in that function's own doc comment).
