# 10.10 — CLI `meridian send`

**Phase:** 10 — File Transfer Stream · **Feature:** T09 · **Depends on:** 10.7, 10.8, 10.9 ·
**Status:** done

**User surface:** this task IS the CLI/demo surface for T09 (`apps/cli` is the reference client and
demo driver per `apps/cli/CLAUDE.md`) — the TUI's own surface is separate (task 10.11, already landed).

## Goal
Give the reference CLI client a `send` subcommand matching the feature spec's demo script:
`meridian send mrd1:<bob>@org-b.test ./video-1GiB.bin`, with a progress bar and an accept/reject prompt
on the receiving end.

## Scope
- **In:** `apps/cli/src/` — a new `send`/file-transfer module wiring `meridian-streams`'s sender/receiver
  engines to a live `P2pSession` (orchestration only, per `apps/cli/CLAUDE.md`: the CLI is a driver, not
  where protocol logic lives), a progress bar rendering the sender engine's progress events, and a
  terminal prompt for the recipient's accept/reject decision when `FileStream::on_open` doesn't
  auto-accept.
- **Out:** the TUI surface (10.11, separate crate/screen); any protocol logic — if this task finds itself
  writing chunking/AEAD/merkle code in `apps/cli`, that logic belongs in `apps/streams` instead.

## Deliverables
1. `meridian send <mrd1-id> <path>...` subcommand (multi-file batch per the feature spec's "multi-file
   batches" in-scope item).
2. Progress bar output matching the demo script's shape (`38% ▓▓▓▓▓░░░░ 41 MB/s`).
3. Accept/reject prompt on the receiving side for a non-auto-accepted incoming file.
4. Tests: CLI-level integration test driving a send/receive pair over the loopback transport.

## Risks / notes
Match the feature spec's exact demo script as closely as practical — it's the acceptance criterion this
task feeds into (task 10.17's full demo run reuses this).

## Outcome
Added `meridian send <mrd1-id> <path>... [--server <ws-url>] [--out <dir>] [--expect <n>] [--json]` in
`apps/cli/src/send.rs`, orchestrating `meridian-streams`'s already-built sender/receiver engines
(10.7/10.8/10.9) over a live `P2pSession` — requires the `webrtc` cargo feature (no cross-process
loopback mode, mirroring `session connect`'s existing precedent). A progress bar renders `SendProgress`
events via a hand-rolled `\r`-overwrite renderer (no new dependency). Accept/reject is wired via
`FileStream::with_ask_user` with a synchronous blocking terminal prompt (`on_open`'s documented seam).

Two design limitations are self-disclosed rather than worked around: a single process can't both stream
a batch out and service inbound frames concurrently (`P2pSession` has no split reader/writer half), so
only the initiator's own paths are sent — the responder side just receives, exiting after `--expect N`
inbound files; and the receiver verifies the *whole-file* merkle root after AEAD-opening each chunk
rather than per-chunk merkle verification, since the wire carries no per-chunk proof (task 10.12's own
disclosed gap) and `FileReceiver::receive_frame` has no real caller today outside its own tests. New
helper logic: `sanitize_file_name`/`create_unique_file` (a path-traversal defense — the first place in
the codebase writing a `mrd.file/1` sender-supplied `name` to disk).

**code-reviewer** (this task's sole named reviewer) went through two full rounds before passing. Round
1 returned **FAIL** with two blocking bugs: (1) the responder's completion check compared raw frame
count to `leaf_count`, so a single duplicate/retransmitted chunk (plausible over a reliable-unordered
channel) could satisfy it while a real chunk was still missing, and `finalized.insert(sid)` ran even on
a failed `finalize_transfer`, permanently blacklisting that transfer and hanging the responder's exit
loop forever; (2) `finalize_transfer` opened a chunk before bounds-checking its index, so a peer holding
`k_f` could send an arbitrary out-of-range `u64` index and trigger an unchecked-multiply overflow — a
panic in debug builds, silent buffer corruption in release. Fixed by tracking completion via distinct
chunk-index count and only marking `finalized` together with a definitive success or terminal failure,
and by bounds-checking `frame.i` before `open_chunk` (mirroring `apps/streams/src/receiver.rs`'s own
check) with `checked_mul`/`checked_add` throughout. The same round closed four should-fixes: a
symlink/TOCTOU hazard in path collision handling (`Path::exists()` → atomic `create_new(true)`), `k_f`
stored as a bare array rather than `Zeroizing`, a sender success line that overclaimed receiver-side
verification with no ack mechanism to back it, and an unbounded allocation driven by unauthenticated
`manifest.size` (now sanity-capped).

An independent re-verification of round 1's fixes found five of six genuinely closed, but caught a new,
reproducible gap in the completion-check fix itself: it checked distinct-index *cardinality* against
`leaf_count`, not *membership* of every required index — a peer could send an extra, out-of-range
spurious frame that inflated the count to match `leaf_count` while a real chunk was still missing,
permanently failing an otherwise-completable transfer. Round 2 fixed this with a genuine membership
check (`(0..leaf_count).all(|i| distinct.contains(&i))`) and made `finalize_transfer` tolerate (skip,
not fail on) an out-of-range frame encountered during reassembly, since the membership check now
guarantees every required index has already arrived by the time it's called — verified independently
against the actual code and a dedicated new regression test reproducing the exact scenario. All 98
`meridian-cli` tests green throughout every round; clippy (default and `--features webrtc`)/fmt clean;
full workspace build clean.
