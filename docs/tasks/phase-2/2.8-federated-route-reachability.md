# 2.8 — Federated envelope forwarding + per-request reachability (§3.3 step 5, §3.4)

**Phase:** 2 — Cross-Org Federation · **Feature:** T06 — Cross-Org Federation · **Depends on:** 2.7, 1.32 · **Status:** done

## Goal
An envelope sealed by Alice reaches Bob at org-b **byte-identically** across the trust boundary, and
org-a can ask org-b "is `K_B` live right now?" **per request** — never a presence subscription.

## Scope
- **In:** `fed_route` on both sides; `fed_reachability` on both sides; delivery into B's local
  `Registry`; the transport-independence invariant; oversized-envelope rejection.
- **Out:** offline queuing — that is T07. A federated `not_connected` stays a **defined error**,
  matching `apps/core/src/signal_relay.rs`'s deliberate hard-error choice.

## Deliverables
1. `federation/inbound.rs`: `handle_fed_route`, `handle_fed_reachability`; `outbound.rs`:
   `route_foreign`, `reachable_foreign`.
2. `apps/rendezvous/src/ws.rs`: `handle_route` branches on `to_hint`.
3. `apps/rendezvous/tests/federation_route.rs`: byte-identical envelope A→B (the
   [wire-protocol.md](../../api/wire-protocol.md) transport-independence invariant, now covering the
   s2s hop); oversized rejected; `closed` origin rejected; reachability is boolean, per-request, **not
   persisted and not logged**.

## Risks / notes
- **This is where 2.1's `from`-attestation decision is cashed.** Whatever ADR 0017 chose, the client's
  `SenderMismatch` check in `apps/core/src/chat.rs` must remain the load-bearing defence, and a forged
  origin from a hostile foreign server must fail closed. **Do not start before 1.32 lands** — its
  harness is what proves this rather than asserting it. (1.32 is done.)
- **Dependency trap.** The server must not decode the envelope to determine `from`; that needs
  `meridian-envelope`. Both `tools/lint-no-serde-on-blob.sh` and its `--selftest` must pass.
- §7.1 and `seq-cross-org-setup.mermaid` both say "deliver (or mailbox if offline)". The mailbox is
  ADR 0007 / Feature 07 — cross-org-offline must resolve to a **defined error** here, not absorb the
  mailbox.

### Architect decisions (resolved before implementation, /next-task 2.8)

1. **Maximum envelope size: no new constant.** The ceiling is `apps/rendezvous/src/federation/link.rs::MAX_FRAME_LEN`
   (1 MiB) — `FedRoute{to,from,envelope}` is already CBOR-nested inside the s2s `FedFrame`, which
   `write_frame`/`read_frame` already hard-cap there, so an oversized envelope cannot cross the wire
   at all today. What 2.8 adds is a *clean, pre-dial* rejection instead of letting the link-level
   `FrameTooLarge` I/O error do the job: `route_foreign` builds the real `FedFrame` locally and checks
   its encoded length against `MAX_FRAME_LEN` before ever dialing, returning a new
   `RouteForeignError::EnvelopeTooLarge{len}` → client-visible `error_codes::BAD_REQUEST` (no new
   code). `handle_fed_route` repeats the check as defense-in-depth against a non-compliant peer,
   replying `FedErr{fed_error_codes::BAD_REQUEST}`. `messaging-envelope-v1.md §4` confirms a real v1
   envelope is orders of magnitude smaller than 1 MiB, so a tighter number would be arbitrary,
   undocumented policy invented mid-task.
2. **No s2s replay/de-dup mechanism in 2.8 — zero, by design, not a deferral invented now.**
   [ADR 0016](../../adr/0016-envelope-deniability.md) C7 (Accepted) already assigns the `eid`
   replay-dedup key to envelope **v2** explicitly; v1, which `fed_route` carries verbatim, has none.
   [Task 2.13](./2.13-ratchet-replay-dos.md) (done) already bounds the actual harm: a replayed
   envelope — locally or across a federation hop, the ratchet cannot tell the difference — now
   degrades to exactly one failed decrypt, never a wedged session. Inventing an s2s-level dedup key
   now would create a second, competing identity the moment v2's `eid` lands. The residual (a hostile
   relay/partner can duplicate a `fed_route` envelope) is an already-accepted residual under ADR
   0016/threat-model A2/A3, bounded by 2.13, not a new hole 2.8 introduces.
3. **`fed_reachability` is s2s-internal only — no new client-visible c2s trigger in 2.8.** The full
   s2s `fed_reachability`/`fed_reachable` request/reply machinery is built per Scope, but its only
   caller in this task is `route_foreign`'s own pre-check before attempting `fed_route` (fail fast on
   an offline target rather than after a round trip) — the client never sees "reachability was
   checked separately." `handle_fed_reachability` implements exactly
   `FedReachable{connected: registry.is_connected(&target)}` and **nothing else** — no `NOT_FOUND`
   branch, ever, mirroring `Registry`'s existing local shape (`is_connected` returns `false`
   identically whether a key never registered or registered-then-disconnected — there is no separate
   existence check to leak). If `route_foreign`'s pre-check comes back `connected:false`, or fails to
   reach B at all, `ws.rs`'s federated-route branch replies with the **same**
   `error_codes::NOT_CONNECTED` the local `handle_route` path already uses for an offline local
   recipient — never a distinct "foreign offline" code — collapsing "target unknown," "target
   known-offline," and "reachability check itself failed" into the one existing outcome. Genuine
   failure to reach server B at all stays the existing `error_codes::FED_UNREACHABLE` (a connectivity
   axis, orthogonal to target liveness). Rate-limit key for `fed_reachability`: `req.target` (no
   `from` field exists on `FedReachability`, same deliberate reading 2.7 established for
   `FedFetchBundle`) under `FederationLimits::check_route`'s existing `Operation::Route` bucket
   (already documented as covering both 2.7 and 2.8's route-shaped ops).

## Outcome
`apps/rendezvous/src/federation/inbound.rs`/`outbound.rs` extended with `handle_fed_route`/
`handle_fed_reachability` and `route_foreign`/`reachable_foreign` (sharing a new `dial_foreign`
helper, which `fetch_foreign_bundle` from task 2.7 now also calls instead of duplicating the
`pinned_identity` dial logic). `apps/rendezvous/src/ws.rs`'s `handle_route` branches on
`body.to_hint`; federated replies collapse to the pre-existing `NOT_CONNECTED`/`FED_UNREACHABLE`/
`FED_DENIED`/`RATE_LIMITED` codes, no new ones invented. Implemented exactly to the three
pre-resolved architect decisions recorded above (max size = `MAX_FRAME_LEN`, zero s2s replay/dedup,
`fed_reachability` s2s-internal with no existence oracle). The implementer self-caught and fixed a
real bug mid-build: the reachability pre-check's own policy/rate-limit answers were initially
collapsing into `not_connected`, silently masking a `closed`-policy origin as merely offline —
caught by the task's own `closed_policy_at_b_is_reported_as_fed_denied` test failing.

**Reviews:** architect — consistent, no blocking findings; confirmed §3.4 per-request-only
presence (no caching/subscription anywhere) and the ADR 0007 boundary (no silent mailboxing); flagged
that `ROUTE_REPLY_GRACE`'s doc comment only justified B's compute latency, not real wire RTT — fixed.
security-reviewer — APPROVE-WITH-CHANGES, required item was procedural (run the lints with real
shell, done); independently confirmed the reachability bug-fix is correctly implemented and traced
every required property against code, not narrative. test-engineer — PASS; mutation-tested the
byte-identity assertion, the existence-oracle collapse, and the bug-fix itself, all held; reported
(and recovered from) a scary `git checkout --` near-miss that briefly reverted the uncommitted
diff — independently verified restored byte-for-byte before proceeding. code-reviewer —
approve-with-nits; found real duplicated pinning logic between `fetch_foreign_bundle` and the new
`dial_foreign` helper (fixed — `fetch_foreign_bundle` now calls `dial_foreign`) and, converging
with the other two reviewers, flagged `ROUTE_REPLY_GRACE` as an unratified fixed latency tax on
every successful route (fixed via honest residual documentation, not a guessed new value — no
reviewer proposed a specific better number). Two non-blocking follow-ups noted, not fixed in this
task: federated envelope delivery isn't counted in `envelopes_routed_total`, and the third
near-identical test-harness duplication across `federation_{mtls,fetch,route}.rs` means a
`tests/common/mod.rs` extraction is now clearly due.

Tests: `cargo nextest run -p meridian-rendezvous --test federation_route` (6/6 pass, plus
`federation_fetch.rs`'s 6 still passing = 12/12), `lint-no-serde-on-blob.sh` (+ `--selftest`) and
`lint-server-no-core.sh` pass, clippy/fmt clean, `cargo test --workspace` green.
