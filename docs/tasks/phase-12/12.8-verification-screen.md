# 12.8 — Verification screen: QR camera-scan safety-number compare

**Phase:** 12 — Browser & Desktop Clients · **Feature:** T11 · **Depends on:** 12.2, 12.7 · **Status:** done

**User surface:** browser + desktop verification screen (wired by 12.14/12.15) — the new-platform
equivalent of the terminal client's existing verification screen (Phase 4, task 4.22). No TUI surface
applies to this task (already shipped, unaffected; see the phase-wide "no TUI task" note in
[phase-12/README.md](./README.md#architect-consult-substratestoresigning-decisions-settled-before-task-breakdown)
point 5).

## Goal
Build a camera-capture (MediaDevices) + QR decode/encode screen comparing the local and remote
`safety_number` outputs (`core-api-contracts.md`), marking `mark_verified` on a confirmed match — this
is T11's realization of the spec's own acceptance walkthrough step ("chat + 200 MB file transfer
browser↔CLI; safety numbers match on both, verified by QR").

## Scope
- **In:** QR display of the local safety number; camera-scan + decode of the remote peer's; visual
  compare UI; the `mark_verified` call on confirmed match, exactly as `core-api-contracts.md` already
  defines it.
- **Out:** any change to the underlying `safety_number`/`mark_verified` core functions (already frozen,
  T08) — this task only builds a UI over them; camera-permission-denied fallback UX beyond a basic error
  state is a nice-to-have, not required for this task's acceptance.

## Deliverables
1. `shared-ui/src/screens/Verification.svelte`.
2. Component tests: QR decode/compare logic unit-tested against known fixture values (the T08 safety-
   number fixtures per the spec's own acceptance criterion — "identical safety numbers across platforms
   for the same key pair"); camera access itself mocked, not exercised in this task's own test suite.

## Risks / notes
This is a safety-critical UX surface (D06) — do not let a partial/ambiguous QR scan result in a
false-positive `mark_verified` call. Mirror the terminal client's own verification screen (4.22)'s
match/mismatch state handling rather than inventing new UX semantics.

## Tests
`pnpm --filter shared-ui test`.

## Reviews
**security-reviewer** (mandatory — verification UX is the safety-critical D06 surface); **code-reviewer**.

## Outcome
Shipped `Verification.svelte` + `verificationStore.ts` + an injectable `QrScanner` interface (real
`MediaDevicesQrScanner` via `qrcode`/`jsqr`, plus a `FakeQrScanner` test double — no library existed
anywhere in the JS/TS monorepo, both operate purely on string/pixel data, no crypto or wire logic
reimplemented in TS). `compareSafetyNumbers` is the sole match/mismatch/invalid decision point: exact
60-digit `===` only, no truncation/padding/fuzzy comparison, tested against the real T08 fixtures
(`test-vectors/safety-numbers-v1.json`, the same file `apps/crypto`'s own conformance tests use).
`confirmVerified()` re-reads the store's live state at call time — the same defense-in-depth pattern as
`chatStore.send()`'s pre-send gate re-check — and throws rather than calling `markVerified` unless the
live state is exactly `"match"`; the "Mark verified" action doesn't exist in the DOM outside that state
(not merely disabled).

The combined review (security-reviewer + code-reviewer) returned **PASS** on both lenses after
specifically trying to find a path from a malformed/mismatched scan to `markVerified` and failing to —
traced `compareSafetyNumbers` and `confirmVerified` line-by-line, reasoned through the counterfactual
that an interior-single-digit-corruption test would catch a regression to fuzzy comparison, and confirmed
the T08 fixtures are genuine (not invented). One non-blocking gap was found and fixed in a same-task
follow-up: `confirmVerified`'s guard checked `scanResult.kind === "match"` but not `!verifying`, so two
synchronous calls before Svelte's reactive DOM update disabled the button could both pass the guard and
double-fire `adapter.markVerified` — not a false-positive-on-wrong-data issue (the underlying match was
still genuine), but a reentrancy gap. Fixed by adding `&& !s.verifying` to the guard; a new regression
test (`confirmVerified — reentrancy guard`) proves two concurrent calls on a genuine match invoke
`adapter.markVerified` exactly once. 78/78 tests passing after the fix (68 pre-existing + 9 component + 1
new reentrancy test), `tsc`/`svelte-check` clean.
