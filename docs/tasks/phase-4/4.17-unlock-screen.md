# 4.17 — Unlock screen

**Phase:** 4 — Verification & Trust + Terminal TUI Client · **Feature:** T17 — Terminal TUI Client · **Depends on:** 4.13, 4.15 · **Status:** done

## Goal
Let a returning user with an existing file-backed account unlock it; OS-keystore-backed accounts skip
this screen entirely.

## Scope
- **In:** masked passphrase entry, retry with attempt count, no invented lockout policy
  (`TODO: confirm` an attempt policy per [tui-client.md §7](../../architecture/tui-client.md#7-what-the-user-sees-when-things-go-wrong)
  if one is ever wanted — do not invent one now).
- **Out:** onboarding (4.16); the passphrase's underlying crypto (already exists in `meridian-store`).

## Deliverables
1. `apps/tui/src/screens/unlock.rs`.
2. Screen-snapshot tests; retry-with-attempt-count test; no secret ever rendered (masked input,
   verified structurally — the passphrase buffer never appears in a snapshot).

## Status
Done. `apps/tui/src/screens/unlock.rs` implements the two mermaid states this screen owns
(`Entering`/`Unlocking`, `Unlock --> Unlock` self-loop on a wrong passphrase with a shown-but-never-
enforced attempt counter, `Unlock --> Main` on success landing on the existing `Screen::Placeholder`
stand-in). Same Elm-architecture I/O boundary as every other screen: the real unlock attempt against
`meridian_core::store::FileSecretStore` is requested via `Effect::Unlock(UnlockRequest)`, never
performed inline. No lockout policy invented, per tui-client.md §7's own explicit `TODO: confirm` for
that condition — only a shown attempt count that never blocks a retry.

Task 4.16 had shipped a real passphrase-`Debug`-redaction bug (a live passphrase field with a plain
derived `Debug`, leaking through this codebase's own `panic!("{other:?}")` test idiom); this task was
briefed on that exact failure mode up front. `Entering` (holds the raw passphrase for the whole typing
phase) has a hand-rolled `Debug` redacting it from the start, mirroring 4.16's fix; `Unlocking` and
`UnlockRequest` were structured to either hold no raw passphrase at all or redact it the same way.
Combined `reviewer` (sole named reviewer) traced the full derive chain (`UnlockState`'s derived enum
`Debug` correctly delegates to each variant's own impl, `Screen`/`Effect` correctly inherit the
redaction transitively) and confirmed both regression tests are genuinely non-vacuous, alongside
confirming no-lockout compliance, correct `FileSecretStore::new` payload shape, and that
`StoreError::Unwrap`'s deliberate wrong-passphrase/corrupt-data conflation (avoiding a
passphrase-guessing oracle) isn't undone by any distinguishing logic in this screen. **Zero findings —
first clean pass of the TUI screen tasks so far**, a direct result of the explicit prior-bug briefing.

`screens_unlock.rs` + 13 `config.rs` + 22 `store.rs` + 1 `terminal_guard.rs`), `cargo test -p
meridian-cli --bins`, `cargo fmt --check`, `cargo clippy --workspace --all-targets -- -D warnings`,
