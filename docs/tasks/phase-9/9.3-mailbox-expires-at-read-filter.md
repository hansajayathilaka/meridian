# 9.3 — Filter `expires_at` on mailbox reads (list + size)

**Phase:** 9 — Review of Phase 8 · **Feature:** review fix (F5) · **Depends on:** 9.1 (soft) · **Status:** done

**User surface:** none — server-internal read-path filter; no client-visible behavior change beyond
correctly *not* delivering something that shouldn't have been (Definition of Done gate 9).

## Goal
Stop expired-but-not-yet-purged mailbox rows from leaking into two read paths: `drain_mailbox` (so a
recipient reconnecting after their TTL has elapsed but before the next purge tick no longer receives an
envelope that should already be gone) and quota accounting (so expired-unpurged bytes stop counting
toward `quota_mb` and causing spurious `mailbox_full` errors for senders).

## Scope
- **In:** `mailbox_list_for_recipient` (`apps/rendezvous/src/store.rs:79-87`, `store/sqlite.rs:183-196`)
  and `mailbox_size_bytes_for_recipient` (`store.rs:118-124`, `store/sqlite.rs:232-241`) — both must
  filter to `expires_at > now` (or equivalent) before returning rows/summing bytes, in both `MemoryStore`
  and `SqliteStore`.
- **Out:** The background purge job (`mailbox_purge.rs`) itself is unchanged — it remains the mechanism
  that actually reclaims storage; this task only stops expired rows from being *observed* by other
  callers before that reclamation happens. If a genuine reason emerges during implementation to keep
  the current eventually-consistent behavior instead (e.g. a performance concern with adding an
  `expires_at` predicate to a hot read path), document that explicitly as an accepted residual rather
  than silently leaving the bug — do not close this task without either the fix or that documented
  rationale.

## Deliverables
1. `mailbox_list_for_recipient` excludes rows past their `expires_at`, both backends.
2. `mailbox_size_bytes_for_recipient` excludes rows past their `expires_at` from the byte sum, both
   backends.
3. A test proving a drain against a mix of expired and live rows returns only the live ones, and a test
   proving quota accounting ignores expired-unpurged bytes.

## Risks / notes
Soft dependency on 9.1: this task edits the same `store.rs`/`store/sqlite.rs` read-path functions that
9.1's quota-serialization fix calls into. Landing after 9.1 means the now-serialized quota check
operates on accurate (non-stale) byte counts from the start, avoiding a second pass over the same code.
Not a hard/blocking dependency — if scheduling requires it, this task can land independently, but expect
minor overlap/rebase with 9.1's diff.

## Tests
`cargo nextest run -p meridian-rendezvous`, `cargo clippy -p meridian-rendezvous --all-targets --features sqlite -- -D warnings`.

## Reviews
**code-reviewer** (correctness of the added filter), **security-reviewer** (the bounded-staleness
window is a data-exposure-timing question worth a security sign-off even though it's not a
confidentiality break — TTL is a stated guarantee in ADR 0007).

## Outcome
`mailbox_list_for_recipient` and `mailbox_size_bytes_for_recipient` (both `MemoryStore` and
`SqliteStore`) now take a caller-injected `now: u64` and filter to `expires_at > now`, exact complement
of the purge job's `expires_at <= now` deletion predicate — no gap or double-counting at the boundary.
`ws::drain_mailbox` sources `now` from the real wall clock (`now_secs()`). Deliverable 3's tests exist
for both backends plus a bonus end-to-end quota-vs-expired-bytes test, each with a "belt-and-suspenders"
assertion that the row is still physically present (purge never ran) — proving the read-time filter,
not an accidental purge, is what's excluding it.

A same-scope follow-up commit fixed several pre-existing tests that seeded mailbox rows with a stale
`expires_at = 10_000` (year 1970) placeholder — genuinely expired against the real wall clock, these
started hanging once the new filter correctly excluded them from delivery. Fixed with a
`FAR_FUTURE_EXPIRES_AT` constant in the three affected test files.

code-reviewer + security-reviewer both PASS. One should-fix (closed in the same pass): a module doc
comment in `apps/rendezvous/src/mailbox_purge.rs` claiming the read path "never filters on `expires_at`
at all" was stale as of this task's own change — corrected to describe the purge job as the sole
*physical deletion* mechanism, with the read-time filter now layered on top as a bounded-staleness
observation guard, not a substitute.
