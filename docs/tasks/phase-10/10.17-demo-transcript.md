# 10.17 demo transcript — File Transfer Stream (T09)

Two parts, both against **real, unmodified `target/debug/meridian`** binaries built from this branch
(`cargo build --workspace --features webrtc`), a real `meridian-rendezvous::serve` instance, and the
**real `WebRtcTransport` backend** (no `LoopbackTransport` substitution anywhere in this transcript —
`meridian send` has no loopback mode to substitute; see "Scope decision" below).

## Scope decision: real WebRTC only — `meridian send` has no loopback mode

The task's own instructions name two options depending on whether the CLI supports selecting
`LoopbackTransport`. It does not: `apps/cli/src/send.rs::run` is `#[cfg(feature = "webrtc")]`-gated
with no alternative code path, and task 10.10's own Outcome states this explicitly ("requires the
`webrtc` cargo feature (no cross-process loopback mode, mirroring `session connect`'s existing
precedent)"). So this demo runs entirely over the real backend, per the task's option (ii): run as
far as the real acceptance demo goes, and document precisely, honestly, what happens at the
network-cut step rather than fabricating a clean pass.

## Part 1 — real `meridian send`, real rendezvous, real WebRTC, multi-chunk, byte-identical

Driver: a throwaway `#[test]` file under `apps/cli/tests/` (not checked in, per the phase-6/8
precedent — "nothing from the driver needs to be checked in, but the transcript quoted must be real

## Part 2 — network cut + `ice_restart()` + resume, over real netns/veth

`meridian send` itself has **no automatic drop-detection or reconnect/resume wiring** — confirmed
directly in `apps/cli/src/send.rs` (no `ice_restart`/`resume`/`watch_resume` reference anywhere in
that file) and already recorded as such in task 10.15's own Outcome. The demo script's "yank the
network mid-transfer… ICE restart… reconnected… resuming" narration is therefore **not reachable
through the shipped `meridian send` command at all** — only through the dedicated test-only driver
example task 10.15 built specifically to exercise this scenario
(`apps/cli/examples/kill_resume_netns_drive.rs`, driving the same real `meridian-core`/
`meridian-streams` primitives `send.rs` itself uses: `P2pSession::ice_restart`, the resume-bitmap
wire shape, `FileStream::watch_resume`). This transcript therefore continues the demo with that
harness (`tools/netns-kill-resume.sh run`), the same one this phase's own tooling already provides
for exactly this gap, run for real on this sandbox's netns/veth rig (root available).

**A new, previously-undiscovered bug found and worked around for this run, not fixed (out of this
task's scope):** `tools/netns-kill-resume.sh`'s own `need_veth_linkstate` pre-flight self-check
constructs probe interface names as `kr-probe-a-$$`/`kr-probe-b-$$` (`$$` = the invoking shell's own
PID). In this sandbox `$$` is a 5-digit PID, producing e.g. `kr-probe-a-21039` — **16 bytes,
exceeding Linux's 15-usable-byte `IFNAMSIZ` limit** — so `ip link add ... type veth peer name
kr-probe-b-21039 ...` itself fails, and the script's self-check reports "basic netns/veth link
up/down is not usable in this environment — skipping" even though the real capability the script
needs (confirmed manually, and via the script's own `topology_up`, which uses short fixed names
`kr-a`/`kr-b`, `ns-kr-a`/`ns-kr-b`, all well under the limit) works perfectly fine. Reproduced
directly:

```
$ ip link add kr-probe-a-99999 netns kr-probe-nsa-99999 type veth peer name kr-probe-b-99999 netns kr-probe-nsb-99999
Error: argument "kr-probe-b-99999" is wrong: "name" not a valid ifname
```

This is a genuine, environment-dependent (any sandbox/CI runner whose shell PID has reached 5 digits
— common in any long-running container) false-negative bug in the harness's own pre-flight check,
independent of anything this task is scoped to fix. Per this task's own "do not fix, log a
gap-closure candidate" rule, the script itself was left untouched; for this run only, a throwaway
copy with the broken pre-flight call sites no-op'd (its actual `run()` logic, using the same short,
safe interface names the real script already uses, byte-for-byte unmodified) was used to exercise
the genuine underlying scenario. See this task's Outcome section for the tracked candidate
fix-task.

### What this genuinely proves and what it doesn't

- **Real, live confirmation of the pre-cut half working correctly over real WebRTC, past 10.18's
  fix**: 15/24 chunks (983040 bytes, well beyond a single 64 KiB chunk) sent and received correctly
  before the cut — the SCTP max-message-size defect (task 10.18) is genuinely closed for a real
  multi-chunk transfer under this harness too, not just Part 1's smaller 4-chunk file.
- **Real, live confirmation of the documented `ice_restart` no-op gap, past 10.18's fix**: after a
  genuine 15-second veth cut (well past the transport's own 9s `ICE_FAILED_TIMEOUT`) and restore,
  `ice_restart()` returns `Ok` on both sides, the receiver *does* correctly compute and send a resume
  bitmap (9 of 24 chunks missing — exactly `24 - 15`, the expected count), but the data channel never
  actually recovers: the sender never receives that bitmap, and the receiver never receives the
  resent chunks. This is **exactly** the gap `docs/tasks/README.md`'s "Live carry-forwards" section
  and task 10.15's own Outcome already predicted and named, now independently reconfirmed live on
  this sandbox for this task's own exit gate, not merely inherited on faith from 10.15's prior run.
- **This is not a clean PASS of the feature spec's literal demo script.** The spec's own script shows
  the same live process narrating cut→reconnect→resume→verified match — that specific behavior does
  not exist today, neither in the shipped `meridian send` CLI (no auto-resume wiring at all) nor in
  the underlying transport it depends on (`ice_restart` does not restore connectivity). Per this
  task's own scope, this is recorded as a genuine, unfixed finding — not silently worked around, not
  papered over with a partial substitute claimed as a full pass.
