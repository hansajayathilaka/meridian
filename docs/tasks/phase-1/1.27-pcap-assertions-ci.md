# 1.27 — pcap-analysis assertions + CI/harness wiring (closes F11 wire-level)

**Phase:** 1 — Review of Phase 0 · **Feature:** review fix (F11 wire-level) · **Depends on:** 1.26 · **Status:** done

## Goal
The pcap captures from [1.26](./1.26-netns-drive-and-capture.md) are turned into strict, fail-closed
pass/fail assertions — this is the task that actually closes F11's wire-level half, not merely "the demo
didn't crash." This is the invariant that makes "relay-only" a real IP-hiding guarantee provable on the
wire, not just in-process (1.16's `enforce_relay_only`) or at the CLI-plumbing level (1.24).

- **In:** a pcap-analysis helper (script or small Rust/Python tool) asserting: (a) the negotiated path
  per cell matches the expected rung (direct/srflx/relay-udp/relay-tls-443); (b) under `relay-only`,
  **zero** packets in `ns-bob`'s capture contain alice's host/srflx addresses — any match is a hard
  failure, never a warning; (c) `ns-turn`'s capture contains only DTLS ciphertext, never plaintext (e.g.
  no cleartext SDP/chat bytes visible via a simple string/pattern scan); wire
  `tools/netns-nat-matrix.sh matrix` to run all four cells end-to-end (1.25 topology → 1.26 drive+capture
  → this task's analysis) and exit non-zero on any assertion failure; CI wiring if root+netns is
  available there, else an `--ignored`/harness job gated on root/`NET_ADMIN` with clear SKIP messaging
  and documented manual run instructions, mirroring `tools/netns-nat-matrix.sh`'s existing `need_root()`
  pattern.
- **Per architect review (2026-07-23, following 1.26/1.29/1.30's resolution)**: split assertions (a)-(c)
  by what each presupposes rather than treating all four cells uniformly. Assertions (a) and (c) both
  presuppose an established path/data flow — scope these strictly to the 3 real-connecting cells
  (`full-cone`, `port-restricted`, `symmetric:symmetric`); `udp-blocked` has no negotiated rung and no
  TURN-relayed application data to assert about (1.30: proven-impossible dependency gap, not a bug this
  task re-proves). Assertion (b) (the `relay-only` zero-host/srflx-leak invariant) is the anonymity-model
  "must never" guarantee and should still run against `udp-blocked`'s pcap too — it must hold trivially
  there (1.16's `enforce_relay_only` means host/srflx are never gathered regardless of whether the
  session ultimately connects), and verifying the zero-leak property holds even during a failed
  `relay-only` attempt is a stronger proof, not one to skip. Add one narrow assertion specific to
  `udp-blocked`: the capture shows no established data channel/successful candidate-pair selection, and
  the process exit + error text match 1.30's documented, bounded failure mode (fails fast, not a hang) —
  proving the "fails fast and loud" claim on the wire, not just via CLI stdout.
- **Out:** any new topology/driving logic (already done in 1.25/1.26); any change to `WebRtcTransport` or
  `enforce_relay_only` — this task proves the existing 1.16 guarantee at the wire level, it does not
  re-implement it. Making `udp-blocked` actually connect (that's 1.30's territory, already resolved as a
  documented dependency limitation — not re-litigated here).

## Deliverables
1. The pcap-analysis helper with strict (a)-(c) assertions, split per the scope note above (3 cells get
   the full (a)-(c) treatment; `udp-blocked` gets (b) plus the fails-fast-on-the-wire assertion).
2. `bash tools/netns-nat-matrix.sh matrix` passing its now-amended acceptance bar end-to-end (3/4 cells
   connect and pass all assertions; `udp-blocked` fails fast with the documented 1.30 error and passes
   its own narrower assertions) — not "all four connect," per 1.26's architect-approved amendment.
3. CI wiring or a documented gated/manual harness job.

## Risks / notes
Keep the assertions strict per the anonymity-model skill's "must never" list — no downgrading a leak to a
warning. This is the task whose completion actually closes finding F11 (wire-level); 1.14/1.22/1.24/1.25
are all prerequisites, not the closure itself.

**Known residual gap (recorded honestly, per security-reviewer's 1.27 review):** assertion (b)'s
zero-host/srflx-leak check only runs a wire-level proof against `udp-blocked`'s `relay-only` attempt,
which never actually establishes a session (1.30's dependency gap) — the task file itself calls this
case "trivial." The genuinely load-bearing scenario — the *actually-connecting* relay session for
`full-cone`/`port-restricted`/`symmetric:symmetric`, which is always the post-fallback `RelayOnly` retry
round (1.29), not their labeled `direct`/`prefer-relay` policy — is not independently wire-verified for
zero-leak; only `enforce_relay_only`'s in-process unit tests and "it connected, so it must have worked"
trust cover it today. A naive whole-capture scan on those 3 cells' `ns-bob` pcap would false-fail on
phase 1's documented, by-design host/srflx exposure (before the fallback kicks in), so closing this
properly needs a timestamp-cutover check (e.g. using `SessionInfo::relay_fallback_wait_ms` to bound a
"packets after the fallback began" window) rather than a quick fix under review-cycle time pressure — left
as a documented gap rather than a rushed, under-tested assertion. See
[docs/security/threat-mitigation-matrix.md](../../security/threat-mitigation-matrix.md)'s A4/A5 rows and
[docs/testing/strategy.md](../../testing/strategy.md) §4 for where this is tracked; not blocking F11's
closure (F11's wire-level claims — path/rung, DTLS-opacity, fails-fast, and the `relay-only`-policy
zero-leak invariant as actually promised by `enforce_relay_only` — are all proven), but worth a scoped
follow-up if a stronger proof is wanted later.

**Separately, [1.31](./1.31-prekey-bundle-republish-race.md)** tracks a real but out-of-scope bug found
during this task's live-rig verification (a prekey-bundle publish/fetch race on reconnect, in
`session_connect.rs` — a reliability/UX bug, not a security regression) — not part of F11's closure,
tracked for its own fix.

## Decision (recorded)
Implemented (devops agent): `tools/netns-nat-matrix.sh` gained `assert_path_and_rung` (a),
`assert_no_alice_leak_in_bob_pcap` (b), `assert_dtls_ciphertext_only` (c), `assert_udp_blocked_fails_fast`
(d), and `cell_expects_success()` to route `drive_real_peers`/`cell`/`matrix` so `udp-blocked`'s expected
failure no longer trips a hard exit. `harnesses/nat-matrix/run.sh`'s header/echo and Feature 05's
acceptance-criteria line were updated to stop claiming "all four cells connect" (stale wording from the
original T05 spec) and reflect the 3/4-cells-connect bar 1.26/1.29/1.30 already established.

**Two real bugs found + fixed during my own independent live-rig verification** (not the implementing
agent's self-report — re-ran the rig personally, multiple times, from clean state):
1. A prekey-bundle publish/fetch race (see [1.31](./1.31-prekey-bundle-republish-race.md) for the
   full write-up) reproduced on most `matrix()` runs from cell 2 onward. Rig-only fix: `alice_home`/
   `bob_home`/`ensure_identities` now scope identities per cell instead of sharing them across a whole
   `matrix()` run, removing the stale-bundle precondition. connectivity-debugger's review confirmed this
   fix is sound and matches the codebase's own existing pattern (`apps/cli/tests/session_connect_webrtc.rs`
   already uses a fresh identity per test peer) — closes the race for first-time-per-identity connects,
   not a workaround.
2. `harnesses/nat-matrix/run.sh` (the actual CI entry point) ran several `cargo test -p meridian-cli`
   steps without `--features webrtc` before invoking the netns rig; those builds silently overwrote
   `./target/debug/meridian` with a webrtc-less binary, so a fresh CI checkout would hit "meridian-cli was
   built without the `webrtc` feature" on cell 1 every time. Fixed by adding an explicit
   `cargo build -q -p meridian-cli --features webrtc` immediately before the rig invocation.
   connectivity-debugger confirmed this is the right fix in the right place, and flagged (fixed too) that
   `tools/netns-nat-matrix.sh`'s own usage banner needed the same prerequisite noted for direct/manual runs.

**Required reviews, both completed against the implementation + my two fixes above:**
- **security-reviewer**: confirmed the assertion (b) scope-narrowing (relay-only-POLICY cells only,
  rather than all four uniformly) is *correct and faithful* to the anonymity model — not a weakening —
  per `.claude/skills/anonymity-model/SKILL.md`'s own documented scope ("optional peer-IP hiding via
  relay-only mode... direct-mode peers see each other's IPs") and `docs/security/anonymity-and-retention.md`'s
  exposure table and residual-risk list. Found two real gaps, both fixed before merge: (1) assertion (b)
  fail-opened (printed PASS) on a missing/unreadable `pcap_bob` — added a baseline packet-count guard
  mirroring assertion (a)'s existing ns-turn sanity check; (2) the actually-connecting relay session for
  the 3 fallback cells was never independently wire-verified for zero-leak (see the Risks section's
  "known residual gap" above — documented rather than rush-fixed). Also confirmed the ns-turn-exposure
  question (should assertion (b) also check `ns-turn`'s capture) is a non-issue, not a gap — added a code
  comment recording why.
- **connectivity-debugger**: confirmed assertion (a)'s `path=="relay"`/`relay_fallback=="true"`
  expectation, assertion (c)'s oracle strings, and assertion (d)'s accepted error signatures are all
  correctly grounded in 1.29/1.30's documented mechanics. Found one real gap, fixed before merge:
  assertion (b) was gated on `cell_expects_success` rather than on `policy == relay-only` — coincided 1:1
  today (`udp-blocked` is the only relay-only cell and the only one expected to fail), but would silently
  stop checking the load-bearing zero-leak invariant for `udp-blocked` the day 1.30's dependency gap
  closes upstream and it starts connecting. Restructured `drive_real_peers` so assertion (b) runs
  unconditionally on policy, independent of the success/failure branch. Also confirmed both of my two
  fixes above are sound and recommended [1.31](./1.31-prekey-bundle-republish-race.md) as a tracked
  follow-up for the underlying (non-rig) race.
