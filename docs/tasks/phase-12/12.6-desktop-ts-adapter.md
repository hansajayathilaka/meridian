# 12.6 — Desktop TS adapter

**Phase:** 12 — Browser & Desktop Clients · **Feature:** T11 · **Depends on:** 12.2, 12.3 · **Status:** done

**User surface:** none directly — the seam the desktop app shell (12.15) and screens (12.7–12.9) run
against. No TUI surface applies.

## Goal
Implement `MeridianClientAdapter` (task 12.2's interface) over `@tauri-apps/api`'s `invoke`/`listen`,
calling into task 12.3's Tauri commands/events — the piece that lets the shared Svelte screens run
unmodified inside the Tauri desktop shell.

## Scope
- **In:** `apps/desktop/ui/src/adapter.ts` (or the equivalent shared-ui-consuming location) implementing
  every `MeridianClientAdapter` method by `invoke`-ing the corresponding Tauri command from 12.3, and
  subscribing to its events for push-style updates (inbound messages, trust/state changes).
- **Out:** any change to `MeridianClientAdapter`'s interface itself (12.2 owns that); any change to the
  Tauri command layer (12.3 owns that — if this task finds the command surface insufficient, that's a
  finding to route back to 12.3's scope, not something to patch around here); the window UI/screens
  themselves (12.15, 12.7–12.9).

## Deliverables
1. `apps/desktop/ui/src/adapter.ts` — the concrete adapter.
2. Adapter unit tests against a mocked `invoke`/`listen`.

## Risks / notes
Keep this a thin marshaling layer — no business logic, no protocol/wire concerns (same
`apps/web/CLAUDE.md` rule applies here even though this is the desktop side: "the web layer only calls
it," and this adapter is the desktop equivalent of that boundary).

## Tests
`pnpm --filter desktop test` (adapter unit tests against a mocked `invoke`).

## Reviews
**code-reviewer**; **security-reviewer** (confirms no secret material leaks across the adapter boundary
into renderer-visible/loggable state).

## Outcome
Shipped `apps/desktop/ui` (`meridian-desktop-ui`, the first TS/frontend layer under `apps/desktop/`):
`TauriMeridianClientAdapter implements MeridianClientAdapter`, marshaling every interface method onto
`invoke`/`listen` over task 12.3's commands/events. No changes to `shared-ui`'s `adapter.ts` (12.2) or
`apps/desktop`'s Rust command layer (12.3) — both correctly treated as out of scope.

The implementation self-reported 10 command-surface gaps where 12.3's Tauri commands don't fully back
what `MeridianClientAdapter` needs (no safety-number query, no generic `open_stream`, `chat:message_request`
drops its intro preview, `closeAccount` can't actually clear backend key material, `sendFile` expects a
filesystem path not a `Blob`, no background push so the adapter polls, unstructured `Result<T, String>`
errors, and others) — each either fails closed or is documented as an honest, flagged limitation rather
than patched around by inventing new Rust commands, per this task's own explicit scope boundary.

The combined review (code-reviewer + security-reviewer) returned **PASS** on both lenses, zero blocking
findings, after specifically stress-testing the single highest-risk claim: whether `sendGateState`/
`trustState`'s client-side re-derivation from cached display fields repeats the exact bug class task
12.2's review found and fixed in the fake adapter (a separately-stored gate value drifting out of sync
with real state). Traced `TrustStore::can_send`'s real precedence (`apps/core/src/trust.rs` —
`user_blocked` checked first, unconditionally) against the adapter's `sendGateState` and confirmed it
mirrors that exact order, kept fresh via `contact:changed` event handling rather than a separately-mutated
field — not the same bug class. Independently confirmed real enforcement stays server-side in
`commands.rs::chat_send` (calls the real `can_send` regardless of what the adapter displays), so a wrong
client-side gate would be a UX bug only, never an actual bypass. `safetyNumber`'s fail-closed behavior,
the intro-preview drop, and the `sendFile` path-vs-Blob mismatch were each independently verified real
against the actual `commands.rs`/`chat.rs` source, not taken on the implementer's word. 39/39 tests
passing, `tsc --noEmit` clean, no secret material found anywhere in the adapter (grepped directly).

Non-blocking recommendations routed back to task 12.3's future scope (not fixed here): a
`contact_safety_number` command (blocks the Verification screen, 12.8, entirely on desktop today), a
structured error shape, a single-contact trust-state query command to remove the client-side
re-derivation category entirely, and — flagged by the reviewer as the most security-relevant of the
group — a real `closeAccount` backend command, since today locking the desktop app only clears the
adapter's local TS cache while the Rust backend keeps its loaded key material resident.
