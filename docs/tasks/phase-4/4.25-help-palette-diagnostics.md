# 4.25 — Help overlay + command palette + diagnostics

**Phase:** 4 — Verification & Trust + Terminal TUI Client · **Feature:** T17 — Terminal TUI Client · **Depends on:** 4.18, 4.19, 4.20 · **Status:** done

## Goal
Make the whole app discoverable without memorizing subcommands: `F1` help, `^K` fuzzy command palette,
a diagnostics view wrapping `doctor`, and the status bar.

## Scope
- **In:** help screen **generated from the binding table** (never hand-written, so a rebinding in
  `config.toml` can't go stale); palette listing every command with its binding, fuzzy-searchable;
  diagnostics view wrapping the existing `doctor` output plus live connection/transport/relay-policy
  state; status bar (connection state, transport path, relay policy).
- **Out:** the binding table itself (comes from 4.11's runtime + whatever screens have registered by
  this point, including 4.18's registry for feature-contributed palette commands).

> **Addendum (4.18 fix pass, architect review):** 4.18 ships `PaletteRegistry::find_binding` — the
> lookup a global "fire a command's keybinding without opening the palette" dispatch step needs — but
> `App::handle_key` never constructs or consults a `PaletteRegistry`; only the hardcoded `Ctrl+Q` quit
> check is a true global key today. This task is the natural owner of that missing dispatch wiring: it
> already handles bindings/help generation, and its own scope note above says it consumes "everything
> registered up to this point, including 4.18's registry" — that includes wiring `App::handle_key` to
> consult `PaletteRegistry::find_binding` before falling through to a screen's own handling, not just
> the palette/help screens' own read-only consumption of the binding table for display.

## Deliverables
1. `apps/tui/src/screens/help.rs`, `palette.rs`, `diagnostics.rs`, status bar component.
2. Test: every binding in the table appears in both the generated help screen and the palette (no
   binding reachable only by memory).

## Status
Done. `apps/tui/src/screens/help.rs`/`palette.rs`/`diagnostics.rs` + `apps/tui/src/statusbar.rs`. This
is the one Phase-4 screen task whose scope is real, currently-executing production code rather than an
isolated screen awaiting future navigation wiring: it closes the gap task 4.18's own fix-pass flagged —
`App::handle_key` now actually consults `PaletteRegistry::find_binding` (plus hardcoded `F1`/`Ctrl+K`
checks) before falling through to per-screen handling, so every registered command's binding fires
globally, not just via the palette UI. The help screen is genuinely generated from the live registry
(never hand-copied); a dedicated test walks the real registered set and proves every entry appears in
both surfaces. Diagnostics wraps `meridian doctor --json` as a subprocess rather than an in-process
dependency, preserving ADR 0020's `apps/tui` → `meridian-core`-only boundary (`apps/cli`'s probe logic
can't be linked in) — an explicit, documented architectural call, not an oversight.

**Review (combined `reviewer`, as named — "discoverability surface, no new trust/crypto content"):** two
blocking correctness findings in the parts of this task that actually run live, both fixed and
re-confirmed clean:
- **Unbounded screen stacking.** `dispatch_palette_action`'s `PushPane` arm lacked the idempotency guard
  the hardcoded `F1`/`Ctrl+K`/`Ctrl+R` checks already carry — repeated dispatch of the same palette
  command (reopening the palette and reselecting an entry, or a held key's terminal auto-repeat) pushed
  a fresh `Screen::Extension` every time with no depth limit, reproducible through ordinary use of the
  one command this task ships. Fixed with the same "don't push if already topmost" pattern, and a
  regression test that genuinely fails against the pre-fix unconditional-push code.
- **A stale hand-written Help section — the exact failure mode the "generated, never hand-written"
  deliverable exists to prevent.** The one hand-written `GLOBAL_KEYS` entries for `Tab`/`Shift+Tab`
  claimed both were hardcoded global checks that "cycle panes"; neither is checked in `App::handle_key`
  at all, and `Shift+Tab` isn't handled anywhere in the crate. The existing test was tautological
  (checked the render against its own source list, not real behavior), so the drift went uncaught.
  Fixed by dropping the two inaccurate entries and adding a test that drives each real global chord
  through a live `App` and asserts the promised transition genuinely happens.
- **Minor, also fixed:** the diagnostics subprocess's `PATH`-resolution of the `meridian` binary lacked
  an explicit accepted-risk note, despite the module doc otherwise justifying every other design choice
  — closed with documentation only (a real, malicious-binary-earlier-on-`PATH` scenario, judged an
  acceptable extension of the trust already implied by launching the TUI in the first place).
- **One non-blocking, informational forward-looking note, left as-is per the reviewer's own framing:**
  `find_binding`'s global interception runs ahead of every screen's text-entry fields too; nothing
  registered today triggers it (the sole command has no keybinding), but a future `Char`-bound global
  command could silently swallow that character app-wide. Worth a guardrail (e.g. reject/`debug_assert!`
  against a modifierless `Char` global binding) before the registered set grows.

`cargo test -p meridian-tui --test screens_help_palette` (grew from 15 to 16 tests during review),

`cargo clippy --workspace --all-targets -- -D warnings`, and `bash tools/lint-tui-no-cli.sh` all clean.
