# 3.1 — Enforce federation policy on the outbound dial path

**Phase:** 3 — Review of Phase 2 · **Feature:** review fix (F1, **blocking**) · **Depends on:** — · **Status:** done

## Goal
A `closed` / `allowlist` server must refuse to resolve or dial a client-named foreign domain, closing
the client-driven SSRF / internal-port-probe oracle that exists today in SRV mode.

## Scope
- **In:** one choke-point `state.federation.policy.admit(hint_domain)` check at the top of
  `dial_foreign` — **before discovery and before dial**; a denial variant on
  `RouteForeignError`/`FetchForeignError`; mapping to the existing client-visible `FED_DENIED` code.
- **Out:** the inbound handlers (already correct — `inbound.rs:86,164,232`); the per-partner map
  `policy` field (3.9/F7); restructuring `dial_foreign`'s dialing (3.7/F10); changing
  `FederationPolicy` itself.

## Deliverables
1. `apps/rendezvous/src/federation/outbound.rs` — `dial_foreign` (L264) consults policy first; new
   `RouteForeignError::Denied` plus its `convert_dial_error` arm (which today `unreachable!()`s on
   unmapped variants).
2. `apps/rendezvous/src/ws.rs` — `Denied` → `FED_DENIED` on both the fetch (L~357) and route (L~535)
   reply paths.
3. `apps/rendezvous/tests/federation_outbound_policy.rs` — `closed` + outbound `Fetch{hint}` →
   `fed_denied`; `closed` + `Route{to_hint}` → `fed_denied`; `allowlist` non-member denied, member
   admitted; **zero DNS lookup and zero TCP connect** asserted (bind a listener on the would-be
   endpoint and assert no accept; use a counted resolver behind the `Discovery` seam).

## Risks / notes
- The check must sit before **any** network I/O, not merely before `link::dial` — a DNS lookup alone
  is already an oracle. The test asserting zero resolver calls is the load-bearing one.
- Must not leak server B's policy to the client beyond the existing `fed_denied` code (2.9's error
  taxonomy is the contract; no new copy).
- Server ⊬ core still holds — this touches only `meridian-rendezvous`.

**Should-fix from code-reviewer, addressed:** the initial diff placed the SSRF policy check ahead
of the pre-existing `NotConfigured` (discovery-`None`) check inside `dial_foreign`. Since
`fetch_foreign_bundle` has no guard of its own and relies entirely on `dial_foreign`, while
`route_foreign` has its own separate, earlier `discovery.is_none()` guard before ever reaching
`dial_foreign`, this made the two outbound entry points disagree on a server that simply has
federation switched off (`Federation::default()`: `enabled: false`, `discovery: None`,
`policy: Closed`) — `fetch_foreign_bundle` would report `fed_denied` (implying a domain-specific
policy decision) while `route_foreign` correctly reported `fed_unreachable` ("not configured").
Fixed by reordering `dial_foreign` to check `discovery.is_none()` (`NotConfigured`) first, ahead of
the policy admission check — both are zero-I/O checks, so this costs nothing on the SSRF closure
(no discovery call, no DNS lookup, no TCP dial happens either way before the policy check still
runs). Added a regression test,
`disabled_federation_is_not_configured_not_denied_on_either_path`, asserting both
`fetch_foreign_bundle` and `route_foreign` return `NotConfigured` (never `Denied`) against
`Federation::default()`. Full suite re-run green after the fix (see Tests below).

## Outcome
`federation::outbound::dial_foreign` (`apps/rendezvous/src/federation/outbound.rs`) now consults
`state.federation.policy.admit(hint_domain)` right after the pre-existing `NotConfigured`/
discovery-`None` check (reordered post-code-review, see below) and before `Discovery::resolve`,
`resolve_dial_addr`, or `link::dial` — both the `NotConfigured` check and the policy check are
zero-I/O, so this ordering costs nothing on the SSRF closure while keeping "federation is off" and
"federation refused this domain" as distinct, correctly-reported outcomes. A `Decision::Reject`
short-circuits with a new `RouteForeignError::Denied` before any DNS-shaped or TCP-shaped call
executes. `state.federation.policy` is this server's OWN
admission policy — the identical `FederationPolicy` value `federation::inbound`'s handlers already
consult for the inbound direction — so admission is now symmetric: a `closed`/`allowlist` server
refuses a non-admitted domain in either direction, not merely when that domain dials in.

Added `FetchForeignError::Denied` and wired it through `convert_dial_error` as a real mapped arm
(not folded into the pre-existing `unreachable!()` group, since `dial_foreign` genuinely produces
it now). `route_foreign`'s own reachability pre-check match (which collapses most `dial_foreign`
failures into the target-liveness `TargetUnreachable`) got a dedicated `Denied` arm alongside its
existing `Fed(fed_err)` arm — without it, A's own policy refusal was silently reported as
`not_connected` ("recipient offline") instead of `fed_denied`, caught by this task's own new test
for the `Route` case. `ws.rs`'s `federated_fetch_error_reply`/`federated_route_error_reply` map
`Denied` to the existing `error_codes::FED_DENIED` — the identical client-visible code a foreign
server's own `POLICY_DENIED` reply already produces, so a client cannot distinguish "A wouldn't
dial" from "B wouldn't admit" by error code alone (no new copy, no wire change, per 2.9's frozen
taxonomy).

**Collateral fix, not scope creep — confirmed necessary, not assumed:** `Federation::default()`'s
`policy` field is `Closed` (fail-closed default), and the existing `org_a_federation()` test
helpers in `federation_fetch.rs`/`federation_route.rs`/`federation_abuse.rs` never set A's own
outbound `policy` field, relying implicitly on the fact that no check consulted it. Running the
full required test list against the new choke-point (before touching the test fixtures) reproduced
5 failures across `federation_fetch.rs` (`FedDenied` instead of the expected outcome) — direct
proof the fix was live and, without this collateral update, would have broken tests whose actual
intent is to exercise B's behavior, not A's own admission decision. Fixed by setting
`policy: FederationPolicyMode::Open` explicitly in those three `org_a_federation()` helpers (a
one-line, well-commented addition each), which is exactly the config change a real operator would
need after this fix — restoring, not weakening, that these fixtures continue to test what they've
always claimed to test. `demo/two-orgs/docker-compose.yml` was already correctly configured
(`policy = allowlist` naming the partner explicitly on both sides) and needed no change.

`apps/rendezvous/tests/federation_outbound_policy.rs` (new) covers all four required cases: (1)
`closed` + outbound `Fetch{hint}` → `fed_denied`; (2) `closed` + outbound `Route{to_hint}` →
`fed_denied` (this is the case that caught the `route_foreign` pre-check gap above); (3) `allowlist`
non-member denied, member admitted — admission proven by getting the DISTINCT `fed_unreachable` code
from a deliberately dead dial target, never `fed_denied`, so a bug that kept rejecting the listed
domain couldn't pass by accident; (4) the load-bearing zero-I/O test — a real `TcpListener` bound at
the would-be dial endpoint (proven to receive zero `accept`s) plus a call-counting `Discovery`
stand-in installed via `Arc::get_mut` into a freshly-built `AppState` (proven to receive zero
`resolve` calls), driven directly through `federation::outbound::fetch_foreign_bundle`/
`route_foreign` (both already `pub`) rather than only through the wire, so the assertion is about
the actual I/O boundary, not just the client-visible error code.
