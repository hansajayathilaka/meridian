# 6.3 — Envelope v2 core cutover: wire shape + canonical AAD + commit-on-decrypt + desync short-circuit fix

**Phase:** 6 — Envelope v2 · **Feature:** ADR 0016 (C2, C3, C5, C6, C7-short-circuit) · **Depends on:** — · **Status:** done

## Goal
The load-bearing rewrite the whole phase gates on. Drops `MessageEnvelope`'s per-message identity-key
signature, moves authentication to the ratchet AEAD under the canonical v2 AAD, makes X3DH provisional
until decrypt succeeds (so a mutated preamble can never burn a one-time prekey or install a poisoned
session), and fixes the `open_bytes` desync short-circuit in the same pass — the ADR requires these
together because it is the same function.

**This is the highest-risk task in the phase.** `ChatState::open_bytes` already carries delicate,
twice-review-fixed desync-recovery machinery (tasks 1.18 and its 4.9 follow-up fixup — see the
extensive doc comments in `apps/core/src/chat.rs` around `open_bytes`, `responder_session_ek`, and
`ResponderEk`). Architect review of this phase's scope confirmed: (a) landing the AAD/domain-tag
change (C3) without simultaneously moving to commit-on-decrypt (C2) would reproduce the exact R3
vulnerability this ADR calls out, so these must not be split across separately-mergeable increments;
(b) the existing eager-OTK-consume behavior inside `establish_responder_session` — used by *both* the
first-contact branch and the 4.9 stale-session fallback branch — is currently intentional (see its doc
comment, cross-referencing task 1.33's `ANSWER_TIMEOUT` precedent) and this task must unwind that
design decision, not just bolt a commit step onto the outside of it.

## Scope
- **In:**
  - `apps/envelope/src/envelope.rs`: `MessageEnvelope` v2 — leading `v: u16` (= 2), drop `sig`, keep
    `sender_pub`/`prekey`/`ct`; `ENVELOPE_DOMAIN` → `b"mrd.env/2"`. Extract the existing presence-flag
    preamble encoding (currently inside `signing_input`) into a reusable
    `preamble_aad_bytes(prekey: &Option<Prekey>) -> Vec<u8>` consumed by the AAD builder, not a
    signature. Remove `signing_input`/`signing_bytes`.
  - `apps/crypto/src/ratchet.rs`: `DoubleRatchet` bakes `"mrd.env/2" ‖ AD` into its fixed `ad` field at
    construction. `encrypt`/`decrypt`/`message_aad` gain a `preamble: &[u8]` parameter so
    `message_aad(preamble, enc_header) = self.ad ‖ preamble ‖ enc_header`. **The decrypt side must use
    the received preamble bytes, never locally-recomputed ones** (C3 is explicit: an implementation
    that "helpfully" uses locally-derived values reintroduces the gap).
  - `apps/crypto/src/session.rs`: `Session::encrypt`/`decrypt` thread the preamble bytes through
    (encrypt derives it from `self.prekey`/`needs_prekey()`; decrypt takes it from the caller, which
    already has the parsed envelope).
  - `apps/crypto/src/x3dh.rs`: doc-comment note only — `derive()` already builds `AD` from raw Ed25519
    encodings (never Montgomery-converted), so C3's "raw Ed25519, never normalized" requirement is
    already satisfied here; no behavior change needed.
  - `apps/core/src/chat.rs`: `seal_bytes` drops the `sign(...)` call. `open_bytes`/
    `establish_responder_session` rewritten for **provisional X3DH**: add a *read-only* prekey lookup
    (a non-destructive counterpart to `take_otk_secret`, e.g. `peek_otk_secret`/`peek_spk_secret`) used
    for the provisional establish+decrypt attempt; only on a successful decrypt does the OTK actually
    get consumed and `sessions.insert` run. The existing desync short-circuit fallback (the
    `UndecryptableHeader` branch and `responder_session_ek` freshness gate from tasks 1.18/4.9) must be
    re-verified — not merely preserved by inspection — under the new provisional control flow.
  - If a post-decrypt "does the derived AD match expectations" check is added as a refactor-regression
    guard (C6), it must be doc-commented as non-authenticating/tautological — never described as a
    security check. A successful AEAD decrypt already implies it.
- **Out:** the `eid` field/replay-dedup (6.4 — not part of the AEAD/AAD safety property, safe to land
  after this task); conformance vectors (6.5); test re-pointing / new adversarial cells (6.6); doc-sync
  (6.7).

## Explicit negative constraint (flag-day, C5/R5)
Architect review flagged this as the sharpest way to get this phase wrong: **the `v` field MUST NOT be
wired through any existing negotiation mechanism.** Two exist in the codebase and are one associative
hop away from "reuse the versioning we already have" — both are the *wrong* pattern here and must not
be touched by this task:
- Bundle `v:1`/`v:2` (`wire-protocol.md §7`) is explicitly *soft*: a version downgrade is tolerated
  with a trust-state warning, not hard-rejected. Reusing that pattern for envelope versioning would
  reintroduce exactly the "malicious server claims your peer only speaks v1" oracle R5 forbids.
- `Hello{streams: [{name, ver, dir, mandatory}]}` (`wire-protocol.md §5`) is capability negotiation for
  `mrd.ctrl/1` stream types — designed for graceful mutual discovery, the opposite of what R5 wants for
  message authentication.

A `v` mismatch on `MessageEnvelope` must be a **local, unilateral hard decode/reject** — never a
round-trip, never a negotiated fallback. This falls out for free from ordinary strict CBOR struct
decoding (`ciborium::from_reader`, confirmed no lenient/default-filling behavior beyond explicit
`#[serde(default)]` opt-outs) as long as `v` is a genuinely mandatory field — **do not** make `v`
`Option`/defaulted "for compatibility," and do not add any code path that peeks at a version number and
branches to a v1-compatible decode/verify path; that branch *is* the forbidden negotiation.

## Risks / notes
- No partial/interim landing that ships C3's AAD without C2's commit-on-decrypt — that combination is
  actively unsafe (R3), not merely incomplete.
- The freshness-gated replay defense (`responder_session_ek`, which took two review rounds — one fix
  that was itself exploitable — to get right) must be preserved exactly, but its evaluation point moves
  from "after an eager-OTK-consuming establish" to "gating a provisional establish-and-decrypt that only
  commits atomically on success." This reordering is the delicate part of this task — do not treat it
  as incidental plumbing.
- `apps/core/src/session.rs` (P2P substrate) and `apps/cli/src/opacity.rs` call `open_bytes`/
  `seal_bytes` only through the existing public API (store/handle/our_ik/peer_ik/blob) — confirmed by
  architect-review code read that no signature-shaped changes ripple into their business logic. Their
  *tests*, and `apps/tui`'s own test suite (`live_session_e2e.rs`, `run_worker_chat.rs`,
  `inbound_delivery.rs`, etc.), may still pin v1-shaped fixtures independently and must be exercised
  explicitly, not assumed to pass because `apps/core`'s own tests do.
- `apps/transport/tests/webrtc_backend.rs::tampered_remote_fingerprint_never_connects` must stay green
  **unmodified** — run it explicitly as a regression check. This is the evidence that dropping the
  envelope signature is a no-op for §4.6 fingerprint binding, which never depended on it.

### Design note: provisional-establish vs. the `responder_session_ek` freshness gate

**The ordering is unconditional and sequential, not a race, and it did not change from the plan:**

1. `open_bytes` decodes the envelope and runs two cheap, unconditional checks first: `envelope.v ==
   ENVELOPE_VERSION` (hard reject, C5/R5 — never negotiated), then `envelope.sender_pub == from`
   (`SenderMismatch`, unchanged from v1).
2. **No session at all for this peer** (`!self.sessions.contains_key`) — the task 1.18 "safe half".
   No freshness check applies here at all (there is nothing yet to roll back to): a provisional
   responder session is built via `establish_responder_session_provisional` (peek-only: reads
   `PrekeyVault::peek_spk_secret`/`peek_otk_secret`, mutates nothing) and a decrypt is attempted
   against it. Only a **successful** decrypt commits: `commit_responder_otk` (the one place
   `take_otk_secret` — destructive — is called), `record_responder_ek`, and `sessions.insert`, in
   that order, atomically, right there in the same match arm. A failed decrypt (or a failed
   provisional establishment, e.g. `UnknownPrekey`) propagates the error with **zero** side effects.
3. **A session already exists** — the existing session's `decrypt` is tried first, unchanged
   priority from task 4.9. Only on `CryptoError::UndecryptableHeader` does the task-4.9 fallback
   even begin to run, and inside that fallback:
   - **The freshness gate (`is_recorded_responder_ek`) runs FIRST, before any provisional
     establishment is even attempted.** It is a pure, cheap, session-free lookup against
     `envelope.prekey.ek_pub` and `self.responder_session_ek` — it does not need, and does not run,
     any crypto. If it matches (this `ek_pub` already established a still-SPK-valid responder
     session), the fallback refuses outright: no provisional establishment is attempted at all, and
     the code falls straight through to `note_desync` + `Err(Desync)`.
   - **Only if the freshness gate passes** does a provisional establishment + decrypt attempt run,
     with the identical commit-on-success discipline as branch 2 above.

**Therefore: the freshness gate is a precondition for attempting provisional establishment, never a
competing or racing check.** There is no scenario where either could "succeed while the other would
refuse" — they are not evaluated against the same event at the same time. Freshness answers "is this
`ek_pub` even worth trying?" *before* any session/decrypt work happens; commit-on-decrypt answers
"did the attempt this gate allowed through actually prove itself?" *after* that work, and only
inside the one call site the gate let through. This is a strict two-stage pipeline
(freshness-prefilter → provisional-attempt → commit-only-on-success), not two independent gates that
could disagree.

This ordering was exactly what was planned before implementation, and the implementation did not
reveal a need to change it — the two mechanisms were already answering different questions
(freshness vs. authenticity-via-successful-decrypt) at different pipeline stages, so composing them
sequentially fell out naturally once C2's "don't touch anything until decrypt succeeds" rule was
applied literally to both the first-contact branch and the 4.9 fallback branch, per the task's
explicit instruction to unwind eager-OTK-consumption on *both*.

### Deviations from the plan

The number of `meridian-crypto` integration test files (`ratchet_replay.rs`, `session_roundtrip.rs`)
and the `xtask` vector generators that call `DoubleRatchet`/`Session::encrypt`/`decrypt` directly and
needed mechanical preamble-argument updates to compile weren't fully anticipated going in — these
aren't named in the task file's scope list, but `cargo build --workspace` / `cargo clippy --workspace
--all-targets -- -D warnings` (both explicitly required by this task) cannot pass without fixing
them, so they were fixed the same way as the explicitly-listed files: mechanically, preserving every
existing assertion's meaning.

**One real, previously-undocumented behavior change, surfaced by code-reviewer and now recorded
here (not a deviation from what the code does, a gap in what this section originally said about
it):** under v1, a first-contact envelope whose freshly-established session failed to decrypt fell
through a shared match block that classified the failure as `ChatError::Desync` (bumping
`note_desync`'s counter). Under the v2 rewrite, the identical scenario now propagates via `?`
(`open_bytes`, the "no session at all" branch) as `ChatError::Crypto(CryptoError::UndecryptableHeader)`
and never touches `note_desync`. This is the correct classification, not an accidental side effect
of routing that branch through `?`: `ChatError::Desync`'s own doc frames it as being about an
*existing* session's two live header keys, a concept that doesn't describe a first-contact attempt
with no prior session to have desynced from, and it is exactly what `preamble_mutation.rs`'s
re-pointed cells now correctly assert. Consequence, made explicit: a burst of bogus first-contact
envelopes against a peer cannot drive `recovery_recommended`'s threshold — only a genuinely
*existing* session repeatedly failing to decrypt (the task-4.9 fallback branch, which still
classifies as `Desync`) can. Now documented in-line at the `provisional.decrypt(...)?` call site in
`open_bytes` as well as here.
