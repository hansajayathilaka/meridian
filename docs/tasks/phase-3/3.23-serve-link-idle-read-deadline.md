# 3.23 — Bound `serve_link`'s idle read (no deadline on the established-link serve loop)

**Phase:** 3 — Review of Phase 2 · **Feature:** review fix (found during 3.22's coverage work, not
part of the original report) · **Depends on:** 3.2, 3.4 · **Status:** done

## Goal
An already-handshaked federation peer that stalls or trickles a frame must not hold a `max_links`
slot forever — the accept-side serve loop needs the same kind of bounded wait every other s2s I/O
exchange in this codebase already has (task 3.2's handshake timeout, task 3.3's outbound timeouts).

## Scope
- **In:** wrap `apps/rendezvous/src/federation/inbound.rs`'s `serve_link` main-loop
  `link.recv_frame().await` in an idle-read deadline (`with_deadline`/`tokio::time::timeout`,
  mirroring the pattern `finish_handshake` and the outbound dial/request path already use), backed
  by a new, explicit config knob (do not silently reuse `handshake_timeout_ms` or
  `request_timeout_ms` — this is a genuinely different phase of the connection's lifecycle from
  either). On timeout, drop the link cleanly (same as any other link-closing path) and free its
  `max_links` permit.
- **Out:** any change to the handshake path itself (task 3.2, already bounded) or the outbound
  dial/request path (task 3.3, already bounded) — this task is the one remaining unbounded s2s I/O
  wait, not a re-audit of the ones already fixed.

## Deliverables
1. A new `Federation` config field (`serve_idle_timeout_ms` or similar — name it for what it
   actually bounds) with a documented, justified default (do not guess a round number without
   reasoning — a real reply on an established link should be fast; consider reusing 3.20's
   measurement methodology or reasoning from `request_timeout_ms`'s existing precedent).
2. `serve_link` wrapped so a peer that stalls mid-frame after handshake is dropped and its
   `max_links` permit reclaimed.
3. A test proving the fix: task 3.22's `slow_loris_after_link_established_reveals_no_idle_read_deadline`
   in `apps/rendezvous/tests/federation_link_dos.rs` currently pins the *absence* of this behavior
   (asserts nothing happens within a bounded window, then the connection resumes once trickled
   input completes) — update it (or add a sibling) to assert the connection is now dropped and the
   permit reclaimed within the new deadline, mirroring task 3.2's cases (c)/(d) "prompt drop, not
   merely eventually" mutation-proof shape.

## Risks / notes
- **Severity is worse than "an admitted partner going rogue."** In the default WebPKI mode
  (`federation.ca_bundle_path` empty), `FederationListener::finish_handshake` neither pins an
  expected domain nor calls `FederationPolicy::admit_any` before a frame is fully decoded —
  admission is checked only inside `handle_fed_fetch`/`handle_fed_route`/`handle_fed_reachability`,
  which a slow-loris connection never reaches. So in WebPKI mode, **any actor holding a TLS client
  certificate that chains to a public CA** — not necessarily an org on this server's federation
  allowlist, not necessarily one this server has ever agreed to talk to, exploitable even when
  `federation.policy = closed` — can occupy a `max_links` slot indefinitely. Private-CA/air-gap
  mode is the narrower case the original framing described (trust root is exclusively the
  operator's own CA). Frame the fix's urgency accordingly — this is closer to "any TLS-cert holder
  can starve federation link capacity" than "a known-bad but already-trusted partner."
  (3.22's security-reviewer sign-off, carried forward here rather than re-derived.)
- Bounded regardless: at most `max_links` peers can hold a slot this way, and each is capped at
  `MAX_FRAME_LEN` bytes of allocation — not an unbounded resource leak, but a real starvation
  vector against every other legitimate partner trying to open a link while slots are held.
- Found and demonstrated by task 3.22's `slow_loris_after_link_established_reveals_no_idle_read_deadline`
  test — read that test first, it already proves the gap precisely.

## Outcome
New `Federation::serve_idle_timeout_ms: u64` config field (`apps/rendezvous/src/config.rs`) —
deliberately a THIRD, independent timeout knob (not a reuse of `handshake_timeout_ms`, which
bounds the PRE-AUTH handshake `serve_link` never reaches, or `request_timeout_ms`, which bounds an
OUTBOUND round trip this server itself initiates). Default `10_000`ms, `TODO: confirm` like its
siblings but derived by analogy from `request_timeout_ms`'s own precedent (a genuine reply on an
already-established link should cost about the same as this server's own outbound request/reply
exchange — one wire round trip between already-mTLS-authenticated peers, no repeated handshake
cost). Fail-closed `validate()` rejects `0`, mirroring the sibling fields exactly. Three new unit
tests (default value, TOML/env override, zero-rejected) alongside the existing timeout-knob tests.

`apps/rendezvous/src/federation/inbound.rs`'s `serve_link` now computes `idle_timeout` once before
its main loop (mirroring `run_federation`'s own once-computed `handshake_timeout`) and wraps
`link.recv_frame()` in `crate::federation::link::with_deadline(idle_timeout, ...)` **inside** the
loop, so the deadline re-arms on every successfully-received frame — a true per-iteration idle
wait, not a total-lifetime cap on the link. On `DeadlineExceeded`, `serve_link` returns cleanly
(no reply frame, same shape as any other link-closing error), and the caller (`run_federation`)
releases the already-held `max_links` permit automatically the instant `serve_link` returns — no
permit-plumbing into `serve_link` itself was needed. The drop path logs nothing, so there is
nothing raw-identifier-shaped for `tools/lint-no-raw-id-logging.sh` to catch.

`apps/rendezvous/tests/federation_link_dos.rs`'s `slow_loris_after_link_established_reveals_no_idle_read_deadline`
(which had pinned the gap as a known residual) is rewritten to
`slow_loris_after_link_established_is_dropped_by_the_idle_read_deadline`, proving the fix rather
than the gap: (a) a stalled post-handshake connection is dropped **promptly** once
`serve_idle_timeout_ms` elapses (bounded assert at `serve_idle_timeout_ms * 5`, mirroring task
3.2's own "prompt, not merely eventual" mutation-proof shape); (b) its `max_links=1` permit is
genuinely reclaimed — a retried dial completes a real `FedOp::Reachability`/`FedOp::Reachable`
round trip over the new link within a bounded window, proving `serve_link` actually took over the
connection (not merely that the client-side handshake succeeded, which `dial()`'s `Ok` alone does
not establish — see the review finding below). A new sibling test,
`periodic_frames_slower_than_the_idle_timeout_keep_the_link_alive`, proves the deadline is a true
idle-reset: six real request/reply round trips spaced 100ms apart against a 200ms idle timeout,
cumulative link lifetime well past one `idle_timeout` window, link stays alive throughout.
`federation_config_full` gained a `serve_idle_timeout_ms` parameter threaded through its one
caller and the `federation_config` wrapper (a generous default for tests that don't care about
this knob, matching the existing `max_links` convention).

**Two-round review, both closed:**
1. Combined `reviewer` agent (architect + security-reviewer lenses) + a parallel `test-engineer`
   mutation-check — **architect: pass, zero findings** (new knob vs. reuse judged correct and
   well-precedented; timeout placement — computed once outside the loop, applied fresh inside it —
   architecturally consistent with `run_federation`'s handshake timeout and the outbound dial path;
   no `meridian-core` dependency, no scope creep into 3.2/3.3's already-bounded paths).
   **security-reviewer: pass on the substantive fix** — genuinely closes the described gap (sits
   upstream of every `FederationPolicy` admission check, so it protects against *any* WebPKI-mode
   TLS-cert holder, not merely an admitted federation partner, matching the task's Risk framing);
   confirmed a true idle-reset (not a lifetime cap) by direct code reading; confirmed no raw
   identity in any log line on the drop path; confirmed the `10_000`ms default is defensibly
   derived, not guessed. **Both passes independently found the same blocking test-soundness gap**
   in part (b) of the rewritten test: `dial()` returns `Ok` purely from the CLIENT-side handshake
   completing, entirely independent of whether the SERVER actually granted a `max_links` permit
   (`run_federation` only checks `link_slots.try_acquire_owned()` *after* `finish_handshake`
   returns) — so the original part (b), which only checked `dial()`'s return value, could not
   distinguish "permit genuinely reclaimed" from "permit leaked, but a separate handshake slot was
   free." test-engineer proved this concretely by mutation (`drop(link_permit)` → `mem::forget`):
   the original test still passed.
2. **Follow-up fix, re-verified by the same mutation:** part (b) strengthened to a real
   `FedOp::Reachability`/`FedOp::Reachable` round trip over the retried link (mirroring this same
   file's existing case (d), which proves permit-exhaustion drops via real post-handshake I/O, not
   `dial()`'s return value alone). Re-ran the identical `mem::forget` mutation against the
   strengthened test: **it now fails** as intended (`BrokenPipe` sending the round-trip frame,
   since the connection was in fact dropped for lack of a permit) — confirming the assertion is
   now genuinely load-bearing. Mutation reverted; `inbound.rs`'s diff is unchanged by the mutation
   check.
