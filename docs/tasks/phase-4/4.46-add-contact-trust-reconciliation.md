# 4.46 — Reconcile `Effect::AddContact` into the live in-memory `TrustStore`

**Phase:** 4 — Verification & Trust + Terminal TUI Client · **Feature:** T17 — Terminal TUI Client (gap closure, fix for 4.45's fourth defect) · **Depends on:** 4.19, 4.36, 4.42 · **Status:** pending

## Goal
Make a contact added via the plain `n`-add flow (`Effect::AddContact`) immediately reachable and
verifiable in the *same* live session — closing the fourth defect the phase's exit gate found (task
4.45): today an initiator can add a contact, send them a first-contact message, and still gets
`TrustError::UnknownContact` pressing `v`→`v`→`y` to mark them verified, because the completion never
syncs into the live in-memory `MainState::trust`. This closes the initiator-side half of T17's own
acceptance criterion "a user with **no prior state** reaches a delivered, verified message using
only on-screen affordances" — the responder-side half was already closed by task 4.42.

## Pre-code consult assessment — recorded here, not deferred
**No mandatory pre-code architect/security-reviewer consult is required.** Compared against why 4.40
and 4.42 needed one: 4.40 extended decrypted key material's in-memory residency for the whole session
lifetime — a real security-posture question with no existing precedent. 4.42 faced a structurally
forced choice between severable shapes, decided by an architect consult at plan time because
`TrustStore::observe`'s `hint == ""` output made one candidate workaround (re-add via a shown `mrd1:`
id) provably impossible — a genuine design decision with alternatives to weigh. This task has neither:
the fix shape is `App::apply_added_contact`, an almost line-for-line mirror of `App::apply_accepted_request`
(`apps/tui/src/app.rs:2195-2229`) — already landed, and independently re-verified twice over in 4.42's
own review round (once by the first `reviewer` pass, once by a dedicated second `architect` pass that
traced every `push_screen`/`Screen::Main`/`Screen::Chat`/`Screen::Verify` construction site and confirmed
the stack-walk's structural invariant holds). There is no ADR-adjacent identity or residency question
here. Ordinary post-diff `reviewer`/`test-engineer` sign-off (below) is sufficient, mirroring 4.44's
precedent, not 4.40's/4.42's. **If implementation reveals a genuine design choice this planning pass
did not anticipate** (most likely in the interleaving-gap fix below, if it turns out to require a
mechanism heavier than reusing `contacts::apply_update`), stop and flag it explicitly rather than
deciding silently — but this planning pass, reading the relevant code paths directly, found none.

## Scope
- **In — the primary, confirmed defect (mandatory):**
  1. Add `App::apply_added_contact(&mut self, added: AddedContact)`, wired from a new
     `WorkerEvent::Completed(Effect::AddContact(effect))` arm in `App::handle_worker`'s event-first
     match (`apps/tui/src/app.rs:1893-1969`), alongside the existing `AcceptRequest`/`RejectRequest`/
     `LoadHistory` arms — matched on the *event*, regardless of what is on top of the screen stack, for
     the same "no single screen owns this consequence" reason those three already are.
  2. `apply_added_contact` reuses `apply_accepted_request`'s exact `live_trust_idx` stack-walk verbatim
     in structure (cite its doc comment, don't re-derive the reasoning in a divergent form): locate
     `Screen::Main`, then scan **above** it for a `Screen::Chat`/`Screen::Verify` frame; if one exists
     (i.e. `MainState::trust` was `std::mem::take`n), route `trust.observe(added.pubkey, "", added.added_at)`
     there instead of the placeholder left on `Main`; else route it to `Screen::Main` directly.
  3. Do **not** hand-optimize a "simpler, always-`Screen::Main`" version on the theory that
     `Screen::Chat`/`Screen::Verify` can never be pushed on top of `Main` while an `Effect::AddContact`
     is in flight (this planning pass traced that it is very likely true today — see Risks/notes — but
     reusing the general mechanism is cheap and forecloses a future navigation feature silently
     reintroducing this exact defect class a third time, the way the original `apply_accepted_request`
     doc comment's own "not reachable today" claim turned out false under 4.42's review).
- **In — a second, closely related interleaving gap traced during this planning pass (required
  investigation; fix is strongly recommended, not optional, unless the investigation genuinely shows it
  cannot be closed safely — say so explicitly if so):**
  `Effect::AddContact` is dispatched from `Screen::Main`'s own embedded `ContactsState.add` sub-flow
  (`apps/tui/src/screens/contacts.rs`), not from a separately-pushed screen the way `AcceptRequest` is
  from `Screen::Requests`. Reading `App::handle_key`'s ordering (`apps/tui/src/app.rs:1468-1541`)
  confirms `Ctrl+R` is a genuinely global, unconditional binding checked **before any screen-specific key
  interception** — it fires even while `state.contacts.add` is `Some` (mid "Adding"), pushing
  `Screen::Requests` on top of `Screen::Main`. When `Effect::AddContact` then completes, the existing
  per-screen fallback dispatch (`match self.screens.last_mut() { Some(Screen::Main(state)) =>
  main::handle_worker(state, event), ... }`, `apps/tui/src/app.rs:1970+`) routes the event to
  `Screen::Requests` instead — whose own `requests::handle_worker` does not forward it anywhere — so
  `contacts::handle_worker`'s `AddContactState::Adding` arm (the *only* place today that transitions the
  sub-flow out of `Adding` and calls `contacts::apply_update` for the display row,
  `apps/tui/src/screens/contacts.rs:748-757`) never runs. Net effect: the add-contact form is stuck in
  `Adding` forever (no visible error, no recovery) and the live Contacts list never shows the new row for
  the rest of the session — a second occurrence of the same "a worker completion doesn't reconcile into
  live state when it isn't the frame that dispatched it" defect class, reachable a different way than
  the primary defect. `apply_added_contact` should therefore also, on whichever `Screen::Main` frame
  exists, call `contacts::apply_update(&mut main.contacts, ContactEntry::from_added(added.clone()), false)`
  and reset `main.contacts.add` back to `None` (or whatever equivalent resolves the stuck sub-flow)
  **unconditionally** — not only when `Main` happens to still be on top. `contacts::apply_update`
  (`apps/tui/src/screens/contacts.rs:769-781`) is a plain upsert-by-pubkey — confirmed idempotent by
  inspection, so a redundant second call in the ordinary non-interleaved case (once here, once via the
  untouched per-screen `contacts::handle_worker` path) is safe and produces no duplicate row or panic.
  **Verify this idempotency claim under test (Deliverable 4) rather than assuming it** — do not remove
  or alter the existing per-screen path to avoid the double call.
- **Out:** any new wire type, protocol, or crypto change; the `--export-json` doc/demo-script mismatch
  (split into task [4.47](./4.47-export-json-doc-fix.md) — unrelated root cause, traced to task 4.15,
  three tasks before `Effect::AddContact` (4.19) even existed); wiring receive-side key-change/desync
  detection into the TUI's live inbound loop (the separate, already-tracked task-4.35 gap 4.45's own
  Status section named as the reason this defect isn't yet actively exploitable — not this task's
  defect); the `run_accept_request` partial-failure repair action and Shape B (4.42's own severed
  findings, already tracked in [phase-4/README.md](./README.md#tasks-todo)'s "Findings with no task
  yet" — unrelated); any change to `TrustStore::can_send`'s fail-open-for-unknown-peer semantics itself
  (T08 core trust-state-machine territory — this fix closes the *staleness* gap that lets an
  unknown-to-the-live-session peer reach that gate in the first place, it does not touch the gate's own
  logic).

## Risks / notes
- Reuse `apply_accepted_request`'s exact stack-walk shape rather than hand-optimizing around the
  planning-time reachability trace above — see Scope point 3. If the implementer's own trace disagrees
  with this planning-time trace (i.e. finds a path that *does* push `Screen::Chat`/`Screen::Verify` on
  top of `Main` while `Effect::AddContact` is in flight), say so explicitly; that would make the
  stack-walk load-bearing rather than merely defensive, and should be called out as such.
- `contacts::apply_update`'s idempotency is asserted here from reading the function, not from a
  dedicated test in this task's own diff before now — Deliverables 3/4's tests must actually exercise the
  double-call path live (the non-interleaved case naturally does, via the unmodified per-screen path
  still running alongside the new App-level call), not just assert it once.
- Do not touch `TrustStore::can_send`'s fail-open semantics, `verification-ux.md`'s wording, or any trust
  state transition. This fix closes a staleness gap, not a trust decision — mirroring 4.42's own binding
  "TOFU is not verification" guardrail. A rendered `verified` glyph, a skipped safety-number step, or a
  dismissible key-change warning anywhere in this diff is a blocking finding for `security-reviewer`.
- `MainState.trust`/`main.contacts` "moved, not cloned" discipline (`crate::screens::main`'s own module
  doc) is the same invariant `apply_accepted_request`/`App::reclaim_trust` already depend on — do not
  introduce a second, divergent `TrustStore` copy anywhere in this fix.
- **Definition of Done gate 9:** no new TUI surface — this repairs existing T17 core-screen wiring
  (Contacts/Main), the same "intrinsically satisfied" reasoning 4.42/4.44 already used. No
  `SurfaceRegistry` registration is added.
- Disjoint files from task [4.47](./4.47-export-json-doc-fix.md) (this touches `apps/tui/src/app.rs` +
  tests; 4.47 touches only `docs/`) — no logical or file-level dependency between the two; either may
  land first.

## Status
**Done.** Both the primary defect and the interleaving gap are closed. This closes the initiator-side
half of T17's own acceptance criterion "a user with no prior state reaches a delivered, verified
message using only on-screen affordances" — the responder-side half was already closed by 4.42.

**Primary fix.** A new `WorkerEvent::Completed(Effect::AddContact(_))` arm in `App::handle_worker`'s
event-first match, alongside `AcceptRequest`/`RejectRequest`/`LoadHistory`, calls
`App::apply_added_contact`, which reuses `apply_accepted_request`'s exact `live_trust_idx` stack-walk
verbatim in structure to replay `trust.observe(added.pubkey, "", added.added_at)` into whichever
`TrustStore` is actually live. The general mechanism was kept rather than hand-optimized away, per the
task's own instruction — this planning pass's and both later independent re-traces' conclusion that
`Screen::Chat`/`Screen::Verify` can never sit above `Screen::Main` while `Effect::AddContact` is in
flight (the add-contact sub-flow is embedded in `Screen::Main` itself, never a separately-pushed
screen) held under three separate independent traces from source, not just repeated assumption.

**Interleaving gap — confirmed reachable, not hypothetical, and fixed.** `Ctrl-R` is a global,
unconditional binding checked before any screen-specific key interception, reachable even mid
`AddContactState::Adding`; without a fix, a completion racing it would land with `Screen::Requests` on
top instead of `Screen::Main`, leaving the add-contact form stuck in `Adding` forever and the new
contact absent from the live Contacts list. `App::apply_added_contact` now also calls
`contacts::apply_update` and resets `main.contacts.add` to `None` unconditionally. **Correction from the
originally-reported mechanism:** this was first documented (in both the code and this section) as a
"double call, exercised live" race tolerated by `contacts::apply_update`'s idempotency. The `reviewer`
pass instrumented the per-screen `Adding` arm directly and proved that claim false — because
`apply_added_contact` runs strictly before the per-screen fallback dispatch and already resets
`main.contacts.add` to `None`, the per-screen arm's own guard never fires afterward, so
`contacts::apply_update` runs exactly **once**, pre-empting the per-screen path rather than racing it.
Not a functional bug (a single call is strictly safer than the claimed race), but the doc comments in
`app.rs` and `docs/architecture/tui-client.md` asserted a mechanism that doesn't exist — corrected in
both places, plus in this section, re-verified clean against fmt/clippy/the full test suite after the
correction.

**Restart-parity (Deliverable 5, cited not re-derived, independently confirmed twice over):** a restart
already makes an added contact verifiable today — `MainState::from_session` builds `trust:
session.trust` directly from a `LiveSession` populated by a fresh `trust.bin` read at boot (`load_trust`
via `handle_unlock`/`handle_load_session`), confirmed by both the implementer and `test-engineer`'s
independent trace. This task's tests correctly focus on the same-session staleness gap only.

**Coverage (Deliverables 3–4).** Two new screen-level tests in `apps/tui/tests/accept_to_chat.rs`:
`add_contact_makes_the_added_peer_reachable_for_verify` (same-session add-then-verify, no restart —
strengthened during review with an assertion that the replayed `pinned_key_history[0].first_seen_unix`
matches the worker-supplied `added_at` exactly, closing a coverage gap `test-engineer` found: a
hardcoded/wrong timestamp survived the original assertions, since neither `trust_state()` nor the
`ContactEntry` fields it also checks are sourced from the `trust.observe()` call this test exists to
exercise) and `a_ctrl_r_interleaved_while_add_contact_is_in_flight_still_reconciles_the_live_contacts_list`
(the interleaving-gap regression). Both drive real `crossterm` key events through `App`, real
`worker::dispatch` against a real sealed `$MERIDIAN_HOME` — no hand-built `WorkerEvent`s or fabricated
`LiveSession`, confirmed independently by `test-engineer`'s own trace of the harness.
