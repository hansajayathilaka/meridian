# 4.43 — File-backed prekey republish performance (188 s → seconds)

**Phase:** 4 — Verification & Trust + Terminal TUI Client · **Feature:** T17 — Terminal TUI Client (gap closure, fix for 4.39's recorded, unfixed defect as measured live by 4.41) · **Depends on:** 4.39, 4.40 · **Status:** pending

## Goal
Stop a file-backed account from waiting **~188 seconds on "Unlocking"** at every single session start.
Task 4.39's `worker::republish_bundle` drives 101 real signatures (1 SPK + `DEFAULT_OTK_COUNT` = 100
OTKs) through a raw, per-call-scrypt-unwrapping `FileSecretStore`; give that one call an
already-unwrapped signing store so the republish costs O(1) scrypt work instead of O(101), bringing a
file-backed session start into the same range as onboarding's own publish (~2.1 s, measured by 4.41) and
an OS-keystore account (< 3 s total).

## The design decision — already made, at plan time
4.39 deferred this fix, reasoning it required the "extending in-memory key residency" security decision
reserved for 4.40's consult. **An architect consult during the `/plan-phase` call that created this file
resolved it.** Outcome recorded here, binding on the implementation.

**Verdict: settled by 4.40's consult — no new consult, no new ADR** for the narrow shape below, because
that shape *reduces* residency rather than extending it. One boundary is binding (see "The boundary").

### 4.40's `live_store` cache is the WRONG mechanism — do not reach for it
`apps/store/src/file.rs`'s `FileSecretStore::use_key` and `derive_key` both call `self.decrypt_seed()?` —
a full age/scrypt unwrap — on **every single call**. 4.40's own reviewer already caught this and corrected
that task's `CountingStore` doc comment: the cache saves a second `FileSecretStore` *construction* and a
second passphrase round-trip, **not KDF compute**. Caching a `FileSecretStore` — in `live_store` or
anywhere else — still pays 101 scrypts. (It is also why 4.41 measured file-backed add-contact at 3.6 s and
accept at 5.5 s versus 0.2 s on OS-keystore.)

The correct mechanism already exists in this module: `worker::open_store_for_bulk_signing` →
`export_seed` **once** → `MemorySecretStore`, whose `use_key`/`derive_key` are a `HashMap` lookup plus the
op. O(1) scrypt instead of O(prekeys). This is exactly what makes onboarding's own `PublishBundle` take
2.1 s.

### Type erasure at `InboundHandoff` blocks the naive fix — 4.39's claim verified
`SecretStore` (`apps/store/src/lib.rs`) has exactly four methods: `store`, `use_key`, `nonextractable`,
`derive_key`. `export_seed` is **inherent** on `FileSecretStore` and `OsSecretStore`, deliberately —
`file.rs`'s own doc states the reason: *"Not on `SecretStore`, so enclave-backed stores never expose it."*
`InboundHandoff.store: Box<dyn SecretStore>` is therefore a hard wall: neither `republish_bundle` nor
`run_worker` can unwrap once from what they are handed.

**So the fix must land where the concrete type is still in scope — inside `inbound_handoff`**, whose
`Effect::Unlock` arm still holds `boxed.request.keyfile` / `boxed.request.passphrase` and constructs the
`FileSecretStore` itself. This is also the right place on the passphrase-handling rule: `inbound_handoff`'s
own doc comment already justifies reading that passphrase there ("this *is* that same round trip, just
read a second time"). **Do not re-thread the passphrase further down into `republish_bundle`** — that
would newly violate `UnlockRequest`'s "a live passphrase must never cross more than one effect round
trip" invariant.

### The recommended shape
1. Extract the unwrap-once body of `open_store_for_bulk_signing` into a helper taking an **explicit
   keyfile path** (`inbound_handoff` has `request.keyfile`; the existing function hardcodes
   `default_keyfile_path()`), and have `open_store_for_bulk_signing`'s `File` branch delegate to it —
   one implementation, not two.
2. Add a field to `InboundHandoff`, e.g. `bulk_signing_store: Box<dyn SecretStore>`:
   - `Effect::Unlock` arm (file-backed): the one-time-unwrapped `MemorySecretStore`, keyed by
     `descriptor.label` — matching the existing `handle: KeyHandle::from_label(&descriptor.label)`
     exactly (`MemorySecretStore::store` keys by label), so no handle plumbing changes.
   - `Effect::LoadSession` arm (OS-keystore): a second `OsSecretStore::new(&service)` — free, no branch
     at the call site.
   - Leave `InboundHandoff.store` **unchanged** (still the `FileSecretStore`) so `run_inbound_loop`'s
     behavior is byte-for-byte as shipped.
3. `run_worker` passes `handoff.bulk_signing_store.as_ref()` to `republish_bundle`, then **drops it before
   spawning `run_inbound_loop`**. `MemorySecretStore` holds `Zeroizing<Vec<u8>>`, so the seed is zeroized
   on drop — **raw-seed residency ends at republish completion (~2 s), not process exit.**

**Correctness check, already verified at plan time:** `republish_bundle` uses the store for three things —
the connect-time auth signature, the 101 bundle signatures, and `load_chat`/`save_chat`'s at-rest sealing.
All three derive from the same Ed25519 seed: `FileSecretStore::derive_key` is
`derive_key_from_seed(&self.decrypt_seed()?, info)` and `MemorySecretStore::derive_key` is
`derive_key_from_seed(seed, info)` — identical output for the same seed, so the resealed `sessions.bin`
stays readable by every other handler's `FileSecretStore` path. No migration, no compatibility risk.

### Why this needs no new security sign-off
The question 4.39 deferred was *"may we extend in-memory key residency?"* Scoped as above, this task
**does not extend residency at all** — it reduces it:
- The raw seed is **already materialized 101 times** in this exact call path today (`decrypt_seed()` →
  `Zeroizing<Vec<u8>>` per `use_key`), across 188 seconds. Holding it once for ~2 s is strictly less
  aggregate exposure of identical material.
- The passphrase — the *stronger* secret (passphrase + on-disk keyfile ⇒ seed) — is **already** resident
  for the whole process life in two places: `InboundHandoff`'s `FileSecretStore` (4.35) and
  `OnboardingSession::live_store` (4.40).
- The exact pattern is **already shipped in this module** with review sign-off:
  `open_store_for_bulk_signing` → `PendingConnection::store` (4.30), mirroring `apps/cli/src/main.rs`.
- Threat-model residual **A6** (live-endpoint compromise) already covers this class; 4.40's consult read
  both `threat-model.md` and `anonymity-and-retention.md` in full and found no "must never" contradiction.

### The boundary (binding)
The **narrow** shape above proceeds directly. If the implementer instead **widens** it — putting the
`MemorySecretStore` into `live_store` (to make the eleven contacts/trust/chat handlers scrypt-free) or
handing it to `run_inbound_loop` (to make per-delivery signing scrypt-free) — that **does** change what
4.40's consult approved, from "session-lifetime passphrase" to "session-lifetime raw seed", and needs a
short delta sign-off from **security-reviewer** before landing. Both are genuinely attractive follow-ups
(they would fix the 3.6 s add-contact / 5.5 s accept latencies), but they belong in **their own task**,
not folded into this one. Record the deferral explicitly rather than leaving it invisible.

## Scope
- **In:** the recommended shape above, confined to `apps/tui/src/worker.rs` (`republish_bundle`,
  `inbound_handoff`, `InboundHandoff`, `open_store_for_bulk_signing`) plus `apps/tui/src/lib.rs`'s
  `run_worker` wiring, with the test coverage and measurement in Deliverables 3–5. The `StoreKind::Os`
  branch of every function touched stays byte-for-byte unchanged.
- **In (a second, same-code-path question to decide and document, `TODO: confirm`):** `run_worker`
  currently `await`s `republish_bundle` **before** forwarding the completed outcome to `App` (the
  `replies.send(AppEvent::Worker(..))` call sits after the `inbound_started`-guarded branch), so the whole
  republish latency is on the critical path to `Screen::Main` — which is *why* 4.41 observed a frozen
  "Unlocking" screen rather than a slow background republish. After the store fix it becomes ~2–3 s,
  tolerable. Moving `replies.send(...)` ahead of the republish is mechanically easy
  (`inbound_handoff(&outcome)` already borrows before the move) and would reach `Screen::Main`
  immediately, at the cost of a ~2–3 s window where the worker still can't service a new effect. Decide,
  and document the reasoning as an explicit choice rather than a silent one. Note that `chat_state_lock()`
  already serializes every `sessions.bin` writer, so concurrency is not the hazard here. If the ordering
  changes, say explicitly what it does to the `inbound_started` one-shot guard that 4.39's
  `republish_only_fires_once_per_session_via_the_inbound_started_guard` test pins.
- **Out:** the OS-keystore path (already fast; must stay byte-for-byte unchanged); onboarding's own
  `handle_register`/`handle_publish_bundle` path (already correct, already using
  `open_store_for_bulk_signing`); **the wide shape** described under "The boundary" (its own task, gated
  on a security-reviewer delta sign-off); any change to `DEFAULT_OTK_COUNT`, bundle lifecycle,
  OTK-exhaustion or republish-frequency policy (protocol policy, not a perf fix); unifying the two live
  `FileSecretStore` copies a session now holds (4.40's own explicit `TODO: confirm`, still out of scope);
  4.42's Defect C; 4.44's chat-history gap; any new `Effect`/wire type.

## Deliverables
1. The helper extraction + `InboundHandoff.bulk_signing_store` + `run_worker` wiring, per the recommended
   shape. `InboundHandoff.store` unchanged; OS-keystore branch unchanged.
2. The recorded answer to the inline-vs-off-critical-path question above, in the Status section.
3. **A real, recorded measurement** in the Status section: wall-clock time from the completed
   `Effect::Unlock` to `run_inbound_loop`'s spawn (and to a rendered `Screen::Main`) for a **file-backed**
   account, **before and after**, measured on the same machine in the same session. The "before" number
   must be re-measured, not copied from 4.41 — a claimed speedup with no locally-measured baseline is not
   evidence. Record the machine/conditions so 4.45 can compare like with like.
4. Test coverage extending `apps/tui/tests/republish_bundle.rs`:
   - a **file-backed** republish that actually completes and whose republished secrets are resolvable by
     `ChatState::open_inbound` — the test 4.39 could not write (its
     `inbound_handoff_also_produces_a_working_handoff_for_a_file_backed_account` deliberately never calls
     the real `republish_bundle` against a file-backed store, because it took > 90 s and climbing);
   - a **derivation-count** assertion in the spirit of 4.40's `CountingStore`, proving the expensive
     unwrap happens once, not 101 times. State the claim accurately: per 4.40's own review-outcome
     correction, `FileSecretStore::decrypt_seed` runs on *every* `use_key`/`derive_key` call regardless of
     caching, so the property to assert is "one `export_seed` / one expensive-store construction for the
     whole republish", not a vague "the cache prevents scrypt".
   - an assertion that the `MemorySecretStore` is **dropped before `run_inbound_loop` is spawned** (the
     residency bound this task's security rationale depends on).
5. The existing failure-path guarantee stays proven: 4.39's
   `republish_bundle_fails_cleanly_without_panicking_on_an_unreachable_server` must still pass, and if the
   wiring/ordering changes, add coverage that a failed or slow republish still never prevents
   `run_inbound_loop` from starting.
6. Docs: `worker::republish_bundle`'s own doc comment and 4.39's "Update (task 4.39)" note in
   `docs/architecture/tui-client.md` §11 updated to state this performance defect is closed and how (§10
   and §11's original text stay frozen as historical record, per the existing convention);
   `docs/tasks/phase-4/README.md`'s T17 exit-criteria bullet updated to record it. **The exit-criteria
   checkbox stays unflipped** — that's [4.45](./4.45-t17-acceptance-demo-closure-attempt-4.md)'s job.

## Risks / notes
- **Never log, `Debug`-print, or persist the unwrapped store or the exported seed.** Follow the existing
  redaction precedents (`OnboardingSession`'s hand-rolled `Debug`, `crate::session::LiveSession`'s
  redaction test, `run_worker_account.rs::effect_debug_never_leaks_a_passphrase`). The new
  `InboundHandoff` field needs its own redaction coverage if that type is `Debug`-reachable.
- **Do not weaken `open_account_store`'s fail-closed `None` branch** or any of the three
  `*_fails_closed_with_an_actionable_message` tests.
- **`chat_state_lock()` discipline in `republish_bundle` must survive any re-ordering** — `sessions.bin`
  is one serialized document and `run_inbound_loop` touches it on its own tokio task.
- Only a latency change is user-visible; **there is no new TUI surface** for Definition of Done gate 9 to
  register (stated explicitly, per the gate's own "no user surface? say so" rule). The improvement shows
  up on the existing Unlock screen.
- Land **before** 4.42 if convenient: it has no open design question, and it cuts every subsequent live
  file-backed verification cycle from ~190 s/peer to ~3 s/peer — which 4.42, 4.44 and 4.45 all pay
  repeatedly. No logical dependency either way.
