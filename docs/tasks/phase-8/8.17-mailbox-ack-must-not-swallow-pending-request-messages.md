# 8.17 — Mailbox-drained messages arriving before a first-contact request is accepted must not be silently lost (fix-task, found during 8.14's live demo)

**Phase:** 8 — Offline Ciphertext Mailbox · **Feature:** T07 · **Depends on:** 8.7, 8.8 · **Status:** done

## Goal
Fix a real, confirmed, severe defect found while driving task 8.14's live same-server demo — the
feature spec's own headline scenario (an offline recipient's client is stopped, three envelopes
queue at their home server, all three arrive correctly ordered on reconnect): when a **new**
contact's first three offline messages drain on reconnect, only the first one (which triggers the
`ChatError::MessageRequest` first-contact gate) is ever actually shown. The second and third — which
arrived in the same drain, before the user answered the first message's accept/reject prompt — hit
`ChatError::RequestPending` ("already gated: refused, never merged into the pending request", task
2.10's own deliverable) and were, before this fix, unconditionally acked and deleted from the
server's mailbox in the same loop iteration that dropped them. The message was durably queued,
successfully drained, and then **silently, permanently discarded** — acked as if delivered, never
actually shown to the user, no error, no trace. This directly contradicts the mailbox's core
promise ("durably queued... will arrive on reconnect") and the feature spec's own acceptance
criteria ("all three messages arrive, correctly ordered, ratchet intact"; "redelivered duplicates
are dropped" — this is not a duplicate, it is a genuine message never delivered even once).

## Scope
- **In:**
  1. `apps/cli/src/chat.rs::handle_inbound`'s `Err(ChatError::RequestPending)` arm: when the
     delivery that hit this arm was mailbox-drained (`deliver.mailbox_id.is_some()`), call
     `client.discard_pending_mailbox_ack(id)` (task 8.8's own mechanism, previously only used for a
     `save_state`/`save_trust` I/O failure) so the loop's per-iteration
     `client.ack_pending_mailbox()` does not delete this row — it survives for redelivery once the
     user resolves the pending request and reconnects.
  2. `apps/tui/src/worker.rs::process_inbound_delivery`'s inbound-processing closure: same fix,
     threaded through the existing `persisted`-gated ack-withholding mechanism (task 8.8) rather
     than a duplicate code path — a new `defer_mailbox_ack` flag set in a dedicated
     `Err(ChatError::RequestPending)` match arm (split out of the generic catch-all it previously
     fell into), folded into `persisted`'s final computation.
  3. Regression tests, both crates: three offline messages queued to a **new** contact; on
     reconnect, the first is shown and accepted; the mailbox must still hold rows 2 and 3
     (unacked); a second reconnect must deliver both, correctly ordered; the mailbox must then be
     empty.
- **Out:** no change to `ChatError::RequestPending`'s own semantics (still never merged into the
  pending request — task 2.10's deliverable stands) or to the genuinely-bad-envelope rejections
  (Desync, Crypto, SenderMismatch, …), which remain acked exactly as task 8.8 left them: a bad
  envelope is never going to become good on redelivery, so acking it is correct, unlike a merely
  *undecided* one.

## Risks / notes
This is precisely the class of defect this project's own precedent treats as in-scope on discovery
(task 6.3's fix, found the same way) — a genuine, severe, silent data-loss bug in the mailbox's own
headline acceptance scenario, not scope creep for a phase-exit task. The fix must not weaken
`ChatError::RequestPending`'s existing "never merged" behavior (task 2.10) — only its interaction
with the mailbox's ack timing changes.

## Tests
`cargo test -p meridian-cli --bin meridian`, `cargo test -p meridian-tui` — existing suites stay

## Status
**Done.** Both fixes land exactly as scoped: `apps/cli/src/chat.rs::handle_inbound`'s
`Err(ChatError::RequestPending)` arm now calls `client.discard_pending_mailbox_ack(id)` when the
delivery was mailbox-drained; `apps/tui/src/worker.rs::process_inbound_delivery` gained a new,
dedicated `Err(ChatError::RequestPending)` match arm (split out of the generic catch-all it used
to share with genuinely-bad envelopes) setting a `defer_mailbox_ack` flag folded into the existing
`persisted` computation task 8.8 already gates the tail-side ack on. New regression tests in both
crates (`apps/cli/tests/mailbox_request_pending_not_lost.rs`,
`apps/tui/tests/inbound_delivery.rs::three_offline_messages_from_a_new_contact_are_never_silently_lost`)
reproduce the feature spec's own headline scenario end to end and assert the mailbox row count
directly (`Store::mailbox_list_for_recipient`) after the first drain — the exact assertion that
failed before this fix.

### Review round
**reviewer** (security-reviewer + code-reviewer + architect lenses) — PASS on all three, zero
blocking findings, two non-blocking notes, both recorded here rather than silently dropped:
1. **Correctness/completeness**: `drain_mailbox` (`apps/rendezvous/src/ws.rs`) fires only once, at
   connect time — `accept_request` never triggers an on-demand re-drain, so for a **new** contact's
   queued burst, the second and third messages genuinely cannot arrive within the same connection
   the user accepts on; a second reconnect is architecturally required. This isn't a defect this
   task introduces or needs to fix (nothing in the current wire protocol lets a client request an
   on-demand re-drain), but it does mean the feature spec's literal demo-script text ("all three
   messages arrive" on one `meridian chat` reconnect) is only true for an *already-accepted*
   contact, not a brand-new one — task 8.14's own live demo transcript records this precisely
   (two reconnects for a new contact) rather than overclaiming the spec's literal wording, mirroring
   how 8.6/8.13 already corrected the analogous cross-org "queued at org-b" overclaim. A follow-up
   backlog item (re-drain immediately after `AcceptRequest`, within the same connection) is a
   reasonable future enhancement, out of this fix's own narrow scope.
2. **Security**: deferring the ack for `RequestPending` doesn't weaken `MAX_PENDING_REQUESTS` (keys
   on distinct gated identities, untouched by a same-identity `RequestPending` rejection) or the
   mailbox's own quota/TTL enforcement (unchanged code paths), but it does change the *residency
   time* for one attack shape: an already-gated attacker identity can now flood additional
   envelopes that occupy the victim's shared per-recipient mailbox quota for up to the TTL window,
   instead of being deleted almost immediately as before this fix (which is precisely the bug being
   fixed — immediate deletion was the data loss). This is an inherent, correctly-bounded trade-off
   (bounded by the same `quota_mb`/`ttl_days` any other queued mail already is, never unbounded),
   recorded here per the reviewer's own request rather than left implicit.
