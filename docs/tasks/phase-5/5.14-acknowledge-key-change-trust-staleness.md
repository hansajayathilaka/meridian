# 5.14 — `run_acknowledge_key_change` has the same `contacts.json` trust-staleness bug as F3

**Phase:** 5 — Review of Phase 4 · **Feature:** review fix (follow-up to F3, found by 5.3's own review) ·
**Depends on:** 5.3 · **Status:** pending

## Goal
Close the second instance of the trust-staleness bug 5.3 fixed for `run_mark_verified`.
`run_acknowledge_key_change` (`apps/tui/src/worker.rs`) mutates `TrustState` to `Pinned` (normal ack) or
`Blocked` (escalation) via `TrustStore::acknowledge_key_change` and calls `save_trust`, but never touches
`contacts.json`. A contact that was `PinnedKeyChanged` (mirrored into `contacts.json` as `Pinned`, per
`to_trust_label`'s approximation) that gets escalated to `Blocked` still shows `"trust": "pinned"` in
`--export-json` — the exact bug class 5.3 exists to close, reproduced in a code path 5.3's Scope didn't
name.

## Scope
- **In:** `apps/tui/src/worker.rs::run_acknowledge_key_change` — apply 5.3's own write-through pattern
  (reload `contacts.json`, patch the matching row's `trust` field via the existing `to_trust_label`
  helper, save), inside whatever async/blocking shape the function already has. Consider, as part of
  this task, whether an export-time join in `apps/tui/src/store/export.rs::export_json` (5.3's own
  rejected alternative) would close this and any *future* instance of the same bug class at once,
  instead of requiring a write-through patch at every trust-mutating call site — 5.3's review round
  flagged this as worth revisiting now that a second instance has been found, but did not decide it.
- **Out:** Any change to `trust.bin`'s own on-disk format, or to the live in-memory join
  `build_contact_entries` already performs correctly. Any change to `run_mark_verified`/`run_set_petname`
  (5.3/5.4's own scope, already closed).

## Deliverables
1. The chosen fix (write-through mirroring 5.3, or an export-time join superseding both) landed.
2. A bug-pinning test mirroring 5.3's own discipline: first proves today's wrong output (a `Blocked`
   escalation still reads `"trust": "pinned"` after export), then flips to asserting the correct value
   once the fix lands, in the same PR.
3. If an export-time join is chosen instead of write-through, this task's own file should record why —
   including whether it also lets 5.3's write-through be simplified or left as harmless redundant
   belt-and-suspenders (implementer's call, documented either way).

## Risks / notes
Mirrors 5.3's own inherited, not-newly-introduced crash-window risk (a crash between the two writes
leaves the documents briefly disagreeing) if write-through is chosen again — same accepted precedent, not
a new concern.
