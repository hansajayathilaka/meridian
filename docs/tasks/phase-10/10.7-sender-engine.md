# 10.7 — Sender engine: chunking, backpressure, progress, multi-file batches

**Phase:** 10 — File Transfer Stream · **Feature:** T09 · **Depends on:** 10.6 · **Status:** pending

## Goal
Drive the actual outbound transfer: split a file into 64 KiB chunks, seal each (task 10.5), send over
the stream (via task 10.4's `send_stream_frame`), throttled by the buffered-amount watermark (task
10.2), emitting progress events, and sequencing multiple files in a batch.

## Scope
- **In:** `apps/streams/src/sender.rs` (or similar): the chunking/send loop, a low-watermark
  backpressure policy (poll `buffered_amount`, pause sends above a high watermark, resume below a low
  one — pick concrete byte thresholds and record them in the Outcome), a progress event type (`bytes
  sent / total`, throughput) the CLI/TUI can subscribe to, and multi-file batch sequencing (send
  manifests/chunks for file 2 only after file 1 completes, or interleaved — implementer's call, record
  the choice).
- **Out:** the receiver side (10.8), resume (10.9), the actual CLI/TUI progress bar rendering
  (10.10/10.11 consume the progress events this task defines).

## Deliverables
1. Sender engine in `apps/streams/src/sender.rs`.
2. Progress event type + a way to subscribe to it (channel/callback — match this crate's existing async
   idioms).
3. Tests over the loopback transport: a small multi-chunk file sends completely and in order-of-offset
   (even though the channel is unordered, the receiver must reassemble by the `i` field, not channel
   order — this task's test should deliberately interleave/reorder frames at the loopback layer to prove
   the engine doesn't assume in-order delivery).

## Risks / notes
The channel is `reliable + unordered` (task 10.6's `channel_cfg`) — chunks may arrive out of order. The
sender engine itself doesn't need to handle reordering (it just sends), but its test must simulate it to
catch an implementer accidentally assuming order. Watermark thresholds are a `TODO: confirm` design
choice — no doc pins concrete numbers; pick reasonable defaults (e.g. high watermark = a few MB, low
watermark = a fraction of that) and record the rationale, since the soak test (10.14) will validate
whether they're too conservative or too aggressive against real throughput.
