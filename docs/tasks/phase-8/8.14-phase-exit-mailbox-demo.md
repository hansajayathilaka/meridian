Ran the feature spec's own demo script live, against real binaries and a real, file-backed SQLite
mailbox store: three offline messages queue for a brand-new contact, `meridian-admin mailbox dump`
shows only opaque ciphertext (count/sizes/timestamps — the A7 honesty demo), reconnect drains and

with accurate client-visible copy (task 8.15's own fix). Ran the cross-federation case against a
real two-org mTLS stack, with the sender-visible framing correction the phase's own architect
consult (point 2) and tasks 8.6/8.13 already established: Org A's sender sees the optimistic
`RouteOk{delivered:true}`; Org B's own mailbox (inspected the way `meridian-admin`'s dump actually
would) is the real, honest proof of queuing. Full transcript:
[8.14-demo-transcript.md](./8.14-demo-transcript.md).

**Two real defects found while preparing the live demo, not silently worked around:**
- **[8.16](./8.16-cli-register-persists-prekey-secrets.md)**: `meridian register` published a
  bundle's public keys but discarded the matching private prekey secrets entirely — any message
  sent against a `register`-only-published bundle was permanently undecryptable, even by a later
  `meridian chat` run for the same account. Fixed by routing `cmd_register` through the same
  correct connect+publish+persist sequence `chat.rs::run` already used.
- **[8.17](./8.17-mailbox-ack-must-not-swallow-pending-request-messages.md)**: the second and third
  of a burst of offline messages to a brand-new contact were silently, permanently lost — drained
  successfully, then acked and deleted despite never reaching the user, because they arrived before
  the first message's contact request was accepted. Fixed by extending task 8.8's own
  ack-withholding mechanism to this case in both clients.

Both were fixed, reviewed (PASS, zero blocking findings across both), and landed as their own
commits before this task's own demo was re-run and captured clean. This directly mirrors phases
4/5/6/7's own precedent: a live phase-exit demo finding real gaps is expected, not exceptional, and
the fix belongs in a properly tracked, reviewed task — not silently patched inline or glossed over
in the transcript.

**One structural finding, not a defect, recorded rather than silently worked around:** the demo
transcript documents precisely (see its own inline note) that a brand-new contact's queued burst
needs **two** reconnects to fully arrive — the first delivers only the opening message (gated as a
first-contact request); the second delivers the rest, once accepted — since `drain_mailbox`
(`apps/rendezvous/src/ws.rs`) only fires at connect time and `accept_request` doesn't trigger an
on-demand re-drain. Task 8.17's own review round flagged this precisely; it's an accurate reading
of the feature spec's demo script for the *already-accepted-contact* case (which does redeliver
everything on one reconnect), not a claim that overclaims for the first-contact case. No ADR or
wire change implicated — recorded here and in 8.17's own Status section as a known, correctly
bounded property, with an on-demand-re-drain-after-accept enhancement noted as a reasonable future
backlog item, out of this phase's own scope.
