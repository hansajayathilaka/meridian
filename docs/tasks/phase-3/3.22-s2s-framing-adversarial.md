## Outcome
Added four adversarial cells to `apps/rendezvous/tests/federation_link_dos.rs`, each reusing task
3.4's shared harness, no production code touched: malformed CBOR body, unknown `FedOp` mid-stream,
truncated/oversized length-prefix framing (two sub-cases), and a slow-loris trickle after link
establishment. Three of the four arms were mutation-checked (neutered, confirmed the cell fails,
restored) — the CBOR-decode-error arm, the unknown-op catch-all, and `MAX_FRAME_LEN`'s guard; the
truncated/EOF sub-case has no dedicated arm to neuter (falls through `read_exact`'s built-in
short-read propagation) and is documented as such rather than silently skipped.

**Found a real, unfixed defect, reported per this task's explicit scope (do not fix inside a
coverage task):** `serve_link`'s main loop (`apps/rendezvous/src/federation/inbound.rs`,
`link.recv_frame().await`) has no idle-read deadline at all — unlike the handshake path
(`handshake_timeout_ms`) or the outbound dial/request path (`request_timeout_ms`). An
already-established peer that stalls or trickles a frame indefinitely holds one `max_links` permit
forever. Filed as [3.23](./3.23-serve-link-idle-read-deadline.md) to carry it forward, not lose it.

Reviews: security-reviewer — **pass**; independently re-verified the defect is real (confirmed no
`with_deadline` wraps the serve loop) and refined its severity: in default WebPKI mode, the accept
side never pins an expected domain or calls `FederationPolicy::admit_any` before a frame is fully
decoded, so any TLS client cert chaining to a public CA — not necessarily an admitted federation
partner, not gated by `federation.policy` at all — can occupy the slot; this correction is carried
into 3.23's framing rather than the original "admitted-peer-only" characterization. Also
independently re-ran the mutation-check on the CBOR-decode arm and confirmed identical results.
test-engineer — **pass**; verified all four cells' assertions are load-bearing on their claimed
arm (not incidental), timings are consistent with (and more generous than) this file's own
pre-existing conventions, no new resource-leak pattern, ran the suite ~15x (one anomalous
first-run flake on cold start, not reproduced across 9+ subsequent runs including under injected
CPU load — noted as worth watching, not a design defect), and confirmed this closes exactly the
review-report's named coverage gap.
