## Status

consistency pass, all completed against a real, owner-operated rendezvous server,
`wss://rendezvous.hansajayathilaka.com` — a deliberate, explicitly authorized deviation from every

### Environment notes common to both runs
- Both peers' identities created with `--hint rendezvous.hansajayathilaka.com` (must match the server's
  own configured domain — a mismatched hint makes `fetch-bundle` treat the lookup as cross-org
  federation, which this server has disabled, failing with "federation is not enabled on this server").
  Confirmed directly via a standalone core-level CLI smoke test before either TUI run: `meridian
  register --server wss://rendezvous.hansajayathilaka.com`, `fetch-bundle`, and a live two-peer `chat
  --json` exchange all succeeded once both identities shared that hint.
- OS-keystore (Secret Service) was **not** preinstalled in this sandbox; both runs independently
  installed `gnome-keyring` + `dbus-x11` + `libsecret-tools`, started a real session bus +
  `gnome-keyring-daemon --components=secrets --unlock` under a short scratch `$HOME`/`XDG_RUNTIME_DIR`
  (the known AF_UNIX-socket path-length hazard applies to this control socket too), and verified it
  genuinely functional with a real `secret-tool store`/`lookup` round trip before trusting `meridian id
  new --store os`.
- Both runs built their own from-scratch PTY driver (Python `pty` + `pyte` screen-scraping; nothing
  checked into the repo) and handled the initiator-role trap by decoding `mrd1:` ids via `meridian id
  parse` and regenerating an identity when pubkey-byte ordering put it on the wrong side of
  `worker::run_send_message`'s `account_pub.as_slice() <= peer_pubkey.as_slice()` rule.
- Both runs disclosed and fixed their own driver bugs before trusting any result (screen-scraping races
  against optimistic UI updates, premature transcript-empty assertions before `Effect::LoadHistory`
  resolves, and timeouts too short for the real network's higher latency vs. a local demo server) —
  distinguished explicitly from product defects in both reports.

### Scope point 5 — safety-number match, mark-verified both sides, timed `run_mark_verified`
**PASS on safety-number match** (byte-identical 60-digit numbers both sides, both runs) — **and one
confirmed-open finding, independently reproduced by both runs**: `verify::apply_action` mutates
`TrustStore` and flips the UI to "verified" synchronously, in-memory, *before* `Effect::MarkVerified`
dispatches — both runs measured this optimistic label flip at ~0.004–0.005s regardless of store type,
which is **not** the real completion signal. Measuring actual backend latency instead (input-loop
responsiveness — sending `Esc` immediately after `y` and timing until the single-threaded runtime
processes it back to Contacts, since the effect executor and input loop share one thread): **Run 1: bob
(file-backed) 4.07s. Run 2: bob (file-backed) 3.714s.** Both closely match 4.43's/4.50's own previously
recorded ~3.4s figure. **This finding was never fixed by 4.51** — 4.51's own Deliverable 7 explicitly
evaluated it and split it off as a named follow-up (13 call sites through `OnboardingSession::live_store`,
a disproportionately wider diff than 4.51's own scope) rather than folding it in. The `reviewer` pass
independently re-read `apps/tui/src/worker.rs::run_mark_verified` and confirmed it is a plain synchronous
`fn`, unwrapped, still routed through the cached raw `FileSecretStore` via `OnboardingSession::live_store`
— exactly the already-known, already-named hazard, not a new regression 4.51 introduced (4.51's diff
never touches `live_store`/`set_live_store`).
