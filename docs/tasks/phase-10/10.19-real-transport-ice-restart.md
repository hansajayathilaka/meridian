# 10.19 — Real `Transport::ice_restart` (webrtc-rs primitive)

**Phase:** 10 — File Transfer Stream · **Feature:** T09 (fix; benefits any future stream type/call
riding `P2pSession`) · **Depends on:** 10.18 · **Status:** done

## Goal
Make `WebRtcTransport::ice_restart` actually invoke webrtc-rs's real ICE-agent restart
(`create_offer` with `ice_restart: true`), producing a fresh local offer the session layer can seal
and send to the peer — the transport-layer half of [ADR 0025](../../adr/0025-ice-restart-renegotiation.md).
Today it only resets local candidate-gathering bookkeeping and never touches the real ICE agent.

## Scope
- **In:** `apps/transport/src/webrtc_backend.rs`'s `WebRtcTransport::ice_restart` — call the real
  `RTCPeerConnection::create_offer` with `ice_restart: true`, `set_local_description` with the result,
  and ensure `Transport::local_description`/`local_fingerprint`/candidate-gathering (`local_candidates`/
  `gather_done`) all reflect the restarted state afterward, exactly as they do after the original
  `dial_established` offer (mirror that pattern, don't invent a new one). Retire/rewrite the module
  doc's "ICE restart does not (yet) fulfill the resumability promise (known gap)" section once this
  lands — it should describe the real mechanism, not the old gap.
- **Out:** any session-layer signaling to actually deliver the new offer to the peer (that is
  [10.21](./10.21-tolerant-restart-delivery.md)/[10.22](./10.22-session-ice-restart-signaling.md)'s
  job) — this task's own `ice_restart()` still returns after only the *local* half of a restart, same
  return shape as today (`Result<()>`), just doing something real instead of a no-op. Also out: any
  change to `LoopbackTransport::ice_restart`, which ADR 0025 explicitly keeps a documented no-op (the
  loopback fabric has no real network to restart). Also out: any automatic trigger/detection of when
  to call this (ADR 0025 names that a separate, later follow-up).

## Deliverables
1. `WebRtcTransport::ice_restart` invokes the real primitive.
2. A real-backend regression test (mirroring the existing gated tests in
   `apps/transport/tests/webrtc_backend.rs`) proving: (a) after `ice_restart()`, `local_description()`
   returns SDP with a genuinely different ICE ufrag/pwd than before (confirms it's a real restart, not
   a no-op relabeled), (b) the already-open data channels and their `buffered_amount()`/`send()`
   behavior are untouched by the local half alone (no peer coordination yet, so nothing should break
   locally just from calling this), (c) `local_fingerprint()` is byte-identical before and after (the
   DTLS cert must not change across a restart — this is the invariant [10.22](./10.22-session-ice-restart-signaling.md)'s
   layered fingerprint check depends on being true at the transport level).
3. Module-doc rewrite in `apps/transport/src/webrtc_backend.rs` retiring the "known gap" framing.

## Risks / notes
This task alone does **not** make ICE restart work end-to-end — calling only this without 10.21/10.22
landed will (as before) still knock the live connection out from under itself with no peer
coordination, since nothing sends the new offer anywhere yet. Confirm this honestly in the new test's
own doc comment (e.g. "this test does not call the real primitive against an already-connected pair
expecting the channel to survive — that needs the full signaling round trip, landing in 10.22") so a
future reader doesn't mistake this task's own test for proof the gap is closed.

## Outcome
`WebRtcTransport::ice_restart` now calls the real webrtc-rs primitive:
`create_offer(RTCOfferOptions { ice_restart: true, .. })` → `set_local_description`, with
`local_candidates`/`gather_done_flag` reset *before* the call so a subsequent `local_candidates()`
correctly waits on the fresh gathering pass. Confirmed against `webrtc-ice` 0.17.1's own
`Agent::restart` source that this genuinely rotates ICE ufrag/pwd and deletes the selected candidate
pair — a real restart, not cosmetic — and empirically confirmed via a throwaway instrumented run:
ufrag/pwd differ before/after, the DTLS fingerprint stays byte-identical.

**Found while building this**: the pre-existing gated test `ice_restart_keeps_the_live_channel_flowing`
asserted the *old*, no-op-era invariant that calling `ice_restart` never disrupts an active connection.
Once the primitive became real, calling it on both sides of an already-connected pair with zero peer
coordination hangs indefinitely — exactly what ADR 0025 predicts (a real restart with no peer
signaling breaks the live association until 10.22 lands the round trip). Replaced that test with
`ice_restart_produces_a_genuinely_new_local_offer_without_disturbing_channels_or_fingerprint`, which
proves only this task's own scope (ufrag/pwd change, channels/`buffered_amount()` undisturbed by the
local-only call, fingerprint identical) with an explicit doc comment that it does not prove end-to-end
resumability. The module doc's "known gap" section is rewritten to describe the new state precisely:
local primitive real, peer signaling still pending.

`LoopbackTransport::ice_restart` is untouched (stays a no-op, per ADR 0025). No `meridian-proto`
changes; diff confined to `apps/transport`.

The combined **reviewer** pass (architect + code-reviewer, run together with task 10.20) returned
**PASS, zero blocking findings** — independently verified the restart primitive against `webrtc-ice`/
`webrtc` 0.17.1's own source (confirming both the restart's real effect and the reset-before-restart
ordering has no race), independently reproduced the old test's hang against the new code to confirm
it's the expected/predicted failure mode rather than something else, and confirmed the new test's
three assertions are genuinely proven rather than merely commented.
