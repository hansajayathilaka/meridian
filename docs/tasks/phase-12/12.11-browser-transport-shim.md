# 12.11 — Browser `Transport` shim

**Phase:** 12 — Browser & Desktop Clients · **Feature:** T11 · **Depends on:** 12.10 · **Status:** done

**User surface:** none directly — the primitive the browser client's real P2P sessions run over,
consumed by the browser adapter (12.13). No TUI surface applies.

## Goal
Implement `apps/wasm/src/transport.rs`'s `BrowserTransport`, the browser realization of the frozen
`meridian_transport::Transport` trait (`core-api-contracts.md`), over the browser's native
`RTCPeerConnection`/`RTCDataChannel` via `web-sys`/`js-sys` — the reason `Transport` is a trait at all
(`system-design.md` §6: "browser policy forbids any other stack").

## Scope
- **In:** every `Transport` method against the browser's native WebRTC objects, matching the exact
  signature frozen in `core-api-contracts.md` — including `set_remote_offer_and_answer` and
  `ice_restart` (task 10.22/[ADR 0025](../../adr/0025-ice-restart-renegotiation.md)'s additions, not
  the pre-10.22 shape).
- **Out:** libwebrtc media/`add_transceiver` real behavior beyond satisfying the trait signature — this
  phase ships no call UI, so a correct-but-unexercised media stub is acceptable; the signaling client
  itself (12.4 already closed that); any UI.

## Deliverables
1. `apps/wasm/src/transport.rs` — `BrowserTransport`.
2. A same-process SDP offer/answer loopback test: two `BrowserTransport` instances in one headless-browser
   tab, exercising the negotiation subset (`new_session`/`add_data_channel`/`local_description`/
   `set_remote_description`/`add_ice_candidate`/fingerprint accessors) without needing real network
   connectivity between two machines.

## Risks / notes
Exact trait conformance matters here more than almost anywhere else in this phase — any signature drift
from `core-api-contracts.md` breaks the "semver-stable from Phase 1" policy that section states. Full
real-network P2P proof (two actual browser instances, or browser↔CLI) is explicitly deferred to the
interop-matrix task (12.17) — this task's own test is a same-tab loopback, not a live network test.

## Tests
`wasm-bindgen-test` (or the runner confirmed by 12.10) exercising the same-process offer/answer loopback.

## Reviews
**reviewer** (combined pass: architect lens — exact `Transport` trait conformance, no signature drift;
security-reviewer lens — mandatory, the DTLS-fingerprint binding this shim must correctly expose is the
safety-critical `system-design.md` §7.1 step 13 property).

## Outcome
Implemented `BrowserTransport` in `apps/wasm/src/transport.rs`, every `Transport` method against real
`RTCPeerConnection`/`RTCDataChannel` objects via `web-sys`/`js-sys`, matching the frozen trait byte-for-
byte including the post-ADR-0025 `set_remote_offer_and_answer`/`ice_restart` shapes. `local_fingerprint`/
`dtls_fingerprint` extract the `a=fingerprint:` line from cached, ratchet-encrypted-in-transit SDP text,
mirroring the native backend's already-accepted "fingerprint binding without blocking" rationale. A
real, version-matched headless Chromium test (`wasm-pack test --chrome --headless`) proved the
system-design.md §7.1 step 13 cross-binding property against genuine DTLS certificates from two
independently-created `RTCPeerConnection`s — `a`'s negotiated remote fingerprint equals `b`'s own local
fingerprint and vice versa, and the two peers' local fingerprints are distinct.

Along the way, found and fixed a real bug: real Chrome throws `OperationError` for at least one
negotiated SCTP stream id in the native backend's 65,534-wide `stream_id_for_label` modulus range.
Narrowed the browser-side modulus to 1,000 — correct and safe for this task's own same-tab
browser↔browser loopback scope (both sides agree), but this leaves a confirmed, unreconciled
browser↔native id mismatch for any future browser↔CLI/browser↔desktop session, since fixing the native
side is out of this task's file scope. Recorded as a tracker carry-forward (not left only as a code
comment, per this repo's own established convention) and flagged in task 12.17's Risks/notes, the task
most likely to hit it live.

The combined review (architect + security-reviewer) returned **PASS** on both lenses, zero blocking
findings, after independently reproducing the real browser test (3/3 pass against real Chrome 147.0.7727.24,
not taken on the implementer's word) and diffing every `BrowserTransport` method signature against the
trait definition directly. The stream-id modulus finding was assessed as correctly out-of-scope for this
task's own file boundary but under-tracked as only a code comment — resolved by adding the tracker
carry-forward and 12.17 note above, per the reviewer's explicit recommendation.

Test mechanism: `wasm-bindgen-test` against a real, version-matched headless Chrome-for-Testing (the same
approach task 12.5 established for WebCrypto) — the only option, since Node has no `RTCPeerConnection`.
Full real-network P2P proof (two actual machines, or browser↔CLI) remains explicitly deferred to task
12.17 per this task's own scope; this task's test is a same-tab loopback only.
