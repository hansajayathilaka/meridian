# 10.15 — Kill/resume test automation

**Phase:** 10 — File Transfer Stream · **Feature:** T09 · **Depends on:** 10.9, 10.10, 10.13 ·
**Status:** done

## Goal
Automate the feature spec's demo script: yank the network mid-transfer (the testrig cuts the veth), let
the session ICE-restart and reconnect, confirm the resume protocol (task 10.9) kicks in and the transfer
completes to a verified BLAKE3 match.

## Scope
- **In:** a netns-rig-driven test that starts a transfer, cuts the veth partway through, restores it,
  and asserts: the session reconnects, resume reports the correct missing-range count, the transfer
  completes, and the final file matches byte-for-byte (BLAKE3 root match, `sha256sum` parity per the
  demo script).
- **Out:** a full CLI-process kill/restart (see `TODO: confirm` below) unless this task's own
  investigation confirms it's in scope.

## Deliverables
1. Kill/resume automation on the netns rig.
2. Assertion of the ≤2% re-send bound (task 10.9's own test covers this at the engine level; this task
   covers it at the full end-to-end/process level).

## Risks / notes
`TODO: confirm` — the feature spec's own demo script only shows a network cut + ICE restart (the process
stays alive), not a full CLI-process kill and restart from cold. A full-process-kill resume would require
on-disk-persisted partial-transfer state, which no other task in this phase scopes. This task's
implementer should confirm which is meant (the demo script is the authoritative acceptance artifact) and
not silently assume the harder (process-kill) interpretation without a task to build the persistence it
would require. If the spec is read as requiring process-kill resume, stop and flag for a follow-up task
rather than expanding this one silently.

## Outcome

### Scope resolution (the file's own `TODO: confirm`)
Read `docs/architecture/features/09-file-transfer.md`'s demo script in full: it shows `meridian send`
printing progress, a comment ("yank the network mid-transfer... then restore"), then **more output
from the same invocation** ("[session] ICE restart… reconnected", "[file] peer reports N missing
ranges — resuming", "done ✔"). This is the same live process narrating a network cut + ICE restart,
not a cold process restart. Confirmed against `apps/streams/src/resume.rs`/`apps/streams/src/receiver.rs`:
the resume protocol (task 10.9) is entirely in-memory, keyed by a live `StreamId`/`P2pSession` — no
on-disk partial-transfer state exists anywhere in this phase. **Resolution: network-cut interpretation
only**, as the task file's own risk note anticipated; no follow-up flag needed for this question.

### Driver choice: (b) — a dedicated test harness driving the real primitives directly, not CLI wiring
`apps/cli/src/send.rs` has no automatic drop-detection/reconnect/resume wiring, and adding it would
need a genuine "the network changed" signal — no `SessionEvent`/`StreamType` hook for that exists
without a `meridian-core` change (`apps/streams/src/resume.rs`'s own module doc already tracks this
gap separately). Investigating further: `send.rs`'s real receiver deliberately does **not** use
`FileReceiver`'s per-chunk-proof API (no wire mechanism delivers merkle proofs per chunk today —
a separate, upstream `TODO: confirm`), so even a from-scratch CLI integration would need either (i) a
heuristic timeout-based drop detector (an unreviewed, fragile addition to production code for this
task to invent) or (ii) solving that unrelated proof-delivery gap. Both are materially larger than
this task's own scope. Chose **(b)**: `apps/cli/examples/kill_resume_netns_drive.rs`, a standalone
driver binary calling the real `meridian-core`/`meridian-streams` primitives
(`P2pSession::ice_restart`, `send_missing_chunks`, the `FRAME_TAG_RESUME` wire shape,
`FileStream::watch_resume`) directly, with the *timing* of "when to call `ice_restart`" driven by the
harness script via marker files (the script is the one cutting the veth, so it already knows when).

### Deliverables
1. **Real-netns harness**: `tools/netns-kill-resume.sh` (`run` = full `mrd.file/1` scenario,
   `probe` = a smaller chat-only companion — see below) + two driver examples
   (`apps/cli/examples/kill_resume_netns_drive.rs`, `apps/cli/examples/netns_ice_restart_probe.rs`),
   using a trivial file-based `SignalRelay` (network namespaces share the host mount namespace) so two
   real `meridian-core`/`WebRtcTransport` processes can complete a genuine offer/answer/ICE exchange
   across a real veth pair without needing a real rendezvous/coturn instance for this task's purposes.
2. **In-process validation** (no network): `apps/streams/tests/kill_resume_simulated.rs` — always
   runs, mirrors the real driver's own exact bookkeeping (raw `pending_chunks` distinct-index tracking
   + whole-file BLAKE3 finalize, not `FileReceiver`) and asserts the ≤2% re-send bound plus a literal
   `sha256` comparison (the demo script's own wording) alongside the BLAKE3 root check. Passes.
3. **The ≤2% re-send bound** is asserted both in the simulated test and computed identically by the
   real driver's own JSON summary line, parsed and asserted by the shell harness (`awk`, since bash has
   no float comparison).

### Two pre-existing, independent defects found and confirmed LIVE while building this (out of this
task's own scope to fix — flagged, not silently worked around)
1. **`WebRtcTransport::ice_restart` is a real no-op that does not survive a genuine network cut.**
   `apps/transport/src/webrtc_backend.rs`'s own module doc already said as much; this task
   **independently reproduced it live** on this sandbox's real netns/veth rig (root available) via
   `tools/netns-kill-resume.sh probe`: cut a real veth for 15s (past the backend's own 9s
   `ICE_FAILED_TIMEOUT`), restore it, call `ice_restart()` on both sides — the sender's own
   `send_chat()` call returns `Ok(())` with **no error and no hang**, but the message never reaches
   the peer even after a further 25s wait. Precision correction to the module doc's own framing: it is
   not the local send call that "hangs forever" — it returns successfully; it is *delivery* that
   silently never happens, with **no local signal at all** that it was lost. Needs a real ctrl-channel
   ICE-renegotiation message (the module doc's own suggested fix) — an architect-review-worthy
   `meridian-core`/`meridian-transport` change, out of this task's scope.
2. **`mrd.file/1`'s `CHUNK_SIZE` (65536 bytes) collides with `webrtc-sctp`'s default
   `max_message_size` (also 65536)**: any full-size chunk, once wrapped in its AEAD tag + CBOR framing
   + the outer ratchet envelope, exceeds the real transport's outbound message-size limit — confirmed
   live via `tools/netns-kill-resume.sh run`, which fails immediately on the very first
   `send_chunk_frame` call, before the veth is ever cut. **Independently, concurrently reproduced by
   task 10.14's own soak-test work** (`docs/testing/soak-file-transfer-throughput.md`), which hit the
   identical error on a completely different harness and root-caused it identically (recommended fix:
   `SettingEngine::set_sctp_max_message_size_can_send`, in `apps/transport/src/webrtc_backend.rs`) —
   two independently-built harnesses landing on the same specific error is strong corroborating
   evidence this is real, not an artifact of either harness's own setup. This means `run`'s file-
   transfer scenario cannot currently reach its own post-cut resume phase at all; `probe` (chat-only,
   well under the size limit) is what actually exercises/confirms finding 1 above.

Both gaps are named explicitly in `tools/netns-kill-resume.sh`'s own header comment so a future
`--features webrtc` run failing this way is understood as "rig doing its job," not a rig bug.

### What was actually observed in this sandbox vs. what needs a real CI runner
- **Observed directly, live, with root**: basic netns/veth create + link up/down/up works in this
  sandbox (a different kernel capability than task 10.13's netem, confirmed separately per this task's
  own instruction); a real cross-process `WebRtcTransport` dial/answer over a real veth pair with
  direct host-candidate pairing (no NAT, no TURN) connects successfully and delivers real chat data
  *before* a cut; both of the defects above, live, not merely inferred from source comments.
- **Not observed / needs a real CI runner or a fix landing first**: a genuine PASS of `run` (blocked on
  defect 2, then would hit defect 1) or `probe` (blocked on defect 1) — neither can pass until the
  corresponding upstream gap closes. `apps/streams/tests/kill_resume_simulated.rs` is the one piece of
  this task's own logic that **is** fully, repeatably verified today (`cargo nextest run -p
  meridian-streams`, part of the normal suite, no `--ignored`/root/netns needed).
- Deliberately did **not** add a scheduled/`workflow_dispatch` CI job for this rig (unlike task 10.13's
  own precedent) given both `run` and `probe` would currently fail every scheduled run for the reasons
  above, and a concurrently-landing sibling task (10.14) already opened a CI workflow for its own,
  overlapping soak-test finding — adding a second permanently-red job right now seemed likely to add
  noise rather than signal. Recommended as a fast-follow once either upstream gap closes, or as a
  deliberately-expected-red job if the team wants that signal sooner.
