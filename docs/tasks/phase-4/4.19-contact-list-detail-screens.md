# 4.19 — Contact list + add-contact + contact detail

**Phase:** 4 — Verification & Trust + Terminal TUI Client · **Feature:** T17 — Terminal TUI Client · **Depends on:** 4.3, 4.6, 4.15, 4.17 · **Status:** done

## Goal
Land the first T17 screens that consume T08's real trust module — the rendezvous point where the two
phase tracks (T08's core, T17's client) converge.

## Scope
- **In:** Contacts pane (add by pasting an `mrd1:` ID or importing a QR image, via 4.6's petname
  assignment — never populated from the wire), trust-state glyph + label display (never color alone),
  filter/search; Contact detail screen (trust state, key history, per-contact relay-policy override,
  petname, block/delete).
- **Out:** the Verify screen (4.22, reached from here via `^V`/`v` but implemented separately); chat
  content (4.20).

## Deliverables
1. `apps/tui/src/screens/contacts.rs`, `apps/tui/src/screens/contact_detail.rs`.
2. Screen-snapshot tests at 80×24 and narrow width; a test asserting the key fingerprint is shown
   alongside the petname wherever a spoofed display name could mislead (security rule 2 of
   [tui-client.md §6](../../architecture/tui-client.md#6-security--privacy-rules-binding)).

## Status
Done — the convergence point of Phase 4's two tracks. `apps/tui/src/screens/contacts.rs` (Contacts
pane: list/filter, add by pasted `mrd1:` id or QR-image import) and `contact_detail.rs` (trust state,
key history, petname, per-contact relay-policy override, block/delete) consume T08's real trust module
(`meridian_core::trust::TrustStore`, task 4.3/4.6) for the first time. Petname assignment mirrors
`apps/cli/src/contact.rs::cmd_add`'s discipline exactly — only ever from explicit user input, never
from the parsed id or QR payload. Trust state renders as glyph + label always paired (never color
alone, tui-client.md §6 rule 2), with a dedicated test proving the key fingerprint (truncated pubkey
hex, matching `trust.rs`'s own display convention) appears alongside the petname wherever a spoofed
display name could mislead. `ContactEntry` joins trust-critical fields from `TrustStore` (including
`PinnedKeyChanged`/`user_blocked`, which the TUI-local `ContactRecord`'s narrower `TrustLabel` enum
structurally cannot represent) with TUI-only display fields from task 4.15's sealed store.

**Review (combined `reviewer`, as named) — one round of real findings, fixed and re-confirmed clean:**
- **Blocking (correctness/security):** the add-contact completion path hard-coded every newly-added
  contact as freshly `Pinned` with a fabricated single-entry key history, assuming a genuine first
  `TrustStore::observe`. Since this task's own `DeleteContact` only ever removes the *local* display
  row (leaving `TrustStore`'s real record — including any `Blocked`/`PinnedKeyChanged` state — intact
  by design, no `TrustStore::remove` primitive exists), a user deleting and re-adding a contact that
  was mid key-change-incident would see it silently rendered as freshly-trusted, hiding the live
  incident. Fixed: the add-contact effect's outcome now carries the real post-`observe` trust state,
  block flag, and full key history for the screen to display truthfully; a re-add guard checks for an
  already-known pubkey before ever dispatching the add effect and routes to the existing contact's real
  detail instead. Reviewer independently confirmed the fix is load-bearing by reverting it locally and
  watching four of the five new regression tests fail.
- **Minor:** the delete-confirmation prompt didn't disclose that trust state and key history survive
  deletion and resurface on re-add — copy tightened to say so explicitly.

`cargo test -p meridian-tui` (`screens_contacts.rs` grew from 32 to 51 tests during review), `cargo
test -p meridian-core --lib trust`, `cargo test -p meridian-cli --bins`, `cargo fmt --check`, `cargo
clippy --workspace --all-targets -- -D warnings`, and `bash tools/lint-tui-no-cli.sh` all clean.
