# 12.16 — Desktop signed release + updater pipeline

**Phase:** 12 — Browser & Desktop Clients · **Feature:** T11 · **Depends on:** 12.15, 12.3 · **Status:** done

**User surface:** none directly (release/CI infrastructure) — no in-app behavior for a client to render,
same class of exemption as ADR 0022/0023's own "No TUI surface" notes.

## Goal
Implement [ADR 0027](../../adr/0027-desktop-signed-updates.md): wire `tauri-plugin-updater` with a
bundled Ed25519/minisign-style public key, add a CI release-pipeline step signing each desktop artifact
with a CI-held private key, and prove the app's own updater rejects a tampered/missing signature —
satisfying the feature spec's acceptance criterion ("desktop updater rejects an unsigned/tampered update
in test") without OS-trusted Authenticode signing (deliberately still deferred per the ADR).

## Scope
- **In:** `tauri signer generate` (run once, private key stored as a `TAURI_SIGNING_PRIVATE_KEY` GitHub
  Actions repo secret per ADR 0027's decision); `apps/desktop/tauri.conf.json`'s updater-plugin config
  with the bundled public key; a release-pipeline signing step (extending `.github/workflows/
  release-binaries.yml` or a new desktop-specific workflow, mirroring ADR 0022/0023's rolling-release
  pattern where applicable); an acceptance test driving an update with a tampered/missing `.sig` sidecar
  and asserting the app rejects it.
- **Out:** OS-trusted Authenticode/notarization signing (explicitly deferred, ADR 0027 R1); any change
  to the update *content* delivery mechanism beyond what Tauri's updater plugin provides out of the box.

## Deliverables
1. `apps/desktop/tauri.conf.json` — updater plugin config with bundled public key.
2. Release-pipeline signing step (workflow YAML).
3. `apps/desktop/tests/updater_rejects_tampered.rs` — the acceptance test.

## Risks / notes
The signing private key is real, security-load-bearing CI infrastructure (ADR 0027 R2) — treat it with
the same care as any other repo secret; do not print it in logs, do not add a debug path that could echo
it. Confirm the ADR's residuals (R1: MSI itself still unsigned at the OS level; R2: standing CI-secret
risk) are documented in whatever operator-facing release doc already covers ADR 0022/0023 (likely
`docs/operations/release-binaries.md`), not silently left undocumented.

## Tests
`cargo test -p meridian-desktop --test updater_rejects_tampered`.

## Reviews
**reviewer** (combined pass: security-reviewer lens — mandatory, signing-key handling and an
auto-apply update path are exactly the kind of surface CLAUDE.md requires review before touching;
architect lens — confirms exact ADR 0027 conformance; code-reviewer lens for the pipeline/config diff
itself).

## Outcome
Wired `tauri-plugin-updater` into `meridian-desktop` (registered as a plugin only — no `.check()`/
`.download()` call anywhere in production code, no new WebView IPC permission granted). A new
`.github/workflows/release-desktop.yml` builds and signs each desktop artifact, referencing
`TAURI_SIGNING_PRIVATE_KEY`/`TAURI_SIGNING_PRIVATE_KEY_PASSWORD` only via `${{ secrets.* }}`
interpolation — never hardcoded, echoed, or written to an uploaded artifact.

**Deliberately did not generate a real production signing keypair or touch any real GitHub secret** —
that is a human-operator decision requiring real repo-admin access, out of scope for an autonomous
agent session. `apps/desktop/tauri.conf.json`'s bundled `pubkey` is a clearly-labeled placeholder
(`TODO_CONFIRM__REPLACE_WITH_REAL_PRODUCTION_PUBLIC_KEY__...`), confirmed harmless at both compile time
and runtime (parsed lazily only inside signature verification, never eagerly at plugin setup — a
mismatched/invalid pubkey fails closed, never silently trusts an update). The acceptance test
(`apps/desktop/tests/updater_rejects_tampered.rs`) uses its own local, test-only Ed25519/minisign
keypair, clearly labeled and never referenced outside that one file. `docs/operations/release-binaries.md`
§4 documents both ADR 0027 residuals (R1: installer still OS-unsigned; R2: standing CI-secret risk) and
states explicitly that a human operator must generate the real keypair and set the real secrets before
this pipeline can sign an actual release.

The combined review (security-reviewer + architect + code-reviewer) returned **PASS** on all three
lenses, zero blocking findings, after independently verifying — against the actual vendored `tauri-cli`
source, not just the implementer's claim — that the sign step genuinely fails closed on an empty/missing
secret (an empty private-key string fails to parse as a valid minisign secret-key box, propagating an
error that `set -euo pipefail` turns into a failed CI step), and that the acceptance test drives the
REAL `tauri_plugin_updater::Updater::check()` → `Update::download()` path via `tauri::test::mock_app`
against a local `axum` mock server — not a hand-rolled crypto stub. 4/4 tests passing (missing signature,
tampered signature, correctly-signed accepted, and an unrequested-but-valuable fourth case: signature
from an unrelated key correctly rejected). `cargo tree -p meridian-rendezvous` confirmed the
server-no-core invariant is untouched despite new workspace dependencies.
