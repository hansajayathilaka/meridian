# 4.16 — Onboarding screen

**Phase:** 4 — Verification & Trust + Terminal TUI Client · **Feature:** T17 — Terminal TUI Client · **Depends on:** 4.14, 4.15 · **Status:** done

## Goal
Take a user with no account on disk from nothing to a registered, published identity — the first thing
a new `meridian tui` run shows, and the start of the acceptance demo's walkthrough.

## Scope
- **In:** keystore choice (OS keychain / passphrase-wrapped file) → org hint → keypair generation via
  `meridian-identity` → `mrd1:…@domain` ID + in-terminal QR render → rendezvous registration + prekey-
  bundle publish, all through `meridian-core`/`meridian-identity` (no new protocol logic — every
  capability already exists per the design doc's opening rule).
- **Out:** unlock (4.17, the returning-user path); any T08 verification screen content.

## Deliverables
1. `apps/tui/src/screens/onboarding.rs`: screen states + transitions.
2. Screen-snapshot tests (`TestBackend`) at 80×24 and a narrow width, for each onboarding sub-step.

## Tests
`cargo nextest run -p meridian-tui --test screens_onboarding`

## Reviews
- **reviewer** (combined) — orchestrates existing core capability, no new security surface.

## Status
Done. `apps/tui/src/screens/onboarding.rs` implements the full mermaid sub-step sequence (`ChooseStore
→ OrgHint → Generate → ShowIdentity → Register → PublishBundle → done`) as a pure, synchronous state
machine — `App::update`/`render` stay I/O-free throughout (Elm architecture, tui-client.md §4);
everything that touches the network or a `SecretStore` (account generation, register, publish) is
requested via new `Effect` variants (`GenerateAccount`, `Register`, and a payload added to the
existing `PublishBundle` placeholder) for a future worker to execute — none of the real
`meridian-identity`/`meridian-signaling` calls are made from this pure layer itself. `Screen::Onboarding`
takes full ownership of its own key handling (including `Esc`, since nothing exists beneath it on a
first run); completion lands on the existing `Screen::Placeholder` as an explicitly-commented stand-in
for `Main`, which doesn't exist until 4.19/4.20+. QR rendering (`meridian_core::identity::
render_terminal`) is called inline from `handle_worker`, confirmed genuinely I/O-free by reading its
implementation directly.

**Review (combined `reviewer`, as named) — one round of real findings, fixed and re-confirmed clean:**
- **Blocking (security/correctness):** `ChooseStore.passphrase` — the live file-store passphrase the
  user is mid-typing — derived a plain, unredacted `Debug`, unlike its sibling `StoreChoice`'s
  hand-rolled redacted one. Since `ChooseStore` nests inside `OnboardingState`/`Screen`/`App` (all
  `derive(Debug)`), any `{:?}` dump during passphrase entry — including this codebase's own
  `panic!("{other:?}")` test idiom, used throughout `screens_onboarding.rs` itself — would print the
  raw passphrase in cleartext, contradicting the mermaid diagram's own binding "never rendered"
  invariant for secrets. Fixed with a hand-rolled `Debug` impl mirroring `StoreChoice`'s (unconditional
  `"<redacted>"`, not state-dependent), plus a regression test asserting a real, non-trivial passphrase
  never appears in the `{:?}` output.
- **Non-blocking, also fixed:** two tests named `*never_shows_raw_key*` asserted only presence, no
  negative check — renamed with honest doc comments (there's no private-key value in scope to compare
  against in this pure-UI layer, so the property they actually verify is structural, not render-time);
  added a missing empty-org-hint rejection test; documented the deliberate invite-token drop on a
  publish-failure back-navigation (avoiding a double-redeem on retry); documented `account_pub` as the
  intended worker-side `SignalingClient`-cache key across the `Register`/`PublishBundle` effect split.

Reviewer independently confirmed the redaction is unconditional (not just conditional on
`entering_passphrase`), traced every render path to confirm no other passphrase-leak route exists, and
confirmed no test assertion was weakened by the renames. `cargo test -p meridian-tui` (27 tests in
`tests/screens_onboarding.rs`, up from the original 25, plus the full existing suite), `cargo test -p
meridian-cli --bins`, `cargo fmt --check`, `cargo clippy --workspace --all-targets -- -D warnings`, and
`bash tools/lint-tui-no-cli.sh` all clean.
