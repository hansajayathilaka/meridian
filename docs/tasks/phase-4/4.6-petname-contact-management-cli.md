# 4.6 — Petname assignment + contact management CLI

**Phase:** 4 — Verification & Trust + Terminal TUI Client · **Feature:** T08 — Verification & Contact Trust · **Depends on:** 4.3 · **Status:** in progress

## Goal
Land petname assignment as a strictly local, wire-never operation, with a CLI surface to manage
contacts — the reference implementation the TUI's contact list (4.19) builds on.

## Scope
- **In:** `meridian contact add/list/rename/block`; petnames are assigned only by explicit local user
  input, never populated from a QR payload, an `mrd1:` ID, or any wire field ([system-design §3.1](../../architecture/system-design.md)).
- **Out:** directory-attestation petname *suggestions* (4.8, which layers provenance-not-authority on
  top of this); the TUI's Add Contact screen (4.19).

## Deliverables
1. `apps/cli/src/contact.rs` (or equivalent): `add/list/rename/block` subcommands over `trust.rs`.
2. Test: adding a contact whose QR/ID payload contains a name-like string never populates `petname` —
   only an explicit `--petname`/prompt input does.

## Risks / notes
- This is a threat-model invariant (display names are never taken from the wire), not a style
  preference — a spoofed "petname" arriving via any wire path is exactly the kind of thing a malicious
  peer or server would try.

## Tests
`cargo nextest run -p meridian-cli --test contact_mgmt`

## Reviews
- **security-reviewer** — required; petnames-never-from-wire is a threat-model invariant, and this task
  is where it's first enforced in code.
