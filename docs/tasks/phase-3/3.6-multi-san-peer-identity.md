# 3.6 — Accept-side peer identity must consider all authenticated SANs

**Phase:** 3 — Review of Phase 2 · **Feature:** review fix (F9) · **Depends on:** 3.4 (sequence after 3.2/3.3 — same file) · **Status:** done

## Goal
A partner with a multi-SAN cert must not be false-rejected by an allowlist, and rate-limit keys must
not shift across cert renewals.

## Scope
- **In:** carry all validated SANs on `FederationLink`; `admit` / limits match against the set with a
  deterministic tie-break for the metering key. **Or** the documented alternative — enforce "exactly
  one SAN" at accept time with a clear error. Pick one and record why.
- **Out:** the dial side (already pins `expected_domain` correctly).

## Deliverables
1. `apps/rendezvous/src/federation/link.rs` (L452) — `peer_domains: Vec<String>` + a stable
   `metering_key()`.
2. `apps/rendezvous/src/federation/inbound.rs` — the L86/L164/L232 consumers updated.
3. `apps/rendezvous/tests/federation_mtls.rs` — a multi-SAN cert whose **non-first** SAN is
   allowlisted is admitted; SAN reordering does not change the metering key.

## Risks / notes
- The set-match must not admit a domain the cert does not authenticate — the fail-closed direction
  must not invert. This is the single assertion security-reviewer should focus on.
- Today's behaviour is fail-**closed** (false-reject), so this is an availability fix, not a hole
  being closed; do not overstate it.

## Outcome
Took **Option 1** (carry all validated SANs, deterministic metering-key tie-break) over the
"reject multi-SAN certs" alternative — domain-migration/aliasing via multi-SAN certs is a
legitimate real-world pattern, and today's bug is a false-reject (availability defect, not a
hole), so the fix restores availability rather than trading one availability problem for another.

`FederationLink::peer_domain: String` → `peer_domains: Vec<String>` — on accept, the full
validated SAN/CN set from `peer_identities()`, never `identities[0]` alone; on dial, unchanged
(a single-element vec of the already-pinned `expected_domain`, out of scope, already correct).
New `FederationPolicy::admit_any` checks the allowlist against the whole set (superset match) —
`admit` itself (dial side) untouched. New `FederationLink::metering_key()` picks the
lexicographically-smallest SAN as a single, deterministic rate-limit bucket key, stable across SAN
reordering as long as the SAN values themselves don't change. Authorization (`admit_any`, full
set) and metering (`metering_key`, one deterministic value) are kept structurally separate —
neither influences the other.

**Review (security-reviewer + architect + code-reviewer, combined pass): clean, zero findings.**
Traced the fail-closed invariant end to end: `peer_domains` on the accept side is populated
exclusively from the mTLS-validated cert (`peer_identities`), never from `exchange_hello`'s
self-asserted `FedHello.domain` at any point in the chain from `finish_handshake` through
`serve_link` to the handlers; `admit_any`'s allowlist check is a genuine any-match, never a
subset/inverted check, and normalizes identically to `admit`. Architect confirmed no contradiction
with ADR 0017(a) — the dial side's existing any-match belt-and-suspenders check already used this
same shape; this task generalizes it to the accept side, no companion ADR note needed. Test
quality confirmed non-vacuous: the new non-first-SAN-allowlisted test explicitly demonstrates
first-SAN-only matching would have wrongly rejected; the SAN-reordering test mints two real certs
with identical SAN values in opposite orders via the shared harness's new `TestCa::issue_multi_san`
and asserts equal `metering_key()`.
