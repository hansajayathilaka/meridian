# 8.9 — TTL expiry purge job

**Phase:** 8 — Offline Ciphertext Mailbox · **Feature:** T07 · **Depends on:** 8.1, 8.2 · **Status:** done

## Goal
Prove expired envelopes are provably purged, not merely excluded from queries — the acceptance
criterion the feature spec names explicitly.

## Scope
- **In:** a background interval task in `apps/rendezvous` calling `Store::mailbox_purge_expired`
  on a fixed cadence (config-surfaced interval, sane default — e.g. hourly), started alongside the
  server's other background tasks (TURN credential cleanup, rate-limiter window rotation, or
  whatever precedent already exists for a periodic server-side task — follow that pattern rather
  than inventing a new task-spawning convention).
- **Out:** no change to enqueue-time TTL computation (8.5/8.6 already set `expires_at` at insert
  time); no per-request purge-on-read (that would be a different, also-valid design, but the
  feature spec's "test advances clock" framing implies a scheduled sweep, not lazy purge-on-access
  — confirm this reading against the feature spec before implementing, and record the choice if the
  alternative was live at plan time).

## Deliverables
1. The purge interval task, wired into server startup.
2. Test: enqueue a row, advance a fake/injectable clock past `expires_at`, run one purge cycle,
   confirm the row is gone via `mailbox_list_for_recipient` returning empty **and** (for the sqlite
   backend) a direct row-count query — proving actual deletion, not just a query-time filter masking
   a still-present row.

## Risks / notes
"Provably purged" means the test must demonstrate the row is physically gone, not merely that
`mailbox_list_for_recipient` happens to filter on `expires_at` at read time (which would satisfy a
weaker, wrong reading of the acceptance criterion while leaving stale ciphertext on disk
indefinitely — a real ADR 0007 violation, since the TTL promise is about server-side data lifetime,
not query visibility).

## Tests
`cargo nextest run -p meridian-rendezvous --test mailbox_purge`

## Reviews
- **security-reviewer** — confirms the test proves physical deletion, not query-time filtering
  (this is the one place a subtly wrong implementation would look correct under casual testing).
- **test-engineer** — clock-injection correctness, non-vacuity.

## Status
**Done.** New `apps/rendezvous/src/mailbox_purge.rs`: `run_purge_once(state, now)` (a thin,
clock-injectable wrapper over 8.1's `Store::mailbox_purge_expired`) and `purge_loop(state)` (a
`tokio::time::interval`-driven loop on `config.mailbox.purge_interval_secs`, new config field,
default hourly, `TODO: confirm` since no cadence appears in the design docs). Wired into
`main.rs` via `tokio::spawn`, following the federation-accept-loop's existing precedent for a
long-running background task; a single purge-pass failure doesn't kill the loop.

Two new tests (`apps/rendezvous/tests/mailbox_purge.rs`) prove "provably purged," not just
query-time-filtered, per this task's central risk: an in-memory case (before/after the deadline,
via `mailbox_list_for_recipient`) and a SQLite case using a **second, independent** `sqlx`
connection to the same on-disk file running a raw `SELECT COUNT(*)` before and after — physical
deletion, confirmed from outside the store's own view. `mailbox_list_for_recipient`'s SQL has no
`expires_at` predicate of its own (verified in `store.rs`/`store/sqlite.rs`), so the purge job is
structurally the sole enforcement point, not merely by convention.

Doc-synced a pre-existing gap found along the way: `[mailbox]` had never been added to
`rendezvous.example.toml` or `rendezvous-protocol-v1.md` §5's config-surface example since task
8.1 introduced the section — three tasks (8.1's `ttl_days`/`quota_mb` plus this task's
`purge_interval_secs`) were undocumented there. Fixed, and locked in with a new regression test
(`example_toml_parses_and_documents_every_mailbox_field`) that loads the real example file through
`Config::load`.

**A genuine pre-existing test-isolation gap surfaced and was fixed along the way:** adding two new
`Config::load`-based tests exposed that `mailbox_ttl_days_zero_round_trips_through_config_parsing`
(landed in task 8.1) called `Config::load` — which always merges process env vars — without
acquiring this test module's `ENV_LOCK` mutex, so it could read pollution from a concurrently
running `EnvGuard`-holding test. Fixed by adding the same `EnvGuard::set(ENV_LOCK.lock().unwrap(),
&[])` pattern every other `Config::load`-calling test in the file already uses.
