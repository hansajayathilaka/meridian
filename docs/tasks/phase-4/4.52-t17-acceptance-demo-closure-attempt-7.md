# 4.52 — T17 acceptance-demo closure (seventh exit-gate attempt)

**Phase:** 4 — Verification & Trust + Terminal TUI Client · **Feature:** T17 — Terminal TUI Client (gap closure, phase re-exit gate) · **Depends on:** 4.51 · **Status:** in progress

## Goal
Mirror 4.28's, 4.38's, 4.41's, 4.45's, 4.48's, and 4.50's role a seventh time: run the T17 demo script
live, end to end, for both account types — and, **only if it genuinely passes**, flip Phase 4's
exit-criteria checkbox and clear the tracker's carry-forward note.

## Scope
- **In:** a live PTY run of the full demo script from
  [17-terminal-tui-client.md](../../architecture/features/17-terminal-tui-client.md)'s "Working output"
  (unchanged since 4.48's own corrected version), for a **file-backed** account and an **OS-keystore**
  account, covering every step every prior attempt already covered, with particular focus on the two
  directions 4.51's fix touches:
  1. onboarding → registered → bundle published → `Screen::Main`, both account types;
  2. **the specific defect this attempt re-verifies**: an OS-keystore initiator sends a first-contact
     message to a file-backed responder and it is received **reliably and promptly** — repeat this
     specific direction across **at least 10 fresh two-peer trials** (mirroring 4.50 Run 2's own
     ~15-trial evidentiary bar, and 4.51's own Deliverable 6 bar), each timed and reported individually,
     not averaged away. A single passing trial does **not** clear this gate — the defect this attempt
     exists to re-verify was itself non-deterministic (silent or 70 s–260 s across ~15 trials), so a
     small trial count would not distinguish "fixed" from "got lucky." Also re-confirm the reverse
     direction (file-backed sender → OS-keystore responder) stays reliable, unchanged;
  3. responder sees the message request (key + safety number + intro) and accepts;
  4. responder opens a chat with the accepted sender and confirms the sender's original intro message is
     present in the transcript (4.42's/4.49's fixes, re-confirmed), then replies;
  5. `n`/`v` shows the same 60-digit safety number on both sides → mark verified on both, including a
     **file-backed account's own `run_mark_verified` call, timed** (4.43's/4.50's own recorded ~3.4 s
     latency finding — confirm whether 4.51 closed it, and if so, that the improvement is real and
     locally re-measured, not merely claimed);
  6. restart both peers (`pkill` + relaunch) and confirm contact list, petnames, full history including
     the original intro message with no duplicate, and the ratchet session are all restored with no
     re-handshake;
  7. `meridian tui --export-json <path>` + `jq '.contacts[0].petname' <path>/contacts.json` returns
     `"bob"`.
  Also: record the file-backed session-start latency and, if 4.51 closed it, the `run_mark_verified`/
  `run_set_petname` latency, and compare both against every prior attempt's own recorded numbers — a
  regression is a failure of this gate even if every functional step passes. Re-run the standing
  regression set every prior attempt held itself to: `cargo test -p meridian-tui --all-targets
  --no-fail-fast`, `cargo test -p meridian-cli --bins`, `cargo test -p meridian-tui --test
  live_session_e2e --test live_session_file_backed --test republish_bundle`, `bash
  harnesses/mitm-sim/run.sh` (T08 regression), `bash tools/lint-tui-no-cli.sh`, `bash
  tools/check-docs.sh`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo fmt --check`,
  plus 4.51's own new targets.
  Hold to the **two-independent-runs discipline** every prior attempt used — implementer once,
  `reviewer`/`test-engineer` once, independently. **Not relaxed: six exit-gate attempts in a row have
  each found a real defect this exact way** (4.28, 4.38 [two defects], 4.41, 4.45, 4.48, 4.50), and this
  is now the sixth genuine functional/reliability defect the discipline has caught across those attempts
  — there is no basis in this project's own track record for treating a seventh pass as more likely to
  be clean than the prior six, and doing so would be exactly the kind of complacency this discipline
  exists to prevent.
- **Out:** any new feature code; fixing anything newly found live here. **If a genuine defect surfaces,
  report it honestly in this task's own Status section, do not fix it here, file a new task (working
  number 4.53), and leave both the exit-criteria checkbox and the carry-forward note open** — the same
  non-negotiable rule every prior attempt held. Never weaken an assertion (this task's own, or any prior
  task's) to make the demo appear to pass. In particular: **do not shrink the ≥10-trial bar in Scope
  point 2** to make a pass easier to obtain — if trials are flaky, that flakiness is itself the finding.

## Deliverables
1. This task file's own **Status section** with live-run evidence (condensed chronological transcripts,
   command output, timings, and the full per-trial timing table for Scope point 2's ≥10 trials) at the
   same evidentiary bar every prior attempt set — including an explicit, named statement of anything that
   had to be narrowed and why.
2. **Only if the demo genuinely passes:** a new `docs/architecture/tui-client.md` §13 documenting this
   attempt (§10–§12 stay frozen as historical record, per the existing convention);
   `docs/tasks/phase-4/README.md`'s T17 exit-criteria checkbox flipped; `docs/tasks/README.md`'s
   carry-forward note cleared and ▶ NOW/NEXT advanced to `/start-review-phase` for Phase 5.
3. Any residual coverage gap not closed by 4.51's own new tests, named explicitly rather than silently
   absorbed or silently dropped — in particular, honestly report whether 4.51's own investigation left
   any part of the 70 s–260 s range unexplained (per that task's own Deliverable 4), and whether that
   residual is acceptable to pass this gate on or not.

## Risks / notes
- **Hard join on 4.51 only** — a single-dependency join, mirroring 4.50's own single-dependency join,
  since this wave has exactly one fix task.
- **Reuse the accumulated methodology from every prior attempt instead of re-deriving it** (full detail
  in those tasks' own Status sections): OS keystore setup, the initiator-role trap, a screen-scraping
  driver parsing narrow single-line anchors, both peers running **concurrently**, distinguishing driver
  bugs from product defects before reporting anything, and — new for this attempt — 4.50 Run 2's own
  fix for a scratchpad `$HOME` path over 108 bytes silently truncating/colliding the keyring's AF_UNIX
  control-socket bind (use a short `$HOME`).
- Nothing from the driver needs to be checked in — but the transcripts quoted in Status must be real
  output, not reconstructed.
- **Definition of Done gate 9:** no new TUI surface — this is a verification task (stated explicitly),
  unless 4.51 itself added a status affordance, in which case confirm it renders correctly live rather
  than re-scoping it here.
