# 1.28 — Active relay-rewrite adversarial test (rendezvous `test-tamper-hook` extension)

**Phase:** 1 — Review of Phase 0 · **Feature:** on-the-fly (open coverage gap, not a numbered finding) · **Depends on:** — · **Status:** **done** — security-reviewer APPROVE-WITH-CHANGES; all 5 required changes applied

## Goal
Prove, adversarially, that a malicious/compromised rendezvous *actively rewriting* a routed P2P
signaling blob (not just substituting a `Fetch` bundle) cannot get past DTLS-fingerprint binding — closing
an open note left by `apps/core/src/session.rs`'s module doc and `harnesses/mitm-sim/run.sh`, both of
which currently point at a stale task number ("1.16"/"1.23") for this gap.

## Scope
- **In:** extend `meridian-rendezvous`'s `test-tamper-hook` feature (currently only substitutes `Fetch`
  bundle responses, per 1.12) to also support rewriting a *routed* blob in transit; a harness test driving
  a real `dial`/`answer` P2P session establishment through a tampering rendezvous, asserting the rewrite
  is detected and the session establishment fails closed (fingerprint mismatch), never silently accepts a
  substituted offer/answer.
- **Out:** any production (non-`test-tamper-hook`) code path; this is adversarial test infrastructure
  only, gated the same way as the existing `Fetch`-substitution tamper hook (dev-only feature, never
  enabled in the release `meridian-rendezvous` binary).

## Deliverables
1. `test-tamper-hook` extended to rewrite routed blobs.
2. A harness test (likely alongside `harnesses/mitm-sim/`) proving the rewrite is caught, fail-closed.
3. Doc-sync: repoint `apps/core/src/session.rs`'s module doc and `harnesses/mitm-sim/run.sh`'s stale
   "1.16"/"1.23" references to this task.

### What landed
- **`apps/rendezvous/src/auth.rs`** — `rewrite_routed_blob()`, `#[cfg(feature = "test-tamper-hook")]`:
  flips one byte at `len()/2`, inside the ratchet ciphertext for any realistic envelope.
- **`apps/rendezvous/src/config.rs`** — `Server::allow_test_route_tamper` (default `false`), an
  *additional* runtime gate on top of `allow_test_tamper`. Kept separate on purpose: the documented
  `fetch-bundle --tamper` bundle-substitution demo must keep working without every routed envelope
  also being corrupted.
- **`apps/rendezvous/src/ws.rs`** — `handle_route` rewrites the outbound blob only under the cargo
  feature **and** both runtime flags. It still never *inspects* the blob, only mutates opaque bytes —
  which is all a real relay can do.
- **`apps/cli/tests/relay_rewrite.rs`** (new) — a real in-process `meridian-rendezvous`, two peers with
  real `SignalingClient`s over real sockets, `LoopbackFabric` for the data path, a real `dial`/`answer`.
- **`harnesses/mitm-sim/run.sh`** — runs the new test; its stale "tracked for 1.28" note is now a
  statement that the gap is closed.
- **`apps/core/src/session.rs`** module doc — repointed off the stale `TODO: 1.28`.

### Result
```
[1.28] hostile relay → dialer: StillWaiting / responder:
       Rejected("crypto/envelope error: envelope signature verification failed")
```
Both asserted properties hold: **fail-closed** (neither side establishes) and **detected** (a side
rejects explicitly, with a reason). The control case through an honest relay establishes on both sides,
so the adversarial assertion cannot pass vacuously on unrelated breakage.

**A first version of this test hid the detection.** It wrapped both sides in one combined timeout and
reported only `timed out` — because the responder rejects immediately but the dialer then waits for an
answer that never comes, so the join always hit the timeout. Timing each side independently was needed
to observe that the rewrite is genuinely *detected* rather than merely absorbed into a stall.

### F17 gating, verified structurally
A `nm` symbol check was tried first and was **inconclusive** — the symbol count was 0 with the feature
*on* as well (inlined away), so it would have reported "absent" either way. The check that actually
demonstrates the property is feature resolution:
```
cargo tree --workspace -e normal     -f "{p} {f}" → meridian-rendezvous ... default
cargo tree --workspace -e normal,dev -f "{p} {f}" → meridian-rendezvous ... default,test-tamper-hook
```
So a normal/release workspace build never activates the hook, while `cargo test` does. Resolver 2 is
what keeps dev-dependency features out of the normal graph.

### Acknowledged coverage gaps (recorded, not folded in)
1. **A byte flip breaks the Ed25519 envelope signature**, so rejection happens at the *signature*
   check — the ratchet AEAD and the §4.6 DTLS-fingerprint cross-check are never reached on this path.
   An earlier draft of the code comment claimed a byte-level rewrite is "the strongest attack a real
   relay actually has". **That was false and has been corrected.** A relay also has replay, reorder,
   drop, and cross-delivery — none need key material, all would *pass* the signature check, and all
   probe deeper into the ratchet. Exercising those is a genuine follow-up; it is out of this task's
   deliverable, which is specifically an in-transit *rewrite*.
2. **The dialer has no timeout awaiting an answer**, so a hostile relay can hang it indefinitely with
   no diagnostic. Fail-closed (no session, nothing downgraded) and inside threat-model goal 6's
   conceded "a malicious server can deny service", but poor diagnostics. Not fixed here — 1.28's scope
   is adversarial test infrastructure, not production timeout behaviour.

## Review outcome — security-reviewer: APPROVE-WITH-CHANGES (all 5 required changes applied)

The review confirmed the gating is structurally sound and that no "must never" invariant is violated
(the hook mutates opaque bytes without parsing them; `lint-no-serde-on-blob` is neither tripped nor
weakened; goal 1's property is *detectability*, not immutability, so simulating a modification is the
correct way to test it). It also found five required problems. Each is fixed:

**F-D (HIGH) — the most valuable finding: 1.12's existing compile-gate guard had NEVER run in CI.**
`tamper_flag_is_inert_without_feature` is `#[cfg(not(feature = "test-tamper-hook"))]`, but resolver-2
feature unification turns that feature **on workspace-wide** whenever dev targets are built, because
`apps/cli/Cargo.toml`'s dev-dependency pins it. CI's only rendezvous test invocation was
`cargo test --workspace`, so the guard was compiled out — the only evidence for F17 was a one-time
manual `nm` recorded in a task file. Fixed by:
- a new CI step `cargo test -p meridian-rendezvous` (default features), the only invocation under
  which these guards execute — verified locally: `route_tamper_is_inert_without_feature ... ok` and
  `tamper_flag_is_inert_without_feature ... ok`;
- `route_tamper_is_inert_without_feature` (both flags `true`, no feature → byte-identical delivery);
- `route_tamper_requires_its_own_flag_not_just_allow_test_tamper` (feature ON, `allow_test_tamper =
  true` + route flag `false` — the exact `demo.toml` configuration, previously unverified);
- a CI step asserting `test-tamper-hook` is not active in a **normal** build, checked by feature
  *resolution*. The reviewer's optional `nm`-symbol suggestion was **declined and replaced**: measuring
  it showed the symbol is absent from an optimised build whether the feature is on or off, so that
  check can never fail. A check that cannot fail is not a gate (cf. F4/F18). The resolution check was
  verified sensitive in both directions (`-e normal` → `default`; `-e normal,dev` →
  `default,test-tamper-hook`).

**F-C (HIGH) — the test could pass while the property was broken.** It accepted a rejection from
*either* side with *any* non-empty message. If the hook became inert and an unrelated signaling
regression made the dialer fail with `Relay(..)`/`SignalingEnded`, both assertions would pass: green
test, untested property — and the control case cannot catch it, since it runs against an honest server.
Fixed by pinning the outcome: the **responder** must reject with `SessionError::Chat(_)`
(envelope-authentication class), and the dialer must be `StillWaiting` **or** an envelope error, never
a bare relay/transport error. Matched on the variant, not the message, so it survives ADR 0016 moving
the detector from the signature to the ratchet AEAD. Now reports
`Rejected(Chat(BadSignature))` explicitly.

**F-A (HIGH) — false security claim in a code comment.** I had already softened "a byte-level rewrite
is the strongest attack a real relay actually has", but the review supplied the correct framing, now
adopted: it is the *cheapest* attack, and the byte flip is *provably* incapable of reaching deeper —
`MessageEnvelope` has four fields and `signing_input` covers `sender_pub + prekey + ct` with `sig` the
remainder, so every byte is either signed or is the signature and any mutation must fail CBOR decode or
`verify`. Reaching the AEAD by mutation is therefore an **impossibility for this server**, not a gap.
The review also identified strictly stronger relay attacks I had not enumerated: `substitute_bundle`
itself (the server ends up holding real ratchet state with both peers) and a **forged `Deliver.from`**,
which the server asserts itself and can forge for free.

**F-B (MEDIUM) — "CLOSED" overclaimed against the task's own goal.** The goal says "cannot get past
DTLS-fingerprint binding", but this path never reaches it — `recv_sdp` errors before
`set_remote_description` and `verify_fingerprint`. `harnesses/mitm-sim/run.sh` no longer claims the gap
is closed; it states the rewrite is stopped at envelope authentication, *earlier* than §4.6, that no
test has a hostile relay cause §4.6 to fire, and that none can by mutation. Also repointed
`1.15-webrtc-backend.md`'s stale "tracked for 1.23" note, and made the claim discoverable by adding
1.28 to the **A2 row** of `threat-mitigation-matrix.md` and the mitm-sim line of `testing/strategy.md`.

**F-E (MEDIUM) — the new config field was undocumented.** `allow_test_route_tamper` added to
`docs/api/rendezvous-protocol-v1.md` §5 and `rendezvous.example.toml`, both carrying the three facts an
operator needs: inert without the cargo feature, additionally requires `allow_test_tamper`, and —
unlike `allow_test_tamper` — **no per-request opt-in**, so enabling it corrupts *every* routed blob for
*every* user while still replying `route_ok{delivered:true}`. `demo.toml` states it is deliberately off.
Plus the reworded invariant comment in `ws.rs` ("without ever inspecting, and — outside the cfg-gated
hook — without altering").

The reviewer **confirmed the double gate is correct** and not a footgun (`demo.toml` already ships
`allow_test_tamper = true`, and the new field defaults to `false`), and that the config path is
fail-closed: `#[serde(default)]` with a hand-written `Default` means a typo'd key silently lands on
`false`, and no deserialization path can produce `true` by accident.
